# 작업분해

기획 세션이 만든 **사양서 1장**을 → 개발 세션들이 나눠 가질 수 있는 **표준 작업표**로 쪼갭니다.
"여러 개발자가 규칙에 의해 협의하며 개발"의 현실판 — 협의를 실시간 대화가 아니라 **의존 그래프 문서**로 고정합니다.

## 자동 트리거 (명시 호출 없이도)

사용자가 `/작업분해`를 직접 치지 않아도, **사양서 기반 개발 착수**가 감지되면 개발 세션이 스스로 판정한다. `task-breakdown-reminder.js` 훅이 매 요청에서 상기시킨다.

- **자동 판정 기준(정량)** — 아래 중 **하나라도** 해당하면 코딩 전에 이 명령을 먼저 실행:
  - 수정 예상 파일 3개 이상
  - 데이터베이스 변경 있음 (테이블·컬럼·함수·정책·트리거)
  - 단계(PR)가 2개 이상으로 나뉨
  - 병렬로 나눌 수 있는 조각이 있음
- **미달이면 스킵** — 파일 1~2개·데이터베이스 변경 없음·버그 한 줄이면 작업표 없이 바로 진행.
- **자의적 스킵 금지** — 기준은 "판단"이 아니라 "통과 여부". 규모가 애매하면 관련 코드를 먼저 Read/Grep 으로 확인해 파일 수·데이터베이스 변경을 세고 판정한다. (`memory/feedback_agent_invocation_gaps.md` — 자체 판단 스킵 반복 위반 방지)
- **자동은 「작업표 문서」까지만** — 실제 코딩 착수는 사용자 승인 후. 작업표를 만들어 "이렇게 나눠 하겠습니다" 보고까지가 자동 범위. (2026-07-22 사용자 확정 — 위험한 자동 코딩 방지, `.claude/rules/request-validation.md`)

## 입력

`$ARGUMENTS` = 분해할 사양서 경로(권장) 또는 주제 키워드.
- 경로가 있으면 그 사양서를 읽고 분해.
- 주제만 주면 `docs/specs/` 최근 파일에서 해당 주제를 먼저 찾음(못 찾으면 사용자에게 되묻기).

## 실행 절차 (메인 Claude)

1. **`reverb-planner` 호출** — 아래 「표준 작업표 양식」 그대로 채우라고 지시하며 사양서를 넘긴다.
   - planner는 먼저 `.claude/rules/planning.md` 규칙 A(현재 상태 검증)·규칙 B(반대론자)를 적용해 사양서와 실제 코드가 어긋나지 않는지 확인한 뒤 분해한다.
   - **코드는 수정하지 않는다. 분해 문서만 만든다.**
2. planner 결과를 받아 **표준 작업표 양식**에 맞는지 점검(산출 계약 누락·선결 조건 미기재·사양서 stale 반영 여부 확인).
3. 산출물을 `docs/specs/{YYYY-MM-DD}-{주제}-breakdown.md`로 저장.
4. 사용자에게 **배분 제안**을 요약 보고. 병렬 가능 조각이 2개 이상이면 `AskUserQuestion`으로 "순차 진행 / 세션 나눠 병렬" 확인.
5. **자동 실행 금지** — 이 명령은 분해 문서까지만. 실제 개발 세션 가동은 사용자가 문서를 보고 `/새세션`으로 배분한다.

## 표준 작업표 양식 (planner가 채우는 산출물)

```markdown
# 📋 작업 분해표 — {기능명}
**사양서:** {경로}
**분해일:** {YYYY-MM-DD}
**총 작업 조각:** N개 · **병렬 가능:** X개 · **순차 필수:** Y개

## 🚦 착수 전 선결 조건 (작업표보다 먼저)
(개발 조각을 시작하기 전에 **밖에서 먼저 정해져야 하는 것**. 없으면 「없음 — 바로 착수 가능」 명시)
| # | 선결 조건 | 근거 | 막는 조각 |
|---|---|---|---|
| S0 | (선행 사양서 확정 / 미결 결정 / 외부 승인 등) | (사양서 어느 항목·왜) | (이게 안 정해지면 못 시작하는 작업 번호) |

> 종류: ①**선행 사양서 종속**(다른 사양서가 먼저 확정돼야 함) ②**미결 결정**(사양서 「사용자 확인 필요」 항목) ③**외부 승인·계정·법률**(운영·약관·외부 서비스). 이게 있으면 해당 조각의 「선행」 칸에 S번호를 적는다.

## ⚠️ 사양서 stale 점검 (있으면)
(사양서 작성 후 코드가 앞서가 어긋난 지점. 기획 에이전트가 현재 상태 검증 중 발견하면 여기 명시 → 중복 구현 방지. 없으면 생략)

## 한눈에 보는 의존 순서
(작업 1 → 작업 2 → 작업 3 식의 화살표 그래프. 병렬이면 ∥ 로 표기)

## 작업 조각 표
| 번호 | 제목 | 담당 파일 | 산출 계약 | 선행 | 병렬? | 담당 |
|---|---|---|---|---|---|---|
| 1 | … | … | (다음 작업이 쓰는 테이블·함수·id 이름) | 없음 | — | 개발 |

## 조각별 상세
### 작업 N — {제목}
- **하는 일:** (1~3줄)
- **담당 파일:** (이 조각이 만지는 파일 전부)
- **산출 계약:** (이 작업이 **다음 작업에 넘기는 것** — 테이블명·함수 시그니처·DOM id·i18n 키 등 이름을 그대로 명시. 뒷 작업은 이 이름을 전제로 시작한다)
- **선행 의존:** (어느 작업 다음인지 + 이유)
- **완료 정의:** (기계가 확인 가능하게 — 빌드 통과 / 함수 존재 / "한 건 등록 시 목록 갱신" 같은 관찰 가능 조건)
- **필요 검문소:** (reverb-supabase-expert / reverb-reviewer / reverb-qa-tester 중 필요한 것)
- **주의·롤백:** (데이터베이스 변경 등 위험 조각만 — 실패 시 되돌릴 범위)

## ⚠️ 공유 지점 경고 (충돌 주의)
(여러 조각·다른 기능이 함께 만지는 공용 파일 나열 — admin.js·admin-core.js·index.html·shared.js·build.sh 등. 겹치면 병렬 금지)

## 🧭 배분 제안
(개발 몇 명이 어떤 순서로. 병렬 이득이 없으면 "1명 순차" 명시)
```

## 배분·충돌 가드 (planner·메인 공통 준수)

- **핫스팟 파일은 무조건 순차** — `dev/js/admin.js`·`dev/admin/app.js`·`dev/js/admin-core.js`·`dev/lib/shared.js`·`dev/admin/index.html`·`build.sh`를 두 조각이 동시에 만지면 충돌 100%. 이 파일이 겹치면 병렬 칸을 ✗로. (`.claude/rules/multi-session.md` 핫스팟 규칙)
- **데이터베이스 변경 조각은 한 세션만** — 마이그레이션 번호는 파일 만드는 순간 확정. 병렬 세션이 동시에 만들면 번호 충돌. 데이터베이스 조각은 항상 순차 + 번호 미리 안 박음(생성 시 확정, `.claude/rules/planning.md` 규칙 A).
- **산출 계약이 비면 분해 미완성** — 뒷 작업이 앞 작업 산출물(테이블·함수 이름)에 의존하는데 그 이름이 안 적혔으면, 뒷 작업 에이전트가 추측하다 어긋난다. 이 칸이 이 도구의 핵심.
- **완료 정의는 관찰 가능하게** — "잘 됨" 금지. "빌드 에러 없음 + 목록에 즉시 반영" 처럼 확인 방법을 쓴다.

## 정교함 분기 (과잉 방지)

- **작은 사양서**(파일 1~2개·데이터베이스 변경 없음·조각 1~2개): 표만 채우고 「조각별 상세」는 생략 가능.
- **큰 사양서**(파일 5개+·데이터베이스 변경·병렬 후보): 「조각별 상세」 + 「주의·롤백」까지 전부 채움.
- 사양서를 그대로 베끼지 말 것 — 분해표는 **누가/무엇을/언제·겹침 여부**만. 상세 설계는 사양서가 단일 소스.
