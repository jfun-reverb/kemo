# REVERB 피그마 작업 길잡이

원칙은 전역 `~/.claude/rules/common-planning.md` **규칙 E**. 여기는 이 저장소에서 **어디를 보고 어떤 순서로** 하는지만 적는다.
화면 기획과 디자인은 **기획 세션이 함께 맡는다**(2026-10-14 사용자 결정 — 별도 디자인 세션 없음).

## 0. 순서

1. 이 스킬 → 2. 피그마 플러그인 스킬 `figma:figma-use`(`use_figma` 전 필수) → 3. 그리기

## 1. 그리기 전에 — 기준 잡기 (규칙 A 의 그림판)

**① 이 화면이 어느 기준을 따르나** — 사양서에 적혀 있지 않으면 **사용자에게 묻고 사양서에 적는다**.

| 화면 | 기준 | 정본 |
|---|---|---|
| 인플루언서 모바일 앱 | Apple 디자인 지침 + 회원 앱 공용 부품 | `.claude/rules/ui.md` 「Apple 디자인 지침」 · `dev/css/member-ui.css` |
| 관리자(PC) | 흑백 + 보라 강조색 | `.claude/rules/ui.md` · `dev/css/` |
| 새 화면(브랜드 포털 등) | 사양서가 정한 것 | 해당 사양서 |

🔴 `ui.md` 는 경로 조건부라 기획 세션에서 자동으로 안 읽힌다 — **Read 도구로 직접 연다.**

**② 실제 화면을 먼저 본다** — 기존 화면을 닮게 그릴 때는 개발서버 화면(크롬)이나 CSS 값을 먼저 확인하고, 피그마에 **기준 프레임**(색·여백·라운드·사이드바)을 하나 두고 거기서 복제해 그린다.
⚠️ 실측(2026-10-13): 이걸 안 해서 「배경 흰색」·「여백」·「메뉴 색과 박스 라운드 불일치」를 사용자가 **서너 번** 지적했다.

**③ 현재 동작을 확인한다** — 그 화면이 다루는 데이터가 지금 어떻게 돼 있는지 `CLAUDE.md` 해당 절·사양서 「구현 결과」로 본다.
⚠️ 실측: 오리엔시트는 **1건에 제품 1개**인데 여러 개로 그렸다.

## 2. 그리는 중

- **화면 이름은 화면 코드로** — 브랜드 포털은 사양서 `docs/specs/2026-07-15-brand-portal.md` §15(「단계 기기+페이지-화면+상태」). 규칙을 바꾸면 사양서와 피그마 맨 위 「화면 이름 읽는 법」 상자를 **함께** 고친다. 다른 기능도 같은 형식을 쓴다
- **화면마다 설명** — 어느 페이지에서 · 언제 뜨는지(토스트·모달·오류·빈 상태는 특히) · 관련 사양서 절
- **결정이 생기면 그 턴에 사양서로** — 흐름·조건·문구가 정해지면 피그마에만 두지 않는다. 사양서와 피그마가 다르면 **사양서가 이긴다**
- **화면 문구** — 인플루언서 문구는 `reverb-ui-copy` 스킬. 사용자에게 보일 때 일본어엔 한국어 뜻 병기(`interaction.md`)

## 3. 지우거나 바꿀 때 — 남은 자리 찾기

화면·버튼·용어를 지우거나 바꾸면 **피그마 파일 전체에서** 그것을 가리키는 자리를 찾는다(버튼 문구·링크·안내문·흐름 화살표).
⚠️ 실측: 회원가입 화면을 지웠는데 로그인 화면에 「계정이 없으신가요?」 링크가 남았다.
같은 낱말이 코드·메일에도 있으면 그쪽은 개발 세션 몫 — 목록만 넘긴다(`request-validation.md`).

## 4. 동시 작업

- **한 피그마 파일은 한 세션만** 쓴다. 다른 세션이 같은 파일을 쓰는지 모르면 **사용자에게 묻는다**(보조로 `ListAgents` 로 떠 있는 세션을 보고 그 세션에 물어도 된다)
- 서브에이전트에 나눌 때는 **겹치지 않는 섹션 단위**로 맡기고, 공통 요소(기준 프레임·부품)는 **메인이 먼저 만든 뒤** 나눈다
- ⚠️ 2026-10-13 한 세션이 서브에이전트 약 70개로 같은 파일을 고쳤고, 그날 「화면이 완전 틀어졌다」는 지적이 있었다 — 인과는 확인 안 됨

## 5. 끝낼 때

- 바꾼 화면은 **스크린샷으로** 사용자에게 보인다(`get_screenshot`)
- 사양서 변경분은 기획 규칙대로 기능 브랜치 → 병합 요청
- 개발에 넘길 때 **화면 코드로** 가리킨다(「2차 w04-06a」)
