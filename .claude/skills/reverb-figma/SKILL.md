# REVERB 피그마 작업 길잡이

원칙은 전역 `~/.claude/rules/common-planning.md` **규칙 E**. 여기는 이 저장소에서 **어디를 보고 어떤 순서로** 하는지만 적는다.
화면 기획과 디자인은 **기획 세션이 함께 맡는다**(2026-10-14 사용자 결정 — 별도 디자인 세션 없음).

## 0. 순서

1. 이 스킬 → 2. 피그마 플러그인 스킬 `figma:figma-use`(`use_figma` 전 필수) → 3. 그리기

**화면 개선 일감의 흐름**(2026-10-16 사용자 정의): 수정·개선안 요청 → 시안 작업(피그마 `시안` 단계) → 검토 → 수정 → 컨펌 완료 → **적용**. 🔴 여기서 「적용」은 **피그마 화면·설명 패널 정리 + 사양서(필요하면 작업표) 작성**까지이고, **코드 구현은 개발 세션 몫**이다 — 기획 세션이 「적용해 줘」를 구현 착수로 읽지 않는다(2026-10-16 실제로 한 번 그렇게 읽어 작업 폴더까지 만들었다 되돌림). 컨펌된 화면은 이름의 `시안`을 `현행`으로 바꾸고 끝에 「구현 중 날짜」를 붙였다가 운영 반영 뒤 뗀다.

## 1. 그리기 전에 — 기준 잡기 (규칙 A 의 그림판)

**① 이 화면이 어느 기준을 따르나** — 사양서에 적혀 있지 않으면 **사용자에게 묻고 사양서에 적는다**.

| 화면 | 기준 | 정본 |
|---|---|---|
| 인플루언서 모바일 앱 | Apple 디자인 지침 + 회원 앱 공용 부품 | `.claude/rules/ui.md` 「Apple 디자인 지침」 · `dev/css/member-ui.css` |
| 관리자(PC) | 흑백 + 보라 강조색 | `.claude/rules/ui.md` · `dev/css/` |
| 새 화면(브랜드 포털 등) | 사양서가 정한 것 | 해당 사양서 |

🔴 `ui.md` 는 경로 조건부라 기획 세션에서 자동으로 안 읽힌다 — **Read 도구로 직접 연다.**

**② 실제 화면을 먼저 본다** — 기존 화면을 닮게 그릴 때는 개발서버 화면(크롬)이나 CSS 값을 먼저 확인하고, 피그마에 **기준 프레임**(색·여백·라운드·사이드바)을 하나 두고 거기서 복제해 그린다.
⚠️ 실측(2026-10-13): 이걸 안 해서 「배경 흰색」·「여백」·「메뉴 색과 박스 라운드 불일치」를 사용자가 **서너 번** 지적했다.

🔴 **흰 배경은 도구가 넣는다 — 틀을 만들 때마다 배경을 비운다**(2026-10-19 사용자 재지적). `figma.createAutoLayout()`·`createFrame()` 은 **흰 배경을 기본으로** 단다. 회색 화면(#fafafa) 위에 줄·제목·입력 묶음용 틀을 만들고 그대로 두면 글자 뒤에 흰 띠가 생긴다(10/19 하루에 161곳).
- 만들 때: 배경이 필요 없는 묶음 틀은 **`fills = []`** 를 바로 준다. 흰 바탕이 **의도인 것**(카드·입력칸·메일 본문)만 색을 직접 적는다
- 다 그린 뒤: 그 구역에서 **「흰 배경 + 테두리 없음 + 부모가 흰색이 아님」** 인 틀을 세어 0건인지 본다(겹침 검사와 같은 때). ⚠️ 운영 캡처를 복제한 화면 안쪽은 원래 모양이라 건드리지 않는다

**③ 현재 동작을 확인한다** — 그 화면이 다루는 데이터가 지금 어떻게 돼 있는지 `CLAUDE.md` 해당 절·사양서 「구현 결과」로 본다.
⚠️ 실측: 오리엔시트는 **1건에 제품 1개**인데 여러 개로 그렸다.

## 2. 그리는 중

- **화면 이름은 화면 코드로** — 브랜드 포털은 사양서 `docs/specs/2026-07-15-brand-portal.md` §15(「단계 기기+페이지-화면+상태」 — 기기 글자는 브랜드 웹 `bw` · 브랜드 모바일 `bm` · 관리자 `a`, 2026-10-15 사용자 지시로 옛 `w`·`m` 에 `b`(brand)를 붙였다). 규칙을 바꾸면 사양서와 피그마 맨 위 「화면 이름 읽는 법」 상자를 **함께** 고친다. 다른 기능도 같은 형식을 쓴다
- 🔴 **화면 이름 맨 끝에 업데이트 일시**(2026-10-15 사용자 지시) — `(업데이트 2026-10-15 13:50)` 형식, 한국 시각. 화면을 **새로 그리거나 고칠 때마다** 그 순간 시각으로 바꾼다(`TZ=Asia/Seoul date "+%Y-%m-%d %H:%M"`). 그 전에 그린 화면은 비워 둔다(사용자 결정 — 피그마가 화면별 수정 시각을 주지 않는다). 사양서·설명 패널에서 화면을 가리킬 때는 일시를 붙이지 않는다
- **화면 이름·설명의 용어**(2026-10-14 사용자 결정) — 「창」 대신 형식에 맞는 말: 어두운 배경 위에 뜨는 것은 **모달**, 화면 전체를 쓰는 것은 **페이지·화면**, 잠깐 떴다 사라지는 것은 **토스트**. ⚠️ 화면 **안의 문구**(관리자·브랜드가 읽는 글)는 이 규칙 대상이 아니다 — 「모달」은 사용자에게 낯선 말이라 화면 문구는 쉬운 말을 쓴다. 브라우저의 「새 창」·「인쇄 창」도 그대로. 웹은 모달이고 모바일은 전체 화면인 화면은 기기별로 따로 적는다(예: `bw04-01` 작성 모달 · `bm04-01` 작성 화면)
- **화면마다 설명 패널**(2026-10-14 사용자 결정 — 개발자가 피그마를 보고 개발한다) — 화면 **오른쪽**에 연보라 카드, 순서 고정: 어떤 화면 → **정책**(정해진 것 / 아직 정하지 않은 것 — 따로 칸) → 들어오고 나가는 길 → 화면 동작 → 개발 시 주의 → 확인 필요(화면·흐름에서 빠진 것) → 저장소 참고 → 자세한 근거
  - 🔴 **본문은 패널만 읽어도 이해되게 쓴다** — 저장소(사양서)를 못 보는 외부 개발자도 있다. 사양서 번호·마이그레이션 번호·함수 이름을 본문에 쓰지 않는다
  - 코드 이름은 회색 「저장소 참고」 상자에만, 사양서 번호는 맨 아래 「자세한 근거」에 **절 제목과 함께** + 파일 위치(저장소 권한 필요 안내)
  - 견본: 브랜드 포털 Figma 「[1차] 01 로그인」 구역
- 🔴 **메일을 보내는 화면이면 메일 양식도 같이 그린다**(2026-10-15 사용자 지시) — 그 화면 설명 패널 **오른쪽**에 메일 프레임(번호 규칙의 정본은 브랜드 포털 사양서 §15 「`90`·`91`·`95`」 줄 — 요지: 기기·페이지는 **받는 사람이 링크로 여는 페이지**, 메일 종류(무슨 일을 알리나)가 다르면 `95`·`96`…, 같은 종류 안에서 문구나 단추가 달라지는 갈래는 `96a`(다시 보냄도 문구가 달라질 때만). 그림은 **보내는 단추가 있는 화면** 옆, 그 화면이 Figma에 없으면 결과가 보이는 화면 옆). 한 프레임 = 맨 위 「메일 정보」(제목 · 받는 사람 · 보내는 때 · 링크·기한 · 정하지 않은 것) + 메일 미리보기(실제 양식 모양) + 맨 아래 회색 「저장소 참고」(양식 파일·서버 함수)
  - 모양·문구는 **실제 양식 `docs/email-templates/` 와 서버 함수의 제목**을 먼저 읽고 그대로 옮긴다. 사양서와 다르면(예: 링크 유효 시간) 사양서 값으로 그리고 「개발 참고」에 차이를 적는다. 양식이 없는 새 메일은 제목에 「(초안)」
  - **보낼지 정하지 않은 메일은 그리지 않는다** — 화면 설명의 「아직 정하지 않은 것」에 남긴다
  - 메일 프레임을 넣으면 그 줄 오른쪽 화면·흐름도를 밀고, 구역이 커지면 오른쪽 구역도 민다 — 그 뒤 겹침 검사(아래)
- 🔴 **버튼·입력칸 높이 44px 이상 — 웹 화면이라도 모바일을 고려**(2026-10-19 사용자 지시) — 브랜드·인플루언서 화면의 누르는 것(버튼·메뉴 줄·입력칸)은 최소 높이 44px. 관리자(PC 전용) 화면은 대상 아님. 그린 뒤 그 구역의 44px 미만 버튼을 세어 0건인지 본다
- 🔴 **구역은 흐름 하나씩, 위에서 아래로 · 구역 안은 흐름 순서대로 가로로**(2026-10-19 사용자 지시 — Client·Admin·Brand 모두) — 구역 이름 「[단계] 페이지-흐름 (A → B → C)」, 같은 열(같은 x)에 번호 순서로 600 간격으로 쌓는다. 구역 안 첫 줄 = 흐름 순서대로 「화면 → 오른쪽 설명 패널」을 왼쪽에서 오른쪽으로(맨 끝에 흐름도), 아랫줄 = 오류·상태 변형, 맨 아랫줄 = 토스트·상태 모음·메일. ⚠️ 한 구역에 여러 흐름을 넣고 화면을 위아래로 길게 쌓지 않는다(실측: 한 구역이 2만 5천 높이가 되어 「너무 길다」 지적). 구역 번호(`05-2`)는 화면 코드가 아니다 — 화면 코드는 그대로 둔다
- 🔴 **구역 맨 앞 화면 = 들어오는 곳**(2026-10-19 사용자 지적 「관리자 화면들이 시작하는 위치가 없다 — 어느 페이지에서 들어오는지 모른다」) — 모달·상세부터 시작하지 않는다. ①사이드바 메뉴로 들어오면 그 **목록 페이지**(사이드바 선택 표시 = 그 메뉴, 보라 테두리로 다음에 누르는 곳) ②다른 화면의 단추로 들어오면 **그 화면 복제** + 누르는 곳 보라 테두리·꼬리표(「→ 화면 코드」). 모달 배경도 실제로 여는 화면이어야 한다(실측: 공지 작성 모달 뒤가 브랜드 상세였다). 설명 패널 「들어오고 나가는 길」과 그림이 같은지, **사이드바 선택 표시(굵은 글씨 + 왼쪽 막대)가 그 화면 메뉴인지** 확인한다. 아래쪽 메뉴(관리자 설정 등)가 선택이면 사이드바를 굴린 모습으로 그린다
- **흐름도**(구역마다 하나, 그 구역 오른쪽 끝) — 화면 코드 상자를 격자에 놓고 화살표로 잇는다. 범례: 검은 테두리 = 화면 · 회색 점선 = 메일 · 보라 = 다른 화면에서 시작 · 초록 = 도착점 · 주황 점선 = 아직 없는 화면 · **빨간 점선 = 실패 흐름**
  - 🔴 **화살표는 꺾은선으로, 상자 사이 통로로만** — 상자 위를 지나가면 안 된다(2026-10-14 사용자 지적). 같은 통로를 여러 선이 쓰면 조금씩 띄운다. 그린 뒤 **선분이 상자와 겹치는지 계산으로 확인**한다(0건)
  - 실패 흐름도 그린다 — 입력 오류·저장 실패·링크를 쓸 수 없음·로그인 안 된 채 들어옴
- 🔴 **겹치는 화면은 늘 같이 정리한다**(2026-10-14 사용자 지시) — 화면·패널·흐름도를 넣거나 옮기거나 키운 뒤에는 **매번** 구역 안 겹침과 구역끼리 겹침을 검사하고 고친다(부탁받지 않아도)
  - ⚠️ **프레임 테두리가 아니라 실제로 보이는 범위**(`absoluteRenderBounds`)로 검사한다 — 프레임을 넘쳐 그려진 내용(긴 스크롤 화면·모달)은 테두리 검사에 안 걸린다. 실측: 모바일 작성 화면이 테두리 852인데 내용 2,655라 아래 화면을 덮었다. 넘친 프레임은 **내용 길이만큼 키우고** 그 아래 줄을 내린다
  - 구역이 커지면 같은 열의 아래 구역을 600 간격으로 다시 쌓는다
- **결정이 생기면 그 턴에 사양서로** — 흐름·조건·문구가 정해지면 피그마에만 두지 않는다. 사양서와 피그마가 다르면 **사양서가 이긴다**
- **화면 문구** — 인플루언서 문구는 `reverb-ui-copy` 스킬. 사용자에게 보일 때 일본어엔 한국어 뜻 병기(`interaction.md`)

## 3. 지우거나 바꿀 때 — 남은 자리 찾기

화면·버튼·용어를 지우거나 바꾸면 **피그마 파일 전체에서** 그것을 가리키는 자리를 찾는다(버튼 문구·링크·안내문·흐름 화살표).
⚠️ 실측: 회원가입 화면을 지웠는데 로그인 화면에 「계정이 없으신가요?」 링크가 남았다.
같은 낱말이 코드·메일에도 있으면 그쪽은 개발 세션 몫 — 목록만 넘긴다(`request-validation.md`).

## 4. 동시 작업

- **한 피그마 파일은 한 세션만** 쓴다. 다른 세션이 같은 파일을 쓰는지 모르면 **사용자에게 묻는다**(보조로 `ListAgents` 로 떠 있는 세션을 보고 그 세션에 물어도 된다)
- 서브에이전트에 나눌 때는 **겹치지 않는 섹션 단위**로 맡기고, 공통 요소(기준 프레임·부품)는 **메인이 먼저 만든 뒤** 나눈다
- ⚠️ 2026-10-13 한 세션이 서브에이전트 약 70개로 같은 파일을 고쳤고, 그날 「화면이 완전 틀어졌다」는 지적이 있었다 — 인과는 확인 안 됨

## 5. 끝낼 때
