# Git / 배포 규칙

## 브랜치
- 개발: `dev` 브랜치 → `dev.globalreverb.com` (개발서버) 자동 배포
- 배포: `main` 브랜치 → `globalreverb.com`, `www.globalreverb.com` (운영서버) 자동 배포
- PR 생성 시 dev → main

## 운영서버 배포 확인 (필수)
- **개발서버(dev 푸시) 배포 완료 직후, 운영서버 배포 여부를 항상 `AskUserQuestion`으로 물어본다**
- 예외: 사용자가 같은 요청 안에서 "운영까지 같이 배포해줘" / "main까지 머지해줘" 등 **명시적 지시**를 이미 한 경우에만 바로 진행
- 검증도 없이 자동으로 main merge·운영 배포 금지
- 질문은 2~3택: `지금 운영 배포` / `개발서버에서 검증 후 결정 (추천)` / `배포 보류`

**Why:** 개발서버에서 검증되지 않은 변경이 운영에 바로 올라가면 롤백 비용이 크다. 사용자가 개발서버에서 직접 확인 후 판단하는 게 원칙.

## 개발서버 배포(dev 머지)는 위임 — Claude가 진행 (2026-05-22 사용자 명시)
- **개발서버 반영(= feature 브랜치 → dev PR 머지)은 사용자에게 매번 확인하지 않고 Claude가 진행한다.** 사용자 지시: "개발서버는 배포까지 해줘".
- 단 **배포 전 게이트는 그대로 모두 거친다**: ① `reverb-reviewer` GO ② 빌드(`bash dev/build.sh`) ③ PR 충돌 있으면 해소(origin/dev 머지 + 재빌드) 완료 후 머지.
- 머지 방식: `gh pr merge <PR> --merge` (기존 "Merge pull request #N" 패턴 유지).
- **운영서버(dev → main) 배포는 위 「운영서버 배포 확인 (필수)」 그대로 — 반드시 사용자 확인.** dev 위임이 main까지 확장되지 않는다.
- 멀티세션 규칙 「PR 머지는 사용자가 GitHub에서 직접」(`.claude/rules/multi-session.md` 4단계)은 **운영(main)·미검증 PR에 한정**으로 해석. reviewer GO + 빌드 + 충돌해소가 끝난 **dev 머지는 예외로 Claude 진행 가능**.

**Why:** 개발서버는 검증 환경이라 롤백 부담이 작고, 사용자가 매 PR 머지를 손으로 누르는 반복을 없애려고 위임함. 운영(main)만 사람이 최종 판단 (2026-05-22 사용자 명시 지시 + "규칙에 남겨줘" 요청).

## 거버넌스 문서는 고문이 dev 직접 커밋 (dev push 금지의 예외, 2026-06-05)
- 거버넌스 문서(`.claude/rules/*`·`.claude/agents/*`·`.claude/commands/*`·메모리·HANDOFF·`docs/specs/*` 신규)는 **고문 세션이** 직접 수정하고 **같은 턴에 `dev` 직접 커밋·push** 한다. (목록 정의처는 `session-roles.md` §2 — 양쪽 동일 유지)
- ⚠️ **기획 세션은 이 예외가 아니다** (2026-08-25 결정) — 기획은 `feature/기획-…` 브랜치에서 일하고 **사양서를 PR 로** 올린다. 이유: 기획이 `dev` 를 쥐면 **고문이 구조적으로 제자리를 잃는다**(git 은 같은 브랜치를 두 폴더에서 못 연다). ⚠️ 이 조항은 오래 「고문/기획」이라 적혀 있었지만 **`session-roles.md` §1·§2 표는 처음부터 기획을 `feature` 브랜치로 적고 있었다** — 규칙끼리 모순이던 것을 2026-08-25 에 **표 쪽으로** 맞췄다. 사양서 `docs/specs/2026-08-25-planner-commit-location.md`
- `dev` 직접 push 금지 원칙(`multi-session.md`)의 **명시적 예외** — 거버넌스 문서는 개발 코드(`dev/*`·`supabase/*`)와 파일이 안 겹쳐 충돌 위험이 없다(고문=메인 폴더 `dev`, 개발=worktree `feature`, 다른 폴더+다른 브랜치).
- 조건 3종: ① **거버넌스 문서만** (코드·빌드 산출물·마이그레이션 SQL·`CLAUDE.md` 는 제외 → 개발 세션) ② push 직전 `git pull --rebase origin dev` 로 최신화 ③ **미커밋 방치 금지**(고친 즉시 커밋 — 과거 유실 사고는 미커밋+브랜치 전환 조합이었음).
- 세션별 전체 경계·인수인계는 `.claude/rules/session-roles.md` 정의처 참조.

**Why:** 규칙을 정하는 건 고문/기획의 본업인데, 거버넌스 문서 수정을 개발 세션에 넘기면 비효율. 직접 수정+즉시 커밋이면 유실 위험(미커밋 방치)이 사라지므로 직접 처리 허용 (2026-06-05 사용자 지시).

## 배포 워크플로 (필수)
1. dev/ 수정 → `cd dev && bash build.sh`
2. dev 브랜치 커밋 + 푸시 → 개발서버 자동 배포
3. **개발서버에서 기능 검증** (로그인/DB 쓰기/UI 확인)
4. DB 변경이 있다면 **개발서버 DB에 먼저 적용** 후 코드와 함께 검증
5. PR dev → main 생성
6. 운영서버 DB에 마이그레이션/패치 적용 (SQL Editor)
7. PR merge → 운영서버 자동 배포
8. 운영서버 실데이터/환경에서 최종 검증

## 빌드 필수
- 빌드 명령·순서·새 파일 추가 절차는 `.claude/rules/build.md` 정의처 참조
- 루트 `index.html`, `admin/index.html`는 빌드 산출물 (직접 수정 금지)
- 루트 `js/`, `css/`, `lib/` 폴더는 **존재하지 않음** (2026-04-14 정리 완료)

## Cherry-pick 배포 (개발서버 한정 기능 제외)
- 개발서버만 적용할 커밋(예: i18n Phase 1)은 main에 머지 금지
- 필요한 커밋만 cherry-pick해서 새 브랜치 → PR → merge
- 충돌 발생 시 `dev/` 소스 파일을 가져와서 rebuild하는 방식 권장

## 커밋 컨벤션
- conventional commit: `feat:`, `fix:`, `refactor:`, `docs:`, `chore:`, `build:`
- 영어 한 줄 메시지 선호 (한국어 설명은 body에)
- 본문에 변경 이유(why)와 영향 범위 기록

## 🔴 저장소에 넣은 것은 기본으로 **운영에 공개된다** (2026-09-02 사고)

**Vercel 이 저장소를 통째로 배포한다.** 「이건 내부용이니까」는 아무 효력이 없다 — **`.vercelignore` 에 안 적힌 것은 전부 인터넷에서 주소로 열린다.**

### 실제로 무엇이 열려 있었나 (2026-09-02 차단 전)

- **마이그레이션 전부** — 접근 정책·함수 본문, 그리고 **「이 조항을 빼면 조용히 깨진다」는 우리 주석까지**
- **`CLAUDE.md`**(24만 자) — **아직 안 닫은 것을 안 닫았다고 적어 둔 자리 포함**
- **`.claude/rules/` 전체** — 규칙 파일이 **자기가 공개되는 걸 몰랐다**
- **사양서 176 · 조사 문서 11** — 지난 전수조사의 **미조치 결함 목록**이 그대로
- `dev/js/admin.js`(38만 자) · 서버 함수 원본 · `.mcp.json`

⚠️ **그날 실제로 새어 나갔다** — 그날 오후 배포에 전수조사 문서 3건이 함께 올라가, **아직 안 고친 보안 결함 목록**이 인터넷에서 읽혔다.

### 지킬 것

1. 🔴 **새 폴더·새 문서를 만들면 「공개」가 기본이다.** 내부용이면 **`.vercelignore` 에 넣는 것이 그 문서를 만드는 작업의 일부**다.
2. **차단은 「빼는 목록」으로 둔다** — 「넣는 목록」을 틀리면 **사이트가 죽고**, 「빼는 목록」을 틀리면 **파일 하나가 더 공개될 뿐**이다. 되돌리기 비용이 다르다.
3. ⚠️ **문법 함정** — 부모 폴더를 통째로 제외하면 `!` 로 자식을 되살릴 수 없다. `docs/` 가 아니라 **`docs/*`** 여야 한다. **실제로 배포해야 아는 종류**라 개발서버에서 먼저 확인한다.
4. **배포 뒤 양쪽을 확인한다** — 404 여야 하는 것과 **200 이어야 하는 것 둘 다**. 차단이 과했는지는 200 쪽에서만 드러난다.
5. 🔴 **`curl` 200 으로 끝내지 말 것** — 실행 중에 가져오는 문서(약관 4개)는 **화면을 열어야** 정상인지 안다. 실측에서 **첫 스크린샷이 두 번 다 백지**였다(가져오는 중이었고 몇 초 뒤 정상) — 상태 코드만 봤으면 몰랐고, 첫 화면만 봤으면 없는 고장을 보고했을 것이다.

### 지금 열려 있는 것 (2026-09-02 기준)

인플루언서·관리자 화면 · `admin-setpw.html` · `event-scan.html` · `robots.txt` · **약관 4개**(`docs/{TERMS,PRIVACY}_{kr,ja}.md` — `dev/lib/legal.js` 가 **실행 중에 가져와** 푸터 약관을 그린다. 막으면 그 화면이 깨진다).

⚠️ **코드에서 `docs/…` 를 검색하면 35개쯤 나오지만 전부 주석 참조다.** 실제로 가져오는 자리는 `legal.js` 하나뿐이다 — 그 목록을 보고 「메일 양식·사양서도 앱이 쓴다」로 읽지 말 것.

⚠️ **내부 흐름도 2개는 `!` 로 되살려 개발서버에서만 200 이다.** `.vercelignore` 는 브랜치를 못 나누므로, **운영에서 404 인 것은 「`main` 에 그 파일이 없다」는 전제에 기댄다.** 누가 다시 올리면 그 순간 공개된다.

**Why:** 이 사실이 **어디에도 적혀 있지 않아** 2026-09-02 에 두 세션이 각각 밟았다. 조사한 쪽(고문)도 「내부 문서 2개가 열린다」에서 멈춰 **폴더 전체를 안 셌고**, 범위가 두 번 더 넓어졌다. 눈에 띈 것은 **「운영에 없다」고 문서가 시끄럽게 주장한 자리뿐**이었고, 조용히 공개된 나머지는 아무도 세지 않았다.

## 🔴 배포됐는지 확인할 때 — `curl -sL` + md5, 그리고 양성 대조

`globalreverb.com` 은 **307 로 `www.globalreverb.com` 으로 보낸다.** `-L` 이 없으면 받는 것은 **15바이트짜리 「Redirecting...」**뿐이다(2026-08-31 실측: `-L` 없이 15바이트 / 붙이면 1,212,607바이트).

- 🔴 **그 15바이트에 `grep` 을 걸면 당연히 0건인데, 그 0 은 「없다」와 「잘못 찾았다」가 구분되지 않는다.**
- **md5 대조가 낫다** — `curl -sL <주소> | md5` 를 저장소의 `git show origin/main:index.html | md5` 와 맞춰 본다. 「배포됐나」에 바로 답이 나오고, **인플루언서 화면과 관리자 화면이 같은 해시로 나오면 그 자체가 경보**다(둘 다 리다이렉트 본문을 받은 것).
- ⚠️ **「없다」를 읽기 전에 양성 대조를 함께 돌린다** — 반드시 있어야 할 문자열(예: 그 화면의 대표 함수 정의)이 실제로 걸리는지부터 본다. 그게 0이면 찾는 방법이 틀린 것이다.

⚠️ **실측(2026-08-31) — 같은 날 두 세션이 각자 걸렸다.** 한쪽은 「인플루언서와 관리자 산출물이 같은 md5」로, 다른 쪽은 「운영 산출물 0건」을 **두 번 보고**하는 형태로 나타났다. 서로 모른 채 같은 함정을 밟았으므로 **한 사람의 부주의가 아니라 이 저장소 주소 구조가 만드는 함정**이다.
