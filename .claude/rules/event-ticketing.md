# 오프라인 팝업 방문 예약(티켓팅)

> 이 파일은 **행사 화면·마이그레이션을 열 때만** 읽힌다. 다른 영역을 고칠 때 알아야 하는 셋은 `CLAUDE.md` 본문에 남겨 뒀다.

> 오프라인 행사 방문 예약 + 입장 QR 확인. **모집 형식을 새로 만들지 않고** 방문형(visit)에 「행사 모드」 표시만 얹는다. 사양서 `docs/specs/2026-07-30-offline-popup-ticketing.md`
> ⚠️ **기능은 전부 운영에 있으나 아무도 켠 적이 없다** — 운영 데이터 0건(행사 캠페인·타임·티켓·묶음 모두). 8월 팝업은 행사 모드로 진행하지 않기로 결정됐다. 다음에 쓸 캠페인이 생기면 **캠페인 등록·타임 생성·묶음 지정**이 필요하다.
- `campaigns` 컬럼 2개(280): `event_mode boolean`(행사 캠페인 — **판정 단일 소스**, 클라 헬퍼 `isEventCampaign()`) · `is_invite_only boolean`(비공개). ⚠️ `CHECK (NOT event_mode OR recruit_type='visit')` — 리뷰어형에 켜지면 자동 승인 트리거(049)가 「대기」를 승인으로 덮어써 **티켓은 대기인데 신청은 당선**인 모순이 생긴다. ⚠️ 두 컬럼은 275 낙관적 락의 제외 목록에 없어 **자동 보호 대상**(편집 저장은 `updateCampaign(id, updates, expectedVersion)` 필수). ⚠️ 변경 이력 화이트리스트(265·266)에는 **의도적으로 넣지 않았다**(세 곳 동시 수정 위험)
- **`event_groups`(291·292) + `campaigns.event_group_id`** — **같은 행사를 날짜별로 여러 캠페인으로 나눈 경우 하나로 묶는다.** 안 묶고 현장 확인 화면을 캠페인 하나에 고정하면 **다음 날 아침 명단이 빈 화면**이 된다. 연결은 `ON DELETE SET NULL`(묶음을 지워도 캠페인 저장이 안 막힌다). RLS 조회 `is_admin()`·CUD `is_campaign_admin()`. 🔴 **정규화는 공백(일반·전각)을 전부 제거**하고 비교한다(292 가 현행) — 회사 마스터(119)의 공백 **압축** 패턴을 그대로 쓰면 「REVERB팝업」과 「REVERB 팝업」이 **둘 다 저장된다**. **압축과 제거는 목적이 다르다** — 회사명은 「제이 펀」과 「제이펀」을 다른 회사로 남기는 게 맞고, 행사 묶음은 같은 것으로 봐야 한다. ⚠️ 275 낙관적 락 **자동 보호 대상**, 변경 이력 화이트리스트(265·266)에는 **넣지 않음**(앞선 행사 칸 3개와 같은 판단). ⚠️ 편집 폼은 **연결된 묶음이 보관 상태여도 선택지에 남긴다** — 빼면 칸이 빈 채로 열리고 다른 칸만 고쳐 저장해도 **연결이 경고 없이 끊긴다**(`fetchEventGroups(keepId)`). 같은 이유로 조회 실패는 `null`, 0건은 `[]` 로 **구분**한다(다른 조회 함수들이 예외를 삼키고 `[]` 를 주는 관행과 다름). 사양서 `docs/specs/2026-08-05-event-group-and-scoped-checkin.md`
- `event_invites`(280) — 초대 번호(캠페인당 1줄, 대문자 영숫자 8자리). ⚠️ **캠페인 표에 두지 않은 이유**: 캠페인은 조회가 공개고 인플 앱이 `select('*')`로 통째 받아와 **브라우저 개발자 도구로 번호가 그대로 보인다**. 그러면 예약 함수의 서버 재검증도 무력해진다. RLS 조회는 `is_campaign_admin()`만, 방문객은 `verify_event_invite()`로 「맞나/틀리나」만 받는다. ⚠️ 남은 위험 = 초대 전용 캠페인의 **내용 자체**(제목·이미지)는 여전히 브라우저로 내려온다(목록 제외가 화면 단계 필터)
- `event_slots`(281) — 타임(날짜+시각+정원) 1줄. 3일 합계 32줄. RLS 조회 **로그인 전체**(개인정보 없음·§0 결정 16), CUD `is_campaign_admin()`. **정원 판정은 이 표가 한다** — `campaigns.slots`는 표시용 합계일 뿐. ⚠️ 예약이 걸린 타임은 **삭제 차단 트리거**(지우면 티켓이 소리 없이 연쇄 삭제되고 신청 행만 남아 「당선인데 예약번호 없음」). 캠페인이 통째로 지워지는 중이면 통과시키는 탈출구 있음(연쇄 순서 미보장 → 완전 삭제가 막히는 것 방지). 닫으려면 `is_active=false`
- `event_tickets`(282) — 예약 1건. `ticket_code`(QR에 담기는 값, 혼동 글자 0·O·1·I·L 제외 31자 집합) · `status(confirmed|waitlist|cancelled)` · `waitlist_position` · `entered_at`/`entered_by`(**첫 입장 시각 불변**)/`scan_count` · `version`. RLS = 본인+관리자 **조회만**, 쓰기는 SECURITY DEFINER 함수만(예약번호 위조·정원 우회 차단, 217 선례). 부분 유니크 `(campaign_id, influencer_id) WHERE status<>'cancelled'` = 「한 캠페인 1타임」. ⚠️ `application_id ON DELETE CASCADE` — 캠페인 보관 삭제(255)가 신청을 즉시 파기할 때 **입장 기록도 함께 파기**(개인정보 원칙, 삭제 함수 자체는 무수정)
- 신청 행과의 짝: 확정→`approved` **INSERT** / 대기→`pending` INSERT / 취소→`cancelled`. ⚠️ **대기도 신청 행을 미리 만든다** — 안 만들면 승격 시점(마감 후)에 INSERT가 마감 가드(272)에 막혀 승격 자체가 실패
- ⚠️ **취소 후 재예약**: 신청 표의 옛 유일 제약(050 `uidx_applications_user_campaign`)은 **마이그레이션 305로 제거됐다**. 104 가 지울 이름을 자동 생성 이름으로 잘못 적어 `IF EXISTS` 가 조용히 통과했던 결함으로, 그때부터 **「취소 후 재응모」가 플랫폼 전체에서 한 번도 동작하지 않았다**. 티켓 예약이 **신청 행을 지우지 않고 `cancelled` 로 두었다가 재예약 때 되살리는** 동작 자체는 그대로다(활성 행 유일 제약 `applications_user_camp_active_uidx` 가 여전히 사람당 1행만 허용한다)
- 서버 함수 5개(283, 전부 `SECURITY DEFINER`+`search_path=''`+행 잠금, 실패는 예외가 아니라 `{ok:false, reason}`): `reserve_event_ticket(slot, invite)` (타임 행 `FOR UPDATE` 잠금 후 정원 계산 → 확정/대기. **316이 「캠페인이 `active` 인가」·「타임 날짜가 오늘 이후인가」를 함께 본다** — 없으면 캠페인을 미리 만들어 둔 것만으로 공개 전 예약이 들어가고 지난 날짜 타임도 잡힌다. ⚠️**날짜 단위로만 자르고 오늘 것은 시각이 지나도 통과**시킨다 — 14시 타임을 14시 10분에 현장에서 받아 주는 경우가 있어 화면(`loadEventSlotPicker`)과 같은 기준으로 맞췄다. 거부 사유는 새 코드를 만들지 않고 기존 `slot_closed`·`not_found` 재사용. **중복 예약 검사는 행사 묶음 단위**(330) — 한 행사를 날짜별 캠페인 둘로 나눈 구조에서 캠페인 단위로만 보면 **한 사람이 두 날을 다 잡는다**. ⚠️ **묶음이 없으면 종전 그대로 캠페인 단위** — `NULL = NULL` 함정을 피하려고 `event_group_id IS NOT NULL` 을 명시적으로 앞에 둔다. ⚠️ **데이터베이스 제약이 아니라 함수 게이트다** — `event_group_id` 는 `campaigns` 에 있어 캠페인 편집마다 다시 저장되므로, `event_tickets` 에 복사본을 두면 **행사와 무관한 모든 캠페인 저장 경로**에 동기화 장치가 필요해진다. 새 행을 만드는 곳이 이 함수 하나뿐이라 문 하나에 세웠다. ⚠️ 남는 구멍 = 같은 사람이 **두 캠페인 화면에서 정확히 동시에** 누르면 서로 다른 타임 행을 잠가 둘 다 통과할 수 있다(330 파일 하단 조회로 사후 탐지). 거부 사유는 기존 `already_applied` 재사용 — 화면 문구가 원래부터 「이 행사를 예약했습니다」라 묶음으로 넓혀도 맞는다) · `check_in_ticket(code)`(관리자, 첫 입장 시각 보존·재확인은 `scan_count`만 증가, **입장을 막지 않는다**) · `cancel_event_ticket(ticket)`(본인, **시작 2시간 전까지** 일본 시각 서버 판정 + 대기 1번 자동 승격·순번 재정렬) · `verify_event_invite` · `get_event_slot_counts`(방문객은 남의 티켓을 못 봐 잔여를 직접 셀 수 없다)
- **대기 승격 알림**(283): 알림 종류에 `event_waitlist_promoted` 추가(273의 10종 → 11종, **목록 원본은 273**). 앞사람이 취소해 대기자가 확정으로 올라가면 `cancel_event_ticket` 이 **직접** 알림을 넣는다(트리거는 행사에서 조기 반환하므로 안 나간다). `ref_table='event_tickets'`. ⚠️ 알림 클릭 분기(티켓 화면으로 이동)는 **작업 4에서** 넣어야 한다 — 없으면 눌러도 아무 데도 안 간다
- ⚠️ `record_application_status_event()` 재정의(283, **베이스는 154**) — 행사 캠페인은 **조기 반환**. 알림 문구가 결과물 제출을 요구해 방문객에게 부적합(결정 14)이고, 대기 승격이 **다른 방문객의 취소 트랜잭션**에서 일어나 감사 기록의 처리자가 사실과 달라지기 때문
- ⚠️ 연령(180)·마감(272) 가드는 **신규 삽입 전용** 트리거라 되살리기(UPDATE) 경로에 안 돈다 → 예약 함수가 같은 판정을 먼저 하고, 트리거는 삽입 경로 최종 방어선으로 유지(공유 지점이라 무수정)
- ⚠️ 예약·취소는 **관리자 도구(SQL 편집기)로 검증 불가**(「본인 계정만」 가드 + 서비스 키는 로그인 사용자가 없다). 방문객 화면 완성 후 **테스트 계정 2개로 브라우저에서** 확인
- 접근 함수는 `dev/lib/storage.js` 한곳에 12개(`fetchEventSlots`/`fetchEventSlotCounts`/`upsertEventSlot`/`deleteEventSlot`/`reserveEventTicket`/`cancelEventTicket`/`checkInTicket`/`fetchMyEventTickets`/`fetchEventTicketsByCampaign`/`verifyInviteCode`/`fetchEventInvite`/`upsertEventInvite`), 헬퍼는 `dev/lib/shared.js`(`isEventCampaign`/`isInviteOnlyCampaign`/`eventCancelWindowPassed`)

#### 신청 접수 방식 — 선착순형 / 선정형 (마이그레이션 376~380, 2026-08-25 · ★**개발·운영 양쪽 적용 완료**)
> 비공개 행사에서 **예약이 곧 당선**(선착순)이 아니라 **관리자가 직접 뽑는** 방식을 고를 수 있게 한다. 기본값은 선착순형이라 **안 켜면 지금과 완전히 동일**하다. 사양서 `docs/specs/2026-08-24-event-invite-only-selection.md`(「구현 결과」에 회귀 확인 32건 결과 포함), 작업표 `…-breakdown.md`
- `campaigns.event_selection_mode`(376) — `first_come`(기본) / `selection`. 편집 폼의 「신청 접수 방식」 라디오. ⚠️ **예약이 한 건이라도 들어오면 못 바꾼다**(중간에 바꾸면 이미 확정된 사람과 심사중인 사람이 한 화면에 섞인다). ⚠️ 275 낙관적 락 **자동 보호 대상**, 변경 이력 화이트리스트(265·266)에는 **넣지 않음**(앞선 행사 칸들과 같은 판단).
- **정원은 뽑을 때만 지킨다.** `reserve_event_ticket`(현재 원본 **378**, 베이스 330)은 선정형이면 **정원을 아예 안 세고** 항상 `waitlist`(심사중)+신청 `pending` 으로 접수하며 **순번을 비운다**(순번이 보이면 「먼저 낸 순서대로 뽑힌다」는 오해를 준다). 🔴 분기는 330 원문의 「정원 판정」 블록이 시작되는 **바로 그 자리**에만 심는다 — 함수 맨 앞에 두면 초대 번호·묶음 중복 등 **앞선 아홉 개 검사를 통째로 건너뛴다**.
- ⚠️ **함수 분기만으로는 저장이 안 된다.** 제약 `event_tickets_waitlist_pos_chk`(282)가 「대기면 순번이 반드시 있어야 한다」를 요구해, **①제약 완화(378-A)와 ②`_renumber_event_waitlist` 선정형 조기 반환(378-B)을 둘 다** 해야 성립한다. 한쪽만 하면 「취소할 때마다 번호가 붙는」 최악이 된다.
- `pick_event_tickets`(뽑기) / `reject_event_tickets`(탈락) — **379**. 타임을 오름차순으로 잠그고 `확정 수 + 이번 요청 수 ≤ capacity` 를 확인해 **넘치면 부분 통과 없이 전부 거부**하고 어느 타임에 몇 자리 모자란지 배열로 돌려준다(`capacity_exceeded`). 화면은 고르는 즉시 「남은 자리 N명 · 이번에 N명」을, 넘치면 **「→ N명 초과」**를 빨간 글씨로 미리 보여준다.
- **380** — 뽑기가 신청 행에 **처리자·시각**(`reviewed_by`/`reviewed_at`)을 남긴다. 신청자 목록 「처리」 칸에 「{관리자명} {시각}」으로 표시.
- **377** — 자동 승격(`_promote_next_event_waitlist`)은 선정형에서 **조기 반환**. 뽑는 순서가 없으므로 앞사람이 취소해도 올릴 대상이 없다. 🔴 그 조기 반환을 없애거나 선정형에 정원 채우기를 붙이면 **관리자가 안 뽑은 사람이 자동으로 당선된다.**
- **당선과 낙선의 통지 경로가 다르다** — 당선은 **즉시 앱 알림**(`event_selection_won`, 376) + 입장 티켓 QR. 낙선은 응모를 `rejected` 로 두어 **다음날 아침 일일 다이제스트 메일**과 기존 **「落選」 배지**를 그대로 쓴다(새 사유 코드를 만들지 않은 이유 — 「낙첨은 원래 조용하다」는 전제가 사양 작성 중 뒤집혔다). 확인 창이 그 차이를 명시한다.
- **선정 기간**(`selection_start`/`selection_end`)은 **307이 시딩형용으로 만든 기존 칸**이고, 행사에는 「예약이 곧 당선이라 뽑는 기간이 없다」는 이유로 닫혀 있었다. **선정형에만 연다**(선착순형 행사는 지금도 안 뜬다). ⚠️ 인플루언서 상세·관리자 미리보기·진행현황·엑셀 **네 곳은 조건이 글자 그대로 같아야** 하고, **폼만 「이미 값이 저장돼 있으면 보여준다」 예외가 하나 더** 있다(그 분기를 지우면 목록엔 보이는데 고칠 자리가 없는 값이 생긴다). ⚠️ **관리자 캠페인 목록 열은 조건 없이 저장값을 그대로** 그린다 — 선착순형 행사에 옛 값이 남아 있으면 목록엔 뜨고 인플루언서에겐 안 뜬다.
- **현장 확인 화면·명단 엑셀**은 같은 `waitlist` 를 방식에 따라 **다른 말로** 부른다 — 선정형 「심사중」 / 선착순형 「대기 N」. ⚠️ **두 숫자를 합치지 않는다**(한 묶음에 두 방식이 섞이면 나란히 표시). 🔴 심사중인 사람에게는 **입장 버튼을 아예 안 그리고**, 예약번호를 직접 넣어도 「아직 선정되지 않았습니다」로 막는다. 엑셀은 요약에 「심사중」 열 + 명단 상태 「심사중」 + **대기순번 빈 칸**.
- ⚠️ **복제는 접수 방식·비공개·묶음을 이어받지만 초대 번호와 타임은 안 옮긴다.** 타임은 「캠페인마다 다르므로」 일부러 그렇고, **초대 번호는 그런 근거 없이 빠진다** — 편집을 열면 「번호 생성을 눌러 주세요」가 보이고 저장 때 오류 안내도 뜨지만, **상태 드롭다운으로 바로 공개하면 그 경로를 안 거쳐 아무도 못 들어간다**(비공개 기능 도입 때부터 있던 구멍, 미해결).
- ⚠️ **관리자 계정으로 인플루언서 화면을 시험하면 일반 사용자와 다른 경로를 탄다** — `dev/js/app.js` 가 관리자면 `currentUserProfile` 에 `{name, email}` 만 담고 **인플루언서 행을 안 불러온다.** 그래서 이미 저장한 생년월일·이름(가나)이 안 실려 응모마다 연령·필수정보 게이트가 다시 뜬다. **일반 인플루언서는 `select('*')` 라 해당 없다** — 시험 결과를 결함으로 오독하지 말 것.
- ⚠️ 관리자 예약 현황에서 **입장 처리 직후 상단 요약 카드가 안 갱신된다**(표는 즉시 바뀜). 페인을 다시 열면 맞는다. 미해결.
