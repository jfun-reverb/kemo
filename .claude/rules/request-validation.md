# 수정 요청 구조 적합성 검토 규칙 (영구)

> 사용자가 개발 세션에 수정을 요청했을 때, 개발 세션이 **무조건 실행하지 않고** 먼저 현재 구조와의 적합성을 검토하도록 하는 규칙. 2026-05-21 사용자 명시 지시.

## 세션별 역할 분담

> 아래 표는 **이 규칙(요청 구조 검토) 관점의** 역할만 다룬다. 세션 전체 역할·파일별 경계·인수인계 매트릭스는 [`session-roles.md`](session-roles.md) 정의처 참조.

| 세션 | 이 규칙에서의 역할 |
|---|---|
| **고문 세션** | 규칙·정의를 정해 개발/기획 세션의 방향을 잡아준다. 개발에 직접 관여하지 않고, 매 요청을 직접 검토하지도 않는다 (메타 레벨). |
| **개발 세션** | 사용자 수정 요청을 **무조건 실행 금지**. 구조 영향 있는 요청은 현재 구조와의 적합성을 먼저 검토하고, 안 맞거나 애매하면 코딩 전에 되묻는다. |
| **기획/설계 세션** | 개발 세션이 판단하기 애매한 구조 결정(설계 분기 큼)을 위임받아 판단한다. |

## 개발 세션 행동 규칙

### 적용 대상 — 구조 영향 있는 요청만
- 데이터베이스 구조 변경 (컬럼/테이블/원격 호출 함수(RPC)/행 단위 보안 정책(RLS))
- 화면 흐름 변경 (페이지 이동·라우팅·진입 경로)
- 기능 동작 변경 (기존 로직의 결과·조건이 달라짐)
- 여러 파일을 동시에 손대야 하는 변경
- **여러 자리가 공유하는 낱말·이름을 바꾸는 것** (아래 「낱말 전파 점검」)

### 낱말 전파 점검 — 문구 변경도 검토 대상이 될 수 있다 (2026-08-11 추가)

「문구만 바꾸는 것」이라도, 그 낱말이 **화면에 이름으로 등장하는 것**이면 한 자리만 고치면 안 된다. 코딩 전에 **그 낱말이 또 어디 있는지부터 센다.**

**검토 대상 (전파 점검 의무)**
- 기간·날짜의 이름 (「영수증 제출 마감일」·「모집 기간」·「선정 기간」 등)
- 상태·단계의 이름 (「인증 성공」·「검수 불필요」·「정산대기」 등)
- 화면·메뉴·버튼·탭의 이름
- 금액·수치의 이름과 그 계산 기준을 설명하는 안내문 (「최대 ¥N」·「페이백」 등)
- 모집 형식·채널처럼 **여러 화면이 같은 값을 부르는** 말

**검토 제외 (바로 진행)**
- 오탈자·띄어쓰기·문장 다듬기 (부르는 이름 자체는 그대로)
- 한 자리에서만 쓰이는 안내문·설명문
- 색상·여백·정렬 등 시각 조정

**점검 방법 — 코딩 전에 옛 표현을 아래 5곳에서 전부 검색한다**
1. `dev/` — 인플루언서 화면·관리자 화면·번역 파일(`dev/lib/i18n/{ja,ko}.js`)
2. `supabase/functions/` — 메일 본문(일일 다이제스트·승인 안내·검수 결과·홍보 메일)
3. `docs/email-templates/` (+ `_templates/` 미러)
4. 자주 묻는 질문 자동응답 — `faq_nodes` 시드·마이그레이션 (`supabase/migrations/`·`supabase/seed/`)
5. 엑셀 내보내기 열 이름 (`dev/js/admin-excel.js`)

**보고 의무** — 찾은 자리를 사용자에게 **목록으로 보여주고**, ①전부 바꿀지 ②일부만 바꿀지 확인받은 뒤 착수한다. 안 바꾸기로 한 자리는 그 이유를 사양서·PR 본문에 남긴다.

⚠️ 판정 함수·공용 헬퍼를 새로 만들었다면 **그 함수를 쓰는 자리가 곧 전부인지** 확인한다. 헬퍼만 만들고 옛 문구가 남은 화면이 있으면, 화면마다 다른 이름이 보인다.

### 행동 순서
1. 요청을 받으면 **바로 코딩하지 않는다.** 먼저 현재 코드에서 그 부분이 어떻게 되어 있는지 파악한다.
2. 요청이 현재 구조와 맞지 않거나 부작용이 우려되면, 코딩 전에 사용자에게 되묻는다:
   - 형식 예시: 「현재 ◯◯는 ~이렇게 동작합니다. 요청하신 변경은 여기와 맞지 않아 보입니다(이유). 어떤 의도이신가요?」
   - 선택지가 생기면 `AskUserQuestion` 사용 (`.claude/rules/interaction.md` 규칙 적용)
3. 적합성 판단이 개발 세션 수준에서 애매하면(설계 분기가 크면) → `reverb-planner` 호출 또는 기획/설계 세션으로 라우팅.
4. 사용자가 의도를 설명하고 그대로 진행을 원하면 **따른다** (최종 결정권은 사용자). 단, 우려했던 점은 PR 본문·사양서에 기록.

### 적용 제외 — 바로 진행
- 오탈자·띄어쓰기·색상 수정
- **한 자리에서만 쓰이는** 라벨·안내문 수정 (여러 자리가 공유하는 이름이면 위 「낱말 전파 점검」 대상)
- 1개 파일 내 사소한 스타일 조정

## 관련 규칙
- `.claude/rules/interaction.md` 「변경 프로세스」 — 개선 요청 시 계획 먼저 → 영향 체크 → 애매한 부분 질문
- 추가 수정 요청 라우팅(새 기능→기획, 버그→개발): 메모리 `feedback_change_request_routing.md`
- 고문 세션 역할 경계: 메모리 `feedback_main_session_advisor_role.md`

**Why (낱말 전파 점검, 2026-08-11 추가):** 예전 「적용 제외」 조항이 **「단순 라벨/문구 수정」을 통째로 면제**해 줘서, 개발 세션이 규칙대로 한 자리만 고치고 넘어갔다. 실제 사고 — 2026-08-06 에 리뷰어형 제출 마감 이름을 바꾸면서 공용 판정 함수 2개를 만들어 놓고 **네 자리에서만** 썼고, 메일·자주 묻는 질문 자동응답·활동관리 화면·관리자 목록은 옛 이름 그대로였다. 그 결과 **매일 아침 자동 발송되는 메일이 영수증 마감을 2주 이른 날짜로** 안내했고 5일 뒤에야 발견됐다(`04e2142a`·`8203d061`). 메모리에 「고칠 자리를 찾으면 또 어디 있나부터 세라」는 교훈이 이미 있었으나 규칙으로 승격되지 않아 아무도 안 봤다 (2026-08-11 사용자 지적).

**Why:** 사용자는 비개발자라 요청이 현재 구조와 충돌하는지 스스로 판단하기 어렵다. 기획 단계는 질문-답변으로 길을 찾지만, 개발 단계에서 요청을 무조건 실행하면 구조가 어긋난 채 쌓인다. 개발 세션이 「이 요청이 여기 맞나」를 먼저 검증하고 되묻는 게이트를 둬서, 사용자가 의도를 다시 점검할 기회를 만든다 (2026-05-21 사용자 명시 지시).
