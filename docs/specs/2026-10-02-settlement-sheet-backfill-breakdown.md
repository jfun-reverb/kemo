## 조각별 상세

### S1 — 마이그레이션 ① 추정 표시 칸 2개
- **하는 일**: `settlement_transfers` 에 `sent_at_estimated`·`fee_estimated` 추가. 기존 행은 거짓(화면 기록 = 실제값). 표 원본 485
- **완료 정의**: 개발 DB에서 `select count(*) from settlement_transfers where sent_at_estimated or fee_estimated` = 0
- **검문소**: 데이터베이스 전문 에이전트 · 코드 검토 에이전트
- **주의**: S2·S3 가 기대므로 되돌릴 때는 묶어서

### S2 — 마이그레이션 ② 소급 함수 신설
- **하는 일**: 사양서 설계 ① (나) 그대로. 핵심만:
  - 출처는 **항상 `sheet_backfill`**(입력으로 받지 않는다)
  - 항목 종류 셋(이미 송금완료·정산대기·미등록)을 한 묶음에 섞을 수 있다. 「옛 송금」 항목은 **연결만**
  - 🔴 **페이팔 유무로 막지 않는다** — 486 의 페이팔 거부 세 곳을 옮기지 않는다. `paypal_email` 은 **입력의 시트 주소**
  - 미등록이면 `_settlement_register_judge`(486)에서 `paypal_missing` 만 통과. 🔴 **후보가 아니면 회원·캠페인을 `applications` 에서 직접 읽는다**
  - 이미 송금완료 건은 정정 이력(`correct`)에 옛 송금일·옛 금액을 남긴다(완료 기준 7)
  - 수수료: 추정이면 `_settlement_fee_calc`(484 규칙)로 서버가 계산하고 규칙 스냅샷을 채운다. 합산 탭 값이면 **반올림** + `fee_manual=false` + **스냅샷 3칸 비움**(결정 6)
  - 확인 표시 없는 항목의 금액 비교는 `COALESCE(paid_amount_jpy, amount_jpy)`
  - 「옛 송금」은 `settlement_events.settlement_id = 그 건 AND action='revert'` 를 직접 확인
  - 정산 행을 **id 순으로 먼저 잠근 뒤** 「이미 반영됨」 판정(묶음 통째 건너뜀) → 조건 검사 → 하나라도 걸리면 아무것도 안 쓴다
  - 송금일은 **일본 시각 자정**. 알림 없음. 권한 `settlement.pay` 쓰기
- **산출 계약**: 함수 이름·입력 모양·반환 — **F1·T1·P2 가 이 모양에 맞춘다**. 확정 즉시 사양서 「구현 결과」에 적는다
- **베이스**: 486(`record_settlement_transfers`·`_settlement_register_judge`·`_settlement_fee_calc`) · 485(표) · 341(이력 action 7종 — `correct` 있음)
- **검문소**: 데이터베이스 전문 에이전트 · 코드 검토 에이전트. 실행 권한은 회수 방향 둘(`PUBLIC`·`anon` 회수 + `authenticated` 부여)
- **주의**: `SECURITY DEFINER` + `SET search_path = ''`. 🔴 도입일 판정을 넣지 않는다(완료 기준 2). 반려·취소 신청에 송금완료가 생기면 247·320 가드로 이후 반려가 막힌다 — 운영팀 안내

### S3 — 마이그레이션 ③ 정정 재정의 + 조회 3개 재생성
- **하는 일**:
  - `correct_settlement_transfer`(베이스 **486**, 인자 그대로 → `CREATE OR REPLACE`, 권한 보존): 송금일이 오면 `sent_at_estimated=false`, 수수료가 오면 `fee_estimated=false`. NULL 칸 표시는 그대로. 「추정 칸에 값이 들어옴」도 변경으로 센다(조기 반환 회피). 🔴 **넘긴 수수료가 지금 값과 같으면 `fee_manual` 을 건드리지 않는다**(결정 7)
  - 조회 3개(`get_settlement_transfers`·`_monthly`·`_by_round`, 베이스 **487**): 두 표시와 「추정 포함 건수」. **`DROP` 후 `CREATE`** → 실행 권한 3줄 재설정
- **완료 정의**: 개발 DB에서 `p.proacl::text` 로 세 조회의 권한이 이전과 같다(맨 앞 `=X/` 없음 · `anon` 없음 · `authenticated` 있음)
- **주의**: 🔴 `DROP`·`CREATE`·권한을 **한 파일 한 트랜잭션**에. 편집기 경고는 뜬다(무해). `get_settlement_transfer_unrecorded` 는 건드리지 않는다

### S4 — 개발 DB 적용 + 서버 시험
- **하는 일**: 파일 3개 절대경로 + 「편집기 경고」 한 줄씩을 사용자에게 넘김 → 적용 → 시험
- **시험 목록**: 세 종류 섞인 묶음 · 다시 돌리기(현재·옛 송금 각각 → 0행) · 확인 표시 없는 항목 거부와 「아무것도 안 씀」 · 확인 표시 있는 항목(금액 다름·보류 건·옛 송금 연결·후보 아닌 미등록) · 옛 송금일 이력 · 알림 0건 · `sheet_backfill` 만 있을 때 옛 송금완료 경로 통과 · 정정으로 표시 하나만 지워짐·같은 수수료면 `fee_manual` 그대로 · 합산 탭 수수료는 건별 금액 정정에도 재계산 안 됨 · 동시 잠금 · 불변식·표시값(시험 입력)
- **주의**: 🔴 권한 판정은 SQL 편집기로 재현 안 됨 — 함수 호출 시험은 **관리자 로그인 브라우저 콘솔**에서. 시작 전 수수료 규칙이 초기값인지 확인(G2)

### F1 — 소급 함수 래퍼
- `recordSettlementTransfers` 옆에 1개. 실패 규약 같게. 🔴 `storage.js` 핫스팟 — 작업 폴더 병렬 금지
- **완료 정의**: 관리자 빌드 산출물에 그 함수가 있다(양성 대조로 `recordSettlementTransfers` 도 함께)

### F2 — 「송금 내역」 화면 5곳
- 묶음 줄 `_transferListHtml`: 송금일·수수료 옆 「추정」 배지 + 툴팁 「정정 창에서 실제 값을 넣거나 『값이 맞음』을 체크하면 사라집니다」
- 요약 `_transferSummaryTableHtml`: 월별·회차별 「추정 포함 N건」
- 상세 `_transferDetailTableHtml`: 배지
- 엑셀(`exportTransferHistoryExcel`): 사용자 결정에 따름
- 정정 창 `openTransferCorrectModal`/`saveTransferCorrect`: 추정 칸에 「값이 맞음(추정 해제)」 체크, 체크된 칸은 같은 값이라도 보낸다. 「바꾼 칸이 없습니다」 거부 판정을 그에 맞게
- ⚠️ 합산 탭 묶음은 **규칙 스냅샷이 비어 있다**(결정 6) — 스냅샷을 그리는 자리가 빈 값에서 「—」로 나오는지, 「고친 값」으로 오판하지 않는지 확인

### T1 — 콘솔 쓰기 도구
- 운영 SQL 편집기는 로그인이 없어 권한에 막히고, 수백 묶음을 손으로 나눠 부르면 실수가 난다 → `scripts/backfill-storage-thumbs.js` 선례처럼 붙여넣는 일회성 도구
- P2 산출물(JSON)은 실행 때 붙여넣는다 — 🔴 **도구 파일에 개인정보를 넣지 않는다**
- ①미리보기(묶음 수·건수·금액·추정 건수, 쓰지 않음) → ②확인 문구 입력 → 묶음 단위 호출 → 쓰인·건너뛴·거부 요약. 한 번에 보내는 묶음 수 제한
