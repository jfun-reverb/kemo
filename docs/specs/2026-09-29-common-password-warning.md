# 흔한 비밀번호 — 회원은 경고, 관리자는 거부

> **작성일:** 2026-09-29 · **작성:** 기획 세션
> **상태:** 설계 확정 — 개발 착수 가능(화면 모양·문구도 사용자 결정 완료 — §6)
> **계기:** 2026-09-29 운영 보안 점검 화면에 「유출 비밀번호 검사 꺼짐」 경고. 대시보드에서 확인하니 운영·개발 둘 다 꺼져 있었다(§1-1)
> **사용자 결정(2026-09-29):** 거부는 가입 허들이 높다 → **회원은 경고만 띄우고 진행을 허용, 관리자는 거부** · 경고는 **비밀번호 칸 아래 안내 줄** · 문구는 **「추측되기 쉬운 비밀번호」**(§6)
> **코드 변경:** 서버 함수 1개 신설 + 판정 함수(`dev/js/ui.js`·`dev/admin-setpw.html`) + 비밀번호를 정하는 여섯 자리(회원 셋·관리자 셋 — `auth.js`·`mypage.js`·`admin-setpw.html`·`admin-accounts.js`) + 회원 안내 줄 자리·번역 문구. 파일 전체는 §4. 데이터베이스 변경 없음

## 0. 한 줄 정의

비밀번호를 정하는 순간, 그 비밀번호가 **이미 공격자 손에 있는 공개 유출 목록**(Have I Been Pwned 의 Pwned Passwords)에 있는지 본다. 있으면 회원에게는 「추측되기 쉽다」고 **알리고 선택을 맡기고**, 관리자에게는 **다른 비밀번호를 요구**한다. 목록 조회는 **우리 서버 함수를 거쳐** 하므로 회원 브라우저가 외부 서비스에 직접 접속하지 않는다.

### 1-2. 비밀번호를 정하는 자리 (개발 브랜치 `ba78289a` 기준)

- `reset_admin_password`(최신 정의 `supabase/patches/2026-04-15_fix_reset_admin_password.sql`)는 **두 벌**(대상을 고유번호로 받는 것 — 화면이 부르는 것 / 이메일로 받는 것)이고, 둘 다 인증 서버를 거치지 않고 해시를 직접 쓴다 — **서버 쪽에는 어떤 검사도 없다.** 이 사양서도 서버 검사는 넣지 않는다(§2-1 ⑤).

- 이 여섯 말고 계정 비밀번호를 서버로 보내는 자리는 없다(2026-09-29 코드 대조 — `updateUser`·`signUp`·`reset_admin_password` 전수). 리포트 공유 링크 비밀번호는 계정 비밀번호가 아니라 범위 밖(§5).
- 버튼 잠금: 가입은 규칙 검사(72행) **뒤** 약관 확인을 거쳐 81행에서 잠근다 · 재설정은 약 398행에서 잠근다 · **마이페이지 변경은 잠금이 없다.**
- 브라우저에서 해시를 계산하는 코드(`crypto.subtle`)는 `dev/` 에 없다 — 새로 쓴다.

### 1-3. 외부 목록 서비스 — 실측(2026-09-29)

- `GET https://api.pwnedpasswords.com/range/{해시 앞 5글자}` — 열쇠 불필요, 응답 200, 교차 출처 허용(`access-control-allow-origin: *`), 후보 약 2,000줄
- `Password1!` → 목록에 있음(**584,516회**). `sakura-2026-reverb!q` → 없음
- 우리 사이트에는 접속 주소를 제한하는 보안 정책(콘텐츠 보안 정책)이 없다 — 어디로든 요청할 수 있다

### 1-4. 서버 함수 선례

`supabase/functions/qoo10-product-lookup` — 공개 키로 브라우저가 부르고, 서버가 외부 페이지를 대신 읽어 필요한 값만 돌려준다. 교차 출처 허용 헤더·OPTIONS 응답·「실패는 전부 `{ok:false}` 하나」 규칙이 이미 있다.

### 1-5. 개인정보처리방침

- §5(국외 이전) 표의 수탁자 = Supabase·Vercel·Brevo·Google. Have I Been Pwned 는 없다.
- §8.1(외부 서비스로의 정보 송신)은 메타 픽셀 하나 — 회원 브라우저가 외부로 직접 보내는 경우의 선례이고, **공고 30일**을 거쳤다.

### 1-6. 이 제안과 충돌 가능성 있는 기존 동작

- 보안 규칙·기능 문서의 「HIBP 활성」 서술 — 보안 규칙은 이 사양서와 함께(기획), 기능 문서는 단계 1 구현과 함께(개발) 바로잡는다(§3-5)
- 그 밖의 충돌 없음 — 로그인·세션·가입 트리거는 건드리지 않는다

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 깨질 가능성

| # | 분류 | 무엇 | 대응 |
|---|---|---|---|
| ① | 법률 | 회원 브라우저가 외부 서비스에 **직접** 물으면 회원 IP 가 미국 쪽 서비스로 간다 — 방침에 없는 송신이라 메타 픽셀처럼 공고가 필요할 수 있다 | **우리 서버 함수를 거친다**(§3-1). 외부 서비스는 우리 서버 주소와 해시 앞 5글자만 본다. 그래도 **단계 2 를 운영에 내기 전에** `/약관확인` 을 한 번 거친다(§7) |

| ⑤ | 권한 | 관리자 거부가 **화면에서만** 걸린다 — 슈퍼관리자 초기화의 서버 함수를 직접 부르면 우회된다 | 받아들인다. 우회하는 사람이 곧 슈퍼관리자 본인이다. 서버 검사를 넣으려면 데이터베이스 함수가 외부로 나가야 해서 비용이 크다 |

| ⑨ | **UX** | 관리자 초대 화면은 링크로 들어온 **비로그인** 상태다 | 서버 함수는 공개 키로 부를 수 있어 문제없다. 거부 문구는 그 화면의 한국어 문구 체계를 따른다 |

### 2-2. 현재 구현과 어긋나는 지점

- 문서 두 곳의 「HIBP 활성」(§1-1). 그 밖에는 충돌 없음 — §1-6.

### 2-3. 의도 모호점

- 「관리자」 = 관리자 비밀번호를 정하는 세 자리(§1-2 아래 셋). 관리자를 겸한 회원이 **인플루언서 화면**에서 비밀번호를 바꾸면 회원 규칙(경고)이 적용된다 — 인증 계정이 하나라 그 사람의 관리자 비밀번호도 바뀐다. 드문 경우라 받아들인다.
- 「경고」 = 진행을 막지 않는다. 안내 줄이 떠도 회원이 그대로 버튼을 누르면 종전과 똑같이 가입·변경된다.

## 3. 설계

### 3-1. 서버 함수 신설 — 이름은 `password-range-lookup`(가칭, 개발 세션이 정함)

| | |
|---|---|
| 입력 | `{prefix}` — 16진수 **정확히 5글자**(대소문자 무관) |
| 하는 일 | `https://api.pwnedpasswords.com/range/{prefix}` 를 읽어 그대로 돌려준다. 요청 머리 `Add-Padding: true`(응답 길이로 추측하지 못하게) |
| 출력 | `{ok:true, lines:"…"}` / 실패는 전부 `{ok:false}` |
| 관문 | 형식 검사 하나(§2-1 ③). 로그인·토큰 불필요 |
| 기록 | 받은 5글자를 로그에 남기지 않는다 |
| 선례 | `qoo10-product-lookup` 의 교차 출처 헤더·OPTIONS 응답·실패 규칙을 그대로 따른다 |

- **Supabase 인증 설정의 유출 검사는 꺼 둔 채로 둔다.** 켜면 서버가 회원을 거부해 「경고만」이 성립하지 않는다.

### 3-2. 판정 함수 — 브라우저

```
commonPasswordCheck(pw) → 'common' | 'ok' | 'unknown'
  1. SHA-1(pw) → 16진수 대문자 40글자
  2. 앞 5글자로 서버 함수 호출 (3초 상한)
  3. 돌아온 줄 가운데 나머지 35글자와 같은 것이 있고 횟수가 0보다 크면 'common'
  4. 없으면 'ok' / 해시 계산·호출·응답 실패는 전부 'unknown'
```

- `'unknown'` 은 **통과로 다룬다**(§2-1 ②).
- `Add-Padding` 으로 섞여 오는 횟수 0 짜리 줄은 `'common'` 으로 치지 않는다.
- 🔴 **같은 판정이 두 곳이 된다** — `dev/js/ui.js` 와 `dev/admin-setpw.html`(자립형이라 `ui.js` 를 안 싣는다). 규칙 판정(`passwordPolicyIssue` / `validateAdminPassword`)과 **같은 두 곳**에 둔다. 사본이 더 늘지 않게, 두 곳에 서로를 가리키는 주석을 단다.

### 3-3. 회원 화면 — 경고 (세 곳)

**버튼을 막지 않는다.** 비밀번호 칸 아래에 안내 줄만 띄운다(§6 ①).

| 언제 판정하나 | 새 비밀번호 칸에서 입력을 멈추고 약 0.6초가 지났을 때, 또는 칸을 떠날 때. **규칙 검사(8자·소문자·기호)를 통과한 값만** 판정한다 — 규칙 위반이면 판정하지 않는다 |
|---|---|
| `'common'` | 칸 바로 아래 노란 안내 줄(§6 ② 문구). 버튼은 그대로 눌리고, 누르면 종전과 똑같이 보낸다 |
| `'ok'` · `'unknown'` | 안내 줄을 지운다 |

- **늦게 온 응답은 버린다** — 판정하는 사이 회원이 값을 바꿨으면, 바뀐 값의 판정만 반영한다.
- **판정이 끝나기 전에 버튼을 눌러도 기다리지 않는다** — 경고만인 기능이라 전송을 늦출 이유가 없다. 그래서 세 화면 모두 **버튼 잠금을 새로 만들지 않는다**(마이페이지에 잠금이 없는 것도 그대로 둔다).
- 대상 칸: 가입 `signupPw` · 재설정 `resetPwNew` · 마이페이지 `newPw`(확인용 두 번째 칸 `signupPw2`·`resetPwConfirm`·`newPw2` 는 판정하지 않는다).
- 안내 줄은 **새 요소로** 만든다(지금 그 자리에 쓸 요소가 없다). 기존 규칙 안내 줄(`.pw-policy`)·오류 줄(`signupError`·`resetPwError`·`pwChangeError`)과 겹치지 않게. ⚠️ 마이페이지는 두 칸이 한 줄에 반씩 놓인 구조라 안내 줄이 반쪽 폭에 들어간다 — 글이 몇 줄로 접혀도 읽히는지 볼 것.
- 마이페이지는 변경에 성공하면 칸을 비운다(`mypage.js` 성공 처리) — **그때 안내 줄도 함께 지운다.**
- 경고를 보고 진행했는지 **기록하지 않는다** — 새로운 정보 수집이 되기 때문이다.

### 3-4. 관리자 화면 — 거부 (세 곳)

**버튼을 누를 때** 판정한다(규칙 검사 통과 뒤, 서버로 보내기 전).

| 판정 | 화면 |
|---|---|
| `'common'` | 거부. 「많은 사람이 쓰는 비밀번호라 사용할 수 없습니다. 다른 비밀번호를 입력해 주세요.」 |
| `'ok'` · `'unknown'` | 종전대로 진행 |

- 판정하는 동안(최대 3초) **버튼을 잠근다** — 거부가 걸려 있어 두 번 눌러 판정 전에 보내지면 안 된다.
  - `admin-setpw.html` 은 잠금이 이미 있다(규칙 검사 뒤 · `updateUser` 앞) — 판정을 그 잠금 **뒤**, `updateUser` 앞에 넣고 거부면 잠금을 푼다
  - `changeMyAdminPassword`·`executeResetPw` 는 잠금이 없다 — 새로 만든다

- 문구는 규칙 위반 문구와 같은 자리(오류 줄)에 같은 모양으로 띄운다.
- 관리자 초대 화면(`admin-setpw.html`)은 현재 오류 시 「링크가 만료되었을 수 있습니다」로 안내한다 — 이 거부는 서버로 보내기 **전에** 걸리므로 그 문구와 섞이지 않는다.

## 4. 단계

| 단계 | 내용 | 파일 | 선행 |
|---|---|---|---|
| **1** | 서버 함수(§3-1) + 판정 함수 두 곳(§3-2) + **관리자 거부** 세 곳(§3-4) + 기능 문서 | `supabase/functions/{새 함수}/index.ts` · `dev/js/ui.js` · `dev/admin-setpw.html` · `dev/js/admin-accounts.js` · `docs/FEATURE_SPEC.md` | 없음 |
| **2** | **회원 경고** 세 곳(§3-3) + 번역 문구(`dev/lib/i18n/{ja,ko}.js`) + 안내 줄 자리(`dev/index.html`) | `dev/js/auth.js` · `dev/js/mypage.js` · 번역 두 파일 · `dev/index.html` | 1 |

- 단계 1 은 회원 화면을 건드리지 않아 방침과 무관하다(관리자는 직원).
- 단계 2 는 **운영에 내기 전에** `/약관확인` 을 거친다(§7). 착수와 개발서버 반영은 그 전에 해도 된다.
- 서버 함수는 **개발·운영 각각 배포**한다(git 병합으로 반영되지 않는다). 🔴 **함수를 먼저 배포하고 화면을 나중에** — 반대면 화면이 없는 함수를 불러 `'unknown'` 이 되어 조용히 검사 없이 지나간다(막히지는 않지만 효과가 0).
- 데이터베이스 변경 없음 — 마이그레이션 없음.

- 관리자 2단계 인증
- 리포트 공유 링크 비밀번호(`enable_report_share`·`reset_report_share_password`) — 계정 비밀번호가 아니다

## 6. 사용자 결정 (2026-09-29)

- ✅ **① 회원 경고 위치** — **비밀번호 칸 아래 안내 줄**. 버튼은 막지 않는다. (다른 안이었던 「버튼을 누를 때 확인 창」은 고르지 않았다)
- ✅ **② 회원 경고 문구** — **A**
  - 「このパスワードは多くの人に使われていて、推測されやすいパスワードです。別のパスワードをおすすめします。」 — "이 비밀번호는 많은 사람이 쓰고 있어 추측되기 쉽습니다. 다른 비밀번호를 권합니다."
  - 고르지 않은 B(「他のサービスから流出したパスワードの一覧に含まれています」 — "다른 서비스에서 유출된 비밀번호 목록에 들어 있습니다")는 「내 계정이 털렸나」로 읽혀 문의가 생긴다
  - 한국어 번역 파일에는 위 한국어 뜻을 쓴다
- 관리자 거부 문구(§3-4)는 한국어 화면 문구라 따로 확인받지 않았다

## 7. 약관·개인정보

- 단계 1: 관리자(직원)만 대상 — 영향 없음
- 단계 2: 회원 브라우저 → **우리 서버 함수**(Supabase — 이미 수탁자) → 외부 서비스. 외부로 가는 것은 **우리 서버 주소와 해시 앞 5글자**뿐이고, 5글자로는 비밀번호도 사람도 특정할 수 없다. 기획 판단은 **방침 개정 불필요**. 단 단계 2 를 운영에 내기 전 `/약관확인` 으로 한 번 확인한다
- 서버 함수를 거치지 않고 브라우저가 외부 서비스에 직접 묻는 방식으로 바꾸면 **이 판단이 뒤집힌다**(회원 IP 가 외부로 간다) — 그 경우 기획 세션에 되돌린다
