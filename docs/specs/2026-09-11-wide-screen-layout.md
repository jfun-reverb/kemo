# 넓은 화면(아이폰 폴드 「iPhone Duo」·아이패드) 대응 — 사양서

**작성일:** 2026-09-11 · **작성:** 기획 세션 · **받는 곳:** 개발 세션(웹)
🔴 **범위 변경(2026-09-11 오후, 사용자 결정):** 이 사양서는 **웹(브라우저)만** 다룬다. iOS 앱은 「좌우 여백 없이 채우기 + iPad 2단·3단」으로 가기로 해 **별도 iOS 사양서**(작성 예정)가 맡는다. 앱은 웹 CSS 를 번들로 그대로 싣기 때문에, 이 사양의 규칙(기둥 720·안전영역·시트 등)을 앱에서 어떻게 덮어쓸지는 그 iOS 사양서가 정한다. 아래 본문에서 「iOS」가 나오는 자리는 **사실 기록**(기기·빌드·브랜치 상태)이거나 **iOS 사양서로 넘긴 것**이다.
**근거 조사:** `docs/specs/2026-09-11-wide-screen-current-state-survey.md`(iOS 개발 세션, 2026-09-11) — 이 사양서는 그 조사의 주장을 **코드로 다시 대조**한 뒤 쓴다(§1-1).
**사용자 결정(2026-09-11, iOS 세션 경유):** ①대상 기기 = 아이폰 폴드 + 아이패드 전 기종 ②범위(폭만 채우기 / 열 수를 늘리는 새 배치)는 기획이 정한다.

## 0. 한 줄 결론 — 범위는 「폭 채우기 + 카드 3열」까지, 「새 배치」는 뒤로

**기둥(`#appShell`)을 없애지 않고, 화면 폭 600 이상에서만 상한을 480 → 720 으로 올린다**(600 미만은 지금 그대로). 같은 조건(600 이상)에서 글과 입력칸은 **읽기 폭 560** 으로 묶고, 캠페인 카드만 **3열**로 늘린다. 상세 2단·마이페이지 사이드바 같은 **「새 배치」는 이 사양의 범위 밖**이다 — 그것은 Apple 지침 기반 화면 재설계(`.claude/rules/planning.md`)에서 화면 통째로 다룬다.

왜 이렇게 자르나 —
- 기둥이 **떠 있는 요소 전부의 기준 상자**다(원리는 조사 §2-1, 목록은 조사 §2-3 — 이 사양은 개수를 따로 세지 않고 그 목록을 그대로 가리킨다). 기둥을 버리면 그 전부를 다시 앉혀야 하고, 그 작업은 화면 재설계와 겹친다.
- 폴드 속 화면을 가장 먼저 받는 것은 **Safari 웹**이다(앱은 iOS 27 SDK 이전 빌드라 폭을 못 받는다, §1-2 — 앱은 별도 iOS 사양서). 웹에서 먼저 얇은 층을 깔아 두는 편이 순서상 맞다.
- 새 배치는 화면마다 설계 결정이 따로 든다. 얇은 「폭 대응 층」을 먼저 깔고, 재설계가 그 위에서 열 수를 정하는 편이 두 번 일하지 않는다.

### 1-2. 기기 사실 (외부 — 2026-09-11 웹 확인)

아이폰 폴드의 공식 이름은 **iPhone Duo**(2026-09-09 발표, 10월 출시). 개발자에게 중요한 것만:

| 항목 | 값 | 우리에게 뜻하는 것 |
|---|---|---|
| 밖 화면 | 5.4형, **466 × 678 pt** | 세로(466)는 480 보다 좁다 → **지금 폰과 같은 취급**. 가로(678)는 폰 가로와 같이 「넓음」(아래 폭 구간) |
| 속 화면 | 7.6형, **669 × 951 pt** (세로 기준. Apple 이 pt 를 공표하지 않아 개발자 커뮤니티 계산값 — 626×890 이라는 계산도 있다. **어느 쪽이든 600 보다 넓어 「넓음」이고 720 상한 안에 든다**) | 기둥 720 이면 **속 화면을 꽉 채운다** |
| 기기 분류 | **아이폰**(idiom). 속 화면은 가로·세로 모두 「regular」 크기 클래스 | 아이패드 전용 설정(`~ipad`)은 안 탄다 |
| 방향 | 🔴 **속 화면에서는 앱의 방향 잠금(`UISupportedInterfaceOrientations`)을 시스템이 무시한다** | 세로 잠금이 있어도 속 화면은 **가로(951×669)로도 뜬다** |
| 안전영역 | 다이내믹 아일랜드가 세로로 서 있어 **좌우 인셋이 비대칭** | `env(safe-area-inset-left/right)` 가 0건인 지금은 그 자리에 내용이 깔린다 |
| 접힘선 | 시트·알림·메뉴는 시스템이 접힘선을 피해 옮긴다 | 웹뷰 안 요소는 우리 몫 |
| 🔴 옛 SDK 빌드 | **iOS 27 SDK 이전으로 빌드한 앱은 속 화면에서 「익숙한 크기·비율」로만 뜬다**(폭을 다 못 받는다). iOS 27 SDK 는 상태바 왼쪽까지, iOS 27.1 SDK 는 화면 끝까지 | 우리 앱은 **Xcode 26.6** 빌드 → Duo 속 화면 대응은 **Xcode 27.1(9월 말 베타) 재빌드 뒤에야** 효과가 난다. 그 전에는 **Safari 웹에서만** 넓은 화면을 받는다 |

아이패드 CSS 폭(세로 기준, 근사): 미니 **744** · 11형 **820~834** · 13형 **1032**. 가로 1133~1376. 분할 화면은 **320** 부터.

→ **폭 구간**: 320(분할·슬라이드 오버) · 375~440(폰 세로) · 466(Duo 밖 세로) · **667~932(폰 가로·Duo 밖 가로 678 — Safari 웹에서만, 앱은 세로 잠금)** · **669(Duo 속)** · 744~1032(아이패드 세로) · 951(Duo 속 가로) · 1133~1376(아이패드 가로). ⚠️ **폰 가로는 600 을 넘어 「넓음」이다** — 지금도 폰 가로는 480 기둥에 양옆 회색이라 폰 관습이 아니었고, 이 사양 뒤에는 720 기둥이 된다(§3-4). 이 사양은 **600 을 경계**로 「좁음(지금 그대로)」과 「넓음(이 사양)」을 가른다(§3-0).

### 1-3. 관련 결정·문서

- **앱 화면 로딩 방식(A 운영 주소 직접 / B 번들+무선 업데이트 / C 번들+재심사)은 아직 미결**(`docs/specs/2026-07-14-influencer-app-transition-handoff.md` §3, 2026-07-14 고문 → 기획 인계, 기획 미착수). 지금 앱은 **번들 스냅샷**이라 웹을 고쳐도 앱은 재빌드 전엔 안 바뀐다. **이 사양은 그 결정과 독립**이다 — 어느 쪽이든 CSS 는 같다. 다만 「언제 앱에 닿나」가 그 결정에 달렸다.
- **iOS 브랜치의 웹 공용 수정 2건 미이식**(`docs/specs/2026-08-26-ios-shared-fixes-handoff.md`). 이 사양과 파일이 겹칠 수 있다(`campaign.css`·`components.css` — 자바스크립트는 이 사양이 안 고치므로 안 겹친다) — 순서는 iOS 사양서가 정한다.
- **Apple 지침 기반 화면 재설계**(`.claude/rules/planning.md` 「인플루언서 화면 설계 기준」, 2026-09-02 사용자 결정 — 기존 화면도 순차 재작업, 단위는 화면 통째). 이 사양은 **재설계가 아니다**(색·글자·구성 요소를 안 바꾼다). 재설계는 이 사양이 만드는 변수(§3-0) 위에서 열 수를 정한다.

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 깨질 수 있는 경우

1. **(기술) 상세 정사각 히어로가 화면을 삼킨다.** 기둥 720 에서 `#campSlider` 는 안쪽 폭 688(=720−32, §3-4 계산식)의 정사각이라 688px 높이. 아이패드 가로(높이 820)·Duo 속 가로(높이 669)에서 **첫 화면이 사진 하나**가 된다. → 히어로에 상한을 둔다(§3-2 「상세 히어로」).
2. **(기술) 접었다 펴는 순간.** 폭을 읽는 자바스크립트가 0건이라 CSS 가 다시 계산하면 끝난다. `adjustHeight` 는 높이만 다시 쓰고 폭은 `width:100%` 라 저절로 맞는다. 사진 넘김은 퍼센트 이동이라 안 어긋난다. **다만 지금은 확인 수단이 없다** — Duo 시뮬레이터는 Xcode 27.1 뒤, 실기기는 손에 들어온 뒤(§3-5 ⑥). 그 전엔 크롬 반응형 모드에서 폭을 바꿔 보는 것으로 대신한다(§3-5 ②).
3. **(데이터) 썸네일이 흐려진다.** 카드 한 장 폭은 **§3-4 의 계산식 한 벌**로 센다 — 넓은 폭 3열 최대 약 221px(기둥 720), 지금 2열 약 218px(기둥 480). 3px 차이이고 221 × 2배 화면 = 442 기기 픽셀 < 720 파일이라 **카드는 그대로 충분**. 상세 사진(첫 장·둘째 장 모두 720 파일, §1-1)은 560 상한 × 2배 화면 = 1120 기기 픽셀을 720 으로 그린다(지금은 웹 기둥 안쪽 448 × 2배 = 896 → 이미 1.24배 확대, 이 사양 뒤 1.56배). **눈에 띄는지는 실기기로 봐야 안다.** 띄면 저장 폭을 올리고 소급 도구(`scripts/backfill-storage-thumbs.js`)를 다시 돌린다 — 이 사양은 **저장 폭을 건드리지 않는다**(§3-3).
4. **(환경) iOS 앱은 이 사양의 범위 밖이고, 두 겹으로 늦다.** ①앱은 번들 스냅샷이라 웹 CSS 가 dev 에 들어가도 iOS 브랜치가 다시 병합·재빌드하기 전엔 안 실린다(§1-1) ②Xcode 26.6 빌드라 Duo 속 화면에서 폭을 못 받는다. **Duo 대응의 첫 효과는 Safari 웹**이고, 앱 몫(채우기·2단·3단)은 별도 iOS 사양서 + Xcode 27.1 재빌드 뒤다.
5. **(UX — 필수) 아이패드 가로에서 「폰 앱을 가운데 놓은 모양」이 남는다.** 1180 폭에 720 기둥이면 양옆 230px 씩 회색. 이건 **범위를 「새 배치 없이」로 자른 결과**이고 이 사양의 가장 큰 의도적 한계다. 사용자가 이 모습을 받아들이기로 **확정**(§4 Q1).
6. **(UX) 읽기 폭을 빠뜨린 화면만 줄이 길어진다.** 규칙을 「목록에 있는 선택자」에만 걸면, 목록에서 빠진 화면 하나가 688px 한 줄 일본어를 보여 준다. → 적용 목록을 사양서에 박고(§3-2 「읽기 폭」), 검증 때 **화면별로 한 번씩** 본다.
7. **(UX) 아래 붙는 시트가 720 폭으로 늘어난다.** 시트 폭이 기둥을 따라가므로(§3-2) 넓은 화면에서 응모 모달·약관 창·로그인 안내(인라인 480 을 지운 뒤)가 720px 짜리 아래 붙는 시트가 된다 — 폰 관습을 태블릿 폭으로 늘린 모양. Apple 지침은 넓은 폭(regular)에서 시트를 **가운데 카드**로 바꾼다. → 가운데 카드형으로 확정(§3-2 「시트」·§4 Q2).
8. **(영향 기록 — 이 사양은 결정을 내리지 않는다) iOS 알약 탭바가 기둥을 따라 늘어난다.** `calc(100% - 32px)`(과 뒤로 단추 켜짐 변형)이 기둥을 따라간다 — 앱이 이 CSS 를 그대로 실으면 넓은 폭에서 탭 4개가 손이 닿는 거리를 넘는다. → **iOS 사양서 몫**(앱은 기둥 자체를 풀기로 해 탭바 자리를 거기서 새로 정한다).
9. **(UX) 좁은 폰이 같이 바뀌면 안 된다.** 카드 열을 `auto-fill` 로 하면 375 폭 폰(SE·mini)이 **1열로 줄어든다**(343px 안에 200px 두 장이 안 들어간다). → 자동 채움이 아니라 **폭 경계 600 에서 3열로 바꾸는 규칙**으로 하고, 검증 때 390·375 폭 스크린샷이 **변경 전과 픽셀 단위로 같은지** 본다(§3-5 ① 양성 대조).
10. **(환경) PC 웹도 함께 바뀐다.** `dev/css` 를 고치면 PC 크롬에서 보는 인플루언서 웹이(창 폭 600 이상이면) 480 → 720 기둥이 된다. 관리자 미리보기(400px)는 안 바뀐다. **PC 웹의 모습이 바뀌는 것**을 사용자가 알고 수용하기로 **확정**(§4 Q3).
11. **(환경) 분할 화면·슬라이드 오버(320~).** 기둥이 `width:100%` 라 320 에서도 지금 폰과 같이 뜬다. 이미 열려 있고 이 사양은 막지 않는다(§3-1 #6). 다만 **320 은 어떤 폰보다 좁아**(가장 좁은 폰 375) 지금도 본 적 없는 폭이다 — 검증 목록에 넣는다.
12. **(법률·약관)** 없음 — 수집 항목·외부 서비스·개인정보 흐름 변화 0.
13. **(권한)** 없음 — 인플루언서 화면만, 로그인 여부와 무관.

### 2-2. 현재 구현과 어긋나는 지점
§1-4 표 8줄 중 **실제로 이 사양이 바꾸는 2줄** — `.camp-grid` 2열 · 상세 슬라이더 정사각(둘 다 `≥600` 에서만). 나머지 6줄(회색 배경 미디어 쿼리·회원가입 카드 인라인 560·`#cropModal`·관리자 `.form-row`·관리자 미리보기·필터 80px)은 **그대로 두거나 영향 없음**. 그 밖에 **충돌 없음 — 웹 4개 영역(CSS 5파일·index.html·인플루언서 JS·관리자 미리보기) 확인 완료.** 범위 밖 2개(iOS 테마·Info.plist)는 「안 건드림」만 확인.

## 3. 설계

### 3-0. 원칙
- **화면 재설계가 아니다.** 색·글자 크기·구성 요소·기능 동작은 그대로. 바뀌는 것은 **넓은 폭(≥600)에서의 상자 크기와 자리**뿐 — 시트가 아래 붙음에서 가운데 카드(페이드 등장)로 옮겨 앉는 것(§3-1 #5)까지가 그 범위다.
- **스타일만 고친다** — 고치는 파일: 웹 CSS **5파일**(`base`·`components`·`auth`·`campaign` + `mypage` — 마지막은 읽기 폭 선택자 몫만, §3-2 전체 목록 1항) + `index.html` 인라인 스타일 3곳(로그인 안내 창 한 곳의 부모·자식 — 마크업 구조는 그대로, 클래스 둘 붙이는 것까지). iOS 테마 파일은 **안 건드린다**(iOS 사양서). **자바스크립트 0줄, 데이터베이스 0.** 새 `≥600` 블록은 **파일 끝(기본 규칙 뒤)**에 둔다 — 같은 선택자·같은 특이도라 소스 순서가 이긴다(시트 4자리·`.hero-sub`·`.auth-card` 모두 같은 구조).
- **값은 한 곳, 그리고 기본값은 지금 값.** `base.css` `:root` 에 변수 둘 — `--shell-max:480px`(기둥 상한, **기본은 지금과 같은 480**) · `--reading-max:560px`(읽기 폭). 그리고 `@media(min-width:600px){:root{--shell-max:720px}}` — **넓은 폭에서만 720 으로 올린다.** 변수를 쓰는 9자리(아래)는 이 한 줄로 함께 넓어진다 — 그중 시트 4자리는 같은 조건에서 560 으로 다시 좁힌다(§3-2 「시트」).
- 🔴 **600 미만은 한 픽셀도 안 바뀐다 — 결과 기준, 예외 없음.** 보장하는 방법은 둘 중 하나 — ①새 규칙을 `min-width:600px` 블록 안에 둔다(읽기 폭·시트·카드 열·안전영역·상한 720) ②블록 밖에 두는 규칙은 **600 미만에서 지금과 같은 값을 낸다**(`:root` 기본값 480 = 지금 값 / `.login-prompt-sheet{max-width:var(--shell-max);border-radius:20px 20px 0 0}`·`.login-prompt-overlay{align-items:flex-end}` = 옮겨 온 인라인 셋과 같은 값). 그래서 481~599(폰 가로 아님·창을 줄인 PC 등)도 지금처럼 「480 기둥 + 옆 회색」이고, 회색 배경 미디어 쿼리(`min-width:481px`)도 **손대지 않는다**. 폰 **세로**(375~440)가 양성 대조(§3-5 ①), 481~599 는 §3-5 ②의 540 이 본다. 폰 **가로**(667~932)는 「넓음」이라 바뀐다(§1-2).
- **480 이 박힌 8곳 + 기둥(`#appShell`) = 9자리 전부 `var(--shell-max)` 로 바꾼다**(그중 `#loginPromptOverlay` 자식의 **480 이 박힌 인라인 1곳**은 지우고 `components.css` 의 `.login-prompt-sheet` 로 옮긴다 — 자리 수는 그대로 9. 그 창에서 지우는 인라인은 셋이지만 480 자리는 이 하나뿐, §3-2). 숫자를 남기면 다음에 상한을 옮길 때 또 센다.
- **미디어 조건은 둘뿐** — `min-width:600px` · `min-width:600px and (orientation:landscape)`(상세 히어로 한 곳). 🔴 **2026-09-11 정정 — 가로 조건은 없앴다(§5 「대표 사진 크기 정정」). 지금 새로 들어간 것은 `min-width:600px` 한 종류뿐이다.** 아래는 그 전 서술이다. **이 사양이 새로 넣는 미디어 조건은 이 둘뿐**(기존 `min-width:481px` 는 그대로 남는다 — 「변경분」 기준). 블록 수는 세지 않는다(같은 조건은 파일마다 한 블록에 모은다 — 조건이 다르면 블록도 다르다. 개수는 「구현 결과」에 사실만 적는다).

⚠️ **가로로 누운 짧은 화면에서는 사진이 꽤 작아진다** — 아이패드 가로 **260** · 폴드 속 가로 **234**. 높이로 묶는 규칙의 당연한 결과다. 너무 작다고 느껴지면 최소값을 함께 거는 방법이 있다(`min(560, max(280px, 35vh))`) — 지금은 안 걸었다.

**무엇이 깨졌나** — `.modal`·`.modal-overlay` 는 **관리자 화면도 쓰는 공용 클래스**인데(관리자 마크업 54·56곳 + 관리자 자바스크립트가 만드는 것 21곳) 그 둘만 `#appShell` 로 안 좁혀져 있었다. `components.css` 는 **관리자 빌드에도 이어붙여지고**(`dev/build.sh` 의 `ADMIN_CSS_FILES`), 관리자 화면은 폭이 **늘 900 이상**(`#page-admin .admin-layout{min-width:900px}`)이라 넓은 화면 규칙이 **상시** 걸린다. 그래서 관리자의 작은 확인·알림 창이 아래 붙는 시트에서 **가운데 카드**로, 모서리 위쪽만 28px 에서 **사방 20px** 로, 올라오기에서 **페이드**로 바뀌고 상한도 480 → 560 이 됐다.

⚠️ **`.form-row` 는 같은 이유로 이미 `#appShell` 로 좁혀 놨는데 `.modal` 두 개만 빠졌다** — 같은 판단을 한 곳에만 적용한 전형적인 누락이다.

**어떻게 고쳤나** — `.form-row` 와 같은 방식. 기본 `.modal` 은 **480 리터럴로 되돌려** 관리자를 지금 그대로 두고, 기둥 안쪽만 `#appShell .modal{max-width:var(--shell-max)}` 로 변수를 쓴다. 넓은 화면 규칙 둘도 `#appShell .modal`·`#appShell .modal-overlay` 로 좁혔다.

**관리자에 닿는 선택자 전수 확인**(마크업 + 관리자 자바스크립트 양쪽)

|---|---|---|
| `.modal` · `.modal-overlay` | **54·56 + 자바스크립트 21** | `#appShell` 로 좁힘 |
