# 인플루언서 화면 → iOS 앱 전환 인수인계 (HANDOFF)

**작성일:** 2026-07-14
**작성:** 고문 세션
**받는 곳:** 기획 세션(reverb-planner)
**성격:** 방향만 확정 · 아키텍처·파이프라인 상세 설계는 기획이 결정

---

## 1. 배경 (사용자 의도)

- 베타 오픈 시점부터 **인플루언서(클라이언트) 화면을 앱을 주 운영 채널로 전환**한다.
- 앞으로 **기획·개발 세션이 인플루언서 화면 코드를 고칠 때, iOS 앱에도 반영되는 것을 상시 전제**로 삼는다. 기획 단계부터 "앱 배포까지" 고려한다.
- 사용자 결정(2026-07-14): **지금은 큰 방향만 정하고, 로딩 방식·배포 파이프라인 상세 설계는 기획 세션에 넘긴다.**

---

## 2. 현재 상태 (2026-07-14 코드로 직접 확인)

| 항목 | 확인 결과 |
|---|---|
| 앱 형태 | Capacitor(캐패시터)로 인플루언서 웹 화면을 감싼 **하이브리드 앱**. 별도 앱 코드 아님 — 지금의 웹 화면이 곧 앱 내용물 |
| 화면 로딩 방식 | **번들 방식**. `ios-app/capacitor.config.json`에 `webDir:"www"`만 있고 **운영 주소 직접 로딩 설정(`server.url`) 없음** → 화면 파일을 앱 안에 복사해 로컬에서 띄움 |
| 코드 반영 경로 | `dev/build.sh` → `ios-app/sync-ios.sh`(빌드된 화면을 `www/`로 복사 + iOS 전용 자산 주입) → 앱 재빌드 → **애플 심사 재통과** 필요 |
| 커밋된 앱 파일 | iOS 전용 2개만: `www/ios-theme.css`(디자인 레이어), `www/native-push.js`(푸시). 실제 화면 `www/index.html`은 빌드 산출물이라 `.gitignore` 제외 |
| 위치 | 별도 작업 폴더 `reverb-jp-ios`, 브랜치 `feature/ios-app`. **실험 단계 — 앱스토어 미등록, 개발서버만 연결** |
| iOS 전용 요소 | 안전영역·글라스 네비바·바텀 탭바·GNB 알림 버튼·세그먼트 컨트롤·푸시 토큰 등록. **웹에 없는 오버라이드가 이미 상당함** |
| 심사 인프라 | **미완**: 애플 개발자 계정($99)·푸시 인증키(.p8)·Xcode 권한 설정 없음. 푸시 발송 백엔드도 미구현(토큰 등록 구조만) |

> 근거 메모리: `project_ios_hybrid_app`(하이브리드 앱 실험 전모), `project_beta_launch`(3차 단계 = iOS 앱)

**결론:** 지금 구조 그대로면 인플루언서 화면을 고칠 때마다 앱 재빌드 + 애플 심사(보통 1~7일)를 다시 거쳐야 반영된다. "코드 수정 = 앱 자동 반영"과 가장 거리가 멀다.

## 3. 결정해야 할 핵심 갈림길 — 앱의 화면 로딩 방식

이 결정이 "코드 수정 시 앱 반영" 프로세스 전체를 좌우한다. **먼저 정하지 않으면 어떤 프로세스 규칙을 써도 어긋난다.**

| 방식 | 코드 반영 | 애플 심사 | 오프라인 | 비용·구축 |
|---|---|---|---|---|
| **A. 운영 주소 직접 로딩** (`server.url` 추가) | 웹 배포만으로 **즉시 자동 반영** | 껍데기 바뀔 때만 | ✕ (네트워크 필요) | 설정 한 줄 수준. 단 애플 심사 4.2(최소기능성) 반려 위험 → 푸시 등 네이티브 가치 보강 필요 |
| **B. 자산 번들 + 무선 업데이트(OTA)** | 코드 변경분만 무선 갱신, 심사 우회 | 최소 | ○ | 별도 도구·비용·설정. 애플 OTA 정책 준수 필요 |
| **C. 자산 번들 + 매번 재심사** (현재) | 앱 재빌드 + 심사 | 매번 | ○ | 추가 구축 없음. 단 웹-앱 반영 시차 며칠 |

**고문 권고:** 사용자 목표("클라이언트 코드 = 앱 자동 반영")에 가장 자연스러운 길은 **A(운영 주소 직접 로딩)**. `capacitor.config.json`에 운영 주소 설정 한 줄이면 전환 가능하고, 이러면 기획·개발이 앱을 위해 따로 할 일이 거의 없어져 규칙도 가벼워진다. **단 최종 선택은 기획이 아래 경우의 수를 검토한 뒤 결정.**

## 4. 반대론자 모드 — 기획이 반드시 검토할 경우의 수

1. **애플 심사 4.2(최소기능성) 리스크** — 순수 웹뷰 앱은 "그냥 웹사이트"로 반려될 수 있음. A안 채택 시 네이티브 가치(푸시·기기 기능·오프라인 안내 등)를 심사 전 확보해야 함. 이미 푸시 토큰 등록 구조는 있으나 **발송 백엔드가 미구현**.
2. **"앱으로 전환"의 범위 모호 — 웹 완전 차단 vs 병행** — 웹 접근을 막으면 앱 미설치자·검색 유입·기존 웹 응모자가 끊긴다. 웹뷰 앱이라 본질은 같은 코드이므로 **병행이 자연스러움**. 사용자에게 "전환"이 차단인지 병행인지 확인 필요.
3. **iOS 전용 요소가 웹 수정에 조용히 깨질 위험** — 앱 전용 오버라이드(디자인·탭·푸시·안전영역)가 많아, 기획·개발이 웹만 보고 화면 구조를 바꾸면 앱이 깨진다. 실제 사고 이력 있음(주입 검사 오판으로 테마 통째 누락, 추적에 오래 걸림 — `project_ios_hybrid_app` §sync-ios.sh 사고).
4. **심사·인증서 인프라 전제 미충족** — 개발자 계정·인증키·권한 설정이 없으면 "앱 배포"가 성립 안 됨. 규칙을 박기 전 이 전제부터 갖춰야 함.
5. **안드로이드 계획 유무** — 현재 iOS만. 클라이언트 운영을 앱으로 옮기면 안드로이드 사용자 처리(웹 병행 유지 등)를 정해야 함. (사용자 확인 대상)
6. **웹뷰 인증·세션 취급** — 앱 웹뷰에서 Supabase 세션·비밀번호 재설정 링크·이메일 인증 리다이렉트가 웹과 동일하게 동작하는지. 앱 딥링크·Universal Links 필요 여부.
7. **약관·개인정보 영향** — 앱 스토어 배포 시 앱 개인정보 라벨(App Privacy)·푸시 동의·기기 정보 수집이 추가되면 개인정보처리방침 반영 필요(`/약관확인`).

## 5. 기획이 산출할 것 (이 HANDOFF를 받은 뒤)

1. **로딩 방식 A/B/C 확정** — §3·§4 근거로. 확정 시 사용자 확인(AskUserQuestion).
2. **앱 배포 파이프라인 설계** — 웹 배포와 앱 껍데기 배포의 관계, 심사 주기, iOS 전용 요소 회귀 점검 지점.
3. **"기획·개발이 앱을 챙기는 방식" 프로세스 규칙 후보** — 예: 인플루언서 화면 구조 변경 시 iOS 전용 오버라이드(`ios-theme.css`·탭바·주입 자산) 영향 점검 의무. **규칙 문서화는 아키텍처 확정 후 고문이 담당**(지금 박으면 어긋남).
4. **베타 로드맵 반영** — `docs/specs/2026-06-18-beta-launch-plan.md` §2에 한 줄 갱신(현재 3차 = iOS 앱).

## 6. 규칙화 보류 이유 (고문 메모)

- 이 HANDOFF는 **규칙 파일이 아니다.** 로딩 방식(§3)이 미정인 상태에서 프로세스 규칙을 박으면 A/B/C 중 무엇이 되든 어긋난다.
- 아키텍처 확정 → 파이프라인 설계 → **그 결과를 고문이 `.claude/rules/`에 규칙으로 고정**하는 순서. 적용 범위는 **이 프로젝트 한정**(REVERB JP 앱 운영)으로 판정됨.
- 시행일·약관 영향이 있으면 `.claude/rules/release-timing.md`·`policy.md` 게이트 적용.
