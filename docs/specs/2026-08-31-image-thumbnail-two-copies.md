# 캠페인 이미지 — 올릴 때 두 벌 저장(본체 + 썸네일), 유료 변환 기능 중단

**작성일:** 2026-08-31
**작성:** 기획 세션
**요청:** 「유료를 쓰고 싶지 않다. 방법을 찾아 달라」 → 「두 벌 저장으로 사양서를 써 달라」 (사용자, 2026-08-31)

---

## 왜 하나

Supabase 의 **Storage Image Transformations**(사진을 원하는 크기로 줄여 내보내는 유료 기능)가 한도를 크게 넘었다.

| 항목 | 값 (2026-08-31 실측) |
|---|---|
| Pro 플랜 포함 | **100장** |
| 이번 주기 누적 | **1,710장** |
| 초과 | **1,610장** |
| 단가 | **1,000장당 $5** (`100 origin images included, then $5 per 1000 origin images`) |
| 예상 비용 | **월 $8 안팎** |

- **세는 단위는 「원본 사진 장수」**다 — 공식 문구: 「한 사진을 네 가지 크기로 변환하고 다른 사진을 한 번 변환하면 **2로 센다**」. 같은 사진을 여러 크기로 내보내도 1장이다.
- **결제 주기 첫날(8/24)에 이미 381장**이었다. 어쩌다 넘은 것이 아니라 **매 주기 시작하자마자 넘는다.**

🔴 **아껴서 될 수준이 아니다** — 캠페인 목록을 **한 번 여는 것만으로 고유 사진 103장**을 쓴다(실측). 한도가 100장이다.

## 현재 상태 (규칙 A — 직접 확인함)

### 확인 방법
- 운영 사이트(`globalreverb.com`) 캠페인 목록에서 이미지 주소를 뽑아 **원본 103장의 실제 크기를 전수 측정**
- Supabase 대시보드 Usage 화면(단위·수치·요금표 원문)
- 저장소 코드 — `dev/js/ui.js`·`dev/lib/storage.js`·`dev/lib/image-compress.js`·`dev/js/admin.js`·`dev/js/campaign.js`·`dev/js/application.js`

### 실측 — 지금 저장된 캠페인 사진 (103장)
| | |
|---|---|
| 합계 | **40.1MB** |
| 평균 | **399KB** |
| 500KB 초과 | **16장** |
| 1MB 초과 | **7장** |
| 최대 | **5,021KB (약 5MB)** |
| 480px 로 줄인 것 평균 | **71KB** |

→ **대부분은 이미 작고 소수가 크다.** 변환을 쓰면 목록이 약 7.3MB, 안 쓰면 **40.1MB**(5.5배).

### 관련 코드
| 대상 | 위치 | 상태 |
|---|---|---|
| 변환 주소 생성 | `dev/js/ui.js:276` `imgThumb(url, width, quality)` | `/object/public/` → `/render/image/public/?width=&quality=` |
| 공통 이미지 렌더 | `dev/js/ui.js:287` `renderCroppedImg(url, _ignoredCrop, opts)` | `src`=줄인 주소 · `data-orig`=원본 · **`onerror` 로 원본 폴백** |
| 캠페인 이미지 업로드 | `dev/lib/storage.js:1677` `uploadImage(base64Data, fileName, pathPrefix)` | 🔴 **압축 없이 원본 그대로 저장** |
| 압축 기능 | `dev/lib/image-compress.js:45` `compressImageFile(file, opts)` | **이미 있다.** 기본 긴 변 2048 · 품질 0.85 |

### 🔴 압축 기능은 이미 있는데 캠페인 대표 사진에만 안 걸려 있다
`compressImageFile` 을 쓰는 곳은 **두 군데뿐**이다:
- `dev/js/admin.js:680` `_shrinkRichImage` — 캠페인 **설명글 안** 이미지(가로 1600)
- `dev/lib/storage.js:3867` — 메시지 첨부(2048)

**목록에 뜨는 대표 사진(`img1`~`img8`)은 압축을 안 거친다.** 그래서 5MB 짜리가 그대로 있고, 줄이는 일을 **올릴 때 하지 않고 보여줄 때마다** 하게 됐다.

### ⚠️ 이미 한 번 대응했고 부족했다
`storage.js:1691` 주석:
> `cacheControl: '86400'` — 응답 헤더에 `max-age=86400` 부여 → 브라우저 24h 캐시. 재방문 시 transform/object API 재호출 차단, **Storage Image Transformations 월 한도 보호**

**한도를 의식해 캐시를 이미 걸어 뒀는데도 1,710장이 됐다.** 캐시는 「같은 사람의 재방문」만 막고, **처음 보는 사람마다 새로 센다.** 이 사양은 그 한계를 전제로 한다.

### 이 제안과 충돌 가능성 있는 기존 동작
- **충돌 없음 — 4개 영역 확인.**
  1. **크롭은 표시에 안 쓰인다** — `renderCroppedImg` 주석: 「crop 인자는 하위호환으로 받지만 **무시**」. `image_crops` 는 저장만 되고 화면에 반영되지 않는다 → **썸네일을 만들 때 크롭을 고려할 필요가 없다**
  2. **폴백 구조가 이미 있다** — `data-orig` + `onerror` 로 되돌린다. 썸네일이 없는 사진도 안 깨진다
  3. **캐시 설정은 그대로 둔다** — 이 사양과 무관하게 유효하다
  4. **압축 함수의 기존 호출부 2곳은 안 건드린다** — 인자를 새로 주지 않으면 동작이 같다

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우 6가지

1. **[기술] 🔴 캠페인 사진만 고쳐서는 한도 아래로 안 내려갈 수 있다.**
   1,710장은 **모든 버킷 합계**다. `imgThumb` 는 캠페인 사진 말고 **영수증·리뷰 인증샷**(`admin-deliverables.js` 3곳, `application.js` 2곳)과 **아웃바운드 명단 사진**(`admin-outbound.js`)에도 쓰인다. 캠페인 103장을 없애도 **나머지가 얼마인지 모른다.**
   → **착수 전에 버킷별 비중을 확인할 것.** 캠페인이 대부분이면 이 사양으로 충분하고, 영수증이 크면 그쪽도 같은 처리가 필요하다.
   ⚠️ 영수증은 **개인정보**라 공개 버킷 정책·보존 기간이 캠페인과 다르다. **같은 설계를 그대로 복사하면 안 된다.**

2. **[기술] 기존 103장에는 썸네일이 없다.**
   폴백이 받아 주지만, 폴백은 **404 를 한 번 받고 나서** 원본을 요청한다 — 요청이 두 번이고 그만큼 늦다.
   → 일괄 생성을 **어디까지** 할지 정해야 한다(전부 / 큰 것 16장만 / 안 함).

3. **[UX] 폴백이 도는 사진은 늦게 뜨거나 깜빡인다.**
   목록에 썸네일 있는 것과 없는 것이 섞이면 **어떤 카드는 즉시, 어떤 카드는 두 박자 늦게** 나타난다. 일괄 생성을 안 하면 **기존 캠페인이 전부 그 상태**가 된다.
   → 일괄 생성을 하거나, 하지 않는다면 **그 기간 동안 목록이 고르지 않게 뜬다는 것을 감수**한다고 적어 둘 것.

4. **[데이터] 🔴 복제 캠페인이 같은 파일을 가리킨다.**
   `CLAUDE.md` 경고 — 「복제(`duplicateCampaign`)가 세 칸을 문자열째 복사해 **두 캠페인이 같은 파일을 가리키므로**, 참조 세기 없이 지우면 복제본 이미지가 깨진다」.
   → **썸네일도 같은 성질을 갖는다.** 캠페인을 지울 때 썸네일을 지우면 복제본이 깨진다. **이 사양에서는 썸네일을 지우지 않는다**(용량은 2% 라 여유가 크다).

5. **[기술] 두 벌 중 하나만 실패할 수 있다.**
   본체는 올라갔는데 썸네일이 실패하면? → **본체만 저장하고 넘어간다.** 폴백이 그 사진을 원본으로 그린다. **썸네일 실패가 업로드를 막으면 안 된다** — `_shrinkRichImage` 가 이미 같은 원칙이다(「줄이지 못하는 것이 못 올리는 것보다 낫다」).

6. **[UX] 상세 화면 화질.**
   본체를 1600px 로 줄이면 **원본이 사라진다**(되돌릴 수 없다). 지금 상세 캐러셀은 480px 로 요청하므로 1600px 이면 충분하지만, **나중에 더 큰 화면·인쇄에 쓸 일이 생기면 못 되돌린다.**
   → 본체를 **줄이지 않고 원본 그대로 둘지**도 선택지다(아래 「사용자 확인 필요」).

### 사용자 의도와 다르게 읽힐 수 있는 부분
- **「두 벌」이 무엇과 무엇인지** — 이 사양서는 **본체 + 썸네일**로 읽었다. 「원본 + 줄인 것」이 아니라 **본체도 줄일 수 있다**는 점이 다르다(경우의 수 6).
- **적용 범위** — 이 사양서는 **캠페인 대표 사진(`img1`~`img8`)만** 다룬다. 영수증·아웃바운드는 범위 밖이다(경우의 수 1).

## 설계

### 저장 — 올릴 때 두 벌 만든다
`uploadImage`(`storage.js:1677`)를 고친다. 지금은 받은 그대로 한 벌 저장한다.

| | 크기 | 경로 |
|---|---|---|
| **본체** | 긴 변 **1600px** (원본이 더 작으면 그대로) | `campaigns/{시각}_{난수}.{확장자}` — **지금과 같음** |
| **썸네일** | 가로 **480px** | `campaigns/thumb/{같은 파일명}` |

- 압축은 **이미 있는 `compressImageFile`** 을 쓴다. 새로 만들지 않는다.
- ⚠️ `keepIfSmall: true` 를 준다 — 줄일 필요가 없으면 원본 파일을 그대로 둔다. **다시 그리면 JPEG 가 되어 투명한 PNG 의 배경이 검게 된다**(`CLAUDE.md` 에 기록된 함정).
- ⚠️ **썸네일 실패는 삼킨다**(경우의 수 5).

### 표시 — 썸네일을 먼저, 없으면 본체
`renderCroppedImg`(`ui.js:287`)를 고친다. **호출부 7곳은 안 건드린다** — 지금도 `{thumb:480}` 처럼 크기를 넘기고 있고, 그 값을 **「썸네일을 쓸지」의 표시로만** 해석한다.

```
지금:  src = imgThumb(원본, 480)        ← 유료 변환 주소
바꾼 뒤: src = 썸네일주소(원본)          ← 우리가 저장한 파일
        data-orig = 원본                ← 없으면 onerror 가 여기로 (이미 있는 구조)
```

- **썸네일 주소는 규칙으로 만든다** — `campaigns/xxx.jpg` → `campaigns/thumb/xxx.jpg`. **데이터베이스 칸을 추가하지 않는다.**
- 🔴 **그래서 기존 사진도 안 깨진다** — 썸네일이 없으면 404 → `onerror` → 원본. 이미 있는 폴백이 그대로 받는다.

### 유료 변환 중단
`imgThumb` 을 **캠페인 사진 경로에서** 쓰지 않는다.
⚠️ **함수 자체는 지우지 않는다** — 영수증·아웃바운드가 아직 쓴다(경우의 수 1). 그쪽 판단이 끝나기 전에 지우면 그 화면들이 원본을 받는다.

### 기존 103장
**일괄 생성한다.** 방법은 개발 세션이 정하되, 후보 둘:
- 관리자 화면에 일회성 버튼(브라우저가 내려받아 줄이고 다시 올림)
- 로컬 스크립트(공개 버킷이라 읽기는 자유, 쓰기는 서비스 키 필요)

⚠️ **원본은 지우지 않는다**(경우의 수 4·6).

### 데이터베이스 변경
**없음.** 칸 추가도 마이그레이션도 필요 없다 — 썸네일을 **주소 규칙**으로 찾기 때문이다.

## 사용자 확인 필요

1. **본체를 줄일지** — 긴 변 1600px 로 줄이면 5MB 짜리가 사라져 좋지만 **원본을 되돌릴 수 없다**. ①1600px 로 줄인다 ②원본 그대로 두고 썸네일만 추가한다(저장 용량만 조금 늘고 안전).
2. **기존 103장 일괄 생성 범위** — ①전부 ②500KB 넘는 16장만 ③안 함(폴백에 맡김, 목록이 고르지 않게 뜸).
3. **영수증·아웃바운드** — 이 사양 범위 밖이다. 캠페인만으로 한도 아래로 안 내려가면 그쪽도 판단이 필요하다(경우의 수 1).
