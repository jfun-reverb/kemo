# 이미지 축소 — 유료 변환 기능 끊기

**세 갈래:** ①올릴 때 압축(공통) ②캠페인은 썸네일 한 벌 더 ③영수증은 변환 호출 제거

**작성일:** 2026-08-31
**작성:** 기획 세션
**요청:** 「유료를 쓰고 싶지 않다. 방법을 찾아 달라」 → 「두 벌 저장으로 사양서를 써 달라」 (사용자, 2026-08-31)

---

## 왜 하나

Supabase 의 **Storage Image Transformations**(사진을 원하는 크기로 줄여 내보내는 유료 기능)가 한도를 크게 넘었다.

| 항목 | 값 (2026-08-31 실측) |
|---|---|
| Pro 플랜 포함 | **100장** |
| 이번 주기 누적 | **1,710장** |
| 초과 | **1,610장** |
| 단가 | **1,000장당 $5** (`100 origin images included, then $5 per 1000 origin images`) |
| 예상 비용 | **월 $8 안팎** |

- **세는 단위는 「원본 사진 장수」**다 — 공식 문구: 「한 사진을 네 가지 크기로 변환하고 다른 사진을 한 번 변환하면 **2로 센다**」. 같은 사진을 여러 크기로 내보내도 1장이다.
- **결제 주기 첫날(8/24)에 이미 381장**이었다. 어쩌다 넘은 것이 아니라 **매 주기 시작하자마자 넘는다.**

🔴 **아껴서 될 수준이 아니다** — 캠페인 목록을 **한 번 여는 것만으로 고유 사진 103장**을 쓴다(실측). 한도가 100장이다.

## 현재 상태 (규칙 A — 직접 확인함)

### 확인 방법
- 운영 사이트(`globalreverb.com`) 캠페인 목록에서 이미지 주소를 뽑아 **원본 103장의 실제 크기를 전수 측정**
- Supabase 대시보드 Usage 화면(단위·수치·요금표 원문)
- 저장소 코드 — `dev/js/ui.js`·`dev/lib/storage.js`·`dev/lib/image-compress.js`·`dev/js/admin.js`·`dev/js/campaign.js`·`dev/js/application.js`

### 실측 — 지금 저장된 캠페인 사진 (103장)
| | |
|---|---|
| 합계 | **40.1MB** |
| 평균 | **399KB** |
| 500KB 초과 | **16장** |
| 1MB 초과 | **7장** |
| 최대 | **5,021KB (약 5MB)** |
| 480px 로 줄인 것 평균 | **71KB** |

→ **대부분은 이미 작고 소수가 크다.** 변환을 쓰면 목록이 약 7.3MB, 안 쓰면 **40.1MB**(5.5배).

### 관련 코드
| 대상 | 위치 | 상태 |
|---|---|---|
| 변환 주소 생성 | `dev/js/ui.js` `imgThumb(url, width, quality)` | `/object/public/` → `/render/image/public/?width=&quality=` |
| 공통 이미지 렌더 | `dev/js/ui.js` `renderCroppedImg(url, _ignoredCrop, opts)` | `src`=줄인 주소 · `data-orig`=원본 · **`onerror` 로 원본 폴백** |
| 캠페인 이미지 업로드 | `dev/lib/storage.js` `uploadImage(base64Data, fileName, pathPrefix)` | 🔴 **압축 없이 원본 그대로 저장** |
| 압축 기능 | `dev/lib/image-compress.js` `compressImageFile(file, opts)` | **이미 있다.** 기본 긴 변 2048 · 품질 0.85 |

### 🔴 압축 기능은 이미 있는데 캠페인 대표 사진에만 안 걸려 있다
`compressImageFile` 을 쓰는 곳은 **두 군데뿐**이다:
- `dev/js/admin.js` `_shrinkRichImage` — 캠페인 **설명글 안** 이미지(가로 1600)
- `dev/lib/storage.js` `uploadMessageAttachment` — 메시지 첨부(2048)

**목록에 뜨는 대표 사진(`img1`~`img8`)은 압축을 안 거친다.** 그래서 5MB 짜리가 그대로 있고, 줄이는 일을 **올릴 때 하지 않고 보여줄 때마다** 하게 됐다.

### ⚠️ 이미 한 번 대응했고 부족했다
`uploadImage` 안 주석:
> `cacheControl: '86400'` — 응답 헤더에 `max-age=86400` 부여 → 브라우저 24h 캐시. 재방문 시 transform/object API 재호출 차단, **Storage Image Transformations 월 한도 보호**

**한도를 의식해 캐시를 이미 걸어 뒀는데도 1,710장이 됐다.** 캐시는 「같은 사람의 재방문」만 막고, **처음 보는 사람마다 새로 센다.** 이 사양은 그 한계를 전제로 한다.

### 이 제안과 충돌 가능성 있는 기존 동작
- **충돌 없음 — 4개 영역 확인.**
  1. **크롭은 표시에 안 쓰인다** — `renderCroppedImg` 주석: 「crop 인자는 하위호환으로 받지만 **무시**」. `image_crops` 는 저장만 되고 화면에 반영되지 않는다 → **썸네일을 만들 때 크롭을 고려할 필요가 없다**
  2. **폴백 구조가 이미 있다** — `data-orig` + `onerror` 로 되돌린다. 썸네일이 없는 사진도 안 깨진다
  3. **캐시 설정은 그대로 둔다** — 이 사양과 무관하게 유효하다
  4. **압축 함수의 기존 호출부 2곳은 안 건드린다** — 인자를 새로 주지 않으면 동작이 같다

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우 7가지

1. ✅ **[기술] 🔴 캠페인만 고쳐서는 부족하다 — 실측으로 확정됐다 (2026-08-31 운영 조회).**

   | 종류 | 저장된 장수 | 누가 보나 |
   |---|---|---|
   | 캠페인 대표 사진 | **280** | 회원 전체 |
   | 🔴 **영수증·리뷰 인증샷** | **2,507** | 관리자만 |
   | 메시지 첨부 | 257 | 관리자·본인 |
   | 아웃바운드 명단 | **0** | — |

   목록에 실제로 뜨는 캠페인 사진은 103장이므로 **1,710장 중 약 6%**다. **캠페인만 고치면 한도 아래로 못 내려간다.**
   ⚠️ 착수 전 우려였던 아웃바운드는 **사진이 한 장도 없다**(`rep_image_path` 0건).
   → **범위를 넓힌다.** 아래 「설계 2 — 영수증·메시지 첨부」 참조. **다만 같은 방식이 아니다**(개인정보라 사본을 늘리지 않는다).

2. **[기술] 기존 280장에는 썸네일이 없다.**
   폴백이 받아 주지만, 폴백은 **404 를 한 번 받고 나서** 원본을 요청한다 — 요청이 두 번이고 그만큼 늦다.
   → ✅ **전부 생성하기로 확정**(아래 「확정된 결정」).

3. **[UX] 폴백이 도는 사진은 늦게 뜨거나 깜빡인다.**
   목록에 썸네일 있는 것과 없는 것이 섞이면 **어떤 카드는 즉시, 어떤 카드는 두 박자 늦게** 나타난다. 일괄 생성을 안 하면 **기존 캠페인이 전부 그 상태**가 된다.
   → 일괄 생성을 하거나, 하지 않는다면 **그 기간 동안 목록이 고르지 않게 뜬다는 것을 감수**한다고 적어 둘 것.

4. **[데이터] 🔴 복제 캠페인이 같은 파일을 가리킨다.**
   `CLAUDE.md` 경고 — 「복제(`duplicateCampaign`)가 세 칸을 문자열째 복사해 **두 캠페인이 같은 파일을 가리키므로**, 참조 세기 없이 지우면 복제본 이미지가 깨진다」.
   → **썸네일도 같은 성질을 갖는다.** 캠페인을 지울 때 썸네일을 지우면 복제본이 깨진다. **이 사양에서는 썸네일을 지우지 않는다**(용량은 2% 라 여유가 크다).

5. **[기술] 두 벌 중 하나만 실패할 수 있다.**
   본체는 올라갔는데 썸네일이 실패하면? → **본체만 저장하고 넘어간다.** 폴백이 그 사진을 원본으로 그린다. **썸네일 실패가 업로드를 막으면 안 된다** — `_shrinkRichImage` 가 이미 같은 원칙이다(「줄이지 못하는 것이 못 올리는 것보다 낫다」).

6. **[UX] 🔴 상세 화면 첫 장은 720px 를 요청한다.**
   `dev/js/application.js` 상세 캐러셀 — `const thumb = idx === 0 ? 720 : 480;`. **썸네일을 480 으로 만들면 상세 첫 장이 흐려진다.**
   → 썸네일을 **720px** 로 만들어 목록·상세가 **한 벌을 함께 쓰게** 한다(아래 설계). 목록에서는 필요보다 크지만, **두 벌을 더 만드는 것보다 단순하고 관리할 파일이 하나다.**
   ⚠️ 대가 — 목록이 내려받는 양이 약 7.3MB → **약 15MB** 로 는다(480 평균 71KB → 720 은 대략 두 배). 화면에 보이는 것만 받는 방식이라 체감은 그보다 작다.
   ⚠️ 480 으로 하고 상세만 본체를 쓰는 안도 있으나, 그러면 **상세에서 5MB 짜리를 그대로 받는다.**

7. ✅ **[UX] 본체를 줄이면 원본이 사라진다 — 해소됨.**
   1600px 로 줄이는 안을 검토했으나 **되돌릴 수 없다**는 점 때문에 **본체를 안 줄이기로 확정**했다(아래 「확정된 결정」). 저장 용량에 여유가 커서 줄일 실익도 없었다(아래 「예상 효과」 표 — 저장소 전체가 한도의 1.6%).

### 사용자 의도와 다르게 읽힐 수 있는 부분
- **「두 벌」이 무엇과 무엇인지** — 이 사양서는 **본체 + 썸네일**로 읽었다. 「원본 + 줄인 것」이 아니라 **본체도 줄일 수 있다**는 점이 다르다(경우의 수 6).
- **적용 범위** — **두 갈래를 함께 다룬다**: ①캠페인 대표 사진(`img1`~`img8`) — 두 벌 저장 ②영수증·리뷰 인증샷·메시지 첨부 — 변환 호출만 제거. **아웃바운드는 사진이 0건이라 해당 없음.**
  ⚠️ 초안은 「캠페인만」이었다. 경우의 수 1 의 실측(캠페인은 6%)으로 **범위를 넓혔다.**

## 설계

### 저장 — 올릴 때 두 벌 만든다
`uploadImage`(`storage.js:1677`)를 고친다. 지금은 받은 그대로 한 벌 저장한다.

| | 크기 | 경로 |
|---|---|---|
| **본체** | 🔴 **줄이지 않는다 — 원본 그대로** | `campaigns/{시각}_{난수}.{확장자}` — **지금과 같음** |
| **썸네일** | 가로 **720px** | `campaigns/thumb/{같은 파일명}` |

**본체를 안 줄이는 이유** (사용자 확인 완료, 2026-08-31): 저장 용량에 여유가 크다 — **캠페인 사진 40.1MB 는 한도 100GB 의 0.04%** 이고, **저장소 전체(1.56GB)도 1.6%** 다. 용량 때문이 아닌데 줄이면 **원본을 되돌릴 수 없다.** 썸네일만 있으면 목록·상세 어디서도 5MB 짜리를 받지 않으므로 **줄일 실익이 없다.**
**썸네일을 720 으로 하는 이유**: 상세 첫 장이 720 을 요청한다(경우의 수 6). 목록·상세가 **한 벌을 함께 쓴다.**

- 압축은 **이미 있는 `compressImageFile`** 을 쓴다. 새로 만들지 않는다.
- ⚠️ `keepIfSmall: true` 를 준다 — 줄일 필요가 없으면 원본 파일을 그대로 둔다. **다시 그리면 JPEG 가 되어 투명한 PNG 의 배경이 검게 된다**(`CLAUDE.md` 에 기록된 함정).
- ⚠️ **썸네일 실패는 삼킨다**(경우의 수 5).

### 표시 — 썸네일을 먼저, 없으면 본체
`renderCroppedImg`(`dev/js/ui.js`)를 고친다. **호출부 6곳은 안 건드린다** — 지금도 `{thumb:480}` 처럼 크기를 넘기고 있고, 그 값을 **「썸네일을 쓸지」의 표시로만** 해석한다.

⚠️ **호출부 6곳 중 4곳이 관리자 화면이고, 요청 크기가 작다:**

| 자리 | 요청 크기 | 720px 썸네일을 받으면 |
|---|---|---|
| 관리자 캠페인 목록 | **96** | 필요보다 큼 |
| 관리자 캠페인 목록(다른 자리) | **88** | 〃 |
| 관리자 이미지 묶음 | **144** | 〃 |
| 관리자 미리보기 | 480 | 무방 |
| 회원 캠페인 목록 | 480 | 무방 |
| 회원 캠페인 상세 | 720 / 480 | **딱 맞음** |

🔴 **96px 자리에 720px 사진이 내려온다.** 운영 캠페인 195건이라 관리자가 목록을 훑으면 적지 않다.
→ **그래도 한 벌로 간다.** 관리자용 작은 썸네일을 또 만들면 **파일이 세 벌**이 되고, 관리자는 소수·유선 PC다. **다만 이 사실을 알고 정한 것임을 적어 둔다.**

```
지금:  src = imgThumb(원본, 480)        ← 유료 변환 주소
바꾼 뒤: src = 썸네일주소(원본)          ← 우리가 저장한 파일
        data-orig = 원본                ← 없으면 onerror 가 여기로 (이미 있는 구조)
```

- **썸네일 주소는 규칙으로 만든다** — `campaigns/xxx.jpg` → `campaigns/thumb/xxx.jpg`. **데이터베이스 칸을 추가하지 않는다.**
- 🔴 **그래서 기존 사진도 안 깨진다** — 썸네일이 없으면 404 → `onerror` → 원본. 이미 있는 폴백이 그대로 받는다.

### 설계 「압축」 — 올릴 때 줄인다 (2026-09-01 신설, **모든 갈래의 토대**)

🔴 **캠페인 사진·영수증·리뷰 인증샷이 전부 같은 함수(`uploadImage`, `dev/lib/storage.js`)로 올라가는데 그 함수에 압축이 없다.** 그래서 12MB 짜리가 그대로 저장돼 있다.
→ **그 함수 한 곳에 압축을 넣으면 셋이 한꺼번에 해결된다.** 이미 있는 `compressImageFile` 을 쓴다(새로 만들지 않는다).

#### ✅ 실측 — 효과와 가독성 (2026-09-01)
운영 영수증을 실제 압축 함수(기본값: 긴 변 2048 · 품질 0.85)로 줄여 봤다.

| | |
|---|---|
| 가장 큰 영수증 | **12,198KB** · 3826×5101 → **363KB** · 1536×2048 (**97% 감소**) |
| 12장 표본 합계 | **51.5MB → 2.8MB (94% 감소)** |
| 큰 것 6장 | 7,076~12,198KB → **129~491KB** |
| 평균 크기 6장 | 238~241KB → **86~181KB** (작은 것도 절반) |
| 🔴 **글씨 가독성** | ✅ **사용자 확인 완료 — 2048px 에서 주문번호·구매일·금액이 읽힌다** |

⚠️ **가독성 확인이 이 설계의 전제였다.** 영수증 검수는 관리자가 그 숫자들을 **눈으로 읽는 작업**이라, 아무리 작아져도 글씨가 뭉개지면 쓸 수 없다. 코드 주석의 「영수증 작은 글씨 가독」이 2048 을 정한 근거였는데 **확인된 적이 없었다** — 이번에 원본과 나란히 놓고 확인했다.

#### 적용
| 종류 | 압축 |
|---|---|
| 영수증·리뷰 인증샷 | 긴 변 **2048** (가독성 확인된 값) |
| 캠페인 사진 | 본체는 **안 줄인다**(아래 「썸네일」 절 참조) · 썸네일만 720 |

⚠️ **`keepIfSmall: true` 를 준다** — 줄일 필요가 없으면 원본 그대로 둔다. **다시 그리면 JPEG 가 되어 투명한 PNG 배경이 검게 된다**(기록된 함정).
⚠️ **압축 실패는 삼킨다** — 원본으로 올린다. **줄이지 못하는 것이 못 올리는 것보다 낫다**(`_shrinkRichImage` 가 이미 같은 원칙).

#### 🔴 기존 파일은 그대로다
**앞으로 올라오는 것만** 해결한다. 기존 **영수증 2,604장(1.46GB)** 은 손대지 않는다.
- **일괄 압축은 기술적으로 가능하다**(위 실측이 그 방법 그대로다)
- ⚠️ 그러나 **영수증은 개인정보**다. 2,604장을 브라우저로 왕복시키는 작업이고, **원본이 사라진다.** 별건으로 판단할 것.

### 설계 2 — 영수증·메시지 첨부는 **다르게 한다** (변환 요청만 뺀다)

🔴 **썸네일을 따로 저장하지 않는다.** `imgThumb` 호출만 빼고 **화면에서 작게 표시**한다(`width`/`height` 는 이미 지정돼 있다).

**왜 캠페인과 다르게 하나 — 보는 사람이 다르다:**
| | 캠페인 사진 | 영수증·첨부 |
|---|---|---|
| 보는 사람 | 회원 수천 명 | **관리자 열두 명** |
| 기기 | 휴대폰 | 주로 유선 PC |
| 개인정보 | 아님 | **맞음** (6개월 파기 대상, 마이그레이션 364) |

🔴 **개인정보 사본을 새로 만들지 않기 위함이다.** 썸네일을 저장하면 **파기해야 할 파일이 두 배**가 되고, 364 의 파기 대상 목록도 함께 고쳐야 한다. 지우다 하나를 빠뜨리면 **지웠다고 적고 남아 있는** 상태가 된다.

**대상** — `admin-deliverables.js` 3곳 · `application.js` 2곳 · `admin-outbound.js` 1곳(대상 0건이라 사실상 무해)

#### 🔴 대가를 두 번 쟀고, 첫 번째가 틀렸다 (2026-08-31)

**1차 — 브라우저 화면 표본 (틀림)**
결과물 관리 화면에 뜬 70장을 재서 **합계 15.7MB · 평균 229KB · 최대 776KB · 1MB 넘는 것 0장**을 얻고 **「감당 가능」**이라 적었다.

**2차 — 저장소 메타데이터 전수 (맞음)**
사용자 지시로 **다른 방법**(`storage.objects` 조회)으로 다시 쟀다:

| 구분 | 장수 | 합계 | 평균 | 최대 |
|---|---|---|---|---|
| 🔴 **영수증·인증샷** | **2,604** | **1,457.7MB** | **573KB** | 🔴 **12,198KB (약 12MB)** |
| 캠페인 사진 | 229 | 65.8MB | 294KB | 5,021KB |
| 설명글 이미지 | 10 | 3.9MB | 400KB | 782KB |
| 기타 | 99 | 80.3MB | 830KB | 4,658KB |

🔴 **평균이 2.5배, 최대가 16배 어긋났다.** 「1MB 넘는 것 0장」도 사실이 아니었다.

**왜 틀렸나** — 화면에 뜬 70장은 **첫 화면에 보인 것뿐**이다. 목록이 스크롤할 때 받는 방식이라 **아래쪽 큰 파일들은 애초에 받지 않았고**, 그래서 표본에 안 들어왔다. **표본이 대표성이 있는지 확인하지 않았다.**

#### 다시 계산한 대가
| | |
|---|---|
| 한 화면 70장 기준 | 0.5MB → **약 40MB** (기존 추정 15.7MB 의 2.5배) |
| 개별 최악 | **12MB 한 장** — 그 한 장만으로 체감된다 |
| 전체 | 2,604장 · **1.46GB** — 관리자가 여러 화면을 훑으면 누적된다 |

🔴 **「감당 가능」이라는 1차 판단은 취소한다.** 40MB 는 유선에서도 눈에 띄고, **12MB 짜리 한 장**은 크기와 무관하게 오래 걸린다.

#### → 이 항목은 **사용자 판단이 필요하다** (아래 「미결」)

### `imgThumb` 함수 자체
**지우지 않는다.** 설계 1·2 를 다 해도 호출부가 0 이 되지만, 되돌릴 여지를 남긴다. **죽은 코드가 되는 것은 감수한다** — 지우는 것보다 안전하다.

### 기존 280장
**전부 일괄 생성한다** (사용자 확인 완료, 2026-08-31). 목록에 뜨는 103장만 하면 **어떤 카드는 즉시·어떤 카드는 늦게** 떠서 고르지 않고, 캠페인은 앞으로 늘어나므로 **지금이 가장 적을 때**다. 방법은 개발 세션이 정하되, 후보 둘:
- 관리자 화면에 일회성 버튼(브라우저가 내려받아 줄이고 다시 올림)
- 로컬 스크립트(공개 버킷이라 읽기는 자유, 쓰기는 서비스 키 필요)

⚠️ **원본은 지우지 않는다**(경우의 수 4·6).

### 데이터베이스 변경
**없음.** 칸 추가도 마이그레이션도 필요 없다 — 썸네일을 **주소 규칙**으로 찾기 때문이다.

2차 실측으로 「변환만 빼도 된다」가 한 번 무너졌으나, **「압축」 설계가 들어가면 조건이 달라진다:**

| | 지금 | 압축 적용 후(앞으로 올라오는 것) |
|---|---|---|
| 영수증 평균 | 570KB | **약 200KB 이하** |

선택지 셋:

| | 무엇 | 대가 |
|---|---|---|
| ① **영수증도 썸네일 저장** | 캠페인과 같은 방식 | 변환 0 · 화면 속도 유지. 🔴 **개인정보 사본이 두 배**가 되고 **마이그레이션 364 의 파기 대상 목록을 함께 고쳐야** 한다 |

| ③ **영수증은 그대로 두고 캠페인만** | 설계 1 만 | 변환 **6% 만** 감소 — **유료가 안 끊긴다** |

⚠️ **③ 을 고르면 이 사양서의 목적(유료 끊기)이 달성되지 않는다.** 그 점을 알고 골라야 한다.

## 이 사양서의 한계 (밝혀 둔다)

### 규칙 C 점검 이력
이 세션은 요청 없이 서브 에이전트를 부르지 않는다는 지시를 받아 자가 재독만 했고, **다른 눈은 개발 세션 `reverb-jp-e6` 가 맡았다.**

| 회차 | 설계 축 | 무엇이 왜 바뀌었나 |
|---|---|---|
| 1 | **6건** | 🔴 **미측정 항목이 곁다리가 아니라 임계 경로**임을 짚어 줘서 **영수증 크기를 실제로 쟀다**(0.5→15.7MB, 31배) → 설계 2 를 「측정 후」에서 「지금 가능」으로 · 설계가 넓어졌는데 **「캠페인만 다룬다」 문장이 그대로 남아** 설계 2 와 정면 모순 · 제목이 낡음 · 저장 용량이 **내려받는 양의 숫자를 옮겨 적음**(+15 → +42MB) · 관리자 호출부 4곳이 88~144px 를 요청한다는 사실 누락 · 참조 번호·호출부 개수 |
| 2 | **2건** | 🔴 **1회차에서 표만 고치고 본문을 안 고쳤다** — 「0.04%」가 세 곳에 남아 새 표의 「1.6%」와 어긋남(무엇을 세는지가 다르다) · **이 「한계」 절이 통째로 낡아** 바로 위 「착수 순서」와 정면 모순 |

| 3 | **0건** | 멈춤 조건 도달 |

**추세: 6 → 2 → 0.**

### 🔴 규칙 C 가 못 잡은 것 — 사용자가 잡았다 (2026-08-31)
3회차 검토자가 **「직접 확인 안 한 것: 영수증 70장·15.7MB 측정 그 자체」**를 명시했다. **사용자가 그 재확인을 지시했고, 다른 방법으로 재니 틀렸다**(평균 2.5배·최대 16배).
⚠️ **문서 점검으로는 원리적으로 못 잡는다** — 문서 안에서는 앞뒤가 맞았고, 틀린 것은 **바깥 세계를 재는 방법**이었다.
🔴 **교훈: 표본을 쓸 때는 그 표본이 대표성이 있는지 따로 확인한다.** 화면에 뜬 것만 재면 **화면이 안 보여준 것은 표본에 없다.**

⚠️ **두 회차 모두 「고치는 과정에서 새로 생긴 것」이 있었다.** 표를 고치면 본문을, 범위를 넓히면 「범위」라 적힌 자리를 함께 봐야 한다.
