# 캠페인 목록에 「결과물 현황」 열 추가

**작성일:** 2026-09-03
**작성:** 기획 세션
**상태:** 설계 확정 — 착수 가능

---

## 무엇을 만드나

캠페인 관리 목록의 **「결과물 제출 마감」 열 바로 오른쪽**에, 그 캠페인의 **영수증·결과물 제출·승인 건수**를 보여주는 열을 하나 더한다. 캠페인별 진행현황 화면에 들어가지 않고도 목록에서 한눈에 보기 위한 것이다.

---

## 현재 상태 (규칙 A — 2026-09-03 기준)

### 캠페인 목록 열 구성 (`dev/admin/index.html` 362~383행)

선택칸 · 캠페인 · 채널 · 브랜드 · 제품 · 상태 · 노출 · **신청** · 기간 · 선정기간 · **결과물 제출 마감(379행)** · 조회 · 등록일 · 수정일 · (더보기)

→ **새 열은 379행과 380행 사이.**

### 이미 있는 비슷한 것

| 무엇 | 어디 | 겹치나 |
|---|---|---|
| 「신청」 열 — 승인수/모집수 + 대기 배지 | 캠페인 목록 373행 | **분모가 겹친다.** 새 열의 분모를 「승인 수」로 잡으면 두 열이 같은 수를 다르게 부르게 된다 → 아래 설계에서 정리 |
| 진행바 3종(모집·제출·인증 성공) | 캠페인별 진행현황 화면 | 겹치지 않는다 — 그 화면에 **들어가야** 보인다. 이 열은 목록에서 보려는 것 |
| 인증 성공 막대 | 브랜드 운영현황 미니카드 | 겹치지 않는다(브랜드 단위) |

### 🔴 집계를 가져오는 방식이 이 저장소에 두 가지 있고, 하나는 쓰면 안 된다

| 방식 | 어디 | 판정 |
|---|---|---|
| **서버 집계 함수 1회** — `get_campaign_application_counts()` | 「신청」 열 (`storage.js` `fetchCampaignApplicationCounts`) | ✅ **이 방식을 따른다** |
| **캠페인마다 조회**(N+1) — `hydrateCampCertBars()` | 브랜드 상세 미니카드 (`admin-brand-ops.js` 292행) | ❌ **쓰면 안 된다** |

`storage.js` 171행 주석이 그 이유를 적어 두었다.

> 신청 전건(약 3,000건)을 클라이언트로 전송하던 방식에서 **서버 집계 1회 호출로 전환**

브랜드 상세는 캠페인이 몇 개뿐이라 N+1 을 견디지만, **캠페인 목록은 수백 개**다.

### ⚠️ 「신청」 집계 함수의 현재 원본은 **179**다 (151 아님)

`151_campaign_application_counts.sql` 이 만들었고 **`179_audit_influencer_account.sql` 이 재정의**하면서 **감사용 계정(`is_audit=true`)을 제외**하게 했다.

→ 🔴 **새 함수도 감사용을 제외해야 한다.** 안 그러면 같은 줄에서 「신청 12/20」(감사용 제외)과 「결과물 13/12」(감사용 포함)처럼 **분모보다 분자가 큰** 표시가 나온다.

### 이 제안과 충돌 가능성 있는 기존 동작

**충돌 없음 — 4개 영역 확인**(캠페인 목록 열 구성 / 신청 집계 함수 / 결과물 조회 / 감사용 격리). 기존 함수를 고치지 않고 새 함수 하나를 더한다.

## 의심·경우의 수 (규칙 B)

### 깨질 가능성

**① 🔴 캠페인마다 조회하면 화면이 멎는다**

위 「현재 상태」의 두 방식 중 N+1 을 고르면, 캠페인 200개짜리 목록에서 조회가 200번 나간다. 이 저장소는 **이미 같은 이유로 한 번 방식을 바꿨다.**
- → **서버 집계 함수 1개**를 새로 만든다(데이터베이스 변경 1건).

**② 🔴 감사용 계정을 안 빼면 분자가 분모를 넘는다**

같은 줄의 「신청」 열은 감사용을 뺀 수다. 새 열이 안 빼면 **「12명 승인인데 결과물 13건 승인」** 같은 표시가 나온다.
- → 179 와 **같은 방식으로** 제외한다.

**③ 시딩·방문형에는 영수증 단계가 없다**

리뷰어형만 영수증을 낸다. 시딩·방문형 캠페인 줄에 「영수증 0/12」가 뜨면 **안 낸 것처럼** 보인다.
- → **「해당 없음」과 「0건」을 구분한다.** 결과물 관리 화면의 구매금액 칸이 이미 같은 규칙을 쓴다(사양서 「구매금액 열」 — 「해당 없음」과 「—」를 구분).

**④ 임시저장을 세면 안 된다**

`deliverables` 에는 인플루언서가 올려만 두고 제출하지 않은 임시저장(`draft`)이 섞여 있다. 그걸 「제출」로 세면 실제보다 부풀어난다.
- → **`status <> 'draft'` 를 반드시 넣는다.** 이 저장소는 같은 누락으로 정산에서 한 번 데였다(마이그레이션 318).

**⑤ 반려·취소된 신청의 결과물이 섞인다**

승인됐다가 반려·취소된 신청의 결과물은 검수 대상이 아니다(「검수 불필요」). 그것까지 세면 숫자가 늘어난다.
- → 화면 판정 `isCertExcluded` 와 같은 기준으로 **신청이 `rejected`·`cancelled` 면 제외**한다.

**⑥ UX — 열이 이미 15개다**

하나 더 늘리면 가로로 밀려 오른쪽 열들이 화면 밖으로 나간다.
- → **한 열 안에 두 줄**로 넣는다(영수증 한 줄, 결과물 한 줄). 열 하나만 는다.
- → 폭을 고정해 다른 열이 안 밀리게 한다.

**⑦ UX — 0건일 때 무엇을 보여주나**

아직 아무도 안 낸 캠페인(모집 중·시작 전)은 전부 0이다. 그 줄에 「0/0」이 뜨면 눈에 거슬리고, 승인 0명이면 분모도 0이라 나눗셈이 안 된다.
- → **승인이 0명이면 「—」** 를 표시한다. 「아직 볼 것이 없다」와 「냈는데 0건」이 구분된다.

**⑧ 조회 실패와 0건을 구분한다**

집계 조회가 실패하면 이 저장소 관행대로 빈 맵으로 폴백하는데, 그러면 **모든 줄이 0으로 보인다.**
- → 조회 실패 시 그 칸을 **「—」로 두고 0으로 그리지 않는다**(기존 `fetchCampaignApplicationCounts` 는 실패 시 `{}` 를 돌려주므로, 화면에서 「값이 없음」과 「0」을 구분해야 한다).

### 현재 구현과 어긋나는 지점

**충돌 없음 — 확인 완료.** 다만 하나를 **맞춰야** 한다 — 새 함수의 감사용 제외 방식을 **179 와 같게**. 다르면 같은 줄의 두 열이 서로 다른 모수를 쓴다.

### 사용자 의도와 다르게 읽힐 수 있는 부분

1. **「승인 현황」이 무엇의 승인인가** — 이 사양서는 **결과물 검수 승인**(`deliverables.status='approved'`)으로 읽었다. 신청 승인이 아니다.
2. **「인증 성공」은 넣지 않는다**(2026-09-03 사용자 결정) — 그 판정은 모집 형식·채널마다 갈리고 **이미 다섯 곳에 사본이 있어**(정산 서버·검수 화면·엑셀·검수 결과 메일·일일 다이제스트) 여섯 번째를 만들면 나중에 한 곳만 고쳐져 어긋난다.

## 설계

### 화면 — 열 하나, 두 줄

「결과물 제출 마감」 바로 오른쪽에 **「결과물 현황」** 열.

```
결과물 현황
─────────────
영수증  12/12
결과물   8/12
```

- 앞 수 = **승인된 건수**, 뒤 수 = **제출한 건수**
- 분모(제출)와 나란히 두어 「낸 사람 중 몇 명이 통과했나」가 바로 보인다
- 승인이 제출보다 적으면 그 차이가 **검수가 남은 몫**이다

| 상황 | 표시 |
|---|---|
| 시딩·방문형의 영수증 줄 | **「해당 없음」** (0/0 이 아니다) |
| 승인된 신청이 0명 | **「—」** (아직 볼 것이 없다) |
| 집계 조회 실패 | **「—」** (0 으로 그리지 않는다) |
| 제출 0건 · 승인 신청 있음 | **「0/12」** (진짜로 아무도 안 냈다) |

⚠️ **분모를 「승인된 신청 수」가 아니라 「제출 건수」로 잡은 이유** — 같은 줄의 「신청」 열이 이미 승인수를 보여준다. 두 열이 같은 수를 다르게 부르면 헷갈린다. 「승인/제출」은 **검수가 얼마나 남았나**를 말해 주고, 「제출/승인신청」은 **신청 열과 나란히 놓으면 사람이 눈으로 계산**할 수 있다.

### 데이터베이스 (마이그레이션 **1개**)

번호는 개발 세션이 파일을 만들 때 확정한다.

**캠페인별 결과물 집계 함수 1개**

- 이름: `get_campaign_deliverable_counts()` (인자 없음 — 신청 집계 함수와 같은 모양)
- 반환: 캠페인마다 한 줄 — `campaign_id` · `receipt_submitted` · `receipt_approved` · `result_submitted` · `result_approved`
- 🔴 **`get_campaign_application_counts()`(현재 원본 179)를 본떠 만든다** — `SECURITY DEFINER` + `SET search_path=''` + `is_admin()` 가드 + `GRANT EXECUTE … TO authenticated`
- 🔴 **감사용 계정 제외** — 179 와 같은 방식(`influencers` 를 이어 붙여 `is_audit = false`)
- 🔴 **임시저장 제외** — `status <> 'draft'`
- 🔴 **반려·취소된 신청의 결과물 제외** — 그 신청의 `status` 가 `rejected`·`cancelled` 면 뺀다
- 「영수증」 = `kind = 'receipt'` / 「결과물」 = `kind IN ('post','review_image')`
- **사람 수가 아니라 건수를 센다** — 한 사람이 채널 2개에 내면 2건이다(⚠️ 「신청」 열은 사람 수라 두 열의 단위가 다르다. 그래서 분모를 제출 건수로 두어 **한 열 안에서 단위가 닫히게** 했다)

### 화면 코드

| 파일 | 무엇 |
|---|---|
| `dev/admin/index.html` | 열 머리글 한 줄(379행 다음). ⚠️ **빈 상태 `colspan` 도 함께** — 이 목록의 빈 상태 칸 수가 어긋나면 표가 밀린다 |
| `dev/lib/storage.js` | `fetchCampaignDeliverableCounts()` — `fetchCampaignApplicationCounts` 를 그대로 본뜬다(맵으로 변환, 실패 시 `{}`) |
| 캠페인 목록 행을 그리는 곳 | 칸 하나 추가. ⚠️ 목록은 점진 렌더(IntersectionObserver)라 **집계를 행마다 조회하지 않고 미리 받아 둔 맵에서 꺼낸다** |
