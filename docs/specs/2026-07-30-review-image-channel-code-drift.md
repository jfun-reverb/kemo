# @cosme 리뷰 인증샷이 화면에서 사라진 문제 — 채널 코드 어긋남 복구

**작성일:** 2026-07-30
**작성 세션:** 기획/설계
**발단:** 운영 인플루언서 문의 3건(2026-06-08 · 07-15 · 07-21) → 「업로드한 사진이 사라졌다」 / 「@cosme 리뷰를 올릴 곳이 없다」

---

## 한 줄 요약

@cosme 채널의 **내부 코드가 `channel-96r9y3` → `cosme` 로 바뀌었는데 이미 제출된 리뷰 인증샷은 옛 코드로 남아**, 화면·인증성공 판정·정산 후보에서 **전부 누락**됐다. 대상 81건은 **모두 관리자가 이미 승인한 인증샷**이고, 그중 응모 55건은 아직 아무도 손대지 않아 지금도 가려져 있다.

### 관련 코드·데이터베이스 진입점 (직접 확인)

네 곳이 모두 **「캠페인에 저장된 채널 코드」와 「결과물의 `post_channel`」을 문자열로 그대로 비교**한다. 그래서 코드가 어긋나면 네 곳이 동시에 깨진다.

|---|---|---|

### 기존 복구 도구로는 고칠 수 없음 (중요)

마이그레이션 162 `assign_review_image_channel(...)` 은 이 상황을 처리하지 못한다.

- **채널 지정**: 「이미 채널이 지정된 행입니다. 해제 후 다시 지정해 주세요」로 **거부** — 옛 코드 행은 채널 값이 있다
- **채널 해제**: 「검수 완료된 행은 채널을 해제할 수 없습니다」로 **거부** — 81건 전부 `approved`
- `delete_legacy_review_image(...)` 도 「채널이 지정된 행은 삭제할 수 없습니다」로 거부

→ **관리자 화면에서 사람이 손으로 고칠 경로가 존재하지 않는다.** 일회성 데이터 교정(패치 SQL 또는 마이그레이션)이 필요하다.

### 제약: 중복 금지 제약

```
deliverables_review_image_app_channel_uniq
  UNIQUE (application_id, post_channel) WHERE kind='review_image' AND post_channel IS NOT NULL
```

- **A 그룹**: 같은 응모에 `cosme` 행이 없으므로 옛 코드를 `cosme` 로 바꿔도 **충돌 없음**
- **B 그룹**: 이미 `cosme` 행이 있어 **바꾸면 제약 위반으로 실패**

### 이 문제와 충돌 가능성 있는 기존 동작

- **결과물 제출 마감 차단(사양서 `2026-07-29-deadline-server-enforcement.md` 2단계)** — 판정 함수가 `d.post_channel = p_post_channel` 로 비교한다. 지금 상태로 배포하면 **A 그룹 55건은 반려 예외 판정에도 걸리지 않아 재제출조차 막힌다.** 이 사양서의 1단계보다 **뒤에** 배포해야 한다
- **정산 도입일(컷오프)·인플루언서 노출 잠금** — 인증성공이 회복되면 `backfill_settlements()` 가 정산 후보를 새로 만든다. 인플루언서 노출은 잠겨 있어 알림은 안 가지만, 관리자 정산 화면에 없던 건이 갑자기 늘어난다
- **기준 데이터 hard delete 차단** — 기준 데이터 관리에는 「사용 중이면 완전 삭제 차단」이 있는데, 실제로 옛 채널 코드가 삭제됐다. **그 차단이 `deliverables.post_channel` 까지 보지 않는 것**이 이번 사고의 근본 원인으로 의심된다(코드 확인 필요 — 아래 조사 항목)

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우 7가지

1. **다른 채널도 같은 문제일 수 있다 (전수 점검 없이 진행하면 재발)**
   @cosme 만 확인했다. LIPS 등 다른 채널, 그리고 `kind='post'` 행에도 **기준 데이터에 없는 코드**가 남아 있을 수 있다. 이번 복구를 @cosme 단건으로만 처리하면 같은 신고가 다른 채널에서 다시 올라온다. → **배포 전 전수 조사 필수**(설계 0단계)

2. **교정 UPDATE 가 인플루언서 알림을 발생시킬 수 있다 (데이터·UX 동시 위험)**
   `deliverables` 에는 상태 변경 알림 트리거(`trg_deliverable_notify`)와 이력 트리거(`trg_deliverable_status_event`)가 걸려 있다. 채널 값만 바꾸고 `status` 는 건드리지 않으므로 발동하지 않아야 하지만, **트리거 발동 조건을 확인하지 않고 81건을 UPDATE 하면 5~6월 건에 대해 지금 알림 55건 이상이 한꺼번에 나갈 수 있다.** → 교정 전 트리거 조건 확인 + 1건 시험 교정 후 알림 발생 여부 확인

3. **B 그룹 잔재를 지우면 승인 이력이 함께 사라진다**
   `deliverable_events.deliverable_id` 는 `ON DELETE CASCADE` 라, 결과물 행을 지우면 그 행의 승인 이력(`approve` 이벤트)도 소멸한다. 이 프로젝트에는 **대리 회수가 audit 을 함께 지운 선례**가 이미 기록돼 있다(CLAUDE.md). 81건은 전부 관리자가 승인한 금전·성과 근거다. → **삭제하지 않고 유지**를 권고(아래 설계 2단계)

4. **A 그룹 인플루언서가 지금 재업로드를 시도하면 오류 화면을 본다 (UX)**
   교정으로 `cosme` 행이 생긴 직후, 「사라졌으니 다시 올리자」고 마음먹은 인플루언서가 같은 채널에 인증샷을 올리면 **중복 금지 제약에 걸려** 「이미 등록된 데이터」류 오류를 만난다. 加瀬는 이미 "다시 업로드하겠습니다"라고 예고했다. 반대로 교정 전에 올리면 B 그룹처럼 2행이 된다. → 교정과 안내의 **순서**를 정해야 한다

5. **인증성공이 회복되면 광고주 보고 숫자가 사후에 바뀐다**
   이미 낮은 숫자로 보고가 나갔다면, 55건이 회복되는 순간 같은 캠페인의 인증성공률이 올라간다. 광고주가 이전 보고와 다른 숫자를 보게 된다. → 회복 대상 캠페인 목록을 뽑아 **재보고 여부를 운영·영업이 판단**해야 한다(개발 범위 밖이지만 통지 대상)

6. **정산 금액이 걸린다**
   대상은 전부 리뷰어형(monitor)이고, 리뷰어형 정산 금액은 캠페인 제품 가격 페이백이다(마이그레이션 262). 55건이 인증성공으로 돌아오면 정산 후보가 새로 생기고 **금액이 작지 않다.** 정산은 현재 인플루언서에게 잠겨 있어 즉시 지급 의무가 발생하는 것은 아니지만, 관리자 화면 숫자와 「과거 미등록」 목록이 함께 움직인다

7. **교정 시점과 마감 차단(274) 배포 순서가 뒤바뀌면 구제가 불가능해진다**
   274 를 먼저 올리면 A 그룹은 화면에서도 안 보이고 서버에서도 막혀 **본인·관리자 양쪽 모두 손댈 수 없는 상태**가 된다. 순서 역전은 되돌리기 비용이 크다

### 현재 구현과 어긋나는 지점

- **어긋남 있음(위 「기존 복구 도구로는 고칠 수 없음」)**: 마이그레이션 162 가 만든 채널 지정·해제·삭제 3경로가 모두 이 상황을 거부한다. 즉 **이 사양서는 기존 관리자 도구를 재사용할 수 없고 새 경로가 필요하다**
- **어긋남 있음**: 「채널 미지정 레거시 행」 구제 장치(`hasLegacyReviewImage`, 검수 모달 정리 박스)는 `post_channel` 이 **빈 값일 때만** 동작한다. 옛 코드 행은 값이 있어 이 장치의 사각지대다
- **충돌 없음 — 확인 완료**: 인플루언서 화면·관리자 인증 상태·정산 후보 세 곳은 모두 같은 「캠페인 채널 = 결과물 채널」 규칙을 쓰므로, **채널 값을 새 코드로 맞추면 세 곳이 동시에 정상화**된다. 판정 로직을 고칠 필요가 없다

### 사용자 의도와 다르게 해석될 수 있는 부분

- **「복구」의 범위** — ①인플루언서 화면 복귀만 / ②인증성공 판정까지 회복 / ③정산 후보까지 회복 / ④광고주 재보고까지. 이 사양서는 ①~③을 범위로 두고 ④는 통지만 한다고 가정한다
- **「B 그룹 잔재」의 처리** — 「정리」가 삭제인지, 그대로 두고 화면에서만 감추는 것인지. 이 사양서는 **유지 + 사후 식별 가능**을 가정한다
- **대상 범위** — @cosme 만인지, 기준 데이터에 없는 모든 채널 코드인지. 이 사양서는 **전수 조사 후 같은 방식으로 일괄 처리**를 가정한다

## 설계

원칙: **판정 로직을 고치지 않는다. 어긋난 데이터를 맞춘다.** 네 곳의 판정이 같은 규칙을 쓰고 있으므로 데이터를 맞추면 전부 함께 정상화된다.

### 0단계 — 전수 조사 (교정 전 필수, 읽기 전용)

기준 데이터에 존재하지 않는 채널 코드가 남은 결과물을 **종류·채널 전체**에 대해 뽑는다. @cosme 단건으로 끝내면 재발한다.

- 대상: `deliverables` 의 `post_channel` 이 비어 있지 않은데 `lookup_values(kind='channel', active)` 에 없는 값
- 함께 확인: 같은 코드가 `campaigns.channel` 에도 남아 있는지(캠페인 쪽이 옛 코드인 사례가 있으면 방향이 반대가 된다)
- 산출물: 채널 코드별 × 종류별 건수, A/B 분류, 대상 캠페인·인플루언서 명단

### 1단계 — A 그룹 채널 코드 교정 (즉시 효과)

- `kind='review_image'` 이고 옛 코드이며, **같은 응모에 새 코드 행이 없는** 행만 새 코드로 UPDATE
- 반드시 **B 그룹을 제외**하는 조건을 SQL 안에 넣는다(중복 금지 제약 위반 방지). 제약에 의존해 실패를 감지하는 방식은 쓰지 않는다 — 배치 전체가 중단된다
- `status` 는 **건드리지 않는다**(알림·이력 트리거 미발동 목적). 교정 전 트리거 발동 조건 확인 + **1건 시험 교정 후 알림 발생 여부 확인**을 거친 뒤 나머지를 진행
- 교정 근거를 남긴다 — `deliverable_events` 에 남길 수 있는 동작 종류(`channel_assign`)가 이미 있으므로 그 형식을 따르되, **이력 기록 방식은 개발·데이터베이스 세션이 결정**한다(트리거 우회 여부와 함께 판단)
- 효과: 인플루언서 화면 복귀 + 관리자 인증 상태 회복 + 정산 후보 편입

### 2단계 — B 그룹 잔재 방침

- **삭제하지 않고 유지**한다(경우의 수 3 — 승인 이력 소멸 방지)
- 유지하면 화면·판정에는 영향이 없다(새 코드 행이 대표로 잡힘). 다만 **관리자 결과물 목록에 유령 행으로 남아** 「같은 응모에 인증샷이 두 개」로 보일 수 있다
- 보완: 관리자 검수 화면에서 이런 행을 **「옛 채널 코드」로 식별 가능하게 표시**한다. 새 기능을 만들기보다, 기존 「채널 불일치」 경고 배지(게시물용)와 같은 방식으로 리뷰 인증샷에도 표시하는 것을 우선 검토
- 판단 보류 항목: 잔재를 영구 보존할지, 일정 기간 후 별도 보관 테이블로 옮길지

### 3단계 — 인증성공·정산 재집계 확인

- 1단계 후 대상 캠페인의 인증성공 수·진행률이 실제로 회복됐는지 **관리자 화면에서 눈으로 확인**(집계는 화면 진입 시 계산되므로 별도 배치 불필요)
- 정산: 관리자가 정산 화면에 진입하면 후보가 새로 생성된다. **생성 건수·금액 합계를 먼저 확인**하고, 도입일(컷오프) 설정과의 관계를 점검한다
- 회복된 캠페인 목록을 운영·영업에 전달(광고주 재보고 판단은 그쪽 몫)

### 4단계 — 재발 방지

- **원인 차단**: 기준 데이터에서 채널 코드를 완전 삭제·변경할 때 **이미 제출된 결과물(`deliverables.post_channel`)과 캠페인(`campaigns.channel`)에 그 코드가 남아 있으면 막는다.** 현재 「사용 중이면 완전 삭제 차단」이 어디까지 보는지 확인해 범위를 넓히는 방식이 1순위
- **감지 장치**: 0단계 조사 조회를 상시 점검 항목으로 등록(기준 데이터에 없는 채널 코드가 결과물에 남아 있으면 드러나게)
- 채널 코드를 바꿔야 할 때의 절차를 문서화 — 코드 변경은 **기준 데이터·캠페인·결과물 3곳 동시 이관**이 한 세트

### 5단계 — 마감 차단(274) 배포 선행 조건

- 결과물 제출 마감 차단은 **1단계 교정 완료 후에** 배포한다(경우의 수 7)
- 배포 전 확인: 0단계 조사가 **0행**이어야 한다(기준 데이터에 없는 채널 코드가 남아 있지 않은 상태)

## 단계 분할

| 단계 | 내용 | 데이터베이스 변경 | 선행 |
|---|---|---|---|
| 0 | 전수 조사 (읽기 전용) | 없음 | — |
| 1 | A 그룹 채널 코드 교정 | 일회성 교정 1건 (패치 또는 마이그레이션 — 개발 세션이 형식·번호 확정) | 0 |
| 2 | B 그룹 잔재 식별 표시 | 없음(화면만) 또는 판단에 따라 변동 | 1 |
| 3 | 인증성공·정산 재집계 확인 | 없음 | 1 |
| 4 | 재발 방지(삭제 차단 범위 확대 + 절차 문서화) | 함수 변경 1건 예상 | 0 |
| 5 | 마감 차단(274) 배포 | 별개 사양서 | 1 · 4 |

- 1단계가 **가장 시급**하다(운영 인플루언서 55건이 현재 가려진 상태)
- 4단계는 1단계와 병행 가능하지만, 4단계 없이 1단계만 하면 **같은 사고가 다른 채널에서 반복**된다

## 사용자 확인 필요

1. **인플루언서 안내 여부** — 교정 후 「사라졌던 인증샷이 복구됐다」고 알릴지, 조용히 복구할지. 알리면 신뢰 회복이 되지만 「그동안 시스템 문제였다」를 인정하는 안내가 된다. 이미 문의한 3명에게는 개별 답변이 필요하다(경우의 수 4와 연결 — 재업로드 시도 시 오류를 보게 되므로 **최소한 문의자 3명에게는 안내 권고**)
2. **B 그룹 26건 잔재** — 유지(권고) / 삭제 / 별도 보관
3. **광고주 재보고** — 인증성공률이 올라가는 캠페인의 이전 보고를 정정할지
4. **정산 처리** — 회복된 55건을 정산 대기로 그대로 둘지, 도입일(컷오프) 기준으로 과거분으로 다룰지

## 규칙 C(자기 정합성) 점검 상태

- **미실시.** 이 세션은 서브에이전트를 사용하지 않도록 지시받아, 「작성하지 않은 다른 눈이 문서만 읽고 대조」하는 점검을 돌리지 못했다
- 단계가 6개이고 결정표·배포 선행 조건 절차가 있어 **규칙 C 적용 대상에 해당**한다. 사용자 승인 시 점검 후 이 절을 갱신한다
