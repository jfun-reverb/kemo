## 한 줄 요약

@cosme 채널의 **내부 코드가 `channel-96r9y3` → `cosme` 로 바뀌었는데 이미 제출된 리뷰 인증샷은 옛 코드로 남아**, 화면·인증성공 판정·정산 후보에서 **전부 누락**됐다. 대상 81건은 **모두 관리자가 이미 승인한 인증샷**이고, 그중 응모 55건은 아직 아무도 손대지 않아 지금도 가려져 있다.

### 관련 코드·데이터베이스 진입점 (직접 확인)

**영향 지점 4곳.** 앞의 3곳은 「캠페인에 저장된 채널 코드」와 「결과물의 `post_channel`」을 문자열로 그대로 비교하므로, 코드가 어긋나면 동시에 깨지고 **데이터를 맞추면 동시에 정상화된다.** 4번째는 성질이 다르다 — 아래 표의 마지막 행 참조.

| 위치 | 파일·함수 | 어긋날 때의 결과 | 데이터 교정으로 회복되나 |
|---|---|---|---|
| 인플루언서 활동관리 화면 | `dev/js/application.js` `loadDeliverablesForActivity` → `renderActivityReviewImageList(…, channels)` — `channels` 는 캠페인 채널 목록 | 옛 코드 행이 **어느 채널 카드에도 안 붙어 화면에서 사라짐** | ✅ |

→ 즉 **데이터 교정으로 회복되는 것은 3곳**이고, 4번째는 「이 문제를 사람이 발견하지 못한 이유」로만 의미가 있다.

### 기존 복구 도구로는 고칠 수 없음 (중요)

마이그레이션 162 `assign_review_image_channel(...)` 은 이 상황을 처리하지 못한다.

- **채널 지정**: 「이미 채널이 지정된 행입니다. 해제 후 다시 지정해 주세요」로 **거부** — 옛 코드 행은 채널 값이 있다
- **채널 해제**: 「검수 완료된 행은 채널을 해제할 수 없습니다」로 **거부** — 81건 전부 `approved`
- `delete_legacy_review_image(...)` 도 「채널이 지정된 행은 삭제할 수 없습니다」로 거부

→ **관리자 화면에서 사람이 손으로 고칠 경로가 존재하지 않는다.** 일회성 데이터 교정(패치 또는 마이그레이션 — 형식은 개발 세션이 결정)이 필요하다. 이 사양서의 어느 단계도 위 3개 함수를 복구 수단으로 쓰지 않는다.

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우 7가지

1. **다른 채널·다른 종류도 같은 문제일 수 있다**
   @cosme·리뷰 인증샷만 확인했다. LIPS 등 다른 채널, 그리고 `kind='post'` 행에도 **기준 데이터에 없는 코드**가 남아 있을 수 있다. @cosme 단건으로만 처리하면 같은 신고가 다른 채널에서 다시 올라온다. → 0단계에서 **전 종류·전 채널을 조사**하고, 리뷰 인증샷 밖에서 나온 것은 1단계가 아니라 **별도 판단 대상**으로 분리한다(1단계 「범위」 항목 참조)

2. **교정 UPDATE 가 인플루언서 알림을 발생시킬 수 있다 (데이터·UX 동시 위험)**
   `deliverables` 에는 상태 변경 알림 트리거(`trg_deliverable_notify`)와 상태 이력 트리거(`trg_deliverable_status_event`)가 걸려 있다. 채널 값만 바꾸고 `status` 는 건드리지 않으므로 발동하지 않아야 하지만, **트리거 발동 조건을 확인하지 않고 A 그룹 55건을 UPDATE 하면 5~6월 건에 대해 지금 알림이 최대 55건 한꺼번에 나갈 수 있다.** → 교정 전 트리거 조건 확인 + **1건 시험 교정 후 알림 발생 여부 확인**

3. **B 그룹 잔재를 지우면 승인 이력이 함께 사라진다**
   `deliverable_events.deliverable_id` 는 `ON DELETE CASCADE` 라, 결과물 행을 지우면 그 행의 승인 이력(`approve` 이벤트)도 소멸한다. 이 프로젝트에는 **대리 회수가 audit 을 함께 지운 선례**가 이미 기록돼 있다(CLAUDE.md). 81건은 전부 관리자가 승인한 금전·성과 근거다. → **삭제하지 않고 유지**를 권고(2단계)

4. **A 그룹 인플루언서가 지금 재업로드를 시도하면 오류 화면을 본다 (UX)**
   교정으로 `cosme` 행이 생긴 직후, 「사라졌으니 다시 올리자」고 마음먹은 인플루언서가 같은 채널에 인증샷을 올리면 **중복 금지 제약에 걸려** 오류를 만난다. 加瀬는 이미 "다시 업로드하겠습니다"라고 예고했다. 반대로 교정 전에 올리면 B 그룹처럼 2행이 된다. → 교정과 안내의 **순서**를 정해야 한다(안내 주체는 「사용자 확인 필요 1」에서 운영팀으로 넘김)

5. **인증성공이 회복되면 광고주 보고 숫자가 사후에 바뀐다**
   이미 낮은 숫자로 보고가 나갔다면, 55건이 회복되는 순간 같은 캠페인의 인증성공률이 올라간다. 광고주가 이전 보고와 다른 숫자를 보게 된다. → 회복 대상 캠페인 목록을 뽑아 **재보고 여부를 운영·영업이 판단**(개발 범위 밖, 통지 대상)

6. **정산 금액이 걸린다**
   대상은 전부 리뷰어형(monitor)이고, 리뷰어형 정산 금액은 캠페인 제품 가격 페이백이다(마이그레이션 262). 55건이 인증성공으로 돌아오면 정산 후보가 새로 생기고 **금액이 작지 않다.** 정산은 현재 인플루언서에게 잠겨 있어 즉시 지급 의무가 생기는 것은 아니지만, 관리자 화면 숫자와 「과거 미등록」 목록이 함께 움직인다

7. **교정과 마감 차단의 「운영 데이터베이스 적용」 순서가 뒤바뀌면 구제가 불가능해진다**
   마감 차단(위 「충돌 가능성」의 2단계)의 **마이그레이션을 운영 데이터베이스에서 먼저 실행**하면 A 그룹은 화면에서도 안 보이고 서버에서도 막혀 **본인·관리자 양쪽 모두 손댈 수 없는 상태**가 된다. 코드가 이미 `dev` 에 있으므로 위험 시점은 코드 배포가 아니라 **이 실행 시점**이다. 순서 역전은 되돌리기 비용이 크다

### 현재 구현과 어긋나는 지점

- **어긋남 있음**: 마이그레이션 162 가 만든 채널 지정·해제·삭제 3경로가 모두 이 상황을 거부한다 → **기존 관리자 도구를 재사용할 수 없고 일회성 교정이 필요하다**
- **어긋남 있음**: 「채널 미지정 레거시 행」 구제 장치는 `post_channel` 이 **빈 값일 때만** 동작하므로 옛 코드 행은 그 장치의 사각지대다 → 이 사양서는 이 장치를 **고치지 않고 사실만 기록**한다(영향 지점 표 4번째 행)
- **충돌 없음 — 확인 완료**: 회복 대상인 **3곳**(인플루언서 화면·관리자 인증 상태·정산 후보)은 모두 같은 「캠페인 채널 = 결과물 채널」 비교 규칙을 쓰므로, 채널 값을 새 코드로 맞추면 **판정 로직을 고치지 않고 3곳이 동시에 정상화**된다

### 사용자 의도와 다르게 해석될 수 있는 부분

- **「복구」의 범위** — ①인플루언서 화면 복귀 / ②인증성공 판정 회복 / ③정산 후보 회복 / ④광고주 재보고. 이 사양서는 **①~③을 범위로 두고 ④는 통지만** 한다
- **「B 그룹 잔재」의 처리** — 「정리」가 삭제인지, 두고 표시만 바꾸는 것인지. 이 사양서는 **유지 + 사후 식별 가능**을 권고하되 최종 결정은 사용자에게 묻는다
- **교정 대상의 종류 범위** — 이 사양서의 1단계는 **리뷰 인증샷(`review_image`) 한정**이다. 0단계에서 다른 종류가 나오면 **1단계에 끼워 넣지 않고 별도로 판단**한다(경우의 수 1)

## 설계

원칙: **판정 로직을 고치지 않는다. 어긋난 데이터를 맞춘다.** 회복 대상 3곳이 같은 비교 규칙을 쓰므로 데이터를 맞추면 함께 정상화된다.

### 0단계 — 전수 조사 (교정 전 필수, 읽기 전용)

기준 데이터에 존재하지 않는 채널 코드가 남은 결과물을 **종류·채널 전체**에 대해 뽑는다.

- 대상: `deliverables` 의 `post_channel` 이 비어 있지 않은데 `lookup_values(kind='channel', active)` 에 없는 값
- 함께 확인: 같은 코드가 `campaigns.channel` 에도 남아 있는지(캠페인 쪽이 옛 코드인 사례가 있으면 교정 방향이 반대가 된다)
- 산출물: **채널 코드별 × 종류별** 건수, 리뷰 인증샷은 A/B 분류, 대상 캠페인·인플루언서 명단
- 이 조사 결과가 1단계의 범위와 5단계 게이트의 기준선이 된다

### 1단계 — A 그룹 채널 코드 교정 (즉시 효과)

- **범위**: `kind='review_image'` 이고 옛 코드이며, **같은 응모에 새 코드 행이 없는** 행(A 그룹 55건). 0단계에서 다른 종류(`post` 등)나 다른 채널이 나오면 **이 단계에 합치지 않고 별도 판단**한다 — 종류마다 중복 금지 제약과 재제출 구조가 달라 같은 SQL 로 처리하면 안 된다
- **B 그룹 제외를 SQL 조건으로 명시**한다. 중복 금지 제약에 걸려 실패하는 것을 감지 수단으로 쓰지 않는다 — 배치 전체가 중단된다
- **`status` 는 건드리지 않는다.** 목적은 상태 전이에 딸린 **알림 트리거 미발동**이다(경우의 수 2). 교정 전 트리거 발동 조건 확인 + **1건 시험 교정 후 알림 발생 여부 확인**을 거친 뒤 나머지를 진행
- **교정 이력은 남긴다.** 위 항목이 막는 것은 「상태 전이 트리거가 자동으로 남기는 기록」이고, 교정 사실 자체는 근거로 남아야 한다. `deliverable_events` 에 쓸 수 있는 동작 종류(`channel_assign`)가 이미 있으므로 그 형식을 참고하되, **기록 방식(직접 삽입 여부·트리거와의 관계)은 개발·데이터베이스 세션이 결정**한다
- 효과: 인플루언서 화면 복귀 + 관리자 인증 상태 회복 + 정산 후보 편입

### 2단계 — B 그룹 잔재 방침

- **삭제하지 않고 유지**한다(경우의 수 3 — 승인 이력 소멸 방지). 최종 결정은 「사용자 확인 필요 2」
- 유지하면 화면·판정에는 영향이 없다(새 코드 행이 대표로 잡힘). 다만 **관리자 결과물 목록에 유령 행으로 남아** 「같은 응모에 인증샷이 두 개」로 보일 수 있다
- 보완: 관리자 검수 화면에서 이런 행을 **「옛 채널 코드」로 식별 가능하게 표시**한다. 새 기능을 만들기보다, 기존 「채널 불일치」 경고 배지(게시물용)와 같은 방식을 리뷰 인증샷에도 적용하는 것을 우선 검토
- **유지하기로 하면 0단계 조사가 이 26건을 계속 잡아낸다.** 따라서 이 잔재를 **「알려진 예외」로 목록화**해야 한다 — 그 목록이 4단계 감지 장치와 5단계 게이트의 전제가 된다(발견된 모순을 없애기 위한 필수 산출물)
- 판단 보류: 영구 보존할지, 일정 기간 후 별도 보관 테이블로 옮길지

### 3단계 — 인증성공·정산 재집계 확인

- 1단계 후 대상 캠페인의 인증성공 수·진행률이 실제로 회복됐는지 **관리자 화면에서 눈으로 확인**(집계는 화면 진입 시 계산되므로 별도 배치 불필요)
- 정산: 관리자가 정산 화면에 진입하면 후보가 새로 생성된다. **생성 건수·금액 합계를 먼저 확인**하고 도입일(컷오프) 설정과의 관계를 점검
- 회복된 캠페인 목록을 운영·영업에 전달(광고주 재보고 판단은 그쪽 몫)

### 4단계 — 재발 방지

성질이 다른 세 조각이고 **착수 시점이 다르다.** 하나로 묶어 「1단계와 병행」이라고 하면 (나)가 성립하지 않는다.

- **(가) 원인 차단** — 기준 데이터에서 채널 코드를 완전 삭제·변경할 때 **이미 제출된 결과물(`deliverables.post_channel`)과 캠페인(`campaigns.channel`)에 그 코드가 남아 있으면 막는다.** 현재 「사용 중이면 완전 삭제 차단」이 어디까지 보는지 확인해 범위를 넓히는 방식이 1순위. **0단계 조사만 있으면 착수할 수 있어 1단계와 병행 가능**
- **(나) 감지 장치** — 0단계 조사 조회를 상시 점검 항목으로 등록한다. **2단계 뒤에 착수**한다. 경보 기준은 2단계 결정에 따라 형태가 갈린다:
  - **유지로 결정**: **2단계의 「알려진 예외」 목록을 제외한 결과**를 경보 기준으로 삼는다 — 제외하지 않으면 유지하기로 한 B 그룹 26건이 영구 경보로 남아 장치가 무력화된다
  - **삭제로 결정**: 제외 조건이 필요 없어지고 조회 결과 전체가 경보 기준이 된다. 단 **삭제를 실제로 실행한 뒤**(= 2단계 뒤) 등록해야 한다 — 실행 전에 등록하면 지울 예정인 26건이 경보로 뜬다
  - 어느 쪽이든 **착수 시점은 2단계 뒤로 같다**(「사용자 확인 필요 2」)
- **(다) 절차 문서화** — 채널 코드를 바꿔야 할 때는 **기준 데이터·캠페인·결과물 3곳 동시 이관**이 한 세트임을 문서화. 착수 시점 제약 없음

### 5단계 — 마감 차단의 **운영 데이터베이스 적용** 선행 조건

⚠️ 이 단계의 이름이 「배포」가 아니라 「운영 데이터베이스 적용」인 이유: 결과물 제출 마감 차단의 코드·마이그레이션은 **이미 `dev` 브랜치에 있다**(위 「충돌 가능성」 참조). 코드 배포만으로는 트리거가 생기지 않으므로, 실제 위험 시점은 **그 마이그레이션을 운영 데이터베이스에서 실행하는 순간**이다.

- 결과물 제출 마감 차단(사양서 `2026-07-29-deadline-server-enforcement.md` 2단계)의 **운영 데이터베이스 적용은 1단계 교정과 2단계 실행이 모두 끝난 뒤에** 한다(선행 = 1 · 2, 경우의 수 7)
- **개발 데이터베이스 적용 여부를 먼저 확인**한다. 이미 적용돼 있으면 개발서버에서 A 그룹 동선을 재현할 수 없으므로, 1단계 교정을 개발 데이터베이스에서 먼저 검증하려면 그 사실을 감안해야 한다
- **운영 데이터베이스 적용 전 게이트**: 0단계 조사를 다시 돌린다. 기준의 형태는 2단계 결정에 따른다 — **유지로 결정했으면 「알려진 예외」 목록을 제외한 나머지가 0행**(유지하는 한 전체 0행은 성립하지 않는다), **삭제로 결정했으면 전체 0행**. 어느 쪽이든 **2단계를 실행한 뒤**에 판정한다
- 게이트가 리뷰 인증샷 밖(`post` 등)에서 걸리면, 그 종류의 처리 방침을 먼저 정하고 처리한 뒤 적용한다(경우의 수 1)

- 2단계는 **4-나와 5단계의 선행**이다. **「유지」로 결정하든 「삭제」로 결정하든 2단계 실행이 선행이라는 점은 같다** — 유지하면 감지·게이트가 참조할 「알려진 예외」 목록이 2단계에서 나오고, 삭제하면 그 삭제 자체를 2단계에서 하므로 그 뒤에야 조회가 깨끗해진다. 분기에 따라 달라지는 것은 **선행 순서가 아니라 게이트·경보 기준의 형태**다(유지 = 예외 목록을 제외한 뒤 0행 / 삭제 = 전체 0행)
- **4-가는 1단계와 병행 가능**하다(0단계 조사만 필요). 4-나는 2단계 뒤여야 한다 — 재발 방지를 한 덩어리로 보고 「1단계와 병행」이라고 하면 성립하지 않는다
- 4단계의 어느 조각도 5단계의 선행이 **아니다.** 재발 방지 없이도 마감 차단을 운영 데이터베이스에 적용할 수 있다. 다만 하지 않으면 **같은 사고가 다른 채널에서 반복**된다
