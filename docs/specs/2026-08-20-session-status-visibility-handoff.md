# 여러 세션의 진행 상황이 안 보이는 문제 — 기획 인수인계

**작성일:** 2026-08-20
**작성:** 고문 세션
**받는 곳:** 기획/설계 세션
**성격:** 문제 정의 + 실측 사실 + 방안 후보. **사양이 아니다** — 설계 결정은 기획이 한다.

---

## 1. 문제 (사용자 원문)

> 각 세션이 작업을 진행 중인 건지, 어떤 일감을 얼마나 진행 중이고 대략 얼마나 남은 건지 알 수가 없으니 답답하다.
> 상태 표시줄 우측 하단에 시간은 흐르는데 진행 중인지 나에게 어떤 대답을 기다리는 건지 잘 모르겠다.

핵심은 둘이다.
1. **지금 작업 중인가, 내 답을 기다리는가**를 구분할 수 없다
2. **무슨 일감을 얼마나 했는지**가 그 세션 대화 안에만 있어, 보려면 터미널을 하나씩 열어야 한다

---

## 2. 실측한 사실 (2026-08-20, 고문 세션 조사)

기획이 「현재 상태 검증」(규칙 A)을 다시 하지 않아도 되도록, 확인한 것을 그대로 남긴다.

### 2-1. 상태는 **이미 기록되고 있다**

`~/.claude/sessions/{pid}.json` 에 세션마다 파일이 하나씩 있고, 아래 값이 들어 있다.

| 칸 | 값 | 비고 |
|---|---|---|
| `status` | `busy` / `idle` / `waiting` | **「작업 중」과 「대기」가 이미 갈려 있다** |
| `waitingFor` | 예: `input needed` | 배경 세션에서 확인됨 |
| `cwd` | 작업 폴더 절대경로 | 세션 시작 시점 값 |
| `name` / `nameSource` | 세션 이름 / `derived`(자동) 또는 `explicit`(사람) | |
| `nameSince` | 그 이름을 붙인 시각 | |
| `updatedAt` | 마지막 상태 변화 시각 | |
| `pid` / `procStart` | 프로세스 번호 / 시작 시각 | 생존 확인용 |

→ **볼 방법이 없었을 뿐, 새 장부를 만들 필요는 없어 보인다.** 다만 이 파일들은 Claude Code 소유이며 잠금·버전 검사가 걸려 있다는 근거는 찾지 못했다(단순 스냅샷). 여기에 쓰기를 할지 말지는 설계 결정이다.

### 2-2. 없는 칸은 하나뿐 — 「무슨 일감을 몇 개 중 몇 개까지」

어디에도 기록되지 않는다. 자동으로 딸 방법도 못 찾았다(할일 목록이 파일로 남지 않는다).

### 2-3. 조사 중 드러난 함정 4가지

- **pid 만 보면 죽은 세션이 살아난 척한다.** 다른 프로그램이 그 번호를 물려받는다 → 프로세스 이름까지 봐야 한다
- **오래 방치된 세션이 목록을 오염시킨다.** 실측 당시 12시간~14일째 조용한 세션이 4개 떠 있었다. 이걸 「지금 도는 세션」에 섞으면 목록도, 폴더 공유 경고도 과장돼 아무도 안 믿게 된다
- **`cwd` 는 시작 시점 값이다.** 세션이 폴더를 옮기면 안 맞는다(실제로 「iOS 개발 세션」이 메인 폴더로 기록돼 있었다)
- **자기 세션을 찾는 방법이 중요하다.** 「같은 폴더에서 가장 최근 활동」 같은 추측을 쓰면 **남의 세션을 건드린다** — 한 폴더에 세션이 여럿인 상황이 실제로 있다. 조상 프로세스를 거슬러 올라가는 방법은 실측에서 정확히 동작했다

### 2-4. 같이 드러난 별개 문제 — 폴더 공유

조사 당시 **메인 폴더 하나를 세션 2개가 동시에 쓰고 있었다.** 작업 폴더는 6개나 만들어져 있는데 다들 메인에 몰려 있었다.

그 사이 실제로 이런 일이 있었다.
- 고문 세션이 「커밋 안 된 파일 1개」로 알고 있는 동안 다른 세션이 **20개로 늘렸다.** 아무 경고도 없었다
- 고문 세션이 미커밋 파일 하나를 「과거 세션이 남긴 유물」로 단정하고, 완성도까지 검증한 뒤 「지금 커밋해 잠글까요」라고 사용자에게 제안했다. **실제로는 다른 세션이 리뷰를 기다리던 작업**이었다

→ 이 교훈은 이미 `.claude/rules/multi-session.md` 에 반영했다(「공유 폴더에서 발견한 미커밋은 내 것이 아니면 건드리지 않는다」). **도구는 이걸 보여줄 뿐 막지 못한다** — 근본 해결은 `/새세션` 으로 폴더를 나누는 것이다.

## 3. 방안 후보와 각각 깨지는 지점

| 방안 | 효과 | 깨지는 지점 |
|---|---|---|
| **가** 조회 명령 하나(있는 정보를 읽어 표로) | 지금 상태를 한 장으로. 자동 칸이라 안 낡음 | **진행률은 못 보여준다**(그 정보가 없다) |
| **나** 진행률을 세션 이름에 싣기 | 별도 장부·훅·갱신 규칙이 전부 불필요. 상태 표시줄에도 뜬다 | Claude Code 소유 파일에 쓰기. **사람이 안 바꾸면 낡는다** |
| **다** 별도 진행 장부 파일 | 형식을 자유롭게 정할 수 있음 | 🔴 **갱신을 잊으면 거짓 정보가 된다** — 실무자 가이드가 3개월 낡은 채 「최신」인 척했던 전례. 작업 폴더 안에 두면 폴더마다 갈려 무용지물이라 폴더 밖에 둬야 함 |
| **라** 상태 표시줄 손보기 | 「대기 중」 구분은 가능할 수 있음 | **진행률은 원리적으로 못 넣음** |

**고문 의견(참고용, 결정 아님)**: 「가」가 가장 싸고, 「나」는 별도 장치가 필요 없다는 점이 매력적이나 **남의 파일에 쓰는 것**이 걸린다. 「다」는 갱신 규율이 무너지는 순간 없느니만 못하다.

## 4. 기획이 정해야 할 것

1. **자동으로 채워지는 칸과 사람이 쓰는 칸을 어떻게 가를 것인가.** 자동 칸은 안 낡고 사람 칸은 낡는다 — 섞어 보여주면 전체가 안 믿기게 된다. 낡은 표시를 **낡아 보이게** 하는 장치가 필요한가(예: 「쓴 지 N분 전」)
2. **진행률을 어디에 둘 것인가** — 세션 이름 / 별도 파일 / 아예 포기
3. **Claude Code 소유 파일(`~/.claude/sessions/*.json`)에 쓰기를 허용할 것인가.** 읽기만 할 것인가
4. **어디에 코드를 둘 것인가** ⚠️ 이게 이 문서가 존재하는 이유다 — 아래 §5 참조
5. **남은 시간을 보여줄 것인가.** 고문 의견은 **넣지 말자** — 어떤 세션도 정직하게 답할 수 없어 넣는 순간 그 숫자가 거짓말이 된다. 「몇 개 중 몇 개」로 대체
6. 방치 세션 기준(몇 시간부터 「열려만 있는 세션」인가), 폴더 공유 경고를 띄울 것인가

## 5. ⚠️ 이 일이 인수인계로 온 경위 (반드시 읽을 것)

**고문 세션이 이 도구를 한 번 만들었다가 되돌렸다**(커밋 `3616217f`).

- 만든 것: `.claude/scripts/session-status.js`·`session-name.js` + `/현황` 명령 + 규칙 절
- 되돌린 이유: **도구가 나빠서가 아니라 절차가 규칙 밖이어서**다
  - `.claude/scripts/` 는 고문에게 허용된 카테고리가 아니다. 규칙이 정한 것은 `rules`·`agents`·`commands` 셋뿐인데 새 폴더를 만들었다
  - 설계 결정이 여럿 남아 있었고 파일 4개를 동시에 건드렸다 → 인수인계 트리거 ①에 걸리므로 기획으로 넘겼어야 했다

**그래서 §4-4(코드를 어디 둘 것인가)가 이 일의 핵심 쟁점이다.** 셋 중 하나를 정해야 한다.
- ⓐ `.claude/commands/*` 안에 실행 코드를 넣는다(기존 명령들이 쓰는 방식. 규칙 안)
- ⓑ 새 카테고리(`.claude/scripts/` 등)를 **규칙에 정식으로 추가**한다 → 규칙 변경이므로 **사용자 결정 필요**
- ⓒ 코드 없이 해결한다(설정 변경만으로 가능한 길이 있는지)

되돌린 구현은 git 이력(`ef0327b7`)에 남아 있어 참고할 수 있다. **다만 그대로 되살리지 말 것** — 위 결정이 먼저다.
