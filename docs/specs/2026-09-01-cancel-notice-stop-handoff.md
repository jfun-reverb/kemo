## 1. 🔴 베이스는 356 이다 (사양서 작성 시점의 309 가 아니다)

`cancel_application` 을 재정의한 파일은 **다섯**이다 — `104` → `113`(공지 추가) → `306`(치명적 결함 수정) → `309`(취소 알림을 서버가 만들도록) → **`356`**(관리자 대행 탈퇴가 회원 응모를 철회할 수 있게 본인 검증을 넓힘).

**가장 나중 정의인 356 을 베이스로 삼는다.**

🔴 **309 를 베이스로 다시 쓰면 356 이 넓힌 본인 검증이 통째로 사라진다.** 그러면 관리자 대행 탈퇴가 회원 응모를 **하나도 못 철회**하는데, 그 실패는 예외로 삼켜져 **「접수됨 · 철회 못 한 건 N개」로만** 뜬다 — 오류도 로그도 안 남는 조용한 실패다.

⚠️ 이 함수는 **2026-05 ~ 08 약 석 달간 죽어 있었고 오류 로그에 흔적이 하나도 없었다**(356 의 주석이 직접 경고한다). 같은 유형이 또 나면 또 모른다.

## 2. 걷어낼 것 — 이름으로 적는다 (줄 번호는 세어서 쓸 것)

2026-09-01 기준 `356_withdrawal_proxy_foundation.sql` 안 `cancel_application` 정의.

### 2-1. 본문 — 「8. admin_notices 즉시 등록」 블록 통째

`-- 8. admin_notices 즉시 등록 (recruit 외 단계만 …)` 주석으로 시작하는 `IF v_phase != 'recruit' THEN … END IF;` **하나가 전부**다. 그 안에 단계 한글 이름·형식 한글 이름·사유 라벨 조회·HTML 이스케이프·본문 조립·`INSERT INTO public.admin_notices` 가 다 들어 있다.

⚠️ **바로 위 `-- 7-b.` 블록은 남긴다** — 그건 309 가 넣은 **인플루언서 본인 알림**(`notifications`)이고 공지사항과 무관하다. 두 블록이 붙어 있어 한꺼번에 지우기 쉽다.

### 2-2. 선언부 — 공지에만 쓰이던 변수 **12개**

| 묶음 | 변수 |
|---|---|
| 본문 조립 | `v_phase_ko` · `v_recruit_type_ko` · `v_reason_label` · `v_notice_title` · `v_notice_body` · `v_supplement_html` |
| 이스케이프 임시 | `v_campaign_no_esc` · `v_campaign_title_esc` · `v_influencer_name` · `v_influencer_email` · `v_reason_label_esc` |
| 회원 행 | `v_influencer` |

이스케이프 임시 변수 묶음 위에 붙은 **주석 네 줄**(「내부 escape 매크로용 …」)도 함께 걷어낸다 — 그 주석은 `admin_notices.body_html` 를 설명하는 말이라 남기면 없는 것을 설명한다.

⚠️ **`v_notify_title` 은 그 사이에 끼어 있지만 남긴다** — 309 의 본인 알림 제목이다.

### 2-3. 회원 행 조회 한 줄

`SELECT * INTO v_influencer FROM public.influencers WHERE id = v_app.user_id;`

**전수로 세어 확인했다 — `v_influencer` 는 공지 본문 밖에서 한 번도 안 쓰인다.** 그래서 이 조회도 함께 죽는다.

⚠️ 바로 위 줄의 `v_campaign` 조회는 **남긴다** — 취소 시점(`cancel_phase`) 도출이 그 값을 쓴다.

### 2-4. 주석 두 곳의 문구

- `-- 4. 캠페인 / 인플루언서 조회 (cancel_phase 도출 + admin_notices 본문 빌드)` → 공지 얘기를 뺀다
- 함수 끝 `COMMENT ON FUNCTION …` → 356 의 문장을 살리되 **공지 등록을 뺐다는 사실**을 한 줄 더한다

## 4. 대조하며 함께 확인한 것 (규칙 D)

**① 이 변경 뒤 `admin_notices` 에 서버가 자동으로 쓰는 경로는 0이 된다.**
전수 확인 — 자동 등록은 이 취소 함수 계열이 **유일**하다. 앞으로 공지사항은 **사람이 쓴 것만** 남는다. 의도한 결과다.

**② 화면은 이 공지를 전제하지 않는다.**
관리자 공지 화면에서 작성자 `'system'` 이나 「응모 취소 —」 제목을 특별 취급하는 코드는 **없다**. 자동 등록이 멈춰도 화면이 깨지지 않는다.

**③ 🔴 「중단하면 화면이 조용해진다」고 기대하면 틀린다.**
이미 쌓인 공지는 `published` 상태로 그대로 남아 **미읽음 배지와 로그인 팝업에 계속 뜬다.** 조용해지는 것은 §3-3(이미 쌓인 것 정리)까지 해야 한다 — **이번 범위가 아니다.** 운영팀에 이 점을 먼저 알릴 것.

**④ 개인정보 구멍은 이번으로 안 닫힌다.**
사양서 §2① 이 지적한 「공지 본문에 복사된 이름·이메일이 탈퇴해도 안 지워진다」는 **이미 쌓인 것**의 이야기다. 탈퇴 파기 함수(352)는 `admin_notices` 를 **한 번도 안 건드린다**(확인 완료). 이번 변경은 **더 안 쌓이게 할 뿐**이다.

**⑤ `CLAUDE.md` 의 칸 이름이 틀렸다 — 고칠 것.**
`admin_notice_reads` 를 「`(admin_id, notice_id, read_at)`」라고 적고 있는데 **실제 칸은 `auth_id`** 다(063 원본). 그 문서를 보고 조회문을 쓰면 「칸이 없다」로 실패한다. **문서 수정은 개발 세션 소관**이라 여기 적어 넘긴다.

`reverb-jp-production-tokyo` 에서 직접 셌다. **조회만 했고 바꾸는 문은 없다.**

| 그중 「응모 취소…」 | **64** | **§5 ③ 정리 규모** |
| 그중 수정된 적 있는 것 | **0** | **§5 ①** — 어떤 UPDATE 도 없었다 |
| 그중 사람이 편집한 것 | **0** | §5 ① — 최종 수정자가 남은 것이 없다 |

## 5. 검증 — 코드 리뷰로는 못 잡는다

🔴 **적용한 뒤 실제 로그인 브라우저에서 본인 응모 취소를 눌러 볼 것.** 관리자 도구(SQL 편집기)는 서비스 키라 본인 검증 분기가 아예 안 돌아 **재현되지 않는다.**

봐야 할 것 넷:
1. 취소가 **된다** (오류 없이 `cancelled` 로)
2. 인플루언서에게 **취소 알림이 온다**(309 가 산 것)
3. 관리자 공지사항에 **새 글이 안 생긴다**
4. 모집 기간 취소도 **종전대로** 동작한다(원래 공지가 없던 경우)

그리고 **관리자 대행 탈퇴로 회원 응모가 실제로 철회되는지** 한 번 — §1 의 조용한 실패를 잡는 유일한 방법이다.
