## 2. 의심·경우의 수 (반대론자 모드)

**① 🔴 [UX] 오른쪽 칸이 고정 폭이고 자체 스크롤이 없다 — 메모가 쌓이면 아래가 안 닿는다**
`position:sticky` 요소는 자기 높이가 화면보다 커지면 붙어 있지 못하고, 본문 스크롤이 끝나면 칸 아래쪽은 **도달할 수 없는 자리**가 된다. 메모 5~6건이면 바로 이 상태다.
→ **자체 스크롤**(`max-height: calc(100vh - 머리글 - 여백); overflow-y:auto`) + 폭 **340 → 400픽셀** + 칸 머리줄 `position:sticky`. 관리자 뷰포트가 1280 고정이라 좁은 화면 분기는 불필요하지만 **왼쪽 본문이 안 찌부러지는지는 눈으로** 본다.

**② 🔴 [UX] 저장 시점이 둘로 갈린다**
지금은 메모도 머리글 「저장」에 딸려 간다. 여러 건이 되면 「남기기」는 **즉시 저장**, 옆의 브랜드명·담당자는 여전히 「저장」을 눌러야 한다. 실수 두 갈래가 열린다 — (가) 메모를 쓰고 「남기기」를 안 눌러 사라짐 (나) 다른 칸을 고쳐 놓고 메모만 남기고 떠나 **나머지 수정이 날아감**.
→ 처방 ㉠메모 칸 아래 안내 한 줄 ㉡「남기기」 뒤 알림을 **「메모를 남겼습니다」**로(「저장되었습니다」와 구분) ㉢왼쪽 폼 이탈 경고는 **이번 범위 밖**(브랜드 상세 페이지 사양서 4단계에서 다룬다)

**③ 🔴 [데이터] 옛 칸을 남긴 채 화면이 계속 거기 쓰면 마이그레이션 124 가 재현된다**
→ **같은 배포에서** `_collectBrandFormPatch()` 의 `memo:` 줄과 `<textarea id="brandFormMemo">` 를 함께 제거한다. ⚠️ **신규 등록 모달(`addBrand`)도 같은 함수를 쓴다** — 한쪽만 고치면 「새로 만든 브랜드만 옛 칸에 쓰인다」가 된다.

**④ [기술] 목록 「메모」 열이 조회 한 번으로 안 끝난다**
지금은 `fetchBrands()` 하나면 채워진다. 여러 건이 되면 집계를 따로 받아야 하고, 브랜드마다 부르면 77번이다.
→ 목록을 그릴 때 집계를 **딱 한 번**. ⚠️ **조회 실패(`null`)와 0건을 구분**한다 — 옆 「오리엔시트 수」 열이 이미 그 규칙을 쓴다(실패는 「—」). 실패를 0으로 그리면 「메모가 없다」는 거짓말이 된다.

**⑤ [기술] 신규 등록 모달과 상세 페이지가 같은 본문 함수를 쓴다**
`renderBrandDetailFormHtml` 하나를 둘이 공유하고, 같은 이름의 입력칸이 둘이 되면 **오류 없이 엉뚱한 값이 저장**된다(브랜드 상세 페이지 사양서 2-2 의 사고).
→ 메모 영역은 **브랜드 식별자가 있을 때만** 그린다. 신규 등록 모달에는 **안 그리고** 안내 한 줄(「브랜드를 만든 뒤 상세 화면에서 메모를 남길 수 있습니다」).

**⑥ [권한] 캠페인 매니저의 오늘 동작을 뺏지 않는다** — 1-5 그대로. `is_admin()` 이면 변화 0.

**⑦ [데이터] 병합 — 되돌릴 수 없다**
`merge_brands` 는 되돌릴 수 없으므로 이 조각만 따로 검증한다. 결정 C 대로 **대상으로 옮기고 출처 브랜드 이름을 본문 앞에 남긴다**(또는 별도 칸). 어느 쪽이든 「어느 브랜드 시절 글인지」가 사라지면 안 된다.

**⑧ [삭제] 메모를 삭제 판정 넷째 조건으로 더하지 않는다**
`delete_brand` 는 **셋**을 세고 화면이 **같은 셋**을 본다(코드 주석이 「같은 셋이라 『버튼은 뜨는데 누르면 실패』가 없다」고 명시). 메모는 세지 않고 외래 키 연쇄 삭제로 함께 사라진다. 대신 **삭제 확인 창에 「남긴 메모 N개도 함께 사라집니다」** 한 줄.

**⑨ [법률·약관] 영향 없음** — 관리자 전용 내부 기록이고 브랜드·인플루언서에게 노출되지 않는다. 방침·약관 변경 불필요.

### 현재 구현과 어긋나는 지점 2건
1. **저장 경로** — 「폼 저장에 딸려 가는 값」에서 「독립 저장」으로 성격이 바뀐다(②③)
2. **목록 열** — 「글자 칸 그대로 2줄」에서 「최신 1건 미리보기 + 건수」로 가리키는 것이 바뀐다(이름은 그대로)

그 밖에는 충돌 없음 — 엑셀 0곳·운영현황 0곳·서버 함수 0곳·메일 0곳(1-2).

## 3. 설계

### 3-A. 데이터베이스 — 마이그레이션 ①

**표 `brand_memos`** — `id` · **`brand_id`(외래 키 → `brands(id)` ON DELETE CASCADE)** · `body_html`(공백만 금지 + 20,000자 상한) · `author_id`(외래 키, 계정 삭제 시 NULL) · `author_name`(스냅샷) · `created_at` · `updated_at`
**표 `brand_memo_reads`** — `(memo_id, auth_id)` 기본 키 · `read_at`. 🔴 **이번 단계에서는 만들지 않는다**(결정 A — 안 읽음 표시 없음). 나중에 넣을 때 이 절을 근거로.
**색인** — `(brand_id, created_at DESC)`
**정책** — 조회·작성·수정·삭제 전부 `is_admin()`
**트리거** — `updated_at` 자동 갱신 1개
**낙관적 잠금 없음**(마지막 저장 승리 — 오리엔과 같은 결정)
🔴 **`delete_brand`(현재 원본 325)는 한 글자도 안 고친다**(2-⑧)
**기존 글 이전 없음** — 대상 0건(1-9). ⚠️ 그래도 이전문을 넣지 않는 이유를 파일 주석에 남긴다(나중에 「왜 안 옮겼나」를 되묻지 않게)

### 3-B. 데이터베이스 — 마이그레이션 ② `merge_brands` 재정의

🔴 **베이스는 328**(현재 원본 — 175 가 아니다). 원본 브랜드의 메모를 **대상 브랜드로 옮기고**, 본문 앞에 출처를 남긴다 — 「(구 {원본 브랜드명}) 」 접두. 옮긴 건수를 반환값 `moved_memos` 로 더한다(**기존 키는 그대로 둔다**).
⚠️ **328 의 멱등성 판정에 `brand_memos` 존재 여부도 더한다** — 안 더하면 메모만 남은 보관 브랜드가 재호출에서 안 옮겨진다(328 이 오리엔시트에서 겪은 함정과 같다).
⚠️ 메모를 옮길 때 `author_id`·`author_name` 은 **그대로 보존**한다.
⚠️ 되돌릴 수 없는 함수라 **이 조각만 따로** 개발서버에서 실제 병합을 한 번 돌려 확인한다.

### 3-C. 화면 — 브랜드 상세 오른쪽 칸

사용자가 보내 준 오리엔시트 내부 메모 화면을 따른다.

```
┌──────────────────────────────┬────────────────────────────┐
│ (왼쪽 본문 — 지금 그대로)      │ 영업 메모 (3)     ← 머리줄 sticky
│  기본 정보 / 담당자 /          ├────────────────────────────┤
│  브랜드 콘텐츠 /               │ 김담당 · 09/23 14:02  고침 지움 │
│  [오리엔시트 | 캠페인] 탭       │ 견적 재발행 요청 옴          │
│                              │ ────────────────────────── │
│                              │ 이영업 · 09/20 10:11  수정됨  │
│                              │ 3분기 물량 협의 중           │
│                              ├────────────────────────────┤
│                              │ [B I U S 링크]              │
│                              │ 이 브랜드에 대한 영업 메모     │
│                              │              [ 남기기 ]      │
│                              │ 메모는 「남기기」를 누르면 바로 │
│                              │ 저장됩니다                   │
└──────────────────────────────┴────────────────────────────┘
   minmax(0,1fr)                    400px · 자체 스크롤
```

- 절 제목 = **「영업 메모 (N)」** — 건수는 **조회 성공일 때만**(실패를 「(0)」으로 그리면 거짓말. 같은 화면 「오리엔시트 (N건)」이 이미 이 규칙)
- 메모 0건이면 「아직 메모가 없습니다. 아래에 남겨 주세요.」
- 작성·수정·삭제는 표 직접 접근. 삭제는 확인 한 단계
- 정화·편집기 **재사용**(`sanitizeMemoHtml` + `miniEditorHtml(..., {allowImage:false, sanitize:sanitizeMemoHtml})`)
- 🔴 저장·수정 뒤에는 **메모 영역만 다시 그린다** — 전체 재렌더는 **왼쪽 폼의 입력 중인 값을 날린다**
- 🔴 **브랜드 식별자가 없으면(신규 등록 모달) 메모 영역을 안 그린다**(2-⑤)
- ⑤의 `memo:` 줄·`<textarea id="brandFormMemo">`·관련 CSS 제거(2-③)

### 3-D. 화면 — 브랜드 목록 「메모」 열

| | |
|---|---|
| 보여줄 것 | **최신 1건 미리보기**(태그를 걷은 평문, 2줄 말줄임) + 2건 이상이면 「+N」 |
| 조회 | 목록을 그릴 때 **딱 한 번**(2-④) |
| 실패·0건 | 조회 실패 **「—」**(옆 「오리엔시트 수」 열과 같은 규칙) · 0건 **「—」** |
| 머리글·`colspan` | 열 수가 안 바뀌므로 **그대로** |
| 엑셀 | 없다 — 이번에 만들지 않는다 |

⚠️ 서식 있는 글을 목록에 그대로 넣지 않는다 — **태그를 걷어 평문으로**. `title` 툴팁도 평문.

## 4. 단계 분할

🔴 `dev/lib/storage.js` 가 핫스팟이라 **병렬 금지 — 한 갈래로**.

| 단계 | 내용 | 의존 |
|---|---|---|
| **1단계** | 마이그레이션 ①(표·색인·정책·트리거) | — |
| **2단계** | `storage.js` 조회·작성·수정·삭제 + 상세 오른쪽 칸을 메모 목록으로 + **`memo:` 줄 제거** | 1단계 **뒤** |
| **3단계** | 목록 「메모」 열을 최신 1건 + 건수로 | 2단계 뒤 |
| **4단계** | 마이그레이션 ② `merge_brands` 재정의 | 1단계 뒤(2·3과 순서 무관) |

🔴 **1·2단계는 같은 날 데이터베이스 → 화면 순으로 연달아** 낸다. 그 사이 구간에는 화면이 아직 옛 칸을 쓰기 때문이다(다만 이번에는 옮길 글이 0건이라 위험이 작다).
🔴 **「데이터베이스 먼저, 화면 나중」** — 반대면 화면이 없는 표를 부른다.
