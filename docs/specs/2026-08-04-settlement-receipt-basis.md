# 정산 금액 기준 — 상시가 vs 영수증 실결제액 (논의 기록)

> 이 문서를 남기는 이유: 2026-08-04 에 페이팔 송금 내역·지급 대장·시스템 정산 데이터를 대조해 **기준이 두 갈래로 갈려 있다**는 사실과 실측 수치를 확인했는데, 결론이 노션에만 있고 레포에는 없었다. 다음 사람이 정산을 건드릴 때 이 갈림을 모른 채 시작하면 같은 대조를 처음부터 다시 해야 한다.

## 1. 무엇이 갈려 있나

| | 기준 | 근거 |
|---|---|---|
| **실무(실제 송금)** | 인플루언서가 **실제로 결제한 영수증 금액**을 돌려줌 | 페이팔 송금 내역·지급 대장 |
| **시스템(정산 계산)** | 캠페인에 등록한 **상시가**(`campaigns.product_price`) | 마이그레이션 262·264 |

리뷰어형(monitor)은 제품 값을 되돌려주는 페이백 구조라 두 기준이 **대부분 다르다** — 인플루언서가 할인·쿠폰으로 상시가보다 싸게 사기 때문이다.

## 2. 현재 상태 (코드·데이터베이스 직접 확인, 2026-08-05)

### 금액을 정하는 곳
- `_settlement_cert_candidates()` — 정산 후보와 금액을 함께 뽑는 공통 헬퍼. **유효한 최신 정의는 264**(262 에서 재작성, 264 에서 무보수 시딩·방문형 제외 보강). 금액 분기는 `recruit_type` **하나로만** 갈린다:
  - `monitor` → `campaigns.product_price` (**상시가**, 가구매 여부 무관)
  - `gifting` · `visit` → `campaigns.reward`
- 영수증 실결제액(`deliverables.purchase_amount`)은 **금액 계산에 전혀 쓰이지 않는다.**

### 금액 출처 라벨
`settlements.amount_source` 의 허용값은 **3종뿐**이다 (마이그레이션 261 CHECK):
`'reward'` · `'product_price'` · `'product_plus_reward'`
→ **영수증 기준을 저장하려면 값이 하나 더 필요하다.**

### 인플루언서 화면 문구 (두 곳, 같은 값을 그림)
`dev/js/application.js:130`(캠페인 상세 분홍 박스) · `:313`(하단 고정 바) — 둘 다 `¥{product_price}` + `detail.rewardPayback`

| 표시(일본어) | 한글 뜻 |
|---|---|
| **¥3,000 円ペイバック** | **3,000엔 돌려드립니다** |

모집 조건 표의 「報酬」 줄은 「製品 ¥3,000円相当」(제품 3,000엔 상당) — 이건 **제품 가치 안내**라 지급액 약속이 아니다.

⚠️ 「ペイバック(페이백)」은 일본어에서도 「돌려준다」는 뜻이라, **앞에 붙은 금액을 그대로 받는 것으로 읽힌다.**

### 정산 화면 노출 상태
인플루언서에게 **잠금**(`settlement_settings.influencer_visible=false`)이라 이 금액이 아직 외부에 보이지는 않는다. 다만 캠페인 상세의 「¥3,000 円ペイバック」은 **잠금과 무관하게 지금도 보인다.**

## 3. 실측 (2026-08-04)

### 처리 완료 — 영수증 기준으로 저장함
| 구분 | 건수 | 금액 |
|---|---|---|
| 지급 대장 표시분 | 201건 | 896,978엔 |
| 6/16 회차 누락분 | 2건 | 31,597엔 |
| **합계** | **203건** | **928,575엔** |

### 아직 처리 안 함
| 구분 | 건수 | 화면에 보이는 금액 |
|---|---|---|
| 「과거 미등록」 대기 | 437건 | **상시가** |

⚠️ **관리자 정산 화면에 두 기준이 섞여 보인다.** 저장된 203건은 영수증 금액, 대기 437건은 상시가. **437건을 화면 버튼으로 처리하면 상시가로 저장되어 실무 기준과 어긋난다.**

### 두 기준의 실제 차이
**승인 영수증 589건 중 304건이 상시가보다 싸게 구매**(평균 406엔 낮음). 영수증 기준으로 바꾸면 **그 304명은 화면에서 본 금액보다 적게 받는다.**

## 4. 정해야 할 것 (미결)

### ① 화면 문구를 바꿀지
| 지금 | 바꾼 뒤(안) |
|---|---|
| 3,000엔 돌려드립니다 | **구매하신 금액을 돌려드립니다 (최대 3,000엔)** |
| ¥3,000 円ペイバック | 購入金額をペイバック（最大 ¥3,000） |

싸게 산 사람은 실제 결제액, 정가로 산 사람은 상시가를 받는 구조가 문구와 맞아떨어진다.

⚠️ **소급 적용은 어렵다.** 지금까지 「3,000엔 돌려드립니다」를 보고 응모한 사람에게는 그 약속이 유효하다고 볼 여지가 있다. 문구를 바꾸더라도 **바꾼 뒤 등록되는 캠페인부터** 적용하는 쪽이 안전하다.

### ② 대기 437건을 어느 기준으로 줄지
- **상시가** — 화면 약속대로. 인플루언서에게 유리, 실무 관행과 다름
- **영수증** — 실무 관행대로. 화면에서 본 금액보다 적게 받는 사람 발생(304명 해당)

## 5. 작업 범위 (선택지)

| 안 | 내용 | 작업량 | 한계 |
|---|---|---|---|
| **A. 데이터만** | 437건을 처리할 때 조회·실행문으로 영수증 금액을 지정해 저장 | 작음 | **앞으로 새로 생기는 건은 여전히 상시가** — 매번 손으로 처리 |
| **B. 계산 규칙** | `_settlement_cert_candidates()` 에서 리뷰어형을 상시가 → 영수증 실결제액으로 변경 + `amount_source` 에 값 추가(CHECK 확장) + **화면 문구 정리 동반 필수** | 큼 | 근본 해결 — 관리자 화면 버튼만으로 영수증 금액 저장 |
| **C. 혼합 (노션 권고)** | 437건은 A로 처리하고, B는 문구 정리까지 포함해 별도 사양서로 진행 | — | — |

## 6. 주의사항 (착수 전 해소 필요)

- [ ] **437건 중 8월 인증분 45건은 아직 지급 전** — 「송금완료」로 기록하면 안 된다. 이미 지급한 건만 골라야 하는데 지급 대장이 6~7월분까지뿐이라 **구분 근거가 없다**
- [ ] **영수증 금액이 빈 건** — 관리자 검수는 3개 항목 중 1개만 입력해도 저장되게 완화돼 있어(마이그레이션 178) 구매금액이 없는 건이 생길 수 있다. 금액이 0 이하면 `settlements.amount_jpy CHECK(>0)` 때문에 정산행 자체를 만들 수 없다
- [ ] **영수증 금액을 나중에 수정하면** 이미 저장된 정산액과 어긋난다. 「저장 시점 값으로 고정(스냅샷)」 원칙을 유지할지 결정 필요
- [ ] 정산 화면은 인플루언서에게 잠금 상태라 급하지는 않지만, **437건을 처리하기 전에는 정해야 한다**
