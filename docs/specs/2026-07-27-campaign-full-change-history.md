### 1-2. 관련 데이터베이스 표·함수

**`campaign_caution_history`** (마이그레이션 077 신설, 109 확장)
- 컬럼: `id`, `campaign_id`(캠페인 삭제 시 연쇄 삭제), `changed_by`(변경자 로그인 식별자, 외래 키 미설정 — 관리자 계정이 지워져도 이력 보존), `changed_by_name`(변경 시점 이름 스냅샷), `changed_at`, 주의사항 4칸(prev/next × 묶음id/항목), 참여방법 4칸, NG 4칸(`ng_set_id_prev/next`, `ng_items_prev/next`), `app_count_at_change`(변경 시점 유효 신청자 수), `bypass_warning_ack`(경고 모달 통과 여부)

## 2. 규칙 B — 의심·경우의 수 (반대론자 검토)

### 2-1. 깨질 수 있는 경우의 수 (7개)

**① [기술·데이터] 서버 트리거는 "사람이 바꾼 것"과 "시스템이 바꾼 것"을 구분하지 못한다 (가장 큰 위험)**
- 위 C1·C3 대로, 트리거는 누가 왜 바꿨는지 모른 채 "값이 달라졌다"만 안다.
- 결과: 감사 목적(누가 언제 무엇을)에 쓰려는데 오히려 **잘못된 지목**이 생긴다. 자동 마감을 특정 관리자가 한 것처럼 기록되면 감사 자료로서 신뢰가 무너진다.
- 완화안 3가지 — (ㄱ) 상태를 추적 대상에서 빼기(하지만 사용자가 가장 보고 싶어할 항목 중 하나) (ㄴ) 트리거가 자동 전이 패턴을 추정해 「자동」 표시 붙이기(휴리스틱이라 100% 아님) (ㄷ) 자동 전이 3종을 전용 서버 함수로 옮기고 그 안에서 「시스템」 표식을 세션 설정값으로 남기기(작업량 증가, 회귀 위험).

**② [기술] 저장량 — jsonb 스냅샷과 리치 텍스트**
- 주의사항·참여방법·NG는 한·일 리치 텍스트 묶음이라 한 항목이 수 KB. 지금은 옛 표에 이미 통째로 들어가 있어 새로 늘지 않지만, 새 표로 **통합**하면 이중 저장이 된다.
- 설명·가이드·소구도 리치 텍스트라 변경 1회에 수 KB × 2(이전/이후). 활발한 캠페인 하나가 수십 번 수정되면 표 하나가 급격히 커진다.
- 이미지 8칸은 값이 URL 문자열(각 100~250자)이라 용량은 문제없지만, **URL만 보여주면 사람이 무엇이 바뀐지 모른다**(표시 문제 → ⑤).

**③ [권한·환경] 열람 권한을 지금처럼 최고 관리자 전용으로 두면 실사용이 안 될 수 있다**
- 실제로 캠페인을 수정하는 사람은 캠페인 관리자 등급인데, 자기가 뭘 바꿨는지 확인할 수 없다.
- 반대로 열면 「누가 뭘 고쳤나」가 서로 다 보이는 상태가 되어 조직 분위기 이슈가 생길 수 있다. 사용자 결정 필요.
- 권한 카탈로그의 `campaign.caution_history_view` 가 **등록만 되고 안 쓰이는 상태**라, 이번에 손대지 않으면 "권한 관리 화면에서 켜도 아무 일이 안 일어나는 항목"이 계속 남는다(사용자 혼란).

**④ [데이터] 과거는 복원되지 않는다**
- 트리거를 다는 순간부터의 변경만 남는다. 이미 발생한 수정(예: 어제 모집 인원 20→30)은 영원히 알 수 없다.
- 사용자가 「지금까지의 변경도 볼 수 있냐」고 기대할 여지가 크므로 사전 합의 필요.

**⑤ [UX — 필수 축] 이력 화면이 "읽을 수 없는 로그"가 되기 쉽다**
- 필드별 1행 방식이면 **저장 한 번에 10~15행**이 생긴다. 모달을 열면 스크롤 지옥.
  → 「저장 1회 = 묶음 1개」로 접어야 함(묶음 식별자 필요).
- 컬럼 영문 이름(`min_followers`, `submission_end`)이 그대로 노출되면 비개발자는 못 읽는다. **한국어 라벨 대응표 필수.**
- 값도 코드값이다. `monitor` → 「리뷰어형」, `instagram,x` → 「인스타그램, X」, `active` → 「모집중」, `null` → 「(비어 있음)」 로 바꿔야 한다.
- 이미지는 URL 8줄이 아니라 **작은 미리보기 나란히 비교**여야 의미가 있다.
- 지금 모달 제목이 「주의사항 / 참여방법 변경 이력」이라 전체 항목이 들어오면 제목이 거짓말이 된다(제목 변경 필요).
- 자주 있는 오해: 「내용이 안 바뀌었는데 이력이 남았다」 — 지금도 서식 차이로 발생해 「내용 변경 없음」 회색 배지로 처리한 선례가 있다. 새 항목에도 같은 방어가 필요(특히 리치 텍스트).

**⑥ [기술] 저장 실패·부분 실패로 인한 감사 공백**
- 지금 방식(브라우저가 저장 후 별도 호출)은 캠페인 저장은 성공했는데 이력 기록만 실패할 수 있고, 실제 코드가 `console.warn` 만 남기고 넘어간다(admin.js:2074). **감사 공백이 조용히 발생.**
- 브라우저를 닫거나 네트워크가 끊기면 그 사이 기록이 통째로 사라진다.
- 서버 트리거는 이 문제가 없다(같은 트랜잭션 = 캠페인 저장이 성공하면 이력도 반드시 존재). **트리거의 가장 큰 장점.**
- 다만 트리거는 반대로 **끄면 조용히 멈춘다**(마이그레이션에서 껐다가 다시 켜는 걸 잊는 사고). 배포 후 「트리거 살아있음」 점검 항목 필요.

**⑦ [UX·데이터] 완전 삭제 시 이력도 함께 사라진다**
- 지금 옛 표는 `ON DELETE CASCADE` — 캠페인을 완전 삭제하면 이력도 소멸. 정산 이력은 반대로 삭제 제한(`RESTRICT`)을 걸어 감사 자료를 지켰다(마이그레이션 219 선례, 결과물 이력이 연쇄 삭제로 사라진 사고 반성).
- 캠페인 이력에는 개인정보가 없으므로 남겨도 되지만, 「삭제된 캠페인의 이력만 떠다니는」 상태를 어떻게 볼지 결정 필요.

### 2-2. 현재 구현과 어긋나는 지점

§1-7 표 C1~C7 이 전부 해당. 요약하면:
- **C1(자동 전이 행위자 오기)** 과 **C3(신청 수·조회수 잡음)** 은 설계로 반드시 막아야 하는 필수 항목.
- **C6(3영역 이중 기록)** 은 "기존 표를 어떻게 대우할지"를 정하지 않으면 100% 발생.
- 나머지(C2·C4·C5·C7)는 화이트리스트 설계와 운영 규칙으로 완화 가능.

### 2-3. 사용자 의도가 다르게 해석될 수 있는 부분

| 표현 | 해석 A | 해석 B | 확인 필요 |
|---|---|---|---|

## 3. 권고 (한두 문장)

**서버 트리거(AFTER UPDATE) + 추적 대상 화이트리스트 + 「저장 1회 = 묶음 1개」 방식**을 권고합니다. 브라우저 호출 방식은 감사 공백(⑥)이 구조적으로 남고 데이터베이스를 직접 고친 경우를 못 잡기 때문이며, 트리거의 유일한 큰 약점(자동 전이 행위자 오기)은 화이트리스트와 「자동」 표시로 실무상 충분히 통제 가능합니다.

## 4. 설계

### 4-1. 전체 그림

```
[관리자 편집 저장 / 상태 변경 / 노출 토글]
        ↓ campaigns UPDATE
  ┌─ BEFORE UPDATE 트리거들 (기존, 무변경)
  └─ AFTER UPDATE 트리거 (신설) ──→ 화이트리스트 컬럼만 IS DISTINCT FROM 비교
                                  ──→ 바뀐 칸마다 campaign_change_history 1행
                                  ──→ 같은 저장은 같은 change_group_id 로 묶음
        ↓
[더보기 ︙ → 「변경 이력」 모달]
   상단: 시간 역순 「저장 묶음」 카드 목록 (누가·언제·몇 개 항목)
   펼침: ① 기본 항목 표(항목 한국어 라벨 / 이전 / 이후)
         ② 콘텐츠 가이드 3영역 차이 (기존 diff 엔진 그대로 재사용)
```

### 4-2. 기존 표와의 관계 — **병존(추천)**

| 방식 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **A. 병존 (추천)** | 3영역은 기존 표·기존 방식 그대로, 나머지 항목만 새 표 | 회귀 위험 0, 방금 개편한 차이 표시 엔진 그대로 사용, 저장량 증가 없음 | 화면에서 두 소스를 시간순으로 합쳐야 함(구현 약간 복잡) |
| B. 통합 | 3영역까지 새 표로 옮기고 옛 표는 읽기 전용 보존 | 표 하나로 단순 | 신청자 수·경고 통과 여부 같은 화면 맥락 정보를 트리거는 알 수 없어 **정보 손실**, 이중 기록 위험 |
| C. 옛 표 확장 | 지금 표에 컬럼을 계속 추가 | 새 표 없음 | 항목마다 컬럼 2개씩 늘어 40칸+ 되는 기형 구조, 항목 추가마다 마이그레이션 |

→ **A안 권고.** 3영역은 "신청자 동의에 영향을 주는 특수 영역"이라 경고 모달·신청자 수 같은 맥락이 붙어 있고, 나머지는 단순 값 변경이라 성격이 다르다.

### 4-5. 기록 방식 (트리거 함수)

```
record_campaign_change_history()  — AFTER UPDATE ON campaigns, FOR EACH ROW
  SECURITY DEFINER, SET search_path = ''
  1) 묶음 식별자 1개 생성 (이 UPDATE 전용)
  2) 변경자 = auth.uid(), 이름 = admins 에서 조회(없으면 NULL)
  3) change_source 판정:
       - auth.uid() 가 NULL          → 'system'  (서버 함수·직접 수정)
       - status 변경이면서
         자동 전이 3패턴에 정확히 일치 → 'auto'
           · 모집예정→모집중  이고 모집 시작일 ≤ 오늘
           · 모집중→모집마감  이고 모집 마감일 < 오늘
           · 모집마감→종료    이고 제출 마감일 < 오늘
         (다른 칸은 하나도 안 바뀐 단독 상태 변경일 때만)
       - 그 외                       → 'admin'
  4) 화이트리스트 각 컬럼을 IS DISTINCT FROM 으로 비교, 바뀐 것마다 1행 INSERT
  5) 바뀐 게 하나도 없으면 아무것도 INSERT 하지 않음
```

- ③ 판정으로 §2-1 ①(자동 전이 오기)을 실무 수준까지 완화. 화면은 「자동」 회색 배지 + 툴팁 「시스템이 일정에 따라 자동으로 바꾼 기록입니다」.
- ⑤(사람이 눌렀는데 값은 그대로)는 4)·5) 로 자동 해결 — **아무 것도 안 바뀌면 이력 0행.**
- 리치 텍스트 미세 차이(서식만 재생성)는 서버에서 판단이 어려우므로 **화면 표시 단계에서** 기존 `normalizeRichForCompare` 로 「서식만 변경」 배지 처리(이미 구현된 로직 재사용).

**운영 규칙 (문서화 필요)**
- 데이터 정리용 마이그레이션이 campaigns 를 일괄 UPDATE 할 때는 트리거를 잠시 끄고 실행 후 반드시 다시 켠다 (선례: 메모리 `project_sydney_storage_url_migration`).
- 배포 후 점검: `pg_trigger` 에서 해당 트리거가 켜져 있는지(`tgenabled`) 확인.

  - 이미지 8칸 → 작은 미리보기 나란히(썸네일 헬퍼 `imgThumb` + 원본 폴백 규칙 준수). 값이 URL 문자열이라도 화면엔 그림으로.
  - 긴 본문(설명·가이드) → 앞 120자 + 「전체 보기」 접기. 리치 텍스트는 기존 정제 함수로 안전 처리 후 표시
- 콘텐츠 가이드 3영역이 같은 묶음/근접 시각에 있으면 표 아래에 **기존 차이 표시 섹션 그대로** 이어 붙임(`renderSensitiveDiffSection` 재사용 — 이번에 개편한 결과물을 버리지 않음)

**두 소스 병합 규칙(A안 채택 시)**
- 새 표는 `change_group_id` 로, 옛 표는 행 1개가 곧 묶음.
- 같은 저장에서 나온 두 기록은 시각이 거의 같으므로 **`changed_at` 5초 이내 + 같은 변경자**면 화면에서 한 카드로 합쳐 보여줌(데이터는 각자 유지).

**빈 상태**: 「아직 변경 이력이 없습니다. 2026-XX-XX 이후의 수정부터 기록됩니다.」 — §2-1 ④(과거 미기록) 오해 방지 문구 필수.

### 4-7. 마이그레이션 (번호 미지정 — 개수 + 상대 순서)

**총 2개 (권한을 동적 권한으로 바꾸면 3개)**

1. **①** 이력 표 생성 + 접근 정책(조회 정책 1개, 쓰기 정책 없음) + 인덱스 2개
2. **②** 트리거 함수 생성 + campaigns 에 AFTER UPDATE 바인딩
   - ①이 반드시 ② 보다 먼저 (표가 없으면 트리거가 실패)
3. **③ (선택)** 열람 권한을 동적 권한으로 옮기는 경우 — 권한 항목 시드/기본값 조정 + 조회 정책을 권한 함수 기준으로 교체. ②보다 뒤.

## 7. 사용자 확인 필요 (선택형 질문 변환용)

### Q1. 기록 방식
**질문:** 캠페인 변경 이력을 어떤 방식으로 기록할까요?
- **서버 자동 기록 (추천)** — 데이터베이스가 캠페인이 바뀔 때마다 스스로 남깁니다. 브라우저가 꺼지거나 오류가 나도 빠짐이 없고, 데이터베이스를 직접 고친 경우도 잡힙니다. 대신 시스템이 자동으로 바꾼 것과 사람이 바꾼 것의 구분이 완벽하지 않아 「자동」 표시로 보완합니다.
- **지금처럼 화면에서 기록** — 관리자가 저장 버튼을 누른 경우만 남깁니다. 행위자가 항상 정확하지만, 기록 실패 시 조용히 빠지고 데이터베이스 직접 수정은 못 잡습니다.
- **둘 다 사용** — 서버가 기본으로 남기고, 화면 저장 시에는 신청자 수 같은 추가 정보를 덧붙입니다. 가장 정확하지만 작업량이 가장 큽니다.

### Q2. 기존 「주의사항·참여방법·NG」 이력 처리
- **그대로 두고 새 항목만 추가 (추천)** — 지금 잘 동작하는 부분은 건드리지 않고, 나머지 항목만 새로 기록합니다. 화면에서는 한 목록으로 합쳐 보여줍니다.
- **새 구조로 통합** — 모든 항목을 한 곳에 모읍니다. 구조는 단순해지지만 신청자 수·경고 확인 여부 같은 정보가 사라지고, 방금 개편한 차이 표시를 다시 손봐야 합니다.

### Q3. 열람 권한
- **최고 관리자 전용 유지 (추천)** — 지금과 같습니다. 추가 작업이 없고 감사 자료 성격에 맞습니다.
- **권한 관리 화면에서 조절** — 「권한 관리」에서 등급별로 켜고 끌 수 있게 합니다. 이미 등록만 되어 있고 안 쓰이는 권한 항목을 실제로 살리는 정리 작업이 포함됩니다.
- **캠페인 관리자까지 허용** — 캠페인을 실제로 수정하는 사람이 자기 변경을 확인할 수 있습니다. 서로의 수정 내역도 보이게 됩니다.

### Q4. 상태 변경 기록 범위
- **전부 기록하되 자동은 표시 (추천)** — 사람이 바꾼 것과 시스템이 일정에 따라 자동으로 바꾼 것을 모두 남기고, 자동인 경우 「자동」 표시를 붙입니다.
- **사람이 바꾼 것만** — 자동 전이는 기록하지 않습니다. 목록이 깔끔하지만 「언제 마감됐지?」를 이력에서 찾을 수 없습니다.
- **상태는 기록 안 함** — 다른 항목만 남깁니다. 잡음은 가장 적지만 가장 궁금해할 항목이 빠집니다.

### Q5. 삭제·순서·번호 기록 여부
- **남기지 않음 (추천)** — 보관 삭제·복구는 「삭제됨」 탭에서 이미 확인할 수 있고, 순서 이동은 한 번에 수십 행이 쌓여 목록을 덮습니다.
- **보관 삭제·복구만 추가** — 삭제와 복구는 중요한 사건이므로 이력에 함께 남깁니다.
- **전부 남김** — 모든 변화를 빠짐없이 기록합니다. 대신 목록이 매우 길어집니다.

### Q6. 완전 삭제 시 이력 처리
- **함께 삭제 (추천)** — 지금 주의사항 이력과 같은 방식입니다. 남은 이력이 어느 캠페인인지 알 수 없어 쓸모가 적습니다.
- **이력은 남김** — 캠페인이 사라져도 「누가 무엇을 바꿨었나」 기록은 보존합니다. 감사에는 유리하지만 캠페인 이름을 따로 저장해 둬야 합니다.
