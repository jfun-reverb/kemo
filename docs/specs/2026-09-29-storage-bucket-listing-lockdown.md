## 0. 한 줄 정의

**공개 통은 「주소를 아는 사람이 파일을 여는 것」과 「통 안에 무엇이 있는지 목록을 받는 것」이 별개다.** 앞의 것은 통이 공개라서 되고 정책을 거치지 않는다. 뒤의 것은 조회 정책이 허용해서 된다. 이 사양서는 **뒤의 것만 닫는다** — 화면에 그려지는 이미지와 브랜드사가 받은 **파일 주소**(영수증 등)는 그대로 열린다. 오리엔시트 **작성 링크**는 별개다(§4).

가장 급한 것은 오리엔시트 통이다. **폴더 이름이 곧 작성 링크의 토큰**이라, 목록을 받으면 브랜드의 작성 시트(담당자 이름·이메일·연락처·견적 포함)를 읽고 고칠 수 있다.

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 깨질 가능성

| # | 분류 | 무엇 | 대응 |
|---|---|---|---|
| 1 | 기술 | **비로그인 올리기가 조회 정책에 기대고 있을 수 있다.** 공식 문서는 새 파일 올리기에 넣기 권한만 필요하다고 하지만, 이 저장소에서 「비로그인 + 조회 정책 없음」 조합은 한 번도 돌아 본 적이 없다 | 개발서버에서 **정책을 바꾼 뒤 실제 작성 폼으로 파일을 올려 본다**(§6 검증 1). 실패하면 오리엔시트 통은 거기서 멈추고 되돌린다 — 대안은 별도 설계(§7) |
| 2 | 기술 | **회원의 썸네일 저장이 조용히 죽을 수 있다.** `_uploadThumbCopy` 는 덮어쓰기 허용으로 올려 조회 정책이 필요하고, 실패를 삼킨다. 죽어도 오류가 없고 화면이 원본을 통째로 받아 느려질 뿐이다 | 회원 조회를 「본인이 올린 파일」로 남긴다(§3-2). 그리고 **바꾸기 전에 지금 되는지부터** 본다(§6 검증 4 「앞」 — §5 단계 2 순서에 넣었다) — 수정 정책이 관리자 전용이라 **이미 죽어 있을 수 있다** |
| 3 | 기술 | **지우기가 조용히 성공한다.** 저장소는 안 보이는 파일을 「없는 파일」처럼 성공으로 답한다(`CLAUDE.md` 「이미지 썸네일」 절). 관리자 조건을 잘못 걸면 **개인정보 파기가 오류 없이 실패**한다 | 캠페인 이미지 통의 관리자 조건은 등급 구분 없는 `is_admin()`, 아웃바운드 통은 지우기 정책과 같은 권한 열쇠말. 지운 뒤 **공개 주소가 실제로 안 열리는지**까지 본다(§6 검증 6·8, 캐시 우회 필수) |
| 4 | 환경 | 개발과 운영의 정책이 다르다(§1-5 에 실례) | 단계 0 에서 **두 데이터베이스를 각각** 조회. 마이그레이션 셋 모두 「같은 이름이 있으면 지우고 다시 만들기」라 출발 상태가 달라도 도착 상태는 같다. 단 **이름이 같을 때만** 그렇다 — 개발서버에 같은 일을 하는 정책이 다른 이름으로 있으면 그 이름을 지우는 줄을 함께 넣는다 |
| 5 | 권한 | 캠페인 매니저도 `is_admin()` 이 참이라 캠페인 이미지 통을 조회한다 | 의도한 것. 매니저가 검수 화면에서 영수증을 보는 것은 공개 주소라 어차피 정책과 무관하다. 아웃바운드 통은 권한 판정이라 매니저에게 닫힌다(§3-3) |
| 6 | 데이터 | **이미 가져간 토큰은 정책을 닫아도 계속 통한다** | §4 — 사용자 결정 |
| 7 | 법률 | 시트에 브랜드 담당자의 이름·이메일·연락처가 있다. 누가 실제로 읽었는지는 알 수 없다 | §8 |
| 8 | **UX** | 브랜드는 올리기가 실패하면 「업로드에 실패했어요. 링크(URL)로 넣어 주세요」만 본다. 원인을 알 수 없고 우리에게도 안 보인다 | 운영 적용 직후 **실제 작성 링크로 한 번 올려 본다**(§6 검증 1 을 운영에서 반복) |
| 9 | **UX** | 토큰을 다시 발급하면 브랜드가 가진 옛 링크는 「링크를 확인할 수 없습니다」 화면이 된다. 초대 메일 재발송 단추가 없어 **관리자가 새 링크를 손으로 전달**해야 한다 | §4 선택지에 비용으로 적음 |
| 10 | **UX** | 관리자 화면에는 아무 변화가 없다 — 성공도 실패도 눈에 안 보인다 | 성공 확인은 §6 의 목록 조회 재시험(검증 2·5·8) + 보안 점검 화면의 해당 경고가 사라지는 것(검증 10) |

### 2-2. 현재 구현과 어긋나는 지점

§1-6 의 세 줄. 코드와 어긋나는 곳은 없다(코드 변경 없음).

### 2-3. 의도 모호점

- 「세 통을 한 번에」는 **사양서 한 장**이라는 뜻으로 읽었다. 배포는 급한 순서로 나눈다(§5) — 오리엔시트 통이 나머지 둘의 검증을 기다리지 않게.
- 「목록 조회를 닫는다」는 **바깥 사람과 다른 회원에게** 닫는다는 뜻이다. 관리자의 목록 조회는 세 통 모두 살리고(아웃바운드 통은 **그 권한이 있는 관리자** — 캠페인 매니저에게는 닫힌다), 지우기는 **지우기 정책이 있는 두 통**(`campaign-images`·`outbound-influencer-images`)에서 살린다. `orient-images` 에는 지우기 정책이 원래 없고 이 사양서도 만들지 않는다.

## 3. 설계 — 조회 정책 3개를 바꾸고, 넣기 정책 1개를 옮겨 적는다

세 통의 **조회 정책**을 「지우고 다시 만든다」. 넣기·수정·지우기 정책의 **동작**과 통의 공개 여부는 손대지 않는다. 그 밖에 하는 일은 아래 둘이고, 둘 다 운영의 동작을 바꾸지 않는다.

- 운영에만 있는 넣기 정책을 저장소에 옮겨 적는다(§3-4).
- 개발서버에 **같은 일을 하는 정책이 다른 이름으로** 있으면 그것도 함께 지운다(§2-1 4번 — 도착 상태를 운영과 같게 하려는 것).

아래 표의 「지금」 칸은 저장소 마이그레이션 기준이다(§1-1 단서와 같다).

### 3-1. `orient-images`

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 대상 역할 | 비로그인 + 로그인 | **로그인만** |
| 조건 | 통 이름 | 통 이름 **그리고 관리자**(`is_admin()`) |

- 비로그인은 조회 정책이 없어진다 → 목록이 0건이 된다.
- 관리자 조회를 남기는 이유: 나중에 정리 화면을 만들 때 **무엇이 올라와 있는지 볼 수 있게**. 조회만으로는 지울 수 없다 — 이 통에는 지우기 정책이 없고, 만드는 것은 이 사양서 범위 밖이다.

### 3-2. `campaign-images`

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 대상 역할 | 로그인 | 로그인(그대로) |
| 조건 | 통 이름 | 통 이름 **그리고 (관리자(`is_admin()`) 또는 본인이 올린 파일)** |

- 「본인이 올린 파일」은 저장소가 파일마다 기록하는 **올린 사람 칸**으로 판정한다. 칸 이름과 자료형은 저장소 버전에 따라 다르므로 단계 0 에서 확인하고 정한다.
- 회원을 통째로 닫지 않는 이유는 §2-1 의 2번(썸네일).
- 회원이 목록을 받으면 **자기 파일만** 나온다.

### 3-3. `outbound-influencer-images`

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 대상 역할 | 비로그인 + 로그인 | **로그인만** |
| 조건 | 통 이름 | 통 이름 **그리고 아웃바운드 권한 읽기 이상**(`has_permission('outbound.view','read')`) |

- 같은 통의 넣기·수정·지우기 정책이 이미 같은 권한 열쇠말을 쓴다(쓰기 수준). 조회만 읽기 수준으로 맞춘다.

### 3-4. 저장소에 옮겨 적기

`receipts_insert_authenticated` 의 정의를 운영에서 읽어 **그대로** 마이그레이션에 적는다. 운영에서는 동작 변경이 없다(정의처를 저장소로 되찾는 것). **개발서버에 없었다면 이때 생기고, 그때부터 개발서버에서 회원이 영수증을 올릴 수 있다** — 그래서 **캠페인 이미지 통의 조회 정책 교체(마이그레이션 C)보다 먼저, 따로** 넣는다(검증 4 의 「앞」을 개발서버에서 찍으려면 이것이 먼저 있어야 한다).

### 3-5. 마이그레이션

**3개. 번호는 개발 세션이 만드는 시점에 확정한다.**

| 이름 | 내용 |
|---|---|
| A | `orient-images` 조회 정책 교체(§3-1) |
| B | `receipts_insert_authenticated` 옮겨 적기(§3-4) |
| C | `campaign-images` · `outbound-influencer-images` 조회 정책 교체(§3-2·§3-3) |

- **B 는 C 보다 먼저 적용한다**(§3-4 의 이유).
- **A 는 B·C 와 서로 기대지 않는다.** 파일 번호는 A 가 앞이지만 적용은 독립이다 — A 만 운영에 넣고 B·C 는 검증을 더 해도 된다.
- 되돌리기는 각 파일 하단에 옛 정의를 적어 둔다(311 선례).

## 4. 이미 노출됐을 수 있는 토큰

정책을 닫아도 **그 전에 목록을 받아 간 사람의 토큰은 계속 통한다.** 누가 받아 갔는지는 알 수 없다 — 저장소 요청 기록은 최근 며칠치만 남는다(실제로 확인한 기간은 §10).

| 선택지 | 하는 일 | 비용 |
|---|---|---|
| ✅ **가. 기록을 보고 정한다** (2026-09-29 사용자 결정) | 남아 있는 기간의 요청 기록에서 이 통의 목록 조회를 찾는다. 우리 시험(2026-09-29) 외에 있으면 **나**, 없으면 **다** | 조회 1회. 단 **기록이 남은 기간만** 말해 준다 — 그 전은 모른다 |
| 나. 살아 있는 시트의 토큰을 전부 새로 발급 | 파일 폴더가 있는 살아 있는 시트의 토큰을 바꾸고 브랜드에 새 링크를 전달 | 브랜드가 가진 링크가 죽는다. 재발송 단추가 없어 **시트마다 손으로** 전달. 대상 수는 단계 0 에서 센다 |
| 다. 그대로 둔다 | 정책만 닫는다 | 없음. 토큰은 발급 30일 뒤 만료되고 발행되면 막히므로 **시간이 지나면 저절로 닫힌다** |

- 기록에 흔적이 있어 **나**로 가면 토큰을 바꾸는 절차가 필요하다. 지금 그런 기능은 없다 — 개발 세션이 1회용으로 처리한다. 이미 올라온 파일은 옛 토큰 폴더에 남고 시트에 저장된 주소는 그대로 열린다(공개 주소는 경로로 찾는다).

## 5. 단계

동그라미 번호(①~⑤)는 **단계 0 의 조회 항목**에만 쓴다. 마이그레이션은 A·B·C(§3-5)다.

| 단계 | 내용 | 선행 |
|---|---|---|
| **0** | 조회만. **운영·개발 각각**: ①세 통의 정책 목록·이름·대상 역할·조건식 전문(개발서버에 311 이 적용됐는지, `receipts_insert_authenticated` 가 있는지 포함) ②저장소 파일 표의 「올린 사람」 칸 이름·자료형. **운영만**: ③`outbound-influencer-images` 파일 수 ④파일 폴더가 있는 살아 있는 시트 수 ⑤저장소 요청 기록의 보관 기간과 `orient-images` 목록 조회 흔적 | 없음 |
| **1** | 마이그레이션 A — 개발 적용 → §6 검증 1~3·9 → 운영 적용 → 검증 1~3·9·10 | 0 |
| **2** | 개발: 마이그레이션 B 적용 → 검증 4 「앞」 → 마이그레이션 C 적용 → 검증 4 「뒤」·5~9. 운영: 검증 4 「앞」 → B·C 적용 → 검증 4 「뒤」·5~10 | 0 (단계 1 과 독립) |
| **3** | 토큰 처리(§4 — 단계 0 ⑤의 결과로 **나** 또는 **다**) + 브랜드 담당자에게 알릴지 결정(§8) | 0 의 ④⑤, 1 |

**단계 0 결과를 받아야 정해지는 것**

| 무엇 | 단계 0 의 어느 항목 |
|---|---|
| 마이그레이션 B 에 적을 넣기 정책의 정의 전문(§3-4) | ① |
| 개발서버에서 함께 지울 정책 이름(§2-1 4번) | ① |
| 마이그레이션 C 의 「본인이 올린 파일」 판정에 쓸 칸(§3-2) | ② |
| 토큰 처리 나/다, 알림 여부(§4·§8) | ⑤ |
| 「나」로 갈 때 토큰을 새로 발급할 시트 수(§4) | ④ |

**운영에 넣는 조건**

- 그 단계의 **개발서버 검증이 전부 기대대로** 나와야 운영에 적용한다.
- 검증 1 이 실패하면 마이그레이션 A 를 되돌리고 단계 1 을 멈춘다(§7 의 조건부 항목).
- §6 표에 「(대조)」로 적힌 관리자 쪽 조회가 기대대로 안 나오면 그 검증은 **판정 불가**다 — 합격으로 읽지 않고 멈춘다.
- 단계 1 은 **급하다.** 단계 2 의 검증을 기다리지 않는다.
- 코드·빌드·배포가 없다. 데이터베이스 적용이 곧 반영이다.
- 운영에서 회원으로 올려 보는 시험(검증 4)은 **감사용 계정**으로 한다.

## 6. 검증

SQL 편집기는 서비스 키로 돌아 정책을 거치지 않으므로 **거기서는 확인할 수 없다.** 전부 실제 요청으로 한다. 세 통 모두 같은 틀로 본다.

- **막혀야 하는 쪽**이 0건(또는 자기 것만)인지 본다 — 단 **그 통에 파일이 있는 상태**에서만. 빈 통도 0건을 돌려준다.
- **살아야 하는 쪽**(관리자)이 같은 조회로 파일을 받는지 **대조로 함께** 본다.
- 「안 열린다」를 합격으로 읽는 검증은 **지우기 전에 그 주소가 열리는 것**을 먼저 본다.

| # | 단계 | 누가 | 무엇을 | 기대 |
|---|---|---|---|---|
| 1 | 1 | 비로그인 | 실제 작성 링크를 열어 이미지 1장·문서 1개 올리기 | **성공.** 칩이 뜨고 저장된 주소가 새 탭에서 열린다 |
| 2 | 1 | 비로그인 · 회원 · 관리자 | (검증 1 로 파일이 올라간 상태에서) `orient-images` 목록 조회를 **셋 다** | 비로그인·회원: **0건.** 관리자: 1건 이상(대조) |
| 3 | 1 | 관리자 | 오리엔시트 상세에서 올라온 이미지 링크 열기 | 열린다 |
| 4 | 2 | 회원 | 시험용 캠페인의 활동관리에서 영수증 올리기 — 마이그레이션 C 를 **넣기 전에 한 번(앞), 넣은 뒤에 한 번(뒤)** | 앞·뒤 모두 본체가 저장된다. 썸네일(`receipts/thumb/…`)이 생기는지를 **앞뒤로 비교**한다 — 앞에서 이미 안 생기면 이 변경의 회귀가 아니다 |
| 5 | 2 | 회원 · 관리자 | `campaign-images` 의 `receipts` 폴더 목록 조회를 **둘 다**. 그 폴더에 다른 회원의 파일이 없으면 먼저 **다른 시험 계정으로 한 장 더** 올린다 | 회원: **자기가 올린 파일만.** 관리자: 다른 회원 파일을 포함해 여러 건(대조) |
| 6 | 2 | 관리자 | 검증 4 에서 올린 영수증의 공개 주소가 열리는 것을 확인 → 그 시험용 캠페인을 보관 삭제 → 같은 주소를 캐시 우회로 열기 | 지우기 전: 열린다. 지운 뒤: **안 열린다** |
| 7 | 2 | 관리자(아웃바운드는 쓰기 권한) | 캠페인 이미지 올리기·교체, 아웃바운드 대표 이미지 올리기, 결과물 엑셀 내보내기 | 본체와 썸네일이 둘 다 저장되고 공개 주소가 열린다. 엑셀에 영수증 이미지가 종전대로 들어간다 — 이 확인은 **영수증 주소가 경로 형태로 저장된 행이 든 캠페인**으로 한다(§1-4). 그런 행이 없으면 서명 주소 발급이 돌지 않아 깨질 것도 없으므로 건너뛴다 |
| 8 | 2 | 비로그인 · 캠페인 매니저 · 아웃바운드 **쓰기** 권한이 있는 관리자 | (검증 7 로 파일이 올라간 상태에서) `outbound-influencer-images` 목록 조회를 **셋 다**. 그 뒤 쓰기 권한 관리자가 그 이미지의 공개 주소가 열리는 것을 확인하고 지운 다음, 같은 주소를 캐시 우회로 열기 | 비로그인·매니저: **0건.** 쓰기 권한 관리자: 1건 이상(대조). 지우기 전: 열린다. 지운 뒤: **안 열린다** |
| 9 | 1·2 각각 | 누구나 | 인플루언서 앱 캠페인 목록·상세, 관리자 검수 화면의 영수증 | 이미지가 종전 그대로 보인다 |
| 10 | 1·2 각각, **운영만** | — | 보안 점검 화면 다시 돌리기 | 그 단계가 닫은 통의 경고가 사라진다 — 단계 1 은 `orient-images` 1건, 단계 2 는 `campaign-images`·`outbound-influencer-images` 2건 |

- 검증 6·8 에서 캐시를 우회하지 않으면 지워진 파일이 한동안 그대로 열려 「안 지워졌다」로 오판한다.

- 함수 분류는 **저장소의 최신 정의** 기준이다. 운영에 든 함수 본문과 대조하지 않았고, 「호출자 검사 있음」 79개는 본문을 하나씩 읽지 않았다.

## 10. 진행 기록 — 이 자리에만 적는다

다른 절은 설계를 말하고, 무엇이 언제 적용됐는지는 여기만 고친다.

🔴 **마이그레이션 A 는 이 사양서가 완성되기 전에 먼저 나갔다.** 기획 세션이 이 문서를 점검하는 사이, 개발 세션이 보안 점검 분류 메모를 근거로 같은 설계를 따로 만들어 적용했다(서로 몰랐다). 그래서 **§5 의 순서와 조건(단계 0 먼저 · 개발서버 검증을 전부 통과한 뒤 운영)은 마이그레이션 A 에는 적용되지 않았다.** §5 는 남은 단계(0·2·3)를 다스리고, 단계 1 의 남은 검증은 **사후 확인**으로 한다. 사후 확인에서 검증 1(작성 폼으로 올리기)이 운영에서 실패하면 **되돌릴지는 그때 사용자에게 묻는다** — 되돌리면 목록 조회가 다시 열리고, 안 되돌리면 브랜드는 주소 입력으로만 이미지를 넣는다.
