# 정산(Settlement) 개선 로드맵

**작성일:** 2026-07-08
**상태:** 기획 초안 (기존 정산 PR1~3 dev 구축 완료 후 후속 개선)
**관련:** `docs/specs/2026-06-22-influencer-settlement.md`(기존), 메모리 `project_influencer_settlement.md`

> 기존 정산은 **"정산 원장"** — 실제 송금은 관리자가 외부 PayPal에서 하고 시스템은 상태만 기록.
> 본 로드맵은 그 위에 ①돈 정합성 안전장치 ②인플 신뢰(알림·명세서) ③관리자 효율(합산·일괄) ④통계·세무 집계를 얹는다.
> 벤치마킹 결론: 인플이 전부 일본 거주·엔화 단일·수동 송금이라 **다통화·환율·대량 자동송금 API는 오버스펙 → 제외.**

---

## 현재 상태 (2026-07-08 기준, 코드 조사)

### 구현된 것 (탄탄)
- `settlements` 테이블(1 응모 = 1 정산행, `application_id` UNIQUE 멱등) + `settlement_events` 감사(ON DELETE RESTRICT) — 마이그레이션 217. 최신 225까지
- 상태 4종 pending/paid/on_hold/cancelled + 전이 RPC 4종(`mark_settlement_paid/hold/cancel/revert`), 낙관적 락(version, -1 충돌)
- `backfill_settlements()` — 인증성공 판정을 SQL로 재현해 정산행 자동 생성(멱등), PayPal 미등록 알림. **생성만, 역방향 없음**
- 관리자 페인(`admin-settlements.js`): 상태 탭·캠페인 다중필터·인플 검색·이력 모달·엑셀(현재 필터)·낙관적 락. **1건씩 처리, 일괄 없음**
- 인플 마이페이지(`renderMySettlements`): 누적 수령액·내역·PayPal 안내. **명세서·다운로드 없음, 취소건 숨김**
- 알림 2종: `settlement_paypal_required`, `settlement_paid`. **보류·취소 알림 없음**
- 권한: `menu.settlements`·`settlement.view`·`settlement.pay`(campaign_admin=write / campaign_manager=hidden, 서버 강제)

### 없는 것 (개선 대상)
정산 명세서·인플 알림(보류/취소)·인증 깨짐 역방향·인플별 합산·일괄 처리·통계 리포트·세무 집계·송금 실패 상태·PayPal 계정 검증

### 충돌 가능성
- **충돌 없음** — 기존 테이블·RPC에 컬럼/함수 추가 확장 방식. 상태 전이 규칙은 유지하며 자동화·표시 층만 보강

## 의심·경우의 수 (반대론자 검증)

1. **인증 재승인 시 복구** — 인증 깨져 자동 보류된 건이, 결과물 재승인으로 인증이 다시 성립하면? 자동 pending 복귀 vs 관리자 수동. (자동 복귀는 편하지만, 이미 관리자가 취소 판단한 건과 충돌 가능)
2. **이미 송금(paid)된 건의 인증 깨짐** — 환수 대상인데 자동으로 상태를 되돌리면 "이미 보낸 돈"과 시스템 상태가 어긋남. paid는 자동 보류 대신 **경고만** 띄우는 게 안전할 수 있음
3. **판정 로직 이중화(drift)** — `computeCertStatus`(화면 JS) ↔ `backfill_settlements`(SQL)에 같은 판정 중복. 한쪽만 고치면 정산 오류. 단일 소스화는 어려우니(JS는 즉시 표시용), "정산 판정은 SQL이 최종" 규정 + 정합성 점검 필요
4. **취소 사유의 인플 노출** — 사유가 내부 메모(부정 의심 등)라 그대로 인플에게 보이면 부적절. 인플용 안내 문구/사유 코드 분리 필요
5. **일괄 처리 부분 실패** — 다중 선택 일괄 송금완료 중 일부가 버전 충돌·PayPal 미등록으로 실패 → 부분 성공/실패 명단 처리 필요
6. **명세서의 법적 성격** — 단순 지급 내역 표시인지, 정식 지급 명세(会社 발행 문서)인지에 따라 필수 항목·보관 의무가 달라짐
7. **합산 지급 vs 개별 원장** — PayPal 한 번에 합산 송금하면 정산행 여러 개를 한 번에 paid 처리. 그런데 감사·환수는 건 단위라 원장은 개별 유지해야 함(합산은 "지급 묶음"으로만)

## 제안 / 설계 — 4단계(PR)

### 🔴 PR1. 돈 정합성 안전장치
- **인증 깨짐 역방향**: 결과물 반려·삭제로 인증이 무효화되면
  - pending 정산 → **자동 on_hold + 관리자 경고 배지**
  - paid 정산 → **경고만**(환수는 수동 판단, 자동으로 상태 안 돌림 — 경우의 수 ②)
  - 판정 시점: 결과물 상태 변경 트리거 or 정산 화면 진입 시 재판정(backfill 확장) — 개발 세션 결정
- **재승인 복구**: 자동 on_hold였던 건이 인증 재성립 시 처리 방식 → **사용자 확인 필요**
- **drift 방지**: "정산 인증 판정은 `backfill`(SQL)이 최종 소스" 규정 + JS와 정합성 점검 루틴
- 신규 마이그레이션(역방향 판정 함수/트리거) — 개수·번호는 개발 세션 확정

### 🔴 PR2. 인플 신뢰 — 알림 + 명세서
- **알림 확대**: 보류·취소 시 인플 알림(신규 kind, 예 `settlement_held`/`settlement_cancelled`). **인플용 안내 문구**(내부 사유 그대로 노출 금지 — 경우의 수 ④). 마이페이지 정산 화면으로 라우팅
- **정산 명세서**: 마이페이지 건별 상세 + 다운로드
  - 내용: 캠페인·금액(엔)·인증성공일·송금완료일·PayPal·회사 정보
  - 형식: 화면 상세 + CSV or 간단 PDF — **사용자 확인 필요**(정식 문서 여부에 따라)
  - 취소건도 상태만 표시(현재 숨김) 재검토

### 🟡 PR3. 관리자 효율 — 합산 + 일괄
- **인플별 합산 뷰**: 같은 인플의 여러 정산행을 묶어 합산액 표시(PayPal 한 번에 보낼 준비). 원장은 개별 유지, 합산은 "지급 묶음" 표시만(경우의 수 ⑦)
- **다중 선택 → 일괄 송금완료/보류**: 체크박스 선택 후 일괄 상태 기록. 낙관적 락 각각, **부분 성공/실패 명단**(경우의 수 ⑤)
- **PayPal 계정 사전 확인**: 형식 검증(이미 있음) 외, 인플에게 "이 주소 맞나" 재확인 유도 or 관리자 메모 — 오타 반송 사고 방지

### 🟡 PR4. 통계·세무 집계
- **통계 리포트**: 월별 지급액·대기액·보류액, 캠페인별 정산 현황(대시보드 카드/차트)
- **연간 지급 집계**: 인플별 연간 지급 합계 export(회계·지불조서 참고용). 원천징수는 없지만 지급 기록 근거

### 🟢 제외 (오버스펙)
- 다통화·환율(인플 전원 일본·엔화) / PayPal 대량 자동송금 API·Wise 등 대체 수단(건수 임계 넘으면 재검토) / 인보이스 제도(적격청구서)는 회계팀 실제 필요 시
