# 관리자 「취소 되돌리기」 — 회원이 본인 취소한 신청을 원래 상태로

**작성일:** 2026-09-15
**작성:** 기획 세션
**상태:** 설계 확정(사용자 결정 9건) — 구현 미착수

---

## 무엇을 만드나

회원이 **본인이 취소한 신청**을 관리자가 **취소 직전 상태로 되돌리는** 기능. 누가·언제·왜 되돌렸는지와 **원래 언제·왜 취소했는지**를 기록에 남기고, 회원에게 앱 알림 1건을 보낸다.

**계기(2026-09-15 운영 문의)** — 캠페인 CAMP-2026-0134(디웨더 기프팅)에서 회원이 신청 후 본인 취소했으나 이미 배송 리스트에 들어가 상품이 도착했고, 취소를 거두고 기한 내 리뷰를 내겠다고 했다. 관리자 화면에 되돌릴 수단이 없어 그 1건은 **운영 데이터베이스를 직접 고쳐** 처리했다(아래 「운영 선례」).

### 이 제안과 충돌할 수 있는 기존 동작 — 6건

1. **탈퇴 철회분** — 같은 `cancelled` 라 구분하지 않으면 되살아난다(①)
2. **리뷰어형 정원 가드가 삽입 전용** — 상태 UPDATE 로 정원을 넘길 수 있다(②)
3. **중복 신청 방지 색인** — 이미 다시 신청한 사람의 옛 행을 되돌리면 색인에 걸린다(③)
4. **정산 보류** — 취소 때 보류된 정산이 되돌려도 보류로 남는다(④)
5. **행사 캠페인** — 289 가 막는다
6. **관리자 직접 UPDATE 경로** — 새 함수를 만들어도 캠페인매니저를 포함한 관리자 누구나 표를 직접 고쳐 같은 일을 할 수 있다(⑧)

코드 수정 충돌은 없다 — 기존 함수·트리거는 고치지 않고 새 함수 1개·CHECK 확장 2개·권한 시드를 더한다(확인한 영역은 위 표 전체).

### 운영 선례 (2026-09-15)

CAMP-2026-0134 의 그 1건은 18:39(일본 시각) 사용자 승인으로 운영에서 직접 복구했다 — `cancelled → approved`, 취소 칸 4개(`cancelled_at`·`cancel_reason_code`·`cancel_reason`·`cancel_phase`)와 `previous_status` 비움, `application_events` 에 **수동 1행**(`action='approve'` · `from_status='cancelled'` · `changed_by_name='운영 DB 직접 복구'` · `memo`=취소 시각·사유를 포함한 경위). ⚠️ `from_status='cancelled'` 인 `approve` 행은 이것이 **유일한 사례**다 — 이 기능은 `restore_cancelled` 로 따로 기록하므로 나중에 기록을 셀 때 이 1건을 함께 본다.

## 의심·경우의 수 (규칙 B)

### 깨질 가능성

**① 🔴 탈퇴로 철회된 신청까지 되돌린다**

탈퇴 절차가 회원의 신청을 일괄 철회한 것은 **회원 본인의 캠페인 취소 의사가 아니다.** 되살리면 탈퇴 확정 뒤 개인정보 파기·로그인 차단과 어긋나고, 탈퇴를 취소한 회원이라도 그 캠페인을 계속할 의사는 확인되지 않는다.
- → **취소 사유 코드가 `withdrawal` 이면 항상 거부**(결정 5 — 탈퇴를 취소한 회원도). 되살릴 필요가 있으면 회원이 다시 신청한다.
- → 사유 코드가 다른(본인 취소) 신청이라도 **그 회원에게 진행 중(`pending_payout`·`scheduled`) 또는 확정(`done`) 탈퇴 신청이 있으면 거부**한다(탈퇴 흐름과 충돌)(결정 7).
- → **버튼은 사유 코드만 보고 숨긴다**(목록 조회에 탈퇴 상태를 더하지 않는다). 탈퇴 진행 중·확정 회원의 본인 취소 행에는 버튼이 보이지만 서버가 전용 문구로 거부한다 — 드문 경우라 목록 조회를 늘리지 않는 쪽을 택한다.

**② 🔴 리뷰어형 정원을 넘긴다**

정원 가드가 INSERT 전용이라 상태 UPDATE 로 정원을 넘길 수 있다. 빈자리를 이미 다른 사람이 채웠을 수 있다.
- → **리뷰어형이면 되돌릴 상태와 무관하게, 기존 정원 가드와 같은 기준으로 검사한다**(동시에 두 관리자가 되돌려도 둘 다 통과하지 않도록, 정원 가드처럼 **캠페인 행을 `FOR UPDATE` 로 잠근 뒤** 센다) — 같은 캠페인의 심사중+승인 신청 수(감사용 제외)가 이미 `slots` 이상이면 거부. 되돌리는 회원이 감사용 계정이면 검사하지 않는다. `slots` 가 없거나 0 이하면 검사하지 않는다(가드와 같다).
- → 기프팅·방문형은 원래 초과 응모를 허용하므로 검사하지 않는다(현행 응모 규칙과 같다).

**③ ⚠️ 같은 사람이 이미 다시 신청했다**

- → 부분 유일 색인이 막는다. 함수는 **먼저 조회해 전용 사유로 거부**한다(색인 오류 원문이 화면에 뜨지 않게).

**④ ⚠️ 정산이 보류로 남는다 — 안전장치로만**

결과물 승인이 있으면 취소가 막히므로 정산 행이 있는 취소는 **보통 생기지 않는다.** 다만 결과물이 승인됐다가 관리자 「되돌리기」로 검수대기로 돌아간 뒤 회원이 취소하면, 이미 만들어진 정산 행이 남아 320 이 보류로 돌린다.
- → 자동으로 풀지 않는다(보류 사유가 여럿이라 서버가 판단을 대신하면 위험 — 416 원칙). 함수가 그 신청의 보류 정산 수를 돌려주고, 결과 화면이 **「보류된 정산 N건이 있습니다 — 정산 화면에서 확인하세요」**를 띄운다. 0건 예상, 안전장치로만 둔다.

**⑤ UX — 되돌린 사실을 회원이 모른다**

회원 알림함에는 「応募を取り消しました」(응모를 취소했습니다)가 남아 있다.
- → **앱 알림 1건**(결정 4). 메일은 보내지 않는다.

**⑥ UX — 실수로 누르면**

되돌린 신청을 다시 취소 상태로 만드는 관리자 버튼은 없다.
- → 확인 창에서 **사유 입력 필수**. 되돌린 뒤 후속 처리는 **되돌릴 상태별로** 안내한다 — 승인이면 「되돌리기」로 심사중에 돌린 뒤 「미승인」 / 심사중이면 「승인」·「미승인」.

**⑦ UX — 제출 마감이 지났다**

승인으로 되돌려도 마감 뒤라 회원이 결과물을 못 낸다.
- → 막지 않는다(대리 등록이 있다). **되돌릴 상태가 승인일 때만** 확인 창에 「제출 마감이 지나 회원이 직접 제출할 수 없습니다 — 관리자 대리 등록이 필요합니다」를 띄운다.
- → 판정 기준: **일본 시각 오늘 날짜 > `submission_end`**(마감일 당일은 아직 제출 가능). 확인 창은 목록에 이미 있는 캠페인 `submission_end` 로 **화면에서** 이 식으로 판정한다(서버 반환값을 쓰지 않는다 — 실행 전이기 때문). 오늘 날짜는 `Intl.DateTimeFormat('en-CA', {timeZone:'Asia/Tokyo'})` 로 `연-월-일` 문자열을 만들어 `submission_end` 와 **문자열로** 비교하고, `new Date('연-월-일')` 파싱은 쓰지 않는다. `submission_end` 가 비면 안내를 띄우지 않는다.

**⑧ 권한 — 직접 UPDATE 경로는 남는다**

- → 이번 범위에서 막지 않는다(기존 승인·미승인도 같은 경로라 구조 변경은 별도 작업). 화면 버튼과 새 함수만 권한을 좁힌다.

**⑨ 오래된 취소 행**

`previous_status` 칸이 생기기 전(104 이전) 취소된 행은 그 값이 비어 있을 수 있다.
- → **`previous_status` 가 `pending`·`approved` 가 아니면(비어 있거나 다른 값) 거부**한다. 추측으로 승인시키지 않는다.

**⑩ 원래 취소 기록이 사라진다**

본인 취소는 `application_events` 에 안 남고, 되돌리면 취소 칸 4개와 `previous_status` 를 비운다 — 그대로 두면 **언제·왜 취소했는지**가 어디에도 남지 않는다.
- → 새 기록 행에 **취소 시각·사유 코드·사유 원문·취소 시기**를 함께 옮겨 적는다(아래 설계 — 운영 선례가 `memo` 에 경위를 넣은 것과 같은 몫).

### 사용자 의도와 다르게 읽힐 수 있는 부분

1. **「되돌린다」 ≠ 「다시 신청한다」** — 새 신청을 만들지 않고 **취소된 그 행**을 되살린다. 신청 시각·동의 기록·주의사항 스냅샷이 원래 것 그대로다.
2. **관리자 「미승인」 신청은 대상이 아니다** — 이미 있는 「되돌리기」로 처리한다. 이 기능은 `cancelled` 만.

| 3 | **모집이 끝난 캠페인도 허용** | 요청이 오는 시점이 대부분 모집 뒤 |
| 4 | 되돌리면 **회원에게 앱 알림 1건**(메일 없음) | 알림함에 「취소했습니다」가 남아 있다 |
| 5 | **탈퇴 사유로 철회된 신청은 항상 거부**(탈퇴를 취소한 회원도) | 회원 본인의 취소 의사가 아니라 캠페인을 계속할 의사를 알 수 없다. 규칙이 단순하다 |
| 6 | **관리자 일일 메일 「재처리」 절에 싣지 않는다** | 드문 예외 처리이고 메일 함수를 손대지 않아 범위가 작다. 기록은 `application_events` 에 남는다 |
| 7 | **사유가 달라도 탈퇴가 진행 중(`pending_payout`·`scheduled`)이거나 확정(`done`)된 회원의 신청은 거부** | 탈퇴하는 회원에게 캠페인을 다시 걸면 확정 뒤 개인정보 파기·로그인 차단과 어긋난다 |
| 8 | **종료(`ended`)·노출종료(`expired`) 캠페인에서 심사중으로 되돌리면 확인 창에 안내 한 줄** — 막지 않는다 | 캠페인 종료 시 심사중 자동 낙첨(176)은 **캠페인 상태가 바뀌는 순간에만** 돌아, 이미 종료된 캠페인에 되돌린 심사중 신청은 계속 심사중으로 남는다. 운영자가 직접 승인·미승인해야 한다 |
| 9 | **승인으로 되돌린 회원도 제출 마감 D-5·D-1 안내 메일을 받게 둔다**(메일 함수 무변경) | 결정 4(메일 없음)는 되돌리기 안내에 대한 것이다. 마감 안내 대상 조회가 승인 상태 전체를 보고, 취소 전에 이미 보낸 D-N 은 발송 기록 유일 제약이 막는다. 리뷰를 내겠다는 회원에게는 도움이 된다 |

## 설계

### 데이터베이스 — 마이그레이션 2개(번호는 개발 세션이 확정)

①함수·CHECK 확장 → ②권한 시드. **①이 먼저.**

**① `restore_cancelled_application(p_application_id uuid, p_memo text) RETURNS jsonb`** (이름 제안 — 개발이 바꿔도 된다)

- 소유자 권한 실행 + `SET search_path = ''`
- 가드 `has_permission('application.restore_cancelled','write')`(열쇠말 제안) — 🔴 `is_campaign_admin()` 로 박지 않는다
- **잠금 순서**: ①신청 행 `FOR UPDATE` → ②리뷰어형이면 캠페인 행 `FOR UPDATE`(정원 가드와 같은 대상 — 두 관리자가 동시에 되돌려도 둘 다 정원 검사를 통과하지 않게). 신청 행을 먼저 잠그는 이유: 캠페인 행 잠금이 필요한지는 신청이 가리키는 캠페인을 읽어야 알 수 있다
- **거부 사유 10종 — 아래 순서대로 판정해 처음 걸린 것 하나를 돌려준다**

| 순서 | 코드 | 조건 |
|---|---|---|
| 1 | `forbidden` | 권한 없음 |
| 2 | `memo_required` | 사유가 비었거나 공백뿐 |
| 3 | `not_found` | 신청 없음 |
| 4 | `not_cancelled` | 상태가 `cancelled` 가 아님 |
| 5 | `withdrawal_related` | `cancel_reason_code = 'withdrawal'` **또는** 그 회원에게 `pending_payout`·`scheduled`·`done` 탈퇴 신청이 있음(①) |
| 6 | `previous_status_not_restorable` | `previous_status` 가 `pending`·`approved` 가 아님(⑨) |
| 7 | `campaign_deleted` | 캠페인 `deleted_at` 있음 |
| 8 | `event_campaign` | 캠페인 `event_mode` |
| 9 | `active_application_exists` | 같은 회원·같은 캠페인에 `cancelled` 가 아닌 신청이 있음(③) |
| 10 | `slots_full` | 리뷰어형 + `slots > 0` + 회원이 감사용 아님 + **캠페인 행을 잠근 뒤** 센 같은 캠페인의 심사중+승인 신청 수(감사용 제외)가 `slots` 이상(②) |

- **통과하면**
  1. 비우기 전에 취소 기록 값(`cancelled_at`·`cancel_reason_code`·`cancel_reason`·`cancel_phase`)을 변수에 담는다
  2. `status = previous_status`, 취소 칸 4개와 `previous_status` 를 비운다. 🔴 **`reviewed_at`·`reviewed_by` 는 건드리지 않는다** — 인플루언서 일일 메일이 「어제 `reviewed_at` + 승인」으로 당선 절을 뽑아(`notify-influencer-daily-digest`), 채우면 다음 날 당선 메일이 나가 결정 4를 어긴다
  3. `application_events` 에 1행 — `action = 'restore_cancelled'`, `from_status = 'cancelled'`, `to_status = 되돌린 상태`, 처리자 id·이름, **`memo` = 관리자 사유 + 원래 취소 기록**(예: `사유: {p_memo} / 원래 취소: {cancelled_at 일본 시각} · {cancel_phase} · {cancel_reason_code} · 「{cancel_reason}」`)(⑩)
  4. `notifications` 에 1행 — `kind = 'application_restored'`, `ref_table = 'applications'`, `ref_id = 신청 id`, 제목 **「応募の取り消しが撤回されました — {캠페인 제목}」**(응모 취소가 철회되었습니다 — {캠페인 제목}), 캠페인 제목이 비면 **「応募の取り消しが撤回されました」**(응모 취소가 철회되었습니다)만. 본문 `NULL`(취소 알림 309 와 같은 형식)
  5. 돌려주는 값 `{ok:true, restored_status, on_hold_settlement_count}` — 보류 정산 수(④)
- ⚠️ **기존 트리거와의 관계**: 상태 UPDATE 로 `record_application_status_event`(283)가 돌지만 `cancelled →` 전이는 기록하지 않아 **행·당선 알림을 만들지 않는다** → 3·4를 함수가 넣어도 중복되지 않는다. 283 은 고치지 않는다. 모집 인원은 058 트리거가 재계산한다
- **CHECK 확장 2개(같은 파일)**
  - `application_events.action` — 기존 셋 + **`restore_cancelled`**. ⚠️ 제약 이름을 **실제 이름으로 조회해서** 지우고 다시 만든다(305 교훈 — `IF EXISTS` 는 오타를 조용히 삼킨다)
  - `notifications_kind_check` — 376 의 12종 + **`application_restored`**. 베이스는 376
- ⚠️ 관리자 일일 메일은 `revert_to_pending` 만 읽으므로 **새 action 은 메일에 실리지 않는다**(결정 6 — 메일 함수 무변경)
- 실행 권한: `REVOKE … FROM PUBLIC` · `REVOKE … FROM anon` · `GRANT EXECUTE … TO authenticated`

**② 권한 시드**
- `application.restore_cancelled` — 슈퍼관리자 write/write · 캠페인관리자 write/write · 캠페인매니저 **hidden/hidden**
- 카탈로그 `ADMIN_PERMISSION_CATALOG` 와 `PERM_SUPER_SERVER_ENFORCED`(shared.js)에도 등록 — **새 함수가 권한을 서버에서 검사**하기 때문. ⚠️ 한계: 표 직접 UPDATE 경로(⑧)는 남아, 이 설정은 **「이 함수와 버튼」만** 막는다. 권한 설정 화면의 배지 설명을 바꾸지는 않되, 카탈로그 항목 이름에 「(함수)」 같은 오해 방지 표현을 붙일지는 개발이 카탈로그 관례를 보고 정한다
- 선례 `355_withdrawal_proxy_permission_seed.sql`

### 관리자 화면

- **자리**: 신청 관리 목록·캠페인 신청자 목록의 **취소된 행 동작 칸**. ⚠️ 두 화면이 행 그리기를 따로 갖고 있다(213·1049행) — **두 곳 모두**
- **보이는 조건**: `canWrite('application.restore_cancelled')` 이고 `cancel_reason_code` 가 `withdrawal` 이 아닐 때. 권한이 없으면 **그리지 않는다**(취소 행에는 원래 버튼이 없었다). 탈퇴 진행 중·확정 회원은 버튼이 보이되 서버가 거부한다(①·결정 7)
- **확인 창** — 기존 모달 방식(`modal-overlay`)
  - 회원 이름 · 캠페인 · **되돌릴 상태**(승인/심사중 — `previous_status` 가 그 둘이 아니면 「되돌릴 상태를 알 수 없음」으로 표시하고 실행하면 서버가 거부) · 원래 취소 시각·사유(목록의 `cancelDetailLinesHtml` 과 같은 내용)
  - **되돌릴 상태가 승인이고 일본 시각 오늘 > `submission_end` 이면** 「제출 마감이 지나 회원이 직접 제출할 수 없습니다 — 관리자 대리 등록이 필요합니다」(⑦)
  - **되돌릴 상태가 심사중이고 캠페인이 종료·노출종료이면** 「이 캠페인은 종료되어 심사중 신청이 자동으로 정리되지 않습니다 — 되돌린 뒤 직접 승인 또는 미승인해 주세요」(결정 8)
  - **사유 입력(필수)** — 비면 실행 버튼 비활성
  - 안내: 「회원에게 앱 알림이 1건 발송됩니다」 + 되돌릴 상태별 후속 처리 한 줄(⑥)
- **결과**
  - 성공 → 토스트 + 목록 다시 그리기(신청 관리 페인은 `refreshPane('applications')`, 캠페인 신청자 목록은 그 목록 재렌더). `on_hold_settlement_count > 0` 이면 「보류된 정산 N건이 있습니다 — 정산 화면에서 확인하세요」(④)
  - 거부 → **코드별 문구 10종 + 통신 실패**. 🔴 하나도 「알 수 없는 오류」로 뭉뚱그리지 않는다
- 저장소 함수 `restoreCancelledApplication(appId, memo)`(`dev/lib/storage.js`, 이름 제안) → `{ok, error_code, …}`, 통신 실패 `null` 과 거부를 구분

| `not_found` | 없는 신청 id 로 직접 호출 |
| `not_cancelled` | 승인 상태 신청 id 로 직접 호출 |

| `previous_status_not_restorable` | 개발 데이터베이스에서 시험 취소 행의 `previous_status` 를 SQL 로 비운 뒤 화면에서 누름(확인 뒤 되돌림) |
| `campaign_deleted` | 보관 삭제는 신청을 즉시 파기하므로(현재 상태 표) **정상 경로로는 재현되지 않는다 — 방어용 판정**. 개발 데이터베이스에서 시험 캠페인에 `deleted_at` 만 SQL 로 넣고(신청 파기 없이) 콘솔 호출, 확인 뒤 되돌림 |
| `event_campaign` | 행사 모드 시험 캠페인에서 관리자 예약 취소(288)로 만든 취소 행 — 화면에서 누름 |
| `active_application_exists` | 모집중 시험 캠페인에서 취소 → 재응모한 회원의 옛 취소 행 — 화면에서 누름 |
| `slots_full` | 정원 1인 리뷰어형 시험 캠페인에서 A 취소 → B 응모 → A 되돌리기 |
