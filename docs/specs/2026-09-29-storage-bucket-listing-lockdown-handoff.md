# 인수인계 — 공개 저장소 통 목록 조회 닫기

**작성일:** 2026-09-29
**보내는 곳:** 기획 세션 → **받는 곳:** 개발 세션
**사양서:** [`2026-09-29-storage-bucket-listing-lockdown.md`](./2026-09-29-storage-bucket-listing-lockdown.md) — 설계·검증·결정은 전부 그쪽이 정의처다. 이 문서는 **무엇부터 어디서 하는지**만 적는다
**성격:** 첫 묶음은 **조회와 확인**이다. 마이그레이션·코드 변경은 없다. 단 작성 폼으로 올려 보는 확인은 **시험 시트와 파일을 만든다**(「가」). 마이그레이션은 조회 결과를 받은 뒤

---

## 왜 넘기나

사양서의 단계 0(조회)과 오리엔시트 이미지 통의 사후 확인은 **운영·개발 데이터베이스를 직접 읽고 실제 화면으로 눌러 봐야** 끝난다. 기획 세션은 저장소와 공개 요청까지만 봤다.

⚠️ 오리엔시트 이미지 통 차단(마이그레이션 472)은 이미 운영에 있다. 이 인수인계는 그것을 다시 하라는 것이 아니다 — **기록이 없는 확인을 채우고, 남은 두 통을 준비하는 것**이다.

🔴 **사양서 §10(진행 기록)부터 읽는다.** 이 문서를 쓰는 사이에도 개발 세션이 §10 에 결과를 더했다 — 대상 시트 수(④)와 요청 기록(⑤)은 이미 조회됐고, 토큰은 **교체하지 않기로** 정해졌다. 이 문서와 §10 이 다르면 **§10 이 맞다.**

## 순서

| 순번 | 무엇 | 어디서 | 바꾸는 것 |
|---|---|---|---|
| 가 | 오리엔시트 통 사후 확인 | 개발 먼저. 운영은 사용자 승인 뒤 | 시험 시트·파일(개발) |
| 나 | 단계 0 조회 가운데 남은 셋(①②③) | 운영·개발 | 없음 |
| 다 | 결과를 사양서 §10 에 적고 **사용자에게 보고** | — | 사양서 §10 |
| 라 | 마이그레이션 B → 검증 4 「앞」 → 마이그레이션 C | 개발 먼저 | 사양서 단계 2 |

- **가**와 **나**는 서로 기다리지 않는다. **라**는 **나**의 결과가 있어야 쓸 수 있다.
- 🔴 **라 에서 B 와 C 를 한 번에 넣지 않는다.** B(넣기 정책 옮겨 적기)를 먼저 넣고, 회원으로 영수증을 올려 **바꾸기 전 상태를 찍은 뒤**(검증 4 「앞」) C 를 넣는다. 이유는 사양서 §3-4.

## 가. 오리엔시트 통 사후 확인

사양서 §10 의 「사후 확인」 표가 비어 있는 칸이다. 검증 내용과 기대값은 사양서 §6 의 검증 1·2·3·9·10.

| 검증 | 요점 |
|---|---|
| 1 | **실제 작성 폼으로** 이미지 1장·문서 1개를 올린다. 472 파일 하단의 개발서버 시험은 폼이 아니라 같은 호출을 직접 보낸 것이다 |
| 2 | 비로그인은 이미 0건을 확인했다. **회원과 관리자**로 같은 목록 조회를 해서 회원 0건 · 관리자 1건 이상인지 본다 |
| 3·9 | 관리자 상세에서 이미지가 열리는지, 인플루언서 앱·검수 화면 이미지가 종전 그대로인지 |
| 10 | 운영 보안 점검 화면을 다시 돌려 오리엔시트 통 경고가 사라졌는지(운영만) |

- **개발서버에서 먼저** 실제 작성 폼으로 올려 본다. 폼이 쓰는 경로가 직접 보낸 호출과 같은지는 여기서 확인된다.
- 🔴 **운영에서 폼으로 올려 보는 것은 사용자 승인을 받은 뒤에만** 한다. 부작용이 둘 있다.
  - 시트를 발급하면 **브랜드 담당자에게 작성 링크 메일이 자동으로 나간다.** 실제 브랜드로 발급하면 바깥으로 메일이 간다 — 하게 되면 **담당자 연락처가 없는 내부 시험용 브랜드**로 발급한다(수신자가 없으면 발송을 건너뛴다)
  - 이 통에는 지우기 정책이 없어 **올린 파일이 운영에 남는다.** 개발 세션이 운영에서 실제 올리기를 하지 않은 이유가 이것이다(사양서 §10). 하게 되면 끝난 뒤 대시보드의 저장소 화면에서 그 파일을 지우고, 시험 시트도 지운다
- 브랜드가 쓰고 있는 시트에는 올리지 않는다.
- 🔴 운영에서 검증 1 이 **실패하면 되돌리지 말고 사용자에게 먼저 묻는다**(사양서 §10 머리). 되돌리면 토큰 목록이 다시 열린다.
- 회원·매니저 등 다른 계정으로 봐야 하는 확인은 **사용자에게 로그인을 부탁**한다.

## 나. 단계 0 조회 — 남은 것은 ①②③

항목 번호(①~⑤)는 사양서 §5 단계 0 과 같다. **④⑤는 이미 조회됐다**(결과는 사양서 §10) — 아래 ④⑤는 어떻게 셌는지 되짚을 때 쓰는 참고다. 조회문은 **기획 세션이 돌려 보지 않은 초안**이다 — 칸 이름이 다르면 고쳐 쓴다.

### ① 세 통의 정책 전문 — 운영·개발 각각

```sql
SELECT policyname, cmd, roles::text, qual, with_check
  FROM pg_policies
 WHERE schemaname = 'storage' AND tablename = 'objects'
   AND (coalesce(qual,'') || coalesce(with_check,'')) ~ '(orient-images|campaign-images|outbound-influencer-images)'
 ORDER BY policyname;
```

위 조회는 조건에 통 이름이 **글자로 적힌** 정책만 잡는다. 통 이름 없이 모든 통에 걸리는 정책이 있을 수 있으니 전체 목록도 함께 뽑는다.

```sql
SELECT policyname, cmd, roles::text, qual, with_check
  FROM pg_policies
 WHERE schemaname = 'storage' AND tablename = 'objects'
 ORDER BY policyname;
```

볼 것:
- `receipts_insert_authenticated` 의 조건식 전문 — 마이그레이션 B 에 **글자 그대로** 옮겨 적는다. 개발서버에 있는지도
- 개발서버의 `campaign_images_select` 대상 역할 — 311(캠페인 이미지 통 비로그인 목록 차단)이 개발서버에 적용됐는지
- 같은 일을 하는 정책이 **다른 이름으로** 있는지(있으면 마이그레이션에서 함께 지운다)

### ② 「올린 사람」 칸 — 운영·개발 각각

```sql
SELECT column_name, data_type
  FROM information_schema.columns
 WHERE table_schema = 'storage' AND table_name = 'objects'
   AND column_name IN ('owner', 'owner_id');

SELECT count(*) AS total, count(owner) AS has_owner, count(owner_id) AS has_owner_id
  FROM storage.objects
 WHERE bucket_id = 'campaign-images' AND name LIKE 'receipts/%';
```

- 칸이 둘 다 있으면 **값이 채워진 쪽**을 쓴다. 자료형이 글자면 로그인 사용자 고유번호를 글자로 바꿔 견준다.
- 옛 파일에 값이 비어 있어도 설계는 성립한다 — 회원은 목록을 볼 필요가 없고, 관리자는 관리자 조건으로 본다. 다만 **새로 올린 파일에 값이 들어가는지**는 사양서 검증 4·5 에서 확인된다.

### ③ 아웃바운드 통 파일 수 — 운영

```sql
SELECT count(*) FROM storage.objects WHERE bucket_id = 'outbound-influencer-images';
```

0이면 기획 세션이 본 「비로그인 목록 0건」은 통이 비어서였다.

### ④ 파일 폴더가 있는 살아 있는 시트 수 — 운영 (조회됨 · 참고)

```sql
SELECT count(*)
  FROM public.orient_sheets s
 WHERE s.status IN ('draft', 'submitted')
   AND (s.token_expires_at IS NULL OR s.token_expires_at > now())
   AND EXISTS (
     SELECT 1 FROM storage.objects o
      WHERE o.bucket_id = 'orient-images'
        AND (storage.foldername(o.name))[1] = s.token::text
   );
```

토큰을 새로 발급하게 될 때의 대상 수다. 「살아 있는」 조건은 올리기 허용 판정(`orient_token_can_upload`)과 같다.

### ⑤ 저장소 요청 기록 — 운영 (조회됨 · 참고)

대시보드의 기록 화면(저장소 쪽)에서 `object/list/orient-images` 요청을 찾는다.

- **보관 기간이 며칠인지**부터 적는다. 그 기간 밖은 알 수 없다.
- **우리 시험을 빼고** 센다 — 2026-09-29 한국 시각 12시~13시 사이에 기획 세션이 운영에 두 번, 개발 세션이 개발서버에 여러 번 보냈다. 사후 확인(가)에서 보낸 요청도 우리 것이다.
- 우리 것이 아닌 요청이 있으면 **시각·건수·요청한 쪽 정보**를 적는다.
- ⚠️ 그 화면에 **우리가 보낸 요청이 다 잡히지 않을 수 있다** — 첫 조회에서 기획 세션의 측정이 안 보였다(사양서 §10). 「우리 것뿐」이라는 결과는 그 화면이 보여준 범위 안에서만 말한다.

## 다. 결과를 어디에 적나

| 무엇 | 어디에 |
|---|---|
| 사후 확인 결과(가) | 사양서 **§10** 의 「사후 확인」 표 — 빈 칸을 채운다 |
| 단계 0 조회 결과(나) | 사양서 **§10** 에 줄을 더한다 |
| 조회 결과로 설계가 달라지면 | 사양서 본문을 고치지 말고 **기획 세션에 되돌린다** |

**사용자가 정할 것은 남아 있지 않다.** 토큰은 「교체하지 않는다」, 브랜드 담당자에게는 「알리지 않는다」로 정해졌다(둘 다 사양서 §10) — **다시 묻지 않는다.** 나중에 우리 것이 아닌 목록 조회가 발견되면 그때 `/약관확인` 으로 통지 의무부터 본다.

## 조심할 것

| 무엇 | 왜 |
|---|---|
| 운영 조회는 **크롬으로 대시보드에서** 하고, 어느 서버인지 화면으로 확인한다 | `.claude/rules/supabase.md` |
| SQL 편집기는 쓰고 나면 **그 자리에서 닫는다** — 그냥은 안 닫히니 다른 주소로 옮긴 뒤 닫는다 | `.claude/rules/browser-qa.md` |
| 정책이 막는지는 **SQL 편집기로 확인할 수 없다** | 서비스 키로 돌아 정책을 거치지 않는다. 실제 요청·실제 로그인으로 본다 |
| 「0건」을 합격으로 읽기 전에 **파일이 있는 상태인지, 관리자는 받는지** 본다 | 빈 통도 0건이다 |
| 지우기는 **조용히 성공한다** | 안 보이는 파일을 「없는 파일」처럼 답한다. 지운 뒤 공개 주소를 캐시 우회로 열어 본다 |
| 크롬은 한 번에 한 세션만 | `.claude/rules/multi-session.md` |

- 보안 점검 화면의 나머지 경고(함수 실행 권한 376건 등) — 사양서 §9 에 분류만 해 두었고 이번 범위가 아니다
- 통을 비공개로 바꾸는 일 — 보류 결정 그대로
- 오리엔시트 통에 지우기 정책 만들기 — 범위 밖
