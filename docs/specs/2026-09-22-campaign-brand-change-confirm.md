# 캠페인 브랜드를 바꿀 때 확인 창

**작성일:** 2026-09-22 · **작성:** 기획 세션
**계기:** 오리엔시트·캠페인·브랜드 상관관계 2차 검토(2026-09-22)에서 발견 → 운영 실측 → 사용자 판단 「일부러 옮긴 것이다」(2026-09-22). 사용자 보충: 라페름·팜스테이는 **둘 다 명인화장품의 브랜드**(같은 회사 안에서 옮긴 것). 그래서 **이미 옮긴 캠페인은 그대로 두고**, 앞으로 옮길 때 그 결과를 알려 주는 확인 창만 넣는다.

---

## 0. 한 줄 요약

캠페인의 브랜드가 바뀌는 길이 **둘**이고, 둘 다 아무 말 없이 저장된다. 저장 직전에 결과를 알리는 확인 창을 띄운다. **막지는 않는다.** 데이터베이스 변경은 없다.

| 길 | 바꾸면 번호는 | 오리엔시트는 |
|---|---|---|
| ① 편집 화면에서 브랜드 변경 | **그대로**(이미 매겨진 번호) | 그 캠페인에 연결된 시트가 있으면 시트는 **시트 브랜드에 그대로 남는다** |
| ② 오리엔시트 발행 폼에서 자동으로 채워진 브랜드를 바꿈 | **고른 브랜드 번호**로 새로 매겨짐(저장 전이라) | 시트는 **시트 브랜드에 남고**, 카드는 「발행됨」 |

⚠️ 「같은 회사면 그 사실을 창에 보여 준다」는 한때 넣었다가 **뺐다**(정합성 점검 2·3차에서 비교 대상·보관 브랜드·회사명 빈 값 갈래가 계속 새로 생겼고, 사용자가 요청한 것이 아니라 기획이 덧붙인 것이었다). 필요하면 후속으로.

## 1. 현재 상태 (2026-09-22, `origin/dev` 기준 — 규칙 A)

### 1-1. 두 길 — 둘 다 검사 없음

| 길 | 자리 | 지금 |
|---|---|---|
| ① 편집 화면 | `saveCampaignEdit`(`dev/js/admin.js`) — `editCampBrandId` 를 읽어 `brand_id` 로 저장 | 브랜드 칸(`editCampBrandInput`, `dev/admin/index.html:494`)은 검색형 드롭다운으로 **자유롭게 바뀐다.** 원래 브랜드와 비교하지 않는다. 편집 스냅샷 `_editCampOriginal`(`admin.js:1250`)에 **`brand_id` 가 없다** |
| ② 오리엔시트 발행 폼 | `applyOrientCardPrefill`(`dev/js/admin-orient.js`)이 시트의 `brand_id` 로 브랜드 칸을 채움 → `addCampaign`(`admin.js:4504`)이 `newCampBrandId` 로 저장 | 발행 컨텍스트 `window._orientPublishCtx` 에는 `orientId`·`cardIdx`·`isProxy` 만 있고 **시트 브랜드가 없다.** 저장할 때 시트 브랜드와 비교하지 않는다 |

### 1-2. 번호가 어떻게 되나

- 채번 트리거(`generate_campaign_no`, 마이그레이션 090)는 **삽입 때만** 돈다. 그래서 ①편집으로 바꾸면 번호 앞자리(`B####`)는 **처음 매겨진 그대로**, ②발행 폼에서 바꾸면 **고른 브랜드 번호**로 매겨진다.
- 번호를 다시 매기는 경로는 **브랜드 병합**(`merge_brands`, 175·328)과 **신청 연결**(`link_campaign_to_application`, 121) 둘뿐이다. **편집은 그 둘을 거치지 않으므로 이 사양서에서도 번호를 다시 매기지 않는다** — CLAUDE.md 의 기존 결정(2026-08-26 「과거 33건은 재발급하지 않기로」 — 그 번호로 나간 견적서·메일과 어긋나지 않게)과 같은 방향이다.
- 번호는 화면 표시·검색에만 쓰이고 기능 분기가 없다(1차 검토 확인, 코드에서 번호를 파싱해 분기하는 곳 0건). 그래서 **기능이 깨지지는 않는다.**
- 시트의 `brand_id` 는 캠페인을 따라 바뀌지 않는다. 그래서 시트 브랜드 상세의 오리엔시트 카드는 「발행됨」인데, 그 캠페인은 다른 브랜드 목록에 보인다.

### 1-3. 운영 실측 (2026-09-22, 운영 SQL 편집기 읽기 전용 조회)

| 셈 | 결과 |
|---|---|
| 오리엔시트에 연결된 캠페인 중 시트 브랜드 ≠ 캠페인 브랜드 | **51건 중 8건** — 라페름 시트→팜스테이 6건(B0058-C004~C007·B0071-C001·C002), 티엘비코리아 시트→패치파이 2건(B0062-C001·C002) |
| 계층 번호(`B####-…`) 캠페인 중 번호 앞자리 ≠ 지금 브랜드 | **225건 중 7건** — 위 B0058 4건 + 오가니시티 B0027-C001 + 벤튼 B0040-C001·C002 |

사용자 판단: **일부러 옮긴 것**(2026-09-22, 라페름·팜스테이는 같은 회사 명인화장품). → **과거 건은 고치지 않는다.**

### 1-4. 재사용할 것

- 확인 창 `showConfirm(message, okLabel, cancelLabel)` — 같은 저장 함수 안의 `confirmMonitorWithoutPrice`(`admin.js:4403`)와 같은 꼴.
- 오리엔시트 연결 여부 — `fetchOrientSheets()` 결과의 `data.cards[].campaign_id`. ⚠️ 이 값은 **새로 발행한 캠페인과 기존 캠페인을 연결만 한 경우를 둘 다** 잡는다 — 그래서 창 문구는 「발행됐다」가 아니라 「연결된」으로 쓴다(오리엔시트 화면 `osLinkedCampaignIds`, `admin-orient.js:1766` 과 같은 방식). 연결된 시트를 찾으면 **그 시트의 `brand_id`** 로 시트 브랜드 이름을 얻는다.
- 🔴 **브랜드 이름은 이 규칙 하나로 구한다**(원래 브랜드·새 브랜드·시트 브랜드 세 자리 공통, 판정 순서대로):
  ① id 가 비어 있으면 **「브랜드 없음」** — 옛 캠페인은 `brand_id` 가 없을 수 있다(원래 브랜드 자리에서만 생긴다)
  ② 브랜드 목록 캐시(`_campBrandsCache`)에 있으면 그 이름(`campBrandLabel` — 화면과 같은 「이름 [번호]」)
  ③ 캐시에 없으면(보관된 브랜드 — 이 캐시는 활성만 담는다, `admin.js:5875`) `fetchBrandById` 로 찾아 **「이름 [번호] (보관)」** — 🔴 **폼의 브랜드 칸이 이미 이렇게 보여 준다**(`loadCampBrandSelect`, `admin.js:5880-5884` — `campBrandLabel` 이 번호를 붙이므로 폼 칸도 「이름 [번호] (보관)」). 창도 같은 글자를 쓰게 그 방식을 그대로 따른다
  ④ 그래도 못 찾으면(조회 실패) 「(이름을 불러오지 못한 브랜드)」
- 창에 나오는 새 브랜드·고른 브랜드는 늘 캐시 안에 있다 — 브랜드 칸 목록은 캐시에서 나오고(신규 브랜드를 만들면 캐시를 비워 다시 받는다, `admin-brand.js:1860`), 캐시 밖 값은 **원래 브랜드·시트 브랜드(보관)가 칸 값으로 남아 있는 경우뿐**이다. 창은 그 값과 **다를 때만** 뜨므로, 그때 칸에 든 새 값은 목록(캐시)에서 고른 것이다. 입력 검증이 브랜드를 필수로 요구하므로 비는 일도 없다.

### 1-5. 지금 저장 함수에 있는 확인 창 순서

- 편집(`saveCampaignEdit`): 입력 검증 알림들 → 종료 전환 대량 낙첨 확인(`confirmCampaignEndMassReject`) → 마감일 연장 확인 → 제품 금액 0 확인(`confirmMonitorWithoutPrice`) → 채널 제거 확인.
- 신규·발행(`addCampaign`): 입력 검증 → 제품 금액 0 확인 → (오리엔시트 발행일 때) 일본어 보완 게이트(`window.prompt`/`window.confirm`).

### 1-6. 충돌 가능 동작

- 없음 — 확인한 영역 3개: ①캠페인 복제(`duplicateCampaign`)는 원본 브랜드를 그대로 이어받아 브랜드가 바뀌지 않는다 ②브랜드 병합은 번호·시트를 함께 옮기므로 이 창과 무관하다 ③§1-5 의 기존 확인 창은 문구·동작을 바꾸지 않는다.

## 2. 의심·경우의 수 (규칙 B)

1. **(UX) 확인 창이 너무 자주 뜨면 무시된다** — 저장에는 이미 확인 창이 여럿 있다. → **브랜드가 실제로 바뀐 경우에만** 띄운다.
2. **(UX) 창이 여럿 겹치면 무엇을 확인하는지 헷갈린다** — 두 경로 모두 한 저장에 창이 여럿 뜰 수 있다(편집은 §1-5 의 넷, 발행은 금액 0 확인과 일본어 보완 게이트). → 브랜드 창을 **입력 검증 뒤 가장 먼저** 띄운다(브랜드가 가장 근본적인 변경이라, 거기서 돌아가면 뒤 창을 볼 필요가 없다). 순서는 §3-1 한 곳에서 정한다.
3. **(데이터) 편집 스냅샷에 값이 빠지면 창이 죽은 코드가 된다** — `_editCampOriginal` 에 `brand_id` 를 안 넣으면 비교가 늘 어긋나 창이 안 뜨거나 늘 뜬다. CLAUDE.md 가 같은 유형(채널 제거 확인창이 스냅샷 키 누락으로 죽는 위험)을 이미 경고한다. → 스냅샷에 넣고 **브라우저로 한 번은 실제로 띄워 본다**.
4. **(데이터) 이미 옮겨진 캠페인을 다시 편집하면 「옛 브랜드」가 시트 브랜드가 아니다** — §1-3 의 8건처럼 시트 브랜드와 캠페인 브랜드가 이미 다른 캠페인이 있다. → 오리엔시트 문장의 브랜드는 **캠페인의 옛 브랜드가 아니라 시트 자신의 브랜드**로 채운다. 번호 문장도 「옛 브랜드 번호」라 단정하지 않는다(번호 앞자리가 이미 지금 브랜드와 다른 캠페인·계층 번호가 아닌 캠페인이 있다).
5. **(동시성) 오리엔시트 조회 실패** — 편집 저장 때 연결 여부를 알려고 시트 목록을 부르는데 실패할 수 있다. → 실패하면 오리엔시트 문장 자리에 「오리엔시트 연결 여부는 확인하지 못했습니다.」를 쓴다(실패를 「연결 없음」으로 단정하지 않는다).
6. **(권한) 없음** — 편집·발행 권한 자체는 안 바뀐다.

**현재 구현과 어긋나는 지점:** `_editCampOriginal` 에 `brand_id` 가 없다 · `_orientPublishCtx` 에 시트 브랜드가 없다 — 둘 다 추가해야 한다.

**의도 모호점:** 「막을지 알릴지」 — 사용자 판단(일부러 옮김, 같은 회사)대로 **알리기만** 한다. 막으면 자매 브랜드로 옮기는 정상 업무가 막힌다.

## 3. 설계

### 3-1. 창 순서 — 두 경로 공통 규칙 (이 절이 유일한 정의처)

- 브랜드 창은 **입력 검증을 통과한 뒤 가장 먼저** 뜨는 확인 창이다. 그 뒤 창들의 순서는 **지금 그대로**(§1-5).
  - 편집: 입력 검증 → **브랜드** → 종료 전환 대량 낙첨 → 마감일 연장 → 제품 금액 0 → 채널 제거
  - 발행: 입력 검증 → **브랜드** → 제품 금액 0 → 일본어 보완 게이트
- 두 경로 모두 브랜드 창에서 **「돌아가기」면 저장·발행하지 않고, 뒤 창도 띄우지 않는다.**

### 3-2. 편집 화면 (`saveCampaignEdit`)

- `_editCampOriginal` 에 `brand_id: camp.brand_id || ''` 를 넣는다(`admin.js:1250`).
- `editCampBrandId` 값이 원래 `brand_id` 와 **다를 때만** 창:

```
브랜드를 「{원래 브랜드}」에서 「{새 브랜드}」로 바꿉니다.

· 캠페인 번호 {campaign_no} 는 바뀌지 않습니다.
· 이 캠페인은 「{시트 브랜드}」 오리엔시트에 연결돼 있습니다. 그 시트는 「{시트 브랜드}」에 그대로 남습니다.   ← 연결된 경우만
  (조회 실패면 이 줄 대신 「오리엔시트 연결 여부는 확인하지 못했습니다.」)

[바꿔서 저장]  [돌아가기]
```

- 🔴 `{시트 브랜드}` 는 **연결된 시트의 `brand_id`** 로 채운다 — `{원래 브랜드}` 로 채우면 이미 옮겨진 캠페인(§2 4번)에서 틀린 말을 한다.
- 세 자리(`{원래 브랜드}`·`{새 브랜드}`·`{시트 브랜드}`)의 이름은 §1-4 규칙으로 구한다.

### 3-3. 오리엔시트 발행 폼 (`applyOrientCardPrefill` → `addCampaign`)

- `applyOrientCardPrefill` 이 `_orientPublishCtx` 에 `sheetBrandId: brandId` 를 함께 담는다.
- `_opc` 가 있고 **`_opc.sheetBrandId` 에 값이 있고**, `newCampBrandId` 가 그 값과 **다를 때만** 창(시트 브랜드를 모르면 창을 안 띄운다 — 비어 있는 값과 비교하면 발행마다 창이 뜬다). 이름은 §1-4 규칙으로 구한다.
  - 시트 브랜드가 **보관된 브랜드**여도 브랜드 칸은 비지 않는다 — `loadCampBrandSelect` 가 값을 그대로 두고 「이름 [번호] (보관)」으로 보여 준다(§1-4 ③). 그대로 발행하면 브랜드가 같아 창이 안 뜨고, 다른 브랜드로 바꾸면 창이 뜬다:

```
오리엔시트는 「{시트 브랜드}」 것인데 「{고른 브랜드}」로 발행합니다.

· 캠페인 번호는 「{고른 브랜드}」 번호로 매겨집니다.
· 오리엔시트는 「{시트 브랜드}」에 그대로 남고, 이 카드는 「발행됨」으로 표시됩니다.

[이대로 발행]  [돌아가기]
```

### 3-4. 하지 않는 것

- 과거 8건·7건은 **고치지 않는다**(사용자 판단).
- 편집으로 브랜드를 바꿔도 번호를 다시 매기지 않는다(§1-2). 발행은 처음 매기는 것이라 해당 없다.
- 오리엔시트의 `brand_id` 를 캠페인을 따라 옮기지 않는다 — 시트는 브랜드가 작성해 보낸 원본이라 그 브랜드에 남는 것이 맞다.
- 데이터베이스 변경 없음.

## 5. 운영 배포 전제

데이터베이스 변경이 없다. 조각별로:

- **조각 1(편집 화면)** — 오리엔시트 개편(424~464)과 무관하다. **단독으로 운영에 올릴 수 있다.**
- **조각 2(발행 폼)** — 운영의 `admin-orient.js` 는 개편 이전 판이라 `applyOrientCardPrefill` 모양이 다르다. 개발 세션이 운영 판과 대조해 **그대로 붙으면 조각 1과 함께**, 안 맞으면 **조각 1만 먼저** 올리고 조각 2는 오리엔시트 개편 묶음과 함께 나간다.
- 🔴 조각 2는 **두 파일이 한 묶음**이다 — `admin.js` 의 `addCampaign` 비교 코드와 `admin-orient.js` 의 `sheetBrandId` 담기. 조각 1만 먼저 올릴 때 같은 `admin.js` 에 든 조각 2 비교 코드가 딸려 나가면 안 된다(§3-3 의 「값이 있을 때만」 조건이 막아 주지만, 쓰이지 않는 코드를 운영에 두지 않는다).
