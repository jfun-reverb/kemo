## 조각별 상세

### 작업 1 — 공용 기반: 데이터베이스 4개 + 접근 함수

- **하는 일:** 사양서 §4-2(데이터베이스 변경)를 그대로 만든다. 마이그레이션 4개(상대 순서 고정) + 뒤 조각 전부가 쓰는 접근 함수를 `dev/lib/storage.js` 한 곳에 모아 둔다.
- **담당 파일:** `supabase/migrations/` 신규 4개 · `dev/lib/storage.js` · `dev/lib/shared.js`
- **마이그레이션 상대 순서(번호는 파일 만드는 순간 확정 — 미리 적지 않는다):**
  1. 캠페인 표 컬럼 3개 추가
  2. 타임 표 `event_slots` 생성 + 접근 정책
  3. 티켓 표 `event_tickets` 생성 + 접근 정책
  4. 서버 함수 3개
  → **번호는 S3 병합 후 `ls supabase/migrations/ | tail -5`로 최신값을 다시 확인해 정한다.** 현재 디스크에 273·274가 있어 275부터가 후보지만, 그 세션이 더 만들 수 있어 병합 시점 재확인이 유일한 안전책이다.
- **산출 계약(이름 그대로 뒤 조각이 쓴다):**
  - 표 `public.event_slots` — `id · campaign_id · slot_date · start_time · end_time · capacity · audience_label · is_active · sort_order · created_at · updated_at`
  - 표 `public.event_tickets` — `id · slot_id · campaign_id · influencer_id · application_id · ticket_code · status(confirmed|waitlist|cancelled) · waitlist_position · entered_at · entered_by · scan_count · version · created_at · updated_at`
  - 캠페인 컬럼 — `event_mode boolean NOT NULL DEFAULT false` · `is_invite_only boolean NOT NULL DEFAULT false` · `invite_code text NULL`
  - 함수 3개(전부 `SECURITY DEFINER` + `search_path=''` + 행 잠금, 반환 `jsonb`):
    - `public.reserve_event_ticket(p_slot_id uuid, p_invite_code text DEFAULT NULL) → jsonb`
    - `public.check_in_ticket(p_ticket_code text) → jsonb`
    - `public.cancel_event_ticket(p_ticket_id uuid) → jsonb`
  - **반환 키 이름(계약의 핵심 — 화면 3개가 이 이름으로 읽는다):** `ok` · `reason`(실패 코드: `invite_required`·`invite_mismatch`·`already_applied`·`slot_closed`·`cancel_window_passed`·`not_found`·`cancelled`·`waitlist_cannot_enter`·`permission_denied`) · `ticket_id` · `ticket_code` · `status` · `waitlist_position` · `slot`(중첩: `slot_date`·`start_time`·`end_time`·`audience_label`) · `name_kanji` · `name_kana` · `entered_at` · `already_entered` · `scan_count` · `promoted_ticket_id`

- **주의:** **이 조각이 1차 배포(8월 8일) 자체를 막는다.** 1차 배포 시점부터 방문 예약 정보 수집이 시작되므로 입장 기록 항목까지 **한 번에** 개정해 개정·통지를 두 번 하지 않는다

### 작업 7 — 현장 확인 페이지: 예약번호 손입력

- **하는 일:** 사양서 §4-4의 자립형 페이지. **카메라보다 손입력을 먼저** 완성한다(§8 안전선).
- **담당 파일:** **`dev/event-scan.html`(신규)** · `dev/build.sh`
- **산출 계약:**
  - 주소 `/event-scan.html`(확장자 포함 — 루트 사이트는 확장자 생략 설정이 없다)
  - 요소 id `#codeInput` · `#resultCard` · `#recentList`
  - 관리자 로그인 필요. 자립형이라 `dev/lib/storage.js`를 못 쓰므로 **호출을 이 파일 안에 직접 쓴다**(선례: 관리자 비밀번호 설정 페이지·오리엔시트 작성 폼). 호출은 `check_in_ticket` 하나
  - 로그인 유지 설정은 **켠다**(관리자 비밀번호 설정 페이지에서 이 설정이 모드마다 달랐던 함정 있음 — 현장 확인은 계속 로그인 상태여야 한다)
  - `dev/build.sh` 4번 블록과 같은 방식으로 `../event-scan.html` 복사 블록 추가
- **선행 의존:** 작업 1. **검증은 작업 4가 만든 티켓이 있어야 가능**
- **완료 정의:** 휴대폰에서 예약번호 입력 → 이름·날짜·타임·상태 표시 후 입장 처리, 같은 번호 재입력 시 **「이미 입장 완료 · 첫 입장 시각」** 노란색(입장은 막지 않는다). 취소·대기·없는 번호는 빨간색. 결과 카드 3초 후 다음 확인 준비 + 최근 5건 유지
- **필요 검문소:** `reverb-reviewer` + 휴대폰 실기기 1대 이상
- **주의·롤백:** 인터넷이 끊기면 **손입력도 함께 멈춘다**. 1차 범위 대비는 **당일 아침 명단 엑셀 인쇄**(작업 2 리포트) 눈 대조 후 복구 시 관리자 「입장 처리」로 손 반영. 이 절차를 페이지 안 안내에도 한 줄 넣는다. 롤백은 파일 삭제 + 빌드 블록 제거

### 작업 8 — 같은 페이지에 카메라 QR 스캔 추가

- **하는 일:** 손입력 화면에 후면 카메라 스캔 병설, 권한 거부·미지원 시 손입력만으로 계속 진행.
- **담당 파일:** `dev/event-scan.html`
- **산출 계약:** (마지막 조각). 내부: `#scannerVideo` · `startScanner()` · `stopScanner()`
- **선행 의존:** 작업 7
- **완료 정의:** **실제 운영진 기기 2종 이상**으로 개발서버 스캔 리허설 통과. 권한을 거부해도 손입력 정상 동작(안내 문구)

### 1차 배포(8월 8일)에 반드시 들어가야 하는 것 / 미룰 수 있는 것

**반드시:** 작업 1 · 작업 2의 「행사 모드 폼 + 타임 관리」 · 작업 3 · 작업 4 · 작업 5 · **작업 6**
**2차로 미룰 수 있음:** 작업 7 · 작업 8(현장 확인은 행사 당일에만 필요)

**일정이 밀렸을 때 1차 배포에서 빼도 되는 여유분 2개:**
1. **작업 2의 리포트 엑셀** — 행사 당일 아침 명단 인쇄에 필요하므로 8월 28일 전까지면 된다
2. **작업 2의 「입장 처리」 버튼** — 인터넷 끊김 대비용이라 2차 배포 시점까지면 된다

**절대 미룰 수 없는 것은 작업 6(정책 개정)** — 1차 배포 순간부터 수집이 시작되므로 「나중에」가 성립하지 않는다.

### 배포 사이 빈 구간

1차 배포(8월 8일)부터 2차 배포(8월 19일)까지 **입장 확인 수단이 없다.** 행사는 8월 28일이라 이 구간에 들어가지 않는 것은 확인됐다. 2차 배포와 행사 사이 예비 8일이 남으므로 카메라 스캔(작업 8)이 늦어도 손입력(작업 7)만으로 행사를 치를 수 있다.
