## 0. 한 줄 요약

리뷰어형(monitor) 캠페인은 「캠페인 리워드 금액」이 아니라 **인플루언서가 실제로 결제한 영수증 금액을 돌려주는 방식(페이백)** 인데, 현재 정산 기능은 금액 출처를 `campaigns.reward` 한 곳으로만 보고 있어 리뷰어형 승인 응모 1,064건이 통째로 정산 대상에서 빠져 있다. 금액 산정 규칙을 모집 형식별로 분기하고, 그에 따라 관리자 화면·인플루언서 화면·약관 문구를 함께 정리한다.

### 발단 — 2026-07-23 운영 실측

| 조회 | 결과 |
|---|---|
| 승인 응모 전체 | 1,717건 — 그중 **1,667건이 캠페인 리워드 0원** |
| 리뷰어형(monitor) | 캠페인 56개 **전부** `reward = 0`, 승인 응모 1,064건 → 정산 후보 **0건** |
| 기프팅(gifting) | 34개 중 33개가 0원. 유일하게 금액이 든 `B0032-C002`(5,000엔·승인 50명)만 후보 |
| 현재 「과거 미등록」 39건 | 위 캠페인 1개의 인증 성공분 — **계산 자체는 정확** |
| 리뷰어형 `reward_note` | 「상시가 2200」처럼 **제품 정가 메모**(지급액 아님) |
| 승인 영수증 금액 품질 | 590건 / 미입력 1 / 0 이하 1 / 십만 초과 0 / 최소 822 · 평균 3,734 · 최대 24,269 |

## 1. 현재 상태 (기획 규칙 A — 직접 읽고 검증 완료, 2026-07-23 기준)

### 1-1. 정산 금액이 만들어지는 경로 (데이터베이스 함수)

| 파일 | 지금 하는 일 | 이번 작업과의 관계 |

### 1-2. 인증 성공 판정 단일 기준 (화면 쪽)

- `dev/js/admin-deliverables.js` → `buildDeliverableGroups()` + `computeCertStatus()`
  - 리뷰어형(monitor): **영수증 승인 + 캠페인이 요구하는 채널 전부의 인증샷 승인**
  - 가구매형(`campaigns.proxy_purchase = true`): **영수증 승인만**
  - 시딩(gifting)·방문형(visit): **게시물 승인만**
- 위 판정을 데이터베이스에서 그대로 재현한 것이 `_settlement_cert_candidates()`. **이번 작업에서 인증 성공 판정 자체는 손대지 않는다**(금액 계산만 추가).

### 1-3. 영수증 금액이 들어오는 경로

- 표: `deliverables` (`kind='receipt'`), 금액 칸 `purchase_amount **numeric**`(소수점 허용, 주석에 "엔화·달러 모두 대응"이라 적혀 있으나 **통화 구분 칸은 없음**)
- 인플루언서 제출: 주문번호 + 구매일 + 구매금액 **3종 모두 필수**
- 관리자 수정(`update_receipt_admin`, 마이그레이션 178 「영수증 필수 항목 완화」): **3종 중 1개만 있어도 저장 가능**, 금액은 `0` 이상이면 허용(즉 **0원 저장 가능**), 빈값 저장 가능 → 승인 영수증인데 금액이 비는 경우가 앞으로도 생길 수 있음
- 수정 이력은 `receipt_edit_history`에 자동 기록

### 1-4. 인플루언서가 지금 보고 있는 「금액 약속」 (매우 중요)

`dev/js/application.js`(캠페인 상세·하단 고정 바)를 확인한 결과, **리뷰어형 캠페인의 화면 문구는 `campaigns.product_price`(제품 가격)를 기준으로 「¥○○ 円ペイバック(엔 페이백)」이라고 표시**하고 있다. 즉 인플루언서가 응모 시점에 약속받은 숫자는 **제품 표시가**이지, 나중에 자기가 실제로 결제한 영수증 금액이 아니다.

- `camp.reward > 0`이면 그 아래에 「+ 現金報酬 ¥○○(현금 보수)」가 **추가로** 붙는 구조 → 리뷰어형에도 현금 리워드가 함께 있을 수 있는 화면 구조임(현재 운영 데이터상 리뷰어형은 전부 0원이지만 구조적으로 가능)
- 실측된 `reward_note`의 「상시가 2200」 메모는 **표시가 메모**로 보이며, 지급액 근거로 쓰이고 있지 않다

### 1-5. 관리자·인플루언서 화면

- 관리자 정산 화면 `dev/js/admin-settlements.js`
  - 목록 열: 인플루언서 / 캠페인 / **금액(¥)** / PayPal / 상태 / 인증성공일 / 송금완료일 / 처리
  - 금액은 `settlements.amount_jpy` 하나만 보여줌 — **금액이 어디서 나왔는지, 영수증이 어떤 것인지 화면에 전혀 없음**
  - 「과거 미등록」 별도 화면: 체크박스 다중선택 → 「송금완료 기록」(되돌릴 수 없음, 확인 모달 있음) / 「정산대기 추가」. 필터 없음, 50건씩 지연 로딩
  - 송금완료 모달: 이름·캠페인·금액·PayPal만 표시
  - 엑셀: 이름/이메일/캠페인/금액/PayPal/상태/인증성공일/송금완료일
- 인플루언서 화면 `dev/js/mypage.js` → `renderMySettlements()`
  - 제목 「報酬・精算」, 큰 카드 「累計受取額(누적 수령액)」, 보조 「お支払い予定(지급 예정)」
  - 상태 라벨: 精算待ち / 送金済み / 確認中, 취소 건은 숨김
  - 문구는 전부 「보수(報酬)」 전제 — 환급(돌려받는 돈) 개념 문구는 없음
  - **현재 잠금 상태라 인플루언서에게 안 보임**
- 데이터 접근 함수 `dev/lib/storage.js`: `fetchSettlements` / `fetchMySettlements` / `backfillSettlements` / `markSettlement*` / `fetchPastUnregisteredSettlements` / `registerPastSettlements` / `fetchSettlementEvents`

### 1-6. 이 제안과 충돌 가능성 있는 기존 동작

1. **`c.reward > 0` 후보 조건** — 리뷰어형 전량 배제의 직접 원인. 반드시 분기해야 함
2. **`amount_jpy > 0` 저장 제약** — 영수증 금액이 비었거나 0 이하인 건이 후보에 섞이면 **저장이 통째로 실패**한다. 자동 등록은 한 문장(single statement)으로 여러 건을 한꺼번에 넣기 때문에, **한 건만 잘못돼도 그 회차 전체가 실패**하고 관리자가 정산 화면을 열 때마다 오류가 난다 (실측 「금액 미입력 1건·0 이하 1건」이 정확히 이 상황)
3. **「생성 시점 스냅샷 고정」 원칙**(217번 표 주석) vs 영수증 금액이 나중에 수정되는 현실 — 원칙끼리 부딪힘
4. **인플루언서에게 약속된 금액은 제품 표시가(페이백)** 인데 정산은 영수증 실결제액 → 두 숫자가 다를 수 있음(세일가·쿠폰·포인트·배송비)
5. **`register_past_settlements`(과거 수동 등록)도 캠페인 리워드를 금액으로 사용** → 같이 안 고치면 과거 화면에서 잘못된 금액이 확정 저장됨
6. **헬퍼 함수 반환 항목을 늘리려면** PostgreSQL 특성상 `CREATE OR REPLACE`로는 안 되고 **삭제 후 재생성**이 필요하며, 그 헬퍼를 쓰는 함수 3개도 같은 트랜잭션에서 함께 재생성해야 한다(중간에 호출되면 오류)
7. 정산 삭제 가드·자동 보류·반려 차단(마이그레이션 246·247·251)과는 **충돌 없음 — 확인 완료**(금액 출처와 무관한 로직)

### 1-7. 미해결 백로그·관련 작업

- 정산 개선 로드맵(`docs/specs/2026-07-08-settlement-improvements.md`) — 명세서 메일·합산 일괄 송금·세무 통계. **이번 건은 그 앞단(금액 정합성)** 에 해당
- 포인트 제도 밑그림(`docs/specs/2026-07-08-point-reward-system.md`) — 미착수. 금액 출처를 「원장 항목」으로 일반화할 때 이번 결정이 그대로 상속됨
- 인플루언서 노출 잠금 해제(정산 공개) — 아직 미정. 이번 작업은 **잠금 상태에서 완료**하는 것을 전제
- `settlements.paypal_email`이 민감정보 가림막을 거치지 않는 직접 칸이라는 기존 유의사항(권한을 넓히면 노출) — 이번 작업으로 바뀌지 않음

## 2. 의심·경우의 수 (기획 규칙 B — 반대론자 모드)

### 2-1. 깨질 수 있는 경우의 수

**① [데이터·치명적] 금액이 0이거나 비어 있는 건 하나 때문에 정산 화면 전체가 고장난다**
정산 표는 금액이 반드시 0보다 커야 저장된다. 자동 등록은 여러 건을 한 문장으로 넣으므로, 영수증 금액이 빈 1건이 후보에 들어오면 **그 회차 전체가 실패**하고 관리자는 정산 화면에 들어갈 때마다 오류를 본다. 실측에서 이미 「미입력 1건 · 0 이하 1건」이 존재하므로 **가정이 아니라 확정된 사고 시나리오**다. → 후보 단계에서 반드시 걸러내야 한다.

**② [데이터] 소수점·통화 가정**
영수증 금액 칸은 소수점을 허용하는 형식이고, 정산 금액 칸은 정수형이다. 소수점이 있는 값이 들어오면 자동으로 잘리거나 반올림되어 **한 건당 몇 엔씩 어긋난 채 저장**된다. 또 금액 칸에 통화 구분이 없어 「엔화가 아닌 값이 섞여 있지 않다」는 것은 실측 범위(822~24,269)로 추정한 것일 뿐 보장이 아니다.

**③ [사용자 경험·필수] 인플루언서가 약속받은 숫자와 실제 받는 숫자가 다를 수 있다**
캠페인 상세에는 「¥2,200 円ペイバック」처럼 **제품 표시가**가 적혀 있는데, 실제 정산은 영수증 결제액이 된다. 세일가로 싸게 샀으면 인플루언서는 **약속보다 적게 받았다고 느끼고**, 배송비를 포함해 비싸게 샀으면 회사가 예상보다 많이 지급한다. 정산 화면을 인플루언서에게 공개하는 순간 문의가 몰릴 수 있는 지점이며, 앱 어디에도 「실제 결제하신 금액을 돌려드립니다」라는 설명이 없다.

**④ [사용자 경험] 관리자가 근거 없이 송금 버튼을 누르게 된다**
지금 정산 목록·송금완료 모달에는 금액 숫자만 있고 **어떤 영수증에서 나온 금액인지, 영수증 사진이 무엇인지**가 없다. 리뷰어형은 사람마다 금액이 다르므로 근거 확인 없이는 검증이 불가능하다. 게다가 「송금완료」는 **보류로만 되돌릴 수 있어** 잘못 누르면 회수 절차가 필요하다.

**⑤ [사용자 경험] 과거 미등록 화면이 갑자기 수백 건으로 불어난다**
지금 39건인 화면이 리뷰어형 대응 후 수백 건이 된다. 이 화면에는 **필터가 하나도 없고**, 전체 선택 체크박스가 있으며, 그 옆이 되돌릴 수 없는 「송금완료 기록」 버튼이다. **전체 선택 후 오조작 = 수백 건 일괄 송금완료** 라는 최악 시나리오가 실제로 가능하다.

**⑥ [기술·운영] 금액이 나중에 바뀐다**
관리자가 영수증 금액을 고칠 수 있게 완화(마이그레이션 178)돼 있어, 정산행을 만든 뒤 금액이 바뀌는 일이 정상 업무 흐름 안에 있다. 스냅샷을 고정하면 **틀린 금액으로 송금**되고, 항상 따라가게 하면 **이미 송금한 금액과 기록이 어긋나** 금전 감사가 무너진다.

**⑦ [권한·환경] 개발서버에는 리뷰어형 인증 성공 데이터가 거의 없다**
이번 변경의 핵심 위험(대량 건수·이상치·소수점)은 **운영 데이터에서만 재현**된다. 개발서버 검증만으로 통과시키면 운영에서 처음 터진다(2026-07-21 검수대기 배지 사고와 동일 패턴).

**⑧ [법률·약관] 「보수」와 「구매대금 환급」은 성격이 다르다**
약관 제13조(리워드 지급)는 「報酬(보수)」 기준으로 쓰여 있고, 3항은 "제품 무상 제공만 있는 캠페인은 현금 리워드가 없을 수 있다"만 규정한다. **구매대금을 돌려주는 페이백 유형은 조문에 명시가 없다.** 실비 환급인지 보수인지는 일본 세무상 취급이 달라질 수 있어(원천징수 없음·전액 지급이라는 결론은 같더라도 근거가 다름) — **세무사·변호사 확인이 필요한 영역이며 여기서 단정하지 않는다.**

### 2-2. 현재 구현과 어긋나는 지점

- (1-6의 1~6번 항목이 그대로 충돌점) 특히 **후보 조건의 `c.reward > 0`**, **금액 0 초과 저장 제약**, **스냅샷 고정 원칙**, **과거 수동 등록 함수의 금액 출처**는 코드를 고치지 않으면 이번 요구를 만족할 수 없다.
- 반대로 인증 성공 판정·자동 보류·반려 가드·정산 삭제 차단·권한 체계와는 **충돌 없음 — 확인 완료.**
- **지금이 규칙을 바꾸기 가장 싼 시점**: 운영 정산행이 사실상 없고(2026-07-22 점검 기록), 인플루언서 노출도 잠겨 있어 이미 저장된 금액을 되돌릴 부담이 거의 없다.

### 2-3. 사용자 의도와 다르게 해석될 수 있는 부분

1. **「영수증 구매금액을 환급」의 범위** — 배송비·포인트 사용분·쿠폰 할인 후 실결제액을 말하는지, 제품 정가를 말하는지. 영수증에 적힌 총액을 그대로 쓰면 배송비까지 회사 부담이 된다.
2. **가구매형(proxy_purchase)의 정체** — 인플루언서가 자기 돈으로 사고 영수증만 내는 것이면 환급 대상이지만, 회사가 대금을 미리 대주는 방식이면 **환급하면 이중 지급**이 된다. 실무 확인 필요.
3. **리뷰어형에 현금 리워드가 함께 붙는 경우** — 영수증 환급 + 현금 보수를 **한 건으로 합산**할지, 현금 보수는 지금처럼 별도로 볼지. 정산은 「응모 1건 = 1행」 구조라 합산이 자연스럽지만 명세는 흐려진다.
4. **「과거분」의 범위** — 리뷰어형 인증 성공 전부인지, 이미 오프라인에서 지급을 끝낸 것은 「송금완료 기록」으로만 남기고 미지급분만 정산대기로 올릴지.
5. **「정산」이라는 말** — 인플루언서 화면에서 보수와 환급을 한 화면에 섞을지, 구분해 보여줄지.

### 2-4. 권고 (의심 정리 뒤)

리뷰어형 금액 출처를 **승인된 영수증의 결제 금액**으로 잡는 방향 자체는 실무와 맞다고 본다. 다만 ①금액이 없는 건을 자동 등록에서 확실히 걸러내고 ②금액 근거(어느 영수증인지)를 정산행에 함께 저장해 관리자가 사진까지 확인한 뒤 송금하게 하고 ③제품 표시가와 크게 차이나는 건은 「확인 필요」로 따로 세우는 — 이 세 가지를 **같은 조각에 묶어서** 넣어야 안전하다. 인플루언서 문구·약관은 노출 잠금 덕분에 뒤에 붙여도 된다.

## 3. 설계

### 3-1. 금액 산정 규칙 (핵심)

정산 1건의 금액을 다음 순서로 정한다. **모집 형식 + 가구매 여부**로 갈린다.

| 모집 형식 | 정산 금액 | 금액 구분값(`amount_source`) |
|---|---|---|
| 리뷰어형(monitor, 가구매 아님) | **승인된 최신 영수증의 구매금액** (+ 캠페인 현금 리워드가 있으면 합산 — 사용자 확인 Q3) | `receipt` 또는 `receipt_plus_reward` |
| 가구매형(monitor + `proxy_purchase = true`) | 사용자 확인 Q2 결과에 따름 (초안: 리뷰어형과 동일) | `receipt` |
| 시딩형(gifting) · 방문형(visit) | **캠페인 리워드**(현행 그대로) | `reward` |

세부 규칙:

- **기준 영수증** = 인증 성공 판정에 쓰인 그 영수증(응모별 최신 1건, 상태 `approved`). 정산행에 **그 영수증의 식별자를 함께 저장**해 화면에서 사진·주문번호를 바로 열 수 있게 한다.
- **정수 처리**: 소수점이 있으면 **반올림**해 정수 엔화로 저장(규칙을 한 곳에 고정하고 사양서·주석에 명시).
- **자동 등록에서 제외하는 「금액 미확정」 조건** (아래 중 하나라도 해당):
  - 영수증 금액이 비어 있음
  - 영수증 금액이 0 이하
  - (선택 규칙, 사용자 확인 Q1-B 채택 시) 캠페인 제품 표시가 대비 지나치게 큼
  → 이 건들은 저장하지 않고, 관리자 화면의 **「금액 확인 필요」 목록**에 사유와 함께 표시한다. 관리자가 영수증 금액을 채우면 다음 진입 때 자동으로 정상 등록된다.
- **시딩·방문형의 리워드 0원 캠페인**은 지금처럼 정산 대상이 아니다(제품 제공만 있는 캠페인 — 약관 제13조 3항과 일치).

### 3-2. 데이터베이스 변경 (마이그레이션 **2개**, 순서 고정)

> 규칙에 따라 번호는 적지 않는다. 개발 세션이 파일을 만드는 시점에 확정하고 「구현 결과」에 사후 기록한다.

**마이그레이션 ① — 정산 표에 금액 근거 칸 추가 (먼저)**

- `settlements` 에 칸 3개 추가(모두 비어 있어도 됨 — 기존 행 영향 없음)
  - `amount_source text` — 금액 구분(`reward` / `receipt` / `receipt_plus_reward`). 허용값 제한 걸기
  - `receipt_deliverable_id uuid` — 금액 근거가 된 영수증 행 참조. **연결된 영수증이 지워져도 정산행은 남도록 「연결만 끊김」 방식**(감사 이력 유실 선례 반복 금지)
  - `reward_part_jpy bigint` — 합산했을 때 그중 현금 보수 부분(합산을 채택하는 경우에만 의미. 명세서·문의 대응용)
- 기존 행(있다면)은 `amount_source = 'reward'` 로 채움
- 표 주석의 "생성 시점 `campaigns.reward` 스냅샷" 문구를 새 규칙으로 교체
- 행 접근 정책(RLS)·권한 변경 **없음**

**마이그레이션 ② — 판정·금액 계산 헬퍼와 3개 함수 동시 재정의 (나중, 한 트랜잭션)**

- 공용 헬퍼 `_settlement_cert_candidates()` 를 **삭제 후 재생성**(반환 항목이 늘어나므로 교체만으로는 불가). 같은 파일·같은 트랜잭션 안에서 아래 3개 함수도 함께 재생성한다.
  - 후보 조건에서 **`c.reward > 0` 제거** → 대신 형식별 금액 계산 결과로 판단
  - 추가 반환 항목: `amount_jpy`(계산된 금액) · `amount_source` · `receipt_deliverable_id` · `receipt_amount_raw`(원본 소수점 값) · `reward_part_jpy` · `amount_issue`(금액 미확정 사유: 없음 / 금액없음 / 0이하 / 표시가대비과다)
  - **인증 성공 판정 로직은 한 글자도 바꾸지 않는다**(단일 소스 유지)
- `backfill_settlements()`(자동 등록) 재정의 — 금액을 헬퍼가 준 값으로 저장, **`amount_issue` 가 있는 건은 저장하지 않음**(치명적 사고 ① 차단), 정산 도입일 컷오프·알림 잠금·이력 기록은 **현행 그대로**
- `get_past_unregistered_settlements()`(과거 미등록 조회) 재정의 — 금액·금액 구분·금액 미확정 사유·(추가) 캠페인 번호를 함께 반환
- `register_past_settlements()`(과거 수동 등록) 재정의 — 금액을 헬퍼 값으로 저장, **금액 미확정 건은 서버가 조용히 건너뜀**, **알림 없음 원칙 유지**
- (선택) 「금액 확인 필요」 목록을 별도 함수로 뺄지, 과거 조회 함수에 사유 항목을 얹어 화면에서 나눌지 — 후자를 권장(함수 수 억제)

**변경하지 않는 것:** 인증 성공 판정, 정산 도입일 설정, 송금완료·보류·취소·보류해제 처리, 인플루언서 노출 잠금, 권한 체계, 자동 보류·반려 차단·삭제 차단 트리거.

### 3-4. 인플루언서 화면 (`dev/js/mypage.js` + `dev/lib/i18n/{ja,ko}.js`)

> 지금은 잠금 상태라 실제로 보이지 않는다. **공개 전에 반드시 반영**해야 하는 항목으로 남긴다.

- 항목마다 **금액 종류 한 줄** 표기 (초등학생 눈높이·짧은 말)
  - 환급: 「商品代金のお戻し」(상품 대금 돌려드림)
  - 보수: 「謝礼」 또는 현행 「報酬」
- 큰 카드 문구: 「累計受取額」 유지(둘 다 포함한 총액이라 의미가 맞음). 아래 보조 줄에 **구성 안내 한 줄** 추가 검토
- 화면 하단에 안내 한 줄:
  「レビュアー案件は、**実際にお支払いになった金額（レシートの金額）** をお戻しします。」
- 일본어·한국어 문구를 같은 뜻·같은 줄 수로 등록, 언어 전환 시 다시 그리기(현행 방식 유지)
- 모바일 목록이 2줄로 늘어나므로 줄바꿈·말줄임 확인 필요

### 3-5. 약관·세무 (단정하지 않음 — 확인 항목으로만)

- 약관 제13조는 「報酬(보수)」 지급 기준으로 작성돼 있고 **구매대금 환급(페이백) 유형이 명시돼 있지 않다.** 캠페인 상세에 「円ペイバック」로 안내하고 있어 개별 캠페인 조건으로는 성립하나, 약관 본문에 유형을 한 줄 추가하는 것이 안전한지 **변호사 확인 필요**.
- 일본 세무상 **실비 환급과 보수는 취급이 다를 수 있다.** 「원천징수 없음·전액 지급」이라는 현재 운영 결론이 환급에도 그대로 적용되는지 **세무사 확인 필요**.
- 개인정보 관점 변경은 없음(영수증·정산 정보는 기존 수집·이용 범위 안).
- 약관을 고치게 되면 공고·시행일 규칙(`.claude/rules/release-timing.md`)을 그대로 따른다. **코드 배포와 약관 시행은 분리**해도 된다 — 지금은 인플루언서에게 정산이 안 보이므로 집행 자체가 없다.

## 5. 검증 계획

### 5-1. 설계 확정 전 실측(먼저 돌려야 할 조회 — 운영, 1개씩 순차)

1. 리뷰어형 캠페인의 제품 표시가 유무: `product_price` 가 0이거나 비어 있는 리뷰어형 캠페인 수
2. **표시가 vs 실제 영수증 금액 차이 분포** — 승인 영수증 기준 (차이 ±10% 이내 / 초과 건수). Q1 선택지(상한 도입 여부)의 근거
3. 영수증 금액에 **소수점이 있는 건** 수
4. 리뷰어형 **인증 성공(영수증+채널 인증샷 전부 승인) 실제 건수** — 과거 미등록 화면에 뜰 예상 규모
5. 현재 정산 도입일(`settlement_settings.cutoff_at`) 값과 기존 정산행 수
6. 가구매형(`proxy_purchase = true`) 캠페인·승인 응모 수

### 5-2. 개발서버 시나리오

- 리뷰어형 인증 성공 1건 만들기 → 정산 화면 진입 → 금액이 **영수증 금액과 일치**하는지, 구분 배지가 「영수증」인지
- 영수증 금액을 비우고(관리자 수정) 다시 진입 → **오류 없이** 「금액 확인 필요」로만 잡히는지 (치명적 사고 ① 회귀 테스트)
- 금액 0 저장 → 같은 확인
- 시딩형 1건 → 금액이 캠페인 리워드 그대로인지(**기존 동작 회귀 없음**)
- 과거 미등록 화면 → 필터·선택 합계·금액 미확정 행 잠금·확인 모달 요약
- 송금완료 처리 → 이력에 금액·근거가 남는지, 인플루언서 알림이 **잠금 상태에서 안 나가는지**
- 권한: campaign_manager 계정으로 정산 화면·조회 함수 접근이 **여전히 차단**되는지
- 결과물 검수 화면·인증 성공 집계·운영현황 진행바에 **영향이 없는지**(판정 미변경 확인)

### 5-3. 운영 적용 시

- 마이그레이션 적용 → **정산 화면 진입 전에** 조회 함수로 예상 건수·합계·금액 미확정 건수 먼저 확인
- 자동 등록은 정산 도입일 설정에 걸려 있으므로 **의도치 않은 대량 생성이 없는지** 먼저 확인
- 인플루언서 노출 잠금이 **꺼진 상태 그대로**인지 재확인

## 6. 사용자 확인 필요

> 각 항목은 선택형 질문으로 변환해 1개씩 순차 확인.

**Q1. 리뷰어형 정산 금액의 기준을 무엇으로 할까요?** (헤더: `금액 기준`)
- **영수증 실결제액 그대로 (추천)** — 인플루언서가 실제로 낸 돈을 그대로 돌려줍니다. 가장 단순하고 실비 환급 취지에 맞습니다. 다만 캠페인 화면에 적힌 「¥○○ 페이백」 금액과 다를 수 있습니다.
- **영수증 금액 + 표시가 상한** — 실결제액을 주되, 캠페인 제품 표시가를 넘는 부분은 관리자 확인 대상으로 따로 세웁니다.
- **캠페인 표시가로 통일** — 모두 같은 금액을 지급합니다. 계산은 쉽지만 실제 결제액과 어긋나 환급 취지에서 벗어납니다.

**Q2. 가구매형(영수증만 내고 리뷰는 안 쓰는 캠페인)은?** (헤더: `가구매형`)
- **리뷰어형과 똑같이 영수증 금액 환급 (추천)**
- **정산 대상에서 제외** — 회사가 대금을 미리 대주는 방식이면 이중 지급이 됨
- **캠페인 리워드 기준 유지**

**Q3. 리뷰어형에 현금 보수가 함께 있으면?** (헤더: `보수 합산`)
- **영수증 금액 + 현금 보수를 합쳐 1건으로 (추천)**
- **영수증 금액만 정산**
- **당분간 보류** — 현재 해당 사례 없음

**Q4. 영수증 금액이 비었거나 0 이하인 건은?** (헤더: `금액 미확정`)
- **자동 등록에서 빼고 「금액 확인 필요」 목록으로 (추천)**
- **관리자가 그 자리에서 금액을 넣어 등록**
- **0원으로라도 만들기** — 권장하지 않음(구조 변경 필요)

**Q5. 정산을 만든 뒤 영수증 금액이 수정되면?** (헤더: `금액 변경`)
- **정산대기 상태면 따라 바꾸고, 송금완료는 그대로 (추천)**
- **항상 처음 금액 유지**
- **관리자가 「금액 다시 계산」 버튼으로 직접**

**Q6. 과거 리뷰어형 인증 성공분(수백 건)은?** (헤더: `과거분 처리`)
- **「과거 미등록」 화면에 필터·안전장치를 붙여 처리 (추천)**
- **캠페인 단위로 나눠 순차 처리**
- **정산 도입일을 조정해 대상 축소**

**Q7. 인플루언서 화면에서 환급과 보수를 구분할까요?** (헤더: `인플 문구`)
