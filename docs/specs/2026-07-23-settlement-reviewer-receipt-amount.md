# 인플루언서 정산 — 리뷰어형(monitor) 대응 설계

**작성일:** 2026-07-23
**작성:** 기획/설계 세션 (사양서 — 개발 착수 전)
**관련 사양서:** `docs/specs/2026-06-22-influencer-settlement.md`(정산 기본 설계) · `docs/specs/2026-07-09-settlement-cutoff-past-handling.md`(정산 도입일·과거분 처리)

> **개정 이력**
> - 1차 초안: 리뷰어형 정산액을 **영수증 실결제액**으로 설계
> - **1차 개정(같은 날, 사용자 확인 반영)**: 실무 송금 기준이 **캠페인 상시가(제품 표시가)** 임을 확인 → 금액 출처를 `campaigns.product_price` 로 변경. 영수증은 **구매 증빙**(인증 성공 판정)에만 사용. 이 개정으로 초안이 우려하던 위험 대부분이 소멸(아래 §2-5).

## 0. 한 줄 요약

리뷰어형(monitor) 캠페인은 **캠페인에 적힌 제품 가격(상시가)을 인플루언서에게 돌려주는 방식(페이백)** 인데, 현재 정산 기능은 금액 출처를 `campaigns.reward`(현금 리워드) 한 곳으로만 보고 있다. 리뷰어형 캠페인 57개는 이 값이 전부 0이라 **승인 응모 1,065건이 통째로 정산 대상에서 빠져 있다.** 금액 출처를 모집 형식별로 분기해(리뷰어형 = 제품 가격 / 시딩·방문형 = 현금 리워드) 정산이 실제 지급 실무와 맞도록 한다.

1. 리뷰어형 실제 송금 기준 = **캠페인 상시가(제품 표시가)**. 영수증은 구매했다는 증빙이며 금액 근거가 아니다.
2. 따라서 정산액 = `campaigns.product_price`. 화면에 약속한 「¥○○ 円ペイバック」과 **정확히 일치**한다.

### 1-2. 인증 성공 판정 단일 기준

- `dev/js/admin-deliverables.js` → `buildDeliverableGroups()` + `computeCertStatus()`
  - 리뷰어형(monitor): **영수증 승인 + 캠페인이 요구하는 채널 전부의 인증샷 승인**
  - 가구매형(`campaigns.proxy_purchase = true`): **영수증 승인만**
  - 시딩(gifting)·방문형(visit): **게시물 승인만**
- 이를 데이터베이스에서 재현한 것이 `_settlement_cert_candidates()`. **이번 작업에서 판정 자체는 손대지 않는다**(금액 계산만 교체).
- 즉 **영수증은 계속 필수**다. 금액 근거에서 빠질 뿐, 영수증이 승인되지 않으면 애초에 정산 대상이 아니다.

### 1-3. 인플루언서가 보고 있는 「금액 약속」

`dev/js/application.js`(캠페인 상세·하단 고정 바) 확인 결과, 리뷰어형은 **`campaigns.product_price` 를 기준으로 「¥○○ 円ペイバック」** 이라고 표시한다. `camp.reward > 0` 이면 그 아래에 「+ 現金報酬 ¥○○」가 **추가로** 붙는다(구조상 병행 가능하나 실측 병행 0건).

→ **정산액을 `product_price` 로 잡으면 화면 약속과 정확히 일치**한다. 시딩형은 `product_price` 를 「제품 제공」으로만 표시하고 금액은 `reward` 이므로, 형식별 분기가 화면 구조와도 맞는다.

### 1-5. 이 제안과 충돌 가능성 있는 기존 동작

1. **`c.reward > 0` 후보 조건** — 리뷰어형 전량 배제의 직접 원인. 반드시 분기해야 함
2. **`amount_jpy > 0` 저장 제약** — 금액이 0이거나 빈 건이 후보에 섞이면 저장이 통째로 실패(자동 등록은 여러 건을 한 문장으로 넣음). **제품 가격 기준에서는 실측 누락 0건이라 현재 위험 없음**. 다만 앞으로 가격 없는 캠페인이 생길 수 있으므로 방어는 유지한다
3. **「생성 시점 스냅샷 고정」 원칙**(217 주석) — 제품 가격 기준에서도 그대로 유효. 캠페인 가격을 나중에 고쳐도 기존 정산행은 불변
4. **`register_past_settlements`(과거 수동 등록)도 캠페인 리워드를 금액으로 사용** → 같이 안 고치면 과거 화면에서 잘못된 금액이 확정 저장됨
5. **헬퍼 함수 반환 항목을 늘리려면** `CREATE OR REPLACE` 로는 안 되고 **삭제 후 재생성**이 필요하며, 그 헬퍼를 쓰는 함수 3개도 같은 트랜잭션에서 함께 재생성해야 한다
6. 정산 삭제 가드·자동 보류·반려 차단(246·247·251), 인증 성공 판정, 권한 체계와는 **충돌 없음 — 확인 완료**

### 1-6. 미해결 백로그·관련 작업

- 정산 개선 로드맵(`docs/specs/2026-07-08-settlement-improvements.md`) — 명세서 메일·합산 일괄 송금·세무 통계. **이번 건은 그 앞단(금액 정합성)**
- 포인트 제도 밑그림(`docs/specs/2026-07-08-point-reward-system.md`) — 미착수. 금액 출처를 「원장 항목」으로 일반화할 때 이번 결정이 상속됨
- 인플루언서 노출 잠금 해제(정산 공개) — 미정. 이번 작업은 **잠금 상태에서 완료**하는 것을 전제
- `settlements.paypal_email` 이 민감정보 가림막을 거치지 않는 직접 칸이라는 기존 유의사항 — 이번 작업으로 바뀌지 않음

## 2. 의심·경우의 수 (기획 규칙 B — 반대론자 모드)

### 2-1. 깨질 수 있는 경우의 수 (개정 후 유효한 것)

**① [데이터] 제품 가격이 비어 있는 캠페인이 앞으로 생기면 조용히 누락된다**
현재 리뷰어형 57개 전부 가격이 있지만, 캠페인 등록 폼에서 가격은 필수 입력이 아니다. 앞으로 가격 없이 등록된 리뷰어형이 생기면 그 응모는 **인증에 성공해도 정산이 만들어지지 않고 아무도 모른다**(지금 리뷰어형 1,065건이 통째로 빠져 있었던 것과 똑같은 사고). → 「인증은 끝났는데 금액을 못 정한 건」을 **화면에 드러내는 장치**가 필요하다.

**② [사용자 경험·필수] 과거 미등록 화면이 39건에서 수백 건으로 불어난다**
이 화면에는 **필터가 하나도 없고**, 전체 선택 체크박스가 있으며, 그 옆이 되돌릴 수 없는 「송금완료 기록」 버튼이다. **전체 선택 후 오조작 = 수백 건 일괄 송금완료**가 실제로 가능하다. 리뷰어형을 켜기 **전에** 안전장치를 넣어야 한다.

**③ [운영] 이미 오프라인으로 송금을 끝낸 건과 겹친다**
리뷰어형은 지금까지 시스템 밖에서 수동 송금해 왔다. 과거분을 「정산대기」로 올리면 **이미 보낸 돈을 또 보낼** 위험이 있다. 과거분은 원칙적으로 「송금완료 기록」으로 넣어야 하며, 어디까지가 지급 완료인지 확인이 필요하다.

**④ [기술·운영] 개발서버에는 리뷰어형 인증 성공 데이터가 거의 없다**
대량 건수 위험은 **운영 데이터에서만 재현**된다. 개발서버 검증만으로 통과시키면 운영에서 처음 터진다(2026-07-21 검수대기 배지 사고와 동일 패턴). → 운영 적용 시 **화면을 열기 전에 조회 함수로 건수·합계를 먼저 확인**한다.

**⑤ [사용자 경험] 관리자가 금액 근거를 확인할 수단**
제품 가격 기준이면 금액이 캠페인 단위로 고정이라 검증이 쉽다. 다만 목록에 **어느 기준으로 나온 금액인지**(제품 가격 / 현금 리워드) 표시가 없으면, 두 기준이 섞인 목록에서 관리자가 혼동한다. 작은 구분 배지 하나로 해결된다.

**⑥ [법률·약관] 「보수」와 「구매대금 환급」은 성격이 다르다**
약관 제13조(리워드 지급)는 「報酬(보수)」 기준으로 쓰여 있고, **구매대금을 돌려주는 페이백 유형은 조문에 명시가 없다.** 실비 환급인지 보수인지는 일본 세무상 취급이 달라질 수 있다(「원천징수 없음·전액 지급」이라는 결론이 같더라도 근거가 다름). **세무사·변호사 확인이 필요한 영역이며 여기서 단정하지 않는다.**

### 2-2. 사용자 의도와 다르게 해석될 수 있는 부분

1. ~~**가구매형(`proxy_purchase = true`)**~~ — **해소됨(2026-07-23)**: 인플루언서가 자기 돈으로 사는 방식이 맞으므로 리뷰어형과 동일하게 제품 가격 지급. 이중 지급 우려 없음.
2. ~~**「과거분」의 범위**~~ — **해소됨(2026-07-23)**: 이미 지급을 끝낸 건은 「송금완료 기록」, 미지급분만 「정산대기」. 단 **구분 기준이 시스템에 없어** 관리자가 캠페인 단위로 판단해야 하며, 그 수단이 §3-3 (다) 화면 보강이다.
3. **현금 보수 병행 시** — 리뷰어형에 현금 리워드가 함께 붙으면 합산할지. 실측 0건이라 당장 사례는 없지만 화면 구조상 가능하다. (§6 Q1 — 미결)

### 2-3. 현재 구현과 어긋나는 지점

- §1-5의 1·4·5번이 그대로 충돌점. **후보 조건의 `c.reward > 0`**, **과거 수동 등록 함수의 금액 출처**, **헬퍼 재생성 방식**은 코드를 고치지 않으면 요구를 만족할 수 없다.
- 인증 성공 판정·자동 보류·반려 가드·정산 삭제 차단·권한 체계와는 **충돌 없음 — 확인 완료.**
- **지금이 규칙을 바꾸기 가장 싼 시점**: 운영 정산행이 사실상 없고, 인플루언서 노출도 잠겨 있어 되돌릴 부담이 거의 없다.

### 2-4. 권고

리뷰어형 금액 출처를 **캠페인 제품 가격**으로 잡는다. 화면 약속과 일치하고, 캠페인 단위로 금액이 고정돼 검증이 쉬우며, 실측상 누락이 0건이다. 다만 ①가격이 없어 금액을 못 정하는 건을 화면에 드러내고 ②과거 미등록 화면에 필터·선택 요약·확인 모달 요약을 붙여 대량 오조작을 막는 두 가지는 **리뷰어형을 켜기 전에** 반드시 함께 넣는다.

### 2-5. 1차 초안 대비 소멸한 위험 (기록용)

영수증 실결제액 기준을 버리면서 아래 위험이 사라졌다. 향후 금액 출처를 다시 논의할 때 참고:

- 영수증 금액이 빈 1건 때문에 **자동 등록 전체가 실패**하던 치명적 사고
- 소수점·통화 단위 오류 (실측 소수점 0건이었으나 구조적 위험은 있었음)
- 영수증 금액을 나중에 수정했을 때 정산액을 따라 바꿀지 (「스냅샷 고정 vs 최신 반영」 딜레마)
- 화면 약속(표시가)과 실지급액(실결제액)이 달라 **304명이 약속보다 적게 받는** 문의 사태
- 관리자가 송금 전 영수증 사진을 일일이 대조해야 하는 부담

## 3. 설계

### 3-1. 금액 산정 규칙 (핵심)

| 모집 형식 | 정산 금액 | 금액 구분값(`amount_source`) |
|---|---|---|
| 리뷰어형(monitor) | **캠페인 제품 가격 `product_price`** (+ 현금 리워드가 있으면 합산 — §6 Q1) | `product_price` 또는 `product_plus_reward` |
| 가구매형(monitor + `proxy_purchase = true`) | **리뷰어형과 동일**(제품 가격) — 사용자 확인 완료 2026-07-23 | `product_price` |
| 시딩형(gifting) · 방문형(visit) | **캠페인 현금 리워드 `reward`**(현행 그대로) | `reward` |

→ 가구매 여부(`proxy_purchase`)는 **인증 성공 판정에서만** 갈리고(영수증만 vs 영수증＋채널별 인증샷), **금액 계산에서는 갈리지 않는다.** 계산식이 `recruit_type` 하나로만 분기하므로 구현이 단순해진다.

세부 규칙:

- **금액 확정 시점** = 정산행을 만드는 시점의 캠페인 값을 **스냅샷으로 고정**(기존 217 원칙 유지). 이후 캠페인 가격을 고쳐도 기존 정산행은 불변.
- **영수증은 금액 근거가 아니다.** 다만 인증 성공 판정에는 계속 필수이므로, 영수증이 승인되지 않은 응모는 애초에 대상이 아니다.
- **「금액 미확정」으로 자동 등록에서 제외하는 조건**: 형식별 금액 출처 값이 없거나 0 이하일 때. 이 건들은 저장하지 않고 관리자 화면의 **「금액 확인 필요」 목록**에 사유와 함께 표시한다(현재 실측 0건이지만 방어 유지 — §2-1 ①).
- **시딩·방문형의 리워드 0원 캠페인**은 지금처럼 대상이 아니다(제품 제공만 있는 캠페인 — 약관 제13조 3항과 일치).

### 3-2. 데이터베이스 변경 (마이그레이션 **2개**, 순서 고정)

> 규칙에 따라 번호는 적지 않는다. 개발 세션이 파일을 만드는 시점에 확정하고 「구현 결과」에 사후 기록한다.

**마이그레이션 ① — 정산 표에 금액 구분 칸 추가 (먼저)**

- `settlements` 에 칸 2개 추가(비어 있어도 됨 — 기존 행 영향 없음)
  - `amount_source text` — 금액 구분(`reward` / `product_price` / `product_plus_reward`). 허용값 제한 걸기
  - `reward_part_jpy bigint` — 합산했을 때 그중 현금 보수 부분(§6 Q1에서 합산을 채택하는 경우에만 의미)
- 기존 행(있다면)은 `amount_source = 'reward'` 로 채움
- 표 주석의 "생성 시점 `campaigns.reward` 스냅샷" 문구를 새 규칙으로 교체
- 행 접근 정책(RLS)·권한 변경 **없음**

**마이그레이션 ② — 판정·금액 계산 헬퍼와 3개 함수 동시 재정의 (나중, 한 트랜잭션)**

- 공용 헬퍼 `_settlement_cert_candidates()` 를 **삭제 후 재생성**(반환 항목이 늘어나므로 교체만으로는 불가). 같은 파일·같은 트랜잭션 안에서 아래 3개 함수도 함께 재생성한다.
  - 후보 조건에서 **`c.reward > 0` 제거** → 형식별 금액 계산 결과로 판단
  - 추가 반환 항목: `amount_jpy`(계산된 금액) · `amount_source` · `reward_part_jpy` · `amount_issue`(금액 미확정 사유: 없음 / 금액없음 / 0이하)
  - **인증 성공 판정 로직은 한 글자도 바꾸지 않는다**(단일 소스 유지)
- `backfill_settlements()`(자동 등록) 재정의 — 금액을 헬퍼 값으로 저장, **`amount_issue` 가 있는 건은 저장하지 않음**, 정산 도입일 컷오프·알림 잠금·이력 기록은 **현행 그대로**
- `get_past_unregistered_settlements()`(과거 미등록 조회) 재정의 — 금액·금액 구분·금액 미확정 사유·캠페인 번호를 함께 반환
- `register_past_settlements()`(과거 수동 등록) 재정의 — 금액을 헬퍼 값으로 저장, **금액 미확정 건은 서버가 조용히 건너뜀**, **알림 없음 원칙 유지**

**변경하지 않는 것:** 인증 성공 판정, 정산 도입일 설정, 송금완료·보류·취소·보류해제 처리, 인플루언서 노출 잠금, 권한 체계, 자동 보류·반려 차단·삭제 차단 트리거.

### 3-3. 관리자 화면 변경 (`dev/js/admin-settlements.js`, `dev/lib/storage.js`)

**(가) 정산 목록** — 금액 아래에 작은 **구분 배지**(「제품 가격」 / 「현금 리워드」 / 「제품＋보수」). 두 기준이 섞인 목록에서 혼동 방지.

**(나) 「금액 확인 필요」 안내** — 정산 목록 상단에 「인증은 끝났지만 금액을 정할 수 없어 정산을 만들지 못한 건 N건」 배너 + 클릭 시 해당 목록. 각 행에서 캠페인 편집으로 바로 이동해 가격을 채울 수 있게 한다. **0건이면 배너 자체를 숨긴다.**

**(다) 「과거 미등록」 화면 보강** (수백 건 대비 — 오조작 방지가 목적, **리뷰어형을 켜기 전 필수**)

> 과거분 처리 방침(사용자 확인 2026-07-23): **이미 송금한 건은 「송금완료 기록」, 아직 안 보낸 건만 「정산대기 추가」.** 이중 지급 방지가 목적.
> ⚠️ **어느 건이 이미 송금됐는지는 시스템에 기록이 없다**(지금까지 시스템 밖 수동 송금). 따라서 **관리자가 캠페인 단위로 보면서 직접 판단**할 수 있게 화면을 만들어야 한다 — 이 화면 보강이 곧 과거분 처리 수단이다.

- **캠페인 검색형 다중 필터 추가**(결과물·정산 목록과 같은 방식) + 모집 형식 필터 → **캠페인 하나씩 띄워 놓고 처리**하는 흐름을 기본으로
- 기본 정렬을 **캠페인별 묶음**으로 두어 한 캠페인의 건들이 흩어지지 않게
- 「전체 선택」은 **현재 필터에 걸린 건만** 선택되도록 명시하고, 선택 건수·합계 금액을 버튼 옆에 크게 표시
- 금액 미확정 행은 **체크박스 비활성 + 사유 배지**
- 「송금완료 기록」 확인 모달에 **캠페인별 건수·합계 요약** 추가(예: "3개 캠페인 · 214건 · 합계 ¥812,300") — 되돌릴 수 없는 동작이므로 무엇을 확정하는지 눈으로 확인
- (검토) 처리한 캠페인을 관리자가 알아볼 수 있도록 **캠페인별 남은 건수**를 필터 목록에 함께 표시

**(라) 엑셀** — 금액구분 열 추가

### 3-4. 인플루언서 화면 (`dev/js/mypage.js` + `dev/lib/i18n/{ja,ko}.js`)

> 지금은 잠금 상태라 실제로 보이지 않는다. **공개 전에** 검토할 항목으로 남긴다.

- 정산액이 화면 약속(`product_price` 기준 페이백)과 **일치**하므로, 1차 초안이 걱정한 「약속과 다른 금액」 문의 위험은 없다. 따라서 문구 변경은 **필수가 아니라 선택**이다.
- 선택 사항: 항목마다 금액 종류를 한 줄로 구분 표시(「商品代金のお戻し」 / 「謝礼」). 초등학생 눈높이·짧은 말 규칙 적용, 일본어·한국어 같은 뜻·같은 줄 수.
- 모바일 목록이 2줄로 늘어나면 줄바꿈·말줄임 확인 필요.

### 3-5. 약관·세무 (단정하지 않음 — 확인 항목으로만)

- 약관 제13조는 「報酬(보수)」 지급 기준으로 작성돼 있고 **구매대금 환급(페이백) 유형이 명시돼 있지 않다.** 캠페인 상세에 「円ペイバック」로 안내하고 있어 개별 캠페인 조건으로는 성립하나, 약관 본문에 유형을 한 줄 추가하는 것이 안전한지 **변호사 확인 필요**.
- 일본 세무상 **실비 환급과 보수는 취급이 다를 수 있다.** 「원천징수 없음·전액 지급」이라는 현재 운영 결론이 페이백에도 그대로 적용되는지 **세무사 확인 필요**.
- 개인정보 관점 변경 없음(영수증·정산 정보는 기존 수집·이용 범위 안).
- 약관을 고치게 되면 공고·시행일 규칙(`.claude/rules/release-timing.md`)을 따른다. **코드 배포와 약관 시행은 분리 가능** — 지금은 인플루언서에게 정산이 안 보이므로 집행 자체가 없다.

### 5-2. 개발서버 시나리오

- 리뷰어형 인증 성공 1건 만들기 → 정산 화면 진입 → 금액이 **캠페인 제품 가격과 일치**하는지, 구분 배지가 「제품 가격」인지
- 캠페인 제품 가격을 0으로 바꾸고 다시 진입 → **오류 없이** 「금액 확인 필요」로만 잡히는지 (회귀 테스트)
- 시딩형 1건 → 금액이 캠페인 현금 리워드 그대로인지(**기존 동작 회귀 없음**)
- 과거 미등록 화면 → 필터·선택 합계·금액 미확정 행 잠금·확인 모달 요약
- 송금완료 처리 → 이력에 금액·구분이 남는지, 인플루언서 알림이 **잠금 상태에서 안 나가는지**
- 권한: campaign_manager 계정으로 정산 화면·조회 함수 접근이 **여전히 차단**되는지
- 결과물 검수 화면·인증 성공 집계·운영현황 진행바에 **영향이 없는지**(판정 미변경 확인)

### 5-3. 운영 적용 시

- 마이그레이션 적용 → **정산 화면을 열기 전에** 조회 함수로 예상 건수·합계·금액 미확정 건수 먼저 확인
- 자동 등록은 정산 도입일 설정에 걸려 있으므로 **의도치 않은 대량 생성이 없는지** 먼저 확인
- 인플루언서 노출 잠금이 **꺼진 상태 그대로**인지 재확인
- 과거분 처리는 **캠페인 단위로 나눠** 진행 — 이미 송금한 건은 「송금완료 기록」, 안 보낸 건만 「정산대기 추가」
