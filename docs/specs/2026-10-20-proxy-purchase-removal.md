# 가구매 철거 — 갈래 걷기 (칸은 남김)

**작성일:** 2026-10-20 (기획 세션)
**상태:** 📝 기획 — 개발 착수 전
**요청:** 사용자 「가구매는 우리 플랫폼에서 사용하지 않는데 왜 계속 가구매가 언급되는거야? 가구매 삭제해줘」(개발 세션 reverb-jp-6f 에서) → 「기획 세션에 전체 철거 넘기기」 → 이 세션에서 범위 결정(아래 「확정된 결정」)
**이어받는 미결:** `2026-10-15-client-figma-reviewer-apply-screens.md` §5 ⑫ 「가구매를 완전히 접을지(복제 차단·분기 철거는 별도 결정)」 — **이 문서가 「접는다」로 닫는다**

> 「가구매」 = 리뷰어형(`recruit_type='monitor'`) 캠페인에 `campaigns.proxy_purchase=true` 를 붙여 **영수증만** 받는 변형(마이그레이션 197, 2026-06-23). 오리엔시트 카드 형식 `form_type='proxy_purchase'`(194)에서 발행된다.
> ⚠️ 관리자 「대리 등록」(`admin_create_deliverable_proxy`·`adminProxy*`·`isProxyWindowOpen`)과 탈퇴 「대행」(`proxy_request`·`proxy_notice`)은 **이름만 겹치고 가구매와 무관**하다 — 이 작업의 대상이 아니다.

### 단계 B — 데이터베이스 함수 (마이그레이션 1개 — 다섯 함수 재정의)
- 다섯 함수(표)의 가구매 갈래를 걷어 **현재 원본을 베이스로 `CREATE OR REPLACE`**. 인자·반환 칸은 그대로

### 단계 순서
🔴 **A 를 먼저, B 는 그 뒤**(필수). 어느 순서든 프로그램이 멈추는 실행 오류는 없다(칸이 남는다 · 결과 공유 응답의 키는 의심 8). 그러나 **B 를 먼저 내보내면 길 셋이 열린 동안 판정이 갈린다** — 새로 생긴 가구매 캠페인을 화면은 「영수증만으로 성공」, 서버 정산 후보·인증 성공 숫자는 「인증샷 필요」로 본다(의심 1 의 상황). 또 서버가 가구매 카드 연결을 거부하는데 화면에는 연결 단추가 남아, 누르면 사용자에게 오류 안내가 뜬다. 대상이 0건이면 무해하지만 순서로 막는다.

## 착수 전 확인 (개발 세션 — 운영 데이터베이스, 읽기 전용)

🔴 ①이 0건이 아니면 **착수하지 않고 기획으로 돌린다**(의심 1).

1. `SELECT count(*) FROM campaigns WHERE proxy_purchase;` — **보관 삭제분 포함**(보관 삭제 표시 칸 조건을 걸지 말 것)
2. 옛 양식으로 아직 열리는 시트와 그 안의 가구매 카드 — `orient_sheets` 중 `data->'issued'` 가 없고 작성 기한이 남은 것, 그 `data->'cards'` 안 `form_type='proxy_purchase'`(제출 전·제출 후 나눠서)
3. `campaign_change_history WHERE field_name='proxy_purchase'` 줄 수(이름표를 남기는 근거 확인 — 0이어도 남긴다)
4. 다섯 함수의 현재 원본이 표의 번호와 같은지(파일 목록 → `CREATE` 인지 가르기 — 규칙 D)
5. 다섯 함수의 실행 권한(`p.proacl`)을 개발·운영 각각 조회해 **적어 둔다**(첫 조회 — A 와 B 사이에 바뀌었는지 볼 때만 쓴다)

⚠️ **①은 단계 A 운영 반영 직전과 단계 B 착수 직전에 다시 센다** — 그사이 열린 길로 가구매 캠페인이 생겼을 수 있다. 0건이 아니면 의심 1 대처대로 멈추고 기획으로 돌린다.

⚠️ **4·5 는 단계 B 착수 직전에 한 번 더** 한다 — A 와 B 사이에 다른 작업이 다섯 함수 중 하나를 다시 정의했을 수 있다(그러면 베이스 번호도, 대조할 권한도 바뀐다). 의심 7 의 「착수 때」도 단계 B 착수 때다. 단계 B 의 대조 기준은 **그 다시 조회한 기록**이다
