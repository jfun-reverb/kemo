## A. 결정이 끝나 바로 구현 가능 — **개발 세션**

| 조각 | 하는 일 | 파일 |
|---|---|---|
| 검수 구매일 경고 이름 (지도 1-3) | 경고 문구가 `campaignPeriodRowKind` 를 쓰게 한다. 지금은 두 기간이 다른 캠페인에도 무조건 「모집/구매 기간」이라 부른다. 부를 이름은 **「구매 기간」으로 확정**(지도 Q5) | `dev/js/admin-deliverables.js` |
| 활동관리 제출 마감 이름 (지도 2-3) | 형식 무관 「提出期限」(제출 기한) 하나를 `campaignSubmissionLabelCode` 로 분기. 상세에서 본 이름과 **실제 내는 화면의 이름**을 맞춘다 | `dev/js/application.js` |
| 캠페인 목록에 선정 기간 열 (선정 기간 사양서 조각 1) | 「구매기간」과 「결과물 제출 마감」 사이. ⚠️ 열이 늘어 가로가 넓어지므로 **실제 화면에서 폭 확인** | `dev/admin/index.html` · `dev/js/admin.js` |
| 진행현황 카드에 선정 기간 줄 (조각 2) | 시딩형·값 있을 때만. 「모집」 다음 | `dev/js/admin-applications.js` |
| 엑셀 선정 기간 열 (지도 3-2) | 「캠페인 정보」 시트 | `dev/js/admin-excel.js` |
| 삭제된 캠페인 상세에 선정 기간 줄 (지도 3-3) | 읽기전용 상세 | `dev/js/admin.js` |
| 관리자 도움말 표 (지도 3-4) | 선정 기간 행 추가 + 구매 기간 설명 수정 — 지금은 「고칠 수 있음」이라 적혀 있으나 리뷰어형에서는 그 칸이 숨겨져 있다 | 관리자 도움말 표 |

**공통 조건 (지도 「공통 규칙」)** — 손대는 자리는 **자체 판정을 지우고 헬퍼(`campaignPeriodRowKind`·`campaignSubmissionLabelCode`)를 경유**한다. 이 사양서들의 근본 원인이 「같은 판정을 각자 구현한 것」이다.

⚠️ **관리자 빌드에는 번역 파일이 없다** — 같은 문구를 `admin.js` 가 따로 들고 있어 **두 벌을 항상 같이** 고친다. 어긋나면 관리자 미리보기와 인플루언서 화면이 다른 이름을 쓴다.

⚠️ 데이터베이스 변경 **없음**. 조각끼리 의존 없음 — 나눠 해도 된다.

## B. 결정이 남아 기획을 먼저 거쳐야 함 — **기획 세션**

| 조각 | 남은 결정 | 왜 기획인가 |
|---|---|---|
| 페이백 안내 세 번째 갈래 (지도 1-2, Q2) | 구매 기간이 빈 리뷰어형(운영 10건)에 **문구를 바꿀지 / 안 띄울지** | 인플루언서가 보는 안내문이라 문구 확정이 먼저. 결정 없이 코드를 고칠 수 없다 |
| 관리자 화면 4곳의 날짜 중복 (지도 3-1, Q4) | 두 기간이 같을 때 **①구매 값을 비운다 ②「모집 기간과 같음」으로 적는다 ③그대로 둔다** | 네 자리(목록 셀·진행현황 카드·브랜드 운영현황·엑셀)가 **같은 규칙**을 써야 해 표시 규칙을 먼저 정해야 한다. ⚠️ 열 제목은 못 바꾼다(세 형식이 섞여 나오는 자리) — **값 쪽에서만** 정한다 |
| 오리엔시트 발행 시 선정 기간 자동 입력 (선정 기간 사양서 조각 3, Q3) | **브랜드가 오리엔시트에 직접 넣게 할지 / 관리자만 넣을지** | 「브랜드가 넣는다」를 고르면 **브랜드 입력 폼에 항목 추가 + 오리엔시트 상세 카드 표시 + 발행 자동 입력** 셋으로 늘고, 배포 대상이 다른 프로젝트(`reverb-sales`)까지 걸친다 → 화면 구조 변경이라 기획 트리거 |

⚠️ **결정은 사용자의 것**이다. 기획 세션은 각 선택지의 깨질 가능성·현재 구현 충돌점을 정리해 선택형 질문으로 올린다. 일본어 문구 후보는 **한국어 뜻을 반드시 병기**한다(`.claude/rules/interaction.md`).
