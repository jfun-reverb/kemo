| 회원 | 대화 id + 토큰 | 대화 id 우선(토큰 무시) |
| 운영팀 | 대화 id | 지금 그대로(닫힌 대화면 `thread_closed`) |
| 운영팀 | 대화 id 없음 | 열린 대화가 **정확히 하나**면 거기 · 0개면 `no_open_thread` · 둘 이상이면 `thread_required`(옛 관리자 화면이 남은 몇 분만 생긴다 — 새 관리자 화면은 항상 대화 id) |

- 상한 5 는 **서버의 상한 보조 함수 하나**(발신 함수와 뷰가 함께 부른다). 화면은 숫자를 갖지 않는다(사본 금지) — 「버튼 회색」은 뷰의 `influencer_at_open_limit`(참/거짓)으로 판단하고, 막는 것은 서버 거부(`too_many_open_threads`)다. 화면 판단은 편의

**제목 번역(R2-6)**
- `translate-message` 가 웹훅 페이로드의 `table` 로 갈린다 — `application_messages`(지금) / `general_inquiry_threads`(신설: 제목을 한국어로, `title_translated`·`title_translate_status` 에 저장)
- 웹훅은 대화 표의 **삽입과 고쳐 쓰기** 둘 다 받는다(운영팀 제목 고치기). 🔴 고쳐 쓰기는 닫기·다시 열기마다 오므로 **`old_record.title` 과 `record.title` 이 같으면 번역 API 를 부르지 않고 끝낸다**(비용)
- 운영팀이 제목을 **다른 값으로 고치면** 제목 고치기 함수가 번역 칸을 비우고 상태를 `pending` 으로 되돌리고, 웹훅을 받은 `translate-message` 가 다시 번역한다(옛 번역이 새 제목 옆에 남지 않게)
- 제목이 **비어 있으면**(운영팀이 비움 · 옛 호환 갈래가 만든 제목 없는 대화) `translate-message` 는 번역 API 를 부르지 않고 끝낸다 — 번역 칸·상태는 비어 있는 그대로(운영팀이 비운 경우는 제목 고치기 함수가 이미 비웠고, 옛 호환 갈래의 대화는 처음부터 비어 있다)
- `translate-message` 는 번역 결과를 저장하기 **직전에 제목이 그대로인지 다시 본다** — 번역 도중 운영팀이 제목을 바꾸거나 비웠으면 저장하지 않는다(옛 번역이 되살아나지 않게)
- 🔴 **대시보드 웹훅은 개발·운영 각각 손으로 만든다**(`.claude/rules/git.md` 「외부 시스템 설정 양 서버 동기화」) — 개발서버는 조각 1-C, 운영은 조각 6 체크리스트
- ⚠️ 운영팀이 제목을 **한국어로 고치면 회원 화면에도 한국어로 보인다** — 실무자 가이드에 「제목 고치기는 개인정보 지우기용, 쓸 때는 일본어」로 적는다

- **새 문의 화면 `#inquiry-general`**: 맨 위 **제목 입력란**(이름표 「件名」 — 제목, 안내 「例：ポイントの使い方」 — 예: 포인트 사용 방법, 최대 40자, 글자 16px 이상) → 자주 묻는 질문 안내 → 본문 입력란. 제목이 비면 보내기 때 입력란 아래 「件名を入力してください」(제목을 입력해 주세요). 열린 대화가 1개 이상이면 제목 위에 「開いているお問い合わせがN件あります。同じ内容なら、そちらに続けて書いてください」(열려 있는 문의가 N건 있습니다 — N = 열린 대화 수. 같은 내용이면 거기에 이어서 써 주세요) + 목록으로 가는 링크(같은 질문 중복 방지). 화면에 들어올 때 **토큰을 하나 만들어** 보낼 때마다 같은 것을 쓰고 떠나면 버린다(예외 하나 — `thread_closed` 를 받으면 새로 만든다, 아래 거부 안내). 첫 글이 가면 제목 입력란이 사라지고 머리글에 제목(주소 이동은 조각 3 그대로)

### 관리자 화면 (조각 4 — 이 개정을 반영해 처음부터)

- 목록 한 줄 = 대화 하나: **제목**(한국어 번역 우선 + 원문 작게 · 없으면 「(제목 없음)」 + 첫 글 미리보기) · 회원 이름 · 상태 칩(「미응대」/「회원 답 대기」/「닫힘」) · 마지막 글 시각 · 마지막 글 미리보기(번역 우선) · 「이 회원 대화 N · 열림 M」(누르면 그 회원 대화 전부 — 닫힌 것 포함)
- 대화 화면 머리: 제목(번역 + 원문) · 「제목 수정」 버튼(R2-3 — 비우기 포함) · **같은 회원의 다른 열린 문의 줄**(「이 회원의 다른 열린 문의 2건: [제목] [제목]」 — **열린 대화만**, 「열림 M」과 같은 범위. 같은 질문에 두 번 답하지 않게. 다른 대화의 제목은 대화 뷰를 그 회원 id 로 다시 조회해 가져온다 — 「이 회원 대화 N」을 누를 때와 같은 조회)
- 답장은 **항상 대화 id** 를 넘긴다. 「다시 열기」는 다른 열린 대화가 있어도 된다(`open_thread_exists` 안내 삭제)
- 미응대 수 세 자리(R-4)는 「`needs_reply` 대화 수」 그대로 — 사이드바 숫자는 **사람 수가 아니라 대화 수**임을 실무자 가이드(Notion)에 적는다

### 개정 검증

1. 회원이 「새 문의」 제목+첫 글 → 새 대화(제목 저장), 기존 열린 대화는 그대로 열림
2. 제목 빈 값 → `title_required` · 41자 → `title_too_long` · 열린 대화 5개에서 새 문의 → `too_many_open_threads`(화면 버튼 회색 + 서버 거부 둘 다)
3. 같은 토큰으로 두 번 → 대화 하나 · 다른 토큰 동시 두 번(상한 4개에서) → 하나만 성공(잠금)
4. 닫힌 지 23시간 대화를 열어 씀 → 그 대화 다시 열림 · 25시간 → `thread_closed`, 쓴 글 남음 · 열린 대화가 5개인데 23시간 대화에 씀 → `too_many_open_threads`(R2-2)
5. 옛 화면 호환(대화 id·토큰 없음) — 옛 규칙대로 한 대화로
6. 회원이 남의 대화 id 를 넣어 발신·조회·읽음 → `thread_not_found`(발신만 개정 전 「무시되고 본인 대화로」에서 바뀜 — 조회·읽음은 원래 거부) · 운영팀 — 대화 id 없이 발신, 열린 대화 둘 이상인 회원 → `thread_required` · 다른 열린 대화가 있어도 다시 열기 성공 · 제목 고치기·비우기(번역 칸도 비움)
7. 제목 번역 — 새 문의 뒤 관리자 목록에 한국어 제목 · 닫기·다시 열기로는 번역 API 를 안 부름(함수 기록) · 웹훅 없거나 실패면 원문만
8. 관리자 목록 「이 회원 대화 N · 열림 M」· 「다른 열린 문의」 줄 · 미응대 수 = needs_reply 대화 수(세 자리 일치)

| 8 | 배포 | 데이터베이스가 먼저 나가고 화면이 옛 판인 구간(배포 순서상 몇 분) | 데이터베이스 안에는 틈이 없다 — **옮기기·함수·검사 제약이 마이그레이션 2 한 파일**이다. 데이터베이스와 화면 사이 몇 분은 **완전히 견디지 않는다**: 새 함수의 대화 인자는 기본값 비움이라 조회·읽음(회원 전체)·회원 발신(서버가 대화를 정함)은 옛 화면에서도 돌고, 운영팀 발신은 그 회원의 열린 대화로 간다(없으면 거부). 🔴 **옛 관리자 화면에서 그 몇 분 동안 틀어지는 것 둘** — ①안 읽은 수가 대화별로 바뀌어 **안 읽음 표시가 빠진다** ②옛 화면은 응대 완료 표(477)로 미응대를 세는데 새 발신 함수가 그 표를 더는 안 건드려 **미응대 수가 틀어진다**(허용 — 화면 숫자만 틀릴 뿐 데이터는 맞고, 새 화면이 나가면 바로 맞는다). 옛 회원 배지 조회는 **옛 뷰를 남겨 두어** 그대로 돈다. 그래서 운영 반영은 **회원이 적은 시간대**에 데이터베이스 → 코드를 바로 이어서 한다 |
| 9 | 화면 | 지난 문의가 수십 개가 되면 목록이 길다 | 최근 20개 + 「もっと見る」(더 보기). 대화마다 날짜·첫 줄·**안 읽은 답장 배지**(회원 화면 절) |
| 10 | 법률 | 새 개인정보 수집? | 없다 — 같은 메시지를 묶는 방식만 바뀐다. 방침 문구(「문의 내용」) 그대로. `/약관확인` 불필요 판단(사용자 확인 Q-4) |

### 사용자 의도와 다르게 읽힐 수 있는 곳
- 「대화 목록」 = **회원 화면**의 지난 문의 목록을 말한 것으로 읽었다. 관리자 화면은 지금도 회원별 목록이 있고, 이번에 **대화별 줄**로 바뀐다.
- 「응대 완료」라는 버튼 이름은 그대로 두되 뜻이 「대화 닫기」가 된다 — 이름을 바꿀지는 Q-2.

## 설계

### 데이터 (마이그레이션 3개 — 번호는 개발 세션이 정한다. 「마이그레이션 1 → 2 → 3」 순서) — 🔄 개정 R2 우선(맨 위 「설계 개정」 절)

**마이그레이션 1 — 대화 표 + 메시지 칸**
- 새 표 `general_inquiry_threads` — `id` · `influencer_id`(회원 삭제 시 함께 삭제) · `status`(`open`·`closed`) · `opened_at` · `closed_at`·`closed_by`·`closed_by_name` · `reopened_count`(다시 열린 횟수 — 🔴 **닫은 시각·닫은 사람의 이력은 남기지 않고 마지막 한 번만** 둔다. 운영 판단에 필요한 것은 지금 열렸나·닫혔나뿐이고, 이력이 필요해지면 그때 이력 표를 더한다). 🔴 **「마지막 글 시각·마지막 발신 종류」 칸은 두지 않는다** — 뷰가 메시지에서 계산한다(같은 사실을 두 곳에 두면 한쪽이 어긋난다)
- **부분 유일 색인** `(influencer_id) WHERE status='open'` — P-2 를 서버가 강제
- `application_messages.general_thread_id`(대화 표 참조, 비어 있을 수 있음) + 색인 `(general_thread_id, created_at)`
- 475 의 「응모·회원 중 정확히 하나」 제약은 그대로
- 정책: 회원 본인 조회(숨김 가드 불필요 — 대화 표엔 본문이 없다) · 관리자 조회 `(SELECT public.is_admin())` · **쓰기 정책 없음**(함수만)

**마이그레이션 2 — 옮기기 + 함수 + 검사 제약(한 파일·한 묶음)** — 🔴 **하나로 묶는 이유**: 옮기기와 새 발신 함수 사이에 틈이 있으면 그 사이 옛 발신 함수가 대화 칸 없이 행을 넣어, 다시 채우는 규칙과 그 검증이 따로 필요해진다. 한 파일이면 틈이 없다.
1. **옮기기** — 경우의 수 #5 규칙대로 회원마다 대화 하나를 만들고 메시지에 대화 id 를 채운다. 실행 전·후 건수를 남긴다(일반 문의 메시지 수 = 대화 칸이 채워진 수)
2. **함수** — 478 다섯 중 **넷을 다시 만들고**(조회·발신·읽음 = 인자 추가 / 관리자 안 읽은 수 = 반환이 대화별), **닫기·다시 열기를 새로** 만든다. 감사용 청소 `purge_audit_data_all`(480 베이스)도 다시 정의한다(아래 항목). 다섯째(옛 응대 완료 `mark_general_inquiry_resolved`)는 **손대지 않는다**(아래 「남겨 두는 것」). ⚠️ **인자나 반환 모양이 바뀌는 넷은 `DROP` 후 `CREATE`**. 🔴 그 넷과 **새로 만드는 둘(닫기·다시 열기)** 모두 실행 권한 회수·부여를 **두 방향 모두** 건다 — 새 함수는 만들어지는 순간 기본 권한을 받는다(`CLAUDE.md` 「함수 실행 권한 — 회수 방향이 둘」). 새 인자는 **전부 기본값 비움**(경우의 수 #8)
3. **검사 제약** — 「일반 문의 행(응모 칸이 빈 행)이면 대화 칸 필수」. 맨 끝에 건다
- 🔴 **호출자 판정(이 사양서의 단일 정의 — 발신·조회·읽음이 모두 이것을 쓴다)** — ①넘긴 `p_influencer_id` 가 **호출자 본인**이면 **회원 갈래**: 조회·읽음은 대화 인자를 주면 그 대화의 주인이 호출자인지 확인(아니면 거부) / **발신은 대화 인자를 확인 없이 무시**하고 서버가 정한다 ②아니고 호출자가 **관리자**면 **운영팀 갈래**: 대화 인자를 주면 **그 대화의 주인이 넘긴 회원 id 와 같은지** 확인(아니면 거부 — 알림·읽음 대상이 엇갈리지 않게) ③둘 다 아니면 **거부**(남의 회원 id). ⓪ 단 **`p_influencer_id` 가 비어 있으면** — 호출자가 관리자가 아니면 **본인으로 보고 ①**, 관리자면 **거부**(대상 회원을 모름 — 지금 478 의 「会員を指定してください」와 같다). 대화 인자가 비어 있어도 같은 판정을 먼저 거친다. 화면은 본인 회원 id 를 넘긴다(`currentUser?.id || null` — 로그인 직후 등에 빈 값이 갈 수 있어 ⓪이 있다. messaging.js 28~29 주석)
- 🔴 **잠금** — 발신·닫기·다시 열기 셋이 **같은 회원 단위 잠금**(`pg_advisory_xact_lock`, 열쇠 = 회원 id)을 먼저 잡는다. 대화 행만 잠그면 「열린 대화 찾기 → 새로 만들기」 사이가 비어 경우의 수 #3·#4 가 뚫린다
- 발신 `send_general_inquiry_message(p_body, p_attachments, p_influencer_id, p_thread_id DEFAULT NULL)`
  - 회원: `p_thread_id` 를 **무시**하고 서버가 정한다 — 회원 단위 잠금 → 열린 대화 있으면 그것 / 없고 가장 최근 닫힌 대화의 `closed_at` 이 24시간 안이면 **다시 열기**(`reopened_count`+1, 닫힘 칸 비움) / 아니면 **새 대화**
  - 운영팀: `p_thread_id` 로 대화를 지정한다(비면 그 회원의 열린 대화, 없으면 거부 — 경우의 수 #8). 지정한 대화가 닫혀 있으면 → Q-1(기본안: 거부하고 「다시 열기」 버튼)
  - 🔴 **응대 완료 표(477)를 더는 건드리지 않는다** — 운영팀 답장의 `auto_replied` 덮어쓰기(P-1)와 회원 글의 「그 줄 지우기」를 **둘 다** 들어낸다. 닫힘 상태는 대화 표가 단일 소스
  - 첨부 경로 검사·발신 제한 계량은 **그대로**(P-3)
  - 반환에 `thread_id` 추가 — 화면이 새로 생긴 대화로 주소를 맞춘다
  - 알림: `ref_id = 대화 id`, 안 읽은 알림 중복 방지도 대화 단위
- 조회 `get_general_inquiry_messages(p_influencer_id, p_thread_id DEFAULT NULL)` · 읽음 `mark_general_inquiry_messages_read(p_influencer_id, p_thread_id DEFAULT NULL)` — 「호출자 판정」을 거친 뒤, 대화를 주면 그 대화만, 비면 회원 전체(옛 동작)
- 닫기 `close_general_inquiry_thread(p_thread_id, p_seen_last_message_id)` — 새 함수. 관리자 전원, 열린 대화만. 화면이 본 마지막 메시지 뒤에 회원 글이 있으면 거부(`new_message_since_view` — 경우의 수 #4). 이 비교도 **숨김·회수된 글을 뺀다**(뷰와 같은 기준 — 회수된 글 때문에 영영 못 닫는 일이 없게). 🔴 화면은 **숨김·회수된 글을 뺀 마지막 메시지 id** 를 넘긴다(관리자 화면엔 숨긴 글도 보이지만 그 글은 기준이 아니다. 그런 글이 없으면 비움). 비어 있으면 보이는 회원 글이 하나라도 있을 때만 거부
- 다시 열기 `reopen_general_inquiry_thread(p_thread_id)` — 관리자(Q-1 기본안일 때). 처리는 회원 글로 다시 열 때와 같다(닫힘 칸 비움 · `reopened_count`+1). 🔴 **그 회원에게 열린 대화가 없을 때만** — 있으면 거부(`open_thread_exists`, 화면 문구 「이 회원에게 열린 대화가 이미 있습니다」). P-2 유일 색인과 같은 규칙을 함수가 먼저 말해 준다
- 관리자 안 읽은 수 `general_inquiry_admin_unread_counts` → **대화별**
- 감사용 청소 `purge_audit_data_all`(현재 원본 **480**) — 대화 표도 직접 지운다(메시지 → 대화 순). 응대 완료 표(477)를 지우는 줄은 **그대로 둔다**(감사용 계정의 옛 줄이 남아 있을 수 있다 — 빼는 절차는 단계 분할 「후속」). 인자가 그대로라 **`CREATE OR REPLACE`** — 기존 실행 권한이 보존되므로 권한을 다시 걸지 않는다
- **남겨 두는 것(이번에 안 지운다)** — 옛 응대 완료 함수 `mark_general_inquiry_resolved`(부르면 477 표에만 쓰고 대화는 안 닫힌다) · 응대 완료 표 `general_inquiry_resolutions`(477) · 옛 뷰 `general_inquiry_message_summary`(481). **새 함수·새 화면은 셋 다 쓰지 않고**(예외: 감사용 청소가 477 의 감사용 계정 줄을 지운다 — 바로 위 항목), 옛 화면이 남은 몇 분 동안만 옛 화면이 쓴다. 다음 배포에서 지운다(이번 3개에 들지 않는다). 🔴 **지우는 절차와 주의점은 단계 분할 「후속」 한 곳에만 적는다** — 그쪽을 보고 쓸 것

**마이그레이션 3 — 뷰** — 새 뷰 `general_inquiry_thread_summary`(`security_invoker`) — 🔴 **대화 표에서 출발해 메시지를 붙인다**(대화 한 줄 = 대화 표 한 행. 회원은 대화 표 본인 조회 정책으로, 관리자는 관리자 조회 정책으로 자기 몫의 행을 본다. 회원 표는 312 때문에 기준으로 못 쓴다 — 상위 사양서 §5-6 ①). 그래서 **글이 숨겨지거나 회수돼도 대화 줄은 사라지지 않는다** — 숨김·회수 때문에 화면이 가리키는 대화와 서버가 글을 보내는 대화가 어긋나지는 않는다(24시간 경계의 어긋남은 회원 화면 절에서 따로 다룬다).

대화 한 줄의 칸: 대화 id·회원 id·상태·열린/닫힌 시각(**대화 표**) · 메시지 수·마지막 글 시각·마지막 발신 종류·**첫 글 미리보기**(회원 목록 줄의 「첫 줄」)·**마지막 글 미리보기**(관리자 목록 줄의 미리보기, 둘 다 앞 몇십 자)·회원 안 읽음(**메시지**) · **`needs_reply`** = 대화 표의 상태가 열림 + 메시지에서 구한 마지막 발신 종류가 회원(P-5) · **그 회원의 대화 수**(이 대화 포함, 닫힌 것 포함 — 관리자 목록의 「이 회원 대화 N」, 거름과 무관하게 회원 단위로 센다).
- 🔴 **메시지에서 구하는 칸은 모두 숨김·회수된 글을 뺀다** — 한 줄의 「마지막 글 시각」·「마지막 글 미리보기」·「마지막 발신 종류」·`needs_reply` 가 같은 글을 가리키게(회원이 마지막 글을 회수하면 그 앞 글이 기준이 된다). 회원 쪽은 476 조회 정책이 그런 글을 어차피 가리므로 관리자와 같은 값이 나온다
- 보이는 글이 0건인 대화(유일한 글을 회수·숨김)는 메시지 칸이 비어 있다 — 화면은 미리보기 자리에 회원 「表示できるメッセージはありません」(표시할 메시지가 없습니다) · 관리자 「표시할 글 없음」, 상태 칩은 P-5 대로(열림이면 「회원 답 대기」)
- 옛 뷰(481)는 위 「남겨 두는 것」
