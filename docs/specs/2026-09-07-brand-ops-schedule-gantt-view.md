# 운영현황 「일정」 뷰 — 캠페인 간트차트
**작성일:** 2026-09-07
**작성:** 기획 세션 · **상태:** 사용자 결정 8건 · 기획 확정 3건 · 확인 대기 0건, 개발 착수 전

> 관리 담당자 피드백 — 「지금 운영현황은 캠페인의 상태(기간·제출 현황)와 일정을 관리하기에 보기 어렵다」. 운영현황 페인에 캠페인을 시간축 위에 놓는 **「일정」 뷰**를 새로 넣고 기본 화면으로 삼는다. 지금의 브랜드 카드는 **「브랜드」 뷰**로 남긴다.

> ⚠️ 이 문서는 파일 경로와 함수·상수 **이름**만 적고 줄 번호는 적지 않는다. 줄 번호는 브랜치마다 다르고 곧 낡는다 — 읽는 쪽이 이름으로 찾는다.

### 이 제안과 충돌 가능성 있는 기존 동작
- **축이 다르다.** 운영현황은 「어느 브랜드가 위험한가」(경고축), 피드백은 「어느 캠페인이 언제 무엇을 해야 하나」(시간축). 카드를 없애면 카드에만 딸린 **경고 단계 배너와 브랜드 상세 진입**이 사라진다(회사 필터·검색·최근 신청은 페인 공통이라 뷰 구성과 무관 — 결정 9·설계 1) → **카드는 남기고 뷰를 더한다**(결정 1).
- **인증 성공 판정 사본이 이미 다섯 곳**(서버 `_settlement_cert_candidates()` 331 · 검수 화면 `computeCertStatus` · 엑셀 · 결과물 검수 메일 · 인플루언서 일일 메일). 서버 집계 함수를 새로 만들면 **여섯 번째 사본**이 된다. 게다가 331 은 264 의 「무보수 시딩·방문형 제외」 조항을 그대로 품고 있어(`c.reward IS NULL OR c.reward <= 0` 인 비리뷰어형 제외) **정산 후보 함수를 그대로 빌리면 무보수 캠페인의 인증 성공이 0 으로 나온다.**
- `campaignPeriodRowKind` 의 7갈래를 안 거치고 날짜 칸을 직접 읽으면 리뷰어형(구매=모집 저장 규칙)에서 같은 구간이 두 번 그려진다.
- 선정 기간 표시 조건이 이 화면에서 **5곳째**가 된다.
- 기존 사양서(`2026-05-13-brand-ops-redesign.md`)의 「모집기간 연장 기능은 이번 작업에서 제외」는 그대로 유지한다(결정 2 — 보기 전용).

### 미해결 백로그·관련 작업
- 캠페인 목록 「결과물 현황」 열(2026-09-03) — 같은 숫자를 다른 자리에 또 그리는 셈. 판정 함수를 공유한다.
- 관리자 목록 서버 페이지네이션은 보류 중(재개 기준 미달) — 이 화면도 전건 조회 + 화면 필터.

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우
1. **UX — 간트는 「언제」는 보이지만 「몇 명」은 안 보인다.** 막대 안에 숫자를 넣으면 짧은 캠페인에서 글자가 잘린다. → 왼쪽 **고정 열**에 숫자, 오른쪽에 막대. 역할을 나눈다.
2. **UX — 막대 없는 빈 줄.** 날짜가 빈 캠페인이나 표시 범위 밖 캠페인이 **아무 표시 없는 줄**로 섞이면 「원래 빈 줄이 있는 화면」으로 학습된다. → 준비(draft)는 두 대상 집합 어디에도 넣지 않는다(결정 4). 날짜가 빈 경우와 범위 밖은 **막대 대신 마커 또는 안내 글자**로 그린다(설계 4·5의 예외). 아무것도 없는 줄은 만들지 않는다.
3. **기술 — 규모.** 종료·노출종료까지 그리면 수백 행. → 기본은 모집예정·모집중·모집마감만, 「종료 포함」 전환(결정 4). ⚠️ 운영 건수 실측은 개발 착수 전에(「착수 전 알아야 할 것」).
4. **기술 — 인증 성공 조회 비용.** 지금 방식(캠페인마다 조회)이면 50행 = 50번. → 결과물을 **대상 집합 단위로 묶어** 받아 화면에서 캠페인별로 나눈다(설계 6). 진행 중 캠페인의 결과물은 수천 건 이내로 본다(실측 필요).
5. **기술 — 시간대.** 날짜 칸은 `연-월-일` 문자열이고 `new Date()` 비교가 금지다. 간트는 날짜→픽셀 변환이 필수. → 기준일도 날짜 칸도 **전부 `연-월-일` 문자열로 만든 뒤** 변환 함수 하나(`ganttDayOffset`)로 정수 일수를 낸다. 날짜의 기준은 설계 4에 못박는다.
6. **데이터 — 감사용 계정.** 승인·제출·인증 셋 다 감사용이 빠져 있어야 미니카드와 같은 수가 나온다. 승인 수는 서버 함수가 이미 빼서 주고, 제출·인증은 화면이 빼야 한다 — 지금 상세 화면은 `_brandOpsAuditIds` 로 뺀다. 한 곳이라도 빠뜨리면 「인증 성공 > 제출」 역전이 재현된다(2026-07 실제 사고).
7. **데이터 — 삭제된 캠페인**(`deleted_at`)이 섞인다. 캠페인 조회는 보관 삭제 제외가 기본이지만 결과물 조회는 캠페인 id 로 걸어야 한다.
8. **권한 — 매니저.** 운영현황은 전원 열람이지만 편집은 캠페인관리자 이상. 편집 버튼을 매니저에게 보이면 「누르고 나서 권한 오류」. → 캠페인 목록과 같은 조건으로 버튼을 가린다. 진행현황 열기는 전원.
9. **동시성 — 다른 세션이 상태를 바꿔도** 이 화면은 캐시. 「새로고침」 버튼과 `PANE_REFRESHERS` 재입힘으로 충분(다른 페인과 같은 수준).
10. **UX — 화면 폭.** 기본 12주 × 하루 폭이면 약 900px. 사이드바 펼침 여부에 따라 넘친다. → 시간축 영역만 가로 스크롤(**항상 보이는 스크롤바**, 리포트 화면 선례 2026-09-04). 왼쪽 열은 고정.

### 1. 페인 구조

```
운영 현황                                    [새로고침]
[ 일정 ] [ 브랜드 ]            ← status-tab-bar (기본 「일정」)
회사 ▾  검색 ______  (일정 뷰) ☐ 종료 포함   ‹ 오늘 ›   (브랜드 뷰) 정렬 ▾   (N / 전체 M)
┌──────────────────── 일정 뷰 ────────────────────┐
│ 왼쪽 고정 열                │ 시간축 (가로 스크롤) │
│ 캠페인 · 브랜드 · 형식·채널 · 상태 · 숫자 3 (편집 열은 후속에서 제거) │ 8월 │ 9월 ... │
└─────────────────────────────────────────────────┘

```
(왼쪽 고정 열의 칸 구성은 설계 3 표가 정본이다.)

- 뷰 전환은 정산 페인 3뷰와 같은 방식 — **켜는 함수마다 나머지를 끄는 짝**을 둔다(`showBrandOpsSchedule()` / `showBrandOpsCards()`). 한쪽만 켜면 두 뷰가 겹쳐 보인다.
- 「최근 신청」 표는 두 뷰 아래에 그대로 둔다(결정 1 「카드 유지」의 연장 — 두 뷰 공통 영역).
- **조회는 두 단계다.** ①`loadBrandOps()` 가 두 뷰 **공통 재료**(브랜드 집계·회사 목록·캠페인 행·승인 수·감사용 id)를 한 번에 받고 현재 뷰를 그린다. ②**결과물 조회는 일정 뷰가 그려질 때** 그 시점의 **대상 집합**(결정 4 — 기본 3상태 또는 종료 포함 5상태) 기준으로 묶어 받는다(설계 6). 회사 필터·검색은 화면에서 거르므로 재조회하지 않고, 「종료 포함」을 켜고 끌 때만 대상 집합이 바뀌어 다시 받는다(집합 열쇠별 캐시). **`loadBrandOps()` 로 다시 들어오면(새로고침 단추·`PANE_REFRESHERS` 재입힘) 결과물 캐시도 비운다** — 안 비우면 제출·인증 숫자만 옛 값으로 남는다. `PANE_REFRESHERS['brand-ops']` 는 그대로 `loadBrandOps` — 뷰 상태를 읽어 다시 그리므로 등록 변경 없음.

### 2. 데이터 — 데이터베이스 변경 0

| 필요한 값 | 출처 | 비고 |
|---|---|---|
| 캠페인 행(제목·캠페인 번호·브랜드·상태·모집형식·채널·`proxy_purchase`·날짜 9종[모집 시작·마감, 구매 2, 방문 2, 선정 2, 제출 마감]·모집인원·`first_active_at`·`event_mode`·`event_selection_mode`) | `fetchCampaigns()` (보관 삭제 제외) | 브랜드명은 `brandLabelAdmin(c)` — 캠페인 목록과 같은 표기 |

| 감사용 계정 | `influencers_admin_view` 에서 `is_audit=true` id 집합 (브랜드 상세와 같은 조회) | **제출·인증 두 값**에서 화면이 뺀다(승인 수는 서버가 이미 제외) |

- `fetchDeliverables` 에 캠페인 id 배열 필터가 **이미 있으면 그것을 쓰고, 없으면** storage.js 에 인자를 하나 더한다(`campaignIds` → `.in('campaign_id', ids)`). 기존 호출부는 인자를 안 주므로 동작이 같다. 200개 단위로 자르는 이유는 `.in()` 의 id 가 수백 개면 요청 주소가 길어지기 때문이다.
- 조회 결과 **`null`(실패)과 `[]`(0건)을 구분**한다. 실패면 제출·인증 두 칸을 「—」로 두고(승인/모집은 서버 집계라 그대로) 막대는 그린다(날짜는 캠페인 행에서 온다). 0을 그리지 않는다. ⚠️ 200개 단위 조각 중 **하나라도 실패하면 그 회차 전체를 실패로 본다** — 성공한 조각만 합치면 「0건」과 구분되지 않는 낮은 숫자가 그려진다.

### 4. 시간축

- **날짜의 기준은 둘이고, 한국·일본에서는 같다.** ①「오늘」은 `new Date()` 의 로컬 연·월·일을 `연-월-일` 문자열로 만든 값이다. 캠페인 날짜 칸은 이미 `연-월-일` 문자열(시간대 없음)이라 그대로 쓴다. ②시각(`timestamptz`)인 칸을 날짜로 쓸 때(`first_active_at`)는 **일본 표준시**로 잘라 `연-월-일` 문자열을 만든다(캠페인 날짜 칸이 일본 기준으로 입력되기 때문). 이 화면의 사용자는 한국·일본이라 ①과 ②가 같은 날을 가리킨다. 다른 시간대 PC 에서는 오늘선만 하루 어긋날 수 있고 그것은 감수한다(D-day 배지가 이미 같은 기준이다).
- 🔴 **날짜→위치 변환은 한 함수** `ganttDayOffset(baseYmd, ymd)` — 두 `연-월-일` 문자열을 연·월·일 정수로 잘라 `Date.UTC` 차이를 일수로 만든다. 문자열을 `new Date('2026-09-07')` 로 그대로 파싱하지 않는다(브라우저마다 협정 세계시/로컬 해석이 갈린다). 위 「날짜의 기준」은 *어느 날을 오늘로 볼 것인가·시각을 어느 날로 자를 것인가*이고, 이 함수는 *그 뒤의 계산*이다 — 둘을 섞지 않는다.
- 표시 범위 = 기준일 -14일 ~ +70일(12주). ‹ › 로 **4주씩** 이동, 「오늘」로 복귀.
- 눈금: 주 경계(월요일) 세로 선, 상단에 월 이름표(`9월`)와 주 시작일(`9/7`). 오늘은 강조색 세로선 + 「오늘」 이름표.
- 하루 폭 = 고정 픽셀(개발 세션이 정함, 12주가 약 900px 안에 들도록). 시간축 영역만 `overflow-x:auto` 이고 **스크롤바를 항상 보이게** 한다(리포트 브랜드 표 선례 — 없으면 옆으로 더 있는지 모른다는 사용자 지적이 있었다).
- **범위 밖 처리 — 원칙 하나로 정한다.** 행마다 먼저 **「그릴 것 목록」**을 만든다 = 설계 5 표의 요소들(막대 ①~⑤와 예외 ㄱ·ㄴ의 마커). 요소마다 **구간 이름·시작일·끝일**을 가진다(마커는 시작=끝, 무기한 모집 막대는 끝일 없음 = 시작일 이후 전부). 그다음 **요소 하나하나가 표시 범위와 겹치는지**만 본다:
  - 목록이 **비면** 시간축 칸에 「날짜 없음」 한 단어(회색). 그 표기가 최종이다.
  - 범위와 **겹치는 요소는 겹치는 만큼** 그린다(잘린 쪽 끝은 톱니). 끝일 없는 요소는 시작일이 범위 오른쪽 끝보다 앞이면 겹친다.
  - 범위와 **겹치는 요소가 하나도 없으면** 가장자리 마커를 그린다: 범위보다 앞에 있는 요소들 중 **끝일이 가장 늦은 것**을 왼쪽 가장자리에 「◀ 모집 마감 2026/08/20」, 범위보다 뒤에 있는 요소들 중 **시작일이 가장 이른 것**을 오른쪽 가장자리에 「선정 시작 2026/11/20 ▶」. 앞뒤에 다 있으면 마커 둘, 한쪽에만 있으면 하나.
  - 마커 문구 = **구간 이름(설계 5 표의 이름) + 「시작」 또는 「마감」 + 날짜**. 「시작/마감」은 가장자리 위치가 아니라 **그 요소가 가진 날짜의 성격**으로 정한다 — 막대는 왼쪽 마커면 끝일이라 「마감」, 오른쪽 마커면 시작일이라 「시작」이고, **시작=끝인 점 요소(예외 ㄱ 의 모집 마커·예외 ㄴ 의 제출 마커)는 위치와 무관하게 자기 날짜의 성격**(둘 다 마감일이므로 「모집 마감」·「제출 마감」)을 따른다. 날짜는 `formatDate` 형식이다(눈금의 `9월`·`9/7` 은 눈금 표기이고 이 규칙 밖이다).
  - 결정 4 의 대상 집합 안에서는 상태를 따로 보지 않는다. 왼쪽 마커는 「종료 포함」을 켜면 특히 많고, 오른쪽 마커는 주로 모집예정 건이다.

### 5. 막대 — `campaignPeriodRowKind` 갈래를 이름으로 지목

한 행에 **주 막대 한 줄** + **보조 막대 최대 두 줄**(있을 때만, 주 막대 아래 얇게). 두 줄이 되는 경우 = 갈래가 `visit` 이면서 ⑤ 선정 조건도 만족할 때(행사가 아닌 방문형에 선정 기간이 있는 경우와 선정형 행사) — 방문 + 선정.

| 구간 | 줄 | 시작 | 끝 | 농도 | 그리는 조건 |
|---|---|---|---|---|---|
| ① 모집 | 주 | `recruit_start` | `deadline` | 진함 | 항상. 시작·끝이 빈 경우는 아래 「모집 막대 예외」 |
| ② 제출 | 주 | `deadline` 다음 날 | `submission_end` | 옅음 | `submission_end` 가 있고 `deadline` 도 있을 때. 시작점은 언제나 `deadline` 다음 날 — ①이 막대면 그 끝에 이어 붙고, ①이 마커(예외 ㄱ)면 마커 다음 날부터 단독으로 그려진다 |
| ③ 구매 | 보조 | `purchase_start` | `purchase_end` | 중간 | 갈래 **`split`** 만. `merged`·`monitorNoPurchase` 는 모집과 같거나 없어서 안 그린다 |
| ④ 방문 | 보조 | `visit_start` | `visit_end` | 중간 | 갈래 **`visit`** 만. `visitMerged` 는 안 그린다 |
| ⑤ 선정 | 보조 | `selection_start` | `selection_end` | 중간 | **선정 기간 표시 조건 4곳과 글자 그대로 같은 조건**(gifting / visit 이고 행사 아님·선정형 행사) 이고 값이 있을 때. 갈래 `gifting` 이 그 뜻이지만 **방문형 선정형 행사는 갈래가 `visit`** 이라 갈래만으로는 못 가른다 — 조건을 그대로 옮긴다. ⚠️ 이 자리가 **5곳째**다. 네 곳 주석에 이 파일 경로를 더한다 |

**모집 막대 예외** (①의 시작·끝이 빈 경우)
- ㄱ. **시작(`recruit_start`)이 빈 캠페인**: `first_active_at` 이 있으면 그 날짜를 시작으로 쓴다. 그것도 없으면 **모집 구간은** 마감일 하루짜리 **마커**(◆)만 그리고 툴팁에 「모집 시작일 없음」(② 제출 막대는 자기 조건대로 그대로 그린다). 인플루언서 화면의 「오늘」 폴백을 여기서 흉내 내지 않는다 — 어제 열어도 오늘 열어도 시작이 움직이면 일정표가 아니다.
- ㄴ. **끝(`deadline`)이 빈 캠페인**(무기한 모집): 모집 막대를 **끝일 없는 요소**로 목록에 넣는다 — 그릴 때는 시작일부터 표시 범위 오른쪽 끝까지 이어 그리고 끝에 「마감 없음」 이름표를 붙인다. ② 제출 막대는 시작점이 없으므로 그리지 않고, `submission_end` 가 있으면 그 날짜에 마커(구간 이름 「제출」)를 둔다. 정렬(결정 8)에서는 「마감 없음」으로 뒤에 간다.
- ㄷ. ㄱ·ㄴ을 거쳐도 그릴 것 목록(설계 4 「범위 밖 처리」)이 비면 — 모집·제출 막대도 마커도 보조 막대도 하나 없으면 — 「날짜 없음」 글자가 최종이다(빈 줄 금지 — 의심 2). ⚠️ 날짜 칸 몇 개가 비었는지로 세지 않는다. 방문 기간만 있는 캠페인은 목록이 비지 않는다.

- 마감(`deadline`)·제출 마감(`submission_end`)에 **D-day 배지**(`dDayLabel`)를 막대 끝에 붙인다. D-3 이하·지난 마감은 그 배지 색으로만 강조(막대 색은 안 바꾼다).
- 막대에 마우스를 올리면 툴팁: 구간 이름 + `YYYY/MM/DD ~ YYYY/MM/DD`(`formatDate` — 화면마다 날짜 모양이 다르면 안 된다).
- 방문형 행사(`event_mode`) 의 예약 타임은 이 화면에서 **그리지 않는다**(행사 기능은 아무도 켠 적이 없고 데이터 0건 — 후속).

### 6. 인증 성공 계산 — 사본을 만들지 않는다

```

delivs = ids 를 200개씩 잘라 fetchDeliverables({campaignIds: 조각}) 를 차례로 부른 뒤 합침

row.submittedInf = distinct(user_id) - 감사용
```

- ⚠️ 여기서 서버 함수를 새로 만들지 않는 이유는 위 「충돌 가능성」 — 판정 사본이 이미 5곳이고, 정산 후보 함수(331)는 무보수 시딩·방문형을 **일부러** 뺀다.
