# 슈퍼관리자 권한 자기 제한

**작성일:** 2026-07-29
**작성:** 기획/설계 세션 (reverb-planner)
**상태:** ✅ **운영에 있음** (2026-09-02 기획 세션 확인 — `permSuperEffect`). 배포 시점·마이그레이션 번호는 아래 「구현 결과」가 단일 소스다. ⚠️ 「구현 결과」가 아직 「운영 미적용」이라고 적고 있다.

## 정정 (2026-08-10, 전수조사 I-15)

이 문서가 설명하는 효과 배지 「슈퍼 적용 안 됨」의 **이름과 화면 문구를 「설정 미적용」으로 바꿨다.**

**왜**: 그 12개 항목은 서버 가드가 등급을 하드코딩하고 화면도 등급을 직접 비교해서, **캠페인관리자·캠페인매니저 칸의 설정도 똑같이 무효**다. 그런데 배지 이름과 안내 문구가 전부 「슈퍼관리자가 제한하면…」 관점으로만 적혀 있어 **그 사실이 어디에도 없었다.**

→ 운영자가 캠페인관리자 칸을 「숨김」으로 바꿔 두고 **막혔다고 믿을 수 있었다.** 이 문서 본문의 원인 서술(「서버·화면 가드가 등급 하드코딩이라 무시」)은 원래부터 등급 중립이었지만, **라벨이 그 사실을 가렸다.**

⚠️ **서버 가드는 그대로다.** 12개를 진짜로 제어하려면 가드를 권한 판정으로 갈아끼우는 별도 작업이 필요하다 — 이번에는 **사실대로 말하는 것**까지만 했다.

아래 본문에 남은 「슈퍼 적용 안 됨」 표기는 **당시 기록**이다. 현재 화면 라벨은 「설정 미적용」이다.

## 0. 요구사항

권한 관리 화면(`/admin#permissions`)의 **슈퍼관리자 열도 「쓰기·읽기·숨김」을 고를 수 있게** 한다. 단 「슈퍼 전용」 3개(`permissions.manage`·`admin.manage`·`menu.permissions`)는 잠근다. 목적은 화면 통일이 아니라 **실제 제한(서버 차단 포함)**.

## 2. 의심·경우의 수

### 2-1. 되돌릴 수 없는 잠금 — 「슈퍼 전용 3종만 지키면 항상 복구 가능한가?」 → **아니다**
복구 수단(`update_role_permissions`·`restore_role_permissions_defaults`)은 둘 다 권한 관리 화면 안에만 있다. 도달 경로:

| 경로 | 필요 조건 | 슈퍼가 스스로 끊을 수 있나 |
|---|---|---|
| ① 「관리자 계정」 → 「권한 관리」 버튼 | `menu.admin-accounts` 가 숨김이 아님 | **끊을 수 있음** — 숨김 저장 시 사이드바에서 사라지고 주소창 진입도 가드가 되돌림 |
| ② 주소창 `#permissions` | 진입 가드 통과 | 안 끊김. 단 일반 사용자가 모르는 경로 |
| ③ SQL 편집기 직접 수정 | 개발자 개입 | 항상 가능(최후 수단) |

「관리자 계정」은 **다른 슈퍼를 초대하는 유일한 화면**이라, 슈퍼 1명일 때 숨기면 이중 잠금.

### 2-2. 「행이 없는 기능」 — 거부로 두면 신규 기능마다 슈퍼가 못 보는 사고
→ **슈퍼에 한해 「행 없으면 전권」** 권고(등급 2종은 기존대로 거부). 슈퍼 제한은 보안 경계가 아니라 자기 제한이므로 「명시적으로 잠근 것만 잠긴다」가 옳다.

### 2-3. 서버 차단 5개의 파급
- `influencer.sensitive_pii` 숨김 → 화면뿐 아니라 **신청자·결과물 엑셀의 연락처·배송지 열이 통째로 빈다**(배송 업무 정지 가능)
- `settlement.view` 숨김 → 진입 시 자동 등록(`backfill_settlements`)이 거부돼 **그 기간 정산 대상이 등록되지 않음**(나중에 풀어도 뒤늦게 발견되는 함정)
- `outbound.view` 숨김 → 조회뿐 아니라 **대표 이미지 업로드(저장소 정책)** 도 막힘
- `settlement.pay` 읽기 → 화면은 보이는데 송금완료가 서버에서 거부
- **메뉴 키와 기능 키 불일치** — `menu.settlements`는 쓰기인데 `settlement.view`만 숨기면 「메뉴는 보이는데 들어가면 오류」

### 2-4. 「설정했는데 아무 일도 안 일어남」 — 12개(그룹 C)
서버 가드가 `is_campaign_admin()`, 화면 가드도 등급 하드코딩. 숨김으로 저장해도 버튼이 그대로 보이고 저장도 된다 → 「제한했는데 왜 되지?」로 신뢰 상실

### 2-5. UX
1. 「슈퍼관리자」인데 못 보는 화면이 생김 — 배지·문구가 전부 「슈퍼=전권」 전제. 「실수 방지용 자기 제한이며 언제든 되돌릴 수 있음」 명시 필요
2. **⚠️ 계정별이 아니라 등급 전체** — 슈퍼 2명 이상이면 한 사람의 저장이 다른 슈퍼도 막는다
3. 저장 확인이 한 줄뿐 — 자기 발등을 찍는 동작이므로 강한 경고 + 무엇이 사라지는지 + 되돌리는 법 필요
4. 「기본값 복원」이 **다른 등급 설정까지 초기화** — 응급 복구가 남의 설정을 날리는 구조
5. 잠금 3종만 회색으로 남아 「왜 이 줄만 못 고치나」 툴팁 필요
6. `role_permissions` 조회는 모든 관리자에게 열려 있어 campaign_admin 도 슈퍼 제한 사실을 볼 수 있음

### 2-6. 기술·데이터
- **`role_permission_history` CHECK 를 같이 안 풀면** 슈퍼 행 저장 시 이력 INSERT 가 제약 위반 → **저장 트랜잭션 전체 롤백**
- 42키 × 3등급 = 126칸인데 저장 함수 **배열 상한 100** → 전체 변경 시 실패
- 오류 문구가 거짓("campaign_admin|campaign_manager 만 허용")
- 성능 영향 미미(가림막 뷰는 쿼리당 1회 평가). 정산 1000행 페이지네이션만 호출 횟수 확인
- **권한 설정은 데이터라 배포로 안 옮겨감** — 운영에서 잘못 잠그면 운영에서 풀어야 함
- `maskedFieldByPermission` 은 클라 `canRead` 기반이라 **서버는 지웠는데 화면은 「등록 안 됨」으로 보이는 오표시** → 클라 `permLevel` 도 반드시 함께 수정
- **롤백은 매우 쉬움** — 판정 함수만 옛 정의로 되돌리면 슈퍼 즉시 전권 복구(표 데이터 그대로)

### 2-7. 의도 모호점
① 제한 대상(등급 전체 vs 본인 계정) ② 「실제로 제한」의 범위(5개만/화면까지/12개 서버 가드 교체) ③ 잠금 유지 대상에 「관리자 계정」 메뉴 포함 여부 ④ 「숨김」까지 허용할지

## 3. 권고
슈퍼 제한을 **「보안 경계」가 아니라 「자기 제한(실수 방지 안전장치)」로 못 박고**, ①슈퍼 행을 표에 넣되 **행 없으면 전권** ②복구 경로를 **구조적으로 못 끊게** 잠근 뒤 ③서버가 실제로 막는 5개 + 화면 메뉴만 열고, 효과 없는 12개는 표시만 하는 방향. 12개까지 진짜 막으려면 서버 가드 12곳 교체(위험도 높음)라 별도 작업으로 분리.

## 4. 설계

### 4-1. 데이터베이스 (마이그레이션 3개, 순서 ①→②·③)
**① 등급 허용값 확장 + 슈퍼 행 시드**
- `role_permissions.role` CHECK 에 `'super_admin'` 추가
- `role_permission_history.role` CHECK 에도 추가 (**빠뜨리면 저장 통째 실패**)
- 시드: `SELECT DISTINCT feature_key FROM role_permissions` 를 원본으로 `('super_admin', 키, 'write', 'write')` `ON CONFLICT DO NOTHING` — 카탈로그 상수를 손으로 옮기지 않는 이유는 표와 상수가 이미 어긋나 있을 수 있어서
- `access_level = default_level = 'write'` → **적용 즉시 동작 변화 0**

**② 판정 함수 `has_permission` 재정의**
```
IF is_super_admin() THEN
   ('super_admin', 기능키) 조회
   행 없음 → true (슈퍼 전용 fail-open)
   행 있음 → 수준 비교
ELSE  기존 로직(미등록이면 false)
```
`STABLE`·`SECURITY DEFINER`·`search_path=''` 유지, 시그니처 동일. 주석에 **비대칭 계약** 명시

**③ 저장 함수 `update_role_permissions` 재정의**
- 허용 role 에 `'super_admin'` 추가 + 오류 문구 갱신
- **슈퍼 잠금 규칙**: role=super 이고 잠금 목록이면 **`'write'` 외 거부** (등급 2종 denylist 는 「hidden 외 거부」로 방향이 반대)
- 배열 상한 100 → **200**
- `restore_role_permissions_defaults` 는 재정의 불필요(등급 무관 전체 대상) — 슈퍼 기본값이 전부 write 라 **복원 = 슈퍼 전권 원복**이 자동 성립

### 4-2. 잠금 방지 5중 안전장치
| # | 장치 |
|---|---|
| 1 | 판정 함수 슈퍼 fail-open — 시드 누락이 잠금으로 안 이어짐 |
| 2 | 진입 가드에서 `permissions` 는 **숨김 판정 자체를 건너뛰고** 등급만으로 통과 |
| 3 | 저장 함수의 슈퍼 잠금 목록(서버 최종 방어선) |
| 4 | 「기본값 복원」 = 슈퍼 전권 원복 |
| 5 | 응급 복구 SQL 문서화: `UPDATE public.role_permissions SET access_level = default_level WHERE role='super_admin';` (**함수가 아니라 직접 UPDATE 여야 함**) |

추가로 **「관리자 계정」 도달 보장** — 사이드바에 권한 관리 상설 항목 신설(권장) 또는 `menu.admin-accounts` 도 슈퍼 열 잠금

### 4-3. 화면
- `shared.js permLevel`: 슈퍼면 `_rolePermMap['super_admin|키'] || 'write'` — 이 한 줄로 메뉴·진입 가드·엑셀·이력·민감정보 라벨 5곳에 동시 적용
- `admin-permissions.js`: 슈퍼 무조건 write 제거, `cellLocked` 를 등급별 분기(잠금×슈퍼 = 「쓰기(전권·고정)」 + 툴팁), **효과 범위 배지 3종**(서버 차단 / 화면에서만 / 슈퍼에게는 적용 안 됨 — 카탈로그에 `super_effect` 항목 추가), 슈퍼 변경 포함 저장 시 **별도 확인 모달**(무엇이 사라지는지·되돌리는 법·등급 전체 적용 명시), 경고 배너 문구 교체, 「슈퍼관리자 권한만 복원」 보조 버튼
- `admin-core.js`: `switchAdminPane` 의 permissions 분기 = 숨김 판정 건너뛰기
- `admin/index.html`: 사이드바 권한 관리 항목 1줄
