## 3. ⛔ 착수 전 반드시 알아야 할 것 4가지

### 가. 마이그레이션 번호 — 그 폴더에서 보이는 번호를 믿으면 안 된다

작업 폴더는 `c68e1c4` 시점에 서 있어 **거기서 목록을 보면 마지막이 `290`으로 보인다.**
그런데 **`origin/dev` 에는 이미 `292` 까지 들어와 있다**(행사 묶음 작업이 291·292를 점유).

→ 그대로 만들면 **291을 다시 써서 충돌한다.**
→ **착수 첫 명령은 최신화다:**
```bash
cd ~/Documents/projects/reverb-jp-브랜드사-오리엔시트-메모-기능-추가
git pull origin dev
ls supabase/migrations/ | tail -3   # 최신 번호 재확인 후 그다음부터
```
→ 이 문서 작성 시점 기준 새 번호는 **293부터**. 단 팝업 티켓 작업이 그 사이 더 만들 수 있으니 **파일을 만드는 시점에 다시 확인**한다.

### 나. 브랜드 작성 화면은 배포 대상이 다르다

`dev/sales/orient.html` 은 빌드가 `sales/` 로 복사하고, **별도 Vercel 프로젝트(`reverb-sales`)** 가 배포한다. 인플루언서·관리자 앱과 배포 경로가 다르다.
→ 커밋이 올라갔다고 반영된 게 아니다. **브라우저로 실제 페이지를 열어 확인**한 뒤 다음 단계로 넘어간다.

### 다. 1단계 안의 순서를 어기면 데이터가 날아간다

**저장 함수 → 브랜드 작성 화면 → 기존 데이터 채우기** 순서다. 저장 함수가 먼저 안 나간 상태에서 브랜드가 한 번 저장하면 그 시트의 카드 번호가 통째로 사라진다. 사양서 §6에 이유와 함께 적혀 있다.

### 라. 번호를 만드는 곳은 저장 함수 한 곳뿐이다

브랜드 작성 화면은 번호를 **만들지 않고 실어 나르기만** 한다. 이걸 어기면(화면도 번호를 만들면) 사양서의 검증 절차 ③이 원리적으로 성립하지 않는다 — 정합성 점검에서 실제로 걸린 항목이다.

## 4. 작업 순서와 관문

사양서 §6 이 단일 소스다. 큰 줄기만 적으면:

1. **1단계 — 카드에 고유 번호 심기** (저장 함수 → 작성 화면 → 기존 데이터 채우기)
   → **이 단계 검증이 끝나기 전에 2단계를 시작하지 않는다.** 2단계 전체가 이 번호에 얹혀 있다.
2. **2단계 — 메모 본체** (표 2개 · 서버 함수 2개 · 상세 화면 메모 영역 · 「삭제된 모집 건의 메모」 묶음 · 접근 함수)
3. **3단계 — 목록 배지 + 시트 삭제 경고**

각 단계의 검문소(무엇을 어떻게 확인하는지)는 사양서 §6 표에 있다. **1단계 검문소 ③(물려주기 검증)은 절차가 까다로우니 그대로 따라갈 것** — 저장된 번호를 지우면 검증이 성립하지 않는다는 함정이 있다.

## 7. 기획 세션이 남기는 메모

이 사양서는 정합성 점검을 **9차례** 돌려 수렴시킨 것이다. 매 회 실질 결함이 나왔고 그중 셋은 **고치는 과정에서 새로 생긴 것**이었다:

- 안전망에 개수 조건이 없어 메모가 **조용히 엉뚱한 제품에** 붙던 문제
- 「펼쳐졌을 때만 읽음 처리」가 자동 펼침 때문에 **아무것도 걸러내지 못하는 헛조건**이던 문제
- 검증 절차가 **원리적으로 실행 불가능**하던 문제

→ 사양서의 ⚠️ 표시는 전부 이 과정에서 실제로 걸린 자리다. **구현 중 「이건 굳이 왜 이렇게?」 싶은 조건이 나오면 지우기 전에 그 ⚠️ 를 먼저 읽을 것.**

구현하면서 사양서와 어긋나는 지점을 발견하면, 코드를 맞추지 말고 **먼저 사양서를 고치거나 기획 세션에 되물을 것**(`.claude/rules/request-validation.md`).
