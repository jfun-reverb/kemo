# 리뷰어형 정산 금액을 영수증 실결제액으로 전환 + 화면 문구 정정

**작성일:** 2026-08-05
**작성 세션:** 개발
**선행 문서:** `docs/specs/2026-08-04-settlement-receipt-basis.md`(논의 기록·미결 2건) · `docs/specs/2026-07-23-settlement-reviewer-receipt-amount.md`(상시가로 확정했던 근거)

---

## 요약

리뷰어형(monitor) 캠페인의 정산 금액을 **캠페인 상시가(`campaigns.product_price`)** 에서 **영수증 실결제액(`deliverables.purchase_amount`, 상시가를 상한으로 자름)** 으로 바꾸고, 인플루언서 화면 문구를 그에 맞게 정정한다.

**이 작업은 두 층으로 나눠 봐야 한다.**

| 무엇에 견주는가 | 성격 |
|---|---|
| **실제 지급 실무에 견주면** | **정정**. 페이팔 송금은 **대체로**(리뷰어형 실측 94%) 영수증 금액이었고 시스템 계산·화면 문구만 상시가였다 |
| **화면이 인플루언서에게 한 약속에 견주면** | **불리한 변경**. 상시가를 보고 응모한 사람 중 **317건**(704건 모집단 기준 — 즉시 처리 대상 기준 건수는 §5-2에서 재조회)이 그보다 적은 금액을 받게 된다 |

문서·약관·통지에서 이 두 층을 섞어 쓰지 않는다. 지급 실무는 안 바뀌지만, **화면 약속 대비로는 불리한 변경**이므로 약관·통지는 불리한 변경 기준으로 다룬다(§3-6).

## 1. 현재 상태 (2026-08-05 · 운영 실측 · 규칙 A)

### 1-1. 금액을 정하는 서버 함수

| 함수 | 하는 일 | **현재 유효한 정의** |
|---|---|---|
| `_settlement_cert_candidates()` | 인증 성공 판정 + 금액 계산(공통 헬퍼) | **264** |
| `backfill_settlements()` | 자동 등록 | **262**(242의 알림 잠금 계승) |
| `get_past_unregistered_settlements()` | 「과거 미등록」 조회 | **262** |
| `register_past_settlements()` | 「과거 미등록」 수동 등록 | **262** |

현재 금액 분기(264):
- `monitor` → `campaigns.product_price` (가구매 `proxy_purchase` 여부 무관)
- `gifting`·`visit` → `campaigns.reward`

`deliverables.purchase_amount` 는 **금액 계산에 전혀 쓰이지 않는다.**

⚠️ 262 파일 자체가 「파일 번호가 가장 큰 정의를 베이스로 삼을 것」을 경고로 남기고 있다(262 초안이 232를 베이스로 삼아 알림 잠금이 조용히 사라질 뻔한 사고). 이번 재정의도 같은 함정 구간이다.

### 1-2. 저장 구조

- `settlements.amount_jpy bigint NOT NULL CHECK (amount_jpy > 0)` — 생성 시점 스냅샷(217)
- `settlements.amount_source` 허용값 **3종**(`reward`·`product_price`·`product_plus_reward`, 261) → **영수증 기준 값을 저장하려면 제약 확장 필요**
- `settlements.application_id` UNIQUE — 응모 1건 = 정산 1행(멱등)

### 1-3. 영수증 데이터 구조

- 영수증(`kind='receipt'`)에는 **「기존 행 교체」 분기가 없다** — `dev/lib/storage.js` 의 `insertDraftDeliverable()` 는 게시물·리뷰 인증샷에만 교체 분기가 있어, 영수증은 재제출할 때마다 **새 행이 쌓인다**. 유일값 제약도 없다.
- 헬퍼의 `receipt_latest` 는 `DISTINCT ON (application_id) … ORDER BY submitted_at DESC, updated_at DESC` 로 **상태 무관 최신 1건**을 고르고, 인증 성공은 **그 행이 `approved` 인지**로 판정한다.
- ⚠️ 따라서 **금액도 반드시 그 같은 행에서 가져와야** 판정과 금액이 한 소스로 유지된다. 「승인된 영수증 중 최대값」 같은 별도 조건을 쓰면 판정과 금액이 다른 행을 가리키게 된다. (인증 성공 건은 정의상 최신 행이 승인 상태이므로, 최신 행 = 승인 행이다.)
- `purchase_amount` 는 소수 허용(`numeric`), `amount_jpy` 는 정수 → 구조상 반올림 규칙이 필요하다(실측 소수점 0건).
- 값이 빌 수 있는 경로: 마이그레이션 178이 관리자 인플레이스 수정을 「3종 중 1개만 있어도 저장」으로 완화. 인플루언서 제출 폼(3종 필수)과 관리자 대리 등록(160·161)은 안전.

### 1-5. 운영 실측 (2026-08-05, 운영서버)

**정산 설정**

| 항목 | 값 | 의미 |
|---|---|---|
| `cutoff_at`(정산 도입일) | **비어 있음** | **자동 등록이 0건** — 새 인증 성공 건이 상시가로 저절로 쌓이는 상태가 아니다 |
| `influencer_visible`(인플루언서 노출) | **꺼짐** | 인플루언서는 정산 화면·정산 알림을 못 본다. 단 **캠페인 상세의 페이백 문구는 잠금과 무관하게 전원에게 보인다** |

**저장된 정산 행 — 204건이 전부, 모두 「송금완료」**

| 금액 출처 | 건수 | 합계 |
|---|---:|---:|
| (비어 있음) | 203 | 928,575엔 |
| `product_price` | 1 | 2,190엔 |

- ★ **대기(pending) 행 0건.** 선행 문서가 「대기 437건」이라 부른 것은 **정산 행이 아니라 조회 함수가 뽑아 주는 후보 목록**이었다 → **되돌리거나 재계산할 금액 스냅샷이 존재하지 않는다.** 이번 변경의 가장 큰 걱정거리가 실측으로 소멸했다. **이하 이 문서는 「과거 미등록 후보」로 부른다.**
- 금액 출처 라벨이 비어 있는 것은 시스템 함수가 아니라 **관리자 도구로 직접 넣었다**는 뜻이다(261이 기존 행을 `reward` 로 백필했으므로 비어 있음 = 그 이후 직접 삽입). 그래서 레포에 근거 파일이 없다.
- `product_price` 1건은 **화면 버튼으로 처리하면 상시가로 잘못 저장된다**는 함정이 실제로 한 번 발생한 흔적이다.

**저장 금액이 영수증과 맞는지 — 건별 대조**

| 구분 | 건수 |
|---|---:|
| 영수증 금액과 **건별 일치** | **176건** |
| 영수증이 없는 형식(시딩 15건, 저장액 = 현금 리워드) | 15건 |
| 리뷰어형인데 **영수증과 어긋남** | **12건** |
| `product_price` 라벨 1건(리뷰어형) — 영수증·상시가가 같은 값이라 양쪽에 모두 일치 | 1건 |

→ **리뷰어형 모집단은 189건**(라벨 없는 188건 + `product_price` 1건)이고 그중 **177건이 영수증 금액과 일치(약 94%)**. 이하 이 문서에서 「94%」는 이 기준을 가리킨다.

- 합계도 지급 대장의 「203건 928,575엔」과 1엔 차이 없이 맞는다. 다만 **합계 일치만으로는 「영수증 기준이었다」가 증명되지 않는다**(둘 다 사람이 넣은 숫자다). 근거가 되는 것은 **건별 일치 176건**이고, 리뷰어형 188건 중 **12건은 실제로 어긋난다.**
- → 이 문서가 「실무는 영수증 기준」이라고 말할 때의 강도는 **「리뷰어형 189건 중 177건(약 94%)이 영수증 금액과 일치, 12건은 사람 손 작업 오차」** 다. 100% 증명이 아니다. **다른 절에서도 「줄곧」·「이미」 같은 단정형 대신 「대체로(94%)」로 쓴다.**

**어긋난 리뷰어형 12건**

- 전부 2026년 5월 초·중순. **영수증은 응모당 1장씩뿐이고 모두 승인 상태인데** 저장금액이 다르다. 차액 −853엔 ~ +853엔으로 제각각이라 규칙이 아니라 **사람 손 작업의 오차**다. 합계 −743엔(4명 과소·8명 과다).
- 특히 B0035-C008(저장 2,160 / 영수증 3,013)과 B0010-A001-C004(저장 3,013 / 영수증 2,160)는 제출 1분 차·검수 동일 시각으로, **두 건의 금액이 서로 뒤바뀌어 지급된 것**으로 보인다.
- → **이번 작업 범위 밖의 과거 문제.** 이미 송금 완료라 되돌리기 어렵고 금액도 작다. 다만 자동 계산 전환이 이런 오차를 구조적으로 없앤다는 근거가 된다.

**앞으로 지급할 건들의 영수증 품질**

조회 조건: 영수증 승인 · 응모 승인 · 리뷰어형 · 감사용 계정 제외 → **704건**

| 항목 | 값 |
|---|---:|
| 금액 없음 | **0건** |
| 0원 이하 | **0건** |
| 소수점 | **0건** |
| 상한(상시가)이 없는 캠페인 | **0건** |
| 상시가보다 싸게 삼 | **317건** ← 이 사람들이 상시가 기준보다 적게 받는다 |
| 상시가와 같음 | 342건 |
| 상시가보다 비싸게 삼 | 45건(최대 초과 2,520엔) ← 상한으로 잘려 상시가 기준과 동일 |
| **평균 차액**(영수증 − 상시가, **상한 적용 전**, 704건 기준) | **−346엔** |
| 상한 적용 시 총 지급액 | **2,496,683엔** |
| 상시가로 줄 때 총액 | 2,764,547엔 |
| **차이**(상한 적용 **후**) | **−267,864엔** |

⚠️ **평균 −346엔과 총 차이 −267,864엔은 기준이 다르다.** 앞은 상한 적용 전·704건 평균이고, 뒤는 상한 적용 후 총액 차이다(상한 초과 45건의 양수 차액이 뒤에서는 0으로 잘리므로 값이 어긋난다). 실제 감액 대상은 **317건**이고 1인당 평균 감액은 **약 845엔**이다. 위험 크기를 말할 때는 **317건·평균 845엔**을 쓰되, 이것은 **704건 모집단 기준**임을 함께 밝힌다 — **즉시 처리 대상(후보 437건) 기준 감액 건수·평균액은 §5-2에서 재조회**한다.

**「704건」과 「과거 미등록 후보 437건」의 관계**

- 704건 = **영수증만** 승인된 리뷰어형 응모
- 437건 = 그중 **인증 성공까지 끝난**(리뷰어형은 영수증 + 캠페인 채널별 리뷰 인증샷이 모두 승인) 건 = 정산 후보
- 즉 **437건 ⊆ 704건**. 지금 당장 처리 대상은 **437건**이고, 704건은 앞으로 인증 성공이 진행되면서 정산 후보로 편입될 모집단이다.
- ⚠️ 위 금액 총계(2,496,683엔·2,764,547엔)는 **704건 기준**이므로, 437건을 처리할 때의 실제 총액은 이보다 작다. **처리 직전에 437건 기준 총액을 다시 조회한다**(§5-2).

**8월 인증분 건수**

8월 인증분은 후보 437건 안에 **섞여 있으나 이 문서의 실측에서 따로 갈라 세지 않았다.** 선행 문서가 적은 「8월 인증분 45건」이라는 숫자는 이 문서의 조회로 확인된 값이 아니므로 **근거로 쓰지 않는다**(§1-5의 「비싸게 삼 45건」과는 **다른 집단**이며 숫자가 우연히 같다). 처리 전에 **인증 성공일 기준 월별 분포를 따로 조회**해 실제 건수를 확보한다(§5-2).

### 1-6. 이 제안과 충돌 가능성 있는 기존 동작

1. `amount_source` 허용값 3종 제한(261) — 확장 필요.
2. 헬퍼 반환 항목이 늘어나므로 **삭제 후 재생성** + 호출 함수 3개를 같은 트랜잭션에서 함께 재정의해야 한다(262가 문서화한 순서).
3. **관리자 영수증 수정(178)이 금액을 사후에 바꿀 수 있다.** 지금은 그 값이 돈과 무관하지만, 바뀌면 이미 저장된 정산액과 조용히 어긋나는 통로가 열린다(§3-4).
4. 인증 성공 판정·정산 도입일·송금완료/보류/취소/보류해제·노출 잠금·권한 체계·자동 보류(246)·반려 차단(247)·삭제 차단(251)과는 **충돌 없음 — 확인 완료.**

- 과거 지급 오차 12건(§1-5) — 이번 범위 밖, 별도 판단.

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 깨질 수 있는 경우의 수

**① [사용자 경험 — 가장 큰 위험] 인플루언서가 손으로 적은 숫자가 곧 받는 돈이 된다.**
지금 영수증 금액 칸은 「증빙 보조 정보」라 틀려도 손해가 없었고, 기기 안 글자인식(`dev/lib/ocr-receipt.js`)이 빈 칸을 자동으로 채워 준다. 이 값이 지급액이 되면 세 방향으로 터진다.
- **덜 받음**: 글자인식이 `2,000`을 `200`으로 읽은 것을 확인 없이 제출 → 본인 손해 → 문의.
- **과다 청구 유인**: 숫자를 부풀릴 동기가 생겨, 검수자가 영수증 사진과 숫자를 **일일이 대조**해야 한다(7-23이 버렸던 부담이 최대 강도로 부활).
- **안내 부재**: 활동관리 영수증 입력 화면에 「여기 적은 금액이 지급액이 됩니다」라는 말이 한 줄도 없다. 안 넣으면 위 둘이 반드시 일어난다. → **이 안내는 실제 지급이 일어나는 4단계보다 먼저 배포한다**(§4 의존 순서에 반영). 1단계(서버 규칙)만 나가는 시점에는 자동 등록이 0건이라(§1-5) 지급이 저절로 발생하지 않으므로, 1단계보다 앞설 필요까지는 없다.

**② [사용자 경험] 「최대 ¥2,000」은 응모 판단을 어렵게 만든다.**
지금 배지·카드는 금액이 주인공(17px 굵은 분홍)이라 한눈에 비교된다. 새 문구는 **응모 시점에 받을 금액이 확정되지 않는다.** 하단 고정 바(480px 폭)에서는 줄바꿈·말줄임이 생긴다. 카드 목록(화면 ③)은 지금도 「제품 무상 제공」이라 새 문구와 어긋나 **한 캠페인이 화면마다 다르게 설명된다.**

**③ [데이터] 317건이 화면에서 본 금액보다 적게 받는다** (1인당 평균 약 845엔, **704건 모집단 기준** — 즉시 처리 대상 기준은 §5-2 재조회). 이미 「¥N 円ペイバック」을 보고 응모해 구매까지 마친 사람이 여기 포함된다. **문구 변경이 그들에게는 사후 통지가 된다.** — 단, **실제 지급 실무 대비로는 대체로 달라지는 것이 없다**(리뷰어형 실측 94%가 영수증 기준). 「덜 받는다」는 **상시가로 계산했을 경우와 견준 표현**이다.

**④ [기술] 영수증 행이 여러 개 쌓이는 구조 + 금액이 뒤늦게 바뀌는 경로.** 관리자가 정산행 생성 뒤에도 영수증 금액을 고칠 수 있고(178), 그때 정합을 아무도 확인하지 않는다. 송금까지 끝난 건이 바뀌면 감사 근거가 어긋난다.

**⑤ [권한·환경] 개발서버에는 리뷰어형 인증 성공 데이터가 사실상 없다.** 7-23 때 264(무보수 시딩 261건 오표시)는 **운영 실측에서만** 드러났다. 개발서버 검증만으로 통과시키면 같은 패턴이 반복된다.

**⑥ [법률·약관] 약관 제2조 6항이 「所定金額の報酬」(정해진 금액의 보수)로 못박고 있다**(`docs/TERMS_ja.md:26`). 실결제액 변동 지급은 이 정의와 어긋난다. 제13조에는 페이백 유형 자체가 없다.

**⑦ [운영] 이미 발송된 홍보 메일의 「¥2,000 ペイバック」은 되돌릴 수 없다.**

### 2-2. 현재 구현과 어긋나는 지점

§1-6의 1~3번이 그대로 충돌점이다. 특히 **3번(영수증 사후 수정)** 은 지금 아무 가드가 없어, 규칙을 바꾸는 즉시 어긋남이 조용히 생기는 통로가 열린다. 그 외 영역은 **충돌 없음 — 확인 완료.**

### 2-3. 의도가 갈릴 수 있는 표현

1. **「최대 ¥2,000」의 상한이 무엇인가** → 캠페인 `product_price` 로 확정(§3-1).
2. **「구매 금액」의 범위(쿠폰·적립금·배송비)** → **영수증에 적힌 최종 결제 금액을 그대로 쓴다**로 확정. 근거는 「실무가 지금까지 그렇게 송금해 왔다」이다.
   ⚠️ 「상한 초과분이 어차피 잘리니 정의가 불필요하다」는 논리는 **상한을 넘은 45건에만** 성립한다. **상한 아래 317건은 배송비·적립금 포함 여부가 지급액에 그대로 반영**되므로, 정의가 필요 없는 것이 아니라 **실무 관행을 그대로 성문화하는 것**이다. 인플루언서가 자기 적립금을 써서 싸게 샀으면 그만큼 적게 받는다 — 이 점을 §3-3 (사)의 입력 안내에 한 줄로 밝힌다.
3. **적용 범위·시점** → §3-5 참조(적용 대상은 리뷰어형 전체, 시점은 배포 즉시).

## 3. 설계

### 3-1. 금액 산정 규칙

| 항목 | 규칙 |
|---|---|
| 리뷰어형(가구매 포함) | **min(그 응모의 최신 영수증 `purchase_amount`, 캠페인 `product_price`)** |
| 어느 영수증인가 | **인증 성공 판정에 쓰인 바로 그 행**(`receipt_latest`) — 판정·금액 단일 소스. 인증 성공 건은 정의상 그 행이 승인 상태다 |
| 「구매 금액」의 범위 | **영수증에 적힌 최종 결제 금액 그대로**(배송비 포함·쿠폰/적립금 차감 후). 실무 관행 성문화 |
| 소수 | **버림**(엔 단위). 실측 0건이나 구조상 가능하므로 명시. ⚠️ **버림 결과가 0 이하가 되면 「금액 미확정」으로 보낸다**(0.5엔 같은 값 — 안 정해 두면 `CHECK (amount_jpy > 0)` 위반으로 배치가 죽는다) |
| 영수증 금액 없음·0 이하 | **금액 미확정 처리**(저장하지 않음). 기존 `amount_issue` 구조 재사용 |
| 상한(`product_price`) 없음·0 이하 | **금액 미확정 처리** — 「최대 ¥N」을 약속하면서 상한이 없으면 지급 근거가 없다 |
| 시딩(gifting)·방문형(visit) | **변경 없음**(`campaigns.reward`) |
| 가구매(`proxy_purchase`) | **리뷰어형과 동일 적용** — 인플루언서가 자기 돈으로 사고 영수증만 내는 형식이라 근거가 같다 |
| 스냅샷 | **생성 시점 고정 유지**(217 원칙). 사후 영수증 수정이 저장된 금액을 자동으로 바꾸지 않는다. **예외 — 정산이 아직 「정산대기」 상태인 건에서 「최신 영수증의 금액이 바뀌는 모든 경우」**: ㉮ 관리자가 영수증 금액을 고칠 때 ㉯ 인플루언서가 새 영수증을 내고 그것이 검수 승인될 때. 두 경우 모두 **정산액을 다시 계산해 갱신**한다(§3-4). 그래야 「확인 모달만 띄우고 어긋남은 그대로 남는」 상태가 되지 않는다 |
| 재계산 기준(위 예외) | **상한은 그 시점의 캠페인 상시가를 다시 읽는다**(옛 상한을 그대로 쓰면 캠페인이 수정된 경우 근거가 낡는다). 계산 후 **감사 칸 2개(영수증 원금액·적용 상한)도 함께 갱신**한다 — 안 하면 §3-4가 요구한 「왜 1,500엔인가」 설명이 그 순간부터 거짓 근거를 표시한다 |
| 상태 이름 | 내부 사유 이름은 **「금액 미확정」**, 관리자 화면 표시 라벨은 **「금액 확인 필요」** 로 쓴다(같은 상태의 두 이름) |

「금액 미확정」은 **이미 만들어진 구조를 그대로 재사용**한다 — 262가 `amount_issue` 있는 건을 저장 대상에서 빼도록 만들어 뒀고(`CHECK (amount_jpy > 0)` 때문에 한 건이 배치 전체를 죽이는 사고 방지), 264가 죽은 분기를 정리해 뒀다. **이번엔 사유 종류만 늘린다.**

### 3-2. 데이터베이스 변경 (마이그레이션 **4개**, 상대 순서 고정)

> 초안은 2개였다. 실제로는 ③영수증 신규 제출 차단(§3-4 ★)과 ④영수증 사후 수정 가드·재계산(§3-4)이 각각 데이터베이스 변경을 필요로 해 4개가 됐다. ①②는 1단계, ③은 1단계, ④는 2단계 범위.

> 번호는 개발 세션이 파일 생성 시점에 확정하고 「구현 결과」에 사후 기록한다.

**① `settlements` 확장 (먼저)**
- `amount_source` 허용값에 영수증 기준 값 1종 추가(261의 제약을 넓힘)
- 감사용 칸 2개 추가(영수증 원금액 · 적용된 상한) — 「왜 1,500엔인가」를 관리자가 화면에서 바로 설명할 수 있어야 한다. 기존 행은 비어 있어도 됨

**② 헬퍼·함수 재정의 (한 파일·한 트랜잭션)**
- **베이스 확인 의무** — 헬퍼는 **264**, 나머지 3개는 **262**. 착수 전 `grep -rl "_settlement_cert_candidates\|backfill_settlements" supabase/migrations/` 로 전수 재확인
- ⚠️ **242의 알림 잠금 게이트는 `backfill_settlements()` 한 곳에만 있다**(§1-1 표). 조회 함수와 수동 등록 함수는 원래 알림을 내보내지 않으므로 **게이트를 새로 넣지 않는다** — 없는 것을 넣으려다 262 사고를 반대 방향으로 반복하지 않도록 주의
- `receipt_latest` 가 **가져오는 항목에 `purchase_amount` 를 추가**한다
- 금액 계산 CASE 문에 상한 적용 분기 추가
- ⚠️ **인증 성공 판정의 결과값(`is_success`·`cert_at`)이 달라지지 않아야 한다** — 최신 영수증을 고르는 조건(`DISTINCT ON` · `ORDER BY`)과 승인 여부 판정식은 그대로 두고, **가져오는 항목만 늘린다.** 화면 `computeCertStatus` 와의 단일 소스 유지가 목적이다. 검증은 §5-1의 「인증 성공 집계 영향 없음」으로 확인한다
- 「금액 미확정」으로 보내는 **조건 3종** 추가 — ㉮영수증 금액 없음·0 이하 ㉯상한(캠페인 상시가) 없음·0 이하 ㉰**버림 결과가 0 이하**. ⚠️ ㉰을 빠뜨리면 0.5엔 같은 값이 저장 대상이 되어 `CHECK (amount_jpy > 0)` 위반으로 **배치 전체가 죽는다**. 화면에 보여줄 사유 라벨은 2종(금액 없음 / 상한 없음)으로 묶어도 되지만, **판정 조건은 반드시 3개**다
- 반환 항목이 늘어나므로 **삭제 후 재생성** + 호출 함수 3개 함께 재정의

**변경하지 않는 것:** 인증 성공 판정식, 정산 도입일, 송금완료·보류·취소·보류해제, 노출 잠금, 권한 체계, 자동 보류·반려 차단·삭제 차단.

(바) 다국어 열쇠말에는 **전체형·축약형 2종을 모두** 등록한다(위 표의 값이 곧 열쇠말 값이다).

⚠️ **(사) 영수증 입력 안내와 (자) 자주 묻는 질문의 문안은 이 표에 없다.** 두 항목은 짧은 라벨이 아니라 여러 문장 안내라, **요건만 여기서 정하고 실제 문안은 해당 단계 착수 시 한국어·일본어로 확정**한다. (사)의 요건 = ①여기 적은 금액이 그대로 송금된다 ②상시가를 넘으면 상시가까지만 지급된다 ③쿠폰·적립금을 쓰면 그만큼 적게 받는다 ④제출 전에 영수증과 숫자를 다시 확인한다. 초등학생 눈높이·번호 단계.

두 문안은 **표현 길이만 다르고 의미와 상한 금액은 같아야 한다.** 검증 기준도 「글자가 같은지」가 아니라 **「의미와 상한 금액이 같은지」** 로 본다(§5-1).

### 3-4. 관리자 화면 보강 (필수 — 검수가 곧 돈 판정이 되므로)

- **정산 목록·검수 모달에 상한 적용 표시** — 「영수증 2,300엔 → 상한 적용 2,000엔 지급」처럼 원금액과 잘린 사실을 함께 보여준다(사용자 명시 요구). 저장 시 영수증 원금액을 감사 칸에 남긴다
- **영수증 검수 모달에 경고** — 「이 금액이 정산 지급액이 됩니다」 + 영수증 사진과 숫자 대조 안내
- **영수증 금액 사후 수정 가드**(관리자 경로) — 그 응모에 정산 행이 있으면:
  - **송금완료·보류·취소 상태 → 수정 차단**(반려 차단 트리거 247과 같은 사고방식)
  - **정산대기 상태 → 확인 모달 + 이력 기록 + 정산액 재계산 갱신**(§3-1 스냅샷 예외). 확인 모달만 띄우고 금액을 그대로 두면 **어긋남이 「조용히」에서 「알린 뒤에」로 바뀔 뿐 통로가 닫히지 않는다**
- ★ **영수증 신규 제출 가드**(인플루언서 경로 — §2-1 ④의 나머지 절반) — 영수증은 재제출할 때마다 **새 행이 쌓이고**(§1-3), 정산 행이 생긴 뒤 새 행이 들어오면 최신 영수증이 **검수 전(pending)** 행으로 바뀐다. 그러면 인증 성공 판정과 저장된 정산 금액이 **서로 다른 행을 근거로 삼게 되어** §3-1의 「판정·금액 단일 소스」가 깨진다.
  - **송금완료·보류 정산이 있는 응모 → 영수증 신규 제출 차단**(인플루언서 화면에 사유 안내)
  - ⚠️ **취소(cancelled)는 막지 않는다**(2026-08-05 결정 — 초안은 관리자 수정 가드와 같은 3종 집합이었으나 뺐다). 두 가드는 목적이 다르다 — 관리자 금액 수정 차단은 「확정된 금전 기록이 흔들리는 것」을 막는 것이라 취소분에도 타당하지만, 영수증 제출 차단은 「정산 금액과 영수증이 어긋나는 것」을 막는 것이고 **취소된 정산은 지급 자체를 안 하므로 어긋날 금액이 없다.** 결정적 이유는 **취소가 되돌아올 길이 없는 종료 상태**라는 것 — 「보류 해제」는 보류에서만 되돌리고, 관리자 화면에도 취소 행에는 처리 버튼이 없으며, 금전 이력 보호 장치 때문에 정산행 삭제도 사실상 불가능하다. 여기에 영수증 제출까지 막으면 그 응모는 **영구히 새 영수증을 못 내는 상태로 굳는다**
  - **정산대기 정산이 있는 응모 → 제출은 허용하되 관리자 화면에 「정산 후 영수증이 다시 제출됨」 경고**. 검수 결과에 따라 정산액을 다시 계산한다(위 재계산 규칙과 동일)
  - ⚠️ 이 가드는 **서버에서 막아야 한다**(화면 차단만으로는 우회 가능). 구현 위치는 개발 단계에서 확정하고 「구현 결과」에 기록한다
  - **단계 배정**: 서버 차단은 **1단계**(서버 규칙과 함께), 인플루언서 화면의 사유 안내는 **2.5단계**, 관리자 화면 경고는 **2단계**
- **엑셀** — 영수증 원금액·적용 상한 열 추가

### 3-5. 적용 범위·시점

- **적용 대상: 리뷰어형 전체**(진행 중 캠페인 포함). 캠페인 단위 규칙 칸을 두지 않으므로 `campaigns` 표 변경이 없다
- **시점: 배포 즉시.** 근거 = **화면 문구를 그대로 두면 지키지 못할 약속을 계속하게 된다.** (「실무가 이미 영수증 기준」이라는 근거는 리뷰어형 94% 수준이라 단독으로는 약하므로 보조 근거로만 쓴다)
- **과거 미등록 후보도 영수증 기준으로 처리**(§4 4단계)
- ⚠️ **4단계 이후 새로 인증 성공하는 건은 계속 수동 처리다.** 정산 도입일(`cutoff_at`)이 비어 있어 자동 등록이 0건이고(§1-5), 이 작업은 **도입일을 설정하지 않는다**(§3-2 「변경하지 않는 것」). 즉 704건 중 아직 인증 성공 전인 건들이 나중에 후보로 편입돼도 관리자가 「과거 미등록」 화면에서 손으로 처리해야 한다. **도입일을 켜서 자동 등록으로 넘기는 것은 이 작업 범위 밖**이며, 인플루언서 노출 잠금 해제와 함께 별도로 판단한다
- ⚠️ **약관과의 관계** — 시행일 3층(`release-timing.md`)에서 「집행」에 해당하는 것은 **화면 문구 교체와 새 기준 지급** 둘 다이고, 이 문서는 그 시점을 **배포 즉시**로 정했다. 그런데 §3-6은 **화면 약속 대비로는 불리한 변경**이라 사전 통지가 필요할 수 있다고 본다. **이 둘이 부딪히면 법률 확인 결과가 우선한다** — 즉 5단계(약관·법률 확인)에서 「사전 통지 필요」로 결론이 나면, **3·4단계의 배포 시점을 통지 기간 이후로 미룬다.** 이 조건은 §4 단계 표의 의존 관계에 반영돼 있다

### 3-6. 약관 (단정하지 않음 — 확인 항목)

- **제2조 6항** 「모니터형 = 所定金額の報酬」 → 실결제액 기준(상한 있음)으로 정의 손질 필요
- **제13조**에 페이백 유형(구매 대금 환급) 명시 + 금액 기준(영수증 최종 결제 금액) 한 줄
- 유리/불리 판정: **지급 실무 대비로는 정정**이지만 **화면 약속 대비로는 불리한 변경**이다(§요약의 두 층). → **사전 통지(7일 이상) 필요 여부와 재동의 필요 여부를 함께 변호사에게 확인**한다. 이 문서는 어느 쪽도 미리 확정하지 않는다(§6 미결)
- **일정 처리**: 통지가 필요하다고 나오면 3·4단계는 **정의상 밀린다.** 지연 폭을 줄이려면 **5단계(법률 확인·약관 초안)를 1단계와 동시에 착수**한다. 통지 기간은 확인 결과에 따라 정해지므로, 확인이 끝나는 즉시 §4 표에 실제 일수를 적어 3·4단계의 최단 착수일을 계산한다
- ⚠️ **「재동의 필요」로 결론이 나면 이 사양서의 일정은 성립하지 않는다.** 재동의는 통지보다 작업량·기간이 훨씬 크고, 「몇 명이 동의해야 3·4단계를 열 수 있는가」를 이 문서가 정하지 않았다. 그 경우 **별도 사양서로 분리**한다
- 세무: 실비 환급과 보수는 일본 세무상 취급이 다를 수 있다 — **세무사 확인 항목**(7-23 §3-5 이월)

**핵심 의존:** 1 → 2 → (게이트) → 2.5 → 3 → 4.

⚠️ **2.5단계도 3단계와 같은 법률 게이트에 건다.** (사) 안내의 요건 ①②③은 「지급 기준이 이렇게 바뀐다」를 인플루언서에게 알리는 내용 그 자체라, 통지 절차 전에 먼저 띄우면 **문서가 세운 게이트를 문서 자신이 우회**하게 된다. 게다가 그 시점에 캠페인 상세·하단 바·카드는 아직 옛 문구(고정 금액 약속)라, **같은 사람에게 서로 반대되는 두 약속이 동시에 뜬다.**

**5의 법률 확인 결과가 2.5·3·4의 배포 시점을 정한다** — 사전 통지 불필요로 나오면 즉시, 필요로 나오면 **통지 기간이 지난 뒤**.

**배포 순서:** 운영은 반드시 **마이그레이션 → 조회로 검증 → 코드**. 새 칸을 읽는 코드가 먼저 나가면 조회가 거부되어 화면이 **오류 없이 「0건」으로 비어 보인다**(261 사례).

**동시 작업 주의:** `dev/js/admin.js` 는 2단계가 단독으로 건드린다((라) 이동 후 3단계에는 이 파일을 만지는 항목이 없다). 충돌 상습 파일이므로 **다른 세션이 같은 파일을 만지는 작업과 겹치지 않게** 하고, 2단계 착수 직전 최신 내용을 다시 읽는다.

⚠️ **3단계가 통지 대기로 밀리는 동안 생기는 어긋남**

**홍보 메일((마))이 옛 문구로 계속 발송된다** — 주 2회 자동 발송이라 대기 기간 내내 「¥2,000 円ペイバック」을 약속한다. 대기가 길어지면 **그 기간 홍보 메일 발송을 잠글지** 판단한다(§6 미결에 포함).

(관리자 미리보기((라))는 2026-08-05에 3단계로 되돌려 (가)와 함께 나가므로, 미리보기와 실제 화면이 어긋나는 구간은 생기지 않는다.)

## 5. 검증 계획

### 5-1. 개발서버

리뷰어형 인증 성공 건을 **일부러 만들어** 확인:
- 영수증 = 상시가 → 그대로
- 영수증 < 상시가 → 영수증 금액
- 영수증 > 상시가 → **상한으로 잘림** + 관리자 화면에 원금액·상한 적용 표시
- 영수증 금액 비움 → **오류 없이** 「금액 확인 필요」로만 잡힘(배치 전체 실패 없음)
- 상시가 0 → 마찬가지
- 정산 생성 후 **관리자가 금액 수정** → **송금완료·보류·취소는 차단** / **정산대기는 확인 모달 후 정산액이 실제로 갱신되는지**
- 정산 생성 후 **인플루언서가 영수증 신규 제출** → ①송금완료·보류 정산이 있으면 **서버에서 막히는지**(화면만이 아니라 서버) ②**취소 정산이 있으면 정상 제출되는지**(막히면 잘못된 것) ③정산대기 정산이 있으면 제출은 되고 **관리자 화면에 경고가 뜨는지** ④그 새 영수증을 승인하면 **정산액이 다시 계산되는지**
- 시딩·방문형 → **기존 동작 그대로**(회귀 확인)
- 문구(**3단계 배포 시점에 수행** — 2단계 시점에는 관리자 미리보기만 바뀌어 있어 반드시 실패한다. §4 경고 2): 상세 배지·하단 바·카드·관리자 미리보기 + **홍보 메일 본문**이 **의미와 상한 금액이 같은지**(글자 일치가 아니라 — 전체형·축약형 2종을 쓰기 때문) + **480px에서 안 잘리는지**(브라우저 실측). ⚠️ 홍보 메일은 **개발서버에서 실제 발송하지 않는다**(프로젝트 규칙) — 템플릿 파일과 대상 산출까지만 확인하고, 본문 확인은 운영 적용 후 수동 호출로 한다
- 언어 전환(일본어↔한국어) 즉시 반영
- `campaign_manager` 계정으로 정산 화면·조회가 **여전히 차단**되는지
- **인증 성공 집계·결과물 검수·운영현황 진행바에 영향 없음** — §3-2 ②의 「판정 결과값 불변」을 실제로 확인하는 검증이다
