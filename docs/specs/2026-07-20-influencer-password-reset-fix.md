# 인플루언서 비밀번호 찾기 정상화

**작성일:** 2026-07-20 · **상태:** 기획 초안 (구현 미착수)
**관련 사양서:** [`2026-07-20-admin-invite-mail-and-setpw.md`](2026-07-20-admin-invite-mail-and-setpw.md) (관리자 건 — 같은 원인, 먼저 해결됨)

## 0. 한 줄 요약

인플루언서 비밀번호 찾기는 **세 가지 결함이 겹쳐 사실상 동작하지 않는다.** 관리자 건에서 검증된 「메일 링크를 우리 페이지의 `#` 뒤에 담는다」 원리는 그대로 쓰되, **인플루언서는 메일을 Supabase가 직접 보내므로 우리가 링크 문자열을 만들 수 없다** — 그래서 해법이 관리자와 달라진다. Supabase 메일 서식(템플릿)에서 **일회용 토큰 값만** 받아 우리 앱이 직접 검증하는 방식을 권고한다.

## 1. 현재 상태 (규칙 A — 직접 읽고 확인)

### 1-1. 운영 실측 (사용자 제공, 추측 아님)

감사용 계정(`mtact@jfun.co.kr`)으로 운영에서 비밀번호 찾기 → 메일 버튼 추적 결과:

```
메일 버튼 = https://baghdiag.r.bh.d.sendibt3.com/tr/cl/...      (Brevo 클릭 추적)
   ↓ 가리키는 원본
https://nrwtujmlbktxjgdwlpjj.supabase.co/auth/v1/verify
  ?token=pkce_68162db1...           ← ① 브라우저 종속 토큰
  &type=recovery
  &redirect_to=https%3A%2F%2Fwww.globalreverb.com%2F%23   ← ② `#` 뒤가 통째로 잘림
```

### 1-3. 관련 메일 서식(템플릿)

- `docs/email-templates/reset-password.html` — 일본어 원본이 레포에 **있으나 운영 대시보드에 미적용**. `{{ .ConfirmationURL }}` 을 그대로 버튼에 넣는 구조. 현재 운영은 Supabase 기본 영문 서식으로 나가는 것으로 추정.
- Supabase 메일 서식은 **대시보드 수동 설정이라 레포에 기록되지 않는다**(`.claude/rules/supabase.md`). 개발·운영 각각 적용 필요.

| `supabase/functions/notify-admin-invite`·`admin-password-reset-request` | △ 「자체 발송」안(ⓒ)을 고를 때만. 권고안에서는 미사용 |

### 1-5. `resetPasswordForEmail` 호출부는 이제 인플루언서 1곳뿐 (중요)

`dev/` 전체 검색 결과 호출부는 `auth.js:208` **하나**다. 관리자 초대·재발송·찾기는 2026-07-20 개편으로 서버 발급(`generateLink`) + 자체 발송으로 옮겨갔다(`admin-accounts.js`, `storage.js` 주석에 사유 명시).

→ **Supabase 「Reset password」 메일 서식은 현재 인플루언서 전용이다.** 서식을 바꿔도 관리자 흐름에 영향이 없다. (관리자 건과 서식을 공유하던 제약이 이미 풀려 있다 — 본 사양의 전제 조건.)

### 1-6. 이 제안과 충돌 가능성 있는 기존 동작

1. **`app.js` 의 재설정 감지 3중 장치**(`detectRecoveryUrlEarly` / 초기 라우팅 건너뛰기 / `PASSWORD_RECOVERY` 이벤트)는 **`?code=`·`access_token=`·`type=recovery`** 를 전제로 짜여 있다. 새 방식의 주소에는 이 표식이 하나도 없어 **그대로 두면 새 링크가 홈 화면으로 떨어진다.**
2. **회원가입 확인 메일**도 같은 감지 로직 근처를 지난다(`?code=` 는 가입 확인에서도 쓰임). 감지 조건을 「고치는」 게 아니라 **새 분기를 추가**해야 한다.
3. **수신거부**(`#unsubscribe?token=`)가 이미 같은 모양의 주소를 쓴다 — 파싱을 새로 발명하지 말고 이 선례를 복제할 것.
4. **운영 apex→www 307 넘김** — 메모리 `feedback_prod_curl_follow_redirect`. `globalreverb.com` → `www.globalreverb.com` 으로 넘어갈 때 주소의 `#` 뒷부분이 유지되는지가 새 방식의 생사를 가른다(§3-①).
5. **Supabase 링크 만료 시간**은 인플루언서·관리자 **공용 설정**이다(관리자 사양서 미해결 항목). 한쪽만 늘릴 수 없다.

### 1-7. 미해결 백로그

- 관리자 사양서 §미해결 — 「Email OTP Expiration」 상향 보류 중(인플루언서에도 함께 적용되는 값이라 판단 대기). **본 사양이 그 판단 시점**이다.
- 관리자 사양서 §부수 사항 — `resetPwNew`·`resetPwError` 라는 같은 이름 요소가 인플루언서 페이지와 관리자 모달에 중복. 본 사양은 인플루언서 페이지만 건드리므로 새 충돌은 없음.

## 2. 결함 3가지의 정확한 정체

| 결함 | 관측 | 원인 | 결과 |
|---|---|---|---|
| **①** | 토큰이 `pkce_` 로 시작 | 앱 클라이언트가 `flowType:'pkce'`(`supabase.js:38`) → `resetPasswordForEmail` 이 **교환 검증값을 요청한 브라우저에만** 저장 | PC에서 요청하고 **폰에서 메일을 열면 실패**. 인플루언서는 폰으로 메일을 보는 비율이 높아 실패율이 높을 것으로 의심 |
| **②** | `redirect_to` 가 `.../#` 로 끝남 | 우리는 `/#reset-pw` 를 넘겼는데 `#` 뒤가 사라짐. Supabase가 되돌아갈 주소를 허용목록과 대조·정규화하는 과정에서 `#` 뒷부분이 유실되는 것으로 보임(정확한 단계는 미확정) | 착지해도 **앱이 어느 화면을 열지 모른다** → 홈/가입 화면이 뜨는 증상의 유력 원인 |
| **③** | 버튼이 Brevo 추적 주소 | Brevo는 **트랜잭션 메일의 클릭 추적을 끄는 옵션을 제공하지 않는다**(공식 커뮤니티 확인, `X-Mailin-Track` 헤더 무효 — 관리자 건에서 시도 후 제거) | 1회용 링크를 **추적 서버·메일 스캐너가 사람보다 먼저 열면 소모**된다 → 「만료된 링크」 |

**세 결함은 서로를 가린다.** ①만 고치면 ②로 홈에 떨어지고, ②만 고치면 ①로 폰에서 실패하고, ①②를 고쳐도 ③으로 일부가 만료된다. **한 번에 셋 다 없어지는 설계**여야 한다.

> ②의 정확한 유실 지점은 확정하지 않았다. 권고안(ⓐ)은 **되돌아갈 주소 기능 자체를 쓰지 않으므로** 원인 규명 없이도 문제가 사라진다. 다른 안을 고를 경우에만 규명이 필요하다.

## 3. 의심·경우의 수 (규칙 B)

### 3-1. 깨질 가능성 (기술 3 · UX 3 · 데이터/운영 2)

**① [기술 — 가장 위험] `#` 뒷부분이 중간 경유지에서 사라질 수 있다**

새 방식은 「일회용 값을 주소의 `#` 뒤에 담는다」에 전적으로 의존한다. 그런데 인플루언서 메일은 최소 두 번 경유한다:

```
메일 버튼 → Brevo 추적 서버(302) → globalreverb.com(apex) → 307 → www.globalreverb.com
```

`#` 뒷부분은 **넘김(redirect) 대상 주소에 자체 `#` 이 없을 때만** 브라우저가 이어서 붙여준다. 경유지 중 하나라도 `#` 붙은 주소로 넘기면 **값이 통째로 사라지고 전원이 실패한다.**

- 관리자 건은 같은 원리로 운영 배포됐으나, **관리자는 apex→www 넘김을 안 타는 경로**(`PUBLIC_ADMIN_URL` 직접 지정)일 수 있어 **인플루언서에서 그대로 성립한다고 단정할 수 없다.**
- **대응(필수):** PR 1 배포 직후, 운영에서 **감사용 계정으로 실제 메일 1통을 받아 폰에서 눌러** 값이 살아 도착하는지 먼저 확인한다. 실패하면 Site URL을 `www` 형태로 맞춰 넘김 단계를 없앤다(단 Site URL 변경은 다른 메일·되돌아갈 주소에도 영향 → 별도 확인 필요).

**② [기술] Supabase 메일 서식이 제공하는 값의 실재 여부**

권고안은 서식 변수 `{{ .TokenHash }}` 를 쓴다. 공식 문서상 확인 메일 계열에서 제공되지만, **우리 프로젝트의 현재 버전에서 실제로 값이 채워지는지는 실측 전까지 확정이 아니다.** 빈 값이면 링크가 통째로 무의미해진다.
→ **개발서버에서 서식 적용 후 메일 1통을 실제로 받아 눈으로 확인**하는 단계를 PR에 못 박는다(보내지 않고는 검증 불가능한 항목).

**③ [기술] 요청을 보낸 클라이언트가 여전히 브라우저 종속 방식이면 ①이 안 고쳐진다**

`{{ .TokenHash }}` 를 쓰더라도, 요청을 `flowType:'pkce'` 클라이언트로 보내면 발급되는 값이 여전히 `pkce_` 계열이라 **다른 기기에서 검증할 수 없다.** 즉 서식만 바꾸는 것으로는 부족하고 **요청 쪽도 반드시 함께 바꿔야 한다.** (이 조합 누락이 가장 나기 쉬운 반쪽 수정.)

**④ [UX — 필수] 「계속하기」 한 단계 추가가 인플루언서를 떨군다**

관리자 페이지는 「이 한 단계가 있는 이유」를 한국어로 길게 설명해도 실무자가 읽는다. 인플루언서는 **일본어·초등학생 눈높이**가 기준이고(`ui.md`), 폰에서 메일 앱 → 브라우저로 넘어온 직후라 인내심이 가장 낮은 지점이다. 버튼 하나가 더 있으면 「고장인가?」로 읽힐 수 있다.
- **권고안은 이 단계를 두지 않는다.** 새 방식의 값은 **사람이 누르지 않으면 소모되지 않는 형태**(브라우저에서 자바스크립트가 돌아야 검증이 일어남)라, 추적 서버·스캐너가 주소를 열어도 소모되지 않기 때문이다. 관리자 건에 「계속하기」가 필요했던 이유(주소를 여는 것만으로 소모되는 형태)가 여기선 사라진다.
- **남는 위험:** 일부 기업용 메일 보안 장비는 실제 브라우저처럼 자바스크립트까지 실행해 미리 열어본다. 그런 계정에서는 여전히 만료가 날 수 있다 → **만료 화면에서 곧바로 재요청할 수 있게** 하는 것이 안전망(§4-4).

**⑤ [UX] 「이미 못 바꾸고 있던 사람들」에게 알릴 것인가**

이 기능은 **언제부터 고장이었는지 모른다.** 그동안 재설정을 시도했다 실패한 인플루언서는 ⓐ재시도를 포기했거나 ⓑ LINE으로 문의했을 것이다. 고쳐놓고 아무 말도 안 하면 그 사람들은 **여전히 고장인 줄 안다.**
- 반대로 「지금까지 고장이었습니다」를 전체 공지하면 **불안·신뢰 손상**이 크고, 재설정 요청이 한꺼번에 몰려 Supabase 메일 시간당 한도(운영 100통/시간)를 칠 수 있다.
- 선택지는 §7 Q3.

**⑥ [UX] 만료 화면에서 다시 요청할 때 이메일을 또 쳐야 한다**

현재 만료 감지는 `#forgot` 으로 보내기만 한다(`app.js:376-382`). 폰에서 이메일 주소를 다시 입력하는 것은 이탈 지점이다. 새 방식에서는 만료 시 **주소를 아는 경우가 없으므로**(값만 있고 이메일은 없음) 자동 채움이 불가능하다 → 안내 문구로 보완해야 한다.

**⑦ [데이터·운영] 링크 수명 설정이 관리자와 공용**

만료를 늘리면(예: 1시간 → 24시간) **관리자 초대·관리자 찾기 링크 수명도 같이 늘어난다.** 관리자 사양서에서 이 이유로 보류된 항목이다. 인플루언서 편의(폰에서 나중에 열어봄)와 관리자 보안(초대 링크가 오래 살아있음)이 정면으로 맞선다.

**⑧ [운영] 전환 구간에 두 종류의 링크가 동시에 떠 있다**

메일 서식을 바꾸는 순간부터 **새 형식**이 나가지만, 그 직전에 발송된 **옛 형식** 메일이 사용자 받은편지함에 남아 있다. 옛 형식 착지 경로를 지우면 그 사람들은 실패한다.
→ **옛 경로 코드를 지우지 않고 그대로 둔다**(§5 회귀 경계). 만료 시간(최대 1시간, 상향 시 그만큼)이 지나면 자연 소멸하므로, 실제 제거는 한참 뒤 별도 정리 작업.

### 3-2. 현재 구현과 충돌하는 지점

| 충돌 | 내용 | 처리 |
|---|---|---|
| **충돌 있음** | `app.js` 초기 라우팅이 새 형식 주소(`#reset-pw?…`)를 인식하지 못해 홈으로 떨어진다 | `#unsubscribe?token=` 선례를 그대로 복제해 **새 분기 추가**(기존 분기 수정 아님) |
| **충돌 있음** | 앱 전역 클라이언트가 브라우저 종속 방식(`flowType:'pkce'`)이라 요청 방식을 바꿔야 한다 | **전역 설정을 바꾸지 않는다.** 비밀번호 찾기 요청 전용 보조 클라이언트를 따로 만든다(§4-2) |
| 충돌 없음 — 확인 완료 | 관리자 흐름(`generateLink` + 자체 발송)은 Supabase 메일 서식을 쓰지 않는다(§1-5) | 서식 변경이 관리자에 영향 없음 |
| 충돌 없음 — 확인 완료 | 회원가입 확인 메일은 별도 서식이며 본 사양은 손대지 않는다 | — |
| 충돌 없음 — 확인 완료 | 수신거부(`#unsubscribe`)·홍보 메일 클릭 추적은 별개 경로 | — |

### 3-3. 사용자 의도가 다르게 해석될 수 있는 부분

1. **「고친다」의 범위** — ⓐ비밀번호 찾기만인지 ⓑ회원가입 확인 메일 서식까지인지. 회원가입 확인도 지금 **영문 기본 서식**일 가능성이 높다(레포의 일본어 서식이 미적용 상태와 동일 사유). 본 사양은 **비밀번호 찾기만** 범위로 잡았다.
2. **「착지 화면」** — 기존 `#page-reset-pw`(일본어·모바일·다국어)를 살리는 것과, 관리자처럼 자립형 페이지를 새로 만드는 것 중 어느 쪽을 상정했는지 불명확 → §4-3 에서 비교하고 **기존 화면 재사용**을 권고.
3. **「검증」** — 개발서버에서 테스트 인플루언서 계정으로 실제 메일을 받아보는 것을 허용하는지, 운영 감사용 계정만 쓰는지. `supabase.md` 의 발송 테스트 금지는 **대량·마케팅 메일 대상**이고 트랜잭션 메일은 별도 판단이라, 해석이 갈린다 → §7 Q4.

**ⓑ 비권고 결정적 이유:** 확인 주소를 서식 안에서 `#` 뒤에 담으려면 주소를 통째로 감싸야 하는데, Supabase 메일 서식에는 그 처리를 해 줄 수단이 없다. 게다가 ①을 없애려면 **앱 전역 인증 방식**을 바꿔야 해서, 비밀번호 찾기 하나 고치자고 로그인·세션 유지 전체를 위험에 빠뜨린다.

**ⓒ 비권고 결정적 이유:** 관리자는 대상이 소수라 「비로그인으로 메일을 유발하는 공개 경로」의 위험을 요청 제한으로 눌렀다. 인플루언서는 **정상 이용자 수가 40배**라 같은 임계값을 못 쓰고, 임계값을 풀면 방어가 헐거워진다. 무엇보다 **Supabase Auth 자체 메일 한도라는 공짜 방패를 스스로 버리는** 선택이다. 얻는 것은 「메일 문구를 우리가 관리」 하나인데, 그건 대시보드 서식으로도 (기록성만 빼면) 동일하게 얻는다.

> **권고: ⓐ.** 결함 셋이 한 번에 사라지고, 데이터베이스 변경 0건·새 공개 경로 0건이며, 실패해도 서식을 되돌리는 것으로 원복된다.

### 4-2. ⓐ 상세 설계

#### 흐름

```
인플루언서: 「パスワードをお忘れですか」 → 이메일 입력
   ↓  (보조 클라이언트로 요청 — 브라우저 종속 방식 아님)
Supabase Auth 가 메일 발송 (서식 = 우리가 대시보드에 넣은 일본어 서식)
   ↓  메일 버튼 = https://{사이트 주소}/#reset-pw?<일회용 값>
   ↓  (값이 `#` 뒤 → 추적 서버·스캐너의 열람으로 소모되지 않음)
인플루언서 앱 착지 → 새 라우팅 분기가 값 인식
   ↓  앱이 그 값으로 직접 검증 (브라우저 자바스크립트에서 실행 — 여기서 처음 소모)
성공 → 기존 #page-reset-pw 폼 표시 → 기존 handleResetPassword 그대로
실패 → 「링크 만료」 안내 + 재요청 버튼
```

#### 바꾸는 것 3가지 (이 셋이 한 세트여야 동작)

| # | 대상 | 변경 |
|---|---|---|
| **1** | `dev/lib/supabase.js` | **비밀번호 찾기 요청 전용 보조 클라이언트 추가.** 전역 클라이언트(`db`)는 **그대로 둔다.** 보조 클라이언트는 브라우저 종속 방식을 끄고, 세션을 저장하지 않으며, 저장 칸 이름을 달리해 전역 세션과 섞이지 않게 한다 |
| **2** | `dev/js/auth.js:207-208` | `resetPasswordForEmail` 호출을 보조 클라이언트로 교체. **되돌아갈 주소 지정은 제거**(서식이 주소를 만들므로 불필요 — 결함 ② 원천 제거) |
| **3** | Supabase 대시보드 「Reset password」 서식 | `docs/email-templates/reset-password.html` 을 기반으로, 버튼 주소를 **우리 앱 주소 + `#` 뒤 일회용 값** 형태로 교체. 개발·운영 **각각 수동 적용** |

#### 착지 처리 (`dev/js/app.js`)

`#unsubscribe?token=` 선례를 **그대로** 복제한다:

- `navigate()` 의 해시 파싱에 새 형식 인식 1줄 추가 (`app.js:41-44` 옆)
- 초기 라우팅 분기 추가 (`app.js:413-417` 옆) — 값을 꺼내 검증 함수 호출
- 첫 화면 결정에 새 형식 대응 (`app.js:459-465`)
- **검증 호출 직전에 `sessionStorage['reverb.recovery']='1'` 을 세운다** — 그러면 「재설정 중에는 로그인 상태로 취급하지 않음」(`app.js:286-290`)과 「재설정 중 로그인 신호가 와도 재설정 화면으로 유도」(`app.js:333-340`) 라는 **기존 안전장치가 그대로 작동한다.** 새로 만들지 않고 있는 것을 재사용하는 것이 요점 — 검증에 성공하면 진짜 로그인 상태가 되므로, 이 플래그가 없으면 **비밀번호를 안 바꾸고 이탈해도 로그인된 채로 남는다.**
- 완료 처리는 기존 `handleResetPassword`(플래그 제거 + `signOut()`)를 **한 줄도 안 고치고** 그대로 쓴다

### 4-3. 착지 화면을 어디에 둘 것인가

| 후보 | 판정 |
|---|---|
| **기존 `#page-reset-pw` 재사용 (권고)** | 일본어·480px·다국어 키가 이미 붙어 있고, 완료 후 로그인 화면 이동·토스트까지 동작한다. 만료 상태 표시만 추가하면 된다 |
| 인플루언서 앱에 새 페이지 신설 | 같은 화면이 둘이 되고 다국어 키가 갈라진다. 이득 없음 |
| 관리자처럼 자립형 정적 페이지 | **비권고** — 관리자가 자립형이 된 이유는 「관리자 앱에 로그인 전 화면이 존재할 수 없어서」다. 인플루언서 앱은 **비로그인 화면이 이미 정상 자산**(로그인·가입·수신거부). 자립형으로 빼면 접속 주소·다국어·모바일 껍데기 규칙을 전부 복제해야 하고, 화면 스타일 값이 둘로 갈라진다(관리자 페이지가 지금 겪는 부담) |

**다국어:** 앱 화면은 기존 다국어 구조를 그대로 쓴다(일본어 기본, 개발서버에서 한국어 토글). **메일 본문은 일본어 단일** — 서식은 언어를 분기할 수 없고, 수신자가 인플루언서로 한정되므로 일본어가 맞다.

### 4-4. 만료·무효 시 화면 (UX 안전망)

기존 만료 처리(`app.js:376-382`, 주소에 오류가 실려오면 `#forgot` 이동)는 **새 방식에서 발동하지 않는다**(주소에 오류가 안 실림 — 검증 실패가 앱 안에서 일어남). 새로 만들어야 한다.

`#page-reset-pw` 안에 상태 하나를 추가하고, 문구는 **초등학생 눈높이 일본어·번호 단계**(`ui.md`):

```
このリンクは使えません

1. リンクは受け取ってから しばらくすると 使えなくなります
2. 何回か送った場合は いちばん新しいメールのリンクだけ 使えます
3. 下のボタンから もう一度 送ってください

[ もう一度メールを送る ]  → #forgot 로 이동
```

「최근 것만 유효」를 명시하는 이유: 안 온다고 두세 번 요청한 사람이 **먼저 받은 메일**을 누르면 실패하는데, 이유를 모르면 「시스템 고장」으로 인식한다(관리자 사양서 §의심 ⑦과 동일 구조).

### 4-5. 데이터베이스 변경 — **없음**

새 표·컬럼·접근 정책·트리거·함수 **모두 0개**. 마이그레이션 파일을 만들지 않는다.
(현재 번호는 245까지 사용 — 본 사양에서는 새 번호를 점유하지 않는다.)

4. (Q2에서 상향을 택한 경우) Authentication → **Email OTP Expiration** 값 변경 — ⚠️ **관리자 링크 수명도 함께 바뀜**
5. Redirect URLs 변경 **불필요** — 되돌아갈 주소 기능을 안 쓰므로

> 서식 원본은 `docs/email-templates/reset-password.html` 를 갱신해 레포에도 남긴다(레포가 정본, 대시보드는 사본). **두 곳이 어긋나면 대시보드가 실제로 동작하는 쪽**이라는 점을 파일 상단 주석에 명시할 것.

## 5. 회귀 위험 — 건드리는 것 / 안 건드리는 것 (경계 고정)

### 건드리지 않는다 (불가침)

- `dev/lib/supabase.js` 의 **전역 클라이언트 `db` 설정** — 로그인·세션 유지·회원가입 확인이 전부 여기 얹혀 있다
- `app.js:6-14` `detectRecoveryUrlEarly` **기존 조건** — 회원가입 확인·옛 형식 링크가 공유. **조건을 고치지 않고 새 조건을 추가**만 한다
- `app.js:327-375` `PASSWORD_RECOVERY`·로그인 신호·로그아웃 처리 — 새 흐름은 기존 플래그를 세워 **이 로직을 그대로 타고 간다**
- `auth.js:227-276` `handleResetPassword` — 폼 제출 이후는 완전 동일
- `#page-forgot` 화면·문구 — 만료 화면에서 여기로 보내는 경로만 추가
- 회원가입 확인 메일 서식 · 수신거부 · 홍보 메일 클릭 추적 — 전부 별개 경로
- **관리자 흐름 일체** — `admin-setpw.html`, 관리자용 서버 함수 2개, 마이그레이션 243·244·245

### 건드린다

| 파일 | 변경 |
|---|---|
| `dev/lib/supabase.js` | 보조 클라이언트 **추가**(기존 설정 무변경) |
| `dev/js/auth.js` | `handleForgotPassword` 의 호출 대상·되돌아갈 주소 지정 |
| `dev/js/app.js` | 해시 파싱 1줄 · 초기 라우팅 분기 1개 · 첫 화면 결정 1줄 · 검증 함수 신규 |
| `dev/index.html` | `#page-reset-pw` 안에 만료 상태 블록 추가 |
| `dev/lib/i18n/{ja,ko}.js` | 만료 화면 문구 키 신규 |
| Supabase 대시보드 서식 | 개발·운영 각 1회 (코드 아님) |

### 전환 구간 취급

옛 형식 링크(`?code=`·`type=recovery`)의 착지 경로는 **지우지 않는다.** 서식 교체 전에 발송된 메일이 살아 있기 때문. 링크 수명이 지나면 자연 소멸하며, 코드 제거는 별도 정리 작업(백로그).

### 검증

**PR 1 (배포만으로는 겉보기 변화 없음 — 회귀 확인이 목적)**
1. 인플루언서 로그인·로그아웃·회원가입 정상
2. **옛 형식 재설정 링크가 여전히 동작**(서식 교체 전이므로 지금 받는 메일이 옛 형식) — 착지·변경 성공
3. 새 형식 주소를 **손으로 만들어** 접속 → 값이 엉터리이므로 **만료 화면**이 뜨는지(홈으로 안 떨어지는지)
4. 만료 화면 → 「もう一度メールを送る」 → `#forgot` 이동
5. 폰 폭에서 문구 줄바꿈·입력칸 자동 확대 없음(글자 크기 16 이상)

**PR 2 (실제 메일 발송이 필요 — 감사용 계정 사용)**
1. **개발서버 서식 적용 후** 메일 1통 수신 → 버튼 주소에 **일회용 값이 실제로 채워져 있는지** 눈으로 확인(§3-② 검증)
2. **다른 기기 교차 검증 (가장 중요)** — PC에서 요청하고 **폰에서 메일을 열어** 변경까지 성공. ⚠️ 같은 브라우저의 새 탭·시크릿 창은 **검증이 안 된다**(관리자 사양서 「검증 시 반드시 확인할 것」과 동일 함정)
3. **`#` 뒷부분 생존 확인 (§3-①)** — 폰에서 메일 버튼을 눌렀을 때 최종 주소에 값이 살아 있는지. 실패 시 Site URL 조정 검토
4. 변경 완료 후 **로그인 화면으로 이동하고, 새 비밀번호로 로그인**되는지
5. 변경하지 않고 이탈 → 다시 접속 시 **로그인 상태가 아닌지**(재설정 중 플래그 동작 확인)
6. 같은 계정으로 **연속 2회 요청** → **먼저 받은 메일**의 링크가 만료 화면을 띄우는지 + 문구가 이유를 설명하는지
7. 운영 서식 적용 후 **감사용 계정으로 1~4 재실행**
8. **회귀:** 관리자 초대·관리자 비밀번호 찾기가 여전히 정상(같은 프로젝트의 다른 서식·다른 경로)

**에이전트 호출 의무:** 전 PR `reverb-reviewer` / PR 2 는 인증 흐름 변경이라 `reverb-supabase-expert` **필수** / 운영 배포 전 `reverb-qa-tester` **권장**(로그인·가입 회귀. 브라우저 자원이 하나뿐이라 다른 세션이 안 쓰는지 확인 후 단일 세션에서).
