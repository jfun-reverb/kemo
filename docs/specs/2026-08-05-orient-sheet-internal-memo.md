# 오리엔시트 내부 메모 (관리자 전용)

**작성일:** 2026-08-05
**요청:** 브랜드사 오리엔시트 상세 화면에서 내부 담당자가 메모를 남기고, 브랜드사와 소통한 참고 사항을 시트 내용과 함께 볼 수 있게. 간단한 서식 편집 기능 포함.

### 이 제안과 충돌하는 기존 동작 — **3건 확인됨**

**(1) 시트 데이터(`data jsonb`) 안에 메모를 넣으면 두 가지가 동시에 깨진다**
- 브랜드가 링크로 재제출하면 `submit_orient_sheet`가 `data` 전체를 덮어써 **관리자 메모가 소리 없이 사라진다**
- 브랜드 작성 폼은 `get_orient_sheet`로 `data`를 통째로 읽어가므로 **내부 메모가 브랜드사 화면에 그대로 노출된다**
→ **메모는 반드시 별도 표에 둔다.** 이것은 선택지가 아니라 전제.

**(2) 카드에 안정된 식별자가 없다**
- 브랜드 폼은 카드 생성 시 화면용 임시 번호(`card_1`)만 쓰고 저장 데이터에 넣지 않는다(`addCard` → `collectCard`가 만드는 객체에 식별자 키 없음)
- 카드는 **배열 순서로만** 구분된다. 브랜드가 중간 카드를 지우면(`removeCard`) 뒤 카드가 앞으로 밀린다
- **기존 시스템도 이미 같은 위험을 안고 있다** — 「이 카드로 발행했음」 표시(`mark_orient_card_consumed(시트id, 카드순번, 캠페인id)`)가 순번 기반
→ 카드별 메모는 순번으로 붙이면 안 된다. **카드 고유 번호를 새로 심는다**(확정 결정 ②).

**(3) 새창 출력이 상세 본문을 그대로 재사용한다**
- `osOpenDetailNewWindow()`가 `osDetailHtml(…, readonly=true)`을 그대로 새 창에 그린다. 이 출력물은 인쇄하거나 브랜드사에 화면 공유할 수 있는 성격
→ 메모를 본문에 그냥 얹으면 내부 대화가 브랜드사에 노출된다. **`readonly` 분기에서 메모를 제외**한다.

### 미해결 백로그·관련 작업

- 카드 발행 표시(`mark_orient_card_consumed`)의 순번 기반 참조 — 같은 밀림 위험을 안고 있으나 **이번 범위에서 바꾸지 않는다**(§7 참조)
- 브랜드 서베이 신청 메모의 `product_idx`도 순번 기반. 다만 그쪽은 「제품 순서 변경 기능이 없어 안전」이라고 마이그레이션 주석에 명시돼 있고, 실제로 삭제 기능도 없음 — 오리엔시트와 조건이 다름

## 의심·깨질 수 있는 경우의 수 (규칙 B)

### 기술·데이터

**1. 브랜드 폼이 고유 번호를 실어 나르지 않으면 메모 연결이 통째로 끊긴다** — 최대 위험
`collectData()`가 화면 요소를 읽어 카드 객체를 **새로 만든다**. 고유 번호를 요소에 심고 `collectCard`가 그대로 실어 보내지 않으면, 브랜드가 한 번 저장하는 순간 모든 카드의 고유 번호가 사라지고 메모가 어느 카드에도 안 붙는다.
→ 대응: ①폼이 고유 번호를 보존 ②**서버 저장 함수에 물려주기 안전망**(아래 3) ③1단계를 따로 떼어 브라우저에서 실제 재저장 확인 후에야 2단계 착수

**2. 안전망이 붙기 전에는 옛 폼 저장 한 번으로 번호가 전부 날아간다**
옛 폼은 고유 번호를 아예 안 실어 보낸다. 저장 함수에 물려주기 안전망(아래 3)이 **아직 없는 동안**에 옛 폼이 저장하면, 그 시트의 카드 번호가 통째로 사라진다.
→ 대응: **저장 함수 안전망을 가장 먼저 적용한다**(§6 배포 순서). 안전망이 붙은 뒤에는 옛 폼이 저장해도 **카드 개수가 그대로인 한** 번호가 물려져 유지된다(개수가 달라진 경우는 3번 참조 — 메모가 「삭제된 모집 건」으로 빠진다). 데이터 채우기의 선후는 그 뒤라면 자유롭지만, **폼 배포는 빠를수록 좋다**.

**3. 순서 자리로 물려주는 안전망 — 조용히 틀리지 않게 조건을 좁힌다**
저장 함수가 「들어온 카드에 번호가 없으면 같은 순서 자리의 기존 번호를 물려준다」로 막는다. 단 조건을 좁힌다.

⚠️ **조건 없이 물려주면 조용히 틀린다.** 옛 폼이 카드를 **지운 채** 저장하면 번호가 사라지는 게 아니라 **뒤 카드로 한 칸씩 밀려 붙는다**. 그러면 그 번호는 여전히 「현재 카드 목록에 있는」 번호라서 「삭제된 모집 건의 메모」(§의심 4)에도 안 잡히고, 메모가 **엉뚱한 모집 건 아래에 아무 표시 없이** 나타난다. 가장 나쁜 실패 방식이다.

→ **물려주기 조건: 번호가 없는 카드가 들어왔고, 들어온 카드 개수와 기존 카드 개수가 같을 때만.** 개수가 달라졌으면(추가·삭제) 물려주지 않고 그 빈자리에 새 번호를 부여한다.
※ **번호를 싣고 들어온 카드는 이 판정을 아예 타지 않고 그대로 유지된다**(§설계 1의 1단계). 아래 **첫 세 항목**이 「번호 없이 들어온 카드」에 대한 판정 갈래이고, **뒤 두 항목**은 보충 설명이다(넷째=번호를 싣고 들어온 경우와의 대비, 다섯째=이 안전망의 역할 범위).
- **개수가 같음** = 순서 변경 기능이 없으므로 자리와 카드가 1:1로 대응한다 → 안전하게 물려준다
- **개수가 같은데 기존 카드에도 번호가 없음** = 물려줄 것 자체가 없다 → 그 자리에 새 번호를 부여한다(데이터 채우기 전 구간에서 실제로 생긴다)
- **개수가 다름** = 어느 자리가 밀렸는지 알 수 없다 → 물려주지 않고 새 번호를 부여한다. 옛 폼처럼 **모든 카드가 번호 없이** 들어온 경우 그 시트의 메모는 전부 고아가 되어 **「삭제된 모집 건의 메모」(§의심 4 · §설계 4)에 눈에 보이게 모인다**(내용·작성자·제품명 스냅샷은 그대로 보존). 잘못 붙는 것보다 낫다.
- 새 폼은 번호를 **싣고 되돌려 보내므로** 카드를 지워도 남은 카드가 번호를 갖고 들어온다 → 물려주기 판정 자체를 타지 않고 그대로 유지된다. → **폼 배포가 빠를수록 「전부 고아가 되는」 구간이 짧아진다.**
- 안전망은 **옛 폼 호환용**이며, 카드가 실제로 사라진 뒤의 메모 표시는 「삭제된 모집 건의 메모」가 맡는다(대응 근거 §의심 4 · 화면 규정 §설계 4).

**4. 브랜드가 카드를 지우면 메모가 고아가 된다**
번호가 있어도 그 카드 자체가 사라지면 메모가 가리킬 곳이 없다.
→ 대응: 메모 행은 그대로 두고, 상세 화면 맨 아래 **「삭제된 모집 건의 메모」** 묶음으로 표시. 메모마다 **작성 시점 제품명 스냅샷**을 저장해 어느 건이었는지 알 수 있게 한다.

**5. 붙여넣기로 들어오는 서식**
다른 화면에서 복사해 붙이면 서식 태그가 통째로 들어온다. 관리자가 쓰는 글이지만 저장된 뒤 다른 관리자 화면에서 그려지므로 저장형 위험이 성립한다.
→ 대응: 기존 `sanitizeCautionHtml` 패턴으로 **저장 시 + 표시 시 이중 정화**. 이미지를 안 쓰기로 했으므로 `img` 태그는 아예 차단.

**6. 시트를 지우면 메모도 사라진다**
`delete_orient_sheet`가 시트 행을 지운다. 메모 표가 시트를 참조하면 연쇄 삭제로 함께 사라진다(감사 기록으로 남기지 않기로 확정 — 「확정된 결정」의 파생 결정).
→ 대응: 시트 삭제 함수는 **무수정**(연쇄 삭제에 맡긴다). 대신 삭제 확인 창에 「메모 N개도 함께 삭제됩니다」 경고 한 줄 추가.

**7. 두 관리자가 같은 메모를 동시에 고침**
나중 저장이 앞 저장을 덮는다. 브랜드 서베이 메모도 동일하며 실제 문제가 보고된 적 없다.
→ 대응: **낙관적 락 없이 간다**(마지막 저장 승리). 메모는 짧고 작성자·시각이 남아 되짚을 수 있다. 명시적 결정으로 기록.

### 권한·환경

**8. 열람 등급 — 확정 결정 ④와 다른 축이었으나, 둘 다 「전원」으로 확정됨**
확정 결정 ④는 「남겨진 메모를 **누가 고치고 지울 수 있나**」, 확정 결정 ⑥은 「**어느 등급까지 볼 수 있나**」다. 두 축을 따로 확인했고 **둘 다 관리자 전원**으로 정해졌다(캠페인 매니저 등급 포함).
→ 결과적으로 등급 분기가 없어, 접근 정책이 한 줄로 끝나고 「볼 수 없는 사람이 쓸 수는 있는」 어긋난 조합도 생기지 않는다.
⚠️ 다만 브랜드 소통 메모에는 단가·조건 협의가 들어올 수 있다. 나중에 등급 제한이 필요해지면 **읽기와 쓰기를 함께 좁혀야 한다** — 조회만 막으면 그 등급은 자기가 쓴 메모조차 안 보이는 상태가 된다.

**9. 개발·운영 배포 경로가 둘로 갈린다**
브랜드 작성 폼은 별도 Vercel 프로젝트(`reverb-sales`)로 배포된다. 같은 저장소·같은 커밋이지만 배포 대상이 다르므로, **폼이 실제로 갱신됐는지 브라우저에서 눈으로 확인**해야 한다(코드 머지 ≠ 반영).

### 사용자 경험 (필수)

**10. 상세 모달 폭 560px에 내용이 이미 길다**
메모 영역을 펼친 채로 넣으면 시트 내용을 보려고 스크롤해야 한다.
→ 대응: 카드마다 **기본 접힘 + 개수 배지**, 단 **안 읽은 메모가 있으면 자동 펼침**(있는 줄 모르고 지나치는 것 방지). 이 자동 펼침은 **놓치지 않게 하는 장치**이며, 읽음 처리와는 분리된 축이다(11번).

**11. 메모를 남겼는데 상대가 못 본다**
메모는 알림을 보내지 않는다. 목록의 안 읽은 수 배지가 유일한 신호다.

「보지도 않은 메모가 읽음 처리되는 것」을 「그 카드가 펼쳐졌을 때만 처리」로 막으려 했으나, **안 읽은 메모가 있으면 자동으로 펼쳐지므로 그 조건은 항상 참이 되어 아무것도 걸러내지 못한다.** 헛조건을 두느니 규칙을 단순하게 가져간다.

→ 대응: 배지는 **로그인한 본인 기준 안 읽은 수**. **읽음 처리 단위는 시트** — 상세 모달을 열면 그 시트의 메모(고아 메모 포함)가 전부 읽음 처리된다. 배지의 뜻은 「이 시트에 내가 아직 **열어보지 않은** 새 메모가 있다」이다.
→ **놓치지 않게 하는 장치는 읽음 처리가 아니라 자동 펼침이다**(10번). 안 읽은 메모가 있는 자리는 열자마자 펼쳐진 상태로 보인다.
→ ⚠️ **순서가 핵심이다.** 자동 펼침 판정과 읽음 처리가 둘 다 「상세 모달을 열 때」 일어나므로, 순서를 안 정하면 읽음 처리가 먼저 돌아 안 읽은 수가 0이 되고 **펼칠 것이 하나도 남지 않아 장치가 죽는다**. 규칙: **①모달을 열 때 읽어온 「읽음 처리 이전」의 안 읽은 상태로 펼침을 판정해 화면을 그린다 → ②그다음 읽음 처리를 보낸다.** 읽음 처리 결과로 **상세 모달을 다시 그리지 않는다**(다시 그리면 펼쳐둔 것이 접힌다).
→ **목록 배지는 모달을 닫을 때 갱신한다.** 「다시 그리지 않는다」는 모달 안쪽에만 해당하며, 뒤에 깔린 목록의 배지는 닫는 시점에 0으로 반영해야 한다(관리자 모달의 목록 갱신 규칙과 같은 취지).
→ 결과: **상세를 한 번 열면 그 시트의 안 읽은 수는 0이 된다.** 브랜드 서베이 메모와 같은 수준의 단순한 규칙이고, 목록 배지·검문소·서버 함수가 전부 같은 단위(시트)로 맞아떨어진다.

**12. 빈 상태**
메모가 0건인 카드에 빈 영역만 있으면 「고장난 건가」 싶다.
→ 대응: 「아직 메모가 없습니다. 아래에 남겨 주세요.」 한 줄 + 입력칸.

**13. 되돌릴 수 없는 삭제**
메모 삭제는 되돌릴 수 없다.
→ 대응: 삭제 전 확인 한 단계(브랜드 서베이 메모와 동일 수준).

### 의도가 갈릴 수 있는 부분

- **「메모」의 성격** — 여러 건 쌓는 대화 기록으로 잡았다(브랜드 서베이와 동일). 한 칸을 계속 고쳐 쓰는 메모장이 아니다.
- **「안 읽은」 기준** — 로그인한 본인이 아직 안 본 메모. 다른 관리자와 무관하다.
- **메모의 보존 성격** — 감사 기록이 아니다. 시트를 지우면 함께 사라진다.
- **알림** — 메모를 남겨도 메일·알림은 나가지 않는다.

## 설계

### 1. 카드 고유 번호 (`data.cards[].uid`)

- 값: 무작위 문자열(추측 불가). 한 번 정해지면 바뀌지 않는다.

**번호를 부여하는 곳은 저장 함수 한 곳뿐이다.** 브랜드 작성 폼은 번호를 만들지 않는다 — 불러온 카드의 번호를 **요소 속성에 실어 `collectCard`가 저장 데이터에 그대로 되돌려 보내는 일**만 한다. 만드는 곳이 둘이면 규칙이 갈리고, 어느 쪽이 채웠는지에 따라 안전망이 발동하기도 안 하기도 해서 검증조차 할 수 없다.

- **저장 함수**(`save_orient_draft` / `submit_orient_sheet`)가 저장 직전 세 단계로 처리한다:
  1. 번호가 **있는** 카드는 그대로 둔다
  2. 번호가 **없는** 카드가 있고 **「들어온 카드 개수 = 기존 카드 개수」이면** 같은 순서 자리의 기존 번호를 물려준다
  3. 그래도 비어 있는 자리는 **새 번호를 부여**한다 → 어떤 경로로 저장되든 모든 카드가 번호를 갖고 나온다
- **기존 카드**: 위 규칙과 별개로, 데이터 채우기 작업이 번호 없는 카드에 일괄 부여한다(여러 번 돌려도 같은 결과).

이 규칙이 각 경로에서 어떻게 도는지:

| 경로 | 결과 |
|---|---|
| 새 폼에서 카드 추가 | 새 카드만 번호가 비어 있고 개수가 달라짐 → 2단계 건너뛰고 3단계로 **새 카드만 부여**. 나머지는 1단계로 유지 |
| 새 폼에서 카드 삭제 | 남은 카드는 번호를 싣고 돌아옴 → **1단계로 전부 유지**(물려주기 판정 자체를 타지 않음) |
| 옛 폼 저장 (개수 그대로) | 전부 번호 없음 + 개수 같음 → **2단계로 순서대로 물려받아 유지** |
| 옛 폼 저장 (카드 추가·삭제) | 전부 번호 없음 + 개수 다름 → **3단계로 전부 새 번호**. 그 시트 메모는 전부 고아가 되어 「삭제된 모집 건의 메모」에 모인다 |

⚠️ **2단계의 개수 조건이 핵심이다.** 조건 없이 물려주면 옛 폼이 카드를 지운 채 저장할 때(= 모든 카드가 번호 없이 들어올 때) 번호가 한 칸씩 밀려 붙어 **메모가 아무 표시 없이 엉뚱한 모집 건에 나타난다**(§의심 3). 개수 조건을 걸면 그 경우 메모가 **눈에 보이게** 고아로 빠진다.
⚠️ 2단계는 **옛 폼 호환용**이지, 카드가 실제로 사라진 뒤의 메모 표시 수단이 아니다(그건 「삭제된 모집 건의 메모」가 맡는다 — 아래 4).
- ⚠️ **기존 데이터 채우기는 `version`(낙관적 락 값)을 올리지 않는다.** 확인 결과 `version`은 트리거가 아니라 저장 함수 안에서 명시적으로 올린다. 채우기 작업이 `data`만 바꾸면 브랜드가 열어둔 작성 화면에 「다른 곳에서 수정됨」 충돌이 나지 않는다.

### 2. 새 표 2개

**메모 표** (이름 예: `orient_sheet_memos`)

| 열 | 설명 |
|---|---|
| 시트 참조 | `orient_sheets` 참조, **시트 삭제 시 함께 삭제** |
| 카드 고유 번호 | 어느 모집 건의 메모인지. 카드가 사라져도 값은 남는다 |
| 카드 이름 스냅샷 | 작성 시점 제품명. 카드가 지워졌을 때 어느 건이었는지 알기 위함 |
| 본문 | 서식 있는 글. 길이 상한 + 빈 글 차단 |
| 작성자 · 작성자 이름 | 관리자 계정이 지워져도 이름은 남는 스냅샷 (브랜드 서베이 메모와 동일) |
| 작성 시각 · 수정 시각 | 수정되면 「수정됨」 표시 |

**읽음 기록 표** (이름 예: `orient_sheet_memo_reads`) — 기존 `brand_application_memo_reads` 구조 그대로. (메모, 관리자) 짝이 열쇠, 메모 삭제 시 함께 정리.

**접근 정책(행 단위 보안)**: 조회·작성·수정·삭제 모두 관리자 전원(`is_admin()`) — 열람은 확정 결정 ⑥, 수정·삭제는 확정 결정 ④, 작성은 별도 제한 없음. **등급 분기가 없으므로 정책이 한 줄로 끝난다.**
읽음 기록은 **본인 행만** 작성 가능.

### 3. 서버 함수 2개

- **읽음 처리** — **시트 단위**. 그 시트의 메모 전부(카드에 붙은 것 + 고아 메모)를 본인 기준 일괄 읽음. 기존 `mark_brand_app_memos_read`와 같은 형태이되 카드 번호를 받지 않는다. **호출 시점은 상세 모달을 열 때 1회, 단 화면을 그린 뒤**(§의심 11의 순서 규칙 — 펼침 판정이 읽음 처리 이전 상태를 봐야 한다).
- **집계 조회** — (시트, 카드 고유 번호) 짝마다 `전체 개수 / 안 읽은 개수 / 최근 메모`. 목록 배지는 클라이언트가 시트 단위로 합산해 쓴다. 기존 `get_brand_app_memo_summaries`와 같은 형태.
  ⚠️ 집계는 **메모 표 기준**으로 낸다(시트의 현재 카드 목록과 맞춰 거르지 않는다). 그래야 카드가 지워져 고아가 된 메모도 개수에 잡히고, 화면이 「삭제된 모집 건의 메모」로 끌어와 그릴 수 있다.

메모 자체의 작성·수정·삭제는 일반 조회/쓰기로 처리한다(브랜드 서베이 메모와 동일 — 별도 함수 불필요).

### 4. 화면

**상세 모달** (`osCardDetail` 안, 카드 내용 아래)
```
┌ [모집 건 카드] ────────────────────────┐
│ … 기존 시트 내용 …                      │
│ ─────────────────────────────────────  │
│ ▸ 내부 메모 3  ●2                      │  ← 기본 접힘. 안 읽은 게 있으면 자동 펼침
│   ┌ 김담당 · 08-05 14:20  [고침][지움] │
│   │ 브랜드 확인 결과 발송은 8/12부터    │
│   └────────────────────────────────┐  │
│   [ B I U S 링크 ] 입력칸      [남기기]│
└────────────────────────────────────────┘
```
- 접힘 머리줄: 「내부 메모 {전체}」 + 안 읽은 수 분홍 배지
- 입력칸은 기존 간단 편집기 재사용 — **이미지 버튼만 뺀 형태**
- ⚠️ 편집기 함수는 `admin-lookups.js`에 있고 오리엔 화면 파일보다 **뒤에** 이어붙는다. 함수 선언이라 실행 시점엔 문제없지만(같은 방식으로 캠페인 폼이 이미 참조 중), **이미지 버튼을 뺀 형태를 만들 때 기존 호출부를 깨지 않도록** 선택 인자로 처리한다.

**「삭제된 모집 건의 메모」** (상세 모달 맨 아래, 해당 메모가 있을 때만)
- 시트의 현재 카드 목록에 없는 고유 번호를 가진 메모를 모아 보여준다(§의심 4).
- 각 메모에 **작성 시점 제품명 스냅샷**을 함께 표시해 어느 건이었는지 알 수 있게 한다. 스냅샷도 비어 있으면 「이름 없는 모집 건」으로 표기.
- 이 묶음에서는 **새 메모를 남길 수 없다**(붙일 카드가 없음). 수정·삭제는 동일하게 동작한다.
- 접힘·자동 펼침 규칙은 카드 메모와 **동일**하다 — 안 읽은 메모가 있으면 자동 펼침된다. 읽음 처리는 시트 단위라 이 묶음도 상세를 열 때 함께 처리된다(§의심 11).

**새창 출력** — `osDetailHtml(s, catMap, readonly)`의 `readonly=true`(새창)에서는 메모 영역을 **그리지 않는다**. 「삭제된 모집 건의 메모」 묶음도 마찬가지로 제외한다.

**목록 행** — 브랜드명 옆 또는 전용 열에 안 읽은 수 배지. 0이면 아무것도 안 그린다.

**삭제 확인 창** — 메모가 있으면 「내부 메모 N개도 함께 삭제됩니다」 경고 한 줄.

메모 조회 / 작성 / 수정 / 삭제 / 읽음 처리 / 집계 조회 — 기존 브랜드 서베이 메모 함수들과 같은 이름 규칙.

| **1단계 — 카드에 고유 번호 심기** | 저장 함수(번호 부여·물려주기 3단계 규칙) → 브랜드 작성 폼이 번호를 **실어 나르기**(만들지는 않음) → 기존 시트 데이터 채우기 (**적는 순서 = 배포 순서**, 아래 참조) | 1단계에는 번호를 보여주는 화면이 아직 없으므로(메모 영역은 2단계) **저장된 데이터를 직접 조회해** 확인한다. ①**새로 발급한 시트** — 카드를 추가·삭제하며 저장·재제출해도 나머지 카드 번호가 유지되는지 ②**기존 시트** — 데이터 채우기로 번호가 붙었고, 브랜드가 다시 저장해도 그 번호가 그대로인지 ③**물려주기(2단계) 자체** — ①②는 카드가 번호를 싣고 들어오는 경로라 물려주기를 발동시키지 못한다. 물려주기가 도는 조건은 **「저장된 데이터에는 번호가 있는데, 들어온 데이터에는 없을 때」**(= 옛 폼 상황)이므로, **저장된 번호를 지우면 안 된다** — 지우면 물려줄 재료가 사라져 3단계(새 번호)로 떨어진다. 재현 방법: 개발서버 시험용 시트를 **번호가 붙은 상태로 둔 채**, 저장 함수(`save_orient_draft`)를 **카드 번호를 뺀 데이터로 직접 호출**한다(익명 호출 함수라 관리자 도구에서 토큰과 함께 호출 가능). → 카드 개수를 그대로 보내면 **번호가 물려져 유지**되고, 카드를 하나 빼서 보내면 **전부 새 번호**가 되는지 확인한다. ③은 저장 함수만 배포되면 가능하므로 ①② 이전에 해도 된다. ⚠️ 반면 **①②는 세 배포가 다 끝난 뒤**에만 한다 — 폼·채우기가 아직인 중간 구간에서는 번호가 새로 부여되는 것이 **정상 동작**이라 불합격으로 잘못 판정한다(§의심 3) |
| **2단계 — 메모 본체** | 표 2개 + 서버 함수 2개 + 상세 모달 메모 영역 + **「삭제된 모집 건의 메모」 묶음** + 데이터 접근 함수 | 메모 작성·수정·삭제 / 새창 출력에 메모가 **안 나오는지**(삭제된 건 묶음 포함) / 서식 붙여넣기 정화 / **메모를 단 카드를 브랜드가 지운 뒤 그 메모가 「삭제된 모집 건」 묶음에 제품명과 함께 뜨는지** |
| **3단계 — 목록 배지·삭제 경고** | 목록 안 읽은 수 배지 + 시트 삭제 확인 창 경고 | 배지 숫자와 실제 안 읽은 수가 맞는지 / **상세를 열었다가 닫으면 0이 되는지**(읽음 처리는 시트 단위, 목록 배지 갱신은 **닫을 때** — §의심 11. 모달을 열어 둔 채 뒤 목록을 보면 숫자가 그대로인 것이 정상) / 고아 메모만 안 읽은 상태인 시트도 마찬가지인지 / **메모가 있는 시트를 지우려 할 때 「메모 N개도 함께 삭제됩니다」 경고가 뜨는지** |

**의존 순서**: 1단계 완료·검증 전에는 2단계를 시작하지 않는다(2단계가 고유 번호에 통째로 의존).

**1단계 내부 배포 순서**
1. **저장 함수 안전망 적용 — 반드시 가장 먼저.** 이것이 붙기 전에 옛 폼이 한 번 저장하면 그 시트의 카드 번호가 통째로 날아간다(§의심 2).
2. 브랜드 작성 폼 배포 — 번호를 **만들지는 않고**, 불러온 카드의 번호를 그대로 실어 되돌려 보낸다(§설계 1). **빠를수록 「옛 폼이 카드 개수를 바꿔 저장해 메모가 전부 고아가 되는」 구간이 짧아진다**(§의심 3).
3. 기존 시트 데이터 채우기 — 번호 없는 카드에 부여.

⚠️ 2번과 3번의 선후는 안전망이 붙은 뒤라면 자유롭지만, 위 이유로 폼을 먼저 내는 편이 낫다.
⚠️ 브랜드 작성 폼은 별도 배포 대상(`reverb-sales` 프로젝트)이다. 커밋 반영과 실제 페이지 반영이 다를 수 있으므로 **브라우저로 눈으로 확인**한다.

**데이터베이스 변경** (번호는 개발 세션이 파일을 만드는 시점에 확정 — 아래는 **만드는 순서**)
- 1단계: 저장 함수 2개(`save_orient_draft`·`submit_orient_sheet`) 재정의 → **그다음** 기존 데이터 채우기 (위 배포 순서와 같은 이유)
- 2단계: 표 2개 + 접근 정책 → **그다음** 서버 함수 2개

⚠️ 저장 함수(`save_orient_draft` / `submit_orient_sheet`)를 다시 정의할 때는 **파일 번호가 가장 큰 정의를 바탕으로** 한다. 이 프로젝트에서 옛 정의를 바탕으로 고쳐 뒤 버전의 조항이 소실된 사고가 있었다.

⚠️ **잔여**: 「폼에서 카드를 추가·삭제한 뒤 나머지 번호가 유지되는지」는 브라우저로 직접 해보지 않았다. 서버 쪽에서는 같은 코드 경로를 검사 ②·③으로 직접 확인했고, 폼의 역할은 두 경우 모두 「제 번호를 실어 보내기」로 동일해 위험은 낮다고 판단했다.

**초안 대비 변경 사항**

- **추가된 것 ①: 안 읽은 수에서 「본인이 쓴 메모」를 뺀다.** 초안은 읽음 기록 유무만 봤는데, 읽음 처리는 상세를 **열 때 1회** 돌고 메모는 그보다 **뒤에** 생긴다. 그대로 두면 메모를 남기고 창을 닫는 순간 자기가 방금 쓴 글이 자기 배지에 「안 읽음 1」로 뜬다. 배지의 뜻(「내가 아직 열어보지 않은 새 메모」)과 어긋나므로 서버 집계에서 제외했다. ⚠️ 작성자 계정이 지워진 메모가 집계에서 조용히 빠지지 않도록 `COALESCE(author_id = auth.uid(), false)` 로 감쌌다.
- **추가된 것 ②: ESC 키 경로.** 목록 배지는 상세를 **닫을 때** 갱신하는데, ESC 키는 `dev/js/ui.js` 의 전역 처리기가 일반 닫기 함수를 부르므로 `osCloseModal` 을 안 거친다. 그 처리기에 분기를 더했다(기존 `campBundleModal` 선례와 같은 방식). 리뷰에서 발견.
- **추가된 것 ③: 작성 중이던 글 보존.** 메모 영역은 다른 카드에 메모를 남길 때도 함께 다시 그려진다. 입력칸 초기값을 빈 문자열로 두면 **화면에서만 글이 사라지고 기억에는 남아**, 나중에 「남기기」를 누르면 보이지도 않던 글이 등록된다. 초기값에 작성 중 내용을 넣어 막았다.
- **달라진 것 ①: 목록 배지 위치 = 「메모」 전용 열**(사용자 결정). 브랜드명 옆보다 고칠 곳이 많아, 칸 수 세 곳(제목줄·각 줄·빈 목록 안내줄)을 함께 8→9로 맞췄다.
- **달라진 것 ②: 본문 열 이름 `body_html`.** 초안은 「브랜드 서베이 메모와 동일 구조」라고만 적었는데, 그 표의 본문 열 이름 `text` 는 **서식 없는 줄글**이라 성격이 다르다. 이름으로 구분되게 했다.
- **빠진 것: 없음.**

**구현 중 기술 결정 사항**

- **인라인 핸들러에는 카드 순번(숫자)만 넘긴다.** 카드 고유 번호는 브랜드가 보낸 값이 그대로 저장될 수 있어(서버는 비어 있지 않은 문자열이면 유지) 따옴표가 든 값이 오면 핸들러가 깨진다. 메모 지목은 서버가 만든 식별자라 안전하지만 이스케이프를 함께 걸었다.
- **메모 변경 후 모달 전체를 다시 그리지 않는다** — 메모 영역만 갈아 끼운다(전체 재렌더는 펼쳐 둔 카드가 접히고 스크롤이 튄다).
- **`sanitizeMemoHtml` 을 별도 함수로 둔 이유** — 기존 `sanitizeCautionHtml` 은 `<img>` 를 **허용**한다(캠페인 안내문·오리엔 리뷰 가이드가 이미지를 정상적으로 쓴다). 거기서 이미지를 빼면 기존 화면이 전부 깨지므로 정책을 분리했다. 편집기의 이미지 버튼만 감추는 것으로는 부족하다 — 붙여넣기·드래그 경로가 남는다(다만 현재 편집기의 붙여넣기는 서식을 전부 버리고 순수 글자만 넣는다).
- 편집기 `miniEditorHtml` 의 4번째 인자는 **선택**이라 기존 호출부 12곳은 무영향(리뷰에서 실제 실행·파싱으로 확인).
