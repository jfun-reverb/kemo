# 마이그레이션 적용 기록 표 + 병합 요청 자동 검사 — 기획 요청서

**작성일:** 2026-10-20 · **작성:** 고문 세션 · **받는 쪽:** 기획 세션(사양서) → 개발 세션

## 왜

개발자 두 명(대표·wooyoung)이 각자 Claude 로 같은 저장소에 마이그레이션을 올린다. 두 가지가 비어 있다.

1. **데이터베이스에 무엇이 들어갔는지 모른다** — SQL 편집기는 기록을 안 남긴다. 개발·운영 각각 「몇 번까지, 누가, 언제」를 알 길이 없다.
2. **번호 충돌·같은 대상 재정의를 막는 장치가 없다** — 커밋 전 후크는 시간대·권한 좁히기만 본다. GitHub 자동 실행은 `deploy-prod.yml` 하나뿐.
   - 실제 사례: 기준 데이터 종류 검사 제약을 554(배송 리스트)·555(CS 항목)가 같은 날 따로 정의(`CLAUDE.md` `lookup_values` 줄). 번호가 달라 코드 합치기 충돌이 안 나고, **나중 적용이 앞 변경을 조용히 지운다.**

## 사용자 결정 (2026-10-20)

- 적용 기록은 **데이터베이스 안 기록 표**로 한다(공유 문서 손기록 아님).
- 기록 누락·번호 충돌은 **병합 요청 자동 검사**(GitHub 이 돌림 — 두 사람 모두에게 같이 걸린다)로 막는다.

## 기획이 정할 것 (고문이 본 의심점)

1. **기록이 성공할 때만 남는가** — 파일 끝 한 줄로 기록할 때, SQL 편집기가 파일 전체를 한 묶음(전부 되거나 전부 안 되거나)으로 실행하는지 **미확인**. 아니면 중간 실패에도 기록이 남는다.
2. **출발점** — 지난 556개는 기록이 없다. 운영은 일부를 **일부러 안 넣었다**(362 가입 차단, 개발서버 전용 묶음 526~ 등). 「556까지 전부」로 채우면 거짓. 개발·운영 각각 출발점을 어떻게 잡을지.
3. **패치(`supabase/patches/`)도 기록하나** — 데이터 정정·되돌리기 파일.
4. **자동 검사 범위** — ①`dev` 와 번호 중복이면 병합 차단 ②이 요청이 다시 정의하는 함수·제약을 갈라진 뒤 `dev` 에서 또 고쳤으면 경고 ③새 마이그레이션에 기록 줄이 없으면 차단. ②는 `CREATE …` 정의만 세고 권한·주석만 손댄 파일은 빼야 한다(`common-planning` 규칙 D).
5. **이미 있는 표와 겹치는가** — Supabase 명령줄 도구용 기록 표(`supabase_migrations.schema_migrations`)가 있는지·비어 있는지 확인.
6. **누가 보나** — 기록 표의 읽기 권한(관리자만 / 서비스 키만).
