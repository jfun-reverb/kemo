# CS 이력 관리 — 메시지 화면 안의 CS 표·통계

**작성일:** 2026-10-16 · **작성:** 기획 세션
**상태:** 확정 결정 11건(사용자 확인 끝남) · 자기 정합성 점검 11회(7 → 6 → 5 → 4 → 1 → 2 → 2 → 2 → 4 → 3 → 3 — 11차 3건 반영 뒤 멈춤. 1~5차는 설계, 6차부터는 시트 25건 이관의 세부라 D-8 을 「짝 맞춤 표를 사람이 확인」으로 바꿔 규칙을 줄였다. 0건 확인은 못 받았다) · 피그마 화면 작업 중

| D-6 | 재문의 | CS 건 완료 뒤 회원이 같은 대화에 다시 쓰면 **새 건을 자동으로 만든다**(옛 건은 그대로). 새 건에 「재문의」 표시 + 이전 건 연결 |
| D-7 | 과거 대화 | 출시 때 **최근 3개월 대화에만** 행을 만든다(백필). 항목은 「미분류(과거)」(백필 전용 항목 — 완료 창 선택지에는 안 보인다, 4-4 ①), 상태는 지금 미응대면 진행중·아니면 완료(완료 시각 = 마지막 응대 완료 시각 · 완료한 사람 = 비움 · 만들어진 경위 = 「과거 이관」 — 4-4 ②). 실행은 자동 행 생성(4-4 ③)과 **같은 마이그레이션 안에서 바로** — 환경마다 적용될 때 한 번(4-4 ⑤) |
| D-8 | 구글 시트 25건 | 시트를 CS 표로 옮긴다. **짝은 규칙으로 자동 결정하지 않고 사람이 확인한다** — 개발이 「짝 맞춤 표」 초안(시트 줄마다 붙일 곳 후보: 회원 이메일 + 접수일 근처의 CS 건)을 만들고 **사용자가 한 줄씩 확인**한 뒤 붙인다(25건이라 사람이 보는 것이 가장 정확하다). 줄마다 셋 중 하나 — ⓐ **기존 CS 건에 붙임**: 항목·확인 필요 메모만 옮긴다. **이관 때 상태·시각은 바꾸지 않는다**(백필·자동 행 값 그대로). 그 뒤 운영자가 상태를 바꾸면 일반 건과 같다(4-2 — 완료하면 그 순간이 완료 시각이 된다) ⓑ **그 대화의 「건 추가」 행**(대화는 맞는데 붙일 건이 없거나 이미 다른 줄이 붙은 경우) ⓒ **수기 행**(회원·대화를 못 찾은 줄 · 출처 = 「메일」 — 시트 작성 가이드 「메일주소 = CS 회신이 오간 메일」). **ⓑ·ⓒ 「시트 출신 행」 규칙** — 시트의 항목·진행현황·확인 필요 메모(일·한)를 옮기고, ⓒ 는 수기용 칸(유저이름·메일주소·캠페인 이름·분류·문의/대응 내용 일·한)도 옮긴다 · 접수 = 시트 접수일 · **「시간 미상」 표시**(시트는 날짜만 있어 응답·해결 시간 통계에서 뺀다, 건수에는 든다) · 시트가 완료면 완료 시각 = 시트 접수일·완료한 사람 = 비움, 아니면 둘 다 비움 · 만들어진 경위 = 「시트 이관」(4-4 ②). **화면(PR 2·3)이 운영에 나가는 날 시트 입력을 멈추고 같은 날 붙인다** |
| D-9 | 권한 | **메시지 화면 권한(`menu.messages`)을 따라간다** — 메시지를 볼 수 있으면 CS 이력도 보고 고친다. 새 권한 열쇠는 두지 않는다. **엑셀 내보내기는 2단계**(민감정보 엑셀 권한과 함께) |
| D-10 | 보관 | 수기 건(회원과 짝 없음)의 이름·이메일·문의/대응 내용·메모는 **완료 후 3년**이 지나면 자동으로 비운다(항목·시각은 통계용으로 남김). 회원과 짝이 있는 건은 회원 탈퇴 파기를 따른다 |
| D-11 | 언어 | 확인 필요 메모와 수기 건의 문의·대응 내용은 **시트처럼 일본어·한국어 두 칸** |

## 현재 상태 (2026-10-16 기준, 규칙 A)

### 구글 시트 (지금의 관리 방식)
- 칸 14개: 번호 · 접수일 · 분류(리뷰어/기프팅) · 캠페인 이름 · 유저이름 · 메일주소 · **항목 7종** · 문의 내용(일/한) · 대응 안내 내용(일/한) · **진행현황 3단(확인필요 / 진행중 / 완료)** · 확인 필요 내용(일/한)
- 작성 가이드: 「메일주소 = CS 회신이 실제로 오간 메일」 · 「유저이름 = 신청서 기재 성명」 · 「확인필요 = 브랜드·내부 확인이 필요해 회신이 보류된 건」 · 진행현황에 따라 행 색이 바뀐다
- 처리 시간·항목별 건수를 보는 칸이나 요약이 **없다** — 이번 요청의 동기
- 기록 **25건**(첫 접수 2026-07-27) · 보이는 18건 중 정산문의 12건 · 같은 회원이 여러 캠페인을 한 번에 묻는 행이 여러 줄로 쪼개져 있다(시트는 캠페인 단위)

### 관리자 메시지 화면
- `#adminPane-messages`(`dev/admin/index.html` 2172~) — 위에서부터 제목 줄(「메시지」 글자뿐, **오른쪽이 비어 있다** — 2174) · 탭 셋(캠페인 문의 / 서비스 문의 / 일괄발송 이력, 탭 줄 끝에 「자주 묻는 질문」 단추 — `admin-messaging.js` 423~438) · 필터 줄(기간·정렬·미응대만·검색·일괄 발송)
- 대화에 **분류·진행 상태·메모를 붙이는 기능은 없다**
- 「응대 완료」 단추 = `markCurrentResolved()`(`admin-messaging.js` 1377) — 응모건은 `mark_application_resolved`(145), 서비스 문의는 `close_general_inquiry_thread`(505, 대화 닫기)로 갈린다. 확인 창·입력 없음
- 🔴 **운영팀이 답장을 보내면 응대 완료가 자동으로 찍힌다**(`send_application_message` 509 · 일괄 발송 417 — `resolution_method='auto_replied'`). 회원이 다시 쓰면 지워져 미응대로 돌아간다. 즉 「응대 완료」는 **「공이 회원 쪽에 있다」**는 뜻이지 **「CS 가 해결됐다」**가 아니다 → D-4 의 「CS 건 완료」를 따로 두는 이유
- 일괄 발송 글도 보낸 사람이 운영팀(`sender_kind='admin'`)이고 `broadcast_id` 가 붙는다 — 「첫 운영팀 답장」 계산에서 빼야 한다
- 받은편지함 응모건 목록은 회원 이메일을 그대로 보이고 검색 대상에도 넣는다(`admin-messaging.js` 364·396·457). 서비스 문의 목록은 이름만

### 데이터 (시각을 어디서 얻나)
- `application_messages` — 메시지마다 `sender_kind`·`created_at`·숨김(`hidden_by_admin_at`)·회수(`self_withdrawn_at`)·`broadcast_id`·서비스 문의 대화 칸 `general_thread_id`. **접수 시각 · 첫 답장 시각은 여기서 계산할 수 있다**(새 입력 없음)
- 뷰 `application_message_summary`(144) — 칸 7개, 첫 글·첫 답장 칸은 없다
- 뷰 `general_inquiry_thread_summary`(508) — 칸 19개, `opened_at`(접수 후보) 있음, 첫 답장 칸은 없다
- 서비스 문의 여러 대화 구조(504~508)는 **운영에도 반영돼 있다**(2026-10-16 `origin/main` 확인 — 504 파일·`_admMsgGeneralThreadId` 존재). ⚠️ `CLAUDE.md`·`general-inquiry.md` 는 「개발서버에만」이라 적고 있어 낡았다 — 개발 세션에 정정 요청
- 응모건 「응대 완료」 표 `application_message_resolutions`(144) · 서비스 문의 대화 표 `general_inquiry_threads`(504, `status` open/closed · `closed_at`)

### 기준 데이터
- `lookup_values` 의 종류는 데이터베이스 검사 제약이 있다(마지막 확장 227). 관리 화면의 종류 탭은 HTML 단추(`dev/admin/index.html` 2781~2789) + 이름표 `LOOKUP_KIND_LABEL_KO`(`admin-lookups.js` 21) **두 곳**에 박혀 있다

### 권한
- 메시지 관련 권한 열쇠: `menu.messages` · `message.bulk_send` · `message.hide` · `message.unhide`(`shared.js` 2027·2065~2067). 기본값은 214 시드
- 민감 정보 가림막(212)은 전화·LINE·PayPal·주소 6종을 가리고 **이메일은 가리지 않는다**

### 이 제안과 충돌 가능성 있는 기존 동작
1. 「응대 완료」가 답장으로 자동 찍히는 동작 — CS 건 완료와 섞이면 해결 시간이 「첫 답장 시간」이 된다. **별개로 둔다**(D-4)
2. 메시지를 세는 조회가 응모건·일반 문의를 같은 표에서 읽는다 — 새 집계는 두 종류를 **구분해** 센다(`application_id` 유무)
3. 회원 탈퇴 파기(현재 원본 520) — 새 표에 회원 이름·이메일·메모가 들어가면 파기 대상에 넣어야 한다(§4-5)
4. 감사용 계정 격리 — 통계에서 감사용 계정의 대화를 빼야 한다

## 의심·경우의 수 (규칙 B)

1. **[데이터] 「건」의 경계는 사람이 정한다** — 한 대화에 배송 문의 뒤 정산 문의가 이어지면 자동 1행만으로는 항목이 하나뿐이다. 「건 추가」를 안 누르면 통계가 뭉개진다. → 완료 창에서 「이 대화에 다른 주제가 있었나요?」를 묻지 않고, 표에 **「같은 대화의 건 수」**를 보여 주는 것으로 둔다(강제하면 운영 부담이 커진다)
2. **[데이터] 완료 뒤 재문의** — 옛 건을 다시 열면 해결 시간이 며칠씩 늘어 통계가 왜곡되고, 새 건을 만들면 「같은 이야기를 이어 쓴」 경우 건이 둘로 센다. → D-6(새 건 + 「재문의」 표시로 이어 볼 수 있게)
3. **[데이터] 첫 답장 계산에서 빼야 할 글** — 일괄 발송(`broadcast_id` 있음) · 숨김 처리된 글 · 회수된 글. 또 **접수 시각보다 앞선** 운영팀 글(운영팀이 먼저 보낸 안내 뒤에 회원이 쓴 경우)은 답장이 아니다
4. **[데이터] 수기 행의 시각** — 메일·LINE 건은 접수·첫 답장·완료 시각을 운영자가 적는다. 비워 두면 그 건은 시간 통계에서 빠진다(건수에는 든다). 앱 건과 섞어 평균을 내면 기준이 다르다 → 통계에 **출처별 나눠 보기**
5. **[권한·법률] 개인정보** — 수기 행은 회원과 짝이 없을 수 있어 **이름·이메일을 직접 저장**한다. 회원 탈퇴 파기 대상·보관 기간이 필요하다. 이메일은 지금 받은편지함에서도 가리지 않지만, **엑셀 내보내기**를 붙이면 대량 유출 통로가 하나 는다 → D-9(엑셀은 2단계) · D-10(수기 건 보관 3년)
6. **[권한] 누가 보나·누가 고치나** — 캠페인 매니저도 CS 를 하는지(지금 받은편지함은 보인다). 새 권한 열쇠를 둘지 메시지 권한을 따라갈지 → D-9
7. **[환경] 운영 데이터 백필** — 이 기능이 나가는 날 이미 있는 대화는? 행이 없으면 통계가 「출시일부터」만 나온다. 과거 대화에 행을 만들면 항목이 비어 「미분류(과거)」가 쌓인다 → D-7(최근 3개월) · D-8(시트 25건의 항목을 옮겨 붙여 미분류를 줄인다)
8. **[UX] 진입·이탈** — 진입은 메시지 화면 단추 하나(D-1). 표의 행을 누르면 **그 대화로 바로 가야** 하고, 대화에서 표로 돌아오는 길(뒤로 단추)이 있어야 한다. 대화 화면에서도 「이 대화의 CS 건」(항목·상태·메모)을 보고 고칠 수 있어야 운영자가 두 화면을 오가지 않는다
9. **[UX] 인지 부하** — 시트의 14칸을 다 표에 넣으면 PC 폭에서도 넘친다. 문의·대응 원문은 표에 **요약 한 줄**만, 펼치거나 대화로 가서 본다. 일본어·한국어 두 벌 칸은 앱에 **자동 번역이 이미 있어** 앱 건의 문의·대응 내용에는 필요 없다 — 수기 건의 문의·대응 내용과 모든 건의 확인 필요 메모만 두 칸(D-11)
10. **[UX] 빈 상태·실수 방지** — 완료 창에서 항목 미선택이면 단추 비활성(필수). 「CS 건 완료」 되돌리기(다시 열기)가 있어야 잘못 누른 것을 고친다. 수기 행 삭제는 확인 창
11. **[UX] 미응대 배지와 혼동** — 「응대 완료」(배지)와 「CS 건 완료」(통계)가 한 화면에 둘 다 보이면 헷갈린다. 이름을 분명히 가르고 대화 화면 안 위치도 떨어뜨린다
12. **[감사용 계정]** — 통계·표에서 감사용 계정 대화를 기본 제외(`is_audit`)

**현재 구현과 어긋나는 지점**: 위 「충돌 가능성」 넷. 그 밖은 충돌 없음 — 메시지 발송·응대 완료·서비스 문의 닫기의 동작은 그대로 두고 그 위에 새 표를 얹는다.

**의도와 다르게 읽힐 수 있는 것**:
- 「분류(리뷰어/기프팅)」 — 시트에서는 손으로 고르지만 앱 건은 캠페인 모집 형식에서 **자동**으로 채운다(서비스 문의는 「서비스」). 수기 건만 고른다

  - 응답 시간 · 해결 시간 — 전체 평균·중앙값 + 항목별
  - 진행현황별 건수(확인필요 / 진행중 / 완료)

  - 행 누름: 앱 건 → 그 대화(메시지 화면, 해당 탭·대화 열림) / 수기 건 → 수기 건 편집 모달
- **「+ 수기 등록」 단추**(메일·LINE 건): 모달 — 출처(메일/LINE/기타) · 접수일시 · 회원(검색해 고르면 이름·이메일 자동 / 못 찾으면 이름·이메일 직접) · 캠페인(선택, 없어도 됨) · 분류(리뷰어/기프팅/방문/서비스 — 캠페인을 목록에서 고르면 자동, 아니면 직접) · 항목 · 문의 내용(일·한) · 대응 내용(일·한) · 첫 답장 일시(선택) · 진행현황 · 완료 일시(진행현황이 완료일 때만 보이고 필수 — 이미 끝난 메일 건을 등록할 때 해결 시간이 「등록 순간」으로 찍히지 않게) · 확인 필요 메모(일·한)

### 4-2. 상태와 전이
- 자동 행: 회원이 대화를 시작하면(그 대화에 열린 건이 없을 때 회원 글이 들어오면) **진행중**으로 생긴다
- 진행중 ↔ 확인필요: 운영자가 손으로
- 완료: 「CS 건 완료」 — **항목 필수**(D-4), 완료 시각·완료한 사람 기록 · 수기 건을 처음부터 완료로 등록하면 완료 시각 = 모달의 완료 일시, 완료한 사람 = 등록한 사람
- 다시 열기: 완료 → 진행중(완료 시각·완료한 사람 지움)
- 재문의(완료 뒤 회원이 다시 씀): **새 진행중 건**을 자동으로 만들고 「재문의」 표시 + 이전 건 연결(D-6)

### 4-3. 시간 계산 (D-5)
- **접수 시각**: 자동 행 = 그 건을 연 회원 글의 시각 / 「건 추가」 = 추가할 때의 마지막 회원 글 시각(운영자가 고칠 수 있음) / 백필 = 그 대화에서 **3개월 창 안의 첫 회원 글 시각**(「최근 3개월 대화」 = 마지막 회원 글이 3개월 안인 대화) / 수기 = 입력값 / 시트 출신 행 = D-8 ⓑ·ⓒ 규칙
- **첫 답장 시각**: 앱 건은 접수 시각 **뒤**의 첫 운영팀 글 — 일괄 발송·숨김·회수 글 제외. **조회(4-4 ④)가 매번 계산**하고 저장하지 않는다. 수기 = 입력값(선택, 저장)
- **응답 시간** = 첫 답장 − 접수 / **해결 시간** = 완료 − 접수. 값이 없는 건과 「시간 미상」 표시 건(D-8)은 시간 통계에서 빠지고 건수에는 든다
- 표시: 「3시간 20분」·「2일 4시간」 같은 사람이 읽는 꼴. 요약은 평균 + 중앙값(평균은 몇 건의 긴 정산 문의에 끌려간다)

### 4-4. 데이터베이스 (마이그레이션 — 번호는 개발이 정한다)
1. **기준 데이터 종류 추가** — `lookup_values` 의 종류 검사 제약에 CS 항목 종류(이름은 개발이 정함 — 예 `cs_category`) 추가 + 시드 **8행** — 환불·캠페인·배송·운영·제품·정산·기타(한·일) + **「미분류(과거)」**(백필 전용 — 완료 창·수기 모달 선택지에서는 숨긴다, 기준 데이터 화면에서 끄거나 지우지 못하게). 관리 화면 탭 단추·이름표 두 곳도 함께(이름 전파)
2. **CS 건 표**(이름은 개발이 정함 — 예 `cs_cases`): 출처(캠페인 문의 / 서비스 문의 / 메일 / LINE / 기타) · 응모 id(선택) · 서비스 문의 대화 id(선택) · 회원 id(선택) · 수기용 이름·이메일·캠페인 이름 · 캠페인 id(선택) · 분류(수기용 — 앱 건은 캠페인 모집 형식·서비스 문의에서 계산) · 항목 코드 · 진행현황(확인필요/진행중/완료) · 접수 시각 · 첫 답장 시각(**수기 건 입력값 전용** — 앱 건은 4-4 ④가 계산) · 완료 시각 · 완료한 사람 · 확인 필요 메모(일·한) · 수기용 문의·대응 내용(일·한) · 이전 건(재문의 연결) · 「시간 미상」 표시(D-8) · **만들어진 경위**(실시간 / 과거 이관(⑤ 백필) / 시트 이관(⑥ 의 ⓑ·ⓒ) — 담당자 칸 표시의 근거. ⓐ 로 붙은 줄은 경위가 바뀌지 않으므로 이관 결과 대조는 ⑥ 의 「확인된 짝 맞춤 표」로 한다) · 만든 사람·시각
   - 검사 제약: 앱 건은 응모 id 또는 대화 id 중 **정확히 하나**, 수기 건은 둘 다 없음 · 완료면 항목·완료 시각 필수
   - 행 단위 보안 정책: 읽기·쓰기 관리자 — 메시지 화면 권한을 따른다(D-9, 새 권한 열쇠 없음). 회원은 접근 없음
3. **자동 행 생성** — 회원 글이 들어올 때(메시지 삽입 트리거 또는 발신 함수 안) 그 대화에 열린 건(진행중·확인필요)이 없으면 만든다. 그 대화에 완료된 건이 있으면 새 건에 「재문의」 표시와 이전 건 연결(D-6). 🔴 발신 함수(509·508)를 다시 정의하면 현재 원본 번호를 베이스로(규칙 D) — 트리거로 두면 발신 함수를 안 건드려 안전하다
4. **조회 함수 또는 뷰** — 표·요약용. 첫 답장 시각 계산(4-3) · 감사용 계정 제외 · 응모건/일반 문의 구분
5. **백필(D-7 대로 — 항목 「미분류(과거)」 · 상태 규칙 · 완료 시각 규칙)** — 최근 3개월 대화마다 한 행. 대화 하나에 회원 글 묶음이 여럿이어도 한 행(과거는 「건」을 가를 근거가 없다). 🔴 **③과 같은 마이그레이션 안에서 ③ 바로 뒤에** 돈다(환경마다 적용 때 한 번) — 사이에 끼는 회원 글이 없어 「이미 자동 행이 있는 대화」를 따로 가를 일이 없다. 데이터베이스 안의 대화가 기준이라 마이그레이션에 둘 수 있다(⑥은 바깥 시트가 기준이라 패치)
6. **시트 25건 붙이기(D-8 대로 — 짝 맞춤 표를 사용자가 확인한 뒤)** — 운영에서만 한 번, **화면(PR 2·3)이 운영에 나가는 날**(시트 입력을 멈춘 직후 — 그 전까지 운영팀은 시트에 계속 적는다). 개발이 짝 맞춤 표 초안을 만들어 사용자 확인을 받고, 확인된 표대로 이관용 SQL 패치를 돌린다(바깥 시트 값이 들어가서 마이그레이션에 못 둔다). 결과 표(확인된 짝 맞춤 표 기준 — 기존 CS 건에 붙은 줄 — 백필 행 / 자동 행 따로 셈 · 「건 추가」 행이 된 줄 · 수기 행이 된 줄 — 셋의 합 = ⑥ 실행 때 시트 줄 수, 2026-10-16 기준 25)를 「구현 결과」에
7. **수기 건 3년 비우기(D-10)** — 매일 도는 예약 작업 또는 기존 정기 파기에 한 줄
- 순서: ①종류 → ②표 → ③자동 생성 → ⑤백필 → ④조회 → ⑦보관 비우기(여기까지 마이그레이션) · ⑥시트 붙이기(운영만 · 데이터 패치)
