## 2. ⛔ 지금 그 작업 폴더에서 해야 할 것 3가지

### 가. 새로 만든 `297_faq_receipt_payback_amount.sql` 을 **303** 으로 바꿔 주세요

그 폴더에 아직 커밋 안 된 `supabase/migrations/297_faq_receipt_payback_amount.sql` 이 있습니다.
**297·298 은 오리엔시트 내부 메모가 가져갔고, 오늘 운영까지 적용됐습니다.** 그대로 두면 또 중복됩니다.

`dev` 기준 현재 쓰인 번호는 **302 까지**입니다. 다음 빈 번호는 **303**.

```bash
cd ~/Documents/projects/reverb-jp-정산영수증금액
git mv supabase/migrations/297_faq_receipt_payback_amount.sql \
       supabase/migrations/303_faq_receipt_payback_amount.sql   # 추적 전이면 그냥 mv
```
파일 안에 자기 번호(`[297]` 등)를 적어 뒀다면 그것도 함께 고쳐 주세요.

⚠️ **개발 데이터베이스에 이미 297 번 파일을 적용했다면** 다시 적용할 필요는 없습니다 — 이 프로젝트는 손으로 실행하므로 파일 이름과 적용 상태는 별개입니다. 이름만 맞추면 됩니다.

### 나. `dev` 를 받아올 때 사양서에서 충돌이 납니다

`docs/specs/2026-08-05-settlement-receipt-amount-switch.md` 를
- 그쪽: 미커밋 상태로 **수정 중**
- `dev`: 제가 **번호 참조를 293→299 등으로 갱신**

양쪽이 같은 파일을 고쳐 **충돌합니다.** 받아오기 전에 **커밋하거나 임시 보관(stash)** 해 두세요.

충돌 해소 요령 — 그쪽이 새로 쓴 내용은 살리고, **번호만 새 번호로** 맞추면 됩니다.

### 다. 그쪽 미커밋 변경 안에 옛 번호가 남아 있는지 확인

`dev/lib/storage.js`·`dev/js/admin.js` 등을 수정 중이신데, 그 안 주석에 `마이그레이션 293`·`294` 처럼 **정산을 가리키는 옛 번호**가 있으면 새 번호로 바꿔 주세요.

⚠️ **주의** — 같은 숫자라도 **오리엔을 가리키는 것은 그대로 둬야 합니다.**
`293_orient_card_uid_safety_net` · `294_orient_card_uid_backfill` 은 오리엔 것이고 **운영에 배포된 번호라 안 바뀝니다.**
헷갈리면 그 주석이 정산 이야기인지 오리엔 이야기인지 문맥으로 판단하세요.

## 3. 왜 정산 쪽을 옮겼나 (되돌리지 말 것)

- **오리엔 293·294 는 2026-08-05 운영에 적용됐고**, 운영 레퍼런스(`CLAUDE.md`)와 사양서가 그 번호로 적혀 있습니다. 옮기면 운영 문서가 통째로 어긋납니다.
- 정산 293~296 은 **개발서버 전용**(운영 미배포)이라 옮기는 비용이 훨씬 작았습니다.
- **넷 다 옮긴 이유** — 실제로 부딪힌 건 293·294 둘뿐이지만, 295·296 만 남기면 파일 순서상 299·300 **앞**에 오는데 실행은 **뒤**에 해야 해서 순서가 뒤집힙니다.

## 4. 운영에 올릴 때

적용 순서: **299 → 300 → 301 → 302** (그리고 새로 만든 303)

의존 관계는 옛 번호일 때와 같습니다 — 299 가 만든 칸에 300 의 함수가 넣고, 301·302 는 그 뒤입니다.

⚠️ 운영에는 **291·292·295·296 번 파일이 없습니다**(개발 전용 다른 작업이었거나 이번에 비워진 번호). 번호가 띄엄띄엄한 것은 정상이며, 이 프로젝트는 손으로 실행하므로 문제되지 않습니다.

done
