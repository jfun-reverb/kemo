**깨지는 것과 안 깨지는 것을 갈라 둔다:**

- ✅ **결정 1(미지급 있으면 대기)의 구조는 그대로 선다** — 판정을 **서버 함수 안에서** 하면 된다. `SECURITY DEFINER` 함수는 정책을 우회하므로 `settlements` 를 읽을 수 있다. **화면이 세는 설계는 이제 불가능**하다.
- 🔴 **결정 7은 사실과 다르다** — 「유지한다」고 한 정산 안내가 **이미 0건**이다. 그러므로 **「대기 → 예정」 전이 알림이 유일한 통지 수단**이 된다. 이 알림이 없으면 미지급 대기 중인 회원은 **자기 탈퇴가 언제 되는지 영영 모른다**(몇 달일 수 있다).
- 🟡 **§4-4 화면의 금액 표시는 새 결정이 필요하다** → **확인 Q1**

### ② 🟡 `cancel_application` 의 현재 원본은 306 이 아니라 **309**

사양서 §1-4·§1-5 ㄴ 이 「306(현재 원본)」이라 적었다. 실제로는 **309**(취소 완료 알림을 서버가 만드는 판)가 마지막 정의다. **번호가 가장 큰 정의를 베이스로** 삼는다.

### ③ 🟡 사유 기준 데이터는 「시드」만으로 안 된다 — CHECK 확장이 함께 필요

`lookup_values.kind` 의 CHECK 제약은 **마이그레이션 227** 이 마지막 정의다. 새 종류(`withdraw_reason`)를 넣으려면 **DROP + ADD** 로 확장해야 하고, 안 하면 시드 INSERT 가 통째로 실패한다.

### ④ 🟡 알림 종류도 CHECK 확장 대상 — 베이스 **283**(현재 11종)

### ⑤ 🔴 재가입 차단(⑧)의 **집행 위치가 사양서에 없다**

가입은 브라우저가 **`db.auth.signUp()` 을 직접** 부른다(`dev/js/auth.js`). 화면에서만 해시를 대조하면 **개발자 도구로 그대로 우회**된다. 현재 걸린 트리거(`on_auth_user_created`, 마이그레이션 014)는 **AFTER INSERT** 라 거부 수단이 아니다. → **확인 Q3**

### ⑥ 🟢 마이그레이션 최신 = 344 (다음 345). 사양서에 번호가 박혀 있지 않아 문제 없음

## 조각별 상세

### 작업 1 — ★ 거짓 안내 제거 (오늘 배포 가능)

- **하는 일:** 「접수했습니다」라는 **사실이 아닌 말**을 지운다. 그 한 가지만 한다.
- **담당 파일:** `dev/js/mypage.js` · `dev/lib/i18n/ja.js` · `dev/lib/i18n/ko.js`
- **약관 개정 불필요 · 데이터베이스 변경 없음 · 문의 창구 불필요**
- **산출 계약:**
  - `handleWithdraw()` — **확인창(`confirm`)을 없애고** 안내만 띄운다
  - 열쇠말 `mypage.withdrawConfirm` **삭제**, `mypage.withdrawToast` → **`mypage.withdrawGuide`**
  - ⚠️ 이름을 바꾸는 이유: **옛 이름이 남아 있으면 나중에 누가 옛 문구를 되살린다**
- **문구 (일본어 · 한국어 뜻 병기)**

| | 일본어 | 한국어 뜻 |
|---|---|---|
| 지금 (확인창) | `本当に退会しますか？` | 「정말 탈퇴하시겠습니까?」 ← **눌러도 탈퇴가 안 되므로 질문 자체가 거짓 전제** |
| 지금 (토스트) | `退会申請を受け付けました。運営にLINEでご連絡ください。` | 「탈퇴 신청을 접수했습니다. 운영팀에 LINE으로 연락해 주세요.」 ← **앞 문장이 거짓** |
| **바꿀 안** | `退会をご希望の方は、運営までご連絡ください。担当者がご案内します。` | 「탈퇴를 원하시는 분은 운영팀으로 연락해 주세요. 담당자가 안내해 드립니다.」 |

- ✅ 「접수했다」는 말이 **없다** → 거짓말 제거
- ✅ 목적지가 **남는다** → 막다른 길이 아니다
- ✅ 「받는다」를 부정하지 **않는다** → 현행 약관 제6조 1항과 안 부딪힌다
- ⚠️ **LINE 이라는 낱말을 남길지는 확인 Q5**
- **완료 정의:**
  - 햄버거 → 「退会する」 클릭 시 **확인창이 안 뜨고** 안내만 뜬다
  - 빌드 산출물 `index.html` 에서 「受け付けました」 검색 **0건**
  - 일본어·한국어 두 화면 모두 확인
  - `bash dev/build.sh` 통과
- **필요 검문소:** `reverb-reviewer`
- ⚠️ **낱말 전파 점검 완료** — `退会` 관련 문구는 화면 1곳·번역 2곳·햄버거 라벨 1곳이 전부이고 **메일·자동응답·엑셀에는 없다**.

- **산출 계약:** `request_withdrawal(p_reason_code text, p_reason_note text)` → jsonb

- **하는 일:** ①본인 확인·**감사용 계정 거부** ②활성 신청 있으면 그대로(멱등) ③사유 검증 ④**철회 가능한 응모만** 취소(건별, 한 건 막혀도 계속) ⑤**미지급 판정** → 0건이면 `scheduled` + 예정일 = 그날+5일

### 작업 5 — 탈퇴 신청 함수 ✅ 작성 완료 (2026-08-19, **적용 전**)

마이그레이션 **347**. `request_withdrawal(p_reason_code, p_reason_note)` → jsonb `{ok, status, scheduled_date, cancelled_count, uncancelled_count, unpaid_count}`

**초안 대비 달라진 것 — 조사·결정으로 바뀐 3건**

| | 무엇 | 왜 |
|---|---|---|
| ㄱ | **금액을 안 돌려준다**(`unpaid_amount_jpy` 없음) | 결정 Q1 — 오늘 없앤 정산 금액 노출을 탈퇴 화면으로 되살리지 않는다 |
| ㄴ | **사유가 선택**(`reason_required` 반환값 삭제) | 결정 Q7 — 한국 2025-12 규제 흐름·일본 관행(조사 문서) |
| ㄷ | **응모 철회에 넘기는 사유를 분리** | 아래 |

**🔴 ㄷ 이 이번 작업의 핵심 — 두 결함을 함께 고쳤다**

1. **사유를 그냥 선택으로 풀면 조용히 깨진다.** `cancel_application`(베이스 309)은 **모집 기간이 지난 응모에 사유가 비면 거부**한다. 사유를 안 고른 회원은 **그 응모들이 하나도 철회되지 않고** 「철회 못 한 건」으로만 집계돼 **원인을 알 수 없다**
2. **초안은 탈퇴 사유 코드를 취소 사유 자리에 그대로 넘기고 있었다.** 두 목록(`withdraw_reason` / `cancel_reason`)이 달라 ①응모에 자기 목록에 없는 코드가 저장되고 ②**관리자 알림 메일의 사유가 `-`** 로 나온다

→ 전용 취소 사유 **`withdrawal`**(「회원 탈퇴」/「退会のため」)을 시드하고 **항상 그것을** 넘긴다. 회원이 고른 탈퇴 사유는 `withdrawal_requests` 에만 남는다.
→ ⚠️ 그 코드는 **`active=false`** 로 시드했다 — 인플루언서의 「이 응모만 취소」 드롭다운에 「회원 탈퇴」가 뜨면 **계정이 탈퇴되는 것으로 오해**한다.
→ ⚠️ 그 결과 관리자 화면·엑셀이 코드값을 그대로 보여주는 부작용이 생겨 **라벨 조회만 비활성 포함**으로 바꿨다(`fetchCancelReasons({includeInactive:true})`). **이건 우리 코드만의 문제가 아니었다** — 기준 데이터에서 사유 하나를 비활성으로 돌리면 **그 사유가 붙은 과거 기록 전부**가 코드값으로 보이고 있었다
→ ⚠️ 자유 입력은 `cancel_application` 에 **안 넘긴다** — 응모가 여러 건이면 같은 개인 텍스트가 관리자 알림에 반복 노출된다

**적용 후 반드시 눈으로 볼 것** — ⚠️ **SQL 편집기로는 검증 불가**(본인 확인 가드로 무조건 `not_authenticated`). 시험 인플루언서 계정 브라우저 콘솔에서:
- ★ **모집 기간이 지난 응모를 가진 계정으로 사유 없이 호출** → 그 응모가 `cancelled_count` 에 들어가는지 (이번 수정의 핵심. 빠지면 원래 결함 재현)
- `applications.cancel_reason_code` 가 실제로 `'withdrawal'` 로 저장되는지
- 미지급 있는 계정 → `pending_payout` / 없는 계정 → `scheduled` + 예정일 = 오늘+5일
- 두 번 불러도 행이 **1개**(멱등) · 감사용 계정 **거부**

### 작업 6 — 탈퇴 취소 함수 ✅ 작성 완료 (2026-08-19, **적용 전**)

마이그레이션 **349**. `cancel_withdrawal()`(인자 없음) → jsonb
`{ok, status:'cancelled', previous_status}` / 실패 시
`{ok:false, reason:'not_authenticated'|'not_found'|'audit_account_blocked'|'already_done'|'already_cancelled'|'admin_requested'}`

**요청 시점에 지시받은 것 + 이번 작업에서 새로 판단한 것**

| | 무엇 | 근거 |
|---|---|---|
| ㄱ | **`requested_by_kind='admin'` 행은 거부**(`admin_requested`) | 작업표에 없던 결정 — 요청 본문에 명시. 안 막으면 약관 제6조 3항(자격 상실)의 강제 탈퇴가 본인 취소 버튼 하나로 무력화된다. `influencer_id=auth.uid()` 만으로는 못 막는다 — 관리자가 대신 신청해도 `influencer_id` 는 그 회원 본인이라서, 반드시 `requested_by_kind` 를 직접 봐야 걸러진다 |
| ㄴ | **`done`·`cancelled` 는 각각 다른 사유로 거부** | `already_done`/`already_cancelled` 로 분리 — "신청 자체가 없다"(`not_found`)와 구분해야 클라이언트가 다른 안내를 보여줄 수 있다 |
| ㄷ | **`completed_at` 은 안 건드린다**(방어적 NULL 대입도 안 함) | 취소 가능한 대상이 애초에 `pending_payout`/`scheduled` 뿐이라, 이 함수가 다루는 행의 `completed_at` 은 항상 NULL — 값이 있는데 여기 들어왔다면 그 자체가 버그이므로 조용히 덮지 않고 `already_done` 가드가 먼저 걸리게 둔다 |
| ㄹ | **재신청→재취소 반복을 막지 않는다** | Q6 결정("몇 번 탈퇴하려다 말았나가 이탈 신호") — 반복 자체가 관찰 대상. 새로 열리는 남용 경로 없음(재가입 차단은 `done` 만 봄, 응모 취소 루프는 취소할 게 없으면 0회 반복) — 파일 내 "그 외 설계 메모"에 근거 상세 기록 |
| ㅁ | **취소 이력은 새 행 적립으로 남는다** | `cancel_withdrawal` 은 기존 행을 지우지 않고 `status='cancelled'` 로만 바꾸고, 재신청(347)의 멱등 분기는 활성 상태(`pending_payout`/`scheduled`)만 찾으므로 `cancelled` 행은 못 찾아 **새 행을 INSERT** 한다 → 재활성화가 아니라 이력 누적 |
| ㅂ | **철회된 응모는 안 되살린다**(요청에서 이미 확정 — 이유를 함수 주석에 상술) | `cancel_application` 자체가 편도(취소를 되돌리는 기능 없음) + 되살리면 마감·정원 경과와 충돌 가능 + 사양서 §4-6 ⑦ 이 이미 "되살아나지 않는다"로 명시 |
| ㅅ | **홍보 대상 복귀는 별도 처리 없음** | 작업 16(`get_promo_digest_targets` 재정의, 이번 범위 밖·미착수)이 상태를 다시 읽는 구조라면 `cancelled` 전환만으로 자동 복귀 — 지금은 그 조건 자체가 아직 없어 "복귀"랄 것도 없다 |

⚠️ **잠금 순서를 347 과 맞췄다** — `influencers` 먼저 `FOR UPDATE`, 그다음 `withdrawal_requests` 대상 행. 순서가 어긋나면 `request_withdrawal`과 `cancel_withdrawal`을 동시에 부를 때 교착 위험. **작업 7(상태 전이 예약 실행)도 같은 순서를 지킬 것** — 파일 내 주석으로 남김.

⚠️ **감사용 계정 가드는 347 과 동일**(`audit_account_blocked`) — 정상 흐름에서는 감사용 계정이 활성 탈퇴 신청을 가질 수 없지만(347 이 애초에 거부), 비정상 경로 방어로 이 함수에도 동일하게 걸어 둠.

`dev/lib/storage.js` 에 `cancelWithdrawal()` 래퍼 추가(`requestWithdrawal()` 바로 옆) — 인자 없음, 반환 형태·오류 구분(`reason` vs `error`)은 347 래퍼와 동일 패턴.

**적용 후 반드시 눈으로 볼 것** — ⚠️ **SQL 편집기로는 호출 검증 불가**(본인 확인 가드로 무조건 `not_authenticated`). 시험 데이터 준비(INSERT/UPDATE)는 서비스 키로 SQL 편집기에서 가능하지만, **실제 `cancel_withdrawal()` 호출은 반드시 로그인한 브라우저 콘솔**에서:
- ★ `haruka.test@reverb.jp` 로 재신청(`request_withdrawal`) → 취소(`cancel_withdrawal`) → `status='cancelled'` 확인 (이 계정은 정산 미지급 건이 있어 `pending_payout` 경로만 자연 재현됨 — **작업 7이 아직 없어 `pending_payout`↔`scheduled` 자동 전이가 안 돌기 때문에, `scheduled` 취소까지 보려면 미지급 0건인 별도 계정이 필요**함을 파일에 명시)
- 같은 행을 다시 취소 호출 → `already_cancelled`
- 재신청 → **새 행**이 생기고 이전 행은 `cancelled` 로 남는지(이력 보존) 조회로 확인
- (선택) 서비스 키로 `status='done'` 흉내 → `already_done` / `requested_by_kind='admin'` 행 직접 INSERT → `admin_requested`
- 마지막에 시험 데이터 정리(`DELETE FROM withdrawal_requests WHERE influencer_id=...`)

마이그레이션 파일에 위 절차 전체가 **1단계씩 순서대로** 상세 기술돼 있음(`349_cancel_withdrawal_function.sql` 하단).
