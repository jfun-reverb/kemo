## 0. 이 기획이 여는 것 — 세 번째 사용자 유형

지금까지 REVERB JP의 사용자는 **인플루언서**(일본어 앱)와 **관리자**(한국어 앱) 둘뿐이다. 브랜드 포털은 **브랜드사(광고주)** 라는 세 번째 사용자 유형을 처음으로 시스템에 들인다. 그래서 인증·접근제어·개인정보가 전부 새 영역이다.

## 1. 현재 상태 (2026-07-15, 코드·DB 직접 조사)

### 브랜드가 지금 시스템과 닿는 지점 — 전부 "입력(쓰기)"뿐, "조회(읽기)" 0
- **광고주 신청 폼**(`sales/reviewer.html`·`seeding.html`) — 로그인 없이 `submit_brand_application` 원격 호출 함수로 제출. **현재 공개 접수 차단 중**(마이그레이션 206).
- **오리엔시트 작성 폼**(`dev/sales/orient.html`) — 관리자가 발급한 토큰(`?token=`) 링크로, 로그인 없이 캠페인 콘텐츠 작성·제출. 익명 함수 3종(`get_orient_sheet`/`save_orient_draft`/`submit_orient_sheet`, 마이그레이션 187).
- **브랜드가 자기 캠페인 현황·결과물·정산을 "보는" 경로는 전혀 없음.**

### 보여줄 데이터·집계는 이미 있음 (단, 관리자 전용 잠금)
- `get_brand_ops_overview(회사)` / `get_brand_ops_detail(브랜드)` — 모집률·결과물 승인률·캠페인 목록·견적 집계(마이그레이션 120·148·149·150). 둘 다 **`is_admin()` 가드** → 브랜드가 직접 못 읽음. 브랜드 몫만 떼주는 조회 함수 신설 필요.
- 진행현황 비용 카드 산식(견적·운영비, `admin-applications.js:234~`).

### 인증·계정 구조
- 인플루언서·관리자 모두 같은 로그인(`signInWithPassword`) → 로그인 후 `admins` 테이블 조회로 분기(`auth.js:156`).
- ⚠️ **자동 등록 트리거(`handle_new_user`, 마이그레이션 014)**: 어떤 신규 계정이든 무조건 `influencers` 행을 만든다. **브랜드가 정식 로그인 계정을 만들면 인플루언서로 섞임** → 정식 계정 방식 도입 시 이 트리거부터 수정 필요.
- 브랜드측 로그인 계정 개념 없음. 브랜드 대표 담당자 이메일은 `brands.contacts`(jsonb, 정본)에 텍스트로만 존재.

### 검증된 재사용 패턴
- **토큰 기반 익명 조회 함수**(오리엔시트 3종 + 수신거부 토큰 마이그레이션 140) — 로그인 없이 토큰으로 자기 데이터만, 자원 열거 방지(`success:false`). **1차 포털 조회의 최적 템플릿.**

### 충돌 가능성 있는 기존 동작
- 오리엔시트 토큰은 **1시트 스코프**(그 시트 하나만). 브랜드 포털은 **브랜드/회사 단위** 접근이 필요 → 브랜드 단위 토큰 신설.
- 모든 브랜드 관련 테이블 SELECT가 `is_admin()` 전용 → 브랜드는 **직접 테이블 조회 불가**, 반드시 SECURITY DEFINER + 스코프 가드 함수로만.

## 3. 의심·경우의 수 (반대론자 모드)

### 깨질 수 있는 경우의 수
1. **(법률·최중요) 결과물 개별 링크 = 인플루언서 개인정보 제3자 제공** — 브랜드에게 "이 인플루언서가 우리 캠페인에 참여해 이 게시물을 올렸다"(SNS 계정·게시물 연결)를 노출하는 것. APPI(일본)/PIPA(한국) 관점에서 **개인정보처리방침 개정 + 동의(또는 캠페인 참여 시 결과물 공유 동의 근거) 확인**이 필요. 영수증은 명백한 민감정보라 브랜드 노출 제외 권장. → **법률 딥리서치가 출시 전제**(아웃바운드 명단 제3자 제공 관문과 동류, 메모리 `project_outbound_roster_privacy` 참고).
2. **(통제) 브랜드 자체 오리엔시트 생성 → 무제한 생성·스팸·잘못된 발행** — 현재는 관리자가 발급을 통제하고, 발행 시 일본어 미보완 차단 게이트가 있다. 브랜드가 스스로 만들면 이 통제가 사라짐 → **관리자 검토 게이트(제출된 오리엔시트를 관리자가 확인 후 캠페인 발행) 유지 + 브랜드 생성 수량·자격 제한** 필요.
3. **(인증 함정) 정식 계정 도입 시 자동 등록 트리거** — 2차에서 브랜드 로그인 계정을 만들면 `handle_new_user`(014)가 브랜드를 인플루언서로 등록. 트리거 분기 수정 없이는 데이터 오염.
4. **(보안) 토큰 유출** — 1차 토큰 링크가 유출되면 제3자가 브랜드 현황을 봄. 만료·재발급·브랜드 스코프 제한 필요. 특히 결과물 링크가 포함되면 유출 시 개인정보 노출.
5. **(데이터 매핑) 회사 vs 브랜드 단위** — 한 회사에 여러 브랜드, 한 브랜드에 여러 캠페인. 토큰/계정을 **브랜드 단위로 발급할지 회사 단위로 발급할지** 결정 필요(담당자 이메일은 브랜드에 붙어있음).
6. **(UX·빈 상태) 신규 브랜드** — 캠페인이 아직 없는 브랜드가 포털에 들어오면 텅 빈 화면. 안내 문구·"진행 중 캠페인 없음" 상태 필요.
7. **(환경) 세 번째 앱 신설** — `brand/` 전용 페이지 + 빌드 + 도메인(brand.globalreverb.com?) + Vercel 프로젝트 추가 여부. 1차 토큰 조회는 오리엔시트처럼 `sales/` 계열 정적 페이지로 시작 가능.

### 의도 모호점 (확인 완료 / 미결)
- ✅ 포털 성격 = 단계적(토큰→계정)
- ✅ 오리엔시트 = 브랜드 자체 생성
- ✅ 결과물 = 개별 링크
- ⬜ **토큰/계정 발급 단위 = 회사 vs 브랜드** (미결)
- ⬜ **결과물 개별 링크의 법률 판정** (딥리서치 필요)
- ⬜ **브랜드 자체 오리엔시트 생성의 통제 게이트 구체안** (미결)

## 4. 단계 설계 골격

### 1차 — 토큰 링크 조회 포털 (개인정보 관문 없는 것부터)
- **인증**: 브랜드 단위 접근 토큰(오리엔시트 토큰 패턴 확장). 로그인 없음.
- **화면**(`sales/` 계열 정적 페이지 후보):
  - **A. 모집 현황** — 지원·선정·모집률 (기존 `get_brand_ops_detail` 집계를 브랜드 스코프 wrapper로 재사용)
  - **B. 진행 단계·일정** — 캠페인 상태·마감일
  - **C. 오리엔시트** — 브랜드 자체 생성·작성·제출 (통제 게이트 포함)
- **신규 필요**: 브랜드 스코프 조회 함수(SECURITY DEFINER + 토큰 가드, anon GRANT), 브랜드 토큰 발급·관리(관리자 화면), 브랜드 자체 오리엔시트 생성 함수 + 관리자 검토 게이트.
- **D. 결과물 개별 링크는 법률 관문 통과 후** 1차 후반 또는 별도로.

### 2차 — 정식 로그인 계정
- 브랜드 계정 테이블(`brand_users`, auth_id) + `is_brand()` 판정 + 자동 등록 트리거(014) 분기 수정.
- 브랜드 스코프 접근제어(자기 회사/브랜드만) 전면 신설.
- 세 번째 앱(`brand/`) + 자체 로그인 폼.
- 회원가입·온보딩(사업자·담당자 정보).

## 5. 법률 딥리서치 결론 (2026-07-15, 완료)

> `deep-research` 실행(101개 에이전트, 19개 1차/2차 소스, 24개 클레임 검증 통과·1개 반증). 일본 개인정보보호위원회(PPC)·한국 개인정보보호위원회(PIPC) 1차 자료 기반. **결론: 결과물 개별 링크 노출은 무거운 법적 관문이며 변호사 확인이 전제.**

### 핵심 판정 (must / should)
1. **결과물 개별 링크(공개 SNS 게시물 URL·계정명) 노출 = "제3자 제공"으로 판정될 가능성 높음** (위탁 아님). 브랜드가 자기 캠페인 성과를 자기 이익으로 열람하므로, 데이터의 실질 이용 주체가 브랜드 → 위탁(委託) 구성은 무리. 한국 대법원 2016도13263 다요소 판례도 이 방향.
2. **공개된 정보라도 개인정보** (양국 공통). 일본 APPI는 공표 정보도 구별 없이 보호, 한국 PIPA는 처리자·수령자가 보유한 정보와 쉽게 결합해 식별 가능하면 개인정보. **브랜드는 이미 자기 캠페인 응모자·배송정보를 알아** 계정명이 마스킹돼도 재식별됨.
3. **캠페인 참여 동의로 자동 커버 안 됨** — must: "브랜드에게 결과물(개인정보) 제공"에 대한 **별도 명시 동의 + 개인정보처리방침 개정** 필요. (한국 PIPA 17조 5개 고지사항 / 일본 APPI 27조 사전 동의)
4. **국경 간 이전 관문 추가** — 일본 거주자 데이터를 한국 브랜드가 열람 = 국외 관련 이전. 일본 APPI 28조상 "외국 제3자 제공 인정" 취지의 **별도 사전 동의** 또는 상당조치 계약 체계 필요(한국은 PPC 적정성 인정국 아님). ⚠️ 한국 PIPA 국외이전 근거조문은 조사 중 특정 클레임이 **반증**됨 → 변호사가 실제 조문 확정 필요.
5. **★ 별표(`*`) 마스킹은 법적 부담을 완화하지 못함** (사용자 질의 핵심 판정). SNS 계정명은 그 자체로 공개·검색 가능해 부분 마스킹해도 재식별. 가명처리해도 양국 모두 **여전히 개인정보**이고, 동의 면제(통계·과학연구·공익보존)는 **상업적 브랜드 노출에 적용 안 됨**. → 마스킹으로 관문을 우회할 수 없음.
6. **영수증·구매내역 브랜드 노출 제외 = 타당** (목적 비례·최소 제공 원칙). 단 논거는 "민감정보라서"보다 "비공개 최소제공".
7. **집계 숫자(게시 N건·승인 여부)는 규제 밖에 둘 여지** — 단 참여자 소수면 브랜드가 개인 역추정 가능 → **진정한 익명·캠페인 단위 집계**여야 안전.

### 실무 체크리스트 (제3자 제공 구성 전제)
- (a) **개인정보처리방침**: 브랜드 제공 사실·수령 브랜드 범주·제공 항목(게시물 URL·계정명·게시 여부)·목적·보유기간·국외이전(한국) 사실 추가. **배포 시점에 동기화**(선제 반영 금지 — `release-timing.md`).
- (b) **인플루언서 동의**: 캠페인 응모/가입과 **분리된** "브랜드 제공 + 일본→한국 국외이전" 명시 동의(체크박스).
- (c) **안전조치**: 브랜드별 접근제어(자기 캠페인만)·열람 로그·영수증 등 서버 마스킹·최소 항목 노출.

### 법률 자문이 반드시 필요한 지점
① 위탁 vs 제3자 제공 최종 판정(계약 구조·이익 귀속) ② 일본→한국 국경 간 이전 적법 경로 + 한국 PIPA 국외이전 근거조문 확정(반증된 지점) ③ 동의 문안·방침 개정문의 양국 이중 준수.

### 이 결론이 기획에 주는 함의 + 사용자 결정 (2026-07-15)
- **결과물 개별 노출 = 무거운 관문** — 제3자 제공 + 국외이전 + 별도 동의 + 방침 개정 + 변호사 확인이 모두 전제. 별표 마스킹으로도 못 줄임(SNS 계정 재식별).
- **사용자 결정: 결과물 3종(SNS 게시물 링크 · 리뷰 캡처 이미지 · 영수증·구매내역) 개별 노출 진행.** 근거 = 타 인플루언서 시딩 플랫폼도 결과물을 브랜드에 제공하는 **업계 표준**. → 딥리서치와 배치 안 됨: 타 플랫폼도 **인플 동의를 받아** 적법화한 것이라, "동의 받으면 가능"의 방증. 막힌 건 "동의 없이 마스킹 우회"뿐.
- **진행 전제 3종 (must)**: ①인플루언서 동의(응모/가입 시 "결과물 브랜드 제공 + 일본→한국 국외이전" 명시) ②개인정보처리방침 개정(배포 시점 동기화) ③국외이전 경로 변호사 확인(우리 특유 관문 — 타 플랫폼은 일본 내수라 국경 없음).
- **⚠️ 영수증 특별 취급 (반대론자 기록)**: 영수증·구매내역은 비공개 민감정보(구매처·금액·이름·주소·결제수단). SNS 공개 게시물과 층위가 다름. → **개인정보(이름·주소·결제수단) 마스킹 후 노출** 권장(여기선 마스킹이 "정보 최소화"로 유효 — 계정 재식별 무효와 별개 층위). 원본 그대로 노출은 위험. 영수증 포함으로 변호사 확인 비중↑.

## 9. 브랜드 자체 오리엔시트 생성 통제 게이트 (2026-07-15)

### 현재 상태 (이미 발행 단계에서 통제)
- 브랜드는 관리자 발급 토큰으로 **작성·제출까지**. 발행(캠페인화)은 관리자(`is_admin`, `mark_orient_card_consumed` 마이그196). **일본어 미보완 차단 게이트**(`addCampaign` — 가이드 비면 campaign_admin 이상 사유 입력 긴급 발행). 제출 알림 인프라(`notify-orient-submitted` + 과다발송 방지 게이트). 30일 기한(`token_expires_at` — 저장·제출 시점에만 만료로 바뀜, 자동으로 도는 작업 없음 — §13-1).

### 결정 (사용자): 생성·제출 자율 / 캠페인 발행 관리자
- **브랜드**: 포털에서 오리엔시트 **생성·작성·제출까지 자율**.
- **관리자**: **캠페인 발행 검토 유지**(현 구조 그대로) — **핵심 통제**. 브랜드가 만들어도 "생성=초안 제출"까지이고 "생성=캠페인"이 아님.
- **신규 필요**: 브랜드 토큰용 **생성 함수**(익명, 토큰 검증). 현 `create_orient_sheet`는 `is_admin` 가드라 확장 또는 브랜드 토큰용 신규 함수.
- **보조 통제 4종**: ①브랜드당 동시 미처리(**캠페인 등록 전**) 오리엔시트 **수량 상한** ②30일 만료(기존 — ⚠️ §13-1 조사로는 자동으로 도는 만료 작업은 없고 저장·제출 시점에만 만료로 바뀐다. 방치 흡수는 아래 반대론자 기록의 날짜 기준 수량 상한으로 해결 — 자동 만료 작업은 필요 없다) ③제출 시 **관리자 알림·검토 큐**(기존 인프라 재사용) ④**생성 자격 = 발급된 브랜드 토큰 보유 브랜드만**.

### 반대론자 기록
- **캠페인 발행 게이트를 관리자가 쥐므로** 잘못된 내용·일본어 미보완이 인플루언서 화면에 **바로 노출되지 않음**(핵심 리스크 차단). 브랜드 자체 생성의 편의는 살리고 통제 부담은 발행 단계에 집중.
- **스팸·방치**는 수량 상한 + 30일 만료로 흡수. ⚠️ 만료가 자동으로 돌지 않는다(§13-1) — 그래서 수량 상한을 상태값이 아니라 **날짜로** 센다(해결, 아래). ⚠️ 견적 2차 시트에서 30일은 **미제출 시트만** 끝낸다 — 「검토 중」 방치는 관리자 목록의 검토 중 표시(§13-4 ③)로 메운다. ①의 수량 상한은 **판정 기준 한 줄로 센다 — 「작성 기한(발급 + 30일) 안」이면서 「카드가 하나도 캠페인에 등록되지 않은」 시트**(상태 이름·견적 1·2차와 무관). 그래서 기한이 지난 시트와 카드가 하나라도 등록된 시트는 세지 않는다 — 방치된 시트가 새 시트 작성을 영구히 막지 않게. 견적 2차 시트의 기한 뒤 방치는 관리자 목록의 「검토 중」·「유효기간 지남」 표시(§13-4 ③)로 운영팀이 정리한다(견적 1차는 지금처럼 따로 정리하지 않는다).
- ⚠️ 브랜드가 만든 오리엔시트는 신청 개념을 모르므로 `brand_id`에 붙는 **독립 오리엔시트**로 생성 → 관리자가 캠페인 발행 시 캠페인·신청 연결(기존 링크 경로).

## 8. 인플루언서 동의 설계 (2026-07-15)

### 현재 상태 (핵심 발견 — 완전 신설 아님, 강화·확장)
- **개인정보처리방침 §3.1 「브랜드 제공」이 이미 존재** — 제공 항목에 "게시된 콘텐츠 링크", 목적에 "콘텐츠 확인·캠페인 리포트 작성", **"신청·승인 시점에 동의한 것으로 간주"**. 즉 SNS 링크 제공은 이미 방침·동의 구조로 운영 중.
- **약관 근거**: 제19조(콘텐츠 링크 1년 무상 사용권을 회사·브랜드에 부여), 제11조(브랜드 콘텐츠 링크 활용), 제18조(브랜드 리포트 목적 SNS 데이터 이용).
- 동의 컬럼: `influencers.terms_agreed_at`·`privacy_agreed_at`(마이그022)·`age_consent_at`(마이그185), `applications.caution_agreed_at`+`caution_snapshot`(마이그067). 재동의 선례 = 연령 게이트(응모 직전 소급, 유일한 실제 재수집 동의). 약관 개정 재동의는 「묵시적 동의 + 사전 통지」 방침(사양서 `2026-05-28-policy-versioning.md`).

### 결정 (사용자, 2026-07-15): 방침 개정 + 동의 간주
현행 §3.1 방식(신청·승인 시 동의 간주)을 **유지·확장**. 명시 체크박스 신설 안 함.

**개정할 항목** (개인정보처리방침, 한·일 동시):
1. §3.1 브랜드 제공 **항목에 리뷰 캡처·영수증 추가** (영수증은 개인정보[이름·주소·결제수단] 마스킹 후).
2. §3.1 제공 **목적에 "브랜드 포털 열람" 추가**.
3. §5 국외이전에 **"한국 브랜드가 한국에서 열람" 경로 추가**(현재 §5는 클라우드 인프라만).

**기존 회원(약 1,400명)**: 별도 소급 게이트 없이 **방침 개정 + 사전 통지**(묵시적 동의, policy-versioning 패턴). 통지 인프라(마이그153 `policy_notice_*` + Edge Function `notify-policy-change`) 재사용.

### ⚠️ 반대론자 기록 — 안전지대 / 위험지대
| 결과물 | 동의 간주 적합성 | 대응 |
|---|---|---|
| SNS 게시물 링크 | ✅ 안전(이미 운영 중) | 방침 목적 확장만 |
| 리뷰 캡처 | 🟡 주의 | 항목 추가 + 캡처 내 개인정보 마스킹 |
| 영수증 | ⚠️ 위험(민감정보) | 마스킹 필수 + **변호사 확인** |
| 국외이전(한국 브랜드) | ⚠️ 가장 위험 | APPI 28조 외국이전 본인동의 원칙 → **변호사 확인이 핵심** |

- **동의 간주 vs 명시 동의**: 사용자 결정은 동의 간주(가벼움)이나, **영수증·국외이전 두 항목은 변호사 판단에 열어둠**.
- **★ 2차 심화 딥리서치 정정 (2026-07-15) — 국외이전은 동의 간주 불가 확정**:
  - **한국 PIPA 제28조의8**(국외이전, 2023-09-15 시행)이 **"별도의 동의"를 명문 요구** → 묵시적·번들 동의로 불가. "제공(조회되는 경우 포함)"이라 **브랜드 포털 열람이 직접 포섭**됨.
  - **일본 APPI 제28조**(외국 제3자 제공)도 사전 본인 동의 + 3종 고지(외국 명칭·보호제도·수령인 조치) 요구.
  - → **한국 브랜드 열람(국외이전) 부분은 "동의 간주"로 적법해지지 않는다.** 두 대안: **(A) 명시 동의**(국외이전 부분만 별도 체크박스, 문구는 부드럽게) / **(B) 계약 기반 상당조치 경로**(브랜드와 계약 시 명시 동의 없이 — 단 브랜드마다 계약). **어느 경로든 변호사 확정.**
  - **★사용자 결정 (2026-07-15): (A) 인플루언서 명시 동의**. 구현 방향 — 응모 시 체크박스 1개 추가(「한국 브랜드가 검수를 위해 결과물을 확인하는 것에 동의합니다」, 문구는 부드럽게 §8 톤 / 법정 고지 5+3종은 펼침·링크). 기존 주의사항 동의·연령 게이트 패턴 재사용. 기존 회원은 **응모 직전 소급 게이트**(연령 게이트 선례)로 취득. 즉 최종 동의 구조 = **브랜드 제공은 방침 개정+동의 간주 / 국외이전은 명시 체크박스** 하이브리드. (문안·고지 완전성 변호사 확정.)
  - (1차 조사가 이 조문을 "반증"했으나 오류였음 — 옛 법과 착각. 2차에서 25개 클레임 전부 검증 통과로 정정.)

### 인플루언서 안내 문구 톤 (2026-07-15 사용자 지시)
- **딱딱한 법률용어·위협적 표현 지양** — "국외이전", "당신 정보가 (해외로) 넘어갑니다" 같은 표현 금지. 인플루언서가 겁먹지 않게.
- **목적 중심의 쉬운 말** — 예: 「**한국 브랜드가 검수를 위해 결과물을 확인할 수 있습니다**」(주체=한국 브랜드 / 목적=검수 / 행위=확인). 인플루언서 안내 초등학생 눈높이 규칙(`.claude/rules/ui.md` 「인플루언서 안내 문구」)과 일치.
- ⚠️ **단 법적 고지 완전성은 유지** — 톤은 부드럽게 하되, "한국 브랜드가 본다"는 **사실 자체를 숨기거나 모호하게 하면 동의 무효 위험**. 사용자 제안 표현은 주체·목적·행위를 다 담아 부드러움 + 고지 요건을 함께 충족. 톤은 순화, 사실은 정확 — 최종 고지 완전성은 변호사 검토.
- 이 톤 원칙은 인플루언서에게 보이는 동의 체크박스·안내 배너·통지 메일 문구 전반에 적용.

## 11. 변호사 자문 후 갖춰야 할 증빙 체크리스트 (2026-07-15)

> **"변호사가 괜찮다고 하면 끝"이 아니다.** 변호사 자문은 *"무엇을 갖춰야 적법한지"*(설계도)이고, 실제 본체는 **그 조건을 이행하고 증빙을 남기는 것**이다. 법은 "변호사 자문을 받아라"가 아니라 "적법하게 처리하라(동의·고지·안전조치)"를 요구한다. 이 체크리스트는 "괜찮다만 받고 끝내는" 실수를 막는다.

### 변호사 답변의 성격
- 보통 "그냥 괜찮다"가 아니라 **"이런 조건(동의·마스킹·계약·기록)을 갖추면 괜찮다"는 조건부**. 그 조건을 실제로 이행해야 한다.
- **서면 자문의견서**(조건·전제·한계 명시)를 받아둔다 — 법적 필수는 아니나, 규제기관 조사·분쟁 시 "성실 노력" 방어 자료 + 자문 범위 명확화. 구두 "괜찮다"는 근거로 쓰기 어렵다.

### 실제로 남겨야 할 증빙 (법적 본체)
| 증빙 | 필요성 | 우리 현황 |
|---|---|---|
| **인플루언서 동의 기록**(누가·언제·무엇에) | ✅ 법적 필수 | `influencers.*_agreed_at`·`applications.caution_*` 등 동의 시각 기록 구조 **이미 있음**(유리). 브랜드 제공·국외 관련 이전 동의도 동일 패턴으로 기록 설계 |
| **개인정보처리방침 개정·공지 이력**(언제 무엇 고지) | ✅ 필수 | 부칙 개정 이력 + 통지 인프라(마이그153 `policy_notice_*`) 재사용 |
| **제3자 제공 기록**(누구에게 제공) | ✅ 필수(일본 APPI, 원칙 3년 보존) | **신규 필요** — 어느 브랜드에 어느 회원 정보를 언제 제공했는지 기록 테이블/로그. 딥리서치 확인 항목 |
| **위탁 계약서**(위탁 구성 시) | ✅ 위탁이면 필수 | 브랜드와의 계약서(위탁으로 판정될 경우) — 범위 초과 처리 금지·안전조치 명시 |
| **접근 로그**(브랜드가 언제 무엇을 열람) | 🟡 권장(안전조치) | 브랜드 포털 열람 로그 — 사고 시 추적. `PROJECT_CONTEXT.md` 「접근 로그」 방향과 일치 |
| **변호사 서면 의견서** | 🟡 필수 아니나 강력 권장 | 방어 자료 |

### 확신도·한계
- 위 큰 원칙(자문≠증빙, 동의·공지·제공기록이 본체 = 개인정보보호 「책임성 원칙」)은 일반적으로 타당.
- **정확한 증빙 양식·보존 기간·제3자 제공 기록 세부 요건**은 나라·상황별로 달라 **변호사 확정 영역**.
- → 변호사 자문 시 **"증빙으로 무엇을·어떤 양식으로·얼마나 보존할지"까지 함께 확인**할 것(자문 질문에 포함).

## 12. 변호사에게 넘길 질문 리스트 (딥리서치 2회 산출 — 자문 준비)

> 딥리서치 2회(1차 판정 + 2차 심화, 각 100+ 에이전트·양국 규제기관 1차 자료)로 아래 쟁점을 사전 정리했다. 변호사는 "무엇을 검토할지"를 처음부터 찾을 필요 없이, 이 목록을 **우리 사실관계(계약 구조·데이터 흐름)에 적용해 확정·책임**하면 된다. → 자문이 빠르고 저렴해짐.

### 딥리서치로 이미 확정된 것 (참고로 제시, 재확인만)
- 결과물(공개 SNS 게시물·계정명 포함)은 양국 개인정보 → 브랜드 제공 = 제3자 제공.
- 별표(*) 마스킹으로 개인정보성 우회 불가.
- 한국 국외이전 근거 = **PIPA 제28조의8**(2023-09-15, "별도의 동의"·"조회 포함"). 일본 = **APPI 제28조**(외국 제3자 제공 + 3종 고지).
- 국외이전은 **동의 간주 불가**.
- 제3자 제공 기록 의무: 제공 때마다 기록, 원칙 3년 보존(일본 APPI 29조).
- 스텔스 마케팅(일본 景表法, 2023-10-01): 규제 대상 = 브랜드사(광고주), 인플루언서 아님.

### 변호사 확정이 필요한 질문 (사실관계·판단 종속)
1. **위탁 vs 제3자 제공 최종 판정** — 브랜드 포털 열람을 APPI 27조5항 "위탁"으로 구성하려면 계약상 최소 조건(재활용 금지·목적 검수 한정·처리 수단 결정권 유지)이 무엇인가? 우리 구조가 실제로 위탁에 포섭되는가?
2. **국외이전 경로 선택** — (A) 인플루언서 명시 동의 vs (B) 한국 브랜드와 상당조치(계약 기반) 체제. 우리 상황(브랜드 다수)에 어느 쪽이 실무적으로 나은가? 한-일 표준계약에 넣을 구체 조항 세트는?
3. **동의 UI·문안** — 명시 동의로 갈 경우, 국외이전 별도 동의(한국 5개 고지)와 일본 APPI 28조 3종 고지를 캠페인 신청·승인 시점에 어떤 화면·문안으로 분리 제시해야 "별도성"·"사전 고지"를 동시 충족하는가? (인플 눈높이 톤 §8 유지하면서)
4. **영수증 마스킹 수준** — 영수증이 일본 要配慮個人情報 / 한국 민감정보에 해당하는가? 성명·주소·결제수단·카드번호를 어느 수준까지 가려야 "최소 제공"으로 적법한가? (딥리서치 2회 미해결 — 자문 핵심)
5. **증빙 요건 확정** — 제3자 제공 기록·국외이전 기록의 정확한 양식·보존기간, 동의 기록·방침 공지 이력의 증빙 형태(§11 체크리스트 검증).
6. **다른 법 누락 점검** — 개인정보보호법·景表法 외에 이 기능에 걸리는 법이 더 있는가?

### 자문 요청 시 함께 전달할 것
- 이 사양서(특히 §5·§8·§10·§11·§12) + 딥리서치 2회 결과 요약.

## 13. 오리엔시트 견적 흐름 — 1차 현행 유지 / 2차 「관리자 견적 발행」 (2026-10-13)

> 이 절은 **오리엔시트 견적**이라는 한 축만 다룬다. 위 §4의 「포털 1차(토큰 조회)·2차(정식 계정)」와는 **다른 축**이다. 아래에서 「견적 1차·견적 2차」라고 부른다.
> 이 절은 §2 결정표의 「견적·입금 내역 — 제외」 줄을 **오리엔시트 견적에 한해 보완**한다(입금은 여전히 범위 밖). 「견적 확인」을 포털 니즈에 넣는 것(추천: 넣음)과 견적 2차 전환 시점은 §13-6 4번에서 정한다.
> 용어: **「견적 발행」**(금액을 확정해 브랜드에게 보여 줌)과 **「캠페인 발행」**(인플루언서에게 공개)을 이 절부터 구분해 쓴다.

### 13-1. 현재 상태 (2026-10-13 코드 조사)

**브랜드 화면** — `sales/orient.html`(`dev/sales/orient.html` 과 같은 내용)
- 흐름: 작성 → 「작성 완료」(`btnReview`) → **입력 내용 확인**(`openPreview`·`renderPreview`) → 「견적 보기」(`openQuotePreview`) → **견적서**(`showQuoteScreen`) → 「제출하기」(`submitSheet`) → 완료 화면(`enterDoneScreen`, 견적서가 펼쳐져 있음)
- 견적은 **서버가 입력값으로 자동 계산**한다. 미리보기는 `preview_orient_quote`(저장 없음, 현재 원본 430), 제출은 `submit_orient_sheet`(현재 원본 461). 둘 다 안에서 `_orient_compute_quote`(현재 원본 463) **한 벌**을 부른다
- 제출 뒤에도 「내용 수정하기」로 고쳐 다시 제출할 수 있다. **견적 차수(`revision`)는 다시 제출할 때만** 오르고(임시저장으로는 안 오름) 지난 판은 `quote_history` 에 쌓인다(`orient_sheets.data` 안). **캠페인 발행(`consumed`)된 시트와 기한이 지난 시트는 수정이 막힌다**
- 견적서는 「인쇄 · PDF」 단추로만 저장한다(`printQuote`). 견적서를 그리는 코드는 `orient.html` 한 벌이고, 관리자 화면은 **저장된 시트**를 `?embed=quote` 로 끼워 보여 준다

**상태값** — `orient_sheets.status`
- `draft` → `submitted`(제출) → `consumed`(모든 카드가 캠페인 발행됨). 기존 캠페인 연결을 풀면 `consumed` → `submitted`
- `expired`: 발급 때 기한을 **+30일**로 잡고, 이 날짜가 견적서의 「유효기간」이기도 하다. **기한이 지난 뒤 저장·제출을 시도할 때만** `expired` 로 바뀐다(따로 도는 만료 작업은 못 찾음)
- 카드(제품) 단위 상태 칸은 없다 — `cards[].campaign_id`·`linked_existing` 유무로 판정

**관리자 화면** — `dev/js/admin-orient.js`
- 견적은 **보기·인쇄만** 된다(`osQuoteCard`·`osOpenQuoteDoc`). 관리자가 견적을 발행하거나 금액을 고치는 기능은 **없다**
- 발급할 때 모집비 직접 지정만 된다(캠페인 관리자 이상, 서버 거부 `recruit_fee_forbidden`)
- 광고주 신청(서베이)의 견적 칸(`quote_sent_at`·`quote_sent_url`·`final_quote_krw`)은 오리엔시트 견적과 **별개**로 손으로 입력한다
- 제출 알림 메일(`notify-orient-submitted`)에는 과다 발송 게이트가 둘 있다 — 같은 제출이면 건너뛰고, 재제출은 30분 안에 다시 보내지 않는다

**충돌 가능성 있는 기존 동작**
- 캠페인 발행 함수(`mark_orient_card_consumed`)·기존 캠페인 연결 함수(`link_orient_card_to_campaign`)가 **`status='submitted'` 를 전제**한다 → 2차에서 `status` 값을 새로 늘리면 이 둘이 깨진다(13-4 ②에 반영)
- 🔴 **확인 필요(결함 후보)**: 기한 전에 열어 둔 화면에서 기한이 지난 뒤 저장하면, **이미 제출된** 시트가 `expired` 로 바뀌어 캠페인 발행이 실패할 수 있다(461 의 기한 검사 → 196 이 `submitted` 만 받음). 코드 추론일 뿐 재현하지 않았다. 견적 1·2차와 무관하게 13-5 의 0번에서 처리한다
- 브랜드는 기한(30일)이 지나면 완료 화면의 견적서를 다시 볼 수 없다(조회 단계에서 기한 오류 화면)

### 13-2. 사용자 결정 (2026-10-13)

| 항목 | 결정 |
|---|---|
| 견적 1차 | **지금 방식 그대로** — 작성 → 입력 확인 → 견적서(자동 계산) → 제출 |
| 견적 2차 흐름 | 브랜드가 **요청** → 관리자(담당자)가 **확인** → 관리자가 **견적서 발행** |
| 2차 예상 견적 | **참고용으로 보여 준다** — 제출 전 확인 화면에 「예상 금액(참고용)」 |
| 관리자 금액 조정 | **항목별 조정 + 할인 줄 + 브랜드에게 보이는 메모**. 캠페인 관리자 이상. 바꾼 내역은 이력으로 |
| 브랜드 수락 단계 | **두지 않는다** — 브랜드는 보기·인쇄만, 수락은 지금처럼 메일·전화 |
| 견적 발행 뒤 브랜드 수정 | **고쳐서 다시 제출하면** 발행 견적은 「이전 판」이 되고 다시 「검토 중」. **다시 제출하는 순간 현재 차수에 발행 견적이 있으면 확인 창**으로 알린다. 카드가 하나라도 캠페인에 등록된 뒤에는 **수정 잠금** |
| 견적 유효기간 (견적 2차 시트) | **견적 발행일 + 30일**. 작성 기한(발급 + 30일)이 지나도 **제출된 시트의 완료 화면(검토 중·발행 견적)은 읽기 전용으로 계속 볼 수 있다**. 견적 1차 시트는 지금처럼 발급 + 30일 · 기한 뒤 보기 없음 |
| 견적 발행과 캠페인 발행 순서 | **견적 먼저** — 견적 2차 시트는 현재 차수의 발행 견적이 없으면 캠페인 발행·기존 캠페인 연결을 **서버가 거부**한다 |

### 13-3. 의심·경우의 수 (반대론자 모드)

**깨질 수 있는 경우**
1. **(화면 — 기다림)** 2차에서 브랜드는 제출 뒤 견적이 나올 때까지 기다린다. 「검토 중」 안내·예상 소요·발행 알림 메일이 없으면 「제출이 된 건가」 문의가 온다 → 완료 화면 문구 + 발행 알림 메일(13-4 ⑤)
2. **(동시 수정)** 관리자가 견적을 고치는 동안 브랜드가 내용을 다시 제출하면 견적이 **옛 내용 기준**이 된다 → 발행 요청에 「어느 차수를 보고 만든 견적인가」를 싣고, 서버가 그 사이 다시 제출됐으면 **거부**한다(13-4 ③)
3. **(기한)** 지금은 발급 + 30일이 작성 기한 **겸** 견적 유효기간이다. 2차에서 관리자 검토가 늦으면 **브랜드 잘못이 아닌데** 유효기간이 준다 → 견적 유효기간을 발행일 기준으로 가른다(13-4 ⑥, 2026-10-13 결정)
4. **(전환)** 2차로 바꾸는 순간 이미 자동 견적을 받은 시트가 어떻게 보일지 → **시트마다 견적 방식을 기록**해, 전환 날짜가 아니라 그 시트가 만들어질 때의 방식으로 판정한다(13-4 ①)
5. **(말 — 「발행」이 둘)** 2차부터 「견적 발행」과 「캠페인 발행」이 같은 말을 쓴다. 디자인 시안의 상태 「발행됨」도 어느 쪽인지 모호했다 → 브랜드 화면 상태 이름을 나눈다(13-4 ⑦, 시안 반영 완료)
6. **(이중 기록)** 서베이의 「견적 발송」 기록과 오리엔시트 발행 견적이 따로 놀면 운영팀이 두 곳에 적는다 → 연결 여부 사용자 확인 필요(13-6)
7. **(권한별 화면)** 캠페인 매니저가 견적 발행 단추를 보고 눌렀다가 거부되는 것은 사고 → 권한이 없으면 단추를 회색으로 두고 이유를 말한다(13-4 ③)
8. **(알림이 묻힘)** 견적 발행 뒤 브랜드가 30분 안에 고쳐 다시 내면, 지금의 30분 게이트 때문에 관리자 알림이 안 가고 시트가 「검토 중」에 멈춘다 → 관리자 목록의 「검토 중」 표시로 메우고, 「발행 견적 뒤 재제출」은 30분 게이트의 예외로 둔다(13-4 ⑤)

**현재 구현과 어긋나는 지점**
- 관리자 견적 발행 기능 자체가 없다(신설)
- 캠페인 발행·연결 함수가 `status='submitted'` 를 전제 → **`status` 값은 늘리지 않고**, 견적 2차 시트에만 「현재 차수 발행 견적 있음」 검사를 더한다(13-4 ②)
- 견적서를 그리는 코드는 `orient.html` 한 벌이라는 규칙 → 관리자 발행 창의 미리보기도 **같은 그리기 코드**를 써야 한다. 그런데 지금의 끼워 보기는 **저장된 시트만** 보여 준다(13-4 ③에서 처리)

**의도와 다르게 읽힐 수 있는 부분**
- 「요청」: 2차에서도 브랜드는 지금처럼 **내용을 다 채워서** 제출한다(빈 요청이 아님). 바뀌는 것은 금액을 누가 확정하느냐뿐
- 「견적서 발행」: 금액을 확정해 브랜드에게 보여 주는 것. **캠페인 발행과 별개**이고, 견적 2차에서는 **반드시 그보다 앞**이다(13-2)
- 「수락은 메일·전화」: 시스템에는 **수락 기록이 남지 않는다**. 금액 분쟁 때 근거는 발행 이력(누가·언제·얼마)뿐이다

### 13-4. 견적 2차 설계

**① 시트마다 견적 방식을 기록** — `자동`(견적 1차) / `관리자 발행`(견적 2차)
- **시트가 만들어질 때** 정해지고 바뀌지 않는다 — 관리자 발급이든, 포털에서 브랜드가 직접 만들든(§9) 같다
- 새 시트의 기본값은 설정 하나로 고른다(전환 = 그 설정을 바꾸는 것)
- 기존 시트는 전부 `자동` → 전환해도 옛 시트의 화면이 바뀌지 않는다
- 되돌리기: 설정을 되돌리면 **새 시트만** `자동` 으로 돌아간다. 이미 만든 `관리자 발행` 시트는 그대로이므로 관리자가 끝까지 견적을 발행해야 한다

**② 상태는 기존 4개 그대로 두고 「발행 견적」을 따로 둔다**
- `status` 에 값을 늘리지 않는다(캠페인 발행·연결 함수가 `submitted` 를 전제)
- 대신 「발행 견적」(금액 항목·할인·메모·발행자·발행 시각·**근거 차수**)과 그 이력을 따로 저장한다
- 화면 상태 판정(견적 2차 시트):
  - `submitted` + 현재 차수의 발행 견적 없음 = **검토 중**
  - `submitted` + 현재 차수의 발행 견적 있음 = **견적 발행됨**
  - `consumed` = **캠페인 등록됨** — 지금처럼 수정이 막혀 있으므로 「검토 중」으로 돌아갈 일이 없다
  - **일부 카드만 캠페인 등록된 시트**(아직 `submitted`)와 **캠페인 연결을 풀어 `submitted` 로 돌아온 시트**: 견적 2차에서는 **카드 하나라도 캠페인 등록되면 브랜드의 수정·재제출을 막는다**(2026-10-13 결정). 그래야 이미 만든 캠페인과 발행 견적이 같은 차수에 묶여 있고, 남은 카드가 「견적 먼저」 검사에 막히지 않는다. 화면 상태는 **「캠페인 등록 중 (n/m)」**. 캠페인 연결을 **전부** 풀어 등록된 카드가 0개가 되면 잠금이 풀리고 상태는 「견적 발행됨」(현재 차수 발행 견적이 없으면 「검토 중」)으로 돌아간다
- 수정 중(다시 제출 전) 임시저장 상태에서는 화면에 **「견적 발행됨 · 수정 중」**(또는 검토 중에 고치는 경우 **「검토 중 · 수정 중」**)으로 보인다 — 차수가 아직 안 올랐기 때문이다. 다시 제출하는 순간 「검토 중」
- 작성 기한이 지나면 「· 수정 중」을 떼고 **마지막 제출 차수의 상태**(검토 중·견적 발행됨)로 표시한다 — 다시 제출할 수 없으므로(13-4 ⑥)
- **「만료」 판정**: 견적 2차 브랜드 화면에서 「만료」는 **제출 차수가 하나도 없는 시트**이면서 **작성 기한(발급 + 30일)을 넘겼거나 `status` 가 `expired` 인 경우**만이다. 제출 차수가 있으면 `status` 값과 관계없이 만료로 보지 않는다. 제출된 시트는 기한이 지나도 「검토 중」·「견적 발행됨」으로 남고, 관리자는 기한 뒤에도 견적을 발행할 수 있다(13-4 ⑥·13-5 1번②)
- **견적 발행의 기준은 「마지막으로 제출된 차수의 내용」**이다. 관리자 화면의 자동 계산 출발점도 그 내용으로 만든다. 브랜드가 임시저장 중인 미제출 내용은 쓰지 않는다. 🔴 임시저장이 제출된 내용을 같은 자리에 덮어쓰는 구조라면 **제출 차수의 내용을 따로 보존**해야 한다 — 어느 쪽인지는 개발 세션이 13-5 1번에서 확인
- **견적 먼저(13-2)**: 견적 2차 시트는 현재 차수의 발행 견적이 없으면 캠페인 발행(`mark_orient_card_consumed`)·기존 캠페인 연결(`link_orient_card_to_campaign`)을 서버가 거부한다. 관리자 화면은 그 단추를 회색으로 두고 「견적서를 먼저 발행해 주세요」를 보여 준다. 견적 1차 시트는 지금과 같다

**③ 관리자 — 견적 발행 창** (오리엔시트 상세 안)
- 자동 계산값을 출발점으로 채운다 → 항목별 금액 수정 · 할인 줄 추가 · 브랜드에게 보이는 메모
- 미리보기는 `orient.html` 의 견적서 그리기 **한 벌**을 쓴다. 아직 저장 안 된 값을 넘기는 방법(임시 저장 뒤 끼워 보기 / 값을 전달해 그리기만 공유 등)은 **개발 세션이 정한다** — 단 그리기 코드를 두 벌로 만들지 않는다
- 「발행」 → 확인 창 → 저장 + 이력 + 브랜드 알림 메일
- 권한: 캠페인 관리자 이상(모집비 직접 지정과 같은 선). 캠페인 매니저에게는 단추를 회색으로 두고 이유를 보여 준다. **서버가 다시 검사**한다
- 서버는 합계를 **항목에서 다시 계산**해 저장한다(화면이 보낸 합계를 믿지 않는다)
- 서버는 「근거 차수」가 지금 시트 차수와 다르면 거부한다(경우의 수 2)
- 관리자 목록에서 「검토 중」 시트를 눈에 띄게 보여 준다(알림 메일이 묻힐 때의 안전망 — 경우의 수 8). 견적 유효기간(발행일 + 30일)이 지났는데 캠페인 등록이 없는 「견적 발행됨」 시트는 **「유효기간 지남」**으로 표시한다(방치 안전망)

**④ 브랜드 화면** (`sales/orient.html`, 시트의 견적 방식이 `관리자 발행` 일 때만)
- 확인 화면의 견적서에 **「예상 금액(참고용) — 확정 견적은 담당자가 발행합니다」** 표시. 참고용 견적서의 유효기간 자리에는 날짜 대신 **「발행일로부터 30일(확정 견적에서 안내)」**
- 제출 단추 이름 「제출하기」 → 「견적 요청하기」
- 완료 화면: 「검토 중 — 담당자가 확인한 뒤 견적서를 보내 드립니다」. 예상 소요 문구는 13-6 에서 정한다
- 발행되면 같은 링크에서 **확정 견적서**를 본다(인쇄·PDF 그대로). 수락 단추는 없다
- 견적 발행 뒤 「내용 수정하기」 → 작성 화면 맨 위에 안내 줄 「발행된 견적서가 있는 시트를 고치고 있습니다. 다시 요청하면 새 견적서를 받습니다」 → 「견적 요청하기」를 누를 때 **현재 차수에 발행 견적이 있으면** 확인 창 「다시 요청하면 지금 발행된 견적서는 이전 판이 되고, 다시 검토를 거쳐 새 견적서를 받습니다」 → 다시 제출하면 검토 중
  - 확인 창을 「다시 제출할 때」 띄우는 이유: 「검토 중」에 고치기 시작했는데 그 사이 견적이 발행된 경우에도 빠짐없이 알리기 위해서다(시작할 때만 띄우면 이 경로가 확인 없이 지나간다)
- 카드가 캠페인에 등록된 시트는 「내용 수정하기」를 회색으로 두고 「캠페인이 등록되어 수정할 수 없습니다. 담당자에게 문의해 주세요」를 보여 준다 · 상태는 「캠페인 등록 중 (n/m)」
- 🔴 견적 방식이 `자동` 인 시트에서는 **견적 2차 변경 때문에** 지금과 **한 글자도 달라지지 않는다**(상품 기능 §14 는 별개)

**⑤ 메일 둘**

## 14. 브랜드 상품 관리 — 저장한 상품으로 오리엔시트 작성 (2026-10-13)

> 포털 **2차(정식 로그인 계정, §4)** 와 묶는다. 「저장해 두고 다시 쓰기」는 상품 목록의 주인(로그인한 브랜드)이 있어야 성립하기 때문이다. 견적 1·2차(§13)와는 **다른 축**이다 — 어느 견적 방식의 시트에서든 쓸 수 있다.

### 14-1. 현재 상태 (2026-10-13 코드 조사)
- **상품을 저장해 두는 표가 없다.** 오리엔시트를 쓸 때마다 카드(제품)별로 판매 URL·제품명·판매가·가이드를 새로 입력한다(`sales/orient.html` 카드 양식)
- **Qoo10 불러오기가 이미 있다** — 서버 함수 `qoo10-product-lookup`: Qoo10 주소를 주면 상품번호·제품명·판매가(販売価格)·정가·행사가·대표 이미지·브랜드명을 돌려준다. 폼의 「큐텐에서 불러왔어요 · 확인해 주세요」가 이것
  - 🔴 관문 3종이 한 세트다 — ①**살아 있는 오리엔시트 작성 토큰**만 ②qoo10.jp 주소 + 상품번호 ③토큰당 분당 5회(데이터베이스 계수). → **상품 관리 화면(오리엔시트 토큰 없음)에서 부르려면 관문 ①을 「로그인한 브랜드 계정」으로 바꾼 새 관문이 필요**하다
  - 🔴 행사가(メガ割時)는 판매가 칸에 쓰면 틀린다 — 판매가는 販売価格
- 광고주 신청(서베이)의 `products` 는 그 신청서 안의 기록일 뿐 다시 꺼내 쓰는 구조가 아니다
- 캠페인은 오리엔시트 카드 값을 **발행할 때 복사**한다(`applyOrientCardPrefill`) — 카드 사본 기준이라 상품 표가 생겨도 이 흐름은 그대로 돈다

### 14-2. 의심·경우의 수 (반대론자 모드)
1. **(데이터 — 과거 기록이 바뀜)** 상품의 가이드를 고쳤을 때 이미 제출된 오리엔시트·발행 견적·캠페인이 따라 바뀌면 안 된다 → 오리엔시트에는 **불러온 순간의 사본**을 저장한다(주의사항 묶음 스냅샷과 같은 방식). 상품을 고쳐도 기존 시트는 그대로
2. **(가격 — 자주 바뀜)** Qoo10 판매가는 시기·행사마다 달라 저장값을 그대로 쓰면 페이백 견적이 틀린다 → 판매가는 상품에 **참고값으로만** 두고, 오리엔시트에서 **매번 확인 필수**(「Qoo10에서 다시 불러오기」 단추)
3. **(화면 — 확인이 형식이 됨)** 「그대로 쓸지 확인」은 대부분 그냥 넘겨진다 → **판매가 기준일**을 보여 주고 기준(14-5 1번 — 추천 90일)을 넘으면 경고. 상품의 마지막 수정일도 함께 보여 준다(가이드만 고쳐도 바뀌므로 경고 기준으로는 쓰지 않는다). 오리엔시트(카드)에서 바꾼 값은 「작성 완료」 때 「상품에도 저장」 여부를 묻는다(기본: 이 시트에만). 세부는 14-3 ③ 「판매가 규칙」
4. **(화면 — 시작 장벽)** 처음 쓰는 브랜드가 상품부터 등록해야 하면 번거롭다 → **두 길**: 상품 관리에서 미리 등록 / 오리엔시트를 쓰다가 「이 제품을 상품으로 저장」
5. **(형식별 가이드)** 리뷰어와 시딩은 가이드 항목이 다르다(시딩은 촬영 가이드·해시태그·태그 계정) → 상품 하나에 **리뷰어용·시딩용 가이드를 따로** 둔다. 비어 있으면 그 형식으로 불러올 때 빈칸
6. **(권한 — 여러 담당자)** 한 브랜드에 담당자가 여럿(멤버관리)이면 누가 고치나 → 같은 브랜드 멤버는 모두 보고 고칠 수 있고, 수정 이력(누가·언제)을 남긴다(이번 설계 — 역할 구분은 포털 2차의 「멤버관리」(Figma 사이드바 메뉴, 계정·브랜드 연결의 일부) 설계 때)
7. **(삭제)** 오리엔시트에 쓰인 상품을 지우면 → 시트는 사본이라 영향 없음. 상품은 **보관(숨김)** 으로 처리하고 완전 삭제는 두지 않는다(추천)

**현재 구현과 어긋나는 지점**
- 상품 표 신설 · Qoo10 불러오기의 관문 ①(작성 토큰)을 로그인 계정용으로 하나 더 · 오리엔시트 카드에 「어느 상품에서 불러왔나」 칸
- 견적 계산·캠페인 발행 자동 채움은 **카드 값 기준이라 바꿀 것이 없다**

**의도와 다르게 읽힐 수 있는 부분**
- 「상품」 단위 = **Qoo10 상품 1개(주소 1개)** 를 추천한다(14-5 4번). 판매처가 여러 곳인 「브랜드 제품」 개념이 아니다 — 리뷰어형은 Qoo10 고정이고 LIPS·@cosme 는 추가 옵션일 뿐이라서
- 줄어드는 입력: 상품을 불러오면 오리엔시트에서 **새로 넣는 것은 캠페인마다 다른 값뿐**이다 — 모집 인원 · 추가 옵션 · 희망 모집 시작일 + 판매가 확인. 이 세 값은 상품에 저장하지 않는다(캠페인마다 다름)

### 14-3. 설계

**① 상품에 저장하는 것 / 안 하는 것**

| 저장 (상품) | 저장 안 함 (오리엔시트에서 매번) |
|---|---|
| 상품명 · Qoo10 주소 · 상품번호 · 대표 이미지 | 모집 인원 |
| 판매가(**참고값** · 기준일과 함께 — Qoo10에서 불러왔으면 불러온 날, 상품 관리 화면에서 판매가를 손으로 입력·수정해 저장했으면 저장한 날, 오리엔시트에서 「상품에도 저장」·「상품으로 저장」했으면 카드 기준일) · 배송비 | 추가 옵션(LIPS·@cosme) |
| 구매 가이드(자율/지정) | 희망 모집 시작일 |
| 리뷰어용 리뷰 가이드 | 판매가 **확인**(참고값을 보여 주고 매번 확인) |
| 시딩용 리뷰 가이드 · 촬영 가이드 · 해시태그 · 태그할 계정 | |
| 예시 이미지·자료 | |

**② 브랜드 화면 — 상품 관리** (포털 사이드바 「상품」 메뉴 신설)
- 목록(리스트/카드 보기 — 오리엔시트 목록과 같은 전환) · 등록 · 수정 · 보관
- 등록: Qoo10 주소 입력 → 「불러오기」 → 상품명·상품번호·판매가·이미지 자동 채움 → 가이드 입력 → 저장
- 마지막 수정일 · 「이 상품으로 만든 오리엔시트 n건」 표시

**③ 오리엔시트 작성 — 「상품에서 불러오기」**
- **어디서 되나**: 포털 2차에 **로그인한 상태로 연 오리엔시트**에서만. 토큰 링크만으로 연 시트(로그인 없음)에서는 「불러오기」·「상품에 저장」 단추를 **숨긴다**
- 카드에 「저장한 상품에서 불러오기」 단추 → 상품 고르기 → 저장값이 칸에 채워지고 **「상품에서 불러온 값 · 확인해 주세요」** 표시
- **판매가 규칙** (네 줄로 끝낸다 — 화면에 보이는 2·3번은 **로그인한 상태로 연 시트에서만**. 토큰 링크만으로 연 시트에는 상품 기능 때문에 생기는 화면 변화가 없다 — 견적 2차 화면 변경은 13-4 ④ 대로)
  1. **카드 기준일**: 상품에서 불러올 때마다(같은 상품이든 다른 상품이든) 그 상품의 값·기준일로 카드 사본·「불러온 시각」·「불러온 상품」 표시를 새로 잡는다. 카드에서 「Qoo10에서 다시 불러오기」를 하거나 판매가를 손으로 고치면 카드 기준일은 **그날**이 된다. 상품에서 불러오지 않은 카드는 폼에서 Qoo10으로 불러온 날(또는 판매가를 처음 입력한 날)이 카드 기준일이다
  2. **표시·경고는 카드 기준일로**: 참고값·카드 기준일·상품의 마지막 수정일을 보여 주고 **확인 체크 필수**. 카드 기준일이 14-5 1번의 기간을 넘으면 「오래됨」 경고
  3. **「상품에도 저장할까요?」는 「작성 완료」를 누를 때 한 번만** 묻는다 — 카드의 값(판매가 포함, 다시 불러오기·손 수정 모두)이 **불러온 때의 사본과** 달라졌을 때(= 브랜드가 카드에서 바꾼 것만). 기본값은 「이 시트에만」. 상품의 값·기준일은 여기서 「상품에도 저장」을 고를 때만 바뀐다
     - 「상품에도 저장」하면 상품의 값·기준일은 **카드의 값·카드 기준일 그대로** 복사한다. 판매가는 같고 기준일만 새로워진 경우도 「달라졌을 때」에 넣어 묻는다
     - **「작성 완료」를 누를 때마다 다시 판정**한다(전에 「이 시트에만」을 골랐어도 그때 불러온 때의 사본과 다르면 다시 묻는다). 질문 창 **하나**에서 카드별로 고른다. 한 시트에서 **같은 상품을 「상품에도 저장」할 수 있는 카드는 하나**다(둘째 카드의 선택지는 회색 — 「같은 상품은 한 카드에서만 저장할 수 있어요」). 「그 사이 바뀜」 판정은 **카드마다 저장하는 순간** 한다
     - 불러온 뒤 **상품이 그 사이 바뀌었으면**(다른 담당자나 같은 시트의 다른 카드가 고침 — 상품의 마지막 수정이 불러온 시각보다 늦음) 그 카드에는 「상품에도 저장」을 띄우지 않고 「상품이 이 카드에 불러온 뒤에 수정되어 저장하지 않았습니다 — 상품 관리에서 확인해 주세요」만 보여 준다(새 값을 옛 값으로 덮어쓰지 않게)
     - **기준 다시 잡기**: 「상품에도 저장」하거나 「이 제품을 상품으로 저장」한 순간, 그 카드의 「불러온 때의 사본」은 방금 저장한 값으로, 「불러온 시각」은 저장 시각으로 바꾼다 — 다음 「작성 완료」에서 같은 질문이 또 뜨거나, 내가 방금 저장한 것을 「그 사이 바뀜」으로 잘못 보지 않게
  4. **토큰 링크만으로 연 시트**(로그인 없음)에서는 2·3번(기준일 표시·확인 체크·「오래됨」 경고·저장 질문)을 띄우지 않는다. 1번의 카드 기준일 **기록**은 화면에 보이지 않게 그대로 한다 — 그래야 나중에 로그인해 연 시트에서 새 판매가에 옛 기준일이 붙지 않는다. 근거: 운영 중인 토큰 링크 화면(`sales/orient.html`)은 상품 기능 때문에 바뀌지 않는다
- 새로 입력한 제품은 「이 제품을 상품으로 저장」 — 저장하면 **그 카드에도 「불러온 상품」 표시를 단다**(「이 상품으로 만든 오리엔시트 n건」에 들어간다)

**④ 사본 저장 — 카드에 두는 칸은 여기 한 곳에서만 정한다**(다른 절은 이 목록을 가리킨다)
- 카드 값(불러온 값의 사본 — 브랜드가 고치면 바뀐다) · **카드 기준일** · **「불러온 상품」 표시**(상품 id) · **불러온 시각** · **불러온 때의 사본**(비교 기준 — 그때의 값과 기준일을 함께 담는다 · 판매가 규칙 3번)
- 상품이 바뀌어도 기존 시트·견적·캠페인은 바뀌지 않는다
- 이 기능 전에 만든 카드처럼 **카드 기준일이 없으면** 로그인한 시트에서 「오래됨」으로 보고 확인을 받는다

### 14-4. 준비 순서

> 포털 2차(정식 로그인 계정) 기반이 먼저다 — 계정·브랜드 연결·로그인한 브랜드 범위 접근 정책(§4 2차). 마이그레이션 번호는 박지 않는다.

| 순서 | 무엇 | 의존 |
|---|---|---|
| 1 | 데이터베이스 — 마이그레이션 2개, **①→②**: ①상품 표(브랜드 소속·보관 표시·수정 이력) + 로그인한 브랜드 범위 접근 정책 ②오리엔시트 카드의 칸(14-3 ④ 목록 — 카드 데이터 안에 둔다) + 상품 조회 함수 + 오리엔시트 화면에서 쓰는 **상품 저장·수정 함수**(「상품에도 저장」·「이 제품을 상품으로 저장」) — 로그인한 브랜드만 | 포털 2차 계정 |
| 2 | Qoo10 불러오기 관문 — 로그인한 브랜드 계정용 관문 추가(분당 횟수 제한은 계정 단위, 데이터베이스 계수) | 1 |
| 3 | 브랜드 화면 — 상품 관리(목록·등록·수정·보관) | 1·2 |
| 4 | 브랜드 화면 — 오리엔시트의 「상품에서 불러오기」(로그인한 시트만)·판매가 확인·「오래됨」 경고·「상품에도 저장」·「상품으로 저장」 | 1·2 |
| 5 | 토큰 링크 화면(`sales/orient.html`) — 카드 기준일을 판매가 규칙 1번이 정한 때(처음 불러오기·입력, 다시 불러오기, 손 수정) **보이지 않게 기록**(판매가 규칙 4번). 🔴 상품 기능 때문에 이 화면에 생기는 글자 변화는 없다(견적 2차 변경은 13-4 ④ 대로) | 1 — 4번과 **같은 배포**(상품 기능이 열리기 전에 기록이 시작돼야 옛 기준일이 붙지 않는다) |

### 14-5. 사용자 확인 필요
1. **판매가 오래됨 경고 기준**(카드 기준일부터 — 14-3 ③ 판매가 규칙 1·2) — 90일(추천) / 30일 / 경고 없이 매번 확인만
2. **상품 삭제** — 보관(숨김)만(추천) / 완전 삭제도 허용
3. **관리자 화면** — 관리자가 브랜드의 상품 목록을 볼 수 있게 할지(추천: 보기만, 브랜드 상세 안)
4. **상품 단위** — Qoo10 상품 1개(주소 1개) = 상품 1개(추천) / 판매처가 여러 곳인 브랜드 제품 단위
