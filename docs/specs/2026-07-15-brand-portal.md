## 0. 이 기획이 여는 것 — 세 번째 사용자 유형

지금까지 REVERB JP의 사용자는 **인플루언서**(일본어 앱)와 **관리자**(한국어 앱) 둘뿐이다. 브랜드 포털은 **브랜드사(광고주)** 라는 세 번째 사용자 유형을 처음으로 시스템에 들인다. 그래서 인증·접근제어·개인정보가 전부 새 영역이다.

## 1. 현재 상태 (2026-07-15, 코드·DB 직접 조사)

### 브랜드가 지금 시스템과 닿는 지점 — 전부 "입력(쓰기)"뿐, "조회(읽기)" 0
- **광고주 신청 폼**(`sales/reviewer.html`·`seeding.html`) — 로그인 없이 `submit_brand_application` 원격 호출 함수로 제출. **현재 공개 접수 차단 중**(마이그레이션 206).
- **오리엔시트 작성 폼**(`dev/sales/orient.html`) — 관리자가 발급한 토큰(`?token=`) 링크로, 로그인 없이 캠페인 콘텐츠 작성·제출. 익명 함수 3종(`get_orient_sheet`/`save_orient_draft`/`submit_orient_sheet`, 마이그레이션 187).
- **브랜드가 자기 캠페인 현황·결과물·정산을 "보는" 경로는 전혀 없음.**

### 보여줄 데이터·집계는 이미 있음 (단, 관리자 전용 잠금)
- `get_brand_ops_overview(회사)` / `get_brand_ops_detail(브랜드)` — 모집률·결과물 승인률·캠페인 목록·견적 집계(마이그레이션 120·148·149·150). 둘 다 **`is_admin()` 가드** → 브랜드가 직접 못 읽음. 브랜드 몫만 떼주는 조회 함수 신설 필요.
- 진행현황 비용 카드 산식(견적·운영비, `admin-applications.js:234~`).

### 인증·계정 구조
- 인플루언서·관리자 모두 같은 로그인(`signInWithPassword`) → 로그인 후 `admins` 테이블 조회로 분기(`auth.js:156`).
- ⚠️ **자동 등록 트리거(`handle_new_user`, 마이그레이션 014 — 현재 원본은 420, §16-1)**: 어떤 신규 계정이든 무조건 `influencers` 행을 만든다. **브랜드가 정식 로그인 계정을 만들면 인플루언서로 섞임** → 정식 계정 방식 도입 시 이 트리거부터 수정 필요.
- 브랜드측 로그인 계정 개념 없음. 브랜드 대표 담당자 이메일은 `brands.contacts`(jsonb, 정본)에 텍스트로만 존재.

### 검증된 재사용 패턴
- **토큰 기반 익명 조회 함수**(오리엔시트 3종 + 수신거부 토큰 마이그레이션 140) — 로그인 없이 토큰으로 자기 데이터만, 자원 열거 방지(`success:false`). **1차 포털 조회의 최적 템플릿.**

### 충돌 가능성 있는 기존 동작
- 오리엔시트 토큰은 **1시트 스코프**(그 시트 하나만). 브랜드 포털은 **브랜드/회사 단위** 접근이 필요 → 브랜드 단위 토큰 신설.
- 모든 브랜드 관련 테이블 SELECT가 `is_admin()` 전용 → 브랜드는 **직접 테이블 조회 불가**, 반드시 SECURITY DEFINER + 스코프 가드 함수로만.

## 3. 의심·경우의 수 (반대론자 모드)

### 깨질 수 있는 경우의 수
1. **(법률·최중요) 결과물 개별 링크 = 인플루언서 개인정보 제3자 제공** — 브랜드에게 "이 인플루언서가 우리 캠페인에 참여해 이 게시물을 올렸다"(SNS 계정·게시물 연결)를 노출하는 것. APPI(일본)/PIPA(한국) 관점에서 **개인정보처리방침 개정 + 동의(또는 캠페인 참여 시 결과물 공유 동의 근거) 확인**이 필요. 영수증은 명백한 민감정보라 브랜드 노출 제외 권장. → **법률 딥리서치가 출시 전제**(아웃바운드 명단 제3자 제공 관문과 동류, 메모리 `project_outbound_roster_privacy` 참고). ※ 브랜드 페이지 1차 결과물 표는 해당 없음 — §5 앞 「법률 절 적용 범위」
2. **(통제) 브랜드 자체 오리엔시트 생성 → 무제한 생성·스팸·잘못된 발행** — 현재는 관리자가 발급을 통제하고, 발행 시 일본어 미보완 차단 게이트가 있다. 브랜드가 스스로 만들면 이 통제가 사라짐 → **관리자 검토 게이트(제출된 오리엔시트를 관리자가 확인 후 캠페인 발행) 유지 + 브랜드 생성 수량·자격 제한** 필요.
3. **(인증 함정) 정식 계정 도입 시 자동 등록 트리거** — 2차에서 브랜드 로그인 계정을 만들면 `handle_new_user`(014 — 현재 원본 420, §16-1)가 브랜드를 인플루언서로 등록. 트리거 분기 수정 없이는 데이터 오염.
4. **(보안) 토큰 유출** — 1차 토큰 링크가 유출되면 제3자가 브랜드 현황을 봄. 만료·재발급·브랜드 스코프 제한 필요. 특히 결과물 링크가 포함되면 유출 시 개인정보 노출.
5. **(데이터 매핑) 회사 vs 브랜드 단위** — 한 회사에 여러 브랜드, 한 브랜드에 여러 캠페인. 토큰/계정을 **브랜드 단위로 발급할지 회사 단위로 발급할지** 결정 필요(담당자 이메일은 브랜드에 붙어있음). ※ 정해짐 — §16
6. **(UX·빈 상태) 신규 브랜드** — 캠페인이 아직 없는 브랜드가 포털에 들어오면 텅 빈 화면. 안내 문구·"진행 중 캠페인 없음" 상태 필요.
7. **(환경) 세 번째 앱 신설** — `brand/` 전용 페이지 + 빌드 + 도메인(brand.globalreverb.com?) + Vercel 프로젝트 추가 여부. 1차 토큰 조회는 오리엔시트처럼 `sales/` 계열 정적 페이지로 시작 가능.

### 의도 모호점 (확인 완료 / 미결)
- ✅ 포털 성격 = 단계적(토큰→계정) ※ **2026-10-13 단계가 바뀌었다 — 현재 정의는 §4 맨 위 「현재 단계 정의」**
- ✅ 오리엔시트 = 브랜드 자체 생성 ※ 2026-10-13: 자체 생성은 2차 업데이트, 브랜드 페이지 1차는 운영팀 발급 시트만(§9 · §4 「현재 단계 정의」)

## 5. 법률 딥리서치 결론 (2026-07-15, 완료)

> `deep-research` 실행(101개 에이전트, 19개 1차/2차 소스, 24개 클레임 검증 통과·1개 반증). 일본 개인정보보호위원회(PPC)·한국 개인정보보호위원회(PIPC) 1차 자료 기반. **결론: 결과물 개별 링크 노출은 무거운 법적 관문이며 변호사 확인이 전제.**

### 핵심 판정 (must / should)
1. **결과물 개별 링크(공개 SNS 게시물 URL·계정명) 노출 = "제3자 제공"으로 판정될 가능성 높음** (위탁 아님). 브랜드가 자기 캠페인 성과를 자기 이익으로 열람하므로, 데이터의 실질 이용 주체가 브랜드 → 위탁(委託) 구성은 무리. 한국 대법원 2016도13263 다요소 판례도 이 방향.
2. **공개된 정보라도 개인정보** (양국 공통). 일본 APPI는 공표 정보도 구별 없이 보호, 한국 PIPA는 처리자·수령자가 보유한 정보와 쉽게 결합해 식별 가능하면 개인정보. **브랜드는 이미 자기 캠페인 응모자·배송정보를 알아** 계정명이 마스킹돼도 재식별됨.
3. **캠페인 참여 동의로 자동 커버 안 됨** — must: "브랜드에게 결과물(개인정보) 제공"에 대한 **별도 명시 동의 + 개인정보처리방침 개정** 필요. (한국 PIPA 17조 5개 고지사항 / 일본 APPI 27조 사전 동의)
4. **국경 간 이전 관문 추가** — 일본 거주자 데이터를 한국 브랜드가 열람 = 국외 관련 이전. 일본 APPI 28조상 "외국 제3자 제공 인정" 취지의 **별도 사전 동의** 또는 상당조치 계약 체계 필요(한국은 PPC 적정성 인정국 아님). ⚠️ 한국 PIPA 국외이전 근거조문은 조사 중 특정 클레임이 **반증**됨 → 변호사가 실제 조문 확정 필요.
5. **★ 별표(`*`) 마스킹은 법적 부담을 완화하지 못함** (사용자 질의 핵심 판정). SNS 계정명은 그 자체로 공개·검색 가능해 부분 마스킹해도 재식별. 가명처리해도 양국 모두 **여전히 개인정보**이고, 동의 면제(통계·과학연구·공익보존)는 **상업적 브랜드 노출에 적용 안 됨**. → 마스킹으로 관문을 우회할 수 없음.
6. **영수증·구매내역 브랜드 노출 제외 = 타당** (목적 비례·최소 제공 원칙). 단 논거는 "민감정보라서"보다 "비공개 최소제공".
7. **집계 숫자(게시 N건·승인 여부)는 규제 밖에 둘 여지** — 단 참여자 소수면 브랜드가 개인 역추정 가능 → **진정한 익명·캠페인 단위 집계**여야 안전.

## 9. 브랜드 자체 오리엔시트 생성 통제 게이트 (2026-07-15)

### 현재 상태 (이미 발행 단계에서 통제)
- 브랜드는 관리자 발급 토큰으로 **작성·제출까지**. 발행(캠페인화)은 관리자(`is_admin`, `mark_orient_card_consumed` 마이그196). **일본어 미보완 차단 게이트**(`addCampaign` — 가이드 비면 campaign_admin 이상 사유 입력 긴급 발행). 제출 알림 인프라(`notify-orient-submitted` + 과다발송 방지 게이트). 30일 기한(`token_expires_at` — 저장·제출 시점에만 만료로 바뀜, 자동으로 도는 작업 없음 — §13-1).

### 결정 (사용자): 생성·제출 자율 / 캠페인 발행 관리자

> **단계 (2026-10-13 사용자 결정)**: 브랜드의 **새 오리엔시트 만들기(자체 생성)는 2차 업데이트**에 넣는다(견적 2차·상품 관리와 같은 업데이트 — §13-6 4번·§14). 브랜드 페이지 1차에서는 지금처럼 **운영팀이 발급한 시트**가 브랜드 목록에 나타나고, 브랜드는 그 시트를 작성·제출만 한다(목록에 「새로 만들기」 단추 없음). 아래 결정·보조 통제는 2차 업데이트 기준이다
- **브랜드**: 포털에서 오리엔시트 **생성·작성·제출까지 자율**.
- **관리자**: **캠페인 발행 검토 유지**(현 구조 그대로) — **핵심 통제**. 브랜드가 만들어도 "생성=초안 제출"까지이고 "생성=캠페인"이 아님.
- **신규 필요**: **로그인한 브랜드 계정용 생성 함수**(2차 업데이트 — 그 브랜드 범위만). 현 `create_orient_sheet`는 `is_admin` 가드라 확장 또는 신규 함수. ⚠️ 이 절은 처음에 「익명 + 브랜드 토큰」(§4 골격)으로 쓰였다 — 브랜드 페이지는 1차부터 로그인 기반이므로(§4 「현재 단계 정의」) 계정 기준으로 고쳤다(2026-10-13)
- **보조 통제 4종**: ①브랜드당 동시 미처리(**캠페인 등록 전**) 오리엔시트 **수량 상한** ②30일 만료(기존 — ⚠️ §13-1 조사로는 자동으로 도는 만료 작업은 없고 저장·제출 시점에만 만료로 바뀐다. 방치 흡수는 아래 반대론자 기록의 날짜 기준 수량 상한으로 해결 — 자동 만료 작업은 필요 없다) ③제출 시 **관리자 알림·검토 큐**(기존 인프라 재사용) ④**생성 자격 = 로그인한 브랜드 계정(그 브랜드 범위)만**.

### 반대론자 기록
- **캠페인 발행 게이트를 관리자가 쥐므로** 잘못된 내용·일본어 미보완이 인플루언서 화면에 **바로 노출되지 않음**(핵심 리스크 차단). 브랜드 자체 생성의 편의는 살리고 통제 부담은 발행 단계에 집중.
- **스팸·방치**는 수량 상한 + 30일 만료로 흡수. ⚠️ 만료가 자동으로 돌지 않는다(§13-1) — 그래서 수량 상한을 상태값이 아니라 **날짜로** 센다(해결, 아래). ⚠️ 견적 2차 시트에서 30일은 **미제출 시트만** 끝낸다 — 「검토 중」 방치는 관리자 목록의 검토 중 표시(§13-4 ③)로 메운다. ①의 수량 상한은 **판정 기준 한 줄로 센다 — 「작성 기한(발급 + 30일) 안」이면서 「카드가 하나도 캠페인에 등록되지 않은」 시트**(상태 이름·견적 1·2차와 무관). 그래서 기한이 지난 시트와 카드가 하나라도 등록된 시트는 세지 않는다 — 방치된 시트가 새 시트 작성을 영구히 막지 않게. 견적 2차 시트의 기한 뒤 방치는 관리자 목록의 「검토 중」·「유효기간 지남」 표시(§13-4 ③)로 운영팀이 정리한다(견적 1차는 지금처럼 따로 정리하지 않는다).
- ⚠️ 브랜드가 만든 오리엔시트는 신청 개념을 모르므로 `brand_id`에 붙는 **독립 오리엔시트**로 생성 → 관리자가 캠페인 발행 시 캠페인·신청 연결(기존 링크 경로).

- **목적 중심의 쉬운 말** — 예: 「**한국 브랜드가 검수를 위해 결과물을 확인할 수 있습니다**」(주체=한국 브랜드 / 목적=검수 / 행위=확인). 인플루언서 안내 초등학생 눈높이 규칙(`.claude/rules/ui.md` 「인플루언서 안내 문구」)과 일치.
- ⚠️ **단 법적 고지 완전성은 유지** — 톤은 부드럽게 하되, "한국 브랜드가 본다"는 **사실 자체를 숨기거나 모호하게 하면 동의 무효 위험**. 사용자 제안 표현은 주체·목적·행위를 다 담아 부드러움 + 고지 요건을 함께 충족. 톤은 순화, 사실은 정확 — 최종 고지 완전성은 변호사 검토.
- 이 톤 원칙은 인플루언서에게 보이는 동의 체크박스·안내 배너·통지 메일 문구 전반에 적용.

## 10. 개인정보처리방침 개정 예정 초안 (골격)

> ※ 적용 범위: §5 앞 「법률 절 적용 범위」 — 브랜드 페이지 1차 결과물 표는 해당 없음.

## 11. 변호사 자문 후 갖춰야 할 증빙 체크리스트 (2026-07-15)

> ※ 적용 범위: §5 앞 「법률 절 적용 범위」 — 브랜드 페이지 1차 결과물 표는 해당 없음.


> **"변호사가 괜찮다고 하면 끝"이 아니다.** 변호사 자문은 *"무엇을 갖춰야 적법한지"*(설계도)이고, 실제 본체는 **그 조건을 이행하고 증빙을 남기는 것**이다. 법은 "변호사 자문을 받아라"가 아니라 "적법하게 처리하라(동의·고지·안전조치)"를 요구한다. 이 체크리스트는 "괜찮다만 받고 끝내는" 실수를 막는다.

### 변호사 답변의 성격
- 보통 "그냥 괜찮다"가 아니라 **"이런 조건(동의·마스킹·계약·기록)을 갖추면 괜찮다"는 조건부**. 그 조건을 실제로 이행해야 한다.
- **서면 자문의견서**(조건·전제·한계 명시)를 받아둔다 — 법적 필수는 아니나, 규제기관 조사·분쟁 시 "성실 노력" 방어 자료 + 자문 범위 명확화. 구두 "괜찮다"는 근거로 쓰기 어렵다.

### 실제로 남겨야 할 증빙 (법적 본체)
| 증빙 | 필요성 | 우리 현황 |
|---|---|---|
| **인플루언서 동의 기록**(누가·언제·무엇에) | ✅ 법적 필수 | `influencers.*_agreed_at`·`applications.caution_*` 등 동의 시각 기록 구조 **이미 있음**(유리). 브랜드 제공·국외 관련 이전 동의도 동일 패턴으로 기록 설계 |
| **개인정보처리방침 개정·공지 이력**(언제 무엇 고지) | ✅ 필수 | 부칙 개정 이력 + 통지 인프라(마이그153 `policy_notice_*`) 재사용 |
| **제3자 제공 기록**(누구에게 제공) | ✅ 필수(일본 APPI, 원칙 3년 보존) | **신규 필요** — 어느 브랜드에 어느 회원 정보를 언제 제공했는지 기록 테이블/로그. 딥리서치 확인 항목 |
| **위탁 계약서**(위탁 구성 시) | ✅ 위탁이면 필수 | 브랜드와의 계약서(위탁으로 판정될 경우) — 범위 초과 처리 금지·안전조치 명시 |
| **접근 로그**(브랜드가 언제 무엇을 열람) | 🟡 권장(안전조치) | 브랜드 포털 열람 로그 — 사고 시 추적. `PROJECT_CONTEXT.md` 「접근 로그」 방향과 일치 |
| **변호사 서면 의견서** | 🟡 필수 아니나 강력 권장 | 방어 자료 |

### 확신도·한계
- 위 큰 원칙(자문≠증빙, 동의·공지·제공기록이 본체 = 개인정보보호 「책임성 원칙」)은 일반적으로 타당.
- **정확한 증빙 양식·보존 기간·제3자 제공 기록 세부 요건**은 나라·상황별로 달라 **변호사 확정 영역**.
- → 변호사 자문 시 **"증빙으로 무엇을·어떤 양식으로·얼마나 보존할지"까지 함께 확인**할 것(자문 질문에 포함).

## 12. 변호사에게 넘길 질문 리스트 (딥리서치 2회 산출 — 자문 준비)

> ※ 적용 범위: §5 앞 「법률 절 적용 범위」 — 브랜드 페이지 1차 결과물 표는 해당 없음.


> 딥리서치 2회(1차 판정 + 2차 심화, 각 100+ 에이전트·양국 규제기관 1차 자료)로 아래 쟁점을 사전 정리했다. 변호사는 "무엇을 검토할지"를 처음부터 찾을 필요 없이, 이 목록을 **우리 사실관계(계약 구조·데이터 흐름)에 적용해 확정·책임**하면 된다. → 자문이 빠르고 저렴해짐.

### 딥리서치로 이미 확정된 것 (참고로 제시, 재확인만)
- 결과물(공개 SNS 게시물·계정명 포함)은 양국 개인정보 → 브랜드 제공 = 제3자 제공.
- 별표(*) 마스킹으로 개인정보성 우회 불가.
- 한국 국외이전 근거 = **PIPA 제28조의8**(2023-09-15, "별도의 동의"·"조회 포함"). 일본 = **APPI 제28조**(외국 제3자 제공 + 3종 고지).
- 국외이전은 **동의 간주 불가**.
- 제3자 제공 기록 의무: 제공 때마다 기록, 원칙 3년 보존(일본 APPI 29조).
- 스텔스 마케팅(일본 景表法, 2023-10-01): 규제 대상 = 브랜드사(광고주), 인플루언서 아님.

### 변호사 확정이 필요한 질문 (사실관계·판단 종속)
1. **위탁 vs 제3자 제공 최종 판정** — 브랜드 포털 열람을 APPI 27조5항 "위탁"으로 구성하려면 계약상 최소 조건(재활용 금지·목적 검수 한정·처리 수단 결정권 유지)이 무엇인가? 우리 구조가 실제로 위탁에 포섭되는가?
2. **국외이전 경로 선택** — (A) 인플루언서 명시 동의 vs (B) 한국 브랜드와 상당조치(계약 기반) 체제. 우리 상황(브랜드 다수)에 어느 쪽이 실무적으로 나은가? 한-일 표준계약에 넣을 구체 조항 세트는?
3. **동의 UI·문안** — 명시 동의로 갈 경우, 국외이전 별도 동의(한국 5개 고지)와 일본 APPI 28조 3종 고지를 캠페인 신청·승인 시점에 어떤 화면·문안으로 분리 제시해야 "별도성"·"사전 고지"를 동시 충족하는가? (인플 눈높이 톤 §8 유지하면서)
4. **영수증 마스킹 수준** — 영수증이 일본 要配慮個人情報 / 한국 민감정보에 해당하는가? 성명·주소·결제수단·카드번호를 어느 수준까지 가려야 "최소 제공"으로 적법한가? (딥리서치 2회 미해결 — 자문 핵심)
5. **증빙 요건 확정** — 제3자 제공 기록·국외이전 기록의 정확한 양식·보존기간, 동의 기록·방침 공지 이력의 증빙 형태(§11 체크리스트 검증).
6. **다른 법 누락 점검** — 개인정보보호법·景表法 외에 이 기능에 걸리는 법이 더 있는가?

### 자문 요청 시 함께 전달할 것
- 이 사양서(특히 §5·§8·§10·§11·§12) + 딥리서치 2회 결과 요약.
- 우리 데이터 구조(결과물 종류·수집 항목·기존 동의 컬럼)와 브랜드 계약 실태.

- 흐름: 작성 → 「작성 완료」(`btnReview`) → **입력 내용 확인**(`openPreview`·`renderPreview`) → 「견적 보기」(`openQuotePreview`) → **견적서**(`showQuoteScreen`) → 「제출하기」(`submitSheet`) → 완료 화면(`enterDoneScreen`, 견적서가 펼쳐져 있음)
- 견적은 **서버가 입력값으로 자동 계산**한다. 미리보기는 `preview_orient_quote`(저장 없음, 현재 원본 430), 제출은 `submit_orient_sheet`(현재 원본 461). 둘 다 안에서 `_orient_compute_quote`(현재 원본 463) **한 벌**을 부른다
- 제출 뒤에도 「내용 수정하기」로 고쳐 다시 제출할 수 있다. **견적 차수(`revision`)는 다시 제출할 때만** 오르고(임시저장으로는 안 오름) 지난 판은 `quote_history` 에 쌓인다(`orient_sheets.data` 안). **캠페인 발행(`consumed`)된 시트와 기한이 지난 시트는 수정이 막힌다**
- 견적서는 「인쇄 · PDF」 단추로만 저장한다(`printQuote`). 견적서를 그리는 코드는 `orient.html` 한 벌이고, 관리자 화면은 **저장된 시트**를 `?embed=quote` 로 끼워 보여 준다

**상태값** — `orient_sheets.status`
- `draft` → `submitted`(제출) → `consumed`(모든 카드가 캠페인 발행됨). 기존 캠페인 연결을 풀면 `consumed` → `submitted`
- `expired`: 발급 때 기한을 **+30일**로 잡고, 이 날짜가 견적서의 「유효기간」이기도 하다. **기한이 지난 뒤 저장·제출을 시도할 때만** `expired` 로 바뀐다(따로 도는 만료 작업은 못 찾음)
- 카드(제품) 단위 상태 칸은 없다 — `cards[].campaign_id`·`linked_existing` 유무로 판정

**관리자 화면** — `dev/js/admin-orient.js`
- 견적은 **보기·인쇄만** 된다(`osQuoteCard`·`osOpenQuoteDoc`). 관리자가 견적을 발행하거나 금액을 고치는 기능은 **없다**
- 발급할 때 모집비 직접 지정만 된다(캠페인 관리자 이상, 서버 거부 `recruit_fee_forbidden`)
- 광고주 신청(서베이)의 견적 칸(`quote_sent_at`·`quote_sent_url`·`final_quote_krw`)은 오리엔시트 견적과 **별개**로 손으로 입력한다
- 제출 알림 메일(`notify-orient-submitted`)에는 과다 발송 게이트가 둘 있다 — 같은 제출이면 건너뛰고, 재제출은 30분 안에 다시 보내지 않는다

**충돌 가능성 있는 기존 동작**
- 캠페인 발행 함수(`mark_orient_card_consumed`)·기존 캠페인 연결 함수(`link_orient_card_to_campaign`)가 **`status='submitted'` 를 전제**한다 → 2차에서 `status` 값을 새로 늘리면 이 둘이 깨진다(13-4 ②에 반영)
- 🔴 **확인 필요(결함 후보)**: 기한 전에 열어 둔 화면에서 기한이 지난 뒤 저장하면, **이미 제출된** 시트가 `expired` 로 바뀌어 캠페인 발행이 실패할 수 있다(461 의 기한 검사 → 196 이 `submitted` 만 받음). 코드 추론일 뿐 재현하지 않았다. 견적 1·2차와 무관하게 13-5 의 0번에서 처리한다
- 브랜드는 기한(30일)이 지나면 완료 화면의 견적서를 다시 볼 수 없다(조회 단계에서 기한 오류 화면)

### 13-3. 의심·경우의 수 (반대론자 모드)

**깨질 수 있는 경우**
1. **(화면 — 기다림)** 2차에서 브랜드는 제출 뒤 견적이 나올 때까지 기다린다. 「검토 중」 안내·예상 소요·발행 알림 메일이 없으면 「제출이 된 건가」 문의가 온다 → 완료 화면 문구 + 발행 알림 메일(13-4 ⑤) — 예상 소요 기간은 적지 않는다(13-6 3번)
2. **(동시 수정)** 관리자가 견적을 고치는 동안 브랜드가 내용을 다시 제출하면 견적이 **옛 내용 기준**이 된다 → 발행 요청에 「어느 차수를 보고 만든 견적인가」를 싣고, 서버가 그 사이 다시 제출됐으면 **거부**한다(13-4 ③)
3. **(기한)** 지금은 발급 + 30일이 작성 기한 **겸** 견적 유효기간이다. 2차에서 관리자 검토가 늦으면 **브랜드 잘못이 아닌데** 유효기간이 준다 → 견적 유효기간을 발행일 기준으로 가른다(13-4 ⑥, 2026-10-13 결정)
4. **(전환)** 2차로 바꾸는 순간 이미 자동 견적을 받은 시트가 어떻게 보일지 → **시트마다 견적 방식을 기록**해, 전환 날짜가 아니라 그 시트가 만들어질 때의 방식으로 판정한다(13-4 ①)
5. **(말 — 「발행」이 둘)** 2차부터 「견적 발행」과 「캠페인 발행」이 같은 말을 쓴다. 디자인 시안의 상태 「발행됨」도 어느 쪽인지 모호했다 → 브랜드 화면 상태 이름을 나눈다(13-4 ⑦, 시안 반영 완료)
6. **(이중 기록)** 서베이의 「견적 발송」 기록과 오리엔시트 발행 견적이 따로 놀면 운영팀이 두 곳에 적는다 → 견적 발행 때 연결된 서베이 신청의 견적 발송일을 자동으로 채운다(13-6 2번 결정, 13-5 1번②)
7. **(권한별 화면)** 캠페인 매니저가 견적 발행 단추를 보고 눌렀다가 거부되는 것은 사고 → 권한이 없으면 단추를 회색으로 두고 이유를 말한다(13-4 ③)
8. **(알림이 묻힘)** 견적 발행 뒤 브랜드가 30분 안에 고쳐 다시 내면, 지금의 30분 게이트 때문에 관리자 알림이 안 가고 시트가 「검토 중」에 멈춘다 → 관리자 목록의 「검토 중」 표시로 메우고, 「발행 견적 뒤 재제출」은 30분 게이트의 예외로 둔다(13-4 ⑤)

**현재 구현과 어긋나는 지점**
- 관리자 견적 발행 기능 자체가 없다(신설)
- 캠페인 발행·연결 함수가 `status='submitted'` 를 전제 → **`status` 값은 늘리지 않고**, 견적 2차 시트에만 「현재 차수 발행 견적 있음」 검사를 더한다(13-4 ②)
- 견적서를 그리는 코드는 `orient.html` 한 벌이라는 규칙 → 관리자 발행 모달의 미리보기도 **같은 그리기 코드**를 써야 한다. 그런데 지금의 끼워 보기는 **관리자 화면이 가진 저장된 시트 내용을 넘겨받아** 그린다 — 저장 안 된 값을 넘기는 자리는 아직 없다(13-4 ③에서 처리)

**의도와 다르게 읽힐 수 있는 부분**
- 「요청」: 2차에서도 브랜드는 지금처럼 **내용을 다 채워서** 제출한다(빈 요청이 아님). 바뀌는 것은 금액을 누가 확정하느냐뿐
- 「견적서 발행」: 금액을 확정해 브랜드에게 보여 주는 것. **캠페인 발행과 별개**이고, 견적 2차에서는 **반드시 그보다 앞**이다(13-2)
- 「수락은 메일·전화」: 시스템에는 **수락 기록이 남지 않는다**. 금액 분쟁 때 근거는 발행 이력(누가·언제·얼마)뿐이다

### 13-4. 견적 2차 설계

**① 시트마다 견적 방식을 기록** — `자동`(견적 1차) / `관리자 발행`(견적 2차)
- **시트가 만들어질 때** 정해지고 바뀌지 않는다 — 관리자 발급이든, 포털에서 브랜드가 직접 만들든(§9, 2차 업데이트부터) 같다
- 새 시트의 기본값은 설정 하나로 고른다(전환 = 그 설정을 바꾸는 것)
- 기존 시트는 전부 `자동` → 전환해도 옛 시트의 화면이 바뀌지 않는다
- 되돌리기: 설정을 되돌리면 **새 시트만** `자동` 으로 돌아간다. 이미 만든 `관리자 발행` 시트는 그대로이므로 관리자가 끝까지 견적을 발행해야 한다

**② 상태는 기존 4개 그대로 두고 「발행 견적」을 따로 둔다**
- `status` 에 값을 늘리지 않는다(캠페인 발행·연결 함수가 `submitted` 를 전제)
- 대신 「발행 견적」(금액 항목·할인·메모·발행자·발행 시각·**근거 차수**)과 그 이력을 따로 저장한다
- 화면 상태 판정(견적 2차 시트):
  - `submitted` + 현재 차수의 발행 견적 없음 = **검토 중**
  - `submitted` + 현재 차수의 발행 견적 있음 = **견적 발행됨**
  - `consumed` = **캠페인 등록됨** — 지금처럼 수정이 막혀 있으므로 「검토 중」으로 돌아갈 일이 없다
  - **일부 카드만 캠페인 등록된 시트**(아직 `submitted`)와 **캠페인 연결을 풀어 `submitted` 로 돌아온 시트**: 견적 2차에서는 **카드 하나라도 캠페인 등록되면 브랜드의 수정·재제출을 막는다**(2026-10-13 결정). 그래야 이미 만든 캠페인과 발행 견적이 같은 차수에 묶여 있고, 남은 카드가 「견적 먼저」 검사에 막히지 않는다. 화면 상태는 **「캠페인 등록 중 (n/m)」**. 캠페인 연결을 **전부** 풀어 등록된 카드가 0개가 되면 잠금이 풀리고 상태는 「견적 발행됨」(현재 차수 발행 견적이 없으면 「검토 중」)으로 돌아간다
- 수정 중(다시 제출 전) 임시저장 상태에서는 화면에 **「견적 발행됨 · 수정 중」**(또는 검토 중에 고치는 경우 **「검토 중 · 수정 중」**)으로 보인다 — 차수가 아직 안 올랐기 때문이다. 다시 제출하는 순간 「검토 중」
- 작성 기한이 지나면 「· 수정 중」을 떼고 **마지막 제출 차수의 상태**(검토 중·견적 발행됨)로 표시한다 — 다시 제출할 수 없으므로(13-4 ⑥)
- **「만료」 판정**: 견적 2차 브랜드 화면에서 「만료」는 **제출 차수가 하나도 없는 시트**이면서 **작성 기한(발급 + 30일)을 넘겼거나 `status` 가 `expired` 인 경우**만이다. 제출 차수가 있으면 `status` 값과 관계없이 만료로 보지 않는다. 제출된 시트는 기한이 지나도 「검토 중」·「견적 발행됨」으로 남고, 관리자는 기한 뒤에도 견적을 발행할 수 있다(13-4 ⑥·13-5 1번②)
- **견적 발행의 기준은 「마지막으로 제출된 차수의 내용」**이다. 관리자 화면의 자동 계산 출발점도 그 내용으로 만든다. 브랜드가 임시저장 중인 미제출 내용은 쓰지 않는다. 🔴 임시저장이 제출된 내용을 같은 자리에 덮어쓰는 구조라면 **제출 차수의 내용을 따로 보존**해야 한다 — 어느 쪽인지는 개발 세션이 13-5 1번에서 확인
- **견적 먼저(13-2)**: 견적 2차 시트는 현재 차수의 발행 견적이 없으면 캠페인 발행(`mark_orient_card_consumed`)·기존 캠페인 연결(`link_orient_card_to_campaign`)을 서버가 거부한다. 관리자 화면은 그 단추를 회색으로 두고 「견적서를 먼저 발행해 주세요」를 보여 준다. 견적 1차 시트는 지금과 같다

**③ 관리자 — 견적 발행 모달** (오리엔시트 상세 안)
- 자동 계산값을 출발점으로 채운다 → 항목별 금액 수정 · 할인 줄 추가 · 브랜드에게 보이는 메모
- 미리보기는 `orient.html` 의 견적서 그리기 **한 벌**을 쓴다. 아직 저장 안 된 값을 넘기는 방법(임시 저장 뒤 끼워 보기 / 값을 전달해 그리기만 공유 등)은 **개발 세션이 정한다** — 단 그리기 코드를 두 벌로 만들지 않는다
- 「발행」 → 확인 모달 → 저장 + 이력 + 브랜드 알림 메일
- 권한: 캠페인 관리자 이상(모집비 직접 지정과 같은 선). 캠페인 매니저에게는 단추를 회색으로 두고 이유를 보여 준다. **서버가 다시 검사**한다
- 서버는 합계를 **항목에서 다시 계산**해 저장한다(화면이 보낸 합계를 믿지 않는다)
- 서버는 「근거 차수」가 지금 시트 차수와 다르면 거부한다(경우의 수 2)

**④ 브랜드 화면** (브랜드 페이지의 오리엔시트 작성 모달, 시트의 견적 방식이 `관리자 발행` 일 때만) ※ 2026-10-14 정정: 처음엔 링크 폼(`sales/orient.html`)으로 적었으나, 견적 2차는 브랜드 페이지 출시 뒤라 그때는 링크 폼이 닫혀 있다(16-4 「오리엔시트 작성 경로」).

  - 확인 모달을 「다시 제출할 때」 띄우는 이유: 「검토 중」에 고치기 시작했는데 그 사이 견적이 발행된 경우에도 빠짐없이 알리기 위해서다(시작할 때만 띄우면 이 경로가 확인 없이 지나간다)

**⑥ 견적 유효기간을 발행일 기준으로** (2026-10-13 결정)

- 기한 뒤 **「수정 중」 시트**(한 번 제출한 뒤 고치던 시트)는 **마지막 제출 차수 기준의 완료 화면**을 보여 준다. 임시저장한 미제출 내용은 화면에 보이지 않고 저장값으로만 남는다
- 관리자는 작성 기한 뒤에도 **제출된 시트**에 견적을 발행할 수 있다
- 「제출된 시트를 저장 시 `expired` 로 바꾸지 않는다」는 여기가 아니라 13-5 의 0번(결함 수정) 몫이다 — 견적 1차에도 해당하는 결함 수정이라 따로 간다

**⑦ 브랜드 화면 상태 이름** (Figma 시안 반영 2026-10-13 — 아래 두 개 제외)

## 14. 브랜드 상품 관리 — 저장한 상품으로 오리엔시트 작성 (2026-10-13)

> **2차 업데이트**(브랜드 페이지 1차 출시 뒤 — 견적 2차와 같은 업데이트, §13-6 4번)에 넣는다. 「저장해 두고 다시 쓰기」는 상품 목록의 주인(로그인한 브랜드)이 있어야 성립한다. 견적 1·2차(§13)와는 **다른 축**이라 어느 견적 방식의 시트에서든 쓸 수 있다.
> 단계 이름은 §4 맨 위 「현재 단계 정의」를 따른다(브랜드 페이지 1차 = Figma 「[1차]」 섹션, 로그인 포함 → 2차 업데이트 = 「[2차]」 섹션).

### 14-1. 현재 상태 (2026-10-13 코드 조사)
- **상품을 저장해 두는 표가 없다.** 오리엔시트를 쓸 때마다 카드(제품)별로 판매 URL·제품명·판매가·가이드를 새로 입력한다(`sales/orient.html` 카드 양식)
- **Qoo10 불러오기가 이미 있다** — 서버 함수 `qoo10-product-lookup`: Qoo10 주소를 주면 상품번호·제품명·판매가(販売価格)·정가·행사가·대표 이미지·브랜드명을 돌려준다. 폼의 「큐텐에서 불러왔어요 · 확인해 주세요」가 이것. 실패하면 「자동으로 못 불러왔어요」 한 줄만 보이고 직접 입력한다
  - 🔴 관문 3종이 한 세트다 — ①**살아 있는 오리엔시트 작성 토큰**만 ②qoo10.jp 주소 + 상품번호 ③토큰당 분당 5회(데이터베이스 계수). → **로그인한 브랜드가 쓰는 자리(상품 관리 화면·로그인한 시트)에서 부르려면 관문 ①을 「로그인한 브랜드 계정」으로 바꾼 새 관문이 필요**하다
  - 🔴 행사가(メガ割時)는 판매가 칸에 쓰면 틀린다 — 판매가는 販売価格
- 광고주 신청(서베이)의 `products` 는 그 신청서 안의 기록일 뿐 다시 꺼내 쓰는 구조가 아니다
- 캠페인은 오리엔시트 카드 값을 **발행할 때 복사**한다(`applyOrientCardPrefill`) — 카드 사본 기준이라 상품 표가 생겨도 이 흐름은 그대로 돈다
- 🔴 **오리엔시트 1건 = 제품(카드) 1개** — 새 구조 시트는 카드 1개 고정이다. 화면은 첫 카드만 그리고(`sales/orient.html` 「새 구조는 카드 1개 고정」), 제출은 서버가 2개 이상을 `cards_limit` 로 거부한다(임시 저장은 막지 않는다)(현재 원본 461 의 제출 함수 · 425 부터). 그래서 이 절의 「카드」는 그 시트의 **제품 1개**를 뜻한다

### 14-2. 의심·경우의 수 (반대론자 모드)
1. **(데이터 — 과거 기록이 바뀜)** 상품의 가이드를 고쳤을 때 이미 제출된 오리엔시트·발행 견적·캠페인이 따라 바뀌면 안 된다 → 오리엔시트 카드에는 **불러온 순간의 사본**을 저장한다(주의사항 묶음 스냅샷과 같은 방식). 상품을 고쳐도 기존 시트는 그대로
2. **(가격 — 자주 바뀜) → 판매가는 상품에 저장하지 않는다**(2026-10-13 사용자 결정). Qoo10 판매가는 행사·시기마다 바뀌므로, 오리엔시트에서 상품을 불러올 때마다 **Qoo10에서 판매가를 새로 조회**해 채운다. 저장값이 낡을 일이 없어 「오래됨」 경고·기준일 관리가 필요 없다
   - 조회 실패(상품 페이지 내려감·품절·Qoo10 화면 구조 변경) → 지금 폼처럼 「자동으로 못 불러왔어요 · 직접 입력해 주세요」
   - 행사 기간 가격은 다를 수 있다 → 지금 폼의 「캠페인 진행 기간 중 소비자가 실제로 구매하는 금액」 안내와 「큐텐에서 불러왔어요 · 확인해 주세요」 표시를 그대로 둔다
   - 조회 횟수 제한(분당 5회) → 상품 고르기를 짧은 시간에 여러 번 바꾸거나 여러 시트를 연달아 열면 걸릴 수 있다. 걸리면 「잠시 뒤 다시 불러오기」
3. **(화면 — 확인이 형식이 됨)** 가이드는 「그대로 쓸지 확인」이 대부분 그냥 넘겨진다 → 불러온 칸에 「상품에서 불러옴」 표시와 상품의 **마지막 수정일**을 보여 준다
4. **(화면 — 시작 장벽)** 처음 쓰는 브랜드가 상품부터 등록해야 하면 번거롭다 → **두 길**: 브랜드 화면의 「상품」에서 미리 등록 / 오리엔시트를 쓰다가 「이 제품을 상품으로 저장」
5. **(형식별 가이드)** 리뷰어와 시딩은 가이드 항목이 다르다(시딩은 촬영 가이드·해시태그·태그 계정) → 상품 하나에 **리뷰어용·시딩용 가이드를 따로** 둔다. 비어 있으면 그 형식으로 불러올 때 빈칸
6. **(권한 — 여러 담당자)** 한 브랜드에 담당자가 여럿(멤버관리)이면 누가 고치나 → 같은 브랜드 멤버는 모두 보고 고칠 수 있고, 수정 이력(누가·언제)을 남긴다(역할 구분은 「멤버관리」 설계 때 — §16: 대표·멤버 둘, 대표만 초대 관리·해제 — 관리자도 해제 가능, 브랜드 정보 수정은 멤버도, §16-2)
7. **(삭제)** 오리엔시트에 쓰인 상품을 지우면 → 시트는 사본이라 영향 없음. 상품은 **보관(숨김)** 으로 처리하고 완전 삭제는 두지 않는다(추천 — 14-5)

**현재 구현과 어긋나는 지점**
- 상품 표 신설 · Qoo10 불러오기의 관문 ①(작성 토큰)을 로그인 계정용으로 하나 더(※ 2026-10-14: **브랜드 페이지 1차에서 이미 만든다** — 링크 폼을 닫으므로 1차 작성 모달이 쓴다. 16-4 「오리엔시트 작성 경로」) · 오리엔시트 카드에 「어느 상품에서 불러왔나」 칸
- 견적 계산·캠페인 발행 자동 채움은 **카드 값 기준이라 바꿀 것이 없다**

**의도와 다르게 읽힐 수 있는 부분**
- 「상품」 단위 = **Qoo10 상품 1개(주소 1개)** 를 추천한다(14-5). 리뷰어형은 Qoo10 고정이고 LIPS·@cosme 는 추가 옵션일 뿐이라서
- 줄어드는 입력: 상품을 불러오면 오리엔시트에서 **새로 넣는 것은 캠페인마다 다른 값뿐**이다 — 모집 인원 · 추가 옵션 · 희망 모집 시작일(판매가는 자동 조회 후 확인)

### 14-3. 설계

**① 상품에 저장하는 것 / 안 하는 것**

| 저장 (상품) | 저장 안 함 |
|---|---|
| 상품명 · Qoo10 주소 · 상품번호 · 대표 이미지 | **판매가** — 불러올 때마다 Qoo10에서 조회 |
| 배송비 | 모집 인원 |
| 구매 가이드(자율/지정) | 추가 옵션(LIPS·@cosme) |
| 리뷰어용 리뷰 가이드 | 희망 모집 시작일 |
| 시딩용 리뷰 가이드 · 촬영 가이드 · 해시태그 · 태그할 계정 | |
| 예시 이미지·자료 | |

**② 브랜드 화면 — 상품 관리** (**브랜드 페이지 안에서** 관리 — 2026-10-13 사용자 결정. 좌측 메뉴는 늘리지 않고, **탭으로 나누지 않고 「브랜드」 메뉴 한 화면**에서 위는 브랜드 정보, 아래는 상품 목록을 보여 준다. 상품은 그 브랜드에 딸린 정보라서)
- **브랜드 정보는 평소 읽기 전용**이다. 한 번 등록하면 바뀔 일이 거의 없으므로 카드마다 제목 오른쪽의 「수정」을 눌렀을 때만 칸이 열리고 그 자리에 「취소」·「저장」이 나온다 — 브랜드 정보 카드(대표·멤버 모두)와 회사 정보 카드(대표 담당자만, 주소 검색은 이 카드)가 따로다(16-4 「브랜드 페이지 회사 정보」). 1차 브랜드 화면도 같다. 상품 목록·「상품 등록」은 수정 상태와 상관없이 쓸 수 있다
- 진입: 좌측 「브랜드」 화면 아래쪽 「상품」. 오리엔시트 작성 중의 「저장한 상품에서 불러오기」·「이 제품을 상품으로 저장」은 그대로(③)
- 목록(리스트/카드 보기 — 오리엔시트 목록과 같은 전환) · 등록 · 수정 · 보관
- 등록: Qoo10 주소 입력 → 「불러오기」 → 상품명·상품번호·이미지 자동 채움(판매가는 화면에 참고로만 보여 주고 저장하지 않는다) → 가이드 입력 → 저장. 불러오기가 실패하면 「자동으로 못 불러왔어요 · 직접 입력해 주세요」로 상품명을 직접 넣는다
- 마지막 수정일 · 「이 상품으로 만든 오리엔시트 n건」 표시

**③ 오리엔시트 작성 — 「상품에서 불러오기」**
- **어디서 되나**: 브랜드 페이지의 오리엔시트 작성 모달. 상품 기능은 2차 업데이트이고 그때는 토큰 링크 폼이 닫혀 있어(16-4 「오리엔시트 작성 경로」) **모든 시트가 로그인한 시트**다 — 로그인 없이 연 시트를 따로 다룰 일이 없다(2026-10-14 정정)
- 카드에 「저장한 상품에서 불러오기」 → 상품 고르기 → 저장값이 칸에 채워지고 **「상품에서 불러온 값 · 확인해 주세요」** 표시 + 상품의 마지막 수정일
- **판매가**: 불러오는 순간 Qoo10에서 조회해 채운다(지금 폼의 불러오기와 같은 동작·같은 안내). 실패하면 직접 입력. 조회 횟수 제한에 걸리면 「잠시 뒤 다시 불러오기」
- **「상품에도 저장할까요?」**: 불러온 칸(판매가 제외)을 카드에서 바꾼 경우, 「작성 완료」를 누를 때 **질문 모달 하나**로 묻는다(시트의 제품은 하나라 질문도 하나). 기본값 「이 시트에만」
  - 불러온 뒤 상품이 그 사이 바뀌었으면(다른 담당자·다른 시트에서 고침) 묻지 않고 「상품이 이 시트에 불러온 뒤에 수정되어 저장하지 않았습니다 — 브랜드 화면의 「상품」에서 확인해 주세요」만 보여 준다
  - 「상품에도 저장」·「이 제품을 상품으로 저장」을 하면 그 카드의 「불러온 때의 사본」·「불러온 시각」을 방금 저장한 값·시각으로 다시 잡는다
- 새로 입력한 제품은 「이 제품을 상품으로 저장」 — 그 카드에도 「불러온 상품」 표시를 단다(「이 상품으로 만든 오리엔시트 n건」에 들어간다)

**④ 사본 저장 — 카드에 두는 칸은 여기 한 곳에서만 정한다**
- 카드 값(불러온 값의 사본 — 브랜드가 고치면 바뀐다) · **「불러온 상품」 표시**(상품 id) · **불러온 시각** · **불러온 때의 사본**(「상품에도 저장」 질문의 비교 기준)
- 상품이 바뀌어도 기존 시트·견적·캠페인은 바뀌지 않는다

## 15. Figma 화면 코드 규칙 (2026-10-13)

> Figma 파일 「레버브시딩_브랜드」(`XG4hXdgySeN45Ele3EnN8H`)의 화면 이름 규칙. **코드만 보고 어느 페이지의 어떤 화면인지** 알 수 있게 한다. 사양서·작업표·병합 요청에서 화면을 가리킬 때 이 코드를 쓴다(예: 「2차 w04-06a」). Figma 맨 위 「화면 이름 읽는 법」 상자와 같은 내용이다 — 규칙을 바꾸면 둘을 함께 고친다.

**형식**: `단계 기기+페이지-화면+상태_이름` — 예) `2차 w04-06a_견적 발행됨 — 캠페인 등록 중`

| 자리 | 값 | 뜻 |
|---|---|---|
| 단계 | `1차` · `2차` · `보류` · `시안` | §4 맨 위 「현재 단계 정의」의 브랜드 페이지 1차 / 2차 업데이트 (Figma 섹션 [1차]·[2차]와 같은 뜻). 견적 1차·2차(§13)와는 **다른 말**이다 · `보류` = 어느 단계에 넣을지 정하지 않은 화면(Figma 「[보류] …」 구역 — 예: 이메일 변경, §16-5 5번). 번호는 원래 자리를 그대로 쓴다 · `시안` = 이미 그린 화면을 **다시 그려 보는 초안**(Figma 「[시안] …」 구역 — 지금 시안 화면은 없다. 2026-10-14 관리자 브랜드 상세 탭 재구성이 시안을 거쳐 1차로 확정됐다). 확정되면 그 단계 글자(`1차` 등)로 바꾸고 옛 화면을 지운다. 본문의 「디자인 시안」이라는 일반 낱말과는 다르다 |
| 기기 | `w` · `m` · `a` | 웹(PC) · 모바일 · 관리자 화면 |
| 페이지 (2자리) | `01`~`07` | 브랜드 페이지 **좌측 메뉴 기준** — 01 로그인 · 02 (1차에 없음 — 옛 회원가입, §16) · 03 브랜드(정보·상품 — 한 화면) · 04 오리엔시트 · 05 캠페인 · 06 멤버 관리 · 07 마이페이지(좌측 메뉴 맨 아래). 관리자 화면은 같은 업무의 번호를 쓴다(a04 = 관리자 오리엔시트) |
| 화면 (2자리) | `00` | 그 페이지의 첫 화면(목록) |
| | `01`~`89` | 그 페이지에서 열리는 화면(작성 모달·확인 모달·결과 화면 등). 흐름 순서대로 번호를 준다 |
| | `90` · `91` · `95` | 토스트 모음 · 상태 모음(입력 상태·하단 바 등) · 메일. 상태 모음이 한 페이지에 둘 이상이면 `92`·`93`… 차례로(예: w01-92) |
| 상태 (선택) | `a` · `b` · `c` … | 같은 화면의 다른 상태(오류·빈 상태·잠금·다른 보기). 예) `w04-04` 견적서 확인 → `w04-04a` 계산 실패 |

**정하는 법**
- 화면이 **어느 페이지에서 열리는가**로 페이지 번호를 정한다(그 기능이 어느 묶음이냐가 아니라). 예) 상품 고르기 모달은 오리엔시트 작성 모달에서 열리므로 `w04-12`이지 `w03`이 아니다
- **여러 페이지(03~07)에서 똑같이 열리는 공통 화면**(브랜드 고르기 등)은 `03` 브랜드 번호를 쓴다(2026-10-14 사용자 지시 — 예: `w03-01`·`m03-01`). **여러 페이지에 늘 붙는 표시**(새 초대 빨간 점 등)는 **그 표시가 가리키는 페이지 번호**를 쓴다(예: 새 초대 빨간 점 → 마이페이지로 가라는 표시라 `w07-03`·`m07-03` — 2026-10-14 사용자 지시). 같은 표시가 한 기기에서 여러 자리에 붙으면 대표 자리 하나만 그린다. 닫힌 브랜드 전환처럼 모든 화면 머리에 이미 그려진 것은 따로 번호를 주지 않는다
- 어느 페이지에서도 열리지 않고 **메일 링크로만 들어오는 화면**(비밀번호 설정 등)은 `01` 로그인 번호를 쓴다(로그인 전 화면이라서)
- **1차와 2차가 같은 번호면 같은 자리의 화면**이다(2차가 1차 화면을 바꾼 판). 예) `1차 w04-03` ↔ `2차 w04-03` 작성 내용 확인
- 웹과 모바일이 같은 화면이면 번호를 같게 하고 기기 글자만 바꾼다(`w04-00` ↔ `m04-00`)
- 새 화면은 그 페이지의 빈 번호 중 흐름에 맞는 자리를 쓴다. 기존 번호를 밀어 바꾸지 않는다(문서에 적힌 코드가 틀어진다). **`보류` 화면이 쓰는 번호는 빈 번호가 아니다** — 다른 화면에 주지 않는다. **다른 단계에 같은 번호가 이미 있으면 그 번호도 빈 번호가 아니다**(1차·2차 같은 번호 = 같은 자리 규칙 때문 — 예: 2차 `w04-01d` 가 있어 1차 새 상태는 `w04-01e` 부터)
- `보류` 화면을 어느 단계로 옮기면 **단계 글자만 바꾼다**. 그 단계에 같은 번호 화면이 없으면 「바꾼 판」이 아니라 새 화면이다

## 16. 브랜드 계정·멤버 — 관리자가 만들고, 대표 담당자가 초대 (2026-10-13)

> **브랜드 페이지 1차**에 넣는다(§4 맨 위 「현재 단계 정의」). **브랜드 페이지에는 가입·신청 화면을 두지 않는다**(2026-10-13 사용자 결정) — 계정은 **관리자가 만들거나**(대표 담당자) **대표 담당자가 초대한다**(멤버). 등록 안 된 브랜드는 **reverb.kr 「문의하기」 → 상담 → 관리자가 브랜드·대표 담당자를 등록하고 계정을 만든다**(광고주 신청서로 들어와도 계정은 관리자가 만든다 — 입구 정리는 16-5 4번).

### 16-1. 현재 상태 (2026-10-13, 코드 확인)
- **담당자 정보**: `brands.contacts`(jsonb, 여러 명 · 대표 표시 `is_primary`)가 정본. 관리자 브랜드 상세 페이지에서 이름·전화·이메일을 넣는다(`dev/js/admin-brand.js`). 브랜드 로그인 계정은 없다

  - 가입 인증번호 관문(`trg_signup_ticket_gate`, 493~499 — 시행일 2026-10-13, 스위치 상태는 착수 때 확인) — 관리자·초대로 만드는 브랜드 계정이 이 관문을 통과하는지 **개발 착수 전 코드 대조**(규칙 D)로 확인한다

### 16-3. 의심·경우의 수
1. **(데이터) 이메일 중복 — 「겹침」 정의처는 여기** — 이메일 하나에 계정 하나다. **겹침** = 그 이메일을 다른 계정(브랜드·인플루언서·관리자)이 이미 쓰고 있음. **메일 속 링크는 보낼 때의 상태에 묶인다** — 받는 사람이 링크를 누르는 순간 그 이메일의 계정 상태가 보낼 때와 달라졌으면(그사이 계정이 생겼거나·없어졌거나·다른 종류가 됐으면) 그 링크는 **쓸 수 없는 링크**가 된다(링크 종류와 상관없이 같은 규칙 · 화면은 16-4). 보낸 쪽(대표·관리자 — 재설정 링크와 비밀번호 찾기로 다시 받는 계정 만들기 메일은 본인)이 다시 보내면 그때의 상태로 다시 갈린다. **관리자가 대표 담당자 계정을 만들 때**: 인플루언서·관리자 계정과 겹치면 만들지 않는다 → 관리자 화면에 「이미 다른 용도로 쓰는 이메일입니다 — 다른 이메일을 받아 주세요」. 브랜드 계정과 겹치면(다른 브랜드 담당) 새로 만들지 않고 관리자가 **브랜드 연결**로 처리하고 그 사람에게 「브랜드 연결 안내」 메일을 보낸다(관리자가 브랜드를 추가로 이을 때도 같다 — 관리자가 잇는 연결은 대표로만, 16-2 「여러 브랜드」). 대표의 초대는 아래 수락 방식
   - **대표가 초대할 때 겹치면**(2026-10-13 사용자 결정 — 초대받은 사람이 수락): 겹치든 아니든 **그 이메일로 초대 메일을 보낸다**. 대표 화면은 언제나 「초대를 보냈습니다」·「초대 대기」로 같다(겹침이 대표에게 드러나지 않는다). 다시 보내기·만료·취소도 일반 초대와 같다. 메일 내용만 받는 사람에 따라 다르다 — ⓐ새 이메일: 비밀번호 설정 ⓑ다른 브랜드 계정: 「기존 계정으로 로그인해 수락하면 이 브랜드가 연결됩니다」(비밀번호를 아직 정하지 않은 계정이면 먼저 받은 설정 메일로 정한 뒤 수락) ⓒ인플루언서·관리자 이메일: 「이 이메일로는 브랜드 계정을 만들 수 없어요 — 다른 이메일로 초대를 요청해 주세요」(수락 단추 없음 — 그 초대도 상한 한 자리를 차지하고 만료까지 「초대 대기」로 남으며, 대표가 취소하면 바로 빠진다). 관리자 일은 생기지 않는다
2. **(UX) 갑자기 오는 메일** — 담당자는 신청하지 않은 메일을 받는다(계정 생성 메일 · 관리자가 기존 계정에 브랜드를 이었을 때의 「브랜드 연결 안내」 메일 · 대표 초대 메일 ⓐ·ⓑ·ⓒ — 1번 하위, 모두) → 메일에 누가(레버브 운영팀·초대한 대표 이름) 왜 보냈는지(계정 생성·브랜드 연결·초대·초대 불가), 모르는 메일이면 무시해도 된다는 문장을 넣는다
3. **(법률·약관) 동의 시점** — 계정이 동의 없이 먼저 생긴다 → **비밀번호 설정 화면에서 이용약관·개인정보처리방침 동의**를 받고, 동의 전에는 로그인되지 않는다. 브랜드용 약관·방침 문구는 `/약관확인` 대상이다(브랜드 담당자 정보 수집·이용)
4. **(외부 시스템) 링크 미리 열림** — 메일 보안 검사기가 링크를 먼저 열어 설정 링크가 소진된 사고가 있었다 → 관리자 비밀번호 설정 화면이 쓰는 방식(링크를 열기만 해서는 소진되지 않게)을 그대로 쓴다(계정 만들기·초대·비밀번호 재설정 메일 모두 — 16-4 「링크 확인 화면」). 만료·소진 시 「다시 보내기」(관리자 = 계정 생성 메일 — 비밀번호를 아직 정하지 않은 본인도 비밀번호 찾기로 다시 받는다(16-4 「비밀번호 재설정」 ⓑ) · 대표 = 초대 메일 · 재설정 = 본인이 비밀번호 찾기에서 다시 요청, 자리 제한은 16-2 「멤버 수 상한」). **세 경우(계정 만들기 · 초대 · 재설정) 모두 다시 보내면 새 링크(새 기한)가 가고 이전 링크는 바로 쓸 수 없다**(쓸 수 없는 링크 화면은 만료와 같은 안내 — 이유를 나누지 않는다. 실제 동작은 개발 때 인증 쪽에서 확인)
5. **(UX) 퇴사·대표 부재** — 대표가 퇴사하면 초대는 아무도 못 한다(해제는 관리자도 할 수 있다 — 16-2 예외) → 관리자가 대표를 바꾸는 길(위 결정). **대표 바꾸는 순서(정의처는 여기)**: 멤버가 있으면 관리자가 기존 멤버 중 한 명을 대표로 지정하고, 옛 대표는 **멤버로 내려간다**(필요하면 이어서 해제 — 대표가 직접 대표를 넘길 때도 같다). 멤버가 있는 동안 대표를 바로 해제하지 않는다 — 먼저 새 대표를 지정한다. 멤버가 없으면 관리자가 옛 대표를 해제해 「대표 없음」으로 만든 뒤 「계정 만들기」(그 전에 담당자 목록에서 새 사람 줄에 대표 표시를 옮기거나 대표 이메일을 새 주소로 고친다 — 안 고치면 옛 대표의 이메일이라 1번 「겹침」이 된다) 또는 「브랜드 연결 추가」(서버가 표시를 옮긴다 — 16-4 「화면 정책 넷」 ②)로 새 대표를 세운다. 해제하면 **그 브랜드 범위만** 즉시 끊긴다 — 연결된 브랜드가 하나도 남지 않으면 브랜드 페이지를 쓸 수 없다 — 로그인하면 바로 로그아웃되고 안내 화면이 뜬다(16-4 「로그인은 됐지만 쓸 수 없는 계정」 — 대기 중인 초대가 있으면 예외)(한 계정 여러 브랜드). 그 사람이 만든 오리엔시트는 브랜드에 남는다
6. **(권한) 여러 브랜드 전환** — 화면에 보이는 브랜드와 서버가 허용하는 브랜드가 어긋나면 남의 브랜드가 보인다 → 브랜드 범위는 **서버 접근 정책이 판정**하고 화면 전환은 보기만 바꾼다
7. **(데이터) 대표 담당자 정보 입력 (정의처는 여기)** — 브랜드가 없으면 관리자가 먼저 브랜드를 만든다. 담당자 정보는 어디서 받든(reverb.kr 문의·상담 · 광고주 신청서 · 기존 연락) **관리자가 브랜드 상세 페이지에 직접 입력**한다 — ⚠️ 단 **광고주 신청서로 처음 보는 브랜드가 들어오면** 예외(브랜드 만들기와 입력 둘 다 — 이미 있는 브랜드의 신청서는 위 원칙대로 관리자가 입력한다): **신청서가 브랜드를 만들고 신청자를 대표 담당자로 먼저 넣으므로**(확인 안 된 이메일 — 16-6 「사실 정정」) 관리자는 그 값을 확인하고 고친다. reverb.kr 은 이 시스템으로 자동으로 넘어오지 않는다(16-1). 이메일이 틀리면 비밀번호 설정 메일이 남에게 간다 → 「계정 만들기」 전에 **받을 이메일을 크게 보여 주는 확인 모달**을 둔다
8. **(UX) 로그인 화면 — 로그인·비밀번호 찾기만** — 가입 화면이 없으면 계정 없는 사람이 갈 곳이 없다 → **로그인 화면은 로그인·비밀번호 찾기만 둔다**(2026-10-13 사용자 결정 — 다른 사이트로 가는 연결도 두지 않는다). 브랜드 페이지는 계정을 받은 사람만 오는 곳이고, 계정 없는 브랜드의 안내는 reverb.kr·운영팀 연락이 맡는다
9. **(법률·약관) 다른 곳에서 받은 개인정보** — 7번의 세 곳(reverb.kr 문의 · 광고주 신청서 · 기존 연락)에서 받은 담당자 정보를 이 플랫폼 계정에 쓴다 → **1차 출시 전에 `/약관확인` 으로 한 번 판단**하고, 필요한 안내(용도 알림 등)는 **관리자가 대표를 세울 때 보내는 두 메일 양식**(계정 생성 메일 = 비밀번호 설정 메일 · 브랜드 연결 안내 메일) 자체에 넣는다 — 그러면 7번의 세 곳에서 받은 정보로 관리자가 대표를 세우는 두 길 모두에 같은 안내가 들어간다(5번의 「기존 멤버를 대표로 지정」은 대상이 아니다 — 7번의 세 곳에서 새로 받은 정보를 쓰지 않기 때문이다). **판단이 끝나기 전에는 브랜드 계정을 만들지 않는다**(출시 관문 — 10번). 해제된 멤버 개인정보 보관 기간(16-5 2번)도 이 판단에서 정한다. 계정에 쓰는 정보의 동의는 3번(비밀번호 설정 화면)에서 받는다
10. **(운영) 기존 거래 브랜드** — 대표 담당자 정보가 비어 있는 기존 고객은 브랜드 페이지를 쓸 수 없다 → **1차 출시 전에 운영팀이 거래 중인 브랜드의 대표 담당자 정보를 채워 둔다**(출시 준비 항목 — 계정 생성은 9번 판단이 끝난 뒤)
11. **(데이터) 로그인 이메일이 바뀌어야 할 때 — 1차에는 바꾸는 길이 없다**(2026-10-14 사용자 결정 — 16-2 「마이페이지」). 담당자가 회사 메일을 바꿔도 옛 이메일로 계속 로그인한다. 옛 이메일을 더는 못 쓰게 되면 그 계정은 **비밀번호 찾기도 못 한다**(메일이 옛 주소로 간다). 그때의 우회는 **새 이메일로 새 계정을 만들고 옛 계정을 해제**하는 것뿐이다 — ⓐ**멤버**: 대표가 새 이메일을 초대 → 수락 뒤 옛 계정 해제. 브랜드가 가득 찼으면(16-2 「멤버 수 상한」) 옛 계정을 먼저 해제하거나 관리자가 상한을 늘린 뒤 초대한다 ⓑ**대표 — 멤버가 있을 때**: 16-3 5번대로 기존 멤버를 대표로 세움(옛 대표는 멤버로 내려감) → 새 대표가 그 사람의 새 이메일을 초대(가득 찼을 때는 ⓐ와 같다) → 필요하면 대표를 다시 넘김 → 옛 계정 해제 ⓒ**대표 — 멤버가 없을 때**: 관리자가 담당자 목록의 대표 이메일을 새 주소로 고침 → 옛 대표 해제(「대표 없음」) → 「계정 만들기」. ⓐ·ⓑ는 초대로 들어오므로 비밀번호 설정 화면에서 이름·연락처를 다시 넣고, ⓒ는 담당자 목록 값으로 채워진다. ⓐ·ⓑ·ⓒ 어느 쪽이든 새 주소가 이미 다른 브랜드 계정이면 새 계정이 아니라 16-3 1번대로 브랜드 연결이 된다. 이 우회로 충분한지는 16-5 5번 판단 때 함께 본다

**현재 구현과 어긋나는 지점**: §4 옛 골격 「2차 — 정식 로그인 계정 · 회원가입·온보딩」은 이 절로 대체된다(가입·신청 화면 없음). §3 의도 모호점·§6 다음 액션·§7 확정의 「발급 단위」와 §7 「한 계정 여러 브랜드 연결 단계」는 이 절 결정(브랜드 단위 + 한 계정 여러 브랜드, 1차)으로 정해졌다

### 16-4. 화면 (Figma — §15 코드)
- `02` 페이지는 **1차에 없다**(옛 회원가입 화면은 Figma에서 지웠다 — 2026-10-13). 로그인 화면에는 로그인·비밀번호 찾기만(16-3 8번)
- 비밀번호 설정 화면(메일 링크로 들어옴) — 약관 동의 포함. 초대로 들어온 멤버는 이름·연락처 칸도 나온다(16-2 「마이페이지」)
- **쓸 수 없는 링크 화면** — 설정·초대·비밀번호 재설정 링크 공용(재설정 링크면 「비밀번호 찾기에서 다시 요청」 안내). 만료 · 이미 사용됨 · 보낼 때와 상태가 달라짐(16-3 1번) · 다시 보내서 이전 링크가 무효가 됨(16-3 4번) — 넷 모두 같은 안내로 한 화면이 보여 준다(이유를 나누지 않는다)
- **링크 확인 화면(「계속하기」)** — 계정 만들기·초대·비밀번호 재설정 메일의 링크를 열면 먼저 뜬다. 사람이 「계속하기」를 눌러야 링크를 쓴다(16-3 4번 — 메일 보안 프로그램의 미리 열기 대비). 제목만 메일 종류에 따라 바꾼다. 쓸 수 없으면 쓸 수 없는 링크 화면

13. **브랜드가 많을 때 브랜드 고르기(w03-01a)** — 검색 칸을 몇 개부터 보일지, 목록 순서(지금 브랜드를 맨 위 + 나머지 이름순 / 전부 이름순), 모바일 메뉴 서랍(m03-01)에도 검색을 둘지
14. ✅ **16-6 「대표 담당자 저장 때 자동 발송」 — 정해지지 않았다, 본문 설계대로 바꾼다**(2026-10-14 사용자 정정 — 「지금 개발서버의 저장하면 자동 발송은 정해진 게 아니야. 기존 설계 방식대로 변경될 예정」). 1차 정본은 본문이다. **개발이 개발서버 구현을 바꿀 것**(개발 몫): ①「계정 만들기」 단추 + 받을 이메일 확인 모달(16-3 7번, a03-01·01a·01b) — 담당자 저장으로는 메일을 보내지 않는다 ②이메일 겹침 — 다른 브랜드 계정이면 16-3 1번(새로 만들지 않고 브랜드 연결 + 안내 메일), 인플루언서·관리자 이메일이면 막는다 ③권한 — 「브랜드 페이지 계정 관리」 권한 항목(16-4, 기본 캠페인 관리자 이상, 권한 관리에서 변경 가능). 16-6 의 저장 때 안내(「계정 메일은 캠페인 관리자 이상이 보냅니다」)는 없앤다 — 권한이 없으면 계정 단추가 안 보인다(a03-00f) ④링크 유효 시간 24시간(16-4 「로그인 정책」 ④) — 대표 계정 줄의 「~까지 유효(예상)」 판정의 선행 조건 ⑤잘못된 이메일로 보냈을 때는 「해제」 → 담당자 이메일 고치기 → 「계정 만들기」(대표 계정 줄의 상태와 버튼) — 설정 전 이메일 수정으로 자동 재발송하지 않는다. ⚠️ 광고주 신청서가 신청자를 대표로 넣는 사실(16-3 7번)은 확인 모달이 막는다 — 관리자가 받을 이메일을 보고 「계정 만들기」를 누른다.
