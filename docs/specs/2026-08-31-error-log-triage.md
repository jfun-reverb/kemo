## 조사 결과 — 18건 분류 (5 + 6 + 6 + 1 = 18)

### A. 진짜 결함 — 코드를 고쳐야 함 (5건 / 10회)

| # | 오류 | 횟수 | 최근 | 원인 |
|---|---|---|---|---|
| A1 | `permission denied for function get_application_messages` | 5 | 8/28 | **원인 확정** |
| A2 | `[object Object]` (`countActiveApplications`) | 2 | 8/21 | **원인 확정** |
| A3 | `decode_failed` (`uploadMessageAttachment`) | 1 | 8/19 | 미확인 |
| A4 | `invalid input syntax for type uuid: "demo-4"` | 1 | 8/24 | 미확인 |
| A5 | 오류 자리에 캠페인 데이터가 통째로 (`fetchCampaigns`) | 1 | 8/29 | 미확인 |

#### A1 — 메시지 화면이 세션 끊김에서 안 살아남는다 ★가장 급함
- **증상:** 아이폰 사파리 회원이 응모건 메시지 화면을 열면 거부. 8/25~8/28에 5회.
- **원인:** `storage.js:3808` 의 조회가 `retryWithRefresh` 없이 호출된다. 바로 아래 발송 함수(3819)는 감싸져 있다.
- **왜 그렇게 되나:** 운영 데이터베이스 실측상 이 함수는 로그인 회원(`authenticated`)만 실행 가능하고 비로그인(`anon`)은 거부다. 세션이 끊긴 채 호출하면 비로그인 권한으로 가서 정확히 이 메시지가 나온다.
- **같은 유형 전수 조사:** `storage.js` 안에서 재시도 보호 없이 원격 호출 함수를 부르는 함수 **27개**. 그중 **비로그인 호출이 설계상 정상인 9개**(수신거부·오리엔시트 3종·재가입 차단 확인·행사 초대 확인·방문 기록·오류 기록·조회수)는 제외 대상. **나머지는 개발 세션이 화면별로 판정해야 한다.**
- ⚠️ 특히 `fetchDeliverableGate`(결과물 제출 가부 판정)는 조회 실패를 「막지 않음」으로 처리하도록 설계돼 있어 **실패해도 조용하다** — 우선 검토 대상.

#### A2 — 오류를 기록했는데 무슨 오류인지 모른다
- **원인:** `error-report.js:33` `_toMessage` 가 `message` 없는 객체를 만나면 `String(v)` → `[object Object]`.
- 🔴 **이게 단순 표시 문제가 아닌 이유:** `countActiveApplications`(storage.js:912) 주석이 이미 경고한다 — 「조회 실패가 0(=아무도 응모 안 함)으로 읽혀 **정원이 남은 것처럼 보인다**」. 즉 이 오류가 2회 났다는 것은 **정원 판정이 2회 틀렸을 수 있다**는 뜻이고, 무슨 오류였는지 알 수 없어 **추적이 불가능한 상태**다.

### B. 안내가 막다른 길 (6건 / 36회) ★횟수가 가장 많음

| # | 오류 | 횟수 |
|---|---|---|
| B1~B3 | `Email link is invalid or has expired` | 14 + 14 + 3 = **31** |
| B4~B6 | `For security purposes, you can only request this after N seconds.` | 3 + 1 + 1 = **5** |

- **B1~B3 은 그 자체로는 정상 거부다.** 재설정 링크는 시간이 지나면 못 쓴다. 그리고 링크를 주소의 `#` 뒤에 담아 **메일 클릭 추적이 미리 태우지 못하게** 이미 조치돼 있다(`app.js:199~203` 주석 + 실제 구현 확인).
- **만료 화면도 잘 만들어져 있다.** `#resetPwExpired` 는 이유 3줄과 「もう一度メールを送る」(다시 메일 보내기) 버튼을 준다.
- 🔴 **문제는 그 버튼을 누른 다음이다.** 연타 방지에 걸리면 회원이 보는 것은 `エラーが発生しました`(오류가 발생했습니다) 하나뿐이다(`auth.js:280~282` → `ja.js:881`). **몇 초 기다리면 되는지 안 알려준다.**
- 즉 **「다시 보내세요」라고 안내해 놓고 그대로 했더니 오류만 나오는 막다른 길**이다. B4~B6 5회가 실제로 그 벽에 부딪힌 흔적이다.
- ⚠️ 문구를 일반화한 것은 **계정 존재 여부를 숨기기 위함**이고 그 취지는 옳다(`security.md` 「계정 열거 방지」). 다만 **연타 방지는 계정 존재와 무관하게 걸리므로**, 「잠시 후 다시 시도해 주세요」로 바꿔도 계정 정보가 새지 않는다.

### C. 우리 코드가 아님 — 노이즈 (6건 / 13회)

| # | 오류 | 판정 근거 |
|---|---|---|
| C1 | `Can't find variable: DarkReader` | 다크 모드 확장 프로그램 주입 |
| C2 | `Can't find variable: __gCrWeb` | 아이폰 크롬 내부 객체. **필터에 `window.__gCrWeb` 로 적혀 있어 접두어 없는 메시지를 못 잡음** |
| C3 | `Can't find variable: _AutofillCallbackHandler` | 아이폰 자동완성 |
| C4 | `undefined is not an object ('window.webkit.messageHandlers')` | 아이폰 웹뷰. **필터 목록에 없음**(`webkit-masked-url` 만 있음) |
| C5 | `Object Not Found Matching Id:1, MethodName:update, ParamCount:4` | 알려진 확장 프로그램 오류 |
| C6 | `Maximum call stack size exceeded.` (7회) | **아래 근거 3종** |

#### C6 판정 근거 — 7회나 나서 따로 검증했다
1. 스택이 `Hk` ↔ `Fk` 두 함수의 무한 상호 호출인데, **이름이 축약형**이다. 이 저장소 빌드는 단순 이어붙이기라 **축약을 하지 않는다**(`build.md`).
2. 스택이 가리킨 줄은 `index.html` 의 **187·194·195·224**. 발생 시점(8/20) 운영 빌드에서 **우리 자바스크립트는 2111번째 줄부터** 시작하고, 그 앞은 CSS다. 즉 **우리 코드일 수 없다.**
3. 브라우저가 `GSA/434.2` — **구글 앱 안의 웹뷰**다.

→ 구글 앱이 주입한 스크립트의 무한 재귀가 우리 페이지 주소로 보고된 것.
⚠️ **노이즈 필터의 「2층 일반 규칙」(스택에 우리 파일이 없으면 노이즈)이 이걸 못 잡은 이유**는, 스택 문자열에 `globalreverb.com` 이 들어 있기 때문이다. 규칙은 「우리 파일 이름이 있나」를 볼 뿐 **줄 번호가 우리 코드 영역인지는 안 본다.**

### D. 정상 거부 (1건 / 2회)
- `모집 정원이 마감되었습니다 (slots: 5, current: 5)` — 막은 것이 맞는 동작. **다만 「예상 못 한 오류」로 분류돼 목록에 남는다.**

## 의심·경우의 수 (규칙 B)

### 이 방향에서 깨질 수 있는 경우 5가지

1. **[기술] A1 을 고쳐도 세션 끊김 자체는 안 없어진다.** `retryWithRefresh` 는 갱신 토큰이 살아 있을 때만 산다. 갱신 토큰까지 만료됐으면 재시도도 실패하고, 그때 회원은 **여전히 오류를 본다**. → 재시도 실패 시 **로그인 화면으로 유도**하는 처리가 함께 없으면 절반만 고치는 것.
2. **[기술] 노이즈 필터에 이름을 추가하는 것은 두더지 잡기다.** 코드 주석이 이미 그렇게 경고한다. 다음 달에 다른 확장이 다른 이름으로 또 들어온다. → **줄 번호 기반 판정**(우리 자바스크립트 시작 줄보다 앞이면 우리 코드 아님)이 근본적이지만, **빌드마다 그 줄이 바뀌므로** 빌드 시점에 그 값을 심어야 한다. 난이도가 있다.
3. **[UX] B 를 고칠 때 남은 시간을 정확히 보여주면 오히려 나쁠 수 있다.** 「43초 후 다시」라고 적으면 회원이 43초를 세고 있다가 눌러야 한다. → **「1분쯤 뒤에 다시 눌러 주세요」** 정도로 뭉뚱그리고, 가능하면 **버튼을 그 시간 동안 비활성**으로 두는 편이 낫다. 문구만 고치면 회원은 여전히 연타한다.
4. **[UX] 정상 거부를 목록에서 치우면 「진짜 조용해진 것」과 구분이 안 된다.** 「모집 정원 마감」이 갑자기 하루 500회 나면 그건 이상 신호인데, 무시 처리하면 안 보인다. → **지우지 말고 「예상된 거부」로 분류**해 기본 화면에서만 빼는 편이 안전하다. 이미 그 구조가 있다(`APP_ERROR_EXPECTED_PATTERNS`).
5. **[데이터] A2 를 고쳐도 이미 난 2회의 원인은 영영 모른다.** 기록에 남은 것이 `[object Object]` 뿐이라 복구 불가. → 고치는 것은 **앞으로만** 유효하고, 그 사이 정원 판정이 틀렸을 가능성은 **별도로 확인**해야 한다(해당 시각 캠페인 응모 수 대조).

### 사용자 의도와 다르게 읽힐 수 있는 부분
- **「처리」가 두 가지다.** ①원인을 고치는 것 ②관리자 화면에서 「해결됨/무시」를 눌러 목록을 비우는 것. 이 사양서는 ①을 다루고, ②는 아래 「사용자 확인 필요」에 따로 뒀다.
- **「18건」은 오류 종류 수이지 발생 횟수가 아니다.** 실제 발생은 **61회**이고, 그중 **36회(59%)가 비밀번호 재설정 한 갈래**다.

## 사용자 확인 필요

1. **목록의 「무시」 처리를 지금 할지** — C 6건과 D 1건은 우리 코드 문제가 아니므로 목록에서 치울 수 있다. 다만 **운영 화면을 직접 누르는 일**이라 승인이 필요하다.
2. **「못 읽는 표」 경고 해제** — 별개 항목. `_cert_at_backup_20260819`(마이그레이션 342 백업 표)를 코드가 읽는 자리가 **0곳**임을 점검 스크립트로 확인했다. `--record` 로 그 결과를 남기면 경고가 사라지는데, **운영 데이터베이스에 기록**하는 동작이라 승인이 필요하다.
3. **Supabase 사용량 초과 경고** — 운영 프로젝트 상단에 `EXCEEDING USAGE LIMITS` 딱지가 떠 있다. 이 사양서 범위 밖이지만 **별도로 봐야 한다.**

## 이 사양서의 한계 (밝혀 둔다)

- **규칙 C(자기 정합성 점검)를 다른 눈으로 돌리지 못했다.** 이 세션은 요청 없이 서브 에이전트를 부르지 않는다는 지시를 받았다. 작성자 자가 재독만 거쳤으므로, **개발 세션이 착수 전에 한 번 더 봐 주길 요청한다.**
- **A3·A4·A5 는 원인 미확인이다.** 각 1회씩이라 재현 정보가 부족하다. 추측으로 채우지 않았다.
