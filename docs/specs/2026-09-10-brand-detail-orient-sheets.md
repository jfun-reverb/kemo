# 브랜드 상세 「신청 내역」 → 오리엔시트 기준으로 교체

**작성일:** 2026-09-10
**작성:** 기획 세션 (브랜치 `feature/기획-브랜드상세-오리엔`)
**배경:** 브랜드 서베이(광고주 신청 폼)는 2026-06-30 공개 제출 차단 이후 쓰지 않고, 브랜드 영업은 **오리엔시트(견적서 포함)** 로 관리한다(사양서 `2026-09-08-orient-sheet-simplify-and-quote.md`). 그런데 브랜드 관리 → 브랜드 상세 창의 맨 아래 구역은 여전히 **서베이 신청 표(`brand_applications`)** 만 보여준다. 사용자 지시(2026-09-10): 「이 브랜드의 신청 내역을 현재 기획 내용과 맞춘다」.

---

## 0. 한 줄 요약

브랜드 상세의 「이 브랜드의 신청 내역」 구역을 **「오리엔시트 (N건)」 카드 목록**으로 바꾸고, 브랜드 목록의 「신청수」 열을 **「오리엔시트 수」** 로, 삭제 가능 판정을 **시트 건수까지 보는 것**으로 맞춘다. 서베이 등록 버튼(「이 브랜드로 신규 신청」)은 상세 창에서 뺀다. **데이터베이스 변경 없음.**

### 1-2. 운영 실측 (2026-09-08 사양서 §1-2 재인용 — 이번 사양서에서 다시 세지 않았다)

- 시트 37건(발행 23 · 제출 9 · 임시 5). **운영 시트는 37건 전부 옛 구조**(`issued` 없음 — 새 구조는 9/8 이후 개발서버에만 있고 운영 미배포). 그중 **카드가 여러 개인 것 14건**(나머지 23건은 옛 구조·카드 1개). 견적(`data.quote`)은 새 구조 시트에만 있어 **운영에는 아직 0건** → 이 변경을 운영에 올리는 시점에는 브랜드 상세의 견적 한 줄이 **전부 「견적 없음(옛 형식)」** 으로 보인다. 오류가 아니라 사실이다(§4-1-a).
- ⚠️ **신청 연결 없는 시트 비율·브랜드별 시트 수 분포는 실측하지 않았다.** 그래서 §4-6 의 브랜드 단위 조회도 「브랜드당 몇 건」이라는 가정 없이 목록 집계와 **같은 반복 조회 방식**을 쓴다.

### 1-3. 이 제안과 충돌 가능성 있는 기존 동작

1. **모달 겹침** — 브랜드 상세 창(612)이 오리엔시트 상세 모달(기본 500)보다 위다. 카드에서 상세를 그냥 열면 **브랜드 창 뒤에 깔려 안 보인다.** 「오리엔시트 발급」 버튼이 이미 같은 문제를 「브랜드 창을 먼저 닫는」 방식으로 푼다 → 같은 방식(§4-5).
2. **삭제 판정 어긋남**(위 표) — 이번에 시트 수를 받아 오면 화면 판정을 서버와 같은 셋으로 맞출 수 있다. 서버 함수는 손대지 않는다.
3. 🔴 **「이 브랜드로 신규 신청」은 서베이 신청을 새로 만드는 마지막 살아 있는 길이다.** 브랜드 서베이 페인의 「직접 등록」 버튼(`dev/admin/index.html` 2589줄)은 공개 접수 중단 때 **`disabled`** 로 잠겨 있고, 나머지 호출부(`admin-brand.js` 2486줄)는 **기존 신청의 수정** 경로다. 그래서 이 버튼을 빼면 **신규 서베이 등록 경로가 완전히 끊긴다** — 사용자가 알고 「그래도 뺀다」로 결정(2026-09-10, §2 표). `openNewBrandAppModal` 함수·모달은 수정 경로가 쓰므로 **남긴다**.
4. **`renderBrandAppBundleCard`·`renderBrandAppsBundledView`·`toggleBrandAppBundleCard`·`BRAND_QUOTE_CONST`·`calcBrandAppFinalKrw`** — 상세 구역이 사라지면 앞의 셋은 호출부가 0이 된다. `BRAND_QUOTE_CONST`·`calcBrandAppFinalKrw` 는 서베이 페인·엑셀에서도 쓰므로 **남긴다**. 앞의 셋을 지울지는 개발 판단(지우면 죽은 코드 0, 남기면 무해).
5. `brands.total_applications` 칸·트리거(082) — **손대지 않는다.** 화면에서 안 읽을 뿐이다.

### 1-4. 미해결 백로그·관련 작업

- 운영현황 브랜드 뷰의 신청 트리(`get_brand_ops_detail`)를 오리엔시트 기준으로 바꾸는 것 — 서버 집계 함수 재정의가 필요해 **별건**.
- 캠페인 번호가 앞으로 전부 외부 형식(`B-C`)이 되는 것 — 견적 번호는 `{orient_no}-Q` 로 별개라 충돌은 없지만, 신청 번호 자리(`A`)가 영영 안 쓰이게 된다. 채번 체계를 오리엔 번호 기준으로 바꿀지는 **별도 기획거리**(§8 안내).

## 2. 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우

1. **(UX·모달)** 카드를 눌러 오리엔시트 상세를 열면 브랜드 창 뒤에 깔린다 → §4-5 「브랜드 창을 닫고 연다」. ⚠️ 상세를 닫아도 브랜드 창은 **되돌아오지 않는다**(「오리엔시트 발급」과 같은 동작. 되돌리기를 만들면 브랜드 창 저장 상태를 들고 있어야 해 이번엔 안 한다).
2. **(데이터·옛 시트)** 옛 구조 시트(`issued` 없음 — 운영 37건 전부)는 `form_type` 이 NULL 이고 견적이 없으며, 그중 14건은 카드가 여럿이다 → 형식은 `osCardsSummary(data)` 로(오리엔 목록과 같은 표시), 견적 칸은 **「—」가 아니라 「견적 없음(옛 형식)」** 으로 구분해 오류로 안 읽히게 한다(§4-1). 운영 배포 직후에는 **모든 카드가 이 문구**를 보이게 되는데, 그것이 사실이다.
3. **(데이터·새 시트 제출 전)** 새 구조인데 아직 제출 전(`draft`)이면 `quote`·`quote_error` 둘 다 없다 → 「제출 전」. 제출 뒤 `quote_error` 면 사유별 한 줄(오리엔 상세 `osQuoteCard` 의 문구와 **같은 문구** — §4-1 도우미 공유).
4. **(UX·옛 브랜드)** 서베이만 있고 시트가 0건인 옛 브랜드는 상세가 「오리엔시트 없음」이 되고 **과거 서베이 신청이 어디서도 안 보인다** → 구역 아래 안내 한 줄 「지난 브랜드 서베이 신청 N건은 브랜드 서베이 화면에서 봅니다」(N 은 §4-3 의 건수 조회를 재사용. 0건이면 안 그림).
5. **(조회 실패)** 실패는 전부 `null` 이고 자리마다 실패 표시가 따로 있다 — 목록 열 「—」 · 상세 구역 제목은 건수 없이 「오리엔시트」 + 본문 「불러오지 못했습니다」 · 서베이 건수 안내줄 「서베이 신청 수를 불러오지 못했습니다」 · 캠페인 번호 자리 「—」 · 삭제 버튼은 안 그리고 잠금 안내줄(§4-3). **0건인 척 그리지 않는다**(마이그레이션 276 원칙).
6. **(1,000행)** 목록 집계도, 브랜드 단위 상세 조회도 **둘 다 `fetchAllPaged` 반복 조회**(캠페인 수 함수와 뜻은 같고 — 전건 반복 — 도우미만 `fetchAllPaged` 로 통일, §1-1). 브랜드당 건수를 실측하지 않았으므로(§1-2) 「작을 것」이라는 가정에 기대지 않는다.
7. **(권한)** 오리엔시트 열람은 `is_admin()` 전원 — 서베이와 같아 등급별 차이 없음. 확인 완료.
8. **(삭제 문구)** 서버 거부 문구(325)는 셋을 다 말하지만 서베이 신청을 **「신청」이라는 옛 이름**으로 부른다 — 화면은 「서베이 신청」으로 바꾸므로 이름이 갈리지만, 데이터베이스를 안 건드리므로 그대로 둔다. 화면 확인창 문구만 「캠페인·서베이 신청·오리엔시트」 셋으로 고친다.
9. **(UX·운영현황)** 브랜드 상세는 시트 기준, 운영현황 브랜드 뷰는 서베이 트리 기준으로 **두 화면이 다른 족보**를 말한다 — 사용자가 알고 별건으로 미룬 것(2026-09-10). 사양서에 남겨 다음 기획이 잇는다.

## 4. 설계

### 4-1. 상세 구역 「오리엔시트 (N건)」 — 카드 1장 = 시트 1건

`renderBrandDetailFormHtml(b, sheets, surveyCount, campMap)` 의 마지막 `section(...)` 을 교체한다. 렌더는 새 함수 `renderBrandOrientSheetsView(sheets, campMap)` → `renderBrandOrientSheetCard(s, campMap)`. **펼침 없음**(제품 표는 오리엔 상세가 갖고 있다 — 두 벌 금지). 최신 발급순.

**구역 제목**: 시트 목록 조회가 성공했으면 「오리엔시트 (N건)」, 실패(`null`)면 **건수 없이 「오리엔시트」**(「(0건)」으로 그리지 않는다 — §2-5).

카드 한 장(한 줄 머리 + 한 줄 요약):

| 자리 | 값 | 출처 |
|---|---|---|
| 머리 | 오리엔 번호 | `s.orient_no` |
| 머리 | 형식 배지 | `osCardsSummary(s.data)` — 옛 시트는 카드별 집계, 새 시트는 발급 형식(·시딩 채널) |
| 머리 | 상태 배지 | `osStatusOf(s)` — 발급 / 제출됨 / 일부 발행 (n/m) / 발행됨 / 만료. **오리엔 목록과 같은 배지·색** |
| 머리 우측 | 발급일 · 작성 기한 (만료면 회색) · 제출일(있을 때만) | `created_at` · `token_expires_at` · `submitted_at`, 표기 `formatDate`(quality.md) |
| 요약 | 제품명 | **카드 수 하나로 가른다** — 카드 0개(임시저장 직후 등)면 「—」, 1개면 `data.cards[0].product.name`(비면 「—」), 2개 이상이면 「제품 N개」. 새/옛 구조는 안 본다(새 구조는 항상 카드 1개라 자연히 가운데 갈래) |
| 요약 | **견적 한 줄** | §4-1-a 도우미 |
| 요약 우측 | 발행 캠페인 번호 | `data.cards[].campaign_id` 를 `campMap`(§4-3 ⑥)에서 찾아 `campaign_no`(활성) / 「삭제됨」(보관) / 「(완전삭제)」(맵에 없음) — `osOpenDetail` 과 같은 세 갈래. **`campaign_id` 가 둘 이상이면 앞의 값 하나 + 「외 N건」**(N = `campaign_id` 개수 − 1. 앞세우는 값은 **번호로 풀린 것 중 첫째**이고, 하나도 안 풀리면 첫 `campaign_id` 를 위 세 갈래로 푼 표시(「삭제됨」 또는 「(완전삭제)」) — 그래서 「삭제됨 외 1건」도 가능하다. `campaign_id` 값(긴 식별 문자열) 자체는 어느 경우에도 화면에 내보내지 않는다. 제품명의 「제품 N개」와는 다른 형태다. 번호가 하나라도 있으면 그것을 보여야 어느 캠페인인지 짚을 수 있다). `campaign_id` 가 하나도 없으면 자리를 비운다. `campMap` 조회가 실패(`null`)했으면 이 자리에 「—」 |

**빈 상태**: 시트 0건이면 「오리엔시트 없음 — 하단 「오리엔시트 발급」으로 보냅니다」 한 줄. 조회 실패(`null`)면 「불러오지 못했습니다」(0건과 구분).
**안내줄**(§2-4) — `surveyCount` 세 갈래: `> 0` 이면 구역 아래 「지난 브랜드 서베이 신청 N건은 브랜드 서베이 화면에서 봅니다」 / `0` 이면 안 그림 / **`null`(조회 실패)이면 「서베이 신청 수를 불러오지 못했습니다」**(0건과 구분 — §2-5).

#### 4-1-a. 견적 판정 하나 + 표시 둘 (`admin-orient.js`)

**판정 함수 `osQuoteState(data)` 를 신설**해 네 갈래 중 하나를 돌려준다. `osQuoteCard`(오리엔 상세 카드)는 자기 안의 세 갈래 판정(§1-1)을 **이 함수 호출로 바꾸고**, 브랜드 상세용 `osQuoteSummaryLine(s)` 도 **같은 함수**를 부른다. 오류 사유 문구는 `osQuoteCard` 안 리터럴(1065줄 — `slots_missing`·`calc_error` 두 개의 매핑 + **그 밖의 모든 값에 쓰는 기본 문구**(현재 `price_unreadable` 문구))을 **판정 함수 옆의 상수 하나 + 기본값**으로 옮기고 두 표시가 같이 읽는다. ⚠️ **기본값을 없애면 안 된다** — 매핑 둘에 없는 사유가 오면 두 화면 모두 문구가 빈다.

| `osQuoteState` 결과 | 뜻 | 브랜드 상세 한 줄 표시 | 오리엔 상세(`osQuoteCard`) 표시 |
|---|---|---|---|
| `quote` | `data.quote` 있음 | 「견적 ₩610,500 (2차)」 — `total_krw` 를 `fmtKrw`, `revision` 이 2 이상일 때만 「(N차)」. 지난 판·번호·「견적서 열기」는 **상세에서** | 「예상 견적」 카드(현행 그대로) |
| `error` + 사유 | `data.quote_error` 있음 | 사유별 문구(공용 상수) | 사유 문구 한 줄 + 지난 판(현행 그대로) |
| `pending` | 둘 다 없고 `data.issued` 있음 | 「제출 전」 | **카드를 안 그린다**(현행 「둘 다 없음 → 안 그림」과 같음) |
| `legacy` | 둘 다 없고 `data.issued` 없음 | 「견적 없음(옛 형식)」 | **카드를 안 그린다**(위와 같음) |

즉 오리엔 상세는 `pending`·`legacy` 를 **하나로 합쳐** 지금처럼 안 그린다 — 네 갈래로 늘어난 것은 브랜드 상세 표시를 위한 것이고, 오리엔 상세의 화면 결과는 전과 같다. ⚠️ 판정도 문구도 **한 벌**이다 — `osQuoteSummaryLine` 이 `data.quote` 를 직접 들여다보기 시작하면 결정 6이 막으려던 두 벌이 그 자리에서 생긴다. ⚠️ 개발서버에서 오리엔 상세의 「예상 견적」 카드가 세 경우(견적 있음·오류·없음) 모두 전과 같은지 눈으로 본다.

### 4-3. 삭제 판정·확인 문구

- `openBrandDetailModal` 이 동시에 받는 넷을 **다섯**으로: ①브랜드 행 · ②**오리엔시트 목록**(`fetchOrientSheetsByBrand`, §4-6) · ③**서베이 신청 건수**(`countBrandApplicationsByBrand`, §4-6) · ④회사 목록 · ⑤캠페인 수. 그 뒤 **순차로 하나 더** — ⑥②의 `data.cards[].campaign_id` 를 모아 `fetchCampaignsByIds` 로 받는 **캠페인 맵 `campMap`**(시트 목록이 와야 id 를 알 수 있어 동시 조회에 못 넣는다 — `osOpenDetail` 과 같은 순서). ⑥이 실패하면 `null` 로 두고 카드의 번호 자리만 「—」(§4-1) — 삭제 판정과는 무관하다.
- 삭제 판정은 **두 단계**다. ㉠`sheets`·`surveyCount`·`campCount`(②③⑤)가 **셋 다 `null` 이 아닐 때만** 판정에 들어간다 — 하나라도 조회 실패(`null`)면 **삭제 버튼을 아예 안 그리고**, 하단 버튼 줄에 **「일부 정보를 불러오지 못해 삭제를 잠갔습니다」** 한 줄을 둔다(모르면 열지 않는다 — 탈퇴 카드의 「사전 조회 실패면 버튼 없음」과 같은 원칙. ⚠️ 셋 중 무엇이 실패했든 이 줄이 뜬다 — ②실패는 §4-1 구역 본문, ③실패는 §4-1 안내줄이 따로 말하지만 **⑤(캠페인 수) 실패는 이 줄이 유일한 안내**다). 상세 창 자체는 열린다. ㉡셋 다 유효하면 `canDeleteBrand = sheets.length === 0 && surveyCount === 0 && campCount === 0 && isAdm` — 서버 325 와 같은 셋.
- `deleteBrandConfirm()` 문구 → 「연결된 캠페인·서베이 신청·오리엔시트가 없는 빈 브랜드만 삭제됩니다. 되돌릴 수 없습니다.」

캠페인 맵은 **이미 있는** `fetchCampaignsByIds`(§1-1)를 쓴다 — 신설 3에 안 센다.

- `fetchBrandApplicationsByBrand` 는 호출부가 0이 되면 지운다(개발 판단).
- 행 단위 보안 정책은 셋 다 관리자 조회 정책이 이미 있다(`orient_sheets`·`brand_applications` SELECT `is_admin()`). 새 정책 없음.
