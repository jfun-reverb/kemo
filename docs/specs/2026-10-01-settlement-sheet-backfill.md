## 의심·경우의 수

1. 🔴 **틀린 연결이 없는 연결보다 나쁘다**(데이터) — 잘못 붙이면 실제로 안 보낸 건이 송금완료가 되어 **미지급 목록에서 사라지고 영영 못 받는다.** → 자동은 확실한 경우만(설계 ②의 A), 나머지는 사람 확인 목록
2. **보류 해제 이력이 있는 건**(데이터) — 옛 송금이 메모 글자로만 남아 자동 판정이 불가 → 사람 확인 목록. 사람이 「옛 송금」이라 지정하면 `revert_event_id` 로 연결만(상위 사양서 원칙)
3. **시트 금액 ≠ 시스템 금액**(데이터) — 시트가 실제로 보낸 돈이지만 시스템이 맞고 시트가 오기인 경우도 있었다(9/30: 시스템 맞음 7·시트 맞음 2) → 사람 확인 목록. 기록 금액은 운영팀이 정한다(보통 시트 금액 = 보낸 돈). **이미 있는** 계산값 `amount_jpy` 는 건드리지 않는다
4. **시스템에선 보류·취소인데 시트에선 보냄**(데이터) — 환수·취소 사정이 얽힌다 → 사람 확인 목록
5. **미등록인데 지금은 인증 성공 후보가 아님**(데이터) — 그 뒤 신청 반려·결과물 되돌림 등 → 사람 확인 목록(보낸 돈은 기록해야 하므로 무시하지 않는다)
6. **회원이 지금 페이팔을 지웠다**(데이터) — 기록 함수(486)는 거부하지만 돈은 이미 시트 주소로 나갔다 → 소급은 페이팔 유무로 막지 않는다. **현재 송금** 연결인 정산대기·미등록 항목의 `paypal_email` 은 **시트의 페이팔 주소**로 쓴다(옛 송금 연결은 건드리지 않는다 — 설계 ① (나))(이미 있는 정산대기 행도 덮는다 — 실제로 돈이 간 주소다. 이미 송금완료 행은 그대로)
7. **다시 돌린다**(운영) — 시트를 고쳐 다시 반영할 일이 생긴다 → 이미 반영된 건이 든 묶음은 **묶음 통째로 건너뛰고** 알린다(상위 사양서 「다시 돌려도 안전」 — 판정은 설계 ① (나))
8. **추정값이 진짜처럼 보인다**(UX) — 송금 내역·월별 합계에 추정이 섞이면 운영팀이 실제값으로 읽는다 → 「추정」 배지와 합계의 「추정 포함 N건」(설계 ③)
9. **회차 지급일 추정이 틀린 회차로 간다**(데이터) — 탭 이름과 실제 회차가 어긋난다(위 「시트」) → 탭 → 지급일 대응표를 **개발이 대조 결과와 함께 사용자에게 보이고 확인받는다**(설계 ②)
10. **개인정보 파일**(법률) — 시트·대조 결과에 이름·이메일·페이팔이 있다 → 저장소에 넣지 않는다. 작업 뒤 지울지는 사용자와 정한다(10/1 파일: `~/Downloads/레버브_현황_페이백_지출.xlsx` · `~/Downloads/settlements-204-20261001.xlsx` · `~/Downloads/payout-match-20261001/` )
11. **소급 중에 화면으로 새 송금을 기록한다**(동시성) — 같은 건을 두 쪽이 잡을 수 있다 → 소급 함수도 건을 잠그고 「이미 현재 묶음 있음」을 다시 확인한다(486 과 같은 잠금 순서 — 설계 ① (나), 완료 기준 10)

### 의도와 다르게 읽힐 수 있는 곳
- 「시트 전체」는 **시트에서 「보냄」으로 확인되는 송금 전부**다. FALSE 줄(아직 안 보냄)은 넣지 않는다
- 「추정」은 **값을 모른다는 뜻이 아니라 규칙·회차로 채웠다는 뜻**이다. 총지출 합계에는 들어간다

## 설계

### ① 데이터베이스 — 마이그레이션 2~3개(번호는 개발이 정함. (가)가 먼저)
- **(가) 칸 추가** — `settlement_transfers.sent_at_estimated boolean NOT NULL DEFAULT false`, `fee_estimated boolean NOT NULL DEFAULT false`(기존 행은 false — 화면 기록은 실제값)
- **(나) 소급 함수(새, 이름은 개발이 정함)** — 입력은 묶음 목록(486 과 비슷한 모양): 묶음마다 `sent_at` · `sent_at_estimated` · `fee_jpy` · `fee_estimated` · 항목 목록. 항목마다 `기록 금액` · `페이팔 주소`(시트 값) · `연결 방식`(기본 **현재 송금** / **옛 송금** + 지목할 보류 해제 이력 번호) · `확인 표시`(확인자·사유 — 사람 확인 건만)
  - **연결 방식이 「옛 송금」인 항목은 연결만 만든다** — 종류와 무관하게 상태·현재 묶음·`paid_at`·`paid_amount_jpy`·`paypal_email` 을 건드리지 않는다(그 송금은 보류 해제로 이미 끝난 옛 송금이다 — 상위 사양서 원칙). 아래 종류별 갱신은 **현재 송금** 항목에만
  - **항목 종류 셋을 한 묶음에 섞을 수 있다**(결정 1):
    - **이미 송금완료(현재 묶음 없음)** → 연결을 만들고 `current_transfer_id` 설정. `paid_at` 을 묶음 `sent_at` 으로, `paid_amount_jpy` 를 기록 금액으로 맞추고 옛 값은 `settlement_events`(정정 이력 `correct`)에 「[시트 소급] 송금일 7/30 → 6/15(추정)」처럼 남긴다. 상태·`paypal_email` 은 그대로
    - **정산대기** → 486 기록과 같은 갱신(송금완료·`paid_at`·`paid_amount_jpy`·현재 묶음). `paypal_email` 은 입력의 시트 주소

  - **잠금·검사**: 486 과 같이 건을 id 순으로 **잠근 뒤**(화면 기록과 동시에 돌 수 있다 — 경우의 수 11) 「먼저 전부 검사 → 하나라도 걸리면 아무것도 안 쓴다」. 한 묶음 = 한 사람(486 `bundle_mixed_influencer` 와 같다). 불변식(설계 위 「현재 상태」)은 어떤 입력에도 지킨다

  - **확인 표시가 없는 항목(= 목록 A)** 에만 거는 조건 — 하나라도 어기면 거부: 기록 금액 = 시스템 금액(이미 송금완료면 `COALESCE(paid_amount_jpy, amount_jpy)` — 🔴 `paid_amount_jpy` 는 **비어 있는 것이 정상**이다(338 — 비면 계산값과 같다는 뜻). 그 칸만 보면 실측 204건 대부분이 금액 불일치로 떨어진다(2026-10-02 대조) · 정산대기면 `amount_jpy` · 미등록이면 339 계산값) · 상태가 이미 송금완료(현재 묶음 없음)·정산대기·미등록(후보) 중 하나 · 보류 해제 이력 없음 · 연결 방식은 현재 송금

  - **다시 돌리기**(경우의 수 7): 항목이 **이미 반영됨**이면 그 항목이 든 묶음은 실패가 아니라 **통째로 건너뛰고** 목록으로 돌려준다. 「이미 반영됨」은 연결 방식별로 — 현재 송금 = 그 건에 현재 묶음이 있음 / 옛 송금 = 그 건에 같은 이력을 지목한 옛 송금 연결이 있음
  - 권한 `settlement.pay` 쓰기(486 과 같다). 인플루언서 알림 없음
- **(다) 재정의** — `correct_settlement_transfer`(베이스 **486**, 인자 그대로라 `CREATE OR REPLACE` — 권한 보존): 송금일을 넘기면 `sent_at_estimated=false`, 수수료를 넘기면 `fee_estimated=false`(같은 값을 넘겨도 「사람이 확인함」으로 지운다). 🔴 **넘기지 않은(NULL) 칸의 표시는 그대로** — 정정 창은 지금도 바뀐 칸만 보낸다(2단계 구현 결과 「인자 NULL = 안 고침」).
  - 🔴 지금 함수는 **값이 하나도 안 바뀌면 조용히 끝난다**(486 — 변경 없음 조기 반환) → 「추정 표시가 켜진 칸에 값이 들어옴」도 바뀐 것으로 센다
  - 🔴 지금 함수는 수수료가 들어오면 **같은 값이어도** `fee_manual=true` 로 만든다 → **넘긴 수수료가 지금 값과 같으면 `fee_manual` 을 건드리지 않고 `fee_estimated` 만 지운다**(결정 7). 다른 값이면 지금처럼 `fee_manual=true`(「고친 값」)
  - 조회(베이스 **487**)의 묶음 목록·월별·회차별에 두 표시와 「추정 포함 건수」를 더한다

### ② 반영 절차 (읽기 → 사용자 확인 → 쓰기)
1. **시트 다시 내려받기**(단계 0 이후 — 시트가 멈춘 판)
2. **읽기 전용 대조**(개발) → 송금 1번(묶음) 단위의 **묶음 목록 셋(A·B·C)** + 분류 뒤 정산 건 단위로 세는 **점검 목록 D**:
   - **A 자동** — 묶음의 모든 항목이 (회원, 캠페인)으로 하나씩 맞고, 설계 ① (나)의 「확인 표시 없는 항목 조건」을 전부 만족하고, **송금일이 정해진다**(아래). 합산 줄이 있으면 실제 수수료, 없으면 추정(결정 2)
   - **B 사람 확인** — 이미 반영됨·A·C 가 아닌 묶음 전부. 예: 금액 불일치 · 보류·취소 · 보류 해제 이력 · 후보 아님 · 두 탭 중복(⑤) · 짝이 둘 이상 · 묶음 안 줄 날짜가 서로 다름 · 회차 지급일이 하나로 안 정해지는 탭(두 회차에 걸친 탭 — 예: 「1.2차 누락건」) · 시트 묶음 일부가 이미 화면으로 기록됨(→ 사람이 **남은 항목만으로 묶음을 다시 짜** 넣는다. 그 묶음 메모에 「일부는 화면 기록 묶음 ○○」)
   - **C 페이팔 확인 대기** — 1차 건별에만 있는 건(결정 4)
   - **D 설명 안 되는 송금 기록** — 🔴 **묶음 분류가 아니라 분류가 끝난 뒤 시스템 쪽에서 세는 점검 목록이다.** 시스템에 **송금일이 있고(상태 무관) 현재 묶음이 없는** 건 가운데, 이번 대조의 A·B·C 묶음 어디에도 들어가지 않은 것(현재 묶음이 있는 건은 애초에 대상이 아니다. 옛 송금으로만 연결된 건도 A·B·C 묶음에 없으면 지금의 송금 기록이 설명되지 않았으므로 D 에 든다)(시트에 없음 · 합산 줄 FALSE 로만 있음 등 — 있으면 원인 확인). 10/1 실측: 「시트 어느 탭에도 없음」 0건(FALSE 합산 줄 여부는 그때 나누지 않았다 — 다시 대조할 때 센다)
   - 🔴 **분류 순서** — 시트에서 「보냄」으로 확인되는 송금 묶음(합산 TRUE 줄 · 합산 줄 없는 탭의 묶음)을 **이미 반영됨 → C → A → B** 순으로 처음 걸리는 목록 하나에만 넣는다(D 는 그 뒤 따로 센다). 여기서 「이미 반영됨」은 **묶음의 모든 항목**이 이미 반영된 경우다(설계 ① (나)의 항목 정의 — 앞서 소급이나 화면으로 이미 기록됨). 목록에서 빼고 건수만 보고한다(다시 대조할 때 B 로 떨어지지 않게). **일부 항목만 반영된 묶음은 B**(C 조건을 만족하는 묶음이면 C 가 앞선다 — 그때도 남은 항목으로 다시 짜는 것은 같다)(위 B 의 예시 — 소급 함수는 그런 묶음을 건너뛰므로 사람이 남은 항목으로 다시 짜야 한다)(묶음 목록 A·B·C 는 겹치지 않는다. 이미 반영됨이 아니면서 C 조건을 만족하면 A·B 조건과 무관하게 C. B 는 마지막에 「나머지 전부」라 빠지는 묶음이 없다)
   - 🔴 **묶음 경계** — 합산 탭 TRUE 한 줄 = 한 묶음. **합산 줄이 없는 탭**(누락건 탭·C 등)은 **같은 페이팔 주소 + 같은 탭 + 같은 지급날짜(빈칸끼리도 같은 것으로)** 의 줄들을 한 묶음(상위 사양서 원칙)
   - 🔴 **묶음 송금일 규칙**(결정 3): 묶음 안 줄들의 시트 날짜가 **하나뿐**(모두 같거나 일부만 있음)이면 그 날짜(`sent_at_estimated=false`) · **서로 다르면 B** · **하나도 없으면** 그 송금이 속한 탭의 회차 지급일(`sent_at_estimated=true`)
   - 함께 내는 것: **탭 → 회차 지급일 대응표**(경우의 수 9), 목록별 건수·금액·묶음 수
3. **사용자 확인** — 대응표와 A 목록을 승인받는다
4. **쓰기** — 최고 관리자 로그인 브라우저에서 소급 함수 호출(관리자 콘솔 도구 — `scripts/backfill-storage-thumbs.js` 선례). 🔴 운영 SQL 편집기로 부르면 권한 판정(로그인 필요)에 막힌다
5. **B·C 처리** — 운영팀이 건마다 판단해 **기록 금액·송금일·연결 방식·묶음 구성**을 정하고 **확인 표시**를 붙여 같은 함수로 넣는다(설계 ① (나)). C 는 페이팔 내역으로 보낸 것이 확인된 건만(확인 사유 「페이팔 내역 확인」). 넣지 않기로 한 건은 그대로 둔다
6. **반영 뒤 확인** — 「수수료 기록 없음」(송금일이 있고 현재 묶음이 없는 건)이 **현재 묶음이 아직 없는 B·C(넣지 않기로 한 건 포함) 가운데 시스템에 송금일이 있는 건 + D**만큼인지(A 쓰기 직후와 B·C 처리 뒤에 각각 본다). 미등록 건수가 반영한 수만큼 줄었는지

### ③ 화면 `dev/js/admin-settlements.js` (「송금 내역」)
- 묶음 줄의 송금일·수수료 옆에 「추정」 배지(결정 5). 월별·회차별 합계 줄에 「추정 포함 N건」

## 완료 기준
1. A 목록 반영 뒤 그 건들은 모두 현재 묶음이 있고, 불변식(송금일 = 묶음 송금일, 보낸 금액 = 연결 금액) 위반 0건
2. 반영된 묶음은 전부 출처 `sheet_backfill` 이고 **도입일 계산에 들어가지 않는다** — 소급만 한 상태라면 도입일이 생기지 않는다(옛 송금완료 경로가 소급 때문에 막히지 않음)
3. 수수료를 합산 탭에서 가져온 묶음은 `fee_estimated=false`, 규칙 계산(서버 헬퍼)은 true. 송금일은 설계 ② 2의 묶음 송금일 규칙대로(하나뿐 = false, 회차 지급일 = true)
4. 같은 입력으로 다시 돌리면 쓰인 행 0, 「이미 반영됨」 목록만 돌아온다
5. 확인 표시 없는 항목이 설계 ① (나)의 조건을 하나라도 어기면 그 호출은 거부되고 아무것도 안 쓴다. 확인 표시가 있는 항목은 사람이 정한 값대로 쓰이고(불변식은 지킴) 확인자·사유가 이력에 남는다
6. 「송금 내역」에서 추정 배지·「추정 포함 N건」이 보이고, 정정 창으로 송금일을 고치거나 「값이 맞음」을 체크하면 송금일 배지만, 수수료를 그렇게 하면 수수료 배지만 사라진다 「값이 맞음」 체크는 「고친 값」을 만들지 않는다(결정 7)
7. 이미 송금완료였던 건의 옛 송금일(과 바뀐 경우 옛 송금액)이 정산 이력에 남는다
8. 인플루언서에게 알림이 하나도 안 간다
9. 반영 뒤 「수수료 기록 없음」 = 현재 묶음이 아직 없는 B·C(넣지 않기로 한 건 포함) 가운데 시스템에 송금일이 있는 건 + D(A 쓰기 직후·B·C 처리 뒤 각각 — 설계 ② 6)
10. 소급 함수와 화면 기록이 같은 건을 동시에 잡으면 한쪽만 성공한다(잠금 — 경우의 수 11)

1. **서버**: 마이그레이션(설계 ①) — 사용자에게 SQL 실행을 넘길 때 파일마다 「편집기 경고」 한 줄(전역 `common-interaction.md` §3-C — 칸 추가·새 함수·`CREATE OR REPLACE` 재정의라 「안 뜸」 예상, 파일을 만든 뒤 개발이 판정) — 개발 DB 적용·시험(**완료 기준 2·4·5·7·8·10**, **1·3 은 시험 입력으로**(실제 A 목록·송금일 규칙 확인은 단계 3), **6 은 서버 부분**(정정으로 표시 하나만 지워짐) — 6 의 화면은 단계 2, 9 는 실제 대조 목록이 있어야 해 단계 3. 특히 세 종류 항목 섞인 묶음 · 다시 돌리기 — 현재·옛 송금 각각 · 확인 표시 없는 항목의 거부 · 확인 표시 있는 항목: 금액 다름·보류 건·옛 송금 연결·후보 아님 미등록 · 정정으로 표시 하나만 지우기 · 동시 잠금)
2. **화면**: 추정 배지(설계 ③) — 완료 기준 6 의 화면 부분 확인
3. **운영**: 서버 → 화면 → 설계 ② 절차(대조 → 사용자 확인 → A 쓰기 → B·C 처리) — 완료 기준 9 와 1·3 의 실제 대조 부분(A 목록 반영 결과·묶음 송금일 규칙)은 여기서 확인
4. **후속(범위 밖, 사용자 결정)**: 회차 엑셀 아래 끝(D-6 `2026-10-15`)을 넓힐지 — B·C 가 정리된 뒤에만(상위 사양서 D-6)
