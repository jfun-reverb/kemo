- **기준선**: 이 마이그레이션이 끝 바로 앞에 `baseline` 줄 → 자기 `migration` 줄 순서로 두 줄을 넣는다(자기 줄은 기준선 뒤로 친다). 메모 「이 서버에서 이 줄보다 먼저 실행된 것의 적용 여부는 이 표가 모른다. 운영의 알려진 미적용 목록은 `docs/specs/2026-10-20-migration-ledger.md` 「현재 상태」(P1 고정본)」. 같은 파일을 두 서버에 돌려 각자 기준선을 갖는다

**기록이 들어가는 세 길** (기록 범위를 정하는 곳은 여기 하나다). 「기준선 전/뒤」는 번호가 아니라 **그 서버에서의 실행 순서**다 — 시각으로 가르되, 기준선과 같은 실행 안의 줄(P1 자기 줄)은 시각이 같을 수 있으므로 일련 번호로 가른다
| 그 서버에서의 실행 | 기록 |
|---|---|
| 기준선 **전** | 표가 모른다(운영은 「현재 상태」 고정 목록이 대신 말한다) |
| 기준선 뒤 · **기록 줄 있는** 파일 | 기록 줄이 자동으로 |
| 기준선 뒤 · **기록 줄 없는** 파일(옛 번호 · 양식을 맞추기 전 판 · 기록 줄 없는 데이터·구조 패치) | **손기록** — 끝까지 성공한 것을 대상 객체 조회로 확인한 직후 한 줄(메모 「손기록」). 실패·일부만 들어간 실행은 적지 않는다. 절차는 P1 문서에 적는다 |
- 결정 10 의 「새 이름으로 손기록」도 손기록 길이다(새 이름 줄은 아직 없으므로).
- 성공한 실행 하나에 **그 파일 이름으로** 한 줄이다(결정 10 의 새 이름 손기록은 예외 — 옛 이름 줄이 남는다). 이미 받는 브랜치에 병합된 파일은 기록을 이유로 고치지 않는다(유일한 예외 — 「착수 전 알아야 할 것」 ②)
- ⚠️ 손기록을 빠뜨리면 그 실행은 표에 없다. 실행 뒤 조회(의심 2)가 받치므로 손기록을 그 조회 절차의 마지막 단계로 적고, 여러 번호를 넣는 날은 결정 11 의 대조가 잡는다

### 2. 새 마이그레이션 파일 양식 (검사 시작 번호보다 큰 파일부터)
**판정 조건** (양식을 정하는 곳은 여기 하나다 — 검사 ③·⑤는 이것을 본다): 주석을 뺀 본문이 ⓐ`BEGIN;` 으로 시작하고 ⓑ`COMMIT;` 으로 끝나며 ⓒ그 사이에 `BEGIN;`·`COMMIT;` 이 없고 ⓓ`COMMIT;` 바로 앞 문장이 자기 종류·열쇠·파일 이름의 기록 줄이며(마이그레이션은 `migration`·파일 번호, 패치는 `patch`·파일 이름) 본문 어디에도 `baseline` 줄이 없다
- 데이터·구조를 바꾸는 패치도 같은 양식(결정 5)
- 앞 번호에 기대는 재정의의 실행 전 확인은 의심 5

### 3. 병합 요청 자동 검사 (GitHub — `dev`·`main` 으로 가는 병합 요청)
검사 스크립트 하나 + GitHub 실행 파일 하나. 주석을 뺀 본문으로 판정하고 **받는 브랜치 판의 스크립트**로 돈다. 파일 글자만 본다(데이터베이스에 접속하지 않는다).

| ② | 더한 파일이 정의하는 함수·제약·트리거·뷰를, 갈라진 지점 뒤 받는 브랜치에 들어온 다른 마이그레이션도 정의했다 — `dev` 로 가는 요청에서만 | **경고**(대상 이름·상대 번호 — 의심 5·9) |

## 착수 전 알아야 할 것 (실행 정보 — 설계 본문에서 옮긴 것)
1. **검사 시작 번호 값을 정하는 때** — P2 병합 버튼을 누르기 직전 `dev` 를 다시 받아 마지막 마이그레이션 번호와 스크립트 값이 같은지 확인하고 병합한다(다르면 값을 올리고 다시)
2. **끼어든 파일** — 검사 시작 번호를 맞춘 뒤 ~ `dev` 필수 지정 전에 양식 없이 병합된, 검사 시작 번호보다 큰 파일. 다음 병합 요청에서 그 파일을 설계 2 양식으로 맞춘다(묶음 밖 문장은 안으로). 이미 병합된 파일을 고치는 유일한 예외이고, 검사 ④ 경고를 넘긴다(병합 요청 본문에 「끼어든 파일 양식 맞추기」라 적는다). 맞추기 전 판을 어느 서버에서 돌렸으면 그 실행은 「세 길」대로(기준선 뒤면 손기록). P2 가 `main` 에 들어간 뒤의 `main` 요청부터는 맞추기 전 판이 검사 ③에 막힌다. P2 를 싣고 가는 첫 요청에 같이 실리면 막히지 않고 그대로 들어가므로, **그 요청 전에** 양식을 맞춘다
3. **P1 의 미적용 목록 바로잡기 범위** — 표의 번호 + 「상태를 적은 곳이 없는 최근 번호」 + 2026-10-20 뒤 운영 기준선 직전까지 `dev` 에 들어온 번호 전부(P1 자신은 뺀다)
4. **필수 지정 때** — `dev` 는 P2 를 `dev` 에 병합한 직후 곧바로(그 사이 다른 마이그레이션 병합 금지 — 지정 전에는 실패가 표시돼도 병합이 막히지 않는다. 끼어들면 ②). `main` 은 P2 가 `main` 에 들어간 뒤(그 전에는 `main` 에 스크립트가 없다 · P2 를 싣고 가는 요청은 검사 없이 지나간다)
5. **시험 목록**(모두 `dev` 로 가는 요청 · P2 를 `dev` 에 병합한 뒤 · 시험 파일 번호는 지금 `dev` 마지막 번호보다 크게 — ⓐⓒⓘ 만 예외 · 패치는 번호 조건 없음): ⓐ`dev` 에 있는 번호를 다른 이름으로 → 차단 ⓑ양식 없는 파일 → 차단 ⓒ검사 시작 번호 이하의 빠진 번호(예: 030)로 양식 없는 파일 → 통과 ⓓ갈라진 지점 뒤 `dev` 에 들어온 파일과 같은 함수를 정의한 양식 갖춘 파일 → 경고만 ⓔ`BEGIN;` 만 주석 안에 있고 나머지는 갖춘 파일 → 차단(주석을 빼고 판정하는지) ⓕ ⓓ와 같되 권한만 바꾼 파일 → 경고 없음 ⓖ묶음이 둘인(그 밖은 양식을 갖춘) 파일 → 차단 ⓗ`COMMIT;` 뒤에 문장이 더 있는(그 밖은 양식을 갖춘) 파일 → 차단 ⓘ`dev` 에 병합된 파일 한 줄 고침 → 경고 ⓙ양식 없는 새 패치 → 경고. ⓓⓕ 는 그 함수를 정의한 최근 `dev` 파일보다 앞 커밋에서 시험 브랜치를 갈라 만든다(`dev` 에 시험 파일을 넣지 않는다)
6. **한 파일 = 한 묶음** — `supabase.md` 의 「인자 많은 함수는 별도 트랜잭션으로」가 필요하면 아직 병합 전인 파일을 둘로 나눠 각각 양식으로 쓴다
7. 문서 어긋남 하나는 이미 해소됐다 — 554·555 제약의 「현재 원본」 표기(`9e03eeb9`)

## 알려진 미해결 (사용자 확인 2026-10-20 — 이대로 두고 생기면 그때 정한다)
1. **끼어든 파일 안에 거래가 이미 둘 이상인 경우** — 하나로 감쌀 수 없다. 생기면 그 파일은 손기록으로 기록하고 검사가 그 번호만 건너뛰게 한다

3. **파일 하나만 넣는 날의 손기록 누락** — 결정 11 의 대조는 여러 번호를 넣는 날만이라, 그날 손기록을 빠뜨리면 잡는 자리가 없다
