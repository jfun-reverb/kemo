## 1. 현재 상태 (규칙 A)

### 1-1. 무슨 일이 있었나

마이그레이션 312(2026-08-07 운영)가 `influencers` 원본 표의 「관리자면 통과」 조회 정책을 지우고 가림막 뷰(`influencers_admin_view`)로 갈아타게 했다. 고칠 자리 목록을 **`.from('influencers')` 글자 검색**으로 만들었는데, 그 검색에 안 걸리는 형태가 있어 **관리자 화면 4곳이 죽었다.** ⚠️ 세 숫자가 나오는데 **단위가 다르다** — 죽은 **화면**은 4곳, 312 파일 주석이 적은 「고칠 **자리** 5곳」은 실제로 **9곳**이었다. 이 문서에서 「4곳」은 언제나 화면 수다.

| 죽은 화면 | 발견 경위 |
|---|---|
| 결과물 대리 등록 — 캠페인 검색 | **11일 뒤 사용자가 우연히 발견** |
| 관리자 예약 명단(이름 열) | 그 사고를 고친 날 고문 세션이 파고들어 발견 |
| **현장 입장 확인 화면**(예약자 이름) | 〃 — **8/28~30 행사 당일에 터질 뻔** |
| 예약자 엑셀(이름 열) | 〃 |

⚠️ **뒤 3곳은 사고를 고친 날 리뷰어가 「같은 유형 누락 없음」이라 확인하고도 넘어갔다.** 리뷰어가 **같은 글자 검색**을 반복했기 때문이다.

### 1-2. 왜 안 걸리나 (고문 세션 실측 — 개발서버 브라우저)

**실패가 조용하다.** 행 단위 보안 정책에 막히면 **오류가 아니라 빈 결과**가 온다. `error` 는 `null`, 행만 0개.

| 어디에 남나 | 결과 |
|---|---|
| 오류 로그(`client_error_logs`) | ❌ 안 남음 — 오류가 아니다 |
| 정적 코드 리뷰 | ❌ 원리적으로 못 잡음 — 코드는 멀쩡하다 |
| 화면 | 「데이터 없음」으로 정상처럼 보임 |

**세 가지 실패 형태**(전부 개발서버에서 재현됨)

| # | 형태 | 증상 |
|---|---|---|
| ① | 원본 표 직접 조회 | **0행** |
| ② | 표 이름을 **인자로 받는 헬퍼** | 호출부에 이름이 안 보여 검색에 안 걸림 |
| ③ | **조회문 안쪽 임베드 조인** | 바깥 표는 정상인데 **끼워 넣은 쪽만 `null`** ← 가장 안 보임. 목록은 뜨는데 특정 열만 빈다 |

⚠️ **SQL 편집기로는 재현 불가** — 서비스 키에는 로그인 사용자가 없어 정책 분기가 아예 안 돈다(마이그레이션 272·332 와 같은 함정). **실제 로그인한 브라우저**가 유일한 재현 수단이다.

### 1-3. 기준선 — 실물 정책 목록과 대조 (2026-08-18 · **운영 확정**)

고문 세션은 마이그레이션 파일 332개를 훑어 「진짜로 조회 허가를 좁힌 건 312 하나뿐」이라 결론지었다. ⚠️ 그러나 그 방법은 **오늘 실패한 것과 같은 계열(파일 검색)**이라, 기획 세션이 **실제 데이터베이스의 정책 목록**으로 다시 확인했다.

**실제로 돌린 조회문** (2026-08-18 · 개발서버·운영서버 양쪽에서 같은 결과)

```sql
SELECT
  tablename AS 표,
  bool_or(
    qual ILIKE '%is_admin%' OR qual ILIKE '%has_permission%'
    OR qual ILIKE '%is_campaign_admin%' OR qual ILIKE '%is_super_admin%'
  ) AS 규칙1_관리자통로,
  bool_or(
    qual IS NULL
    OR btrim(qual) = 'true'
    OR btrim(lower(qual)) IN (
         '(auth.role() = ''authenticated''::text)',
         'auth.role() = ''authenticated''::text',
         '(auth.uid() is not null)',
         'auth.uid() is not null'
       )
  ) AS 규칙2_전체공개
FROM pg_policies
WHERE schemaname = 'public' AND cmd IN ('SELECT','ALL')
GROUP BY tablename;
```

⚠️ **이 조회문을 1겹 구현에 그대로 쓰면 안 된다.** **사각지대가 있다** — `pg_policies` 를 표별로 묶으므로 **정책이 0개인 표가 아예 안 나온다**(§1-5-2 ㄷ). **구현은 §3-3 의 뼈대(`pg_class` 에서 시작)를 쓴다.** 이 조회문은 **기준선을 낸 기록**으로만 남긴다.
⚠️ **규칙 2 의 로그인 판정이 문자열을 그대로 맞추는 방식**이라 정책 문구가 조금만 달라도 못 잡는다. 운영에서 정상 4개를 정확히 걸러냈으니 지금은 맞지만, **1겹 구현에서는 `ILIKE '%auth.role()%'` 같은 느슨한 형태**로 바꾸는 편이 안전하다.

**결과: 「관리자 통로 없음」 5개.**

| 표 | 판정 | 근거 |
|---|---|---|
| `campaigns` | ✅ 정상 | 누구나 읽는 **공개 조회** |
| `event_slots` | ✅ 정상 | **로그인 전체** 조회 허용(개인정보 없음) |
| `faq_nodes` | ✅ 정상 | 로그인 전체 |
| `lookup_values` | ✅ 정상 | 공개 |
| **`influencers`** | 🔴 **312 가 좁힌 그 표** | 본인 행만 |

→ **고문의 결론이 실물 정책 목록과 일치한다.** ⚠️ 다만 **잠정**이다 — 아래 두 가지가 아직 안 닫혔다.

⚠️ **ㄱ. 어느 서버에서 돌렸는지 미확인**(§5 ①). 진짜 기준선은 운영이다.
✅ **ㄴ. (해소됨 — 2026-08-18)** 아래 조회는 「전체 공개 조항」을 보지 않았으나, **규칙 2 를 포함한 조회를 따로 돌려 정상 4개가 자동 통과함을 확인**했다(§5 ⑥). 참고로 원래 한계는 이랬다: 위 SQL 은 **관리자 함수 네 가지만** 확인하므로 정상 4개까지 함께 뱉었고, **「공개라서 정상」이라는 판정은 사람이 표에서 했다.** 즉 §3-3 판정 규칙 2(전체 공개 조항)는 **아직 실물에 한 번도 돌려본 적이 없다** → §5 ⑥.
✅ **ㄱ·ㄴ 둘 다 닫혔다**(§5 ①·⑥). 운영 실측에서도 막힌 표는 `influencers` 하나다.
⚠️ **★ 이 숫자는 전부 「운영 기준」이다. 개발서버는 다르다.** 백업 표 3개는 **운영에만 있다**(2026-06-17 복원 작업 때 만든 것). 그래서 **개발서버에서 감지 함수를 돌리면 1건**(`influencers`)**이 정상**이고, 운영에서는 4건이다. **이 차이를 모르면 「결함 재발」로 잘못 보고하게 된다**(2026-08-18 실제로 그럴 뻔했다). 개발서버에서 백업 표의 성질을 확인하려면 **시험용 표를 만들어** 본다.
⚠️ **단 이 「1개」는 「정책이 있는 표 중에서 1개」다** — 아래 ㄷ 참조.

### 1-4. 참고할 선례 — 채널 어긋남 감지 장치

가장 가까운 선례는 `detect_channel_code_drift()`(마이그레이션 277·278·319)와 그 화면(`dev/js/admin-core.js:990~1100`). **구조를 그대로 재사용할 수 있다.**

| 요소 | 선례 구현 | 이번에 재사용? |
|---|---|---|
| 서버 함수 | `SECURITY DEFINER` + `search_path=''` + `is_admin()` 가드 + `STABLE` + 표 형태 반환 | ✅ 그대로 |
| 조회 함수 | `fetchChannelDriftAlerts()`(storage.js:1684) — **실패 시 `null`, 0건은 `[]`** 로 구분 | ✅ 그대로 |
| 부팅 시 1회 조회 | `dev/admin/app.js:161` | ✅ 그대로 |
| 캐시 표시 | `_channelDriftRows` (`null`=미조회 / `[]`=없음) + `applyChannelDriftIndicators()` | ✅ 그대로 |
| 사이드바 표시 | **메뉴 아이콘 자체를 경고 모양으로 교체.** 원래 아이콘은 `dataset.baseIcon` 에 보관(접힌 사이드바 대응 + stale 방지) | ✅ 그대로 |
| 0건 처리 | **아무것도 안 그린다**(아이콘 원복 + 버튼 `display:none`) | ✅ 그대로 |
| 모달 | `DRAGGABLE_ADMIN_MODALS` 등록 — 띄워둔 채 조치 가능 | ✅ 그대로 |

**선례가 세운 원칙 4가지** (이번에도 그대로 적용)
1. **0건이면 아무것도 안 그린다** — 숫자가 늘 떠 있으면 「원래 빨간 게 있는 화면」으로 학습돼 아무도 안 본다
2. **부팅 시 1회 조회해 사이드바에 표시** — 「그 화면에 들어가야만 알 수 있으면 늦다」
3. **하드코딩 예외를 넣지 않는다** — 일반 규칙으로 정상 건이 자동 통과하게
4. **조회 실패(`null`)와 0건(`[]`)을 구분** — 어느 쪽도 0으로 그리지 않는다

### 1-5. 이 제안과 충돌 가능성이 있는 기존 동작

**⚠️ ㄱ. `influencers` 는 지금도 막혀 있고, 그것이 의도된 상태다.** 가림막 뷰로 갈아탔기 때문이다. 그대로 두면 **감지 장치가 첫날부터 경고를 띄우고** 선례 원칙 ①이 즉시 깨진다. **이 사양서의 급소.**
✅ **몇 건이 뜨는지는 확정됐다 — 1건이다.** 판정 규칙 2 가 실물에서 정상 4개를 자동 통과시킴을 확인했다(§5 ⑥).

**⚠️ ㄴ. 데이터베이스는 「그 표를 관리자 화면이 읽는가」를 모른다.** 정책 목록만으로는 「막힌 표가 있다」까지만 알 수 있고, 「그래서 어느 화면이 죽었나」는 **코드 쪽 확인**이 필요하다 — 그게 오늘 실패한 세 형태 검색이다.

**⚠️ ㄷ. 브라우저는 코드를 검색할 수 없다.** 화면 경고(선례 패턴)로는 데이터베이스 쪽만 볼 수 있다. 코드 쪽은 **다른 장치**가 필요하다.

**⚠️ ㄹ. 정책 목록 조회 권한.** `pg_policies` 는 시스템 뷰다. 화면 통로(PostgREST)로는 안 나온다 — 반드시 `SECURITY DEFINER` 함수로 감싸야 한다.

**⚠️ ㅁ. 「관리자」의 정의가 하나가 아니다.** 정책 조건에 `is_admin()`·`is_campaign_admin()`·`is_super_admin()`·`has_permission()` 넷이 쓰인다. 판정에서 넷을 다 봐야 한다.

### 1-5-2. ⚠️ 기준선 조회 자체의 사각지대 (2026-08-18 개발 세션 발견)

**⚠️ ㄷ. `pg_policies` 를 표별로 묶으면 「정책이 하나도 없는 표」는 목록에 아예 안 나온다.** 그런데 그게 **가장 심하게 막힌 상태**다.

| 상태 | 실제 | 표별 묶음 조회에서는 |
|---|---|---|
| 행 보안 켜짐 + 조회 정책 **0개** | **관리자 포함 아무도 못 읽는다** (`influencers` 보다 나쁘다 — 거긴 본인 행은 읽힌다) | **목록에 안 나옴 → 「정상」으로 읽힘** |
| 행 보안 **꺼짐** | 누구나 읽는다 | 〃 |

**이것이 이 사양서 자신의 원칙과 부딪힌다.** §3-3 이 「확인 안 됨을 통과로 그리면 안 된다 — 선례 원칙 ④(조회 실패와 0건 구분)와 같은 함정」이라고 세 번 경고하는데, **기준선 조회가 그 함정에 빠져 있었다.** 목록에 없는 표를 정상으로 읽고 있었다.

**→ 1겹 판정은 `pg_policies` 에서 시작하면 안 된다.** **`pg_class` 의 표 목록에서 시작해 정책을 왼쪽 결합**해야 「정책 0개」가 **0개로 드러난다**(§3-3 반영).

⚠️ **이 변경은 실측 결과와 무관하게 필수다.** 지금 그런 표가 0개여도, **나중에 생기면 감지 대상에서 조용히 사라진다** — 가장 나쁜 실패가 가장 조용해진다.
⚠️ **행 보안이 꺼진 표는 이 장치의 범위가 아니다**(§4). 「관리자가 못 읽는」 문제가 아니라 「아무나 읽는」 문제라 성격이 반대고 조치도 다르다. 같은 조회로 걸리면 **별건으로 보고**한다. — **2026-08-18 운영 실측 결과 0건.**

✅ **기준선 「막힌 표 = `influencers` 1개」는 그대로 유효하다** — 이 3개는 **아무도 안 읽으므로 지금 조용히 죽고 있는 화면이 없다.**

### 1-5-3. ⚠️ 기준선은 결국 **0건**이다 (2026-08-18 확정)

**감지 장치를 켜면 아무것도 안 뜬다. 그게 정상이다.**

`influencers` 를 §3-3 판정에 넣으면:

```
관리자 통로 없음 ✓ → 대체 뷰 있음 ✓ → 관리자 화면에서 원본을 읽는 자리 0곳 → ⚪ 통과
```

**전환이 이미 끝났기 때문이다** — 오늘 마지막 2곳(`storage.js` 의 예약 명단 · `event-scan.html`)을 옮기면서 완료됐다. 본인 행 조회 8곳은 §3-4 의 두 축으로 제외된다.

✅ **선례 원칙 ①(0건이면 안 그린다)이 완벽하게 지켜진다.**
⚠️ **그래서 「장치가 도는지」를 아무것도 안 뜨는 것으로는 확인할 수 없다.** 고장 난 것과 구분이 안 된다 → **일부러 깨뜨려 확인**한다(§3-3 화면 검증, 작업표 작업 5).
⚠️ **사용자에게 이 점을 먼저 알려야 한다.** 안 그러면 「만들었는데 빈 화면」으로 읽힌다. **이 장치는 지금 있는 문제를 찾는 것이 아니라 앞으로 생길 것을 잡는 것**이다.

### 1-6. 미해결 백로그

⚠️ **선례(채널 어긋남 경보)도 조회 실패를 「이상 없음」으로 뭉갠다** (2026-08-18 발견 · **이번 범위 밖**). `fetchChannelDriftAlerts()` 가 실패 시 `null` 을 돌려주는데 `refreshChannelDriftIndicators()` 가 `[]` 로 바꿔 **감지가 죽어도 아무것도 안 그린다.** 이번 장치는 §3-3 ★ 로 고쳤으나 **선례는 그대로다** — 후속으로 같이 고칠 것.

- `/서비스점검` 명령(`.claude/commands/서비스점검.md`) — 정기 점검 도구. 이번 장치를 여기에 얹을지는 §5 ④
- 오늘 제정된 규칙(`971eed08`)은 **앞으로만** 막는다 — 이 사양서가 그 짝이다

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 고문이 제시한 세 방향 — 각각 어디서 깨지나

> 고문 세션이 「제 안이지 결론이 아니다」라며 A·B·C 를 적었다. 결론으로 받지 않고 검증한다.

**A. 정적 대조** (코드가 읽는 표 목록 ↔ 정책 목록)
- 🔴 **오늘 실패한 방법과 같은 계열이다.** 코드 쪽 목록을 만드는 순간 세 형태 문제가 그대로 재현된다
- 🟡 데이터베이스 접속 없이 되지만 **파일과 실물이 어긋나면 못 잡는다**
- ✅ 다만 **방향을 뒤집으면 산다** — §3 참조

**B. 실행 중 기록** (관리자 화면 조회가 0행·임베드 `null` 이면 기록)
- 🔴 **노이즈가 압도적이다.** 진짜로 데이터가 없어 0행인 화면이 대부분이라, 선례 원칙 ①(0건이면 안 그린다)을 정면 위배한다
- 🔴 **모든 조회에 계측을 붙여야 한다** — `storage.js` 함수 수백 개. 붙이는 과정에서 빠뜨리는 자리가 또 생긴다
- 🔴 임베드 `null` 은 **정상적으로도 자주 발생**한다(연결이 없는 행)
- 🟡 유일한 장점: 「실제로 그 화면이 그 표를 읽는다」를 증명한다

**C. 연기 시험** (관리자로 로그인해 주요 화면 조회를 한 번씩 실행)
- ✅ **재현 조건(로그인 세션)을 유일하게 만족한다** — SQL 편집기로 못 하는 것을 한다
- 🔴 **「주요 화면」 목록을 사람이 유지해야 한다.** 새 화면이 생기면 누가 넣나 — 안 넣으면 그 화면은 영원히 안 걸린다(오늘 사고와 같은 구조)
- 🔴 **시험 데이터가 필요하다.** 운영에 0건인 영역(행사)은 개발서버 시험 데이터 없이는 「0행」이 정상인지 막힌 건지 못 가른다
- 🟡 `/서비스점검` 확장이 자연스럽지만 **사람이 실행해야** 한다

### 2-2. 그 밖에 깨질 수 있는 경우

**① 첫날부터 경고가 뜬다.** `influencers` 가 지금도 막혀 있어(§1-5 ㄱ) 감지 장치를 켜는 순간 **1건**이 뜬다(규칙 2 로 정상 4개는 걸러짐 — §5 ⑥ 확인 완료). **선례 원칙 ①이 첫날 깨진다.**

**② 「대체 뷰가 있으면 통과」로 만들면 오늘 사고를 못 잡는다.** `influencers` 에는 `influencers_admin_view` 가 있으니 통과시키고 싶어지지만, **오늘 사고는 뷰가 있는데도 코드가 안 갈아타서** 난 것이다. 뷰 존재는 「정상」이 아니라 「전환 대상」 신호다.

**③ 데이터: 새 표가 생길 때마다 판정이 흔들린다.** 공개 조회 표(`campaigns` 등)는 관리자 조항 없이도 정상인데, 새로 만든 표가 정책을 아직 안 붙였을 때도 같은 모양이 된다 — **「아직 안 붙였다」와 「의도적으로 공개」를 가르는 기준**이 필요하다.

**④ 권한: 이 감지 결과 자체가 민감하다.** 어느 표에 어떤 정책이 있는지는 **공격 표면 정보**다. `is_admin()` 가드로 충분한지, 최고 관리자 전용으로 할지 판단이 필요하다.

**⑤ 사용자 경험 — 「그래서 뭘 해야 하나」가 없으면 무시된다.** 채널 어긋남 선례는 모달에 **결과물 종류별 조치 방법**을 넣었다. 이번엔 「이 표가 막혔다」만 알려주면 관리자는 아무것도 못 한다 — **어느 화면이 영향받는지**까지 가야 행동으로 이어진다. 그런데 그건 데이터베이스가 모른다(§1-5 ㄴ).

**⑥ 사용자 경험 — 경고를 볼 사람이 정해져 있지 않다.** 채널 어긋남은 「결과물 관리」·「기준 데이터」라는 **담당 화면**이 있었다. 이번 건은 **어느 화면의 문제도 아니다**(전역). 사이드바 어디에 붙일지가 자명하지 않다.

**⑦ 시점: 배포 직후에 알아야 의미가 있다.** 부팅 시 조회는 「관리자가 다음에 로그인할 때」다. 마이그레이션을 적용하고 아무도 안 들어오면 며칠이 갈 수 있다.

### 2-3. 사용자 의도와 다르게 읽힐 수 있는 부분

- **「감지 장치」** — ①막힌 표를 찾는 것 ②죽은 화면을 찾는 것, 두 뜻으로 읽힌다. 데이터베이스만으로는 ①까지만 된다(§1-5 ㄴ). **이 사양서는 ①을 데이터베이스가 자동으로 잡고, ②는 기계(검사 스크립트)가 좁힌 범위에서 찾아 목록만 내놓고, 실제 조치는 사람이 하는 구조로 설계한다.**
- **「사람이 안 봐도 걸리는」** — 완전 무인이 아니라 **「사람이 찾아 나서지 않아도 눈에 띄는」**으로 해석한다. 조치는 사람이 한다(선례와 동일).

## 3. 설계 — 방향을 뒤집는다

### 3-1. 핵심 착상

고문이 지목한 급소는 「**정상 0행과 막힌 0행을 무엇으로 가르나**」였다. **0행을 볼 필요가 없다.**

```
지금까지 생각:  화면 조회 결과가 0행인가?  →  노이즈 압도적
바꾼 생각:      그 표에 관리자 통로가 있는가?  →  0행과 무관
```

§1-3 의 실측이 이 방향을 뒷받침한다 — 정상 4개가 전부 **「공개 조회라서 관리자도 읽는다」** 한 가지 이유로 설명됐다. 즉 「관리자 조항이 있거나 **전체 공개 조항이 있거나**」라는 **일반 규칙 하나로 하드코딩 예외 없이 걸러낼 수 있어 보인다.**
✅ **그리고 그 규칙을 실물에 돌려 확인했다**(2026-08-18) — 정상 4개가 전부 규칙 2 로 자동 통과했고 `influencers` 하나만 남았다(§5 ⑥). **착상이 검증됐다.**

그리고 **세 형태 검색 문제도 뒤집으면 풀린다.**

```
지금까지: 코드 전체에서 표 이름을 찾는다   →  세 형태를 다 못 찾음
뒤집으면: 찾을 표를 먼저 좁힌다             →  그 이름만 찾으면 됨
   ㉮ 적용 전 → 적용할 SQL 파일에서 뽑는다  (그 마이그레이션이 건드리는 표만)
   ㉯ 적용 후 → 1겹이 지목한 막힌 표를 받는다 (현재 잠정 1개)
```

어느 쪽이든 **대상이 몇 개로 좁혀지므로** 세 형태를 다 뒤지는 것이 부담이 아니다.
⚠️ **㉯ 의 「잠정 1개」는 §1-3 의 잠정 숫자에 기댄다**(어느 서버인지 미확인 + 판정 규칙 2 미검증). 실물 확인에서 대상이 크게 늘면 **㉯ 쪽 착상을 다시 봐야 한다** — 수십 개면 「그 이름만 찾으면 된다」가 성립하지 않는다.
⚠️ **㉮ 는 이 숫자와 무관하다** — 대상 수가 「그 마이그레이션이 건드리는 표 수」로 정해지기 때문이다(보통 1~2개).

### 3-2. 두 겹으로 만든다

**데이터베이스 쪽만으로는 완결되지 않는다**(§1-5 ㄴ·ㄷ). 두 장치가 각각 다른 것을 본다.

| 겹 | 무엇을 보나 | 언제 도나 | 놓치는 것 |
|---|---|---|---|
| **1겹 — 화면 경고** | **막힌 표가 생겼는가**(정책 목록) | 관리자 부팅 시 1회 | 「어느 화면이 죽었는지」는 모름 |
| **2겹㉮ — 적용 전 점검** | **이번 마이그레이션이 좁히는 표**를 코드가 아직 읽는가(세 형태) | **마이그레이션 적용 전** — **커밋 가드 훅이 자동 실행**(§5 ⑦ 확정) | 1겹과 무관(실물 정책은 안 봄) **+ 파일 기준이라 실물과 어긋나면 못 잡음** |
| **2겹㉯ — 적용 후 점검** | **1겹이 지목한 막힌 표**를 코드가 아직 읽는가(세 형태) | 1겹이 **「미확인」 또는 B** 를 띄운 뒤 | 파일 기준이라 실물과 어긋나면 못 잡음 |

⚠️ **㉮ 와 ㉯ 는 하는 일이 같고 입력만 다르다**(§3-4). 하지만 **역할이 다르다**:
- **㉮ 는 1겹과 독립이다.** 적용 전에는 1겹이 볼 정책이 아직 안 바뀌었으므로 메워 줄 것이 없다. **오늘 사고를 그 자리에서 막는 것**이 ㉮ 의 일이다.
- **㉯ 에서만 두 겹이 서로를 메운다** — 1겹은 실물을 보지만 코드를 모르고, ㉯ 는 코드를 보지만 파일 기준이다. **§3-3 의 B/통과 등급을 가르는 재료는 ㉯ 에서만 나온다.**

### 3-3. 1겹 — 막힌 표 감지 (화면 경고)

> **마이그레이션 2개**(①2겹㉯ 결과 기록 표 ②감지 함수) **+ 관리자 화면 신규**(사이드바 표시 · 모달) **+ 검사 스크립트 1개**(§3-4).
> ⚠️ **표가 필요한 이유** — §5 ② 가 (가)로 확정됐기 때문이다. **2겹㉯ 결과를 어딘가에 적어 둬야 1겹이 그걸 읽어 B/미확인/통과를 가른다.** (나)·(다)를 골랐다면 표가 필요 없었다.
> ⚠️ **표에 무엇을 담나** — 표 이름 · 마지막으로 점검한 시각 · **아직 읽는 자리 수** · 자리 목록(파일·줄). 「한 번도 점검 안 함」과 「점검했는데 0곳」이 **반드시 구분**돼야 한다(선례 원칙 ④). 행이 없으면 「미확인」, 있고 0곳이면 「통과」다.
> ⚠️ **쓰기 주체는 검사 스크립트**다. 사람 세션이 아니므로 **서비스 키로 쓴다** — 행 단위 보안 정책은 조회만 `is_admin()`(§5 ⑤)으로 열고 **쓰기 정책은 두지 않는다**(이 저장소의 기존 관행). 서버 함수는 선례(`detect_channel_code_drift`) 구조를 그대로 따르고, **모달 내용은 새로 쓴다**(아래).

**판정 규칙** (하드코딩 예외 없음)

한 표가 아래 **어느 것도 없으면** 「관리자가 못 읽는 표」다.
1. 조회 정책 조건에 **관리자 판정 함수**가 있다 — `is_admin` · `is_campaign_admin` · `is_super_admin` · `has_permission` **네 가지 전부 확인**(§1-5 ㅁ)
2. **전체 공개 조회 정책**이 있다 — 조건이 `true` 이거나 로그인 여부만 보는 것(→ 관리자도 당연히 읽는다)

**등급으로 나눈다** (§2-2 ①② 대응)

⚠️ **이 절(§3-3)의 등급표·모달 내용은 전부 §5 ② 에서 (가)를 고른 경우다**(2026-08-18 확정). 세 선택지가 등급 구성을 각각 다르게 만들고, **모달의 「등급」·「등급별 조치 안내」도 함께 달라진다.**

**판정은 세 가지를 순서대로 본다.**

```
후보  = 관리자 통로 없음 (관리자 조항도, 전체 공개 조항도 없음)
        ⚠️ 조회 정책이 0개인 표도 여기 들어온다 (§1-5-2 ㄷ)
  │
  ├─ 2겹㉯ 를 아직 안 돌렸나?            → 🟡 미확인 (그린다)
  ├─ 코드가 그 표를 읽는 자리가 0곳인가?  → ⚪ 통과   (안 그린다)
  └─ 읽는 자리가 있다  ┬─ 대체 뷰 있음    → 🟠 B
                      └─ 대체 뷰 없음    → 🔴 A
```

| 등급 | 조건 | 뜻 | 화면 |
|---|---|---|---|
| 🔴 **A** | 코드가 읽음 + 관리자 통로 없음 + **대체 뷰도 없음** | 읽는 자리는 있는데 통로가 아예 없다 | 빨강 경고 |
| 🟠 **B** | 코드가 읽음 + **대체 뷰 있음** | **오늘 사고와 같은 상태** — 뷰는 있는데 안 갈아탔다 | 주황 경고 |
| 🟡 **미확인** | **2겹㉯ 를 아직 안 돌림** | 아직 모른다 | 경고를 **그린다**(자리 수는 「확인 안 됨」) |
| ⚪ **통과** | **코드가 읽는 자리 0곳** | 아무도 안 읽으니 문제가 아니다 | **안 그림** |

**A 는 사유를 둘로 가른다**(등급을 늘리지 않고 모달 안내만 갈린다):
- `no_policy` — **조회 정책이 하나도 없다.** 관리자는 물론 **본인 행조차 못 읽는다**
- `no_admin_clause` — 조회 정책은 있는데 관리자 통로가 없다

⚠️ **★ 「코드가 안 읽으면 통과」가 이 판정의 핵심이다**(2026-08-18 개발 세션 실측으로 추가). 운영에 **조회 정책이 0개인 백업 표 3개**가 있는데(§1-5-2), 그것들을 A 로 올리면 **영원히 안 없어지는 빨간 경고 3개**가 생긴다 — 백업 표는 아무도 못 읽는 것이 정상이라 조치할 것이 없다. 그러면 **선례 원칙 ①을 첫날부터 어기고**, 이 장치가 막으려던 실패를 장치 자신이 재현한다.
⚠️ **이름으로 거르지 않는다**(`backup_` 접두사 제외 같은 것) — §3-3 이 이미 금지했다. 「이름은 언제든 달라진다」.
⚠️ **이 규칙은 미래에도 맞다** — 나중에 누가 그 백업 표를 읽는 코드를 만들면 **그 순간부터 읽는 자리가 생겨 경고가 켜진다.** 지금 문제가 아닌 것은 안 띄우고, 문제가 되는 순간 띄운다.

⚠️ **A 판정에도 2겹㉯ 가 필요해졌다.** 그래서 **장치를 켜기 전에 2겹㉯ 를 1회 돌려야 한다** — 안 돌리면 백업 3개까지 「미확인」으로 떠 **첫날 4건**이 된다. 돌려두면 **1건**(`influencers`)에서 시작한다. 작업표의 마지막 조각에 넣는다.

⚠️ **B 와 통과를 가르는 것은 코드 쪽 정보**라 데이터베이스 혼자서는 못 한다. 그래서 **2겹㉯ 의 결과를 1겹이 받아 쓴다**(§3-5).
⚠️ **그래서 「미확인」 등급이 반드시 필요하다.** 2겹㉯ 는 1겹이 경고를 띄운 뒤에 도는데, 1겹이 경고를 띄울지는 그 결과가 있어야 정해진다 — **첫 실행에는 결과가 없어 순환한다.** 「미확인」이 그 순환을 끊는다: **모르면 일단 그린다.**
⚠️ **「확인 안 됨」을 「통과」로 그리면 안 된다** — 선례 원칙 ④(조회 실패와 0건 구분)와 정확히 같은 함정이다. 안 돌려서 0곳인 것과 돌려서 0곳인 것은 다르다.

**1겹 조회의 뼈대** — ⚠️ **`pg_policies` 에서 시작하면 안 된다**(§1-5-2 ㄷ). **표 목록에서 시작해 정책을 왼쪽 결합**해야 정책 0개인 표가 「0개」로 드러난다.

```sql
SELECT
  c.relname          AS 표,
  c.relrowsecurity   AS 행보안_켜짐,
  count(p.policyname) FILTER (WHERE p.cmd IN ('SELECT','ALL')) AS 조회정책_개수
FROM pg_class c
JOIN pg_namespace n ON n.oid = c.relnamespace
LEFT JOIN pg_policies p
       ON p.schemaname = n.nspname AND p.tablename = c.relname
WHERE n.nspname = 'public'
  AND c.relkind = 'r'          -- 진짜 표만 (뷰·시퀀스 제외)
GROUP BY c.relname, c.relrowsecurity;
```

⚠️ **핵심은 `LEFT JOIN`** 이다. 이래야 정책이 0개인 표가 목록에 남는다.
⚠️ **`relkind = 'r'` 로 뷰를 제외하는 것도 의도다** — **가림막 뷰 자신이 감지 대상으로 잡히면 안 된다.**
여기에 규칙 1·2 의 `bool_or` 를 얹으면 1겹 판정이 된다.

⚠️ **★ 그런데 `LEFT JOIN` 만으로는 안 풀린다 — 집계에서 다시 죽는다** (2026-08-18 개발 세션이 구현 중 발견)

정책이 0개인 표는 `LEFT JOIN` 때문에 **`p.*` 가 전부 NULL 인 행이 하나 생긴다.** 그 행에서 규칙 2 의 첫 조건 `p.qual IS NULL` 이 **참**이 되어 **「전체 공개 조항 있음」으로 서고**, 후보 조건에서 **통째로 빠진다.**

**즉 「조회 정책이 하나도 없는 표」가 「누구나 읽는 정상 표」로 판정된다.** 백업 표 3개가 정확히 여기 해당한다.

```sql
-- ❌ 이렇게 쓰면 정책 0개인 표가 다시 사라진다
bool_or(p.qual IS NULL OR btrim(p.qual) = 'true' OR …)

-- ✅ 집계에서 NULL 행을 걸러야 한다
bool_or(p.qual IS NULL OR btrim(p.qual) = 'true' OR …)
  FILTER (WHERE p.tablename IS NOT NULL)
```

⚠️ **두 `bool_or`(규칙 1·규칙 2) 모두에 필요하다.**
⚠️ **이 함정의 교훈** — **시작점을 고쳤다고 끝이 아니다.** 같은 사각지대가 **한 단계 뒤에서 형태를 바꿔 재현된다.** `pg_class` 로 시작점을 옮겨 표를 살려 놓고, 집계에서 그 표를 다시 죽였다. **「살아 있는지」를 마지막 출력에서 확인해야 한다** — 중간 단계가 맞다고 끝난 것이 아니다.

**대체 뷰 판정** — 그 표를 읽는 뷰가 있고 그 뷰에 관리자 통로가 있으면 「대체 뷰 있음」. 뷰가 어느 표를 읽는지는 데이터베이스가 스스로 안다(의존 관계). **이름 규칙(`_admin_view` 접미사)으로 판정하지 않는다** — 이름은 언제든 달라진다.

**화면** — **표시 방식은** 선례 그대로(§1-4 표 — 부팅 시 1회 조회 · 사이드바 아이콘 교체 · 0건이면 숨김 · 드래그 가능 모달). 사이드바 표시 위치는 §5 ③.

⚠️ **모달에 「그래서 뭘 해야 하나」를 반드시 넣는다**(§2-2 ⑤ 대응). 「이 표가 막혔다」만 띄우면 관리자는 아무것도 못 하고 경고는 무시된다. 선례에서 재사용하는 것은 **모달의 뼈대(드래그·크기 조정)**이고, **내용은 새로 쓴다**:
- 막힌 표 이름과 **등급**(A / B / 미확인)
- **2겹㉯ 가 찾아낸 「아직 읽는 자리」 목록** — 파일 경로·줄 번호. 이게 「어느 화면이 영향받는지」에 가장 가까운 답이다(데이터베이스는 그걸 모른다 — §1-5 ㄴ)
- 등급별 조치 안내 — **A**: 「이 표를 읽을 통로가 아예 없다. 관리자 정책을 만들거나 가림막 뷰를 만들어야 한다」 / **B**: 「가림막 뷰는 있는데 아직 원본 표를 읽는 자리가 남았다. 아래 자리를 뷰로 갈아타야 한다」 / **미확인**: 「아직 코드 점검(2겹㉯)을 안 돌렸다. 스크립트를 돌려야 B 인지 통과인지 정해진다」 ⚠️ **미확인은 그리는 등급이므로 이 안내가 없으면 관리자가 그 화면에서 할 일이 없다**(§2-2 ⑤ 재발)
- - ⚠️ **★ 마지막 점검 시각을 함께 띄운다**(2026-08-18 결정). **감지 결과는 검사를 돌려야 갱신되므로**, 시각이 없으면 **한 달 전 상태를 오늘 상태로 읽는다.** **낡은 초록이 늘 빨간 것보다 나쁘다** — 빨간 건 무시라도 하지만 **초록은 안심시킨다.**
  - ⚠️ **일정 기간이 지나면 초록을 초록으로 그리지 않는다** — 「N일 넘게 확인 안 됨」은 **회색**으로. 검사를 잊은 것이 눈에 보여야 한다
  - ⚠️ 이건 **「조회 실패와 이상 없음을 구분하라」는 원칙의 시간 축 판본**이다(§1-4 원칙 ④)
⚠️ **★ 조회 자체가 실패했을 때를 「이상 없음」으로 그리면 안 된다**(2026-08-18 구현 중 발견 — 실제로 그렇게 짜여 있었다). 화면이 `null`(조회 실패)을 `[]`(막힌 표 없음)로 바꾸면 **감지가 죽어도 「정상」으로 그린다.** **이 장치가 막으려던 실패를 장치 자신이 재현하는 형태다.**
  → **세 상태를 각각 다르게 그린다**: ①0건(아무것도 안 그림) ②**조회 실패(회색 「확인 실패」)** ③실제 감지(빨강·주황·노랑). 모달에도 **「이상이 없다는 뜻이 아닙니다」**를 밝힌다.
- ⚠️ **2겹㉯ 를 아직 안 돌린 상태면 「아직 읽는 자리」 칸을 「확인 안 됨」으로 그린다.** **0곳으로 그리면 안 된다** — 선례 원칙 ④(조회 실패와 0건 구분)와 같은 함정이다

### 3-4. 2겹 — 코드 점검 (㉮ 적용 전 · ㉯ 적용 후)

> **앱 코드는 안 건드린다** — 검사 스크립트 1개 신설(`scripts/` 아래).

**입력**: **두 가지 중 하나** — 어느 쪽이든 「그 이름을 코드에서 찾는다」는 본체는 같다.

| 언제 | 입력을 어디서 얻나 | 무엇을 막나 |
|---|---|---|
| **㉮ 마이그레이션 적용 전**(주 용도 — **커밋 가드 훅으로 자동 실행, §5 ⑦**) | **적용하려는 SQL 파일**에서 뽑는다 — 조회 정책을 지우거나 좁히는 대상 표 이름 | **오늘 사고 자체.** 312 를 적용하기 전에 돌렸으면 9곳이 다 나왔다 |
| **㉯ 이미 적용된 뒤**(점검 용도) | **1겹이 돌려준 「막힌 표」 목록**(현재 잠정 1개) | 이미 좁혀진 표 중 아직 안 갈아탄 자리 |

⚠️ **㉮ 와 ㉯ 를 헷갈리면 안 된다.** 1겹은 **이미 적용된 정책**을 보므로, **아직 적용하지 않은 마이그레이션이 좁힐 표는 알려줄 수 없다.** 주 용도인 ㉮ 의 입력은 반드시 **SQL 파일**에서 나와야 한다 — 1겹에서 받으면 「적용 전에 돌린다」가 성립하지 않는다.
⚠️ **㉮ 가 §2-2 ⑦ 의 답이다 — 단 실행이 강제될 때만.** 화면 경고를 기다리지 않고 적용하기 전에 걸린다. 그런데 **㉮ 는 누가 돌려 주지 않으면 안 돈다** — 로그인은 언젠가 일어나지만 스크립트 실행은 안 하면 영영 안 돈다. 그대로 두면 「규칙을 지키면 걸린다」로 돌아가고, 그것은 이 문서가 **배경 한 줄에서 부족하다고 한 바로 그것**이다.
✅ **그래서 커밋 가드 훅으로 자동 실행하기로 확정했다**(§5 ⑦, 2026-08-18) — 마이그레이션 파일이 커밋에 잡히면 훅이 스크립트를 돌린다. **훅이 구현되는 시점에 §2-2 ⑦ 이 닫힌다.**
**하는 일**: 그 이름을 **세 형태로 각각** 찾는다

| 형태 | 찾는 법 |
|---|---|
| ① 그대로 적힌 것 | `from('이름')` |
| ② 인자·변수로 넘기는 것 | `.from(` 에 **변수가 들어가는 헬퍼**를 먼저 찾고 그 호출부를 본다 |
| ③ 조회문 안쪽 임베드 조인 | `이름:열(…)` 꼴 |

**찾는 범위** — **`dev/` 아래 모든 파일**(`.js`·`.html` 전부). 특정 파일을 열거하지 않는다.
⚠️ **파일 이름을 목록으로 적어 두면 안 된다.** 그것이 §2-1 에서 방향 C 를 탈락시킨 바로 그 결함이다 — 새 파일이 생기면 아무도 목록에 안 넣고, 그 파일은 영원히 안 걸린다. **훑는 범위를 폴더로 잡고 걸러내지 않는다.**
⚠️ 특히 **자립형 단독 화면**(현재 `event-scan.html`·`admin-setpw.html` — **예시이지 목록이 아니다**)은 공용 함수를 안 쓰고 자체 조회를 갖고 있어 **공용 함수를 고쳐도 안 따라온다**. 오늘 사고의 3번째 화면이 이 경우였다.

**⚠️ 무엇을 「읽는 자리」로 셀 것인가** (2026-08-18 개발 세션 실측으로 확정)

**그냥 세면 안 된다.** `influencers` 를 **정당하게** 원본 표로 읽는 자리가 8곳 있다 — 인플루언서가 자기 정보를 보고 고치는 자리다. 312 가 남긴 「본인 행」 정책으로 정상 동작하고, **가림막 통로로 바꾸면 오히려 깨진다**(그 통로는 관리자 조회용이라 본인 로그인에는 권한 판정이 다르게 걸린다).

이 8곳을 세면 `influencers` 가 **영원히 🟠 B** 가 된다 — 조치할 것이 없는데 경고가 안 없어진다. **백업 표 3개에서 고친 것과 정확히 같은 실패가 한 단계 뒤에서 재발한다.**

**두 축으로 가른다. 둘 다 글자 조건이 아니라 구조다.**

| 축 | 판정 | 근거 |
|---|---|---|
| **어느 앱의 파일인가** | **인플루언서 전용 파일이면 제외** | `dev/build.sh` 의 빌드 목록 |
| **읽기인가 쓰기인가** | **쓰기(`insert`·`update`·`upsert`)면 제외** | 쓰기가 막히면 **오류가 나서 조용하지 않다** |

실측으로 8곳이 정확히 갈린다 — 인플루언서 전용 5곳(`auth.js`·`js/app.js`·`notifications.js`·`mypage.js`) + 공용 파일의 쓰기 3곳(`lib/storage.js`).

**「`CLIENT_JS_FILES` 에 있으면 제외」로 짜면 안 된다.** `lib/storage.js` 는 **두 목록 모두에** 들어 있어서, 그렇게 짜면 **그 파일이 통째로 검사에서 빠진다.** 나중에 누가 거기에 관리자용 원본 표 조회를 넣어도 **영원히 안 잡힌다** — **「문제인데 안 뜨는」 방향의 실패**다. 하필 `lib/storage.js` 는 **오늘 죽은 자리 중 하나가 있던 파일**이다.

⚠️ **화이트리스트가 아니라 블랙리스트다.** 「관리자 파일만 센다」가 아니라 「인플루언서 전용 파일을 뺀다」다. `dev/event-scan.html` 은 **어느 JS 목록에도 없어**(별도 복사) 화이트리스트로 짜면 빠지는데, **오늘 죽은 자리 중 하나가 바로 거기**였다. 블랙리스트라야 목록에 없는 새 파일이 **기본으로 검사 대상**이 된다.

⚠️ **빌드 목록에 기대는 것이 방향 C 와 다른 이유** — 이건 **새로 만드는 목록이 아니라 이미 유지되는 목록**이다. 안 맞으면 빌드가 깨지므로 저절로 최신이다. 방향 C 가 탈락한 이유는 「점검용 목록을 사람이 따로 유지해야 한다」였다.

⚠️ **이름이 부분 문자열이다.** `influencers` 는 `influencers_admin_view` **안에 들어 있다.** 글자로 세면 **이미 옮긴 자리까지 「아직 읽는 자리」로 센다**(`dev/` 전체에서 `influencers` 가 85곳 잡힌다). **세 형태 각각에서 경계를 봐야 한다** — `from('influencers')` 는 맞고 `from('influencers_admin_view')` 는 아니다.

**⚠️ ★ 「같은 이름으로 다시 만드는 정책」을 어떻게 다루나** (2026-08-18 구현 중 결정)

정책을 **지웠다가 같은 이름으로 다시 만드는 것**은 대개 교체일 뿐 접근 축소가 아니다(마이그레이션 137 이 53개를 그렇게 최적화했다). 그래서 걸러내면 거짓 경보가 크게 준다.

⚠️ **그런데 진짜가 섞여 있다.** `240_settlement_influencer_visibility_lock.sql` 은 **같은 이름인데 조건이 좁아진** 진짜 축소다(`is_settlement_public()` 추가). 걸러내면 **정산을 인플루언서에게 잠근 그 변경이 통째로 사라진다.**

⚠️ **코드로는 판정할 수 없다** — 좁아졌는지 알려면 **이전 조건**을 알아야 하는데 그건 다른 파일들에 흩어져 있다. **파일 하나만 보고는 원리적으로 불가능하다.**

**→ 판정하지 말고, 사람이 확인할 수 있는 크기로 잘라서 알린다.**

| 모드 | 보는 범위 | 같은 이름 재정의가 몇 건 | 어떻게 |
|---|---|---|---|
| **㉮ 적용 전** | **마이그레이션 파일 하나** | **1~2건** | **경보로 세운다** — 「이 파일이 ◯◯ 를 같은 이름으로 다시 만든다. **조건이 좁아졌는지 확인하라**」 |
| **전체 훑기** | 저장소 전체 | **43건** | **목록에만** 남긴다. 경보로 세우지 않는다 |

⚠️ **★ 두 원칙은 부딪히지 않는다.** 「0건이면 안 그린다」(§1-4 원칙 ①)는 **조치할 게 없는데 그리는 것**을 금지한 것이다. **㉮ 의 1~2건은 조치할 게 있는 것**이라 원칙 위반이 아니다. 43건은 **한 번에 확인할 수 없는 양**이라 경보로 세우면 그때야 원칙을 어긴다.
⚠️ **240 을 이 형태로 걸면 걸린다** — 그 파일만 보면 조건이 붙은 것이 **눈에 보인다.** 기계가 못 하는 판정을 **사람이 볼 수 있는 크기로 넘기는** 것이다.

**출력**: 「대상 표 N개 × 아직 읽는 자리 M곳」 — **파일 경로와 줄 번호까지.** ㉯ 로 돌린 결과의 M 은 1겹의 등급 판정에 쓰인다(§5 ② 에서 잇는 방법을 정한다).

⚠️ **이 스크립트를 리뷰어에게 맡기지 않는다.** 리뷰어가 같은 검색을 반복하면 같은 자리를 같이 놓친다(오늘 실제로 그랬다). **기계가 세 형태를 각각 돌린다.**

### 3-5. 두 겹을 잇는 방법 — §5 ②

## 5. 결정 사항과 사용자 확인 필요 (**②③⑤⑥⑦ 확정 · ① 미확인 · ④ 후속**)

**① §1-3 의 정책 조회를 어느 서버에서 돌렸는가?** → ✅ **확인 완료(2026-08-18) — 운영 실측이 개발서버와 일치.** 막힌 표 = `influencers` 하나. 규칙 2 도 정상 4개를 하드코딩 예외 없이 자동 통과시켰다. **기준선 확정.**

**② 두 겹을 어떻게 잇는가?** → ✅ **확정: (가) 2겹㉯ 결과를 데이터베이스에 기록**(2026-08-18 사용자 결정). **등급은 A·B·미확인·통과 4개로 고정.** 결정 근거 = **오늘 사고가 「B」에 해당**하는데 (나)를 고르면 그 유형이 화면에 아예 안 뜬다.
*(아래 선택지는 확정 근거를 남기려고 자리만 유지한다.)*
- (가) **2겹㉯ 결과를 데이터베이스에 기록** — **적용 후 점검 스크립트(㉯)**가 결과를 표에 넣고, 1겹이 그걸 읽어 등급을 매긴다. 정확하지만 **기록을 갱신 안 하면 stale**. ⚠️ **㉮ 결과를 기록하면 안 된다** — 입력이 SQL 파일이라 실물 정책과 무관하다(§3-5)
- (나) **1겹은 A 등급만 판정** — 「관리자 통로도 대체 뷰도 없음」만 경고. **B 와 미확인이 함께 없어진다**(남는 것은 A 와 그 외뿐). 전환 미완은 2겹 스크립트에서만 본다. 단순하지만 **오늘 사고 유형이 화면에 안 뜬다**
- (다) **1겹이 뷰 존재 시 항상 주황** — **통과와 미확인이 함께 없어진다**(뷰가 있으면 무조건 주황이라 ㉯ 결과를 기다릴 이유가 없다). 전환이 끝나도 계속 떠서 선례 원칙 ①(0건이면 안 그린다) 위배

**③ 화면 경고를 어디에 띄우는가?** → ✅ **확정: 오류 로그 화면(`#errors`)**(2026-08-18 사용자 결정). 근거 = **「앱이 조용히 실패한 것」과 성격이 같다.** 사이드바 항목 `adminErrorsSi`(아이콘 `bug_report`)에 선례 방식으로 경고를 얹고, 페인은 `#adminPane-errors`.
*(아래 선택지는 확정 근거를 남기려고 자리만 유지한다.)* 채널 어긋남은 담당 화면(결과물·기준 데이터)이 있었지만 이번 건은 **전역**이다.
- (가) **오류 로그 화면**(`#errors`) — 성격이 가장 가깝다(「앱이 조용히 실패한 것」)
- (나) **대시보드** — 관리자가 처음 보는 화면
- (다) **전역 배너** — 어느 화면에서도 보인다. 가장 눈에 띄지만 가장 방해된다

**④ `/서비스점검` 에 연기 시험을 보조로 얹는가?** 실제 로그인 세션으로 주요 화면 조회를 한 번씩 돌려 보는 것. 방향 C 의 장점만 취하되 **주 장치가 아니라 정기 점검 항목**으로.

**⑤ 감지 결과 조회 권한을 `is_admin()` 로 할지, 최고 관리자 전용으로 할지**(§2-2 ④ — 정책 구성은 공격 표면 정보다). → ✅ **확정: `is_admin()` — 관리자 전원**(2026-08-18 사용자 결정). 근거 = **오류 로그 화면 자체가 관리자 전원**이라 기준이 일치한다.
⚠️ 대가를 알고 고른 것이다 — **정책 구성이 관리자 전원에게 보인다.** 반대로 최고 관리자 전용으로 좁히면 **경고를 보는 사람이 줄어 경고가 약해진다.**

**⑥ 판정 규칙 2(전체 공개 조항)를 포함한 조회를 실물에 한 번 돌려야 한다.** → ✅ **확인 완료(2026-08-18) — 게이트 통과.**

**⑧ 함수는 반드시 한 번 실제로 호출해 본다** → ✅ **필수 절차로 확정**(2026-08-18 구현 중 발견).

⚠️ **마이그레이션을 적용한 뒤 그 함수를 한 번 호출해 결과를 눈으로 볼 것.** 「적용됐다」로 끝내지 않는다.

**⑦ ㉮(적용 전 점검)의 실행을 무엇으로 강제하는가?** → ✅ **확정: 커밋 가드 훅**(2026-08-18 사용자 결정)

반환 칸이 늘면 서명이 달라져 `CREATE OR REPLACE` 로 못 바꾼다. `DROP` 후 재생성이 필요해 파일을 나눴다. [[feedback_function_redefine_latest_base]] 의 「파일 번호가 가장 큰 정의를 베이스로」가 여기에도 적용된다.

**ㄴ. 대체 뷰를 `information_schema.view_table_usage` 로 찾지 않았다**

그 뷰의 정의에는 **소유자 필터**(`pg_has_role`)가 박혀 있다. 이 함수는 `SECURITY DEFINER` 로 돌아 「현재 사용자」가 함수 소유자로 바뀌는데, 그 소유자가 뷰를 못 보면 **대체 뷰 판정이 조용히 실패해 `influencers` 가 B 가 아니라 A 로 뜬다** — 조치 안내가 틀린 방향을 가리킨다. 지금은 모든 마이그레이션을 같은 계정으로 적용해 우연히 문제가 없지만 **그 전제가 어디에도 강제돼 있지 않다.**

→ 같은 결과를 내되 소유자 필터가 없는 `pg_depend` + `pg_rewrite` + `pg_class` 조인으로 교체했다. **「누가 만들었나」에 안 기대는 판정**이 됐다.

**ㄷ. 검사 스크립트의 「정당한 자리」 제외 기준**

`influencers` 를 정당하게 원본 표로 읽는 자리가 8곳 있다(본인 행 조회 5 · 본인 행 쓰기 3). 이걸 세면 **읽는 자리가 0곳이 될 수 없어 주황 경고가 영원히 안 사라진다.**

글자 조건(`.eq('id', currentUser.id)`)으로 거르는 안은 **「글자로 만든 판정은 빈다」가 이 사고의 원인과 같은 계열**이라 폐기하고, **구조**로 갈랐다 — ①`CLIENT_JS_FILES` **빼기** `ADMIN_JS_FILES`(차집합)로 인플루언서 전용 파일 제외 ②쓰기 제외. ⚠️ 차집합이 아니라 「CLIENT 에 있으면 제외」로 짜면 **두 목록에 모두 있는 `lib/storage.js` 가 통째로 빠진다**(하필 죽은 자리 중 하나가 거기 있었다).

**ㄹ. 화면은 `admin-core.js` 를 안 건드렸다**

모달을 드래그 가능하게 하려면 `DRAGGABLE_ADMIN_MODALS` 에 등록해야 하는데 그 파일은 여러 기능이 몰리는 자리다. 목록을 직접 고치는 대신 `admin-errors.js` 에서 `add()` 로 얹었다(빌드 순서상 `admin-core.js` 가 먼저 읽힌다).

### ⚠️ 이 장치가 **의도적으로 안 보는 것** (2026-08-18 추가)

> **오늘 사고의 본질은 「무엇을 안 봤는지 아무도 몰랐던 것」이다**(파일 주석엔 「관리자 화면 5곳」, 실제는 9곳). 그래서 못 보는 것을 여기 적는다. 고치라는 뜻이 아니라 **모른 채 믿지 말라**는 뜻이다.

**ㄱ. 같은 이름으로 다시 만들면서 조건만 좁힌 것 — 판정하지 않고 「미검증」으로 표시한다**

```sql
DROP POLICY settlements_select_own ON public.settlements;
CREATE POLICY settlements_select_own ON public.settlements
  FOR SELECT USING (influencer_id = auth.uid() AND is_settlement_public());  -- 조건 추가
```

**파일 하나만 봐서는 좁아졌는지 알 수 없다** — 이전 조건이 다른 마이그레이션에 있기 때문이다. 그래서 **결정하지 않고 「미검증」으로 알리고, 확인 명령(`git log -p -S '정책이름'`)을 그 자리에 적는다.**

⚠️ **이걸 「교체니까 안전」으로 조용히 넘기면 안 된다.** 실제로 그렇게 만들었다가 리뷰에서 **NO-GO** 를 받았다 — 마이그레이션 240(정산 조회 잠금)과 084(익명 등록 권한 영구 제거) 두 개가 통째로 사라졌다. **거짓 경보를 줄이려다 진짜를 지운 것이다.**

⚠️ **`137` 처럼 정책을 대량 재작성한 파일은 출력이 100줄을 넘는다.** 훅이 파일당 30줄로 자르고 전체 보는 명령을 안내한다. 완화(「`USING`·`WITH CHECK` 문자열까지 같으면 조용히 통과」)는 **백로그** — 지금 막을 문제는 아니다.

**ㄴ. `ALTER POLICY` — 아예 못 잡는다**

지우고 다시 만들지 않고 **조건만 바꾸는** 형태다. 스크립트는 `DROP POLICY`·`CREATE POLICY`·`ALTER TABLE … ROW LEVEL SECURITY` 세 가지만 본다.

- **저장소 전체 실사용 0건**(2026-08-18 기준, 주석에서만 언급) — 지금은 이론상 구멍이다
- ⚠️ **누가 쓰기 시작하면 조용히 놓친다.** 접근을 좁히는 마이그레이션을 `ALTER POLICY` 로 쓰지 말 것

**ㄷ. 코드 점검(2겹)은 「지금」이 아니라 「마지막으로 돌린 때」를 말한다**

화면의 0건은 **「지금 이상 없음」이 아니라 「마지막 점검 때 이상 없었음」**이다. 검사를 한 달 안 돌리면 화면은 계속 초록인데 실제 상태는 모른다.

⚠️ **낡은 초록이 늘 빨간 것보다 나쁘다** — 빨간 건 무시라도 하지만 초록은 **안심시킨다.** 이 저장소가 반복해 당한 「조회 실패와 0건을 구분하라」의 **시간 축 판본**이다. 화면에 「마지막 점검 시각」을 띄우는 것이 다음 작업 1순위이고, 「언제 다시 도는가」는 §5 ④ 로 미정이다.

### ⚠️ 검증하지 못한 것 (다음 사람이 알아야 할 것)

**검사 스크립트의 `--record` 경로 — 미검증.**

결과를 `admin_table_access_scan` 에 직접 써 넣는 부분이다. **서비스 키가 필요해 개발 세션이 돌려보지 못했다.** 대신 같은 내용을 SQL 편집기로 넣어 **기록된 값과 화면 반응은 전부 확인**했다.

즉 「기록이 들어오면 화면이 어떻게 되는가」는 검증됐고, **「스크립트가 그 기록을 실제로 써 넣는가」만** 안 봤다. 훅(작업 4)은 ㉮ 모드만 쓰고 ㉮ 는 기록을 안 하므로 **훅 연결에는 영향이 없다.** 실패해도 감지·화면은 안 죽고 「확인 안 됨」으로 남는다.

전 갈래를 **실제 로그인 브라우저에서** 하나씩 확인했다(SQL 편집기는 서비스 키라 `is_admin()` 가드를 못 지나간다 — §1-2).

|---|---|---|
| 정책 0개인 표를 잡나 | 시험용 표(`zz_scan_probe`)를 만들어 | ✅ `A`/`no_policy` |

### 이 작업이 남긴 교훈

**결함 7건이 전부 「실제로 돌려봐서」 나왔다.** 자기 정합성 점검 5회를 거친 사양서 · 데이터베이스 전문 에이전트 · 리뷰어를 모두 통과한 뒤에 남아 있던 것들이다.

그중 **2건은 「그것을 고치려고 만든 코드」 안에서** 재현됐다 — 정책 0개 사각지대가 감지 함수 안에서, 조회 실패를 「정상」으로 그리는 문제가 화면에서. 후자는 **이 장치가 막으려던 실패를 장치 자신이 하는** 형태였고, 원인은 **선례를 옳다고 가정하고 그대로 따른 것**이었다.

가장 값진 확인은 **함수를 한 번 실제로 호출해 본 것**이다(§5 ⑧).
