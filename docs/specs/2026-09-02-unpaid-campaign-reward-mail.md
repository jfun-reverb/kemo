# 무보수 캠페인에 「보수를 지급하겠다」고 말하는 메일

**작성일:** 2026-09-02
**상태:** ✅ **설계 확정** — 사용자 결정 2건 반영(2026-09-02, §6). 구현은 개발 세션
**발견:** 2026-08-12 문구↔동작 전수조사에서 **이미 찾아 「착수」로 표시**됐고 3주간 안 됐다(메모리 `project_copy_vs_behavior_audit` 22줄). 2026-09-02 전수조사 2차가 **건수를 처음 실측**했다
**실측:** 무보수 시딩·방문형 승인 응모 **650건**(M4). 금액 없는 리뷰어형 **0건**

## 1. 무슨 일이 벌어지고 있나

제품만 주고 현금은 없는 캠페인(약관 제13조 3항)이 있다. **그것 자체는 정상**이고 회원도 알고 응모한다. 그런데 **메일만 그 사실을 모른다.**

회원이 실제로 겪는 순서:

| 시점 | 회원이 보는 것 | 맞나 |
|---|---|---|
| 응모 전 (캠페인 상세) | **「製品無償提供」**(제품 무상 제공) | ✅ 정확하다 |
| 당선 (일일 메일) | 「報酬 **-**」 | ⚠️ **「없음」인지 「미정」인지 모른다** |
| 결과물 승인 (검수 결과 메일) | **「担当者の最終確認のうえ、報酬のお支払いを進めます」**<br>(담당자 최종 확인 후 **보수 지급을 진행하겠습니다**) | 🔴 **거짓** |

🔴 **마지막이 이 사양서가 고치려는 것이다.** 지급은 **영원히 없다** — 정산 후보를 고르는 함수가 무보수 시딩·방문형을 **의도적으로 제외**하기 때문이다(마이그레이션 264, 현재 원본 318).

⚠️ **제외가 결함이 아니다.** 줄 돈이 없으니 후보에서 빼는 것이 맞다. **틀린 것은 메일뿐이다.**

### 문의가 오면 — 운영팀은 캠페인을 보면 안다

회원이 「보수 준다더니 언제 주나요」라고 물으면, **운영팀은 그 캠페인을 열어 보고 제품 제공만인 것을 확인할 수 있다**(리워드 칸이 비어 있고, 관리자 미리보기가 회원이 본 것과 같은 「製品無償提供」을 그린다).

⚠️ **정산 화면만 보면 안 보이는 것은 맞다** — 그 회원은 목록에 없고, 화면만으로는 「누락」인지 「처음부터 대상 아님」인지 안 갈린다. **다만 운영팀이 정산 화면에만 매인 것은 아니다**(2026-09-02 사용자 지적).

→ **그래서 화면을 새로 만들 일이 아니다.** 고칠 것은 **메일뿐이다.**

## 2. 현재 상태 (규칙 A — 직접 읽고 확인)

### 고칠 자리 — 검수 결과 메일 3곳

`supabase/functions/notify-deliverable-decision/index.ts` 의 `buildNextStepBlock()`:

| 줄 | 갈래 | 지금 문구 |
|---|---|---|
| 325 | 가구매(`proxy_purchase`) 영수증 승인 | 全ての提出が完了しました。担当者の最終確認のうえ、**報酬のお支払いを進めます**。 |
| 381 | 리뷰 인증샷 — 요구 채널 전부 승인 | 위와 같은 문장 |
| 430 | 게시물 — 요구 채널 전부 승인 | 投稿URLの審査が完了しました。担当者の最終確認のうえ、**報酬のお支払いを進めます**。 |

🔴 **그중 650건에 실제로 닿는 것은 430 한 곳뿐이다** — 무보수는 시딩·방문형이고 그 형식은 게시물 갈래로 온다. **325·381 은 리뷰어형 전용 경로**라 지금은 대상이 아니다.
⚠️ **그래도 세 곳을 같은 기준으로 고친다** — 한 곳만 고치면 「같은 문장이 자리마다 다른 규칙을 따르는」 상태가 되고, 이 저장소가 반복해서 데인 유형이다.

### 🔴 조회에 판정할 칸이 없다

같은 파일 585줄:

```
campaigns:campaign_id (id, title, brand, recruit_type, proxy_purchase, channel)
```

**`reward` 도 `product_price` 도 없다.** 넣지 않고 판정만 쓰면 값이 `undefined` 라 **모든 캠페인이 한쪽 갈래로 쏠린다** — 오류도 로그도 없이. 이 파일에서 가장 조용한 실패 지점이다.

### 이미 맞게 되어 있는 곳 (건드리지 않는다)

| | 확인 결과 |
|---|---|
| **캠페인 상세 화면** | `reward > 0` 아니고 `product_price > 0` 이면 **「製品無償提供」** — 정확하다 |
| **홍보 메일** | `reward > 0` 일 때만 「+ ¥N 報酬」를 덧붙인다 — **무보수에는 애초에 안 붙는다** |
| **정산 후보 함수** | 무보수 시딩·방문형을 제외한다(264 → 현재 원본 **318**) — **의도된 동작** |

### 판정 애매 — 일일 당선 메일

`notify-influencer-daily-digest/index.ts` 947줄:

```js
: (c?.reward ? `¥${c.reward.toLocaleString("en-US")}` : "-");
```

무보수면 **「報酬 -」**. 거짓 약속은 아니지만 **대시가 「없음」인지 「미정」인지 말하지 않는다.** §6 확인 1번.

⚠️ **바로 위 941줄에 개발자가 남긴 경고가 이미 있다** — 「レビュアー型に現金報酬を足して表示してはいけない — **支払われない金額の約束になる**」. **같은 위험을 알고 리뷰어형만 고쳤고 무보수 갈래는 남았다.**

### 코드가 이미 알고 있었다

`notify-deliverable-decision/index.ts` 361줄, 채널이 빈 캠페인을 막는 자리의 주석:

> 즉 "담당자 확인 후 보수를 지급합니다"는 **지켜지지 않을 약속**이 된다.

**같은 파일에서 같은 실패 유형을 이미 한 번 막았다.** 이번 건은 그 방어가 **조건 하나를 안 봐서** 빠져나간 경우다.

## 3. 의심·경우의 수 (규칙 B)

### 깨질 수 있는 것

1. 🔴 **판정 기준이 정산 함수와 어긋난다** — 「무보수」를 화면·메일이 각자 판정하면 또 갈린다. 정산 후보 함수(318)의 조건과 **글자 그대로 같아야** 한다: `recruit_type <> 'monitor' AND COALESCE(reward,0) <= 0`.
2. 🔴 **조회 실패·칸 누락 시 방향** — 이 파일은 이미 「모르면 완료를 단정하지 않는다」 관례가 있다(`missingChannels === null` 갈래). **무보수 판정도 모르면 중립 문구로 물러선다.** 「보수 지급」을 기본값으로 두면 지금 결함이 그대로 남는다.
3. **(UX) 문장을 빼기만 하면 완료감이 사라진다** — 「전부 제출됐다」 뒤에 아무 말이 없으면 **「그래서 어떻게 되는 건가」**가 남는다. 무보수 회원에게도 **끝났다는 마무리**는 필요하다.
4. **(UX) 이미 받은 650명** — 앞으로만 고치면 그 사람들의 오해는 남는다. **문의가 왔을 때 운영팀이 볼 근거**가 필요하다(§5).
5. **(데이터) 나중에 보수가 생기면** — 무보수로 시작한 캠페인에 나중에 `reward` 를 채울 수 있다. 이 메일은 **보낼 때마다 실시간 조회**라 자동으로 따라간다. 스냅샷이 아니라 문제없다.
6. **(권한·환경) 배포가 갈린다** — Edge Function 은 **git 머지와 실제 배포가 별개**다. 코드가 `main` 에 있어도 배포 안 됐으면 옛 판이 돈다.
7. **(환경) 개발서버에서 메일 발송 시험 금지**(저장소 정책) — 실제 확인은 운영에서만.

### 현재 구현과 충돌하는 지점

**충돌 없음 — 3개 영역 확인.** 캠페인 상세·홍보 메일·정산 후보 함수 모두 이미 무보수를 맞게 다루고 있고, 이 변경은 **메일 문구만** 바꾼다. 데이터베이스 변경 없음.

### 의도 모호점

- **「무보수」에 리뷰어형 제품 금액 0을 포함할 것인가** — 지금 **0건**(M5)이라 결과는 같지만, 조건을 어떻게 쓰느냐가 미래를 가른다. §6 확인 2번.
- **「보수 문장만 빼기」인가 「제품 제공임을 명시」인가** — §6 확인 1번.

## 4. 설계

### 🔴 판정은 **두 갈래다** — 하나로 합치면 새 거짓말이 생긴다

사용자가 「리뷰어형 제품 금액 0원도 넣는다」로 결정했다(§6-2). **넣되, 무보수와 같은 문구를 쓰면 안 된다.** 확인해 보니 두 상황은 **결과가 다르다**:

| | 무보수 시딩·방문형 | 리뷰어형 제품 금액 0 |
|---|---|---|
| 정산에서 | **영구 제외** — 후보 함수가 아예 뺀다(318 165줄 `reward IS NULL OR reward <= 0`) | **후보에는 든다.** 금액을 못 정해 보류될 뿐(`amount_issue`) |
| 되살아나나 | ❌ 설계대로 안 준다 | ✅ **관리자가 제품 금액을 채우면 지급된다**(「과거 미등록」 화면에 뜬다) |
| 성격 | **정상** — 약관 제13조 3항 | **데이터 미비** — 등록할 때 확인창까지 띄운다(`confirmMonitorWithoutPrice`) |
| 회원이 낸 것 | 없음 (제품만 받음) | 🔴 **자기 돈으로 샀다.** 페이백을 기다린다 |

🔴 **그래서 리뷰어형에 「참여해 주셔서 감사합니다」를 보내면 안 된다** — 그것은 「돈은 안 나갑니다」로 읽히는데, **나갈 수 있다.** 지금 결함(안 줄 것을 준다고 함)을 **정반대 방향의 같은 실수**(줄 것을 안 준다고 함)로 바꾸는 셈이다.

```
무보수     = recruit_type <> 'monitor' AND COALESCE(reward, 0) <= 0   → 「무보수」 문구
금액 미확정 = recruit_type =  'monitor' AND COALESCE(product_price, 0) <= 0 → 「모름」 문구
그 외                                                                  → 지금 그대로
```

⚠️ **첫 줄은 정산 후보 함수(318)의 제외 조건과 글자 그대로 같다.** 그쪽을 고치면 여기도 함께 본다.
⚠️ **값을 못 받았으면(칸 누락·조회 실패) 「모름」이다** — 무보수도 유보수도 아니다.
★ **사용자 결정은 그대로 지켜진다** — 리뷰어형 금액 0에 「지급하겠다」가 나가는 길은 **막힌다**. 다만 **무보수 문구가 아니라 중립 문구로** 막는다.

### 문구 (세 갈래)

| 상황 | 나가는 말 |
|---|---|
| **보수 있음** (지금 그대로) | 全ての提出が完了しました。担当者の最終確認のうえ、報酬のお支払いを進めます。 |
| **무보수** | 全ての提出が完了しました。**ご参加ありがとうございました。**<br>(모든 제출이 완료됐습니다. **참여해 주셔서 감사합니다.**) |
| **모름** | 全ての提出が完了しました。次のステップは「活動管理」でご確認ください。<br>(모든 제출이 완료됐습니다. 다음 단계는 「활동관리」에서 확인해 주세요.) |

⚠️ **무보수 문구에 「보수는 없습니다」라고 쓰지 않는다** — 회원은 응모 전에 이미 「製品無償提供」을 보고 신청했다. 다 끝난 시점에 없는 것을 다시 말하면 **주지 않는다는 통보처럼 읽힌다.**
⚠️ **세 곳(325·381·430)이 같은 함수를 부른다** — 문구를 만드는 자리를 하나로 두고 세 곳이 그것을 쓴다. 각자 쓰면 다음에 문구를 고칠 때 또 갈린다.

### 조회

585줄 캠페인 조회에 **`reward` 를 추가**한다.
⚠️ **`product_price` 도 함께** 넣는다(§6-2 결정 반영). **둘 중 하나만 넣으면 그 갈래가 통째로 죽는다.**

## 7. 구현 결과 (개발 세션이 채울 것)
