## 현재 상태 (2026-08-12 기준, 코드 직접 확인)

### 문제가 되는 문장

`supabase/functions/notify-deliverable-decision/index.ts` 안에 **똑같은 문장이 세 곳**(325·381·430행)에 있다.

> 全ての提出が完了しました。担当者の最終確認のうえ、報酬のお支払いを進めます。今しばらくお待ちください。
> — "모든 제출이 완료되었습니다. 담당자 최종 확인 후 **보수 지급을 진행합니다**. 잠시만 기다려 주세요."
>
> (430행만 앞부분이 「投稿URLの審査が完了しました。」 = "게시물 심사가 완료되었습니다.")

### 세 곳이 각각 누구에게 가나

| 행 | 언제 | 받는 사람 | 실제 지급 | 판정 |
|---|---|---|---|---|
| 325 | 영수증 승인 (가구매 캠페인) | 리뷰어형 | 구매 금액 **페이백** | 「報酬」(보수)라는 낱말이 안 맞음 |
| 381 | 리뷰 인증샷이 요구 채널 전부 승인 | 리뷰어형 | 구매 금액 **페이백** | 위와 같음 |
| 430 | 게시물이 요구 채널 전부 승인 | 시딩·방문형 | **현금 리워드가 있을 때만** | 무보수면 **지급 자체가 없음** |

### 이 함수가 캠페인에서 읽는 칸 (548~555행)

```
campaigns:campaign_id (id, title, brand, recruit_type, proxy_purchase, channel)
```

**`reward`도 `product_price`도 읽지 않는다.** 그래서 보수 유무를 판단할 근거 자체가 함수 안에 없다.

### 서버는 무보수를 어떻게 다루나

마이그레이션 264(`_settlement_cert_candidates()`)가 정산 후보에서 아래를 **완전히 제외**한다.

```sql
NOT (c.recruit_type <> 'monitor' AND (c.reward IS NULL OR c.reward <= 0))
```

즉 **시딩·방문형이면서 현금 리워드가 없거나 0 이하이면 애초에 정산 대상이 아니다.** 제품만 제공하는 정상 무보수 캠페인이며 이용약관 제13조 3항과 일치한다. 264 파일에 기록된 운영 실측은 「시딩 인증 성공 300건 중 261건이 이 경우, 정상 캠페인 34개 중 33개가 리워드 0원」이다.

### 같은 약속을 하는 다른 자리 (낱말 전파 점검 — `.claude/rules/request-validation.md`)

| 자리 | 무보수 시딩·방문형에 뭐라고 하나 | 판정 |
|---|---|---|
| **검수 결과 메일**(이 사양서 대상) | 「보수 지급을 진행합니다」 | ❌ 오지 않을 돈을 예고 |
| 인플루언서 일일 다이제스트 「당선」 안내 (`notify-influencer-daily-digest/index.ts` 828행) | 「報酬 −」(보수 −) | ⚠️ 지급을 약속하진 않지만 「−」는 미정으로도 읽힌다 |
| 캠페인 상세·카드 (`application.js` 413행·`campaign.js` 296행) | 「製品無償提供」(제품 무상 제공) | ✅ 정확 |
| 캠페인 홍보 메일 (`notify-campaign-promo-digest/index.ts` 236행) | 현금이 있을 때만 「¥N 報酬」를 붙임 | ✅ 정확 |
| 자동응답 「리워드는 언제·어떻게 받나요」(Q5-1) | 「모든 결과물이 승인되면 PayPal로 지급합니다」 — 형식 구분 없음 | ⚠️ 무보수 참가자가 보면 같은 오해 |
| 인플루언서 정산 화면 | 정산 행이 아예 안 생기므로 목록에 안 나타남 | ✅ (다만 정산 화면 자체가 지금 잠겨 있음) |

→ **고쳐야 할 곳은 1곳(검수 메일), 함께 볼 곳이 2곳**(일일 다이제스트의 「−」, 자동응답 Q5-1)이다.

### 이 제안과 충돌 가능성 있는 기존 동작

- **채널 판정은 건드리지 않는다.** 마이그레이션 331(요구 채널 전부 승인이어야 인증 성공)이 이 함수에 이미 반영돼 있다(410~443행). 이번 변경은 「완료됐다고 말할 때 지급을 함께 약속하느냐」 한 축만 바꾼다.
- **리뷰어형에 현금 리워드를 덧붙이지 않는다**는 2026-08-05 결정과 방향이 같다. 그때 캠페인 상세·관리자 미리보기·홍보 메일·일일 다이제스트 4곳을 고쳤는데, **이 메일은 금액을 붙이지 않고 「報酬」라는 낱말만 써서 그 조사에 안 걸렸다.**
- 관리자가 「과거 미등록」 화면에서 정산을 **수동으로 등록**할 수 있다(마이그레이션 233 `register_past_settlements`). 즉 리워드 0원이어도 운영 판단으로 지급할 길이 남아 있다 — 아래 §의심 1 참조.

### 미해결 백로그·관련 작업

- 상위 조사 `2026-08-12-copy-vs-behavior-audit.md`의 B(탈퇴)·D(방침 미구현)·E(당선 통지)·F·G·H는 미착수. A는 조치 제외 결정.

## 의심·경우의 수 (규칙 B)

1. **「지급이 없습니다」라고 단정하면 그것도 틀릴 수 있다.** 관리자가 「과거 미등록」 화면에서 수동으로 정산을 등록하는 길이 열려 있다. 리워드 0원 캠페인에 운영 판단으로 사례를 지급하는 경우가 실제로 있다면, 「보수는 없습니다」라고 못 박은 메일이 이번엔 반대로 틀린 말이 된다. → **「없다」를 말하지 말고 「완료됐다」만 말하는 중립 문구**가 안전하다.
2. **리워드 값이 메일 발송 시점과 정산 시점에 다를 수 있다.** 캠페인 편집으로 리워드를 나중에 넣으면, 이미 「완료」 메일을 받은 사람이 지급을 예상하지 못한다. 반대 방향(리워드를 뺌)도 가능하다. 메일은 되돌릴 수 없으므로 **발송 시점 값 기준임을 전제**로 설계한다.
3. **방문형에 리워드 0원 캠페인이 실제로 있는지 확인되지 않았다.** 264의 실측은 시딩(gifting) 숫자다. 방문형은 현장 방문 대가로 보통 현금이 있을 텐데, 만약 방문형 무보수가 0건이면 이번 변경은 시딩에만 실효가 있다. **적용 전 운영 조회 필요**(§검증).
4. ~~**리뷰어형(325·381)까지 고칠지가 별도 판단이다.**~~ → **결정됨: 함께 고친다**(아래 확정 결정 2). 「報酬」를 「ペイバック」(페이백)으로 바꾸는 것은 정확도를 올리는 일이고, 지급이 있다는 사실 자체는 원래 맞았다. 그럼에도 함께 고치는 이유는 **같은 문장을 세 곳에 두고 한 곳만 고치면 다음 사람이 「왜 여기만 다르지」로 헷갈리기** 때문이다 — 이 프로젝트에서 반복된 사고 유형이다.
5. **`reward`를 조회에 추가하지 않으면 조용히 실패한다.** 값이 `undefined`가 되어 「무보수」로 판정되고, **유보수 캠페인에까지 지급 예고가 사라진다.** 이번 변경에서 가장 위험한 실수 지점이다.
6. **판정을 `reward`만으로 하면 틀린다.** 리뷰어형은 리워드가 0이어도 페이백이 나간다. 반드시 **모집 형식과 함께** 본다 — 264와 글자 그대로 같은 기준(`recruit_type <> 'monitor' AND (reward IS NULL OR reward <= 0)`)을 쓴다. 새 기준을 만들면 이번엔 메일과 정산이 갈린다.
7. **[사용자 경험] 지금까지 지급을 기다려 온 사람에게는 나쁜 소식이다.** 이미 「지급을 진행합니다」를 받은 사람이 다음 캠페인에서 「완료되었습니다」만 받으면 대우가 나빠진 것처럼 느낀다. 문구를 **감사 인사와 함께 끝맺음**으로 써서, 빠진 것이 아니라 원래 여기까지가 끝임을 전한다.
8. **[사용자 경험] 「완료」만 말하고 끝내면 다음에 뭘 해야 할지 모른다.** 무보수 캠페인 참가자는 게시물을 계속 유지해야 하는 의무(주의사항 3개월)가 남아 있다. 끝맺음 문구에 **게시물을 지우지 말라는 한 줄**을 함께 넣는 편이 실제 운영에 맞는다.

### 사용자 의도와 다르게 읽힐 수 있는 부분

- 「무보수」는 **현금 리워드가 없다**는 뜻이지 「아무 대가가 없다」가 아니다. 제품은 무상 제공된다. 문구가 이 점을 뒤집어 전하지 않도록 주의한다.

## 설계

### 판정 (메일 함수 안)

게시물 승인으로 **요구 채널이 전부 채워진 순간**(현행 430행 자리)에만 갈림길을 둔다.

```
무보수인가 = (모집 형식이 리뷰어형이 아니다) AND (리워드가 비었거나 0 이하다)
```

264와 같은 기준이다. 나머지 경로(남은 채널이 있음·채널 미기록·조회 실패)는 **현행 그대로** 둔다 — 그쪽은 원래 지급을 약속하지 않는다.

### 문구 (일본어 + 한국어 뜻)

**(가) 시딩·방문형 · 무보수 — 새 문구**

> 全ての提出が完了しました。ご参加ありがとうございました。
> 投稿は一定期間そのまま公開しておいてください（各キャンペーンの注意事項をご確認ください）。
>
> — "모든 제출이 완료되었습니다. 참여해 주셔서 감사합니다.
> 게시물은 일정 기간 그대로 공개해 두세요(각 캠페인의 주의사항을 확인해 주세요)."

지급을 말하지 않고, 없다고도 말하지 않는다(§의심 1). 게시물 유지 의무를 한 줄 덧붙인다(§의심 8).

⚠️ 유지 기간을 **숫자로 쓰지 않는다.** 주의사항 기준 데이터는 3개월인데 죽은 문구에는 6개월이 남아 있어(상위 조사 §4-H) 숫자를 박으면 또 하나의 어긋남이 된다. 캠페인마다 다를 수 있으므로 「주의사항을 확인」으로 넘긴다.

**(나) 시딩·방문형 · 유보수 — 현행 유지**

> 投稿URLの審査が完了しました。担当者の最終確認のうえ、報酬のお支払いを進めます。今しばらくお待ちください。

**(다) 리뷰어형(325·381행) — 낱말 정정 ✅ 확정 (2026-08-12 사용자 결정: 세 곳 모두 고침)**

> 全ての提出が完了しました。担当者の最終確認のうえ、ペイバックのお支払いを進めます。今しばらくお待ちください。
>
> — "모든 제출이 완료되었습니다. 담당자 최종 확인 후 **페이백 지급**을 진행합니다. 잠시만 기다려 주세요."

「報酬」(보수) → 「ペイバック」(페이백). 리뷰어형이 받는 것은 구매 금액 환급이지 별도 보수가 아니다. 금액은 넣지 않는다(상한 계산이 또 하나의 어긋남 후보가 된다).

### 구현 시 반드시 챙길 것 (개발 세션 인계)

1. **캠페인 조회에 `reward`를 추가한다**(548~555행). 이걸 빠뜨리면 유보수 캠페인까지 지급 예고가 사라진다(§의심 5). 조회 항목 추가와 판정 코드는 **같은 커밋**에 넣는다.
2. 판정 조건은 264 원문과 **글자 그대로 같은 형태**로 쓰고, 그 사실을 주석에 남긴다(§의심 6).
3. 메일 양식 미러(`supabase/functions/notify-deliverable-decision/_templates/`)와 `docs/email-templates/`의 **주석에 남아 있는 옛 문구**(「報酬の支払をお待ちください」)도 함께 고친다. 발송에는 영향이 없지만 다음 사람이 그 주석을 근거로 삼는다. 배포 전 `scripts/sync-email-templates.sh` 실행.
4. **Edge Function 은 git 머지와 별개로 배포해야 한다.** `supabase functions deploy notify-deliverable-decision --project-ref <운영>`. 배포 시각은 `supabase functions list`로 눈 확인(메모리 `project_deadline_reminder_misfire` 교훈).

### 단계

한 단계로 끝난다(파일 1개 + 메일 양식 주석). 나누지 않는다.

## 검증

### 적용 전 — 운영 조회 (되돌릴 수 없는 발송이라 먼저 센다)

```sql
-- ① 시딩·방문형 무보수 캠페인이 실제로 몇 개인가 (형식별)
select recruit_type,
       count(*) filter (where reward is null or reward <= 0) as 무보수,
       count(*) filter (where reward > 0)                   as 유보수
from campaigns
where recruit_type <> 'monitor' and deleted_at is null
group by recruit_type;

-- ② 최근 90일간 이 메일을 받았을 가능성이 있는 승인 건 중 무보수 비중
select c.recruit_type,
       (c.reward is null or c.reward <= 0) as 무보수,
       count(*)
from deliverables d
join applications a on a.id = d.application_id
join campaigns   c on c.id = a.campaign_id
where d.kind = 'post' and d.status = 'approved'
  and d.reviewed_at >= now() - interval '90 days'
  and c.recruit_type <> 'monitor'
group by 1, 2 order by 1, 2;
```

②의 「무보수 = true」 행 수가 **이번 변경으로 문구가 바뀌는 규모**다. 0이면 이 작업의 실효가 없으니 착수 전에 판단을 다시 한다.

### 적용 후 — 눈 확인

메일 발송 테스트는 운영에서만 한다(`.claude/rules/supabase.md`). 개발서버에서는 배포까지만 하고, 운영 적용 후 **무보수 시딩 1건·유보수 시딩 1건**의 게시물을 승인해 두 문구가 갈리는지 실제 수신함에서 확인한다.
