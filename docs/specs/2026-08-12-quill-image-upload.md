### ★ 이미지를 막아 둔 원래 이유 — **base64 폭증**

`docs/FEATURE_SPEC.md:1721` 「이미지 태그는 저장 시 제거 (**base64 폭증 방지**)」.

외부 이미지가 아니라 **붙여넣기로 딸려오는 base64 덩어리가 데이터베이스 글자 칸을 수 MB로 부풀리는 것**이 우려였다. 「우리 저장소 주소만 허용」은 `data:` 를 거부하므로 **이 우려를 정확히 해소한다**.

### 이 제안과 충돌 가능성 있는 기존 동작

- **관리자 공지사항**(`admin-notices.js`)이 같은 `sanitizeRich` 를 쓴다 → 정화를 열면 공지도 열린다. **결정: 공지 편집기의 `formats` 에 `image` 를 넣지 않아 동작 변화 0**
- 선행 사양서 `2026-05-12-rich-editor-image-upload.md` — 미니 에디터 3종만 다뤘고 Quill 은 **범위 밖**이었다. §15-2 「저장소 고아 이미지 정리」가 **미해결 후속**으로 남아 있다
- 저장소 업로드 정책(마이그레이션 009)은 `admins` 전체 → 캠페인 발행 권한(`is_admin()`)과 정합. **새 권한 작업 불필요**

## 의심·경우의 수

### ① 【UX·가장 위험】 정화만 풀면 **지금보다 나빠진다**

- **지금**: `formats` 에 `image` 가 없어 붙여넣는 **순간 사라진다.** 운영자는 「안 되는구나」를 바로 안다
- **정화만 풀면**: 외부 이미지가 편집기에 **멀쩡히 보이고** 미리보기에도 나오다가, **저장한 뒤에야** 조용히 사라진다

→ 붙여넣기 단계에서 처리하는 장치가 **반드시 같이** 들어가야 한다. 없이 배포하면 회귀다.

### ② 【기술·실측】 외부 이미지 자동 가져오기는 **Notion 에서 안 된다**

관리자 화면에서 직접 시험한 결과(2026-08-12):

| 대상 | 결과 |
|---|---|
| 노션 이미지 서버(`www.notion.so`) | **차단** |
| 노션 첨부 저장소(S3) | **차단** |
| 일반 이미지 CDN | 가능 |
| 우리 저장소 | 가능 |

Notion 이 교차 출처 접근을 막아 둔 것이라 **우리 쪽에서 풀 수 없다.** 서버를 거치면 되지만 권한·악용(임의 주소 대리 요청) 방지가 따라와 작업이 몇 배가 된다.

⚠️ **화면 캡처 붙여넣기는 다르다** — 클립보드에 **파일 자체**가 담겨 오므로 그대로 업로드할 수 있다.

### ③ 【기술】 크기 조정은 이 편집기에서 저장되지 않는다

Quill 2 의 이미지 조각이 보존하는 속성은 `alt`·`height`·`width` 뿐이라, 미니 에디터가 쓰는 `data-rich-size` 는 **저장할 때마다 지워진다.** 살리려면 사용자 정의 조각 등록이 필요한데 이 프로젝트에 전례가 0건이다.

→ **결정: 가로 100% 고정.** 인플루언서 화면이 375픽셀이라 「작게」(25%)는 약 90픽셀로 거의 안 보이고, 설명은 큰 그림을 쓰는 자리다.

### ④ 【데이터】 이미 저장된 캠페인은 영향 없음

이번 변경은 허용 범위를 **넓히기만** 한다. 기존 데이터에는 `<img>` 가 하나도 없다(저장 시점에 제거돼 왔음). 되돌릴 때도 마찬가지다.

### ⑤ 【데이터】 저장소 파일은 남는다 — 지우면 안 된다

`duplicateCampaign`(`admin.js:2699~2701`)이 세 칸을 **문자열째 복사**한다. 즉 **두 캠페인이 같은 파일 하나를 가리킨다.** 참조 세기 없이 지우면 **복제본 이미지가 깨진다.**

→ **결정: 지금처럼 남긴다**(미니 에디터와 동일). 캠페인 보관 삭제(마이그레이션 325)도 캠페인 자산은 일부러 안 지운다.

### ⑥ 【보안】 공개 버킷이라는 점

`campaign-images` 는 공개 읽기 버킷이다. 캠페인 홍보 이미지라 무방하지만, **개인정보가 담긴 이미지를 올리면 주소를 아는 누구나 볼 수 있다.** 단추 안내에 그 사실을 적는다.

### ⚠️ 공지사항 예외 — 「HTML 소스」 모드는 이미지가 들어간다 (2026-08-12 확인·유지 결정)

결정 5의 「동작 변화 0」은 **평소 편집기(Quill)에만** 해당한다. 공지 편집기에는 **「HTML 소스」 토글**이 있고, 그 모드는 Quill 을 거치지 않고 `body_html = sanitizeRich(raw)` 로 **직접 저장**한다(`admin-notices.js:327·339`). 읽는 쪽도 `renderRich`(`shared.js:815`)가 `formats` 제한 없이 그대로 그린다.

→ 관리자가 그 모드에서 `<img src="https://…supabase.co/…">` 를 직접 적으면 **저장되고 표시된다.** 이번 변경 전에는 무조건 지워졌다.

**유지하기로 한 이유**(사용자 결정)
- **보안 구멍이 아니다** — 주소 화이트리스트가 그대로라 외부 이미지·`data:`(base64)는 여전히 막힌다
- 그 모드는 관리자가 **일부러 HTML 을 직접 적는 자리**라 실수로 들어갈 일이 거의 없다
- 막으려면 공지 저장·표시 **두 자리**를 더 고쳐야 하는데, 얻는 것에 비해 손대는 곳이 는다

⚠️ **다음 사람이 「공지는 이미지가 안 된다」고 잘못 알지 않도록** 여기 적어 둔다. 공지에 이미지를 정식으로 열려면 편집기 `formats` 에 `image` 를 넣고 단추를 붙이면 된다(작은 작업).

## 설계

### ★ 「한 곳만 고치면 깨지는」 짝 맞추기 — 이 사양서의 핵심

| 한 곳만 고치면 | 증상 |
|---|---|
| `sanitizeRich` 만 풀고 `formats` 를 안 고치면 | **편집기에 넣는 순간 사라진다** — 저장까지 가지도 못함 |
| `formats` 만 고치고 `sanitizeRich` 를 안 풀면 | 편집기엔 보이는데 **저장하면 사라진다** |
| 둘 다 고치고 **붙여넣기 장치를 빠뜨리면** | 외부 이미지가 **보이다가 저장할 때 조용히 사라진다**(지금보다 나쁨 — ①) |
| 둘 다 고치고 **편집기 안 이미지 CSS 를 빠뜨리면** | 인플루언서 화면은 멀쩡한데 **편집기 안에서만 상자를 뚫고 나온다**(정화 후처리는 편집기 DOM 에 안 걸림) |
| 코드만 고치고 **문서를 안 고치면** | `CLAUDE.md`·`FEATURE_SPEC.md`·Notion 세 곳이 「이미지는 저장 시 제거됩니다」라고 계속 말한다 |

**반대로 안 고쳐도 자동으로 따라오는 곳**(같은 정화 함수를 타므로): 인플루언서 캠페인 상세 3곳 · 관리자 미리보기 2곳 · 미리보기 자동 갱신 · 변경 이력(`［이미지:파일명］` 로 이미 대응).

## 검증

⚠️ 이 프로젝트에서 **편집기 상태·붙여넣기는 정적 검토로 안 잡힌다.** 개발서버 브라우저 확인이 필수다.

1. 새 캠페인 → 설명 칸 이미지 단추 → 2MB jpg → **편집기 안에 상자를 안 뚫고 보이는지** → 저장 → 다시 열기 → **그대로 있는지**
2. 소구·가이드 두 칸도 반복 (**세 칸 전부**)
3. **미리보기 네 자리를 모두** 확인 (사용자 지적)
   - ① 편집기 안 ② 폼 옆 실시간 미리보기(입력 즉시 반영되는지) ③ 목록 제목 클릭 미리보기 ④ 인플루언서 실제 화면
   - 넷이 **같은 크기·같은 위치**로 보여야 한다. 하나라도 다르면 운영자가 미리보기를 믿을 수 없다
   - **폭 375픽셀**에서 안 넘치는지
4. 화면 캡처 붙여넣기 → **자동 업로드되는지**
5. Notion 문서 붙여넣기 → **제목·목록·인용구 서식은 살고**, 이미지는 안내와 함께 빠지는지
6. 6MB 파일·gif → 각각 차단 문구
7. 이미지 넣은 캠페인 **복제** → 복제본에도 보이는지
8. **관리자 공지사항** 편집기에서 여전히 이미지가 안 들어가는지
9. 기존 캠페인(이미지 없는 것) 열고 그대로 저장 → 본문 무변경
10. 캠페인매니저 계정으로 업로드되는지

**데이터 확인(개발)**

```sql
select length(description), left(description, 200)
from campaigns where description like '%<img%';
```

→ `data:` 로 시작하는 주소가 **하나도 없어야** 한다. 길이가 수만 자면 base64 가 새어 들어간 것이다.

### 구현 중 드러난 결함 3종 (전부 브라우저·데이터로만 잡힘)

1. **이미지만 넣은 설명이 통째로 버려졌다** — `getRichValue` 가 빈 편집기를 **글자만으로** 판정하는데(`getText().trim()`) 이 편집기는 이미지를 글자로 세지 않는다. 개발 데이터베이스 실측에서 저장된 설명 길이가 **0**이었고 미리보기에도 안 떴다.
   ⚠️ **이 함수 하나가 저장·미리보기·이탈 경고 세 곳을 좌우한다** — 한 곳을 고치면 셋이 함께 낫고, 안 고치면 셋이 함께 눈이 먼다.
   ⚠️ 일본어 긴급 발행 게이트(`guidePlain`)는 태그를 지운 뒤 글자를 세므로 **느슨해지지 않는다**(리뷰 확인).
2. **편집기 안 여백 규칙이 틀린 전제 위에 있었다** — 이 편집기는 이미지를 **글자처럼** 다뤄서 연달아 넣으면 문단마다 하나씩이 아니라 **한 문단 안에 여러 개**가 들어간다(실측 `<p><img><img><img></p>`). 「문단마다 이미지 하나」를 전제한 규칙은 거의 아무것도 잡지 못했다. 같은 문단 안 이웃 이미지도 붙이도록 교체(8픽셀 → 0).
   ⚠️ 이미지 **사이에 글이 낀 경우**는 선택자로 글자를 볼 수 없어 편집기에서만 붙어 보인다. 저장 뒤 실제 화면은 글을 보고 정확히 판정한다.
3. **내려받기 메뉴가 스크롤을 안 따라갔다** — 화면 기준 좌표로 한 번만 놓아, 스크롤하면 **엉뚱한 이미지 위**에 떴다. 이미지 오른쪽 위 모서리 안쪽에 붙이고 스크롤·창 크기 변화마다 다시 계산. 이미지가 화면 밖으로 나가면 닫는다.

### 검증 중 알아 둘 것

- **브라우저 자동화를 붙여 둔 채로는 파일 선택 창이 안 뜬다.** 운영자가 이미지 단추를 눌러도 「아무 반응이 없다」로 보이고, 실제로는 선택 창이 자동화 쪽에 **12개까지 쌓여 있었다**. 사람 검증과 자동 검증을 같은 브라우저에서 겹치지 말 것
- 화면이 안 바뀌면 **브라우저 캐시부터** 의심(`Cmd+Shift+R`). 이번에도 새 규칙이 서버에는 있는데 페이지가 옛 파일을 물어 한 번 헛돌았다
