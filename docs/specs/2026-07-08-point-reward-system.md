## 현재 상태 (2026-07-08 기준)

### 기존 정산 구조 (일반화 대상)
- `settlements`(응모 1건 = 지급 원장 1행, `application_id` UNIQUE 멱등), status(pending/paid/on_hold/cancelled), `amount_jpy`, `paypal_email`, `settlement_events` 감사(ON DELETE RESTRICT), 상태 전이 RPC 4종, 낙관적 락. dev 구축 완료·**운영 미배포**(→ 지금이 구조 바꿀 적기)
- `backfill_settlements()`: 인증 성공 판정을 SQL로 재현해 정산행 생성(멱등). **이게 "포인트 적립" 트랜잭션 생성으로 바뀔 지점**
- 약관: **제13조 "전액 현금 지급"** — 포인트·유효기간·교환이 생기면 **개정 필요**
- 인플 프로필: `paypal_email`(출금 수단). 아마존 교환 시 신규 수단 필요

### 정산 개선 로드맵과의 관계
- `2026-07-08-settlement-improvements.md`의 1단계(정합성 자동화)는 이 밑그림 확정 후 리워드 원장 위에 착수. 2·3·4단계(알림·명세서·합산·통계)는 포인트 확장 가능하게 설계

## 법률·세무 리서치 요약 (외부 조사, 2026-07-08)

### 일본 자금결제법 — 포인트 3분류
1. **대가로 구매한 포인트**(선불식 지불수단) → 규제(공탁 의무: 미사용 잔액 절반 공탁, 1천만엔 초과 시 등)
2. **무상 발행 포인트**(대가성 없이 부여) → **규제 대상 아님**
3. **발행 후 6개월 내 소멸** 포인트 → 선불식 지불수단 아님(규제 제외)

### REVERB 적용 방향 (제안 — 전문가 확인 전제)
- REVERB 포인트는 인플이 산 게 아니라 **캠페인 리워드로 받는 것**(무상 발행, 2번) → 선불식 지불수단 규제 회피 여지
- ⚠️ **현금 출금(환금)이 되면 자금이동업(資金移動業) 리스크** — 팁 서비스도 이 벽 회피
- **회피 설계**: 포인트를 **"적립된 미지급 보수(未払報酬)"로 규정** → 현금 출금 = 채무 변제(빚 갚기)이지 환금이 아님, 자금이동업 아님. 아마존 교환 = 현물 지급

### 세무
- SNS 게시 대가 = **원천징수 원칙 대상 아님**(디자인·출연료 성격 섞이면 예외)
- **아마존 기프트권 지급 = 과세 대상**(현금 대신 받은 경제적 이익). 인플 본인 연 20만엔 초과 시 확정신고 의무
- 지불조서 등 회계 대응은 정산 개선 4단계

### 벤치마크 (크리에이터 리워드)
- TikTok/Snapchat Creator Rewards: 적립 → 은행/PayPal 출금(72시간 처리) 또는 기프트카드 교환. 대부분 "적립 → 출금/교환" 2갈래 구조

## 의심·경우의 수 (반대론자 검증)

1. **"포인트" 명칭·양도가 규제를 다시 부른다** — 포인트를 양도·제3자 결제·범용 사용 가능하게 하면 선불식 지불수단으로 재분류 위험. → **본인만·양도 불가·현금 또는 기프트 교환만**으로 한정
2. **유효기간·소멸의 딜레마** — 6개월 소멸을 두면 규제 회피는 확실하나, "미지급 보수를 소멸"시키는 건 인플에게 불리 + 일본 소비자보호·약관 이슈. 미지급 보수 성격이면 소멸 안 두는 게 정합적일 수 있음 → **전문가 확인 필요**
3. **현금 출금 vs 기프트 교환 세무 상이** — 현금(원천징수 원칙 없음) vs 기프트(경제적 이익 과세). 인플 안내·명세서에 구분 필요
4. **잔액 정합성(동시성)** — 적립·차감·출금·교환이 동시에 일어나면 잔액 음수·이중 출금 위험 → 트랜잭션 원장 + 잠금
5. **인증 깨짐 후 이미 출금/교환한 경우** — 적립 취소인데 이미 인출 → 음수 잔액·차기 차감·환수 정책 필요
6. **기존 정산 데이터 마이그레이션** — dev 정산 데이터를 리워드 원장으로 전환(운영 미배포라 부담은 작음)
7. **아마존 기프트 외부 연동** — 기프트권 발급 API(Amazon Incentives API 등) or 수동 코드 발급. 재고·실패·중복 처리

## 제안 / 설계 — 리워드 원장 밑그림

### A. 법적 성격 (뼈대)
- 포인트 = **"적립된 미지급 보수"** (선불식 지불수단 아님). 본인 전용·양도 불가·현금 출금 또는 기프트 교환만
- ⚠️ 세무사·변호사 최종 확인 후 확정

### B. 데이터 모델 (신규 — 번호는 개발 세션 확정)
- **`reward_ledger`(가칭)** — 트랜잭션 원장(append). 유형:
  - `earn`(적립, 인증 성공) / `reverse`(차감, 인증 깨짐) / `withdraw`(현금 출금) / `redeem`(기프트 교환) / `adjust`(수동 조정)
  - 각 행: influencer_id, 유형, 금액(±, 엔 기준), 연결(application_id/campaign_id/출금요청/교환요청), actor, memo, created_at
- **인플별 잔액** = 원장 합계(또는 잔액 캐시 컬럼 + 원장). 동시성 잠금
- **출금 요청**(`reward_withdrawals` 가칭): 인플 신청 → 관리자 PayPal 송금 → 완료. **기존 `settlements`가 이 역할로 흡수·일반화**
- **교환 요청**(`reward_redemptions` 가칭): 아마존 기프트·할인권. 외부 연동·코드 발급
- **적립 규칙**: `backfill_settlements`의 인증 성공 판정 → `earn` 트랜잭션 생성으로 전환

### C. 흐름
- 인증 성공 → `earn` 적립 (기존 backfill 대체)
- 인증 깨짐 → `reverse` 차감 (정산 개선 1단계가 여기에 올라감)
- 인플: 잔액 확인 → 현금 출금 신청(최소액?) 또는 기프트 교환
- 관리자: 출금 요청 처리(PayPal 송금 후 완료 기록) / 교환 처리

### D. 화면
- **인플 마이페이지**: 포인트 잔액·적립/사용 내역·출금 신청·기프트 교환. 기존 `renderMySettlements` 확장
- **관리자**: 리워드 원장·출금 요청 큐·교환 처리·발행/소멸/출금/교환 통계. 기존 정산 페인 확장

### E. 부수 과제
- **약관 개정**: 제13조(전액 현금 지급) → 포인트 적립·출금·교환·유효기간·소멸 정책
- **세무 안내**: 기프트 교환 과세 안내(인플)
- **아마존 연동**: 기프트권 발급 방식(API vs 수동)
