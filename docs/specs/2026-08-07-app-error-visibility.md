# 인플루언서 앱 오류가 관리자 오류 로그에 남게 하기

**작성일:** 2026-08-07
**작성·구현 세션:** 개발(worktree `feature/오류기록`)
**발단:** 「본인 응모 취소가 3개월간 죽어 있었는데 오류 로그에 흔적이 0건」 백로그 해소

---

## 요약

인플루언서 앱에서 오류가 나도 **관리자 오류 로그에 남지 않는 자리가 92곳** 있었다. 그래서 응모 취소 기능이 2026-05-12부터 약 3개월간 **모든 호출이 실패**했는데도 아무도 몰랐다. 화면 문구·동작·반환값은 **그대로 두고 기록만 얹어**, 같은 유형이 재발하면 당일에 보이게 만든다.

## 현재 상태 (2026-08-07 기준 · 규칙 A)

### 수집 경로가 둘뿐이고, 둘 다 쉽게 비껴간다

| 경로 | 위치 | 실제 적용 범위 |
|---|---|---|
| 전역 미처리 예외 | `dev/js/error-report.js:146` | **밖으로 튀어나온 예외만** |
| 처리된 오류 | `dev/js/ui.js:129` (`friendlyErrorJa` 첫 줄) | **인플루언서 앱 전체에서 호출부 9곳뿐** |

「처리된 오류 수집」이라는 이름과 달리, 실제로는 9개 자리에서만 돈다.

### 취소 사고가 두 겹을 모두 빠져나간 경로

1. `cancelApplication`(`dev/lib/storage.js`)이 `catch` 에서 **`{ok:false, error}` 를 반환** → 예외가 밖으로 안 나가 전역 수집기에 안 걸림
2. 호출부 `dev/js/mypage.js` 가 그 값을 **자체 문구 사전으로 매핑**하고 매칭 실패 시 「취소하지 못했습니다」로 덮음 → `friendlyErrorJa` 를 안 거쳐 두 번째 수집기도 안 돎

### 전수 조사 결과 — 같은 모양이 92곳

| 분류 | 개수 | 성격 |
|---|---:|---|
| 화면에 문구를 띄우면서 기록 안 함 | 33 | 사용자는 오류를 봤는데 우리는 모름 |
| 데이터 처리 계층에서 삼킴 | 33 | 빈 배열·`false`·`{ok:false}` 로 뭉갬 |
| 완전 무음 | 26 | 아무것도 안 하고 넘어감 |

### 특히 위험한 것 — 오류가 **다른 의미로 뒤집히는** 자리

| 자리 | 실제로 벌어지는 일 |
|---|---|
| `fetchCampaigns` | 조회 실패가 **데모용 가짜 캠페인 목록**으로 대체됨 |
| `checkDuplicateApplication` | 오류를 **아예 받지 않아** 중복 검사를 그냥 통과 |
| `countActiveApplications` | 실패가 `0` 으로 읽혀 **정원 미달로 오판** |
| `verifyInviteCode` | 통신 장애가 인플루언서에게 **「번호가 틀렸습니다」** 로 표시 |
| 알림 클릭(2곳) | 조회가 일시 실패해도 **그 알림을 영구 삭제** |
| `handleUnsubscribePage` | 통신 장애가 **「잘못된 링크」** 화면으로 |
| 가입·로그인의 `upsertInfluencer` | **프로필 행이 안 생겨도 무음** — 가입은 성공한 것처럼 보임 |

### 관련 데이터베이스

- `client_error_logs`(마이그레이션 165) — `UNIQUE(fingerprint, status)` 로 같은 지문은 1행에 누적
- `context` 칸이 **이미 있고 관리자 화면이 표시·검색까지 하는데**, 앱이 항상 빈 값을 보내 줄곧 비어 있었다
- `report_client_error` 의 **최신 정의는 165가 아니라 279**(인증 토큰 마스킹 규칙 추가). 재정의 시 279를 기준으로 삼아야 한다

### 이 제안과 충돌 가능성 있는 기존 동작

- **충돌 없음 — 4개 영역 확인.** ①화면 문구·반환값·동작을 바꾸지 않는다 ②`collectClientError` 의 새 3번째 인자는 선택이라 기존 호출 2곳 무영향 ③맥락이 없으면 지문 계산식이 종전과 **완전히 동일**해 기존 행과 계속 합쳐진다 ④잡음 필터 2층은 미처리 예외 전용이라 새 수집(`handled`)에 안 걸린다

## 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우

1. **잡음 폭증으로 로그가 못 쓰게 됨 (가장 큰 위험)** — 지금 미해결이 한 자릿수라 「배지에 숫자 뜨면 본다」가 성립한다. 수집을 넓히면 마감 지남·정원 초과 같은 **정상 거부**가 밀려들어 진짜 결함이 묻힌다. **다음 사고는 「신호가 없다」가 아니라 「신호가 묻힌다」가 되어 결말이 똑같다.**
   → 대응: 「정상 거부」를 값으로 구분해 **사이드바 배지에서 제외**하고, 목록 기본값을 「예상 못 한 오류만」으로 둔다.

2. **UX — 예외로 승격하면 지금보다 나빠진다** — 「삼키지 말고 던지자」로 가면 인플루언서 화면이 **아무 반응 없는 상태**가 된다(로그는 남지만 사용자는 눌렀는지도 모름). 지금이 나쁘긴 해도 안내는 뜬다.
   → 대응: **반환값 계약을 건드리지 않는다.** 기록만 얹는다.

3. **개인정보** — 데이터 처리 계층 오류에는 조건절 값이 실릴 수 있다. 일본어 이름·주소는 어떤 정규식으로도 못 가린다.
   → 대응: PostgREST 의 `details`/`hint` 는 **수집하지 않는다**(기존과 동일 — `message` 만 읽음). 맥락은 **함수 이름 고정 문자열만** 넣고, 그마저도 화면·서버 양쪽 마스킹을 거친다.

4. **관리자 앱에서는 조용히 아무 일도 안 함** — `collectClientError` 가 인플루언서 빌드에만 있어, 관리자 앱에서 헬퍼를 불러도 무음이다.
   → 대응: 헬퍼 주석에 명시. 관리자 앱 수집은 별도 작업.

5. **동시성·성능** — 오류 1건 = 서버 왕복 1회이고 `report_client_error` 에 요청 제한이 없다. 오프라인·서버 장애로 여러 조회가 동시에 실패하면 지문이 달라 디바운스를 각각 통과한다.
   → 대응: 이번 범위는 **인플루언서가 지나가는 경로만**(관리자 전용 225개 함수는 손대지 않음)이라 유입 폭이 제한된다. 요청 제한은 후속.

### 사용자 의도와 다르게 해석될 수 있는 부분

- **「오류가 남는다」의 기준이 둘** — ⓐ 행이 생긴다 ⓑ 관리자가 보고 **원인을 특정할 수 있다**. 이번 사고를 진짜로 막으려면 ⓑ 까지 필요해, **맥락(어느 기능인지)을 함께 저장**하고 목록에 노출한다.
- **「조회 실패가 0건으로 보인다」는 별개 문제** — 기록을 남기는 것과 화면이 거짓말하는 것을 고치는 건 다른 작업이라 이번 범위 밖(아래 「남은 것」).

### 데이터베이스 — 마이그레이션 1개(308)

- `client_error_logs.is_expected boolean NOT NULL DEFAULT false` 추가
- `report_client_error` 에 `p_is_expected boolean DEFAULT false` 인자 추가(10인자)
- ⚠️ **279를 기준으로 재정의**했다. 165를 기준으로 삼았다면 279가 넣은 **인증 토큰 마스킹 규칙 (f)가 통째로 사라지는 회귀**가 났다([[feedback_function_redefine_latest_base]] 규칙이 실제로 작동한 사례)

- `is_expected` 는 **최초 기록 때만 저장**하고 이후 누적에서 갱신하지 않는다(맥락이 지문에 들어가 같은 지문이면 같은 자리·같은 성격이다)

### 기록 장치 — `dev/js/error-report.js`

- `collectClientError(오류, 종류, opts)` — `opts.context`(어느 기능인지) · `opts.expected`(정상 거부인가) 선택 인자 추가
- **지문 계산에 맥락 포함** — 데이터 처리 계층이 넘기는 값은 스택이 비어 있어, 맥락이 없으면 서로 다른 기능의 같은 문구가 한 행으로 뭉친다

- 맥락도 마스킹을 거친다(실수로 값이 섞여도 개인정보가 그대로 저장되지 않게)

## 남은 것 (후속)

- **조회 실패와 「0건」 구분** — 지금은 둘 다 빈 배열이라 화면이 「없음」으로 그린다. 이 프로젝트엔 이미 선례가 있다(마감 게이트·행사 묶음 조회는 실패를 `null`, 0건을 `[]` 로 구분). 호출부 전수 점검이 필요해 분리
- **알림 클릭 시 영구 삭제** — 조회가 일시 실패해도 알림을 지운다. 이번엔 기록만 남겼고, 삭제를 막는 것은 동작 변경이라 별도 판단
- **`report_client_error` 요청 제한** — 지금은 없다. 수집을 더 넓히기 전 선행 조건
- **관리자 앱 수집** — `build.sh` 관리자 목록에 `error-report.js` 추가 + 앱 구분 + 관리자 전용 잡음 규칙
- **개인정보처리방침에 「오류 로그 수집」 명시** — 이미 수집 중인데 방침에 항목이 없다. 수집 항목 자체는 이번에 안 늘었지만 점검 시점
- **미해결 오류를 사람이 실제로 보게 하기** — 「로그에 남는 것」과 「사람이 아는 것」은 다르다. 관리자 일일 메일에 미해결 섹션 추가가 마지막 조각(사양서 `2026-06-02-client-error-reporting.md` PR 4)

### 개발서버 절차 (순서 고정)

1. **정상 흐름 먼저** — 응모 → 취소 1회 성공 → 오류 로그에 **새 행이 안 생기는지** 확인
   *(먼저 안 하면 다음 단계에서 뭐가 새 행인지 구분 못 한다)*
2. **일부러 깨뜨리기** — 개발 데이터베이스의 `cancel_application` 을 첫 줄에서 죽는 버전으로 교체
   *(호출 실패가 아니라 **함수 안에서 죽는** 형태여야 이번 사고와 같은 모양이다)*
3. **인플루언서 화면에서 실제로 취소 시도** — 빌드본(`dev.globalreverb.com`)으로. 로컬에서 파일을 직접 열면 잡음 규칙에 걸려 우리 오류가 제외된다
4. **판독 가능성까지 확인** — 행이 생기는 것만으로 부족하다. ⓐ 메시지에 원인이 보이는가 ⓑ **맥락에 `submitCancelApplication`·`cancelApplication` 이 찍히는가** ⓒ 「예상 못 한 오류만」 목록에 뜨는가 ⓓ 사이드바 배지 숫자가 오르는가
5. **복원** — 마이그레이션 306 파일을 통째로 다시 실행. 복원 후 **1번을 다시 실행**해 취소가 성공하는지 확인
6. **정상 거부는 배지에 안 잡히는지** — 사유 없이 취소 시도(`reason_required`) → 「정상 거부」 배지로 뜨고 **사이드바 숫자는 안 오르는지**
7. **하위 호환** — 마이그레이션 308 파일 하단 검증 SQL 3단계(옛 9인자 호출이 여전히 통과하는지)
