# 운영현황 브랜드 뷰·캠페인 비용 카드를 오리엔시트 기준으로

**작성일:** 2026-09-22 · **작성:** 기획 세션
**계기:** 오리엔시트를 읽는 주변 화면 2차 검토(2026-09-22)에서 발견. 사용자 지시 「준비 다 되면 개발 세션에 인계해서 진행」(2026-09-22).

## 0. 한 줄 요약

광고주 신청(브랜드 서베이)은 2026-06-30 공개 제출이 막혔고, 그 자리를 오리엔시트가 대신한다. 그런데 **운영현황 브랜드 뷰**와 **캠페인 진행현황의 비용 카드**는 아직 서베이만 본다. 그래서 오리엔시트만 쓰는 브랜드는 「진행 신청 0」으로 보이고, 오리엔시트에서 나온 캠페인은 「직접 등록 캠페인」으로 분류되며 비용이 안 보인다. 두 화면이 오리엔시트도 읽게 한다. **데이터베이스 변경은 없다.**

| 조각 | 무엇 | 운영 배포 |
|---|---|---|
| A. 운영현황 브랜드 뷰 | 카드·상세가 오리엔시트를 세고 보여 줌 | **단독 가능** — 쓰는 부품이 운영에 있다(§1-4). 단 **즉시 수정 R2 뒤**(§1-5) |
| B. 비용 카드 | 서베이 신청이 없으면 그 캠페인과 이어진 오리엔시트의 견적을 보여 줌 | **오리엔시트 개편 묶음과 함께** — 견적 부품이 운영에 없다(§1-4) |

### 1-2. 캠페인 진행현황 비용 카드 (`dev/js/admin-applications.js` — 운영과 차이 0)

- `appendCampOpsCostCard(camp)`(:976) — ①캠페인 관리자 이상 ②`camp.source_application_id` 가 있을 때만. 값은 `fetchBrandApplicationById` 로 서베이 신청의 `final_quote_krw`·`estimated_krw`·모집비 합(`campOpsCostCard`, :993).

### 1-3. 오리엔시트와 캠페인의 연결

- 캠페인 표에는 오리엔시트를 가리키는 칸이 없다. 오리엔시트 쪽 `data.cards[i].campaign_id` 에만 있다 — **「이 카드로 발행」으로 만든 캠페인과 「기존 캠페인 연결」로 이어 붙인 캠페인 둘 다**(마이그레이션 196·237). 이 문서는 둘을 함께 **「오리엔시트 연결 캠페인」**이라 부른다. ⚠️ 단 **서베이 신청에도 연결된 캠페인**(`source_application_id` 있음 — 2026-07-01 이전 발급분)은 종전대로 「광고주 신청」 쪽에 남고 비용 카드도 서베이 기준이다(§3-3 ③·§4 ①). 「오리엔시트 연결 캠페인」 절과 오리엔시트 비용 카드는 **서베이 신청에 연결되지 않은 캠페인만** 다룬다.
- 한 캠페인은 오리엔시트 카드 **하나에만** 연결된다 — 새로 발행하면 새 캠페인이 생기고, 기존 캠페인 연결은 서버가 전역 중복을 막는다(237). 그래도 둘 이상 걸리면 **`submitted_at` 이 가장 늦은 시트**(비어 있으면 뒤로 · 모두 비어 있으면 발급일 `created_at` 이 가장 늦은 시트)를 쓴다(방어 — 견적 하나를 골라야 하는 비용 카드 §4 ② 에서만 의미가 있다. 조각 A 는 「연결돼 있나」만 본다).
- 🔴 **캠페인 브랜드와 시트 브랜드가 다를 수 있다** — 운영 실측(2026-09-22) 오리엔시트에 연결된 캠페인 51건 중 8건(사용자 판단: 일부러 옮김, 사양서 `2026-09-22-campaign-brand-change-confirm.md`). 그래서 「이 브랜드의 시트만」 보고 캠페인을 가르거나 견적을 찾으면 그 8건을 놓친다. → 이 사양서는 **전체 시트에서 캠페인 id 로** 찾는다.
- 전체 시트 조회 `fetchOrientSheets()`(`dev/lib/storage.js:5397`) — 오리엔시트 화면이 이미 쓴다. 1,000행 반복 조회. 실패하면 예외를 던진다 → 부르는 쪽이 잡아 **`null`** 로 둔다(0건은 `[]`).
- 시트 목록에서 연결된 캠페인 id 를 모으는 함수 — `collectOrientCampaignIds(sheets)`(`dev/js/admin-brand.js:1144`).
- 견적은 새 구조 시트(`data.issued` 있음)만 가진다 — `data.quote`(`total_krw`·`subtotal_krw`·`vat_krw`·`slots`·`tier_name`·`revision`) 또는 `data.quote_error`. 옛 구조 시트는 없다.

### 1-5. 선행 — 즉시 수정 R2

같은 날 개발에 넘긴 즉시 수정 R2 = 「브랜드가 제출한 시트는 작성 기한이 지나도 『만료』로 보지 않는다」(`osIsExpired`). 이 사양서의 「진행」 판정(`osMatchesTab`)이 그 함수를 거친다. **R2 없이 넣으면 기한 지난 제출 시트가 「진행」에서 빠진다**(오리엔시트 화면도 같이 틀리므로 두 화면 숫자는 같지만 **둘 다 틀리다**). → R2 가 먼저다. 검증 A3-2 가 이것을 잡는다.

## 2. 의심·경우의 수 (규칙 B)

1. **(UX) 서베이를 통째로 지우면 옛 브랜드의 이력이 사라진다.** → 서베이 표시는 남기되 **있을 때만** 보인다. 기준은 화면마다 이렇게 다르다(의도한 차이):
   - **브랜드 카드:** 서버가 주는 값이 **진행 중인 신청 수**(`open_applications`)뿐이라 「진행 신청」은 그 값이 **0보다 클 때만** 보인다. 완료·반려만 남은 옛 브랜드 카드에는 안 보인다.
   - **브랜드 상세:** 서버가 신청 **전체** 목록을 주므로 「진행 신청」·「전체 신청」 칸과 「광고주 신청」 절은 **신청이 1건이라도 있으면** 보인다.
2. **(UX) 「진행 오리엔시트」가 무엇을 세는지.** → **오리엔시트 화면의 탭 판정을 그대로** 쓴다(두 화면 숫자가 어긋나지 않게):
   - **진행** = 「작성 중」 탭 + 「제출됨」 탭에 드는 시트 = `osMatchesTab(s,'draft') || osMatchesTab(s,'submitted')`
   - **전체** = 「전체」 탭 = 그 브랜드의 시트 전부(`osMatchesTab(s, '')`)
3. **(성능) 브랜드마다 조회하면 수백 번 부른다.** → 운영현황에 들어올 때 `fetchOrientSheets()` 를 **한 번** 받아 카드와 상세가 **함께 쓴다.** 카드·상세 숫자가 같은 목록에서 나오므로 서로 어긋나지 않는다.
4. **(데이터) 조회 실패** — 실패를 0건으로 그리면 「진행 오리엔시트 0」이라는 거짓말이 된다. 실패 처리는 **이 표 한 곳**에서 정한다:

   | 자리 | 실패면 | 근거 |
   |---|---|---|
   | 브랜드 카드 「진행 오리엔시트」 | 「—」 | 0 으로 그리면 거짓 |
   | 상세 KPI 두 칸 | 「—」 | 같음 |
   | 상세 「오리엔시트 (N)」 절 | 「오리엔시트를 불러오지 못했습니다」 | 같음 |
   | 상세 캠페인 분류 | 전부 「직접 등록 캠페인」 한 절 + 「(오리엔시트를 불러오지 못해 나누지 못했습니다)」 | 0 건을 그리는 게 아니라 **종전 분류로 돌아갈 뿐**이고, 그 사실을 적어 둔다. 단 **「신청에 연결」 단추는 모든 캠페인에서 숨긴다**(§3-4) — 가를 수 없으니 오리엔시트 캠페인에 단추가 붙어 번호가 다시 매겨지는 것을 막는다 |
   | 비용 카드 | 카드 없음 | 오리엔시트 캠페인에 **원래 없던 카드**라 못 그리면 종전 상태일 뿐 |
5. **(데이터) 캠페인 브랜드 ≠ 시트 브랜드**(§1-3, 운영 8건) → 캠페인 분류와 견적 찾기는 **전체 시트**에서 캠페인 id 로 한다. 🔴 **시트 목록·오리엔시트 숫자는 시트 브랜드 기준**이다(시트는 원래 브랜드가 작성한 것). 그래서 라페름 시트에서 나와 팜스테이로 옮긴 캠페인은 팜스테이 상세의 「오리엔시트 연결 캠페인」에 뜨지만, 그 시트는 **라페름의** 「오리엔시트 (N)」·숫자에 남는다 — 팜스테이 상세가 「진행 오리엔시트 0 · 오리엔시트 연결 캠페인 1」로 보일 수 있고, **의도한 결과다**.
6. **(UX) 비용 카드의 견적은 브랜드가 제출할 때 계산한 예상 견적이다** — 실제 청구와 다를 수 있다. → 카드에 「브랜드 제출 시점 예상 견적」이라 적는다.
7. **(권한) 비용 카드는 지금처럼 캠페인 관리자 이상.** 운영현황은 관리자 전원(지금과 같음).

**현재 구현과 어긋나는 지점:** §1-1·§1-2 의 모든 자리가 서베이만 본다. 서버는 안 바꾼다.

**의도 모호점:** 「직접 등록 캠페인」을 없앨지 — 어느 시트에도 연결되지 않은 캠페인이 여전히 있으므로 **나눈다**(오리엔시트 연결 / 직접 등록).

## 3. 설계 — 조각 A: 운영현황 브랜드 뷰

### 3-1. 공통 — 시트 목록 한 번

- 운영현황에 들어올 때(`loadBrandOps`)마다 `fetchOrientSheets()` 를 한 번 받아 모듈 변수에 둔다(예외를 잡아 실패면 `null`). 목록을 새로 받는 곳은 **둘뿐**이다 — ①운영현황 진입(`loadBrandOps`) ②상세로 바로 들어와 아직 안 받은 경우(아래). 이 모듈 변수는 **운영현황 전용**이고, 비용 카드(§4)는 자기 자리에서 따로 받는다.
- 브랜드 상세(`loadBrandOpsDetail`)는 이 값을 쓴다. 🔴 **「아직 안 받음」(`undefined`)일 때만** 그 자리에서 한 번 받는다(상세로 바로 들어온 경우). **`null`(실패)이면 다시 받지 않고 실패로 그린다** — 다시 받으면 카드와 상세가 서로 다른 목록을 보게 된다(§2 ③).
- 이 목록에서 ①브랜드별 시트(`brand_id` 로 거름) ②연결된 캠페인 id 전체(`collectOrientCampaignIds(전체 시트)`)를 만든다.

### 3-2. 브랜드 카드

숫자 줄(:202):
- **「진행 오리엔시트 N」** — §2 ② 진행 판정. 실패면 「—」.
- 「진행 신청 N」 — `open_applications > 0` 일 때만(§2 ①).
- 「진행 캠페인」 — 그대로.

### 3-3. 브랜드 상세

- KPI 바(:286-290): 앞에 **「진행 오리엔시트」·「전체 오리엔시트」**(§2 ②). 실패면 **두 칸 모두 「—」**. 「진행 신청」·「전체 신청」은 서베이 신청이 1건 이상일 때만(§2 ①).
- 절 순서:
  1. **「오리엔시트 (N)」** — 그 브랜드의 시트마다 브랜드 상세 모달과 **같은 카드**(`renderBrandOrientSheetCard`). 누르면 `osOpenDetail`. 0건이면 「발급된 오리엔시트가 없습니다」, 실패면 「오리엔시트를 불러오지 못했습니다」.
  2. 「광고주 신청 (N)」 — 서베이 신청이 1건 이상일 때만 절을 그린다.
  3. **「오리엔시트 연결 캠페인 (N)」** — `external_campaigns`(서베이 미연결) 중 id 가 연결된 캠페인 id 전체(§3-1 ②)에 있는 것. 「이 카드로 발행」과 「기존 캠페인 연결」 **둘 다** 여기로 온다. 서베이 신청에도 연결된 캠페인은 종전대로 「광고주 신청」 절 안에 있다(§1-3). 미니카드는 그대로이되 **「신청에 연결」 단추는 없다**(§3-4).
  4. 「직접 등록 캠페인 (N)」 — `external_campaigns` 의 나머지(어느 시트에도 연결되지 않은 캠페인).
  - ⚠️ 시트 조회가 실패하면 3·4 를 가를 수 없다 → 분류는 지금처럼 전부 「직접 등록 캠페인」으로 두고(단추는 §3-4 — 숨긴다) 절 제목 옆에 「(오리엔시트를 불러오지 못해 나누지 못했습니다)」.
- 「진행 캠페인」·「전체 캠페인」 KPI 는 그대로(서버 값).

### 3-4. 「신청에 연결」 단추

**「직접 등록 캠페인」 절의 미니카드에서만**, 그리고 **서베이 신청이 1건 이상인 브랜드에서만** 보인다.
- 서베이 0건 브랜드 — 그리지 않는다(누르면 따를 수 없는 안내만 떠서).
- 「오리엔시트 연결 캠페인」 — 그리지 않는다(오리엔시트에서 나온 캠페인을 서베이에 다시 이을 이유가 없고, 이으면 번호가 다시 매겨진다).
- 🔴 **시트 조회가 실패하면(`null`) 모든 캠페인에서 그리지 않는다** — 그때는 오리엔시트 캠페인도 「직접 등록」 절로 들어가(§2 ④) 절만 보고 단추를 달면 위 줄을 어기게 된다. 조회가 돌아오면(다시 진입) 종전대로 보인다.

### 3-5. 하지 않는 것

- 서버 함수(259) 변경 없음 — 경고·정렬·일정 뷰 그대로.
- 브랜드 카드 경고 사유에 오리엔시트 상태를 넣지 않는다(별건).

## 4. 설계 — 조각 B: 비용 카드

`appendCampOpsCostCard(camp)`(`admin-applications.js:976`)를 두 갈래로:

1. `camp.source_application_id` 가 있으면 **지금 그대로**(서베이 신청 기준 카드).
2. 없으면 `fetchOrientSheets()` 로 **전체 시트**를 받아 `data.cards[].campaign_id === camp.id` 인 시트를 찾는다(§2 ⑤ — 캠페인 브랜드로 거르지 않는다). 둘 이상 걸리면 §1-3 규칙대로 **`submitted_at` 이 가장 늦은 시트**(비어 있으면 뒤로 · 모두 비어 있으면 발급일 `created_at` 이 가장 늦은 시트). ⚠️ 서버가 전역 중복을 막아 재현이 어려운 **방어용**이라 검증 행은 두지 않는다.
   - 조회 실패·못 찾음 → **카드 없음.** 이 카드는 지금 오리엔시트 캠페인에 **원래 없던 것**이라, 못 그리면 종전 상태로 돌아갈 뿐 거짓 숫자가 생기지 않는다(§2 ④ 의 예외 근거).
   - `{orient_no}` 는 시트 행의 `orient_no`(`fetchOrientSheets` 가 가져오는 칸), 나머지는 `data.quote` 의 값.
   - 견적 있음(`osQuoteState(sheet.data).kind === 'quote'`) → 카드:

```
비용
오리엔시트 {orient_no} · {revision}차 견적 기준 (브랜드 제출 시점 예상 견적)
합계(부가세 포함)   {total_krw}원
공급가             {subtotal_krw}원
부가세             {vat_krw}원
모집 인원 · 구간    {slots}명 · {tier_name}
[견적서 열기]
```
   - 견적 실패(`kind === 'error'`) → 「견적 없음 — {osQuoteErrorText(사유)}」 한 줄.
   - 옛 구조·제출 전(`legacy`·`pending`) → 「견적 없음(이 오리엔시트에는 견적이 없습니다)」 한 줄.
- 「기존 캠페인 연결」로 이어진 캠페인에도 그 시트 견적이 뜬다(§1-3 — 둘을 구분하지 않는다).
- 「견적서 열기」는 `osOpenQuoteDoc` 를 쓴다. 🔴 그 함수는 시트를 `_osDetailSheet`·`_orientSheets` 에서만 찾는다(`osFindSheetForQuote`, `admin-orient.js:1180`) — 진행현황 화면에서는 둘 다 비어 있을 수 있다. → `osOpenQuoteDoc(sheetId, historyIndex, sheetObj)` 로 **셋째 인자를 선택으로** 받아, 주어지면 그 시트를 쓴다(기존 호출부는 인자 하나·둘이라 영향 없음). 현재 견적은 기존 호출(`admin-orient.js:1147`)처럼 **둘째 인자를 비워**(`undefined`) 부른다 — 비용 카드에서는 `osOpenQuoteDoc(id, undefined, sheet)`.
- 금액 표기는 `osKrw`. 권한·중복 방지(`data-cost-card` 지우고 다시 붙이기)·전환 중단(`currentCampApplicantId` 확인)은 지금 흐름 그대로.
