# 관리자 전용 초대 메일 + 관리자 전용 비밀번호 설정 화면

**작성일:** 2026-07-20 · **상태:** PR 1·2 구현 완료 (PR 3~5-B 미착수)

## 현재 상태 (규칙 A)

### 관련 코드·DB·UI 진입점

**초대 흐름 (2단계, 클라이언트 주도)**

| 단계 | 위치 | 내용 |
|---|---|---|
| ① 계정 생성 | `supabase/migrations/031_admin_invite_and_delete.sql` `invite_admin()` | super_admin 가드 → `auth.users`+`auth.identities`+`public.admins` 3행 생성. 임시 랜덤 32자 비밀번호(`extensions.crypt(..., gen_salt('bf',10))`) |
| ② 메일 발송 | `dev/js/admin-accounts.js:317-324` (`saveAdmin`) | `db.auth.resetPasswordForEmail(email, {redirectTo: location.origin + '/#reset-pw'})` |

②는 Supabase Auth 기본 발송 — 우리 코드가 본문을 전혀 통제하지 않는다. `invite_admin`은 **메일 발송 결과를 어디에도 기록하지 않는다.** 발송 실패 시 토스트만 뜨고(admin-accounts.js:320-324) 관리자 행은 그대로 남아 → 목록에서 「메일이 갔는지」 확인 불가.

**기존 비밀번호 경로 4개 (역할 혼재)**

| 경로 | 함수 | 동작 |
|---|---|---|
| 초대 | `saveAdmin` → `resetPasswordForEmail` | 재설정 메일 발송 |
| 값 직접 변경 | `executeResetPw` → `reset_admin_password(uuid, text)` | super_admin이 값 입력해 덮어씀 |
| 재발송 | `sendResetEmail` (401-412) | `resetPasswordForEmail(email)` — **`redirectTo` 없음 → Site URL(인플루언서 홈)로 착지** |
| 본인 변경 | `changeMyAdminPassword` (233-253) | `db.auth.updateUser({password})` |

`reset_admin_password`는 `008_create_admins.sql:78-98` 정의, `023:9-10`에서 `search_path = public, pg_temp`로 변경. **`gen_salt('bf')` 라운드 미지정 = 기본 6** — 규칙(`supabase.md` "round 10")과 불일치. `invite_admin`은 10을 쓴다.

**메일 템플릿 공유:** Supabase Auth는 종류별 템플릿 1개. "Reset password"를 인플루언서 비밀번호 찾기(`dev/js/auth.js:207-208`)와 관리자 초대(admin-accounts.js:319)가 공유. `docs/email-templates/reset-password.html`(일본어)는 레포에 있으나 운영 대시보드 미적용 → 현재 Supabase 기본 영문 발송.

**랜딩 `#reset-pw`는 인플루언서 앱 자산:** DOM `dev/index.html:803-832`(일본어·480px·`data-i18n`), 로직 `dev/js/auth.js:227-276`, 라우팅 `dev/js/app.js` — `detectRecoveryUrlEarly()`(5-14) → `reverb.recovery` 플래그 → `PASSWORD_RECOVERY` 이벤트(328-331) → 세션 복원·초기 라우팅 스킵(286-290, 408-409) → `DOMContentLoaded` 초기 페이지 전환(455-465), 만료 감지 분기(376-380). `location.origin`이 `globalreverb.com`이라 `/#reset-pw` = 인플루언서 앱.

**관리자 앱에는 로그인 전 화면이 존재하지 않는다 (핵심)**

```js
// dev/admin/app.js:93-96
if (!session) { window.location.href = '/#login'; return; }
```

세션 없으면 무조건 인플루언서 앱으로 리다이렉트. 세션이 있어도 `admins` 행 없으면 축출(101-106). 관리자 **로그인 화면조차** 인플루언서 앱 자산이다(`handleLogin`이 admins 조회 후 `/admin/`으로 보냄 — auth.js:156-161). **비로그인 진입 가능한 페인 개념 자체가 없다.**

**자체 발송 선례 `notify-orient-sheet`** (`supabase/functions/notify-orient-sheet/index.ts`): 브라우저 `functions.invoke` 직접 호출 → **다른 출처 허용 헤더(CORS)+OPTIONS 사전요청 있음**(45-52, 161-164, 규칙 준수 유일 사례) / 함수 내부 로그인 토큰→`admins` 재검증(180-200) / 링크 도메인은 **서버 환경변수** `PUBLIC_SALES_URL`(228) / 발송 성공 시 `mail_sent_at`·`mail_sent_to` 기록(266-270, 기록 실패가 발송을 무효화하지 않음) / 템플릿 `docs/email-templates/*` → `sync-email-templates.sh` → `render({{key}})` + HTML 주석 strip(240).

**토큰 링크 선례 `orient_sheets`:** `187:71-114` `get_orient_sheet(p_token)` — SECURITY DEFINER + `search_path=''` + anon 실행권한, 미매칭/만료/consumed를 `{success:false, reason}`로 반환(계정·자원 존재 여부 노출 차단), 조회 함수는 쓰기 부작용 없음. 작성 폼 `dev/sales/orient.html`은 **완전 자립형 정적 페이지**(자체 Supabase 클라이언트 인라인 611-623, storage.js 미사용, 만료/무효 화면 769-774). `dev/build.sh:137-148`이 `dev/sales/*.html` → `../sales/` 복사.

**빌드:** `build.sh:78` `ADMIN_JS_FILES` 이어붙이기(전역 스코프 1개), 관리자 산출물은 `../admin/index.html` **1개뿐**. 새 정적 페이지 추가 시 복사 단계 신규 필요(sales 섹션이 유일 선례).

### 이 제안과 충돌 가능성 있는 기존 동작

1. **관리자 앱 부팅 가드와 정면 충돌** — `/admin/` 안에 설정 화면을 두려면 `admin/app.js:93-96`을 우회해야 하고, 이건 관리자 앱 전체 보안 진입점 변경(cloak 타이밍상 비로그인 노출 위험 포함).
2. **DOM id 충돌** — 관리자 모달이 `resetPwNew`/`resetPwError`(378-380, 388-390), 인플루언서 페이지도 **같은 id**(index.html:815, 827). admin/index.html에 새 화면을 넣으면 즉시 충돌.
3. **`sendResetEmail` 중복** — 손대지 않으면 「초대는 관리자 화면 / 재발송은 인플루언서 홈」 모순 고착.
4. **`supabase.md` "URL/Key는 SUPABASE_ENVS에서만, 하드코딩 금지"** — 자립형 페이지는 `orient.html:611-621`처럼 또 하드코딩하게 된다. 선례는 있으나 규칙 위배 → 명시적 예외 처리 필요.
5. **`invite_admin` 승격 분기(031:32-40)** — 기존 `auth.users` 비밀번호를 임시 랜덤으로 **덮어쓴다**. 신설 흐름에서도 그대로 유지된다.

**충돌 없음 확인:** 인플루언서 `handleForgotPassword`·`handleResetPassword`·`reverb.recovery`·`#page-reset-pw`는 이 제안에서 **한 줄도 건드리지 않는다**(D-4에서 경계 고정).

### 미해결 백로그
- `reset-password.html`(일본어) 운영 미적용 — 관리자를 분리해도 **인플루언서 메일은 여전히 영문 기본**.
- 메인 세션 조사 중인 「회원가입 화면이 떴다」 건 — 본 사양은 구조적 원인(관리자를 인플루언서 앱으로 보냄)을 제거하나 특정 버그 확정과는 별개.
- 메모리 `feedback_edge_function_cors` — 코드 머지 ≠ 픽스, **함수 재배포 필수**.
- `supabase.md` 「개발서버 메일 발송 테스트 금지」 — 실발송 검증은 운영에서만.

## 의심·경우의 수 (규칙 B)

### 1. 깨질 가능성

**① [UX·필수] 초대 링크 수명이 실무 리듬과 안 맞는다 — 가장 흔한 실패.** Supabase 재설정 링크는 1회용+만료(기본 1시간). 밤에 초대 → 다음 날 아침 클릭 → 만료. 메일 앱 링크 미리열기(Outlook Safe Links 등)가 **사람보다 먼저 토큰을 소비**하는 알려진 사고. super_admin이 「안 왔대」라며 두 번 누르면 나중 토큰만 유효 → 먼저 받은 링크는 실패하는데 화면엔 "만료"만. → 만료 화면에 **재발송 요청 경로**가 필수이고, 그 경로가 기존 `sendResetEmail`과 하나로 합쳐져야 한다.

**② [데이터] 기존 인플루언서를 관리자로 초대하면 그 사람의 인플루언서 로그인이 즉시 끊긴다.** `invite_admin`(031:32-40)이 승격 시 기존 비밀번호를 임시 랜덤으로 덮어쓴다. 응모이력·정산을 가진 실사용자라면 초대 메일이 스팸함으로 가는 순간 **계정에서 잠기고 본인은 이유를 모른다.** 감사용 계정(`is_audit`) 승격도 동일. 승격 케이스에서 덮어쓸 **기술적 필요가 없다** — 이미 유효한 비밀번호를 본인이 쓰고 있다. 신규 생성 로직과 뭉쳐서 생긴 부작용. 메일·화면만 고치면 새 흐름에서도 같은 사고가 난다.

**③ [기술·운영] 자체 발송으로 바꾸면 실패가 조용해진다.** Auth 발송은 대시보드 로그에 남지만 Brevo 발송은 Edge Function 로그+Brevo 로그로 흩어진다. `saveAdmin`은 실패 시 토스트만, `admins`엔 기록 없음 → 「초대했는데 안 왔다」 문의 시 super_admin이 **발송 여부를 알 방법이 없다.** 게다가 브라우저 직접 호출이라 **다른 출처 허용 헤더(CORS) 누락 시 정적 리뷰를 통과하고도 100% 실패**(오리엔 발급 메일이 리뷰 GO·운영 배포까지 통과했으나 한 번도 성공 못 한 선례). 개발서버 발송 테스트 금지 정책 때문에 배포 전 검증이 0회 되기 쉽다.

**④ [UX] 관리자는 PC 전용인데 메일은 폰에서 열린다.** 초대받은 실무자는 십중팔구 폰에서 먼저 연다. 설정 페이지는 반응형으로 만들 수 있으나 완료 후 "관리자 페이지로 이동"이 폰에서 열리면 PC 레이아웃이 그대로 뜬다. 게다가 **관리자 로그인 화면이 인플루언서 앱 `/#login`**이라 안내 문구가 어색해진다("일본어 화면에서 로그인하세요").

**⑤ [권한] 비로그인 호출 함수가 `auth.users`에 쓰게 되는 위험 (안 A 한정).** 로직 버그 하나가 **super_admin 계정 탈취**로 직결. Supabase 비밀번호 정책(유출 비밀번호 검사 — `security.md`에 "활성 유지" 명시)을 **우회**한다. bcrypt 라운드를 직접 관리해야 하는데 이미 `reset_admin_password`가 라운드 6을 쓰는 불일치가 있다(008:94). 기존 세션 무효화도 안 된다.

**⑥ [환경] 도메인 분기.** 링크를 클라 `location.origin`으로 만들면 조작 가능, 서버 환경변수로 만들면 **개발·운영 각각 secrets** 필요(`PUBLIC_SALES_URL` 선례). 한쪽만 설정하면 개발서버 초대가 운영 URL로 나간다.

### 1-1. Q3 확장(관리자 비밀번호 찾기)으로 새로 생긴 것

**⑦ [데이터·기술] 승격 계정에서 두 찾기 흐름이 서로의 링크를 죽인다 — 확장분 최대 함정**

인플루언서로 활동하다 관리자로 승격된 계정은 **같은 `auth.users` 행 하나**를 공유한다. 비밀번호도 하나다. 그런데 찾기 경로는 둘이 된다:

- 관리자 찾기 → `generateLink` → 재설정 토큰 발급
- 인플루언서 찾기(`auth.js:187`) → `resetPasswordForEmail` → **같은 사용자의 재설정 토큰 재발급**

Supabase는 사용자당 유효한 재설정 토큰을 하나로 유지하므로 **나중 요청이 먼저 것을 무효화한다.** 실제 시나리오: 관리자 찾기 요청 → 메일 안 옴(스팸함) → 조급해져 인플루언서 화면에서 또 찾기 → **관리자 링크가 죽고**, 뒤늦게 도착한 관리자 메일을 클릭하면 만료 화면. 원인을 알 수 없어 「시스템이 고장났다」로 보고된다.

- 비밀번호 자체는 하나이므로 **어느 쪽으로 바꾸든 양쪽 로그인에 반영된다** — 기능적 손상은 없다. 문제는 **링크 무효화와 그 원인 불투명성**이다.
- 완화: ①만료 화면 문구에 「다른 곳에서 재설정을 다시 요청하면 이전 링크는 사용할 수 없습니다」 명시 ②관리자 재설정 메일에 「이 링크는 가장 최근에 요청한 1개만 유효합니다」 안내. 구조적 해결은 불가(Auth 동작).

**⑧ [UX] 열거 차단의 대가 — 「보냈습니다」인데 영원히 안 온다**

§D-9의 등시간·동일응답 설계는 보안상 필수지만, 다음 사람에게는 **무한 대기**를 만든다: 이메일 오타 / 다른 주소로 등록된 경우 / `remove_admin_role`로 권한이 해제된 사람. 화면은 「발송했습니다」라고 말한다. → §D-9의 안내 문구 3요소(특히 **대체 연락 경로**)가 선택이 아니라 **필수 요건**인 이유.

**⑨ [권한·UX] 부팅 가드 목적지 변경의 유탄 — 인플루언서 오진입**

`/admin/` 무세션 리다이렉트를 관리자 로그인 페이지로 바꾸면, **북마크를 잘못 눌렀거나 URL을 잘못 친 인플루언서**도 한국어 관리자 로그인 화면에 도착한다. 지금은 인플루언서 앱 `/#login`으로 가서 자연스러웠다.

- 로그인 성공 후 `admins` 없음 → 「관리자 계정이 아닙니다」 + **인플루언서 앱 이동 버튼** 필수(막다른 골목 방지)
- 로그인조차 안 한 상태에서 나갈 경로도 필요 — 화면 하단에 인플루언서 앱 링크

**⑩ [기술·운영] Brevo 쿼터 소진의 폭발 반경**

찾기 화면은 이 프로젝트에서 **처음으로 「비로그인 상태에서 메일 발송을 유발할 수 있는 공개 경로」**다. 기존 익명 경로(`unsubscribe_by_token`·`track_promo_click`·`submit_brand_application`)는 메일을 보내지 않거나 관리자 알림 1통에 그친다. 쿼터가 마르면 **광고주 접수 알림·일일 다이제스트·인플루언서 메일이 전부 함께 죽는다.** §D-11 ②(전역 제한)가 이 한 가지를 위해 존재한다.

**⑪ [UX] 로그인 화면도 폰에서 열린다**

찾기 완료 → 메일 → 설정 완료까지 폰에서 진행한 뒤 「관리자 페이지로」를 누르면 PC 레이아웃이 폰에 뜬다(`ui.md` — 관리자는 PC 전용). 설정 완료 화면과 로그인 성공 화면 **양쪽**에 PC 접속 권장 안내가 필요하다.

**⑫ [기술] 다중 탭·세션 잔존**

`setpw` 착지 시 재설정 세션이 생긴다. 사용자가 그 탭을 두고 다른 탭에서 `/admin/`을 열면 **세션이 있으므로 부팅 가드를 통과**해 관리자 앱이 열린다(비밀번호는 아직 안 바꿨는데). 인플루언서 앱은 `reverb.recovery` 플래그로 이걸 막지만(`app.js:286-290`), 관리자 앱에는 그런 장치가 없다.
→ 설정 완료 후 **명시적 `signOut()`**(인플루언서 `handleResetPassword`가 하는 것과 동일 — `auth.js:265`) 후 로그인 화면으로 보내, 재설정 세션이 관리자 앱으로 새지 않게 한다.

### 2. 현재 구현과 충돌하는 지점
- 관리자 앱에 로그인 전 화면이 없다(admin/app.js:93-96) → **별도 자립형 페이지 권고의 결정적 근거.**
- DOM id `resetPwNew`/`resetPwError` 3중 사용 → admin/index.html에 넣으면 즉시 충돌.
- `sendResetEmail`이 `redirectTo` 없이 호출(405) → 손대지 않으면 목적지 모순 고착.
- `supabase.md` URL/Key 하드코딩 금지 → 자립형 페이지는 명시적 예외 처리 필요.

### 3. 의도 모호점
- **"설정 화면"의 범위** — ⓐ초대 최초 설정 전용인지 ⓑ기존 관리자의 「비밀번호 찾기」까지인지. 후자면 **관리자 전용 로그인 화면**까지 필요해진다. → **Q3에서 ⓑ 확장이 선택되어 §D-8로 설계 확정.**
- **「관리자 비밀번호 찾기」가 `reset_admin_password`(super_admin이 값 직접 입력)를 대체하는가?** → 대체하지 않는 것으로 설계했다. 셀프 찾기가 주 경로가 되고, super_admin 직접 변경은 **메일조차 못 받는 상황의 긴급 최후 수단**으로 남는다. 폐지를 원하면 별도 결정 필요.
- **찾기 대상 범위** — 모든 등급(super_admin 포함)이 셀프 찾기 가능한지, 아니면 super_admin은 제외인지. 기본값은 **전 등급 허용**으로 설계했다(super_admin을 제외하면 그 사람이 잠겼을 때 복구 경로가 사라진다).
- **"관리자 전용 메일"에서 '전용'의 범위** — 본문·제목·언어만인지, 발신자명(`REVERB JP`)까지인지. Brevo 발신자는 전 파이프라인 공용이라 분리는 별건.
- **인플루언서 재설정 메일 처리 미정** — 관리자를 빼내면 인플루언서용은 **여전히 영문 기본**으로 남는다. 범위 안/밖 결정 필요.
- **기존 초기화 모달 통합 vs 분리** 미정.

## 권고

**`generateLink`로 링크만 서버에서 발급 + 메일 본문·발송은 Edge Function + Brevo + 랜딩은 `/admin/` 밖 자립형 정적 페이지**(안 B)를 권고한다. 자체 토큰(안 A)은 비로그인 함수가 `auth.users` 비밀번호를 직접 쓰게 되어 위험 대비 이득이 없고, redirect만 고치는 안 C는 「메일 문구」라는 요청의 절반을 못 푼다. 다만 **PR 1만 배포해도 실제 보고된 증상은 사라지므로** 위험을 나눠 가는 순서를 권한다.

### D-8. 관리자 전용 로그인·비밀번호 찾기 진입점 (Q3 확장)

#### 문제의 실체 — 발견 가능성

관리자가 비밀번호를 잊었을 때의 현재 동선:

1. `/admin/` 접속 → 세션 없음 → `admin/app.js:93-96`이 **인플루언서 앱 `/#login`으로 리다이렉트**
2. 그 화면의 「パスワード再設定」은 **인플루언서용**(`auth.js:187` → 일본어 메일 → 인플루언서 `#reset-pw`)

즉 **관리자 찾기 화면을 만들어도, 관리자가 거기 도달할 경로가 없다.** URL을 미리 알고 직접 입력해야 한다.

#### 3안 비교

| 축 | (a) 찾기 화면만 추가 | **(b) 로그인 화면까지 신설 (권고)** | (c) 인플 로그인에 관리자 링크 추가 |
|---|---|---|---|
| 발견 가능성 | **없음** — URL 직접 입력 필요 | 있음 — `/admin/` 무세션 → 관리자 로그인 → 「비밀번호 찾기」 | 있음 |
| `admin/app.js:93-96` 변경 | 불필요 | **필요** (목적지 1줄) | 불필요 |

| 규칙 충돌 | 없음 | 없음 | **위반** — 인플루언서 UI(일본어)에 관리자용 한국어 링크 노출(`ui.md`) + 일반 이용자 혼란 |

#### 권고 — (b), 단 **단일 페이지 3모드**로 구현

PR 1에서 만드는 자립형 페이지를 처음부터 **모드 전환 컨테이너**로 설계하고, 화면 3종을 한 파일에 담는다.

| 모드 | 진입 | 화면 |
|---|---|---|
| `login` | `/admin/` 무세션 리다이렉트 (기본 모드) | 이메일·비밀번호 + 「비밀번호를 잊으셨나요」 링크 |
| `forgot` | login에서 링크 | 이메일 입력 → 발송 안내(항상 동일) |
| `setpw` | 메일 링크 착지 (재설정 세션 보유) | 새 비밀번호 입력 |

**단일 파일인 이유:** ①파일 1개 = build.sh 복사 1줄, 신규 진입점 추가 비용 0 ②`resetPwNew` 등 id 충돌 회피가 파일 경계로 자동 보장 ③Supabase 클라이언트 인라인 중복이 1회로 끝남(`supabase.md` 하드코딩 금지 예외를 최소화) ④PR 1에서 `setpw`만 구현하고 PR 5에서 모드 2개를 추가해도 **파일 재작성이 아니라 추가**가 된다.

#### 부팅 가드 변경 (`dev/admin/app.js:93-96`)

```
현재: if (!session) → '/#login'  (인플루언서 앱)
변경: if (!session) → 관리자 로그인 페이지 (mode=login)
```

**변경 범위를 이 한 줄로 한정한다.** 아래 두 가지는 건드리지 않는다:

- **세션은 있으나 `admins` 행이 없는 경우**(`admin/app.js:101-106`, 토스트 후 `/`) — 유지. 여기를 로그인 페이지로 보내면 세션이 살아있는 채 로그인 화면으로 가 **무한 왕복**이 된다.
- **`auth.js:156-161`**(인플루언서 앱에서 관리자가 로그인하면 `/admin/`으로 이동) — 유지. 기존 관리자의 북마크·습관을 보호하는 하위호환 경로다. 두 입구가 공존해도 도착지가 같아 모순 없음.

**신규 회귀 주의:** 목적지 변경으로 **인플루언서가 `/admin/`에 잘못 진입한 경우**도 관리자 로그인 페이지로 간다. 이 페이지는 로그인 성공 후 `admins` 조회 → 없으면 「관리자 계정이 아닙니다」 + 인플루언서 앱 이동 버튼을 노출해야 한다(막다른 골목 방지).

### D-9. 계정 존재 여부 노출 차단 설계

#### 원칙 — 판정을 클라이언트에 절대 노출하지 않는다

`security.md` 「계정 열거 방지」 + 기존 인플루언서 처리(`auth.js:209-217` — 성공·실패 무관하게 일반 메시지)와 정합.

**익명(anon) 실행권한 함수는 이 용도에 쓰지 않는다.** `orient_sheets`의 `{success:false, reason}` 패턴(`187:88-92`)은 **공격자가 이미 토큰을 가진 경우**의 자원 열거를 막는 설계이지, **입력값이 존재하는지**를 감추는 설계가 아니다. 이메일을 받아 결과가 갈리는 함수는 반환값이 무엇이든 판별 도구가 된다.

> 참고: `is_admin()`이 익명에 실행권한이 부여돼 있으나(`084:172`) 내부가 `auth.uid()` 기반이라 익명 호출은 항상 false — 열거 통로가 아니다. 이 사양은 **신규 익명 실행권한 함수를 0개** 추가한다.

#### 판정 주체 = Edge Function (service_role)

```
브라우저(익명) → admin-password-reset-request (이메일만 전달)
   ↓ [함수 내부, 클라이언트에 안 보임]
   service_role 로 admins 조회
   ├─ 관리자 O → generateLink → Brevo 발송 → 기록
   └─ 관리자 X → 아무것도 안 함
   ↓
항상 동일한 응답 { ok: true }
```

#### 응답·소요시간·화면 동일성 보장 3종

| 축 | 방법 |
|---|---|
| **응답 본문** | 모든 분기에서 `{ ok: true }` 고정. 오류(Brevo 실패·DB 오류 포함)도 동일 — 실패는 **함수 로그에만** 기록. 상태 코드도 200 고정 |
| **소요시간** | 함수 시작 시각을 잡고, 반환 직전 **고정 하한(권장 800밀리초)까지 대기**. 미매칭(즉시 종료)과 매칭(generateLink+Brevo 왕복)의 시간차를 흡수. 하한을 넘으면 그대로 반환(상한은 두지 않음 — 상한을 두면 초과 케이스가 다시 신호가 됨) |
| **화면** | 제출 성공/실패 분기 없이 **항상 같은 안내 화면**으로 전환. 입력 폼을 숨기고 재제출 유도를 끊어 반복 시도 자체를 줄임 |

**안내 문구에 필수로 포함할 3요소** (열거 차단의 필연적 대가를 UX로 보완):

1. 조건 명시 — 「관리자 계정으로 등록된 주소인 경우에만 메일이 발송됩니다」
2. 대기 안내 — 「5분 이내에 도착하지 않으면 스팸함을 확인해 주세요」
3. **대체 연락 경로** — 「그래도 오지 않으면 최고관리자에게 직접 요청해 주세요」

3번이 없으면, 오타를 쳤거나 관리자 권한이 이미 해제된(`remove_admin_role`) 사람은 **영원히 기다린다.**

### D-10. 초대 흐름과 찾기 흐름의 통합 범위

#### 착지 화면 = 통합 (1개)

두 링크 모두 `setpw` 모드에 착지한다. 화면 구조·검증·완료 처리는 동일하고 **문구만 분기**한다.

| 구분 | 초대(최초 설정) | 찾기(재설정) |
|---|---|---|
| 제목 | 관리자 비밀번호 설정 | 비밀번호 재설정 |
| 안내 | 「REVERB JP 관리자로 초대되었습니다. 사용할 비밀번호를 정해 주세요.」 | 「새 비밀번호를 입력해 주세요.」 |
| 완료 후 | 관리자 페이지 안내 + **PC 접속 권장** | 동일 |

**분기 방법:** `redirectTo`에 `?mode=invite` / `?mode=reset`를 붙여 서버(Edge Function)가 결정. 클라이언트가 조작 가능한 값이지만 **문구만 바꿀 뿐 어떤 권한·검증도 이 값에 의존하지 않는다** — 이 성질을 코드 주석에 명시할 것. 값이 없거나 이상하면 중립 문구로 폴백.

#### Edge Function = **분리 (2개)**

| 함수 | 호출자 | 인증 |
|---|---|---|
| `notify-admin-invite` (PR 2) | 관리자 화면 | **super_admin 로그인 토큰 필수** |
| `admin-password-reset-request` (PR 5-B) | 공개 페이지 | **익명 허용** + 요청 제한 |

**겸용을 권고하지 않는 이유:** 하나로 합치면 **익명이 도달 가능한 코드 경로가 super_admin 전용 기능과 같은 함수 안에 공존**한다. 분기 조건 하나만 잘못되면 익명이 임의 이메일에 초대 메일을 쏘는 경로가 열린다. 인증 강도가 다른 진입점은 함수를 나누는 것이 원칙이다.

**공유 가능한 것:** `generateLink` 호출·Brevo 발송·템플릿 렌더 헬퍼는 `supabase/functions/_shared/` 모듈로 분리해 양쪽이 가져다 쓸 수 있다(선택 사항).

**메일 템플릿은 2개** — `admin-invite.html`(PR 2) / `admin-password-reset.html`(PR 5-B). 문구 목적이 달라 하나로 합치면 어느 쪽도 자연스럽지 않다.

### D-11. 악용 방지 (요청 제한)

#### 전제 — Auth Rate Limits 보호 밖

운영 Supabase의 `Rate limit for sending emails = 100/h`는 **Supabase Auth가 직접 보내는 메일**에만 적용된다. 우리가 `generateLink`로 링크만 받아 **Brevo로 직접 보내면 이 제한을 통과하지 않는다.** 즉 무제한 호출 시:

- 특정 관리자에게 **메일 폭탄**
- Brevo 월 20,000통 쿼터 소진 → **전 파이프라인 마비**(광고주 알림·일일 다이제스트·인플루언서 메일 전부)

두 번째가 훨씬 위험하다. 방어를 반드시 자체 구현한다.

#### 3층 방어

| 층 | 기준 | 목적 | 초과 시 |
|---|---|---|---|
| **① 이메일별** | 5분 1회 / 24시간 5회 | 특정 관리자 메일 폭탄 차단 | 조용히 skip |
| **② 전역** | 시간당 30건 (매칭·미매칭 무관) | Brevo 쿼터 방어 | 조용히 skip + **함수 로그 경고** |
| **③ 입력 형식** | 이메일 형식 검사 + 길이 상한 | 쓰레기 요청 조기 차단 | 조용히 skip |

**「조용히 skip」이 핵심** — 제한에 걸려도 응답·시간·화면은 §D-9와 완전히 동일해야 한다. 「요청이 너무 많습니다」를 노출하면 그 자체가 **해당 이메일이 실재한다는 신호**가 된다(제한은 매칭된 이메일에서만 자주 걸리므로).

② 전역 제한은 미매칭 요청도 세야 무작위 이메일 난사로 쿼터를 태우는 것을 막는다.

#### 기록 테이블

- 컬럼: 이메일 해시(sha256, 소문자·공백제거 정규화 후) / 요청 시각 / 매칭 여부(내부 통계용, 외부 미노출)
- **원문 이메일 저장 안 함** — 이 테이블이 유출되어도 관리자 이메일 명단이 되지 않게. `admins`에 이미 이메일이 있지만 그쪽은 `is_admin()` 게이트가 있고, 이 테이블은 요청만 하면 행이 쌓이는 공개 경로다
- RLS: SELECT `is_super_admin()`, **INSERT/UPDATE/DELETE 직접 정책 없음** (service_role 전용)
- 보존: 30일 경과 행 자동 삭제 — pg_cron 일 1회. 선례 `purge_old_influencer_flags` / job `influencer-flags-retention-daily`(마이그레이션 166)

#### 남는 리스크 (수용)

IP 단위 제한은 Edge Function에서 신뢰 가능한 IP를 얻기 어려워 넣지 않는다. ②가 쿼터를 지키므로 실질 피해는 「시간당 30통 한도 내 소음」으로 묶인다. 자동화 방지(캡차·작업증명)는 **현시점 과잉** — ② 초과 경고가 로그에 반복되면 그때 도입을 재검토한다.

### PR 5-B (관리자 비밀번호 찾기) — 2026-07-20

- 마이그레이션 **243** `admin_password_reset_requests` — 요청 기록(이메일 sha256 해시만·원문 미저장) + 요청 제한 판정 함수 + 30일 보존 정리(pg_cron, KST 04:15 — 선례 166과 15분 간격)

- 메일 템플릿 `docs/email-templates/admin-password-reset.html`

**초안 대비 달라진 것 — 등시간 응답 설계**: 초안 §D-9는 「하한 800밀리초」를 제안했다. 검증 과정에서 하한만 두면 발송 경로(generateLink+Brevo 왕복)가 그 값을 넘길 때 시간차가 다시 신호가 된다는 지적이 나와, **하한을 2500밀리초로 올려** 초과 확률을 낮추는 쪽으로 조정했다. 「상한을 둬서 발송을 끊는」 방식은 채택하지 않았다 — 절단 자체가 신호가 되거나 발송이 불완전해지는 쪽이 더 위험(초안 §D-9 결론과 동일). 잔여 위험은 수용하고 코드 주석에 명시.

**요청 제한 기록 시점**: 판정 이후, **결과와 무관하게 항상 기록**. 이메일별 제한에 걸린 요청을 기록에서 빼면 서로 다른 이메일을 돌려가며 두드리는 공격에서 전역 상한이 느슨해지기 때문. 동시 요청은 `pg_advisory_xact_lock` 단일 키로 직렬화.

**미해결 — 링크 만료 시간 상향**: 초안은 24시간 상향을 권고했으나 **아직 적용하지 않았다.** Supabase 대시보드 Authentication → Email 의 「Email OTP Expiration」(기본 3600초)이고, **이 값을 올리면 인플루언서 비밀번호 찾기 링크 수명도 함께 늘어난다**(같은 설정 공유, 분리 불가). 사용자 판단 필요.

**초안에 없던 것 — 승격자용 메일 문구 분기.** 245로 승격자의 기존 비밀번호가 유지되면서, 초대 메일의 「사용하실 비밀번호를 설정해 주세요」가 **사실과 어긋나게** 됐다(링크를 안 눌러도 기존 비밀번호로 로그인됨). 템플릿을 `{{headline}}`·`{{lead}}`·`{{cta_label}}` 로 바꾸고 `promoted_at` 기준으로 분기 — 승격자는 「권한이 추가되었습니다 / 기존 비밀번호로 로그인 가능, 바꾸려면 아래」.

**구현 중 정정** — 이메일 조회를 `ilike` → `eq` 로 바꾸려다 되돌림. `eq` 는 대소문자를 구분하는데 `admins.email` 은 초대 시 입력값 그대로 저장돼 대문자가 섞일 수 있어, 조회가 실패하는 회귀가 된다. **대소문자 무시는 유지하고 와일드카드만 이스케이프**하는 방식으로 확정(`escapeLikePattern`). `_`·`%` 가 든 이메일이 다른 관리자 행에 매칭되는 문제(리뷰 지적)는 이걸로 해소. 두 Edge Function 모두 적용.
