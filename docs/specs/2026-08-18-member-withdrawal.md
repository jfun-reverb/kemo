## 배경 한 줄

**탈퇴 버튼은 있으나 아무 일도 일어나지 않는다.** 확인창과 안내 문구만 뜨고 **서버 호출이 0줄**이다. 그런데 회원에게는 「접수했습니다」라고 말하고, 약관·개인정보처리방침은 그 접수를 전제로 한 규정을 여럿 두고 있다.

## 1. 현재 상태 (규칙 A — 2026-08-18 코드 실측)

### 1-1. 탈퇴 기능의 전부

`dev/js/mypage.js:602` — **이것이 코드 전부다.**

```javascript
function handleWithdraw() {
  const confirmMsg = t('mypage.withdrawConfirm');   // 「정말 탈퇴하시겠습니까?」
  const toastMsg   = t('mypage.withdrawToast');     // 「탈퇴 신청을 접수했습니다. 운영팀에 LINE으로 연락해 주세요.」
  if (confirm(confirmMsg)) toast(toastMsg);
}
```

진입점은 **햄버거 메뉴 하단 「退会する」** 한 곳(`dev/js/notifications.js:97`).

| 확인 | 결과 |
|---|---|
| 서버 호출 | **0줄** |
| 탈퇴 사유 수집 | **없음** (확인창 하나뿐) |
| 안내 내용 | 토스트 **한 줄**. 약관·방침이 정한 안내는 **전무** |
| 기록 | **어디에도 안 남음** |
| 관리자 확인 화면 | **없음** — 관리자 코드 전체에서 탈퇴 관련 항목 **0곳** |
| 데이터베이스 | 인플루언서 탈퇴를 담는 **표·칸 없음** |
| 자주 묻는 질문 | 탈퇴 항목 **없음** |

### 1-2. 「LINE으로 연락」의 정체 — 미완성 흔적이다

**2026-04-06 최초 커밋(`793c0c62`)에 이미 있었다.** 화면 뼈대를 만들 때 서버 기능이 없으니 「일단 사람이 연락하게」 둔 자리다. **설계된 절차가 아니다.**

⚠️ **그리고 방침에 어긋난다.** 2026-05-21 사용자 명시(메모리 `project_line_minimization`):
> LINE 의존을 최대한 줄이고 관리자 응대 창구를 앱 하나로 통합한다. **LINE에 남기는 건 앱에 못 들어오는 경우만**(가입 전·로그인 불가·장애). **앱 안에서 LINE 유도 문구는 제거.**

탈퇴 화면은 **앱 안에서 LINE으로 내보내는** 자리라 정확히 제거 대상이다.

⚠️ **그렇다고 응모건 메시지로 보낼 수도 없다.** `application_messages.application_id` 가 **NOT NULL** 이라 **응모 1건에 붙어 있고**, 탈퇴는 응모와 무관하다. **응모를 한 번도 안 한 회원**은 창구가 아예 없다. 같은 메모리가 「**응모건 밖 일반 문의 창구 신설**이 LINE 축소의 핵심」이라 적어 뒀으나 **미착수**다.

### 1-3. 약관·방침이 지킬 수 없는 약속을 하고 있다

| 문서 | 약속 | 실제 |
|---|---|---|
| 약관 제6조 1항 | 「마이페이지에서 **언제든지 탈퇴 신청**을 할 수 있습니다」 | 버튼은 있으나 **접수되지 않음** |
| 약관 제6조 2항 | 「진행 중인 캠페인 신청(심사중/승인)은 **자동으로 철회 처리**됩니다」 | 철회하는 코드 **없음** |
| 방침 §보유기간 | 「원칙적으로 **탈퇴일로부터 5일** 경과 후 지체 없이 파기합니다(**변심에 의한 탈퇴 취소 대비**)」 | **탈퇴일이 기록되지 않아 셀 수 없음** |
| 방침 수집 표 | 회원가입 정보 「**탈퇴 후 5일** 경과 시 파기」 / PayPal 이메일 「**탈퇴 후 5년**(세법)」 / 프로필·주소·신청 기록 「**탈퇴 시 파기**」 | 〃 |

⚠️ **탈퇴일이 어디에도 없으므로 방침의 보관 기간 규정을 집행할 수단 자체가 없다.** 한국 개인정보 보호법·일본 개인정보보호법 양쪽 준수 대상이다.

### 1-4. 재사용할 수 있는 것들 (설계가 단순해지는 근거)

| 무엇 | 어디 | 이번에 어떻게 쓰나 |
|---|---|---|
| **응모 취소 함수** `cancel_application` | 마이그레이션 113 → **306**(현재 원본) | 약관 제6조 2항의 「자동 철회」에 재사용 |
| **인플루언서 상태 이력** `influencer_flags` | `action`(verify/violation/blacklist/clear) + 사유·메모·시각 | 탈퇴 이력을 같은 표에 담을 수 있다 |
| **관리자 인플루언서 상세 모달** 「상태 관리」 패널 | `dev/js/admin-influencers.js:362·449` | 탈퇴 상태·사유를 여기에 붙인다 |

| **취소 사유 기준 데이터** | `lookup_values(kind='cancel_reason')` | 탈퇴 사유도 같은 방식으로 |

### 1-5. 이 제안과 충돌 가능성이 있는 기존 동작

**⚠️ ㄱ. 「자동 철회」가 서버에서 막힌다.** 마이그레이션 **247** 이 「**송금완료된 정산이 있는 응모는 반려·되돌리기를 차단**」한다. 약관 제6조 2항을 글자 그대로 실행하면 **그 응모에서 반드시 실패**한다.

**⚠️ ㄴ. 응모 취소에도 조건이 있다.** `cancel_application`(306)은 **결과물이 승인된 건을 차단**하고, 구매 기간 이후에는 **사유·동의를 강제**한다. 탈퇴가 이 함수를 재사용하면 **같은 조건에 걸린다.**

**⚠️ ㄷ. 알림·메일이 계속 나간다.** 일일 다이제스트·홍보 메일·마감 안내가 **인플루언서 표를 기준으로** 대상을 고른다. 탈퇴 상태를 안 보면 **탈퇴한 사람에게 계속 메일이 간다.**

**⚠️ ㄹ. 로그인이 계속 된다.** 탈퇴는 인증 계정(`auth.users`)과 별개다. **표시만 바꾸면 그 사람은 여전히 로그인해 응모할 수 있다.**

**⚠️ ㅁ. 감사용 계정**(`is_audit=true`)은 운영팀이 쓰는 공용 계정이라 **탈퇴 대상이 아니다.**

**⚠️ ㅂ. 정산 행은 삭제할 수 없다.** `settlement_events` 가 `ON DELETE RESTRICT` 다. 「탈퇴 시 파기」를 글자 그대로 하면 **정산이 걸린 회원은 파기 자체가 불가능**하다. 방침도 PayPal 이메일은 **5년 보관**이라 해 서로 맞물린다.

### 1-6. 미해결 백로그

- **응모건 밖 일반 문의 창구** — 미착수. 이번 범위 밖이나 **탈퇴 문의가 갈 곳이 없다는 문제와 같은 뿌리**다
- 2026-08-12 문구 대조 조사에서 이 건이 「**미정 — 가장 무거움**」으로 기록됨

## 2. 의심·경우의 수 (규칙 B)

**① 진행 중 응모가 있는데 철회가 막히면 탈퇴가 통째로 실패한다.** §1-5 ㄱ·ㄴ. 「전부 철회하고 탈퇴」로 짜면 **한 건만 막혀도 전체가 멈춘다.**

**② 5일 유예를 어떻게 구현하나.** 방침이 「변심 대비 5일」이라 했으니 **그 사이 취소할 수 있어야 한다.** 그런데 취소하려면 **로그인이 돼야** 하고, 로그인이 되면 「탈퇴했는데 왜 들어가지나」가 된다.

**③ 데이터: 파기 범위가 항목마다 다르다.** 방침은 회원가입 정보 5일 · 프로필·주소·신청 기록 즉시 · **PayPal 이메일 5년**이다. **한 번에 지우는 것이 아니라 항목별로 다른 시점**이다.

**④ 데이터: 재가입.** 같은 이메일로 다시 가입하면? 인증 계정을 지웠으면 새 사람이 되고, 안 지웠으면 **가입이 막힌다.**

**⑤ 권한: 관리자가 대신 탈퇴시키는 경로**(약관 제6조 3항 「자격 상실」)와 본인 탈퇴는 **다른 사건**이다. 같은 표에 담되 **구분**해야 감사에서 갈린다.

**⑥ 사용자 경험 — 사유를 몇 개나 묻나.** 떠나는 사람에게 긴 설문을 내밀면 **끝까지 안 한다.** 그렇다고 안 물으면 **왜 떠나는지 영영 모른다.**

**⑦ 사용자 경험 — 「대기」 상태의 회원이 로그인하면 무엇이 보이나.** 미지급 때문에 대기 중인 사람이 들어왔을 때, **평소 화면 그대로면 탈퇴가 안 된 줄 안다.**

**⑧ 사용자 경험 — 되돌릴 수 없는 동작이다.** 확인창 하나로 끝내면 **잘못 누른 사람이 계정을 잃는다.** 지금은 아무 일도 안 일어나서 문제가 없었지만, **진짜로 동작하기 시작하면 그때부터 위험하다.**

**⑨ 법률: 탈퇴일 기록은 선택이 아니다.** 방침이 그 날짜를 기준으로 파기 기한을 정하고 있다. **기록이 없으면 방침 자체를 못 지킨다.**

**⑩ 시간대.** 「탈퇴일로부터 5일」의 하루 경계는 **일본 시각** 기준이어야 한다.

## 4. 설계

### 4-1. 상태 — 탈퇴는 「즉시」가 아니라 「단계」다

```
신청  →  [대기]  →  [예정]  →  [완료]
              ↑         ↑
        미지급 있음   5일 유예
```

| 상태 | 뜻 | 회원 화면 | 로그인 |
|---|---|---|---|
| **대기**(`pending_payout`) | 받을 돈이 남았다 | 「지급이 끝나면 처리됩니다 · 예정일 ◯월 ◯일」 | ✅ 된다 |
| **예정**(`scheduled`) | 5일 유예 중 | 「◯월 ◯일에 탈퇴 처리됩니다 · **탈퇴 취소**」 | ✅ 된다 |
| **완료**(`done`) | 파기 시작 | 로그인 불가 | ❌ |

⚠️ **「대기」와 「예정」에서 로그인이 되는 것은 의도다** — 방침이 「변심에 의한 탈퇴 취소」를 전제하므로 **취소할 수단이 있어야** 한다(경우의 수 ②). 대신 **화면 맨 위에 상태를 크게 띄워** 「탈퇴가 안 된 줄」 알게 되는 것을 막는다(경우의 수 ⑦).

⚠️ **「대기」에는 유예를 걸지 않는다** — 지급이 끝나는 시점이 언제일지 모르므로, 지급 완료 시점에 **「예정」으로 옮기고 거기서 5일을 센다.**

### 4-2. 진행 중 응모 — 「전부 아니면 전무」로 짜지 않는다

약관 제6조 2항의 「자동 철회」를 **할 수 있는 것만 하고, 못 하는 것은 남긴다.**

| 응모 상태 | 처리 |
|---|---|
| 심사중 · 승인(결과물 없음) | **자동 철회**(`cancel_application` 재사용) |
| **결과물이 승인됨** | ⚠️ **철회 안 함** — 취소 함수가 차단한다(§1-5 ㄴ). 이미 브랜드에 전달된 성과물이다 |
| **송금완료 정산이 있음** | ⚠️ **철회 안 함** — 서버가 차단한다(§1-5 ㄱ) |

⚠️ **철회 못 한 건이 있어도 탈퇴는 진행한다**(경우의 수 ①). 한 건이 막혔다고 전체가 멈추면 **회원이 영영 못 나간다.** 대신 **관리자 화면에 「철회 못 한 건 N개」를 표시**하고, **약관을 이 동작에 맞춰 고친다**(§4-5).

### 4-3. 사유 — 한 번만 묻고, 고르게 한다

- **기준 데이터로 관리**한다(`lookup_values` 새 종류 하나 — 취소 사유와 같은 방식). 항목은 운영팀이 화면에서 늘린다
- **선택 1개 + 자유 입력(선택)**. ⚠️ **여러 개 고르게 하거나 긴 설문으로 만들지 않는다** — 떠나는 사람은 끝까지 안 한다(경우의 수 ⑥)
- **자유 입력은 필수가 아니다.** 「기타」를 고른 경우에만 권한다

### 4-4. 화면

**회원 쪽 — 확인창 하나를 화면 하나로 바꾼다**

```
탈퇴 안내

 · 진행 중인 응모 2건이 자동으로 취소됩니다
 · 받지 못한 보수 2건(¥6,500)이 있어, 지급이 끝난 뒤 처리됩니다
 · 탈퇴 후 5일이 지나면 정보가 지워지고 되돌릴 수 없습니다
 · 세금 신고 때문에 지급 기록은 5년간 보관됩니다

 떠나시는 이유를 알려 주세요
  ( ) 캠페인이 잘 안 맞아서    ( ) 응모해도 잘 안 돼서
  ( ) 앱이 불편해서            ( ) 기타 [        ]

              [ 취소 ]  [ 탈퇴하기 ]
```

⚠️ **되돌릴 수 없는 동작이므로 확인창 하나로 끝내지 않는다**(경우의 수 ⑧). **무엇이 사라지는지 먼저 보여준 뒤** 누르게 한다.
⚠️ **LINE 안내 문구를 지운다**(결정 2). 문의가 필요하면 **자주 묻는 질문에 탈퇴 항목을 넣어** 그쪽으로 보낸다.
⚠️ 인플루언서 화면이므로 **일본어**이고 **초등학생 눈높이**로 쓴다.

**관리자 쪽 — 두 자리에 붙인다**

| 자리 | 무엇 |
|---|---|
| **인플루언서 상세 모달 「상태 관리」** | 탈퇴 상태·신청일·사유·예정일. 기존 패널에 한 줄 추가 |
| **인플루언서 목록 상태 필터** | 「탈퇴 신청」으로 걸러 보기 + 목록에 배지 |

⚠️ **전용 페인을 새로 만들지 않는다** — 인플루언서 관리에 이미 상태 관리·필터·이력이 다 있다. 거기 얹는 편이 운영자가 찾기 쉽다.

### 4-5. 약관·방침 정합 (C)

| 문서 | 지금 | 고칠 방향 |
|---|---|---|
| **약관 제6조 2항** | 「진행 중 캠페인 신청은 **자동으로 철회**」 | 「**철회 가능한 신청은** 자동 철회됩니다. **결과물이 승인되었거나 보수 지급이 완료된 신청은 철회되지 않습니다**」 |
| **약관 제6조 1항** | 「언제든지 탈퇴 신청」 | 유지 + 「**미지급 보수가 있으면 지급 완료 후 처리**됩니다」 |
| **방침 보유기간** | 「탈퇴일로부터 5일」 | 유지 — **이제 탈퇴일이 기록되므로 지킬 수 있다** |

⚠️ **회원에게 불리한 변경인가** — 제6조 2항은 「자동 철회」 범위가 **좁아지는** 것이라 **불리한 변경으로 본다**(보수적 판정). **사전 통지 30일** 대상이다(`.claude/rules/policy.md`).
⚠️ **시행일 규칙**(`.claude/rules/release-timing.md`) — **문서는 미리 고치지 않는다. 기능 배포에 맞춘다.** 코드는 미리 배포해도 되고, **집행은 시행일부터**.

### 4-6. 데이터베이스

> **마이그레이션 3개** (번호는 만드는 시점에 확정 — 미리 박지 않는다). 상대 순서: **①→②→③**

| # | 무엇 | 왜 |
|---|---|---|
| **①** | **탈퇴 신청 표** 신설 — 회원·상태·사유·자유입력·신청 시각·예정일·완료 시각·처리자 | 별도 표로 두는 이유: 한 사람이 **탈퇴했다 재가입 후 또 탈퇴**할 수 있어 이력이 여러 줄이 된다. 인플루언서 표에 칸으로 두면 마지막 것만 남는다 |
| **②** | **신청 함수** — 본인만, 사유 필수, 미지급 있으면 「대기」·없으면 「예정」, **철회 가능한 응모만 취소** | 부분 실패를 허용해야 하므로(§4-2) 함수 안에서 건별로 처리하고 **결과를 돌려준다** |
| **③** | **사유 기준 데이터** 시드 | 운영팀이 화면에서 늘릴 수 있게 |

⚠️ **인증 계정을 지우는 것은 이 범위에 넣지 않는다**(§5 ②). 「완료」 상태로 **로그인을 막는 것**까지가 이번 범위다.
⚠️ **파기 실행(5일 뒤 자동 삭제)도 이번 범위 밖**(§5 ③) — 무엇을 언제 지울지가 항목마다 달라(경우의 수 ③) 별도 설계가 필요하다.

## 5. 사용자 확인 필요

**① 알림·메일을 언제부터 끊는가?** 「대기」·「예정」 상태에서도 캠페인 홍보 메일이 계속 가면 이상하다. 다만 **정산 관련 안내는 가야** 한다(돈을 받아야 나가므로).
- (가) 신청 즉시 **홍보성만** 끊고 정산·마감 안내는 유지 ← 기획 권고
- (나) 신청 즉시 전부 끊음 — ⚠️ 지급 안내를 못 받는다
- (다) 「완료」까지 그대로 — ⚠️ 떠나겠다는 사람에게 계속 광고가 간다

**② 「완료」 상태에서 인증 계정을 지우는가?**
- (가) **안 지우고 로그인만 막는다** ← 기획 권고. **되돌릴 수 있고**, 재가입 시 같은 이메일 충돌이 없다
- (나) 지운다 — 되돌릴 수 없고, 정산 기록이 남아야 하는 것과 부딪힌다(§1-5 ㅂ)

**③ 파기 실행(5일 뒤 자동 삭제)을 이번에 함께 만드는가?**
- (가) **다음 단계로 분리** ← 기획 권고. 항목마다 시점이 달라(5일/즉시/5년) 별도 설계가 필요하고, **잘못 지우면 되돌릴 수 없다**
- (나) 함께 만든다 — 범위가 두 배가 된다

**④ 재가입을 허용하는가?** 같은 이메일로 다시 가입할 수 있게 할지, 막을지. ⚠️ 허용하면 **탈퇴 → 재가입으로 위반 이력을 지우는** 우회가 생긴다(블랙리스트가 이메일 기준이므로).

**⑤ 약관 개정 시행일** — 사전 통지 30일이 필요하다(§4-5). 기능 배포와 시행일을 언제로 맞출지.
