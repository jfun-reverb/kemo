# 캠페인 「중단」 — 데이터를 남긴 채 운영을 동결하는 상태

**작성일:** 2026-08-12
**작성 세션:** 기획/설계
**계기:** 잘못 만들어진 캠페인(B0035-C009)을 중단하려 노출 토글을 껐으나, 관리자 동작이 그대로 열려 있어 조작 실수로 결과물이 인증될 위험이 남았다.

---

## 현재 상태 (2026-08-12, 코드·운영 데이터 직접 확인)

### 지금 「캠페인을 치우는」 수단은 두 가지뿐이다

| 수단 | 인플루언서 화면 | 관리자 동작 | 신청·결과물 데이터 |
|---|---|---|---|
| **노출 토글 OFF** (`status='expired'`) | 목록·직접 접근 차단 | **전부 열려 있음** | 그대로 |
| **보관 삭제** (`deleted_at`, 마이그레이션 254~258) | 완전 비노출 | (대상 없음) | **신청을 완전 DELETE → 결과물 연쇄 삭제** |

즉 **「데이터를 남긴 채 운영만 멈추는」 자리가 비어 있다.** 노출 토글은 아무것도 잠그지 않고, 보관 삭제는 증거까지 지운다.

### 관리자 동작이 캠페인 상태를 보는가 — 전부 안 본다

| 동작 | 캠페인 상태 확인 |
|---|---|
| 인플루언서 신규 응모 | ✅ 서버가 막는다 — 모집중이 아니면 거부(마이그레이션 326) |
| 신청 승인·반려·되돌리기 (`updateAppStatus`) | ❌ 정원 검사만 |
| 결과물 승인·반려 (`update_deliverable_status`, 마이그레이션 035) | ❌ 캠페인을 **참조조차 하지 않는다** |
| 대리 등록·영수증 수정 | ❌ |

### 잠금이 풀리는 경로 (이번 사건의 핵심)

신청이 반려·취소이면 결과물은 「검수 불필요」가 되어 검수 버튼이 전부 사라진다(`isCertExcluded`). **그런데 신청자 목록의 「되돌리기」를 누르면 심사중으로 돌아가 그 잠금이 즉시 풀린다.** 두 단계지만 한 화면 안에서 연쇄로 일어날 수 있다.

### 운영 실측 (2026-08-12)

노출종료·종료 캠페인 중 **미검수 결과물이 남은 캠페인 18개 / 결과물 38건**.

| 상태 | 캠페인 수 | 비고 |
|---|---|---|
| `expired`(노출종료) | 2개 | B0035-C009(8건, 이번 건) · **B0032-C002(7건)** |
| `ended`(종료) | 16개 | 각 1~4건, 합계 23건 |

→ **「노출 OFF면 전면 금지」를 택했다면 B0032-C002의 검수 7건이 막혔을 것이다.** 확인창 방식을 고른 근거가 실측으로 확인됐다.

→ ⚠️ **별개 문제 발견:** 종료된 캠페인 16개에 미검수 결과물 30건이 방치돼 있다. 인플루언서는 제출하고 답을 못 받은 상태다. 이번 작업 범위 밖이지만 별도 정리가 필요하다(§부수 발견).

### 이 제안과 충돌 가능성 있는 기존 동작

- **보관 삭제(「삭제됨」 탭)와 목적이 겹쳐 보인다.** 실제로는 다르다 — 삭제는 개인정보 즉시 파기, 중단은 보존이 목적이다. 두 탭이 나란히 생기므로 **이름과 안내로 구분이 분명해야** 한다.
- **낙관적 락(마이그레이션 275)** — 새 칸은 제외 목록에 없으므로 자동으로 보호 대상이 된다. 중단 처리가 `version`을 올리는데, 그 캠페인 편집 폼을 열어 둔 사람은 저장 시 충돌 안내를 받는다. 중단은 되돌릴 수 있는 동작이라 이 정도 마찰은 감수할 만하다(삭제와 같은 판단).
- **변경 이력 화이트리스트(265·266)** — 행사 칸 3개와 같은 판단으로 **넣지 않는다**(세 곳을 동시에 고쳐야 하는 위험). 중단은 `suspended_at`·`suspended_by`·`suspend_reason` 칸 자체가 기록이 된다.

## 의심·경우의 수 (규칙 B)

1. **중단하면 보상도 막힌다면 본말전도다.** 이번 캠페인은 중단하면서 **보상을 지급하려는** 상황이다. 정산 처리까지 잠그면 중단할수록 보상을 못 준다. → **정산 관련 동작은 차단 대상에서 뺀다.**
2. **문의 창구를 막으면 사과할 길이 사라진다.** 담당자가 지금 응모건 메시지로 사과·설명 중이다. 중단이 메시지를 막으면 그 대화가 끊긴다. → **응모건 메시지는 차단하지 않는다.**
3. **자동 파기가 돌면 증거가 사라진다.** 보관 삭제는 30일 뒤 자동 완전 삭제된다. 중단에 같은 규칙을 붙이면 **보상 분쟁이 끝나기 전에 결과물이 사라진다.** → **중단은 자동 파기 대상이 아니다.** 지우는 시점은 사람이 정한다.
4. **자동 상태 전이가 중단 캠페인에도 돈다.** `autoCloseCampaigns`·`autoEndCampaigns`가 목록 조회 때마다 도는데, 중단 캠페인의 status를 계속 바꾸면 의미 없는 변경과 `version` 증가가 쌓인다. → 전이 대상에서 제외.
5. **홍보 메일·다이제스트에 중단 캠페인이 실릴 수 있다.** 홍보 메일은 `active` 기준이라 대개 안 걸리지만, 운영현황·대시보드 집계에는 들어간다. 광고주 보고 수치가 중단된 캠페인을 포함하면 안 된다. → 집계 제외 지점을 함께 정리한다(보관 삭제가 마이그레이션 259에서 한 것과 같은 작업).
6. **[사용자 경험] 중단 버튼이 삭제 버튼 옆에 있으면 잘못 누른다.** 둘 다 더보기 메뉴에 들어가면 「중단」과 「삭제」가 나란히 놓인다. 결과가 완전히 다른데(보존 vs 파기) 이름이 비슷해 보인다. → **확인 모달에서 「데이터는 남습니다」/「즉시 파기됩니다」를 명시**하고, 삭제와 같은 재입력 확인 절차를 둔다.
7. **[사용자 경험] 왜 버튼이 없는지 담당자가 알아야 한다.** 「검수 불필요」가 안내 문구를 함께 띄우는 것과 같은 수준으로, 중단 캠페인에서도 **「이 캠페인은 중단되었습니다 — 사유」**를 화면 상단에 보여준다. 버튼만 사라지면 고장으로 오해한다.
8. **[사용자 경험] 인플루언서에게는 아무 변화가 없어야 한다.** 중단은 운영 내부 개념이다. 인플루언서 화면에 「중단」이라는 새 낱말이 나타나면 설명해야 할 것이 늘어난다. → 인플루언서 쪽은 **노출종료와 똑같이 동작**시키고 새 문구를 만들지 않는다.
9. **응모이력 진입은 열어 둔다.** 노출종료 캠페인은 응모이력에서 온 진입만 상세를 허용한다(「내가 신청한 게 사라졌다」 방지). 중단도 같게 둔다 — 다르게 두면 이번처럼 사과 중인 상대가 자기 응모 내역을 못 보게 된다.

### 의도가 모호해 확인이 필요했던 지점 → 결정

- **「완전 삭제」를 중단 상태에서 바로 할 수 있게 할지** → 아래 §설계 4 참조. 기존 완전 삭제 함수는 **보관 삭제된 캠페인만** 받으므로(`deleted_at IS NULL`이면 거부, 마이그레이션 257), 중단에서 바로 지우려면 별도 경로가 필요하다.

## 설계

### 1. 새 칸 3개 — `status` 값으로 넣지 않는다

`campaigns`에 아래를 추가한다. **`status`에 새 값을 넣지 않는 이유**는, status가 상태 배지·상태 탭·전이 규칙표·자동 전이·인플루언서 노출 조건에 모두 얽혀 있어 값 하나를 늘리면 손댈 곳이 열 군데를 넘기 때문이다. 보관 삭제가 `deleted_at`이라는 별도 칸을 쓴 선례를 그대로 따른다.

| 칸 | 뜻 |
|---|---|
| `suspended_at` | 중단 시각 (NULL이면 정상) |
| `suspended_by` | 중단한 관리자 |
| `suspend_reason` | 중단 사유 (필수 입력) |

「잘못 만들었다」와 「브랜드 사정으로 멈췄다」를 다른 상태로 나누지 않는다 — 화면에서 갈리는 동작이 같기 때문이다. 구분은 **사유 텍스트**가 한다.

### 2. 중단하면 잠기는 것 / 잠기지 않는 것

**잠근다 (관리자 동작)**

- 신청 승인·반려·되돌리기
- 결과물 승인·반려·되돌리기
- 결과물 대리 등록
- 영수증 인플레이스 수정

**잠그지 않는다 — 잠그면 중단의 목적을 해친다**

- **정산 처리** (§의심 1) — 보상을 주려고 중단하는 경우가 있다
- **응모건 메시지** (§의심 2) — 사과·설명 창구
- 조회·엑셀 내보내기 — 보상 근거를 확인해야 한다

**차단은 화면과 서버 양쪽에** 건다. 화면은 버튼을 감추고 안내를 띄우고, 서버 함수(`update_application_status`·`update_deliverable_status`·`admin_create_deliverable_proxy`·`update_receipt_admin`)는 중단 캠페인이면 거부한다. 화면만 막으면 이번처럼 「버튼이 없어졌을 뿐」이라 다른 경로로 뚫린다.

### 3. 인플루언서 화면 — 노출종료와 똑같이

- 캠페인 목록에서 제외
- 주소로 직접 열기 차단
- **응모이력에서 온 진입은 허용**(상세는 보이고 응모 버튼은 닫힘) — 노출종료와 동일 규칙
- 서버 응모 차단 트리거(마이그레이션 326)에 중단 조건 추가
- **새 문구를 만들지 않는다** (§의심 8)

### 4. 「중단됨」 탭 — 「삭제됨」 탭 패턴을 그대로 미러

캠페인 목록 상태 탭에 「중단됨」을 추가한다. 데이터 출처와 행 동작이 활성 목록과 달라 별도 렌더가 필요하다(「삭제됨」 탭이 이미 그 구조다).

| 동작 | 권한 | 결과 |
|---|---|---|
| **중단 해제** | 캠페인관리자 이상 | 세 칸을 비우고 원래 상태로 복귀 (status는 건드리지 않았으므로 자연 복귀) |
| **삭제로 보내기** | 최고관리자 | 기존 보관 삭제(`soft_delete_campaign`)를 호출 → 「삭제됨」 탭으로 이동, 신청·결과물 파기, 30일 뒤 자동 완전 삭제 |

⚠️ **중단에서 바로 「완전 삭제」하는 버튼은 두지 않는다.** 이유는 두 가지다. ①기존 완전 삭제 함수는 보관 삭제된 캠페인만 받는다(마이그레이션 257). ②중단은 **증거를 남기려고** 만드는 상태인데, 그 화면에 되돌릴 수 없는 파기 버튼을 나란히 두면 이번에 막으려는 종류의 실수가 그대로 재현된다. 지울 때는 「삭제로 보내기」로 한 칸 옮긴 뒤 기존 흐름을 타게 한다.

⚠️ **중단은 자동 파기 대상이 아니다** (§의심 3). 30일 예약 삭제는 보관 삭제된 것만 본다.

### 5. 집계·자동 전이에서 제외

- 자동 상태 전이(`autoOpen/Close/EndCampaigns`) 대상에서 제외
- 운영현황·대시보드 집계에서 제외 (보관 삭제가 마이그레이션 259에서 한 것과 같은 정리)

### 6. 정산 화면에서 중단 건을 구분해 보여준다

정산은 잠그지 않기로 했는데(§설계 2), **잠그지 않는 것과 구분 없이 섞이는 것은 다르다.** 정산 담당자가 그 행을 보고 송금해도 되는지 판단할 근거가 화면에 있어야 한다.

**현재 상태 — 두 화면 모두 캠페인 상태를 아예 모른다**

| 화면 | 캠페인에서 가져오는 것 | 상태 |
|---|---|---|
| 정산 목록 (`fetchSettlements`) | `campaign_no, title, brand, img1, recruit_type` | ❌ 없음 |
| 「과거 미등록」 (`get_past_unregistered_settlements`, 최신 정의 331) | 캠페인 번호·제목 | ❌ 없음 |

⚠️ **「과거 미등록」 화면이 특히 위험하다.** 거기에는 되돌릴 수 없는 **「송금완료 기록」** 버튼이 다중 선택과 함께 있다. 중단된 캠페인 건이 구분 없이 섞이면 한 번에 잘못 처리된다.

**할 일**

1. 정산 목록 조회에 캠페인의 **중단 여부**를 함께 가져온다
2. 「과거 미등록」 함수 반환에 같은 값을 추가한다 — ⚠️ **이 함수의 현재 유효한 원본은 331이다**(232→262→264→300→318→331로 이어졌다). 재정의할 때 **파일 번호가 가장 큰 정의를 베이스로** 삼는다. 과거에 옛 정의를 베이스로 써서 알림 잠금이 소실될 뻔한 전례가 있다
3. 목록 행에 **「중단」 배지**를 단다
4. **「송금완료 기록」 확인 모달에 경고 한 줄** — 선택한 건에 중단 캠페인이 섞여 있으면 몇 건인지 알린다. 막지는 않는다(중단하면서 보상하는 경우가 정상 흐름이므로)

**✅ 노출종료·종료에는 배지를 달지 않는다 — 실측으로 확정 (2026-08-12)**

| 정산이 걸린 캠페인의 상태 | 건수 | 비율 |
|---|---|---|
| `ended`(종료) | 189 | **92.6%** |
| `expired`(노출종료) | 15 | 7.4% |

정산은 인증 성공 뒤에 생기고, 인증 성공은 결과물 검수가 끝난 뒤다. 그 시점이면 캠페인은 이미 종료돼 있다 — **정산 목록의 열에 아홉이 「종료」다.** 배지를 달면 아무 정보도 주지 못하고, 정작 중요한 「중단」 배지가 그 속에 묻힌다.

이 프로젝트에서 이미 배운 것이다 — 채널 어긋남 감지 장치를 만들 때 「0건이면 아무것도 안 그린다」로 정한 이유가 「늘 빨간 게 있는 화면」으로 학습되면 진짜 경보를 놓치기 때문이었다.

노출종료(7.4%)도 달지 않는다. **중단 상태가 생기면 「노출종료」는 정상 수명의 끝만 뜻하게 되기 때문**이다(지금은 「정상 종료 후 내림」과 「중단」 두 뜻을 겸하고 있다). 다만 그러려면 아래 §설계 7(기존 중단 건 이관)이 함께 이뤄져야 한다.

> 부수 확인: 노출종료 캠페인의 정산 15건이 정상 처리돼 있다 — **「노출 OFF면 전면 금지」를 택했다면 이 15건 처리도 막혔을 것**이다(§설계 8 「노출 토글 OFF — 확인창만」의 근거 보강).

### 7. 기존에 노출 OFF로 중단해 둔 캠페인 이관

**중단 상태를 만들어도 과거에 노출 토글로 중단한 캠페인은 자동으로 옮겨지지 않는다.** 그대로 두면 「노출종료」가 계속 두 가지 뜻을 겸해, §설계 6에서 배지를 생략한 전제가 깨진다.

⚠️ **자동 판별은 불가능하다.** 노출종료 캠페인 중 어느 것이 「중단」이고 어느 것이 「정상 종료 후 내림」인지 시스템은 구분할 근거가 없다. 사람이 목록을 보고 골라야 한다.

**절차**

1. 기능 배포 후, 노출종료 캠페인 목록을 뽑는다
2. 운영자가 「중단」에 해당하는 것을 고른다 — 이번 B0035-C009는 확실한 대상이다
3. 고른 것만 중단 처리하고 사유를 적는다(예: 「브랜드 이미지 미제공으로 중단 — 2026-06 처리분 소급 정리」)

**이관 대상을 찾는 조회**

```sql
select c.campaign_no, c.title, c.recruit_type, c.deadline,
       count(distinct a.id)                                    as 신청,
       count(distinct a.id) filter (where a.status='approved')  as 승인,
       count(distinct d.id)                                    as 결과물,
       count(distinct s.id)                                    as 정산
from campaigns c
left join applications a on a.campaign_id = c.id
left join deliverables d on d.application_id = a.id
left join settlements  s on s.campaign_id  = c.id
where c.status = 'expired' and c.deleted_at is null
group by c.campaign_no, c.title, c.recruit_type, c.deadline
order by c.deadline desc;
```

⚠️ **소급 이관은 인플루언서에게 아무 통지도 보내지 않아야 한다.** 몇 달 전 끝난 캠페인이 지금 와서 알림을 만들면 「끝난 줄 알았는데 무슨 일이지」가 된다. 중단 처리 함수 자체에 알림이 없어야 하고(§설계 2에 알림 조항 없음 — 의도된 것), 소급 대상은 특히 그렇다.

### 8. 노출 토글 OFF — 확인창만 (전면 금지하지 않는다)

실측 근거로 전면 금지는 채택하지 않는다(§현재 상태 실측). 대신 **노출이 꺼진 캠페인에서 신청 상태·결과물 상태를 바꾸려 하면 확인창**을 띄운다.

> 이 캠페인은 인플루언서 화면에 노출되지 않는 상태입니다. 상태를 바꾸면 인플루언서에게 알림·메일이 나갈 수 있습니다. 계속할까요?

막지 않고 묻는다 — 이 프로젝트의 기존 패턴(구매 기간 밖 경고·채널 제거 확인·제품 금액 0 확인)과 같다.

### 데이터베이스 변경

마이그레이션 **5개** (번호는 개발 세션이 생성 시점에 확정):

1. `campaigns`에 칸 3개 추가
2. 중단·해제 함수 2종 (`is_campaign_admin()` 가드, 사유 필수)
3. 관리자 동작 서버 차단 — 신청 상태·결과물 상태·대리 등록·영수증 수정 함수에 중단 검사 추가
4. 응모 차단 트리거(326 계열)에 중단 조건 추가 + 운영현황·대시보드 집계에서 중단 제외
5. 「과거 미등록」 함수 재정의 — 반환에 중단 여부 추가 (§설계 6). ⚠️ **베이스는 331**(가장 큰 번호의 정의)

**①이 가장 먼저**이고, ③·⑤는 ① 이후여야 한다. 코드 배포보다 **데이터베이스를 먼저** 적용한다(칸이 없으면 화면이 깨진다).
