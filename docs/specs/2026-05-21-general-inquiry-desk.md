> **작성일:** 2026-05-21

## 0. 한 줄 정의

응모이력 카드가 아니라 **마이페이지의 「お問い合わせ」 메뉴**로 들어가는, **특정 응모 건과 무관한** 인플루언서↔관리자 양방향 메시지. 관리자는 응모건 메시지와 **같은 받은편지함**에서 응대한다.

---

## 1. 범위

- **포함:**
  - 인플루언서: 마이페이지 「お問い合わせ」 진입 → FAQ(응모건 무관 카테고리) 먼저 → 안 풀리면 직접 문의(메시지)
  - 관리자: 받은편지함(`#adminPane-messages`)에 「일반 문의」 구분 추가 — 응모건 메시지와 한 화면
  - 기존 메시지 기능(첨부·압축·회수·강제숨김·응대완료·읽음·rate limit) 재사용
- **제외:**
  - 가입 전·로그인 불가 문의 → 구조상 LINE/이메일 폴백 유지(채널 역할 사양서 §7)
  - 한국어↔일본어 번역(별도)
  - 일반 문의 전용 신규 알림 종류는 기존 `message_received` 재사용 검토(§6)

## 2. 핵심 설계 결정

| 항목 | 결정 | 이유 |
|---|---|---|
| 진입점 | **마이페이지 「お問い合わせ」 메뉴** (+ GNB 햄버거에도 노출 검토) | 응모건과 무관하므로 응모이력 카드가 아닌 독립 진입 |
| FAQ 우선 | **진입 시 일반 카테고리 FAQ 먼저** | LINE 일반 문의의 상당수도 셀프 해결 가능(자동응답 FAQ 재사용) |
| 스레드 단위 | **인플루언서당 1 스레드** | 일반 문의는 응모건처럼 여러 개로 쪼갤 필요 없음. 한 사람=한 대화 |
| 관리자 화면 | **기존 받은편지함에 통합** (별도 페인 아님) | "창구 하나로 통합"이 목표. 응모건 메시지와 같은 화면에서 응대 |
| 기능 재사용 | 첨부·회수·숨김·응대완료·읽음·rate limit **그대로** | 응모건 메시지와 정책 동일 |
| 운영 배포 | **응모건 메시지 운영 배포(약관 D-7 통지)와 함께 또는 직후** | LINE 전환 문구도 이때 동시(채널 역할 §6) |

## 3. 인플루언서 화면 흐름

```
마이페이지 → 「お問い合わせ」
   │
   ├─ 메시지 0건 → 일반 FAQ(계정·정산·기타) 먼저 + [直接お問い合わせ]
   │
   └─ 메시지 1건+ → 기존 대화 스레드
        └─ 하단 입력창에서 추가 문의 (텍스트 + 이미지 첨부, 응모건 메시지와 동일 UX)
```

- 게시판형 풀스크린 모달 — 응모건 메시지(`messaging.js`)의 모달·압축·회수 로직 재사용
- 응모건 메시지와 시각적으로 동일하되, **상단에 "응모건 상태 한 줄"은 없음**(특정 응모건이 아니므로). 대신 "운영팀 문의" 헤더

## 4. 관리자 화면 흐름

- 받은편지함(`#adminPane-messages`)에 **「일반 문의」 필터/구분** 추가
  - 기존: 캠페인 선택 → 응모건 스레드 목록
  - 추가: 「일반 문의」를 고르면 인플루언서별 일반 문의 스레드 목록
- 스레드 열면 응모건 메시지와 동일한 답장·응대완료·숨김 UI
- **응모건 상태 한 줄(자동응답 FAQ §3-1)은 일반 문의엔 미표시** (특정 응모건 없음). 대신 그 인플루언서의 **기본 정보·최근 응모 요약** 정도를 보조로 노출 검토(v2)
- 미응대 배지: 응모건 미응대 + 일반 문의 미응대를 **합산**해 사이드바에 표시(통합 목표)

## 5. 데이터 모델 — ✅ 확정 (2026-08-19)

> **확정: D안 — `application_messages` 를 재사용하되 「추가만 하고 고치지 않는다」.**
> 새 칸(`influencer_id`) · 새 정책 · 새 함수만 더하고, **살아 있는 정책·함수 본문은 편집하지 않는다.**
> 결정 주체: `reverb-supabase-expert`(2026-08-19). ⚠️ **5월의 잠정 권고(B 별도 표)를 뒤집은 것** — 아래 「왜 뒤집혔나」 참조.

### 5-1. 왜 5월 권고(B)를 뒤집었나 — 전제가 깨져 있었다

5월 권고의 근거는 「**운영 대기 중인** 구조를 안 건드리는 게 안전하다」였다. 그런데 **응모건 메시지는 2026-05-28 운영 배포됐고 석 달간 계속 자랐다.**

| 5월 | 2026-08-19 실측 |
|---|---|
| 운영 대기 중 | **운영 가동 중**(실사용자 대화가 살아 있다) |
| — | 원격 함수 **12개** |
| — | **자동 번역**(마이그레이션 235 — 웹훅 + 서버 함수) |
| — | 숨김 가드(315) · 발신 제한(323) · 발신자 식별(326) |

**→ B(별도 표)는 복제할 것이 훨씬 늘었고, A(기존 표 확장)는 운영 중인 표를 고치는 일이 됐다. 둘 다 나빠졌다.**

### 5-2. D안이 공짜로 얻는 것 (실측)

| 얻는 것 | 왜 |
|---|---|
| **숨김·복구·회수 함수 3개** | **메시지 자체의 식별자만 보고 동작**한다 — 응모 유무와 무관. **코드 0줄** |
| **자동 번역** | 웹훅도 서버 함수도 **표 이름과 삽입 사건만** 본다. **추가 설정 0건** ⚠️ B안이면 개발·운영 **두 대시보드에서 손으로** 웹훅을 새로 등록해야 하는데, 이 저장소는 대시보드 설정이 코드에 안 남아 **잊기 쉬운 작업**이다 |
| **고쳐야 할 살아 있는 함수** | **정확히 1개**(아래 5-4 ③) |

### 5-3. 안 고른 안

- **A(기존 표 확장)** — 「누가 이 메시지의 주인인가」 판정을 **이미 쌓인 모든 행에 대해 다시 정의**해야 한다. 살아 있는 함수 5개 본문 + 정책 1개를 **고쳐 써야** 한다. ⚠️ 오늘 이 저장소가 겪은 사고(마이그레이션 312)는 **기존 조건문을 편집**하다 난 것이다.
- **C(스레드 추상화)** — 12개 함수·뷰·정책 **전부**를 다른 구조로 옮긴다. 이번 목적에 비해 범위가 압도적이고, 5월 사양서도 스스로 경계했다.
- **B(별도 표)** — 안전하지만 5-2 의 이점을 **전부 포기**한다.

### 5-4. ★ 구현 규율 — 「권고」가 아니라 **의무**

이게 깨지면 D안의 안전성 근거 자체가 무너진다.

**🔴 ① 새 정책은 반드시 「응모가 없는 행」으로 못 박는다** (2026-08-19 기획 세션 추가 — 데이터베이스 판단에 없던 항목)

접근 정책은 같은 표·같은 동작이면 **「또는」으로 합쳐진다.** 이게 D안의 안전 근거이면서 **동시에 가장 큰 함정**이다 — **느슨한 정책 하나가 엄격한 정책을 통째로 무력화한다.**

현재 정책(315)은 이렇다:
```
숨겨지지 않았고 · 회수되지 않았고 · 본인 응모건일 것
```
⚠️ **새 정책에 「응모 식별자가 비어 있을 것」 조건이 없으면**, 그 새 경로로 **기존 응모건 메시지까지 읽힌다.** 315 가 오늘 막 좁혀 놓은 것이 **되돌아간다.**
⚠️ **새 정책에도 「숨김·회수 가드」를 똑같이 넣는다.** 안 넣으면 일반 문의에서는 숨긴 글이 보인다 — **같은 조항인데 한쪽에만 가드가 붙는** 형태다.
⚠️ **기존 행에 `influencer_id` 를 백필하지 않는다.** 백필하면 위 두 조건이 없을 때 사고 범위가 전체로 커진다.

**② 기존 정책 문장은 단 한 글자도 편집하지 않는다** — 넓히려면 **새 정책 문을 따로** 만든다(표·저장소 양쪽).

**③ 기존 함수 본문은 편집하지 않는다** — 일반 문의는 기존 함수를 **아예 호출하지 않고 옆에 새 짝**을 만든다. **딱 하나 예외**: 관리자 안읽음 집계 함수는 응모 식별자로 묶는데 **빈 값이 하나의 묶음이 되어 여러 사람의 문의가 뒤섞인 유령 행**이 생긴다 → **「응모가 있는 행만」 방어 조건 한 줄**을 더한다.

**④ 응대완료 표는 재사용 불가** — 그 표는 **기본키 자체가 응모 식별자**다. 빈 값은 기본키가 될 수 없다 → **새 표**를 만든다.

**⑤ 관리자 받은편지함 목록도 재사용 불가** — 그 뷰는 **응모 표를 기준으로** 메시지를 곁들이는 구조라, 응모 없는 메시지는 **절대 안 잡힌다** → 일반 문의 목록은 **인플루언서 표 기준으로 새로** 짠다.

**⑥ 첨부 파일 폴더 규칙도 재사용 불가** — 지금 경로가 **응모 식별자를 폴더 이름**으로 쓴다 → 다른 폴더 규칙 + **새** 저장소 정책(기존 정책 미편집).

**⑦ 감사용 계정 흔적 청소 함수**에 일반 문의 삭제 조건 한 줄을 더한다.

**⑧ 적용 후 검증은 실제 로그인 브라우저에서** — 이 표의 접근 정책은 **관리 도구(서비스 키)로는 재현되지 않는다.** 인플루언서 계정·관리자 계정으로 각각 눈으로 확인한다.

**⑨ 직접 조회하는 두 자리 확인**(2026-08-19 기획 세션 확인) — 미리보기 쪽은 **응모 목록으로 거르므로 안전**하고 자체 가드도 있다. 관리자 발송시각 쪽은 **빈 열쇠가 하나 생긴다**(경미하나 화면에서 한 번 확인).

### 5-5. 마이그레이션 (번호는 만드는 시점에 확정 — **미리 박지 않는다**)

| | 무엇 | 선행 |
|---|---|---|
| **①** | 칸 추가(`influencer_id`) + 응모 식별자를 **필수 아님**으로 완화 — **백필 없음**(5-4 ①) | 없음 |
| **②** | **새 정책 2개**(표 조회 · 첨부 다운로드) — **기존 정책과 별도 문장**, 5-4 ① 조건 필수 | 없음 |
| **③** | 응대완료용 **새 표** | ① |
| **④** | **새 함수 4~5개**(문의 조회·발신·읽음·응대완료) | ①③ |
| **⑤** | 관리자 안읽음 집계에 방어 조건 한 줄 | 무관 |
| **⑥** | 감사용 청소 함수에 조건 한 줄 | 무관 |

### 5-6. 남은 설계 (개발 착수 전)

1. 일반 문의 **관리자 목록** 조회 설계(뷰 또는 함수, **인플루언서 표 기준**)
2. **첨부 폴더 규칙**과 저장소 정책
3. **알림 클릭 분기** — `ref_table` 값을 무엇으로 할지(화면 설계와 함께)

## 6. 기존 메시지 기능 재사용 + 알림

- **재사용:** 이미지 압축(`image-compress.js`), 첨부(Storage `application-message-attachments` 또는 신규 버킷), 25분 본인 회수, 관리자 강제 숨김 + 이력, 응대 완료 마킹, 개인별 읽음, rate limit(발신 100/h·회수 50/h)
- **알림:** 관리자가 일반 문의에 답장 시 `message_received` 알림 재사용(자동응답 FAQ·응모건 메시지와 동일 kind). ref_table은 일반 문의 식별자로 분기 — 알림 클릭 시 「お問い合わせ」 모달 오픈
- **메일 지연 큐:** 응모건 메시지 PR 4 정책(있으면) 동일 적용 — 별도 결정

## 7. FAQ 연계

- 일반 문의 진입 시 노출할 FAQ는 **응모건 무관 카테고리** (계정·프로필, 보수·정산 일반, 그 외) — 자동응답 FAQ(`faq_nodes`)에서 `relevant_stages IS NULL`(단계 무관) 항목 중심
- 응모건 단계 맞춤 노출(자동응답 FAQ §3)은 일반 문의엔 미적용(응모건 없음)
- 자동응답 FAQ의 카테고리를 **공유**하되, 일반 문의에서는 "신청·심사·결과물" 같은 응모건 종속 카테고리는 숨기거나 뒤로

## 9. 검증 계획

- 인플루언서: 「お問い合わせ」 진입 → FAQ 노출 → 직접 문의 발신 → 첨부·회수 → 관리자 답장 수신·알림
- 관리자: 받은편지함에서 일반 문의 스레드 응대 → 응대완료 → 미응대 배지에 합산 반영
- 권한: 본인 일반 문의만 조회(RLS), 관리자 전체 조회
- 신규 RPC 스모크 호출(메모리 규칙)
- 에이전트: supabase-expert(데이터 모델·RLS), reviewer, qa-tester
