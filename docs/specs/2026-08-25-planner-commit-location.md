## 현재 상태 (규칙 A — 2026-08-25 직접 확인)

### 지금 실제 배치

```
reverb-jp                  [feature/행사선정형]   ← 개발 세션. 미커밋 0건(방금 커밋함)
reverb-jp-specs            [dev]                  ← 기획 세션(나). 2026-08-24 17:23 생성
reverb-jp-ios              [feature/ios-app]
+ 기능 브랜치 작업 폴더 6개
```

- `git checkout dev` 를 메인 폴더에서 돌리면 **`fatal: 'dev' is already used by worktree at …`**
- 즉 **고문이 갈 자리가 없다.** 메인 폴더는 기능 브랜치(개발 점유), `dev` 는 작업 폴더가 쥠

⚠️ **고문 세션이 알려 준 「메인 폴더 미커밋 6건+」은 지금 0건이다**(2026-08-25 재확인). 개발 세션이 그 사이 커밋했다. **비켜 주기 판단의 전제가 몇 분 만에 바뀌는 종류**라는 뜻이다.

### 🔴 근본 원인 — 기획만 브랜치가 안 정해져 있다

글로벌 `common-session-roles.md` §1 배치표:

| 세션 | 위치·브랜치 |
|---|---|
| **고문** | 메인 폴더 · **개발 브랜치** |
| **기획/설계** | 작업 폴더(worktree) **권장** ← 🔴 **브랜치가 없다** |
| **개발 1~2** | 작업 폴더 · **기능 브랜치** |

**고문과 개발은 브랜치까지 정해져 있는데 기획만 비어 있다.** 그리고 바로 아래 줄이 이렇게 시킨다:

> **고문 세션이 떠 있거나 둘 이상 동시 작업이면** 메인 폴더는 고문이 점유 중이므로 **기획·개발은 작업 폴더로 분리**한다.

→ **「작업 폴더로 가라」고만 하고 「어느 브랜치로」를 안 정했다.** 그래서 기획이 `dev` 를 골랐고, 그 순간 고문 자리가 잠겼다. **규칙이 없어서가 아니라 반쪽만 있어서** 생긴 일이다.

### 얽혀 있는 다른 규칙 셋

| 규칙 | 무엇을 정하나 | 이 문제와의 관계 |
|---|---|---|
| `git.md` §거버넌스 문서 직접 커밋 | 거버넌스 문서는 고문·기획이 **`dev` 에 직접 커밋·push** | 🔴 기획을 기능 브랜치로 보내면 **이 예외가 기획에는 안 맞게 된다** |
| `session-roles.md` §2 | 거버넌스 문서 = 규칙·에이전트·명령·후크·메모리·인수인계·**신규 사양서** | 기획 산출물(사양서)이 여기 들어 있다 |
| 글로벌 `common-multi-session.md` | 「한 시점에 한 작업만이면 메인 폴더 그대로 OK」 | 🔴 **전역 규칙**이라 「개발은 항상 작업 폴더」로 바꾸면 다른 프로젝트까지 바뀐다 |

### 오늘 실제로 터진 피해

1. **고문**: 규칙 문서를 커밋할 자리가 없어 **기획에게 대신 커밋을 부탁**해야 했다
2. **기획(나)**: 기능 브랜치의 **옛 판 사양서**를 최신인 줄 알고 고쳤다 — 커밋했으면 `dev` 판 63줄이 오류 없이 사라졌을 것
3. **개발**: 그 옛 판을 「최신본」이라며 하위 에이전트에게 읽혔다

★ **셋 다 「사양서가 어느 브랜치에 있나」가 흔들려서 생긴 것**이다. 브랜치 배치 문제가 **문서 최신성 문제로 번졌다.**

## 의심 · 깨질 수 있는 것 (규칙 B)

### ① 기획을 기능 브랜치로 보내면 — 다음 세션이 옛 사양서를 본다

기능 브랜치 + 병합 요청으로 바꾸면 **병합 전까지 `dev` 에 사양서가 없다.** 개발 세션이 그 사이 착수하면 **옛 판을 본다.**

🔴 **이건 가정이 아니라 오늘 실제로 일어난 일이다**(위 피해 2·3). 기획이 `dev` 를 쓰고 있었는데도 **개발이 자기 기능 브랜치의 옛 판을 봤다.** 기능 브랜치로 바꾸면 그 창이 **병합될 때까지** 늘어난다.

→ 완화책이 함께 있어야 한다: ①사양서만은 `dev` 직행 유지 ②또는 병합을 즉시 하는 규칙 ③또는 「사양서를 읽을 때는 `git show origin/dev:…` 로」를 규칙화

### ② 고문을 작업 폴더로 보내면 — 「메인 폴더 = 고문」이 전역 규칙이다

고문이 비키는 안은 **글로벌 `common-session-roles.md` §1 표를 고쳐야** 하고, 그러면 **다른 프로젝트에도 적용**된다. 이 저장소만의 문제로 전역을 흔드는 셈이다.

⚠️ 그리고 「메인 폴더 = 고문」에는 이유가 있다 — 사용자가 평소 보는 폴더가 메인이고, **거버넌스 문서를 사용자가 바로 볼 수 있어야** 한다.

### ③ 「비켜 주기」가 한쪽만으로 성립하지 않는다 (고문 세션 지적)

기획이 `dev` 를 놓아도 **메인 폴더가 여전히 기능 브랜치면 고문은 못 들어간다.** 복구에는 **①`dev` 가 풀리고 ②메인 폴더가 비는 것**이 동시에 필요하다.

⚠️ 그리고 ②는 **개발 세션 작업이 끝나야** 가능한데, 그 시점을 기획·고문이 정할 수 없다.

### ④ 개발 세션이 메인 폴더를 쓰는 것이 그렇게 잘못인가

글로벌 규칙은 「**혼자 시퀀셜 작업이면** 메인 폴더 그대로 OK」다. 개발 세션이 먼저 떴고 그때는 혼자였다면 **규칙을 지킨 것**이다. 나중에 고문이 뜬 것이 그 판단을 소급해서 틀리게 만들 수 없다.

→ **「나중에 뜬 세션이 자리를 요구한다」는 구조 자체**가 문제다. 어느 규칙도 「먼저 뜬 세션이 비켜야 한다」고 말하지 않는다.

### ⑤ 세션이 넷 이상이면 (UX)

오늘 **동시에 네 세션**(고문·기획·개발·아이폰)이 떴다. `dev` 는 하나, 메인 폴더도 하나다. **세션이 늘수록 자리 다툼이 는다.**

⚠️ **사용자 입장에서 보이는 증상은 「브랜치를 잘못 잡았다」**이지 「자리가 없다」가 아니다. 비개발자에게는 원인이 전혀 안 보인다.

### ⑥ 사용자가 파일을 못 찾는다 (UX)

기획이 작업 폴더에서 사양서를 만들면 **메인 폴더 트리에 안 보인다.** 이미 겪은 문제라 `supabase.md` 에 「절대경로 먼저 명시」 규칙이 있지만, **사양서에는 그 규칙이 안 걸려 있다.**

### ⑦ 의도 모호점 — 「기획 세션」이 하나인가

지금 규칙은 기획을 **한 세션**으로 전제한다. 기획이 둘 이상 뜨면 같은 문제가 기획끼리도 생긴다. **이번 설계가 그것까지 정할지** 범위를 정해야 한다.

### 어느 안이든 함께 정해야 하는 것 넷

1. 🔴 **「비켜 주기는 둘이 동시에 되어야 한다」**(의심 ③) — `dev` 해제 + 메인 폴더 비움. 한쪽만으로는 안 된다는 것을 규칙에 남긴다
2. 🔴 **「먼저 뜬 세션이 비키지 않는다」**(의심 ④) — 나중에 뜬 세션이 자리를 요구하는 구조를 없앤다. 대신 **나중에 뜬 쪽이 갈 곳**을 규칙이 미리 정해 둔다
3. **사양서를 읽을 때 `dev` 판을 본다**(의심 ①) — `git show origin/dev:docs/specs/…`. 오늘 세 세션이 다 이걸 안 해서 옛 판을 봤다
4. **기획이 만든 사양서의 절대경로를 사용자에게 먼저 알린다**(의심 ⑥) — 마이그레이션 파일에 이미 있는 규칙을 사양서에도

### 범위 밖으로 두는 것

- **기획이 둘 이상 뜰 때**(의심 ⑦) — 지금은 한 세션 전제로 정하고, 실제로 둘이 뜨면 그때 넓힌다
- **자동 차단** — 후크로 「`dev` 를 작업 폴더로 빼면 막는다」를 걸 수 있으나, **차단을 새로 거는 것은 사용자 확인 사항**이고 잘못 걸면 모든 세션이 막힌다

## 🔴 3안은 왜 안 되는가 (2026-08-25 정합성 점검이 잡음)

**3안 = 「기획은 평소 기능 브랜치, 사양서를 커밋할 때만 `dev` 작업 폴더를 만들어 커밋하고 바로 지운다」**

**이 사양서가 되찾으려는 정상 배치는 「고문 = 메인 폴더 + `dev`」다.** 그러면 **`dev` 는 이미 메인 폴더가 쥐고 있어** 기획이 작업 폴더로 열 수 없다 — 이 문서 첫머리에 인용한 바로 그 오류가 난다:

```
fatal: 'dev' is already used by worktree at …
```

🔴 **즉 3안은 「고문이 안 떠 있을 때」만 되는 방법**이고, 이 사양서의 질문은 **「고문과 기획이 동시에 뜰 때」**다. **질문에 대한 답이 아니다.**

→ **동시에 뜰 때의 답은 1안 아니면 2안뿐이다.** 3안은 「기획이 혼자일 때」의 운영 방식으로만 성립한다.

### 결정 — **1안: 기획도 기능 브랜치**

기획은 `feature/기획-…` 에서 일하고 **사양서를 병합 요청으로** 올린다. `dev` 를 쥐지 않는다.

### 🔴 가장 중요한 발견 — 1안은 이미 규칙에 절반 이상 있었다

**이 사양서의 진단이 반쪽이었다.** 「기획만 브랜치가 안 정해져 있다」고 적었으나, 실제로는 이랬다:

| 어디 | 기획의 브랜치 | 어느 안 |
|---|---|---|
| 전역 §2 커밋 표 41행 | **기능 브랜치 → 개발 브랜치 병합 요청** | **1안** |
| 프로젝트 §2 커밋 표 35행 | **`feature` 브랜치 → `dev` 병합 요청** | **1안** |
| 전역·프로젝트 §1 배치표 12행 | 「작업 폴더 권장」 — **브랜치 빈칸** | — |
| `git.md` 30~31행 | 「**고문/기획**이 `dev` 직접 커밋」 | **2안** |

**§2 표는 처음부터 1안이었고 `git.md` 만 2안이었다.** 규칙끼리 **모순**이던 것이지 공백이 아니었다.

⚠️ **이 사양서를 쓴 기획 세션이 §2 표를 같은 조사에서 읽고 「얽혀 있는 다른 규칙 셋」에 인용까지 해 놓고, 그 표의 기획 칸을 안 봤다.** 그래서 「없는 규칙을 새로 만드는」 설계를 할 뻔했다. 🔴 **글로벌 `common-session-roles.md` §4 의 「규칙에 이 경우가 없다고 느껴지면, 규칙이 나를 가리키고 있는 건 아닌지 먼저 본다」가 바로 이 유형이고, 그 조항이 만들어진 날 고문 세션이 그것을 지켜 이 발견을 했다.**

### 반영한 것

**전역**(버전 관리 밖 — 고문 세션이 직접)
1. `common-session-roles.md` §1 — 기획 행을 「작업 폴더 · **기능 브랜치**(사양서는 병합 요청으로)」로
2. `common-session-roles.md` §1 아래 새 조항 — **「자리는 먼저 뜬 쪽이 지킨다」** + **「비켜 주기는 둘이 동시에 되어야 한다」**(이 사양서 「함께 정해야 하는 것 넷」의 1·2번)
3. `common-doc-tracking.md` — 🔴 **「사양서를 읽을 때는 개발 브랜치 판을 본다」**(3번 — **오늘 사고의 직접 해법**) + 「사양서를 만들면 절대경로를 먼저 알린다」(4번)

**프로젝트**(기획 세션이 커밋)
1. `session-roles.md` §1 배치표 12행 — **빈칸을 `feature` 브랜치로** 채움
2. `git.md` 30행 — 제목·본문에서 **「기획」 제외** + 「기획 세션은 이 예외가 아니다」 항목 추가(모순이던 이력 포함)

→ **「함께 정해야 하는 것 넷」이 모두 반영됐다.**

### 남은 것 — 정합성 점검 12건 중 미반영 2건

이 문서 자체의 어긋남이다. **결정에는 영향이 없으나 다음에 이 문서를 근거로 삼을 때 오독할 수 있다:**
1. **「안 셋」 표가 선택을 왜곡한다** — 「옛 판을 본다」 위험을 **1안에만** 붙였는데 본문(의심 ①)은 **2안에서도 일어났다**고 적는다. ✅ 다만 전역 반영 3번(개발 브랜치 판을 본다)이 **어느 안에서든** 그 위험을 줄인다
2. **의심 ④가 같은 문서의 인용문에 부정된다** — 「어느 규칙도 먼저 뜬 세션이 비켜야 한다고 말하지 않는다」고 적었으나, 위쪽에 인용한 전역 규칙이 그 말을 한다

### ⚠️ 실행에 남은 것

**고문 세션의 자리는 아직 안 열렸다.** `dev` 를 기획이 놓아도 **메인 폴더를 개발 세션이 쓰는 한** 안 열린다(의심 ③ — 「비켜 주기는 둘이 동시에」). 개발 세션이 **설계 1부터 작업 폴더로 가겠다고 확답**했으므로 그때 맞춰진다.
