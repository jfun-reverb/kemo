## 3. 결정 — Client 페이지 화면 코드 규칙 (브랜드 §15 형식을 따른다)

**형식**: `단계 기기+페이지-화면+상태_이름 (설명 … · 구현 중 YYYY-MM-DD) (업데이트 YYYY-MM-DD HH:MM)` — 예) `현행 c05-05_응모 시트 (업데이트 2026-10-15 18:25)` · `현행 c05-06_응모 완료 모달 — 리뷰어형 (자동 승인 · … · 구현 중 2026-10-16) (업데이트 2026-10-16 11:30)`. 「구현 중 날짜」는 이름 괄호 설명의 맨 끝 항목이고 업데이트 일시는 그 뒤 별도 괄호

| 자리 | 값 | 뜻 |
|---|---|---|
| 단계 | `현행` · `시안` · `보류` | **현행** = 지금 운영 중인 인플루언서 앱 동작을 그대로 그린 것, **또는 사용자가 확정해 구현 중인 화면**(이름 괄호 설명 맨 끝에 「구현 중 날짜」를 붙이고 운영 반영 뒤 뗀다 — 위 형식 줄 · 2026-10-16 사용자 결정). **시안** = 아직 확정되지 않은 초안. 보류 = 어느 단계에 넣을지 정하지 않은 화면. 브랜드 페이지의 `1차`·`2차`와는 다른 축 |
| 기기 | `c` | 인플루언서 앱(클라이언트 · 휴대폰 폭 390). 브랜드 페이지의 `bw`·`bm`·`a`(2026-10-15 기획 세션이 w·m 에 b 를 붙임) 와 겹치지 않게 따로 둔다 |
| 페이지(햄버거 메뉴 기준) | `01`~`09` | 01 회원가입 · 02 로그인 · 03 비밀번호 찾기 · 04 홈 · 05 캠페인(목록·상세·응모 시트) · 06 마이페이지(응모이력·기본정보·SNS·배송지·PayPal·비밀번호·메일 수신) · 07 활동관리(결과물 제출) · 08 문의(메시지·자주 묻는 질문) · 09 알림 |
| 화면 | `00` · `01~89` · `90` · `91`(둘 이상이면 `92`·`93`…) · `95` | 브랜드 §15와 같다(첫 화면 · 열리는 화면 · 토스트 · 상태 모음 — 한 페이지에 둘 이상이면 92·93… 차례로 · 메일) |
| 상태 | `a`·`b`… | 같은 화면의 다른 상태 |

**정하는 법**(브랜드 §15와 같다): 화면이 **어느 페이지에서 열리는가**로 번호를 정한다 — 응모 시트는 상세에서 열리므로 `c05`, 응모 취소 페이지는 응모이력에서 열리므로 `c06`. 모달·시트·토스트 용어도 같다.

**언어**: 화면은 앱의 **한국어 모드(ko.js)** 로 그린다(사용자가 읽을 수 있게 — 2026-10-15 사용자 지시 「한글화면으로」). 실제 인플루언서에게는 같은 화면이 일본어(ja.js)로 보인다. 설명 패널의 단추·문구는 「한국어(日本語)」로 적는다. 캠페인 제목·본문은 브랜드가 적은 데이터라 일본어 그대로.

**운영 캡처와 색**: 「(운영 캡처)」가 붙은 화면은 2026-10-15 운영 서버 그대로. 새로 그린 화면은 그 캡처 값(분홍 #C878A3 · 검은 머리띠 · Noto Sans KR/JP)에 맞췄다.

**번호 체계 변경(2026-10-19 사용자 결정)**: 회원가입·로그인·비밀번호 찾기를 앞 번호로 옮기고 나머지를 뒤로 밀었다. 옛 → 새: 01 홈 → 04 · 02 캠페인 → 05 · 03 마이페이지 → 06 · 04 활동관리 → 07 · 05 로그인·회원가입·비밀번호 찾기 → 01 회원가입 · 02 로그인 · 03 비밀번호 찾기 · 06 문의 → 08 · 07 알림 → 09. 화면 번호는 그대로 두고 페이지 번호만 바꿨다(예: 옛 c02-05 응모 시트 → c05-05). 이 문서·피그마·관련 사양서의 코드는 모두 새 번호로 고쳤다. ⚠️ 이날 이전 커밋 메시지·병합 요청 본문의 코드는 옛 번호다.

피그마 Client 페이지 맨 위 「화면 이름 읽는 법 (Client — 인플루언서 앱)」 상자(피그마에 실제로 적힌 이름)가 같은 내용이다 — 규칙을 바꾸면 **둘을 함께** 고친다.

## 4. 의심·경우의 수 (규칙 B — 그리면서 드러난 것)

§1~§6 범위에서는 설계 제안이 없다(§7 은 별도 설계). 다만 화면을 한 장씩 패널로 적다 보니 **지금 동작에서 인플루언서가 막히거나 헤맬 수 있는 자리**가 보였다. 각 패널의 「확인 필요」에 적었고 여기 모은다(§5). 그 밖에:
- **같은 화면이 두 언어**라 한국어 그림으로 판단한 뒤 일본어 문구도 같이 봐야 한다(ko.js 와 ja.js 가 뜻은 같아도 길이가 달라 줄바꿈이 다르다).
- **행사(방문 예약) 캠페인은 같은 시트·모달을 재사용**하면서 줄을 숨긴다 — 행사(방문 예약) 흐름은 이번 범위 밖(§2 「범위 밖」)이라 행사 쪽 모양은 담지 않았다.

## 5. 확인 필요 (사용자 판단 — 패널 「확인 필요」 모음)

1. **운영 분홍 vs 개발 흑백** — 개발서버는 회원 앱 스타일 통일(2026-10)로 검정 강조다. 운영 반영 뒤에는 이 그림의 분홍이 검정이 된다. 그림을 그때 다시 캡처할지.
2. **로그인 뒤 보던 캠페인으로 돌아오지 않는다**(c05-02) — 로그인·가입을 마치면 홈. 초대 전용 행사에만 되돌아오는 장치가 있다.
3. **필수 정보 부족 → 「마이페이지」가 응모이력으로 떨어진다**(c05-03) — 비어 있는 폼(기본정보·배송지·PayPal)으로 바로 보내지 않아 인플루언서가 햄버거에서 찾아야 한다.
4. **심사중 카드를 누르면 상세로 가는데 할 일이 없다**(시딩·방문형만 — 그림은 c06-01 의 첫 카드, c06-00 에는 없다) — 버튼은 「응모 완료」뿐, 심사 상황 안내가 없다.
5. **「관리자에게 문의하세요」인데 문의 경로 안내가 없다**(c06-01a) — 카드의 메시지 단추가 그 길이다.
6. **취소 보충 설명 「필수」가 서버에 없다**(c06-02a) — 화면만 막는다. 서버 강화 여부.
7. **응모 시트에서 고친 배송지는 응모 행에만 저장**(c05-05) — 프로필은 그대로라 「고쳤는데 마이페이지는 옛 주소」로 느낄 수 있다.
8. **「그 밖의 저장 실패」 토스트 문구**(c05-90)는 서버 오류마다 달라 한 가지로 그리지 못했다.
9. **응모 완료 토스트 「응모 완료! 결과는 메일로 안내드립니다」가 리뷰어형과 어긋난다**(c05-05 · 옛 c05-90 — 2026-10-16 모음에서 뺌 · 2026-10-15 사용자 지적). 리뷰어형은 응모 즉시 자동 승인이라 「결과」를 기다릴 일이 없고, 토스트가 사라지면 남는 것은 하단 바 「활동 관리」 버튼뿐이다(접수 확인 메일·앱 알림 없음). 문구는 i18n 열쇠 `detail.applyComplete` 하나(ja·ko 두 벌)를 모든 모집 형식이 같이 쓴다 — 리뷰어형용 문구를 가르려면 형식별 열쇠가 필요하다. 운영팀 보고: 리뷰어로 응모한 회원이 「바로 구매해도 되는지, 승인을 기다려야 하는지」 문의하는 일이 잦다(2026-10-15 사용자 전언). → **§7 에서 설계·확정**(이 항목만 예외로 이 문서 안에서 설계했다).

10. **시딩형 낙첨이 상세에서 보이지 않는다**(c05-91a ② — 2026-10-16 시딩형 묶음을 그리며 확인). 낙첨 응모도 「취소 아닌 내 응모」로 잡혀 하단 바가 심사중과 같은 「응모 완료」(눌리지 않음)다. 낙첨은 응모이력 배지와 다음 날 메일로만 안다.
11. **최소 팔로워 미달 모달(c05-07)의 OK 가 SNS 폼으로 가지 않는다** — 팔로워 수를 고치려면 햄버거에서 SNS 계정 폼을 찾아야 한다(③과 같은 유형).
12. **가구매를 완전히 접을지**(2026-10-16 사용자 질문에서) — 정규 경로로는 새 가구매 캠페인을 만들 수 없고(오리엔시트 발급 함수가 거부 · 캠페인 폼에 입력칸 없음) 운영에 가구매 캠페인·응모가 0건인데, **옛 가구매 카드를 발행하거나 캠페인을 복제해 가구매 표시가 생기는 길 둘**과 가구매 분기(활동 관리 2단계·인증 성공 판정·정산·엑셀)는 코드에 그대로 있다. 「진행하지 않는다」는 결정은 문서 어디에도 없다. 옛 카드 발행·복제 때 표시를 끊을지, 분기를 걷을지는 별도 결정 — 이 사양서는 가구매 전용 모달만 뺐다(판정은 중립 갈래로 — 결정 12).

13. **응모 취소·문의 답장은 회원에게 메일이 없다**(2026-10-19 메일 그림을 더하며 확인) — 응모 취소는 관리자 일일 메일에만 들어가고 회원 쪽 일일 메일(c06-95)에는 절이 없다. 문의(c08)에 운영팀이 답해도 앱 알림만 가고 메일은 없다(문의 쪽 서버 함수는 번역만 한다). 그래서 06·08 묶음에는 메일 그림을 넣지 않았다(보낼지 정하지 않은 메일은 그리지 않는다). **2026-10-19 사용자 결정: 지금은 시안도 그리지 않는다**(현재 동작만 그린 상태로 둔다). 나중에 보내기로 하면 새 메일이라 기획 사양서와 약관 영향 확인이 따로 필요하다.
14. **리뷰어형은 다음 날 메일에 같은 캠페인이 두 번 나온다**(c06-95) — 응모와 동시에 자동 승인돼 「신규 응모 접수」와 「응모가 승인되었습니다」 두 절에 함께 실린다.
15. **회원 메일 제목·꼬리말이 서로 다르다** — 일일 메일 제목 머리는 【REVERB】, 인증 코드·이미 가입됨 메일은 【REVERB JP】. 비밀번호 재설정 메일(c03-95)은 다른 회원 메일의 4줄 꼬리말(자동 발송 안내 · LINE · © JFUN · 사이트 주소)이 아니라 한 줄이다(그 양식의 실제 발송본은 인증 서비스 대시보드에 붙여 넣은 사본이라 저장소만 고쳐서는 안 바뀐다).
16. **비밀번호 재설정 링크 「1시간」 문구**(c03-95) — 브랜드 메일의 「24시간」 문구 변경 때 인증 설정을 바꾸면 이 문구도 같은 날 고쳐야 한다(`CLAUDE.md` 「브랜드 메일 링크 「24시간」 문구」 줄).

3. 상세를 먼저 다시 그린 뒤(`openCampaign` 을 **기다린 뒤** — 지금 성공 분기는 기다리지 않는다, 작업표 코드 대조 S4) 모달을 띄운다 — 뒤 화면의 하단 바가 다시 읽은 상태에 맞게 이미 바뀌어 있어야 한다(재조회 `approved` → 「활동 관리」 / `pending` → 「응모 완료」 / 재조회 실패 → 상세 다시 그리기가 정하는 값 그대로). 하단 바는 상세 다시 그리기가 **상태만 보고** 정한다 — ②의 가구매 가름은 **모달 갈래에만** 걸린다(가구매 표시 캠페인이 `approved` 면 하단 바 「활동 관리」 + 모달은 중립). 리뷰어형 조건은 결정 10 대로 — 「승인」만 보고 구매 안내로 가지 않는다.
4. 모달 틀은 공용 `.modal-overlay` 가 아니라 `#ageGateOverlay` 와 같은 `dialog-overlay` 방식 — 공용 Esc 처리기가 `.modal-overlay` 를 무조건 닫기 때문(작업표 코드 대조 S2, `ui.js` 는 관리자 공유라 고치지 않는다).
5. c05-06 갈래(`approved` + 리뷰어형 · 가구매 표시 없음): 체크 → 「확인」 활성 → 누르면 단추 잠금(문구 「처리 중…」 — c05-92 셋째 상태, `withSubmitLock`) → 확인 시각 저장 → 닫힘. **저장 실패해도 닫는다**(안내는 이미 봤다) — 오류만 기록(`logAppError`).
6. pending 갈래(주로 시딩·방문형 — 트리거가 없는 서버의 리뷰어형도 여기): ⑤와 같다 — 체크 → 「확인」 → 확인 시각 저장 → 닫힘. 형식별 안내 줄(시딩·방문형)만 형식을 본다. 중립 갈래(결정 7 의 셋): 체크 없음 · 「확인」·바깥 누름으로 닫힘 · 저장 없음.
7. 모달이 보이는 동안 브라우저 뒤로가기(iOS 밀어서 뒤로가기 포함)는 결정 9 대로 붙잡는다 — 모든 갈래(중립 포함).
8. 행사(방문 예약) 캠페인은 **제외** — 예약 함수·입장 티켓 흐름 그대로.

### 7-7. 의심·경우의 수 (규칙 B)
1. **채널에서 나오는 자리는 둘 — {구매처}·{게시 채널}**(결정 2 · 7-6 표. 날짜 자리 둘은 캠페인 일정) — {구매처} = 캠페인 채널 중 구매 가능한 몰(Qoo10 · LIPS · @cosme)이 있을 때만 그 이름, 없으면(Instagram·X 등 SNS 채널만) 7-6 의 「구매처 없음」 행 · {게시 채널} = 캠페인 채널(둘 이상이면 결정 11 과 같은 표기). 「Instagram에서 상품을 구매」 같은 문장이 나오지 않게 두 자리를 따로 채운다. 채널이 비어 있는 옛 캠페인은 7-6 의 「구매처 없음」·「채널 빈 캠페인」 행.
2. **마감 꼬리** — 고정 문구 「제출 마감 {날짜}」(7-6 표)를 ③ 줄 뒤에 붙인다. 제출 마감이 비어 있는 캠페인(NULL)은 마감 꼬리(7-6 「마감 꼬리」 행 — 별도 열쇠)를 붙이지 않는다(상세도 그때 줄을 안 그린다 — 작업표 코드 대조 S6) — 상세 정보 표의 낼 것별 긴 이름(영수증·게시물 인증샷 제출 마감일 / 영수증 제출 마감일)은 모달에서 쓰지 않는다(할 일 줄에 이미 무엇을 내는지 적혀 있다).
3. **재응모(취소 뒤 「재응모」)** — 같은 길이라 같은 모달. 확인 시각은 새 응모 행에 새로 남는다.
4. **저장은 됐는데 재조회가 실패** — 중립 갈래(결정 7). 승인 여부를 모르는데 「바로 구매」라고 하지 않는다.
5. **모달이 열린 채 세션 만료** — 확인 시각 저장이 실패한다 → 닫고 오류 기록(7-4 ⑤). 응모 자체는 이미 저장됐다.
6. **세 겹 안내** — 상세의 파란 페이백 안내·참여 방법 STEP·다음 날 당첨 메일과 겹친다. 모달은 「지금 할 일」 3단계 + 기간 경고 한 줄로 짧게 두고 토스트를 없애 겹침을 하나 줄인다. **기간 경고(「기간이 지난 뒤 구매는 페이백 제외」)는 일부러 반복한다** — 구매 직전 시점이고, 문의의 핵심이 「언제 사도 되나」이기 때문.
7. **낱말 전파** — 「당첨」·「심사」·「영수증 제출 마감」은 자동응답(FAQ)·일일 메일·활동 관리 화면에도 있다. 개발 착수 전 「낱말 전파 점검」으로 같은 말인지 본다(새 말을 만들지 않았으므로 바꿀 자리는 없을 것으로 본다 — 확인은 개발 몫).
8. **UX — 체크 강제(전 형식)** — 체크 없이는 못 닫게 하므로 모달을 「귀찮은 창」으로 느낄 수 있다. 내용이 3단계 이내·한 화면에 다 보이는 길이여야 한다(그림 기준 모달 높이 약 560px, 휴대폰 844 안에 든다).
9. **UX — 접근성** — 체크박스 누르는 영역 44px 이상(라벨 전체), 「확인」 비활성 상태는 흐림 38%.
10. **관리자 미리보기** — 상세 미리보기에는 응모 저장이 없으므로 모달이 안 뜬다. 영향 없음.
11. **메타 픽셀** — 신청 이벤트는 저장 직후 그대로(모달과 무관).
12. **시딩·방문형에는 구매가 없다** — 시딩은 브랜드가 등록 배송지로 제품을 보내고, 방문형은 장소에 간다. 그래서 06b 의 안내 줄은 형식별로 갈린다(결정 6). 시딩·방문형 응모자에게 「구매」라는 말이 보이면 리뷰어형과 헷갈린다.
