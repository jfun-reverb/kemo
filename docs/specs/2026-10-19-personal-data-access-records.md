# 개인정보 접속·제공 기록 — 관리자·브랜드의 열람·내려받기와 브랜드 제공

**작성일:** 2026-10-19 (기획 세션)
**상태:** 기획 — 개발 착수 전 (브랜드 페이지 1차와 함께)
**피그마:** 「레버브시딩_브랜드」 Admin 페이지 구역 「[1차] a13 개인정보 기록」(a13-00 · a13-01)

> 한 줄 요약: 인플루언서 개인정보를 **누가 언제 보거나 내려받았는지(접속 기록 1년)**와 **어느 브랜드에 무엇을 줬는지(브랜드 제공 기록 3년)**를 서버가 남기고, 관리자 설정 아래 새 메뉴 「개인정보 기록」에서 최고 관리자만 본다. 브랜드 페이지 출시 뒤 **브랜드에는 브랜드 페이지로만 제공**하고, 관리자 엑셀은 사내용이다.

## 1. 현재 상태 (2026-10-19, 직접 확인)

- **접속·제공 기록 장치가 없다** — 접속 기록 표 0건(`docs/PROJECT_CONTEXT.md` 36줄도 「`access_logs` 필요」로 미구현). 있는 것은 메시지 첫 읽음 표시(마이그레이션 144)와 리포트 공유 켬·끔·열람 횟수뿐, 보관·삭제 예약 없음(약관 사양서 `docs/specs/2026-10-19-brand-terms-draft.md` 「개발 확인 결과」 3번)
- **방침이 사실과 다르다** — `docs/PRIVACY_kr.md` 222줄 §9 3호 「접속 기록을 6개월 이상 보관」(한국 「개인정보의 안전성 확보조치 기준」 제8조는 **1년 이상**) · 225줄 6호 「관리자의 문의 열람·다운로드는 감사 로그로 기록」 — 받치는 장치가 없다
- **브랜드 제공 기록(일본 법 제29조, 3년)은 절반만 재구성 가능** — 승인·리포트 공유 켬·끔은 남지만, 어떤 항목을 언제부터 보였나·실제 조회·내려받기·열람자는 없다(약관 사양서 「개발 확인 결과」 2번). 운영팀이 엑셀을 메일로 보내거나 구글 시트로 공유한 제공은 **기록이 전혀 없다**
- 관리자 개인정보 엑셀: `dev/js/admin-excel.js` 의 `exportSelectedCampaignsApplicants` · `exportSelectedCampaignsDeliverables` · `exportCampaignApplicationsExcel` · `exportCampaignDeliverables` · `exportInfluencersExcel` · `exportEventTicketsExcel` — 화면이 브라우저에서 만든다(서버를 거치지 않는다). 민감정보 칸은 `influencers_admin_view`(212·213)가 권한에 따라 비운다
- 비슷한 감사 표 선례: 캠페인 변경 이력 `campaign_change_history`(265·266 — 읽기는 최고 관리자만, 쓰기는 트리거만)
- 함께 생기는 기록: 배송 리스트 전달·열람 기록(배송 리스트 사양서 §4-5, 피그마 a05-11)

### 충돌 가능성 있는 기존 동작
- 관리자 엑셀은 화면에서 만들어져 **서버가 내려받기를 모른다** — 기록하려면 화면이 내려받기 직전 서버 기록 함수를 불러야 한다(아래 §4-3)
- 브랜드 결과물 조회 함수 `get_my_brand_campaign_results`(현재 원본 547, 개발서버만)는 **조회 전용 — 쓰기 없음(열람 기록 없음)**으로 만들어져 있다. §4-3 「브랜드 조회 함수가 같은 거래 안에서 기록」을 하려면 이 함수를 547 베이스로 다시 정의해야 한다(배송 리스트 조회 함수는 아직 없음)
- 감사용(내부 점검) 계정 — 다른 집계에서는 빼지만 **기록에서는 빼지 않는다**(감사용 계정도 개인정보를 본다)

## 2. 의심·경우의 수 (반대론자 모드)

1. **(기술) 기록 실패** — 기록 함수가 실패했는데 내려받기가 되면 기록 없는 제공이 생긴다 → 관리자 엑셀은 **기록이 성공해야 내려받는다**(결정 5). 브랜드 쪽은 서버 조회 함수 안에서 기록하므로 같은 거래로 묶인다
2. **(UX) 운영팀 일상 업무** — 관리자 엑셀을 「사내용」으로 묶으면 지금처럼 브랜드에 엑셀을 메일로 보내던 일이 막힌다 → 배송 리스트·결과물 표가 브랜드 페이지에 모두 있으므로 대신할 길이 있다. 출시 때 운영팀 공지(시트 삭제 관문과 같은 공지)에 함께 넣는다
3. **(데이터) 기록 양** — 운영 데이터베이스가 가장 작은 사양(메모리 1GB)이라, 화면 열람마다 남기면 표가 빨리 커진다 → 범위를 「내려받기 + 브랜드 열람 + 관리자 민감정보 「보기」 + 관리자 문의 첨부 열기·내려받기」로 좁혔다(결정 2·6). 매일 보관 기간 지난 줄을 지운다
4. **(법률) 방침 §9 6호** — 「관리자의 문의 열람·다운로드는 감사 로그로 기록」인데 결정 2는 관리자 화면 열람을 남기지 않는다 → 문의 첨부 열기·내려받기만 넣고 방침 문장을 그 범위로 좁힌다(결정 6)
5. **(권한) 기록 자체가 개인정보** — 기록에 인플루언서 목록이 들어간다(「사람 보기」) → 최고 관리자만 읽고, 쓰기는 서버 함수만
6. **(데이터) 탈퇴 회원** — 탈퇴로 개인정보를 지워도 제공 기록은 3년 남아야 한다(법 의무) → 기록에는 회원 번호와 그때의 표시 이름만 남기고, 탈퇴 파기 함수가 이 표를 지우지 않게 한다(파기 대상에서 제외 — 개발 확인)

### 현재 구현과 어긋나는 지점
- 기록 장치가 없어 **충돌 없음 — 새로 만든다**. 어긋나는 것은 방침 §9 3·6호 문장(§5)

### 의도와 다르게 읽힐 수 있는 것
- 「접속 기록」 = 개인정보를 **보거나 내려받은** 기록(로그인 기록이 아니다)
- 「브랜드 제공」 = 브랜드 사용자가 브랜드 페이지에서 인플루언서 정보를 본 것·내려받은 것 + 운영팀이 배송 리스트를 전달한 것 + 브랜드 공개 설정을 켜거나 열을 바꾼 것

## 4. 설계

### 4-1. 화면 (피그마 a13)
- a13-00 「개인정보 기록」 — 탭 둘: 「브랜드 제공 (3년)」 · 「접속 — 열람·내려받기 (1년)」. 제공 탭의 거르기·줄은 §4-2 (접속 탭은 기간 · 누가 · 어디서만)
- a13-01 접속 기록 탭 모양 · 관리자 엑셀 첫 줄 「사내용」 표시
- 브랜드 상세 머리 「…」 메뉴에 「제공 기록」 항목 — 누르면 a13-00 제공 탭을 그 브랜드로 걸러 연다(같은 메뉴의 「결과물 열람 정지」 a03-12 와 나란히. 메뉴 펼친 모양은 따로 그리지 않음)
- 「사람 보기」 = 그 기록에 든 인플루언서 목록 — 본인이 「내 정보를 어느 브랜드에 언제 줬나」를 물을 때 답한다(일본 법 제29조·제30조)

### 4-2. 남기는 것 — 표 둘, 한 건은 한 표에만
| 표 | 무엇이 들어가나 | 칸 | 보관 |
|---|---|---|---|
| **브랜드 제공** | 브랜드 사용자의 배송 리스트·결과물 표 열람과 엑셀 내려받기 · 운영팀 배송 리스트 전달 · 브랜드 공개 켜기·끄기와 열 바꾸기 | 일시 · 브랜드 · 누가(계정) · 어떻게 · 캠페인 · 칸 목록 · 인플루언서 목록(회원 번호 + 그때 표시 이름) | 3년 |
| **접속** | 관리자 엑셀 내려받기 · 관리자 민감정보 「보기」 · 관리자 문의 첨부 열기·내려받기 | 일시 · 누가(관리자) · 어디서(화면·엑셀 종류) · 칸 목록 · 몇 명 | 1년 |

- 브랜드의 열람·내려받기는 **제공 표에만** 쓴다 — 3년 보관이라 접속 기록 1년 의무도 함께 채운다(같은 일을 두 표에 쓰지 않는다)
- 접속 표에는 인플루언서 목록을 남기지 않는다(몇 명만) — 관리자 행위는 「누가 무엇을 내려받았나」가 목적이고, 「내 정보를 어느 브랜드에 줬나」는 제공 표가 답한다
- 화면(a13-00): **제공 탭** = 기간 · 브랜드 · 누가 · 인플루언서 이름으로 거르기 + 「사람 보기」 / **접속 탭** = 기간 · 누가 · 어디서로 거르기(브랜드·인플루언서 거르기와 「사람 보기」 없음)

### 4-3. 기록하는 방법
- **운영팀 배송 리스트 전달**: 관리자 전달 함수 안에서 같은 거래로 기록
- **브랜드 공개 설정 변경**: 공개 켜기·끄기·열 저장 함수 안에서 같은 거래로 기록(누가·언제·무엇에서 무엇으로)
- **브랜드 쪽**: 브랜드 조회 함수(배송 리스트·결과물)가 결과를 돌려줄 때 같은 거래 안에서 기록한다. 엑셀 내려받기는 내려받기용 조회를 따로 부르게 해 그때 기록한다
- **관리자 엑셀**: 화면이 엑셀을 만들기 **직전** 서버 기록 함수를 부르고, 성공해야 파일을 만든다(결정 5)
- **문의 첨부**: 관리자 화면이 첨부를 열거나 내려받을 때 서버 기록 함수(첨부는 비공개 저장소 — 열 때 받는 임시 주소와 같은 자리에서)
- **민감정보 「보기」**: 관리자 화면이 숨긴 칸을 펼칠 때 서버 기록 함수
- 쓰기는 서버 함수만, 읽기는 최고 관리자만(캠페인 변경 이력과 같은 규칙)

### 4-4. 데이터베이스 (번호는 개발 세션이 정한다)
- 마이그레이션 2개 — ①기록 표 둘(제공 · 접속) + 기록 함수 + 읽기 정책 ②보관 기간 지난 줄 매일 삭제 예약. ①이 먼저
- 탈퇴 파기 함수가 이 표를 지우지 않게 확인(§2-6)

## 5. 약관·방침 영향
- 방침 §9 3호 「접속 기록 6개월 이상」 → **1년 이상**(결정 3) — 장치가 운영에 들어가는 날 같이 고친다(방침 개정안 「함께 볼 것」) — 방침 개정안 `docs/specs/2026-10-19-privacy-revision-brand.md` 「함께 볼 것」에 결정 반영
- 방침 §9 6호 「관리자의 문의 열람·다운로드는 감사 로그로 기록」 → 「관리자의 문의 첨부 열람·다운로드는 접속 기록으로 남깁니다」로 좁힌다(결정 6)
- 브랜드 약관 제8조(파기)와 관계없다 — 이 기록은 회사가 남기는 것
