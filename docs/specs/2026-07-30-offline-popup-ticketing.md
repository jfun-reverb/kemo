# 오프라인 팝업 방문 예약(티켓팅) + 입장 QR 확인

**작성일:** 2026-07-30
**행사:** 2026-08-28(금)~08-30(일) 뷰티 팝업 스토어
**작성 세션:** 기획/설계
**상태:** 설계 확정 — 결정 16건 반영, 정합성 점검 6라운드 완료. 남은 것은 운영 준비 자료 2건(§9)이며 구현을 막지 않는다. 개발 착수 대기

---

## 0. 요청 요약

1. 플랫폼에서 **오프라인 팝업 방문 예약(티켓팅)**이 가능한 캠페인을 만든다.
2. 3일 동안, 하루 8~16개 **타임(시간대)** 별로 방문객을 모집한다. *(요청 원문. 첨부한 표는 날짜별로 구조가 달라 실제 해석은 §2-9 참조)*
3. 신청이 확정된 방문객에게 **개인을 식별할 수 있는 QR 코드**를 발급한다.
4. 행사장 입구에서 운영진이 **노트북 또는 휴대폰 카메라로 QR을 스캔**하면 ① 우리 플랫폼 가입자인지 ② 어느 날 몇 시 타임으로 예약했는지가 확인된다.
5. 스캔되면 **방문 기록**이 남고, 행사 종료 후 **방문객 리포트**를 만들 수 있다.
6. 우선 **주요 필수 기능만 가볍게** 만들어 테스트한 뒤, 될 것 같으면 보강한다.

### 가능 여부 결론

**가능하다.** 단 지금 플랫폼은 「인플루언서가 제품을 받고 SNS에 올리는」 전제로 신청 게이트·정원·결과물·정산이 한 줄로 묶여 있어, 기존 캠페인 형식을 그대로 쓰면 성립하지 않는다. 아래 §2에 부딪히는 지점을, §4에 최소 설계를 정리했다.

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 일반 고객은 신청 버튼을 누를 수 없다 (현재 구현 충돌)

신청 모달을 열기 전 검사에서 **PayPal 이메일·SNS 계정·우편번호·도도부현·시군구·전화**를 모두 요구한다(`application.js:510-542`). 팝업 방문객에게 PayPal 계정을 요구할 수는 없다.

→ **행사 모드 캠페인만 이 검사를 건너뛰는 분기**가 필요하다. 두 층을 구분해야 한다.

- **모달을 열기 전 검사에서 남기는 것**: 이름(한자·가나) · 생년월일·성별. PayPal 이메일·SNS 계정·우편번호·도도부현·시군구·전화는 검사하지 않는다.
- **모달 안에서 받는 것**: 주의사항 동의만. 신청 이유·배송지·PR 태그 동의는 없앤다.
- 가입 계정 이메일은 로그인 상태에서 이미 확보되어 있어 입력 항목이 아니다.

두 층의 정의처는 §4-3 「신청 모달(행사 모드)」이다.

### 2-2. 정원이 서버에서 막히지 않는다 (현재 구현 충돌)

방문형은 초과 신청을 **일부러 허용**한 타입이다. 티켓은 타임별 정원에서 딱 끊겨야 하고, 마지막 한 자리를 여러 명이 동시에 누르는 상황(동시성)까지 막아야 한다. (정원 값은 관리자가 타임별로 입력한다 — §0 결정 8. 이 절은 「정원이 있고 그 선에서 끊긴다」만 전제한다.)

→ 브라우저 화면 검사만으로는 불가능. **자리를 잠그고 정원을 세는 서버 함수**를 새로 만들어 그 안에서 확정/대기를 결정해야 한다.

### 2-3. 타임(시간대)을 담을 곳이 없다 (신규 구조 필요)

3일 합계 **32줄**의 타임이 생기고(줄 수 정의처는 §2-9), 각각 정원이 붙는다. 캠페인 표의 컬럼으로는 표현할 수 없다.

### 2-4. 현장 스캔 화면을 관리자 앱에 넣을 수 없다 (규칙 충돌)

관리자 앱은 PC 전체폭 고정이고 모바일 껍데기 적용이 금지되어 있다. 입구에서 쓰는 휴대폰 스캔 화면을 관리자 앱 안에 만들면 이 규칙과 정면으로 부딪힌다.

→ 관리자 비밀번호 설정 페이지 선례처럼 **독립된 모바일 전용 확인 페이지**를 따로 둔다.

### 2-5. 승인된 신청에는 결과물 제출 폼이 자동으로 붙는다 (현재 구현 충돌)

지금은 신청이 승인되면 인플루언서 활동관리 화면에 SNS 게시물(또는 영수증) 제출 폼이 열린다. 방문객에게 이 폼이 보이면 「무엇을 제출해야 하나」 혼란이 생긴다.

→ 행사 모드는 활동관리 진입을 **티켓(QR) 화면으로 대체**해야 한다. 확정 티켓을 **승인 상태로 저장**하기로 했으므로(§0 결정 14) 이 대체가 없으면 방문객에게 결과물 제출 폼이 그대로 열린다 — 선택이 아니라 필수다.
→ 정산은 리워드 0원인 시딩·방문형이 후보에서 제외되도록 이미 처리되어 있어(마이그레이션 264), **리워드를 0으로 두면 정산에 새지 않는다.** 리워드를 1엔이라도 넣으면 정산 대기가 생기므로 **반드시 0**이며, 관리자 폼에서 값을 잠근다(§4-5).

→ ⚠️ **대체할 자리가 활동관리 하나가 아니다**(2026-08-06 사용자 보고로 드러남). 응모 이력 카드의 더보기(⋮) 메뉴에도 「결과물 제출」 줄이 따로 있고, 이 줄은 활동관리와 **다른 자리**라 활동관리 쪽만 막으면 그대로 남는다. 누르면 티켓 화면으로 돌아가긴 하지만(대체가 그 함수 안에 있으므로), 「영수증·게시 URL을 제출합니다」가 활성으로 보이는 것만으로 §2-5가 없애려던 혼란이 그대로 생긴다. **행사 캠페인은 이 줄 자체를 그리지 않는다.**

→ 같은 메뉴의 「응모 취소」는 회색으로 죽이지 않고 **누르면 입장 티켓 화면으로 보낸다.** 제출 줄을 지우고 나면 이 줄이 행사 캠페인에서 메뉴의 **유일한 항목**이라, 비활성으로 두면 메뉴 전체가 아무것도 못 하는 껍데기가 된다. 취소 자체는 서버(마이그레이션 289)가 이 경로에서 막으므로 티켓 화면으로 길을 알려 주는 것이 유일하게 성립하는 동작이다.

### 2-6. 첫날 초대 전용 캠페인이 목록에 그대로 노출된다 (현재 구현 충돌)

인플루언서 목록은 노출 상태의 캠페인을 전부 보여준다(`campaign.js:30`). 초대받지 않은 사람에게도 8월 28일 캠페인이 보인다.

→ 대응은 **세 겹**이며 §4에 각각 짝이 있다: ① 목록에서 제외(`is_invite_only` — §4-2 ①) ② **상세 화면 진입 게이트**(초대 번호가 확인되지 않으면 상세를 열지 않음 — §4-3 「초대 전용 진입」) ③ 예약 함수에서 초대 번호 재검증(§4-2 ④). 화면 게이트만으로는 주소를 직접 아는 사람을 막지 못하므로 서버 재검증이 최종 방어선이다.

### 2-7. 개인정보 수집 목적에 「오프라인 행사 방문 예약·입장 확인」이 없다 (법률)

현행 개인정보처리방침은 캠페인 참여(제품 배송·정산)를 전제로 수집 목적을 적고 있다. 방문 예약 정보와 **입장 시각 기록**은 새로 수집하는 항목이다.

→ 개인정보처리방침에 수집 항목·목적·보유 기간 추가가 **1차 배포 전 필수 게이트**(§7).

## 3. 권고

**모집 형식을 새로 추가하지 않고**, 기존 방문형(visit)에 「행사 모드」 표시만 얹어 최소 침습으로 붙이는 방향을 권한다. 모집 형식 값을 새로 만들면 형식을 3종으로 나눠 분기하는 코드가 화면·엑셀·결과물·정산·자격 검증에 넓게 퍼져 있어 새 값이 예측 못 한 분기로 떨어진다. 신규 표 2개(타임·티켓)와 자립형 확인 페이지 1개, 서버 함수 3개로 1차 범위를 닫고, 개발서버 리허설 뒤 보강한다.

## 4. 설계 (1차 — 경량 범위)

### 4-1. 전체 흐름

```
[관리자]  캠페인 등록(행사 모드 ON, 리워드 0 잠금)
            → 타임 등록(날짜·시각·정원·대상 라벨)
            → 초대 번호 생성 + 초대 링크 복사(8/28 캠페인만)
                    ↓
[방문객]  가입 또는 로그인 → 캠페인 상세 → 타임 선택 → 신청
            → (정원 여유) 확정 + 예약번호·QR 발급
            → (정원 초과) 대기 명단 + 대기 순번
                    ↓
[입구]    운영진 휴대폰·노트북에서 확인 페이지 열기(관리자 로그인)
            → 예약번호 손입력  또는  QR 스캔
            → 이름·예약 타임·상태 표시 → 입장 처리(첫 스캔 시각 기록)
                    ↓
[행사 후] 관리자 예약 현황 화면에서 타임별 신청·입장·노쇼 집계 + 명단 엑셀
```

### 4-2. 데이터베이스 변경

> 마이그레이션 번호는 적지 않는다(개발 세션이 파일 생성 시점에 확정). **신규 마이그레이션 4개, 아래 상대 순서 그대로.**

**① 캠페인 표에 컬럼 3개 추가**

| 컬럼 | 형 | 뜻 |
|---|---|---|
| `event_mode` | boolean, 기본 false | 행사(티켓) 캠페인 여부. 신청 게이트·활동관리 화면·정원 판정이 이 값으로 분기 |
| `is_invite_only` | boolean, 기본 false | 비공개(초대 전용). true면 인플루언서 목록에서 제외 |
| `invite_code` | text, NULL | 초대 번호(대문자 영숫자 8자리). 링크와 손입력 둘 다 이 값 하나를 검증 |

**② 타임 표 신규 — `event_slots`**

`campaign_id`(캠페인 참조) · `slot_date`(날짜) · `start_time`·`end_time`(시각) · `capacity`(정원) · `audience_label`(대상 표기: 인플루언서 / 일반 고객. 서포터즈·브랜드사는 대상 아님 — §0 결정 7) · `is_active` · `sort_order` · 생성·수정 시각.
접근 정책: 조회는 **로그인 사용자 전체**(§0 결정 16 — 초대 전용 캠페인의 타임도 포함. 캠페인 내용은 상세 게이트가, 예약은 서버 재검증이 막는다), 등록·수정·삭제는 캠페인 관리 권한 이상.

**③ 티켓 표 신규 — `event_tickets`**

| 컬럼 | 뜻 |
|---|---|
| `slot_id` | 어느 타임 |
| `campaign_id` | 어느 캠페인(집계 편의를 위한 중복 보관) |
| `influencer_id` | 누구 |
| `application_id` | 연결된 기존 신청 1건 |
| `ticket_code` | **예약번호 = QR에 담는 값.** 대문자 영숫자 8자리, 표 전체에서 유일. 사람이 손으로도 입력할 수 있는 길이 |
| `status` | `confirmed`(확정) / `waitlist`(대기) / `cancelled`(취소) |
| `waitlist_position` | 대기 순번(확정이면 비움) |
| `entered_at` · `entered_by` | **첫 입장 시각**과 처리한 관리자(재확인해도 덮어쓰지 않음) |
| `scan_count` | 확인된 횟수(재확인 감지용) |
| `version` | 동시 처리 충돌 방지 |

접근 정책: 본인 티켓만 조회 + 관리자 전체 조회. 등록·수정은 **직접 못 하고 서버 함수만**(예약번호 위조·정원 우회 차단).

**④ 서버 함수 3개**

| 함수 | 하는 일 | 가드 |
|---|---|---|
| `reserve_event_ticket(타임, 초대번호)` | 타임 행을 잠그고 정원을 센 뒤, 여유 있으면 확정·없으면 대기로 등록. 같은 트랜잭션에서 기존 신청 1건도 **승인 상태로** 함께 만든다(§0 결정 14) — 이때 기존 승인 알림이 자동 발송되지 않도록 행사 모드 예외를 넣는다. 예약번호를 만들어 돌려준다 | 본인 계정만 · 같은 캠페인 중복 신청 차단 · 비공개 캠페인은 초대 번호 일치 필수 · 만 18세·모집 마감은 기존 트리거가 자동 적용 |
| `check_in_ticket(예약번호)` | 예약번호로 티켓을 찾아 이름·타임·상태를 돌려주고, 첫 확인이면 입장 시각을 기록. 이미 입장이면 첫 입장 시각과 함께 「중복」 표시를 돌려준다 | 관리자 권한 필수 · 취소·대기 티켓은 입장 불가 안내 |
| `cancel_event_ticket(티켓)` | 본인 취소. 확정 티켓이 빠지면 **대기 1번을 확정으로 승격**하고 순번을 다시 매긴다 | 본인 계정만 · 입장 완료된 티켓은 취소 불가 · **예약 타임 시작 2시간 전까지만**(§0 결정 10. 일본 시각 기준으로 서버에서 판정 — 기기 시각을 믿지 않는다) |

모두 `SECURITY DEFINER` + `search_path=''` + 트랜잭션 내 행 잠금.

⚠️ **검증 함정(마감 서버 강제 사양서에서 겪은 것과 같음):** `reserve_event_ticket`·`cancel_event_ticket`은 「본인 계정만」 가드가 있어, 관리자 도구(SQL Editor)는 서비스 키로 붙기 때문에 **로그인한 방문객의 동작을 재현할 수 없다.** 정원 마감·대기 등록·취소 승격은 **반드시 방문객 화면(2단계)이 완성된 뒤 테스트 계정으로 브라우저에서** 확인한다(§5 검증란에 반영).

#### 지나간 타임 (2026-08-06 테스트 발견)

타임 선택표는 원래 **활성 여부만** 보고 지나간 날짜를 걸러내지 않았다. 사흘짜리 행사에서는 **둘째 날 아침에 첫날 탭이 맨 앞에 남아 그게 기본으로 열리고**, 방문객이 그대로 누르면 끝난 날 예약이 만들어진다. 개발서버 실측에서 오늘이 8월 6일인데 기본 선택이 1월 1일이었고 「4명 남음」으로 예약까지 성립했다.

→ **화면에서 지난 날짜를 뺀다.** 지난 날짜가 빠지면 첫 탭이 자연히 「오늘 또는 그 이후 가장 가까운 날」이 되므로 기본 선택 계산은 손대지 않는다. 기준은 기기 시각이 아니라 **일본 날짜**(`jstTodayStr`) — 현장 확인 화면(`prepareRosterDates`)과 같은 기준이어야 두 화면이 어긋나지 않는다.

→ **오늘의 이미 지난 시각 타임은 남긴다**(2026-08-06 사용자 결정). 14시 타임을 14시 10분에 현장에서 받아 줘야 하는 경우가 있어 날짜 단위로만 자른다.

→ ⚠️ **서버는 지난 타임 예약을 막지 않는다**(같은 테스트에서 확인). 이 결함의 최종 방어선은 현재 화면뿐이다. 서버까지 막으면 위의 「늦게 온 사람 받기」가 함께 막히므로 의도적으로 열어 두었다. 화면 필터를 지우면 결함이 그대로 되살아난다.

### 4-4. 화면 — 현장 확인 (자립형 페이지, 한국어)

- 새 파일 `dev/event-scan.html` → 빌드 시 루트로 복사(관리자 비밀번호 설정 페이지와 같은 방식).
- 관리자 로그인 필요. 휴대폰·노트북 세로/가로 모두 대응.
- 구성: **예약번호 손입력칸(상단·항상 노출)** + 카메라 화면(후면 카메라) + **오늘 예약자 명단**.
- **오늘 예약자 명단**(2026-08-03 사용자 결정 — 결정 18): 오늘 날짜의 타임별로 이름·입장 여부를 보여 주고, **이름을 눌러 바로 입장 처리**할 수 있다. QR을 못 찾거나 휴대폰을 두고 온 방문객을 이름으로 찾아 들여보내는 경로다. 「오늘」로 한정하는 이유는 3일치를 다 띄우면 휴대폰 화면에서 목록이 길어져 오히려 못 찾기 때문이다.
  - ⚠️ 이 명단도 서버에서 받아 그린다 — 인터넷이 끊기면 함께 멈춘다(§2-8 U1의 대비는 여전히 종이 인쇄물).
- **스캔 결과 표시 방식**(2026-08-03 사용자 결정): 모달이 아니라 **결과 카드 + 3초 뒤 자동으로 다음 스캔 준비**. 모달로 하면 한 명마다 확인 버튼을 눌러야 해 줄이 길 때 손이 한 번 더 간다.
- 확인 결과 카드: 이름(한자·가나) · 날짜·타임 · 상태(초록=입장 처리 / 노랑=이미 입장 + 첫 입장 시각 / 빨강=예약 없음·취소·대기).
- 결과 카드는 3초 후 다음 확인 준비. 연속 처리 시 마지막 5건 목록 유지.
- 카메라 권한 거부·미지원 시 안내 문구를 띄우고 손입력만으로 계속 진행.

## 5. 단계 분할

| 단계 | 내용 | 산출물 | 검증 |
|---|---|---|---|
| **1단계 — 예약 기반 + 관리자** | 캠페인 컬럼 3개 · 타임 표 · 티켓 표 · 서버 함수 3개 · 관리자(행사 모드 폼·리워드 잠금·타임 관리·예약 현황·리포트 엑셀) | 마이그레이션 4개 + 관리자 화면 | 관리자 화면에서 **타임 등록·수정·일괄 생성·예약 현황 0건 표시·엑셀 내려받기**까지 확인. ⚠️ 정원·대기·취소·「입장 처리」 버튼 동작은 티켓이 있어야 확인되고 방문객 화면이 없으면 티켓을 못 만든다(§4-2 함정) → 2단계 검증으로 이월 |
| **2단계 — 방문객 화면** | 캠페인 상세 타임 선택 · 행사 모드 신청 모달 · 티켓(QR) 화면 · 활동관리 대체 · 초대 링크·번호 진입 · 가입 후 복귀 | 인플루언서 앱 변경 | 테스트 계정 2개 이상으로 브라우저에서 **신청 → 정원 마감 → 대기 등록 → 취소 → 대기 1번 승격 → QR 발급**까지 통과. 여기서 만든 티켓으로 **관리자 예약 현황의 「입장 처리」 버튼**(1단계에서 이월)도 함께 확인 |
| **3-A단계 — 손입력 확인** | 자립형 확인 페이지 + **예약번호 손입력** + 입장 처리 + 중복 표시 | 신규 페이지 1개 | 휴대폰 브라우저에서 예약번호 입력 → 입장 처리 → 재입력 시 중복 표시 확인 |
| **3-B단계 — 카메라 스캔** | 같은 페이지에 QR 카메라 스캔 추가 · 권한 거부 폴백 | 같은 페이지 보강 | **실제 운영진 기기 2종 이상**으로 개발서버 스캔 리허설 |
| **4단계 — 정책 게이트** | 개인정보처리방침 개정(한·일) · 방문객 안내 문구 검수 | 정책 문서 변경 | `/약관확인` 통과 |

**의존 순서:** 1단계 → 2단계 → 3-A단계 → 3-B단계. **4단계(정책 게이트)는 1·2단계와 병행하되 1차 배포 전에 끝낸다** — 3단계와 병행하면 정책 개정이 1차 배포 뒤로 밀려 아래 배포표의 선행 조건을 못 채운다.

**운영 배포는 두 번으로 쪼갠다**(§0 결정 12 — 모집을 최대한 앞당기기 위해).

| 배포 | 무엇을 올리나 | 선행 조건 | 이 배포로 열리는 것 |
|---|---|---|---|
| **1차 배포** | 1단계 + 2단계 | 두 단계 검증 통과 + **4단계 정책 개정 완료** + 사용자 확인 | **모집 시작**(초대 인플루언서 → 일반 고객) |
| **2차 배포** | 3-A단계 + 3-B단계 | **3-A 검증(손입력 확인) 통과** + 3-B를 올릴 경우 실기기 리허설 통과 + 사용자 확인 | 행사 당일 현장 입장 확인 |

정책 개정(4단계)을 **1차 배포 전에** 끝내는 이유: 1차 배포 시점부터 방문 예약 정보가 실제로 수집되기 시작한다. 입장 기록 항목까지 **한 번에 개정**해 두어 개정·통지를 두 번 하지 않는다.

⚠️ 1차 배포 후 2차 배포까지 사이에는 **입장 확인 수단이 없다.** 이 구간에 행사가 들어가지 않도록 2차 배포는 행사 시작(8월 28일)보다 최소 1주 앞에 끝낸다.

**2차 보강 후보(1차에서 제외):** 개별 초대 코드 발급·사용 추적 / 취소 없는 시간 변경 / 확정·대기 안내 메일 / 동반자 신청 / **인터넷 없이 동작하는 확인 화면**(명단을 기기에 미리 저장해 오프라인 대조 — 명단 엑셀 내려받기 자체는 1단계에 포함되며, 여기서 제외하는 것은 「확인 화면이 인터넷 없이 스스로 판정하는 기능」이다) / 노쇼 통계 기반 초과 예약.

4. **입장 기록 열람 범위** — 관리자 전체 조회, 방문객 본인은 자기 기록만.
5. **만 18세 미만 차단 유지** — 현행 연령 정책 그대로. 행사 홍보물에도 「만 18세 이상」 명시 필요(운영 협조 사항).

## 10. 구현 결과

### 작업 1 — 공용 기반 (2026-08-03)

**관련 브랜치:** `feature/팝업티켓` · **마이그레이션:** 280 · 281 · 282 · 283
**검문소:** `reverb-supabase-expert` 통과(지적 3건 반영) → `reverb-reviewer` 통과

#### 초안 대비 변경 사항

**① 초대 번호를 캠페인 컬럼에서 별도 표로 옮겼다 (§4-2 ① 이탈 — 보안)**

사양서는 `campaigns.invite_code` 컬럼을 지시했지만, **캠페인 표는 조회가 공개**이고 인플루언서 앱이 캠페인을 통째로(`select('*')`) 받아온다. 그대로 두면 브라우저 개발자 도구로 **초대 번호가 그대로 보여**, 사양서 §2-6이 「최종 방어선」이라 부른 예약 함수의 서버 재검증이 무력해진다(번호를 아는 사람은 통과).

→ 번호를 `event_invites` 표(캠페인당 1줄, 캠페인 관리 권한만 조회)로 분리하고, 방문객에게는 **「맞나/틀리나」만 답하는** `verify_event_invite()` 함수를 준다. **초대 링크 형식·상세 게이트 등 화면 계약은 그대로**라 작업 2·5의 산출 계약은 바뀌지 않는다.

⚠️ **남은 위험(사용자 판단 필요):** 초대 전용 캠페인의 **내용 자체**(제목·이미지)는 여전히 브라우저로 내려온다 — 목록 제외가 화면 단계 필터이기 때문이다. 사양서 §2-6도 목록 제외·상세 게이트를 화면 단계로 규정했으므로 이번 범위는 그대로 두었다. 내용까지 숨기려면 캠페인 조회를 서버에서 거르는 별도 조각이 필요하다.

**② 서버 함수를 3개가 아니라 5개 만들었다**

| 추가 함수 | 왜 필요했나 |
|---|---|
| `verify_event_invite(campaign_id, code)` | 위 ①로 번호가 표에서 분리되면서 방문객이 확인할 경로가 필요해졌다. 번호는 돌려주지 않고 한 비트만 답한다 |
| `get_event_slot_counts(campaign_id)` | 방문객은 남의 티켓 행을 볼 수 없어(행 단위 보안 정책) 브라우저에서 「잔여 N명」을 셀 수 없다. 작업표 계약에 `fetchEventSlotCounts()`는 있었지만 그 숫자를 만들어 줄 서버 쪽이 빠져 있었다 |

**③ 「취소 후 재예약」을 허용하기로 했다 (사용자 결정 2026-08-03)**

사양서 §2-8 U4는 시간 변경을 「운영진 문의」로 닫았지만, 구현 중 **신청 표에 옛 유일 제약(마이그레이션 050 `uidx_applications_user_campaign`)이 아직 살아 있어 취소하면 같은 캠페인에 다시 신청할 수 없다**는 것을 확인했다. 마이그레이션 104가 이 제약을 지우려 했으나 **지울 이름을 자동 생성 이름으로 적어 `IF EXISTS`가 조용히 통과**했다(기존 백로그).

→ 플랫폼 전체의 제약은 건드리지 않고(「같은 사람·같은 캠페인 여러 줄」이라는 새 데이터 모양을 배포 5일 전에 만들 수 없다), **행사 예약 함수 안에서만 우회**한다: 취소해도 신청 행을 지우지 않고 `cancelled`로 두었다가 재예약 때 **그 행을 되살린다**. 행이 하나뿐이라 옛 제약에 걸리지 않고 취소 이력도 응모 이력에 남는다.

**④ 확정 티켓의 신청 상태 — 결정 14를 트리거 조기 반환으로 구현**

확정은 신청을 `approved`로 **INSERT**하므로 승인 알림 트리거(`AFTER UPDATE OF status`)가 애초에 돌지 않는다. 다만 **대기 승격**은 `pending → approved` UPDATE라 트리거가 돈다. 그래서 `record_application_status_event()`를 재정의해 **행사 캠페인이면 조기 반환**하게 했다. 알림만이 아니라 트리거 전체를 건너뛴 이유는 두 가지다.

- 알림 문구(「成果物の提出をお願いします」)가 결과물을 내지 않는 방문객에게 부적합(결정 14)
- 대기 승격은 **다른 방문객의 취소 트랜잭션 안에서** 일어나므로, 감사 기록의 처리자가 「취소한 방문객」으로 찍혀 **사실과 다른 이력**이 쌓인다

일반 캠페인 동작은 로직 기준으로 154와 동일하다.

**⑤ 대기(waitlist)도 신청 행을 미리 만든다**

안 만들면 승격 시점(행사 직전, 모집 마감 후)에 신청을 새로 넣어야 하는데 마감 가드 트리거(272)에 막혀 **승격 자체가 실패**한다. 모집 기간 안에 만들어 두면 승격은 UPDATE라 그 가드를 타지 않는다.

#### 구현 중 기술 결정 사항

- **정원 판정**: 예약 함수가 타임 행을 `FOR UPDATE`로 잠근 뒤 확정 수를 센다. 마지막 한 자리 경합에서 초과가 구조적으로 불가능하다.
- **예약번호**: 대문자 영숫자 8자리, 혼동하기 쉬운 글자(0 O 1 I L) 제외한 31자 집합. 현장에서 손으로 입력하기 때문.
- **연령·마감 검사를 함수 안에서도 한다**: 두 가드는 **신규 삽입 전용** 트리거라 되살리기(UPDATE) 경로에 발동하지 않는다. 두 경로의 판정이 달라지지 않게 함수가 먼저 검사하고, 트리거는 삽입 경로의 최종 방어선으로 그대로 둔다(공유 지점이라 고치지 않는다).
- **개인정보 파기 연쇄**: `event_tickets.application_id`에 연쇄 삭제를 걸어, 캠페인 보관 삭제(255)가 신청을 즉시 파기할 때 **입장 기록도 함께** 사라진다. 삭제 함수 자체는 고치지 않았다(작업표 stale 점검 7번 해소).
- **행사 모드는 방문형에만**: 리뷰어형에 켜지면 자동 승인 트리거(049)가 「대기」로 넣으려던 신청을 승인으로 덮어써 **티켓은 대기인데 신청은 당선**인 모순이 생긴다. 캠페인 표 CHECK 제약 + 예약 함수 조기 반환 이중으로 막았다.
- **예약이 걸린 타임은 삭제 차단**: 지우면 티켓이 소리 없이 연쇄 삭제되고 신청 행만 남아 「당선인데 예약번호 없음」이 된다. 삭제 차단 트리거를 두되, **캠페인이 통째로 지워지는 중이면 통과**시키는 탈출구를 넣었다(연쇄 순서가 보장되지 않아 캠페인 완전 삭제가 막힐 수 있다).
- **송금 완료된 정산이 걸린 티켓은 취소 불가**: 리워드 0이라 정산이 생기지 않지만, 실수로 값이 들어간 경우 신청을 취소로 바꾸면 가드 트리거(247)가 **예외**를 던져 트랜잭션 전체가 롤백되고 그 한국어 문구가 일본어 화면에 노출된다. 예외 전에 표준 응답으로 돌려준다.
- **관리자 목록 컬럼**: `ADMIN_LIST_COLUMNS`에 `event_mode`·`is_invite_only` 둘 다 추가(계약은 `event_mode`만 — 목록에서 비공개 표시를 하려면 둘 다 필요).
- **캠페인 변경 이력 화이트리스트에는 추가하지 않았다**(작업표 권고). 세 곳을 동시에 고쳐야 하고 어긋나면 캠페인 저장이 통째로 실패한다.

#### 이 단계에서 검증하지 않은 것 (작업 3·4로 이월)

예약·정원 마감·대기 등록·취소·승격은 「본인 계정만」 가드가 있어 **관리자 도구(SQL 편집기)로 재현할 수 없다**(서비스 키로 붙어 로그인 사용자가 없다). 방문객 화면이 붙은 뒤 **테스트 계정 2개로 브라우저에서** 확인한다.

**⑥ 대기 승격 앱 알림 1종을 1차 범위에 추가했다 (사용자 결정 2026-08-03 — 결정 17)**

앞사람이 취소해 대기자가 확정으로 올라가도, **본인이 앱에 들어와 보기 전까지 모른다** → 그대로 노쇼가 된다. 사양서는 확정 안내 **메일**만 2차로 미뤘고(결정 11) 앱 알림은 언급이 없었다.

→ 알림 종류에 `event_waitlist_promoted`를 더했다(현행 10종 → 11종. 목록의 원본은 **273**이라 그 10종을 그대로 옮기고 1종만 추가). 알림은 **취소 함수가 직접 넣는다** — 행사 캠페인은 위 ④의 상태 트리거가 조기 반환하므로 트리거로는 나가지 않는다.

- 문구(일본어): 제목 「キャンセル待ちから予約が確定しました」 / 본문에 캠페인명·날짜·시각·「入場チケット에서 QR 확인」 안내
- 연결: `ref_table='event_tickets'`, `ref_id=승격된 티켓`
- **작업 4에서 할 일**: 알림 목록의 클릭 분기에 이 종류를 더해 **티켓 화면으로** 보내야 한다. 분기를 안 넣으면 알림은 뜨는데 눌러도 아무 데도 안 간다. (알림 조회 자체는 종류 화이트리스트가 아니라 제외 목록 방식이라 별도 조치 없이 표시된다)

#### 초안 대비 변경 사항

**① 행사장 안내 칸을 새로 만들었다 (§4-3 보강 — 마이그레이션 285)**

사양서는 티켓에 「QR + 예약번호 + 이름 + 날짜·타임 + **장소**」를 넣으라고 했는데 캠페인에 장소를 담을 칸이 없었다. §9-1 이 「행사장 이름·주소는 미정, 임시 문구로 만들고 나중에 교체」라고 한 것은 **내용**이 미정이라는 뜻이지 칸이 필요 없다는 뜻이 아니다. `campaigns.event_place` 추가 + 관리자 폼 입력칸. 비면 티켓에 「장소는 정해지는 대로 안내」가 나간다.

**② 보유 기간을 지킬 장치를 함께 만들었다 (§7-1 보강 — 마이그레이션 286)**

개인정보처리방침에 「행사 종료 후 6개월」을 적었는데 **그 시점에 지우는 장치가 없었다.** 방침에 적은 기간을 못 지키는 것 자체가 위반이라, 위반 기록 3년 자동 파기(마이그레이션 166)와 같은 구조로 매일 새벽 파기를 넣었다. 기준일은 그 티켓이 속한 **타임의 날짜**다.

**③ 이용약관은 손대지 않았다 (사용자 결정 2026-08-03 — 결정 19)**

선결 조건 S2(방문 예약만 하는 일반 고객에게 현행 약관이 어떻게 적용되나)에 대해 **개인정보처리방침만 개정하고 진행**하기로 했다. 제품 제공·리워드·뒷광고 표시 조항은 「해당하는 경우에만 적용」으로 보고, 회원 유형 분리는 하지 않는다.

**④ 개인정보처리방침 개정 내용**

- §2.1 수집 항목 2행 추가 — 「예약한 날짜·시간대, 예약번호, 대기 순번, 취소 일시」 / 「입장 확인 시각, 확인 횟수, 확인한 담당자」
- §2.1 안내 4줄 — 이름 표시 목적(현장 대조) · **QR 에 예약번호만 담긴다** · 입장 기록 열람 범위 · 배송이 없어 주소·전화·PayPal 을 안 받는다
- §6.1 보유 기간 1행 — 「행사 종료 후 6개월」
- 부칙 1줄 — **기능 제공일 시행**. 수집 항목 추가지만 ①이 기능을 쓰는 사람에게만 해당하고 ②기존 회원의 이미 수집된 정보는 바뀌지 않아, 같은 문서의 선례(2026-05-28 문의하기 기능 — 새 수집 항목을 기능 제공일에 즉시 시행)를 따랐다. 30일 사전 공지가 붙었던 선례(생년월일·성별)는 **기존 회원 전원에게 소급 요구**한 경우라 성격이 다르다

#### 브라우저 QA 에서 드러난 것 (정적 검토를 전부 통과한 뒤)

## 편집 화면 논리 정합 (2026-08-03 추가 작업)

사용자 보고 — 「행사 캠페인에서 방문 기간을 고치니 결과물 제출 마감일 팝업이 뜬다. 그 칸은 숨겨 놨는데. 편집 화면에 논리에 맞는 기능이 세팅되어야 한다」.

원인은 **숨긴 칸을 규칙이 계속 읽고 있던 것**이었다. 행사 모드는 8개 칸을 숨기고 저장 때 비우는데, 폼 입력칸에는 켜기 전 값이 그대로 남아 있어서 자동 제안·달력 경계·검증·확인창 문구가 모두 그 값을 봤다. 같은 뿌리로 12건이 나왔다.

### 데이터가 잘못 저장되던 것

| 발견 | 성격 |
|---|---|
| 캠페인 A 에서 행사 모드를 켠 뒤 **B 를 열면 B 의 모집 형식이 A 의 옛 형식으로 바뀌고 방문 기간이 비워진 채 저장** | 「켜기 직전 형식」 기억이 모듈 전역인데 캠페인을 새로 열 때 안 비워졌다. 확인창도 없어 알아채기 어렵다 |
| 미리보기가 **행사인 줄 몰라** 숨긴 칸을 그대로 노출 | 미리보기용 객체에 `event_mode` 키가 없어 판정이 늘 거짓 — 가드가 한 번도 안 걸렸다 |

### 구조를 바꾼 것

- **방문 기간·모집 인원은 「행사 시간」에서 계산한다.** 셋이 따로 놀아 방문객 화면에 서로 다른 두 벌의 날짜가 뜰 수 있었고, 모집 인원은 장식이었다(서버 예약 함수는 `campaigns.slots` 를 아예 안 본다). 두 칸은 잠기고 저장 시 시간대를 **다시 읽어** 계산한다(화면 캐시를 쓰면 다른 관리자의 수정을 놓친다). 시간대 0줄이면 잠그지도 계산하지도 않는다
- **예약이 살아 있으면 행사 모드를 못 끈다.** 끄면 예약 현황·입장 확인 진입로가 사라지고 방문객 화면이 결과물 제출 폼으로 바뀌며 억눌러 둔 「당선」 알림이 나간다. 되돌릴 화면 경로가 없어 되묻지 않고 막는다
- **종료 판정에 `campaignFinishDate(camp)` 를 둔다.** 제출 마감일이 없으면 행사는 **마지막 방문일**을 쓴다. 그전엔 행사 캠페인이 「모집마감」에서 영영 안 넘어갔다

### 이 작업에서 배운 것

- **「숨긴다」와 「값을 지운다」는 다른 일이다.** 둘을 한 함수에 묶어 두면, 숨기는 조건이 하나 늘 때마다 멀쩡한 값이 지워진다. 실제로 「행사면 숨긴다」를 넣자마자 ①편집 폼을 여는 순간(행사 여부가 아직 이 캠페인 것으로 안 바뀐 시점) 직전 캠페인의 판정이 새어 들어와 **일반 방문형 캠페인의 방문 날짜가 지워지고** ②행사 모드를 켰다 끄면 원래 날짜가 사라졌다. 지우는 기준은 **모집 형식뿐**으로 되돌렸다
- **표시 규칙은 정의처에 둔다.** 「행사면 숨긴다」를 호출자 쪽에 두면, 형식이 바뀔 때 도는 비동기 렌더가 나중에 끝나며 되살린다(신규 등록 화면에서 방문 기간 칸만 안 사라졌다). 판정을 `applyDeadlineFieldsVisibility`·`applyMinFollowersVisibility` 안으로 옮겨 **순서와 무관**하게 만들었다
- **값을 남기면 이번엔 검증이 막는다.** 숨긴 방문 날짜를 날짜 규칙이 읽어, 모집 시작일을 뒤로 미루면 「방문 시작일은 모집 시작일~… 사이여야 합니다」로 저장이 막혔다 — 화면에 없는 칸을 가리키는 오류라 손쓸 방법이 없다. `campRuleSubmissionEnd`·`campRuleVisitRange` 로 **규칙이 볼 값**과 **저장된 값**을 갈랐다
- **정적 리뷰가 세 번 통과한 뒤 브라우저에서 잡혔다.** 비동기 렌더 순서는 읽어서 안 보인다

### 덤으로 고친 것 (행사와 무관)

신규 등록 폼이 모집 형식 라디오를 **없는 이름**(`newRecruitType`, 실제는 `recruitType`)으로 찾고 있어, 기프팅 캠페인의 「모집 종료 +19일」 제출 마감 제안이 **한 번도 뜬 적이 없었다**.

### 남은 백로그

- **행사 시간(시간대)의 날짜가 모집 기간 밖으로 벗어나는 것을 아무도 안 본다.** 방문 기간 검증이 행사에서는 빠지는데(위 참조) 그 자리를 시간대 쪽에서 대신 봐 줄 규칙이 없다. 별도 설계 필요
- **날짜 선택 칸이 값을 안 보여주는 경우가 있다** — 행사 모드를 껐을 때, 그리고 노출종료 상태 캠페인을 열 때. **데이터는 멀쩡하다**(숨은 칸·미리보기에는 정상 표시되고, 그대로 저장해도 값이 지워지지 않는다). **모집 기간 칸에서도 같은 증상**이 나오는데 그 칸은 이번 작업이 건드리지 않았으므로 이 작업 이전부터 있던 것으로 보인다. 원인 미확인

## 작업 7·8 + 예약 취소 수단 (2026-08-03 ~ 08-04)

**마이그레이션:** 287(다른 날 예약 되묻기) · 288(관리자용 예약 취소) · 289(행사 신청 상태 직접 변경 차단)
**화면:** `dev/event-scan.html` 신규(빌드가 루트로 복사) · 관리자 예약 현황을 캠페인 진행현황 안으로 이동

### 초안 대비 변경 사항

**① 현장 확인 페이지를 1차 배포 전에 만들었다 (작업 7·8 앞당김)**

일정상 2차 배포(8월 19일)로 잡혀 있었으나 손입력·카메라 스캔·명단 대조를 함께 완성했다. 한국어·일본어 전환, 타임별 명단, 예약·입장 집계, **인터넷이 끊기면 손입력도 멈춘다는 안내**(서버 조회 방식이라)와 그때의 대체 절차(인쇄 명단 대조 → 복구 후 관리자 화면에서 손처리)까지 화면에 적었다.

**② 입장 기록을 「먼저 남기고 나중에 묻는」 순서를 뒤집었다 (287)**

원래 `check_in_ticket` 은 입장을 **기록한 뒤** 화면이 「오늘이 아닙니다」를 보여줬다. 운영진이 그 문구를 읽었을 때는 이미 기록이 끝나 거를 기회가 없고, 화면에서만 되물으면 **우회하면 그냥 기록된다**. 인자 `p_confirm_other_day`(기본 거짓)를 더해 **서버가 기록하지 않고 되돌려보내도록** 바꿨다. ⚠️ 이미 입장한 티켓은 되묻지 않고 곧바로 중복 응답을 준다 — 이미 들여보낸 사람에게 다시 물을 이유가 없다.

**③ 관리자에게 예약 취소 수단이 아예 없었다 (288·289)**

관리자는 「신청 미승인」으로 대신 처리해 왔는데, 그러면 신청만 반려되고 **티켓은 확정으로 남는다.** 입장 확인은 신청 상태를 보지 않으므로 **반려된 사람이 현장에서 그대로 입장 처리될 수 있었다.**

- **288** 이 취소 수단을 만들고(관리자용 취소 함수 — 대기 승격·순번 재정렬은 본인 취소와 같은 규칙)
- **289** 가 잘못된 길을 막는다 — 관리자 화면은 신청 상태를 원격 호출 함수 없이 **직접** 바꾸는데, 행사 캠페인에서는 신청 상태가 티켓과 짝을 이루는 파생값이라 신청만 바뀌면 어긋난다
- ⚠️ **288 → 289 순서로 적용해야 한다.** 수단을 먼저 만들고 길을 막는 순서다

**④ 예약 현황을 별도 페인에서 캠페인 진행현황 안으로 옮겼다**

작업표 계약은 `#adminPane-event-tickets` 독립 페인이었으나, 예약은 그 캠페인에 속한 정보라 진행현황의 **탭**(「예약 현황」 / 「신청자 목록」)으로 합쳤다. 요약 카드도 행사용으로 갈라 예약 확정률·입장률·대기·미입장·취소를 함께 보여준다. 행사 캠페인의 더보기 메뉴에서는 결과물 엑셀을 뺐다(행사에는 결과물이 없다).

### 검증에서 드러난 것 (정적 리뷰를 전부 통과한 뒤)

| 발견 | 왜 정적 검토로 못 잡았나 |
|---|---|
| 하단 고정 바에서 리워드 글자가 **한 글자씩 세로로** 쌓임 | 재응모 안내를 넣는 줄이 `insertBefore(안내, 버튼)` 한 줄이고, 그 **버튼의 부모가 가로 한 줄**이라는 사실은 HTML 을 따로 열어 봐야 안다. 폭이 0 이 되는 것은 그려 봐야 보인다. **행사와 무관하게 취소 이력이 있는 모든 캠페인**에 있던 결함 |
| 타임 선택 상태가 **색으로만** 전달됨 | 화면상으로는 멀쩡해 보인다. 화면 낭독기 관점은 속성을 직접 확인해야 드러난다 |

둘 다 고쳐 개발서버에 반영했다(`aria-pressed` 추가 · 안내를 버튼 줄 위로).
