# 오프라인 팝업 방문 예약(티켓팅) + 입장 QR 확인

**작성일:** 2026-07-30
**행사:** 2026-08-28(금)~08-30(일) 뷰티 팝업 스토어
**작성 세션:** 기획/설계
**상태:** 초안 — 사용자 확인 대기 항목 있음 (§9)

---

## 0. 요청 요약

1. 플랫폼에서 **오프라인 팝업 방문 예약(티켓팅)**이 가능한 캠페인을 만든다.
2. 3일 동안, 하루 8~16개 **타임(시간대)** 별로 방문객을 모집한다. *(요청 원문. 첨부한 표는 날짜별로 구조가 달라 실제 해석은 §2-9 참조)*
3. 신청이 확정된 방문객에게 **개인을 식별할 수 있는 QR 코드**를 발급한다.
4. 행사장 입구에서 운영진이 **노트북 또는 휴대폰 카메라로 QR을 스캔**하면 ① 우리 플랫폼 가입자인지 ② 어느 날 몇 시 타임으로 예약했는지가 확인된다.
5. 스캔되면 **방문 기록**이 남고, 행사 종료 후 **방문객 리포트**를 만들 수 있다.
6. 우선 **주요 필수 기능만 가볍게** 만들어 테스트한 뒤, 될 것 같으면 보강한다.

### 가능 여부 결론

**가능하다.** 단 지금 플랫폼은 「인플루언서가 제품을 받고 SNS에 올리는」 전제로 신청 게이트·정원·결과물·정산이 한 줄로 묶여 있어, 기존 캠페인 형식을 그대로 쓰면 성립하지 않는다. 아래 §2에 부딪히는 지점을, §4에 최소 설계를 정리했다.

## 2. 의심·경우의 수 (규칙 B)

### 2-1. 일반 고객은 신청 버튼을 누를 수 없다 (현재 구현 충돌)

신청 모달을 열기 전 검사에서 **PayPal 이메일·SNS 계정·우편번호·도도부현·시군구·전화**를 모두 요구한다(`application.js:510-542`). 팝업 방문객에게 PayPal 계정을 요구할 수는 없다.

→ **행사 모드 캠페인만 이 검사를 건너뛰는 분기**가 필요하다. 두 층을 구분해야 한다.

- **모달을 열기 전 검사에서 남기는 것**: 이름(한자·가나) · 생년월일·성별. PayPal 이메일·SNS 계정·우편번호·도도부현·시군구·전화는 검사하지 않는다.
- **모달 안에서 받는 것**: 주의사항 동의만. 신청 이유·배송지·PR 태그 동의는 없앤다.
- 가입 계정 이메일은 로그인 상태에서 이미 확보되어 있어 입력 항목이 아니다.

두 층의 정의처는 §4-3 「신청 모달(행사 모드)」이다.

### 2-2. 정원이 서버에서 막히지 않는다 (현재 구현 충돌)

방문형은 초과 신청을 **일부러 허용**한 타입이다. 티켓은 타임별 정원에서 딱 끊겨야 하고, 마지막 한 자리를 여러 명이 동시에 누르는 상황(동시성)까지 막아야 한다. (정원의 구체 숫자는 §9-1 확인 대기 — 이 절은 「정원이 있다」만 전제한다.)

→ 브라우저 화면 검사만으로는 불가능. **자리를 잠그고 정원을 세는 서버 함수**를 새로 만들어 그 안에서 확정/대기를 결정해야 한다.

### 2-3. 타임(시간대)을 담을 곳이 없다 (신규 구조 필요)

3일 합계 **32줄에서 46줄**의 타임이 생기고(줄 수 정의처는 §2-9. §9-2 두 답의 조합에 따라 32·33·45·46 중 하나), 각각 정원이 붙는다. 캠페인 표의 컬럼으로는 표현할 수 없다.

### 2-4. 현장 스캔 화면을 관리자 앱에 넣을 수 없다 (규칙 충돌)

관리자 앱은 PC 전체폭 고정이고 모바일 껍데기 적용이 금지되어 있다. 입구에서 쓰는 휴대폰 스캔 화면을 관리자 앱 안에 만들면 이 규칙과 정면으로 부딪힌다.

→ 관리자 비밀번호 설정 페이지 선례처럼 **독립된 모바일 전용 확인 페이지**를 따로 둔다.

### 2-5. 승인된 신청에는 결과물 제출 폼이 자동으로 붙는다 (현재 구현 충돌)

지금은 신청이 승인되면 인플루언서 활동관리 화면에 SNS 게시물(또는 영수증) 제출 폼이 열린다. 방문객에게 이 폼이 보이면 「무엇을 제출해야 하나」 혼란이 생긴다.

→ 행사 모드는 활동관리 진입을 **티켓(QR) 화면으로 대체**해야 한다.
→ 정산은 리워드 0원인 시딩·방문형이 후보에서 제외되도록 이미 처리되어 있어(마이그레이션 264), **리워드를 0으로 두면 정산에 새지 않는다.** 리워드를 1엔이라도 넣으면 정산 대기가 생기므로 **반드시 0**이며, 관리자 폼에서 값을 잠근다(§4-5).

### 2-6. 첫날 초대 전용 캠페인이 목록에 그대로 노출된다 (현재 구현 충돌)

인플루언서 목록은 노출 상태의 캠페인을 전부 보여준다(`campaign.js:30`). 초대받지 않은 사람에게도 8월 28일 캠페인이 보인다.

→ 대응은 **세 겹**이며 §4에 각각 짝이 있다: ① 목록에서 제외(`is_invite_only` — §4-2 ①) ② **상세 화면 진입 게이트**(초대 번호가 확인되지 않으면 상세를 열지 않음 — §4-3 「초대 전용 진입」) ③ 예약 함수에서 초대 번호 재검증(§4-2 ④). 화면 게이트만으로는 주소를 직접 아는 사람을 막지 못하므로 서버 재검증이 최종 방어선이다.

### 2-7. 개인정보 수집 목적에 「오프라인 행사 방문 예약·입장 확인」이 없다 (법률)

현행 개인정보처리방침은 캠페인 참여(제품 배송·정산)를 전제로 수집 목적을 적고 있다. 방문 예약 정보와 **입장 시각 기록**은 새로 수집하는 항목이다.

→ 개인정보처리방침에 수집 항목·목적·보유 기간 추가가 **운영 배포 전 필수 게이트**(§7).

| U7 | 신규 가입자가 가입만 하고 신청까지 못 간다 | 전환 손실 | 초대 링크로 들어오면 **가입 완료 후 그 캠페인 상세로 자동 복귀**(주소에 캠페인·초대 번호 유지, §4-3) |
| U8 | 화면 문구 언어 | 인플루언서 화면은 일본어, 운영진 확인 화면은 한국어 | 방문객 화면 일본어(다국어 키 등록), 확인 화면 한국어 |

### 2-9. 의도가 갈리는 표현 (모호점)

| 표현 | 두 가지 해석 | 이 사양서의 채택 |
|---|---|---|
| 「개인 식별이 가능한 QR」 | ① QR 안에 이름·이메일을 담는다 ② QR에는 의미 없는 번호만 담고 서버가 사람을 찾는다 | **②**. QR 사진이 SNS에 올라가도 개인정보가 노출되지 않는다 |

| 보내주신 표의 타임 구조 | — | **이 칸이 타임 줄 수의 정의처다.** **8월 28일**: 구간형 4줄(11:00~13:00 100명 / 14:00~16:00 100명 / 17:00~18:00 50명 / 19:00 서포터즈 50명). **8월 29일**: 11:00~19:00 30분 단위(13:00 휴식 제외) 16줄. **8월 30일**: 11:00~17:30 30분 단위(13:00 휴식 제외) 13줄. 이틀차·삼일차는 줄당 「80명+@」. → **3일 합계는 §9-2 두 축(첫날 단위 × 서포터즈 포함 여부)의 조합으로 결정된다**: ① 첫날 구간형(100·100·50 3줄)·서포터즈 제외 = **32줄**(초안 전제) ② 첫날 구간형·서포터즈 포함(+50명 1줄) = **33줄** ③ 첫날 30분 단위(16줄)·서포터즈 제외 = **45줄** ④ 첫날 30분 단위·서포터즈 포함 = **46줄** |
| 「방문객」 | 인플루언서 / 일반 고객 / 브랜드사 / 레버브 서포터즈 | 첫날=초대 인플루언서, 이틀=일반 고객. **브랜드사·서포터즈 포함 여부는 §9-2에서 확인**(현재 초안은 제외 전제) |

## 3. 권고

**모집 형식을 새로 추가하지 않고**, 기존 방문형(visit)에 「행사 모드」 표시만 얹어 최소 침습으로 붙이는 방향을 권한다. 모집 형식 값을 새로 만들면 형식을 3종으로 나눠 분기하는 코드가 화면·엑셀·결과물·정산·자격 검증에 넓게 퍼져 있어 새 값이 예측 못 한 분기로 떨어진다. 신규 표 2개(타임·티켓)와 자립형 확인 페이지 1개, 서버 함수 3개로 1차 범위를 닫고, 개발서버 리허설 뒤 보강한다.

## 4. 설계 (1차 — 경량 범위)

### 4-1. 전체 흐름

```
[관리자]  캠페인 등록(행사 모드 ON, 리워드 0 잠금)
            → 타임 등록(날짜·시각·정원·대상 라벨)
            → 초대 번호 생성 + 초대 링크 복사(8/28 캠페인만)
                    ↓
[방문객]  가입 또는 로그인 → 캠페인 상세 → 타임 선택 → 신청
            → (정원 여유) 확정 + 예약번호·QR 발급
            → (정원 초과) 대기 명단 + 대기 순번
                    ↓
[입구]    운영진 휴대폰·노트북에서 확인 페이지 열기(관리자 로그인)
            → 예약번호 손입력  또는  QR 스캔
            → 이름·예약 타임·상태 표시 → 입장 처리(첫 스캔 시각 기록)
                    ↓
[행사 후] 관리자 예약 현황 화면에서 타임별 신청·입장·노쇼 집계 + 명단 엑셀
```

### 4-2. 데이터베이스 변경

> 마이그레이션 번호는 적지 않는다(개발 세션이 파일 생성 시점에 확정). **신규 마이그레이션 4개, 아래 상대 순서 그대로.**

**① 캠페인 표에 컬럼 3개 추가**

| 컬럼 | 형 | 뜻 |
|---|---|---|
| `event_mode` | boolean, 기본 false | 행사(티켓) 캠페인 여부. 신청 게이트·활동관리 화면·정원 판정이 이 값으로 분기 |
| `is_invite_only` | boolean, 기본 false | 비공개(초대 전용). true면 인플루언서 목록에서 제외 |
| `invite_code` | text, NULL | 초대 번호(대문자 영숫자 8자리). 링크와 손입력 둘 다 이 값 하나를 검증 |

**② 타임 표 신규 — `event_slots`**

`campaign_id`(캠페인 참조) · `slot_date`(날짜) · `start_time`·`end_time`(시각) · `capacity`(정원) · `audience_label`(대상 표기: 인플루언서 / 일반 고객. 서포터즈·브랜드사는 §9-2 확인 결과에 따라 추가) · `is_active` · `sort_order` · 생성·수정 시각.
접근 정책: 조회는 로그인 사용자 전체(신청 화면에 필요), 등록·수정·삭제는 캠페인 관리 권한 이상.

**③ 티켓 표 신규 — `event_tickets`**

| 컬럼 | 뜻 |
|---|---|
| `slot_id` | 어느 타임 |
| `campaign_id` | 어느 캠페인(집계 편의를 위한 중복 보관) |
| `influencer_id` | 누구 |
| `application_id` | 연결된 기존 신청 1건 |
| `ticket_code` | **예약번호 = QR에 담는 값.** 대문자 영숫자 8자리, 표 전체에서 유일. 사람이 손으로도 입력할 수 있는 길이 |
| `status` | `confirmed`(확정) / `waitlist`(대기) / `cancelled`(취소) |
| `waitlist_position` | 대기 순번(확정이면 비움) |
| `entered_at` · `entered_by` | **첫 입장 시각**과 처리한 관리자(재확인해도 덮어쓰지 않음) |
| `scan_count` | 확인된 횟수(재확인 감지용) |
| `version` | 동시 처리 충돌 방지 |

접근 정책: 본인 티켓만 조회 + 관리자 전체 조회. 등록·수정은 **직접 못 하고 서버 함수만**(예약번호 위조·정원 우회 차단).

**④ 서버 함수 3개**

| 함수 | 하는 일 | 가드 |
|---|---|---|
| `reserve_event_ticket(타임, 초대번호)` | 타임 행을 잠그고 정원을 센 뒤, 여유 있으면 확정·없으면 대기로 등록. 같은 트랜잭션에서 기존 신청 1건도 함께 만든다. 예약번호를 만들어 돌려준다 | 본인 계정만 · 같은 캠페인 중복 신청 차단 · 비공개 캠페인은 초대 번호 일치 필수 · 만 18세·모집 마감은 기존 트리거가 자동 적용 |
| `check_in_ticket(예약번호)` | 예약번호로 티켓을 찾아 이름·타임·상태를 돌려주고, 첫 확인이면 입장 시각을 기록. 이미 입장이면 첫 입장 시각과 함께 「중복」 표시를 돌려준다 | 관리자 권한 필수 · 취소·대기 티켓은 입장 불가 안내 |
| `cancel_event_ticket(티켓)` | 본인 취소. 확정 티켓이 빠지면 **대기 1번을 확정으로 승격**하고 순번을 다시 매긴다 | 본인 계정만 · 입장 완료된 티켓은 취소 불가 |

모두 `SECURITY DEFINER` + `search_path=''` + 트랜잭션 내 행 잠금.

⚠️ **검증 함정(마감 서버 강제 사양서에서 겪은 것과 같음):** `reserve_event_ticket`·`cancel_event_ticket`은 「본인 계정만」 가드가 있어, 관리자 도구(SQL Editor)는 서비스 키로 붙기 때문에 **로그인한 방문객의 동작을 재현할 수 없다.** 정원 마감·대기 등록·취소 승격은 **반드시 방문객 화면(2단계)이 완성된 뒤 테스트 계정으로 브라우저에서** 확인한다(§5 검증란에 반영).

### 4-3. 화면 — 방문객(인플루언서 앱, 일본어)

| 화면 | 내용 |
|---|---|
| 캠페인 상세 (행사 모드) | 기존 상세 위에 **타임 선택표**(날짜 탭 → 타임 목록, 각 타임에 잔여/마감/대기 표시). 신청 버튼은 타임 선택 후 활성 |
| **초대 전용 진입** | `is_invite_only` 캠페인은 목록에 안 뜨고, 상세도 **초대 번호가 확인될 때만** 열린다. 두 경로 ① 초대 링크(주소에 초대 번호 포함 → 자동 확인) ② 초대 번호 손입력 화면. 확인 실패 시 「초대 번호를 확인해 주세요」 안내만 표시(캠페인 내용 비노출) |
| 신청 모달 (행사 모드) | **모달 열기 전 검사**: 이름(한자·가나) + 생년월일·성별(미입력이면 기존 입력 게이트로)만. SNS·PayPal·우편번호·도도부현·시군구·전화 검사 **없음**. **모달 안 입력**: 주의사항 동의만. 신청 이유·배송지·PR 태그 동의 **없음** |
| 티켓 화면 (신규) | 큰 QR + **예약번호 8자리** + 이름·날짜·타임·장소. 대기 상태면 QR 대신 「대기 3번」 안내. 취소 버튼 |
| 진입 경로 (2곳) | ① 응모 이력 카드의 「입장 티켓」 버튼 ② 햄버거 메뉴 「입장 티켓」(행사 예약이 있을 때만 표시) |
| 활동관리 | 행사 모드 캠페인은 결과물 제출 폼을 **띄우지 않고** 티켓 화면으로 대체 |
| 가입 후 복귀 | 초대 링크·홍보 링크로 들어와 가입한 경우, 가입 완료 후 **그 캠페인 상세로 자동 복귀**(초대 번호 유지) |

QR 이미지는 브라우저에서 생성(외부 전송 0). 라이브러리는 필요 시점에만 불러온다(기존 글자인식·엑셀 방식과 동일).

### 4-4. 화면 — 현장 확인 (자립형 페이지, 한국어)

- 새 파일 `dev/event-scan.html` → 빌드 시 루트로 복사(관리자 비밀번호 설정 페이지와 같은 방식).
- 관리자 로그인 필요. 휴대폰·노트북 세로/가로 모두 대응.
- 구성: **예약번호 손입력칸(상단·항상 노출)** + 카메라 화면(후면 카메라).
- 확인 결과 카드: 이름(한자·가나) · 날짜·타임 · 상태(초록=입장 처리 / 노랑=이미 입장 + 첫 입장 시각 / 빨강=예약 없음·취소·대기).
- 결과 카드는 3초 후 다음 확인 준비. 연속 처리 시 마지막 5건 목록 유지.
- 카메라 권한 거부·미지원 시 안내 문구를 띄우고 손입력만으로 계속 진행.

### 4-5. 화면 — 관리자(한국어)

| 위치 | 내용 |
|---|---|
| 캠페인 등록·편집 폼 | 「행사 모드」 켜기 + 「비공개(초대 전용)」 + 초대 번호 생성·링크 복사 + **행사 모드일 때 리워드 입력칸을 0으로 고정·잠금**(§2-5·§8 대비의 실행 수단) |
| 타임 관리 | 행사 모드 캠페인 전용 섹션. 날짜·시각·정원·대상 라벨을 줄 단위로 추가·수정. **하루 치를 30분 간격으로 일괄 생성**하는 보조 버튼(하루 13~16줄을 손으로 넣지 않게. 3일 합계는 §2-9 참조) |
| 예약 현황 | 타임별 확정/대기/입장/노쇼 수 + 방문객 명단(이름·예약번호·상태·입장 시각). **행마다 「입장 처리」 버튼** — 인터넷이 끊겨 종이 명단으로 대조한 뒤 복구 후 손으로 반영하는 경로(§2-8 U1의 짝). 확인 페이지와 같은 서버 함수를 호출하므로 첫 입장 시각 보존·중복 방지가 동일하게 적용된다 |
| 리포트 | 위 명단·집계 **엑셀 내려받기**(기존 엑셀 방식 재사용) |

## 5. 단계 분할

| 단계 | 내용 | 산출물 | 검증 |
|---|---|---|---|
| **1단계 — 예약 기반 + 관리자** | 캠페인 컬럼 3개 · 타임 표 · 티켓 표 · 서버 함수 3개 · 관리자(행사 모드 폼·리워드 잠금·타임 관리·예약 현황·리포트 엑셀) | 마이그레이션 4개 + 관리자 화면 | 관리자 화면에서 **타임 등록·수정·일괄 생성·예약 현황 0건 표시·엑셀 내려받기**까지 확인. ⚠️ 정원·대기·취소·「입장 처리」 버튼 동작은 티켓이 있어야 확인되고 방문객 화면이 없으면 티켓을 못 만든다(§4-2 함정) → 2단계 검증으로 이월 |
| **2단계 — 방문객 화면** | 캠페인 상세 타임 선택 · 행사 모드 신청 모달 · 티켓(QR) 화면 · 활동관리 대체 · 초대 링크·번호 진입 · 가입 후 복귀 | 인플루언서 앱 변경 | 테스트 계정 2개 이상으로 브라우저에서 **신청 → 정원 마감 → 대기 등록 → 취소 → 대기 1번 승격 → QR 발급**까지 통과. 여기서 만든 티켓으로 **관리자 예약 현황의 「입장 처리」 버튼**(1단계에서 이월)도 함께 확인 |
| **3-A단계 — 손입력 확인** | 자립형 확인 페이지 + **예약번호 손입력** + 입장 처리 + 중복 표시 | 신규 페이지 1개 | 휴대폰 브라우저에서 예약번호 입력 → 입장 처리 → 재입력 시 중복 표시 확인 |
| **3-B단계 — 카메라 스캔** | 같은 페이지에 QR 카메라 스캔 추가 · 권한 거부 폴백 | 같은 페이지 보강 | **실제 운영진 기기 2종 이상**으로 개발서버 스캔 리허설 |
| **4단계 — 정책 게이트** | 개인정보처리방침 개정(한·일) · 방문객 안내 문구 검수 | 정책 문서 변경 | `/약관확인` 통과 |

**의존 순서:** 1단계 → 2단계 → 3-A단계 → 3-B단계. 4단계는 2·3단계와 병행 가능.
**운영 배포는 4단계 완료 + 사용자 확인 후** 별도로 진행한다(어느 단계에도 포함하지 않는다).

**2차 보강 후보(1차에서 제외):** 개별 초대 코드 발급·사용 추적 / 취소 없는 시간 변경 / 확정·대기 안내 메일 / 동반자 신청 / **인터넷 없이 동작하는 확인 화면**(명단을 기기에 미리 저장해 오프라인 대조 — 명단 엑셀 내려받기 자체는 1단계에 포함되며, 여기서 제외하는 것은 「확인 화면이 인터넷 없이 스스로 판정하는 기능」이다) / 노쇼 통계 기반 초과 예약.

## 7. 법률·정책 게이트 (운영 배포 전 필수)

1. **개인정보처리방침 개정(한·일 동시)** — 수집 항목에 「오프라인 행사 방문 예약 정보(예약 일시·타임)」, 「입장 확인 기록(입장 시각)」 추가. 수집 목적에 「오프라인 행사 방문 예약 접수 및 입장 자격 확인」 추가. 보유 기간 명시(권고: 행사 종료 후 6개월).
2. **일반 고객 신규 가입** — 현행 이용약관은 인플루언서(제품 제공·리워드·뒷광고 표시)를 전제로 조항이 짜여 있다. 방문 예약만 하는 회원에게 그 조항이 어떻게 적용되는지 확인이 필요하다. → `/약관확인` 결과에 따라 회원 유형 구분 필요 여부를 판단.
3. **QR에 개인정보를 담지 않는다** — 의미 없는 예약번호만 담는다(§2-9).
4. **입장 기록 열람 범위** — 관리자 전체 조회, 방문객 본인은 자기 기록만.
5. **만 18세 미만 차단 유지** — 현행 연령 정책 그대로. 행사 홍보물에도 「만 18세 이상」 명시 필요(운영 협조 사항).

## 9. 사용자 확인 필요

1. **타임 정원** — 보내주신 표는 이틀차·삼일차가 타임당 「80명+@」다. 시스템에 넣을 정확한 정원(이틀차·삼일차 각각)과, 「+@」를 초과 예약으로 볼지 여부. 첫날 구간별 정원(100·100·50)은 표대로 볼지.
2. **타임 단위와 대상 범위 (두 축)** — ① 첫날을 표대로 **구간형**(11:00~13:00 100명 / 14:00~16:00 100명 / 17:00~18:00 50명)으로 둘지, **30분 단위**로 쪼갤지 ② **19:00 서포터즈 50명·브랜드사를 이 시스템에 포함할지**(현재 초안은 제외 전제). 두 답의 조합이 타임 줄 수를 32·33·45·46 중 하나로 정한다(§2-9).
3. **일정** — §6의 날짜(8월 13일 배포, 8월 14일 초대 모집 시작, 8월 18일 전후 공개 모집)가 실제 홍보 계획과 맞는지.
4. **취소 마감** — 본인 취소를 언제까지 허용할지(권고: 예약 타임 시작 2시간 전까지).
5. **QR 발급 통지** — 확정 시 메일을 보낼지(권고: 1차는 앱 안 화면만, 메일은 2차).
6. **첫날·이틀차 중복 신청** — 초대 인플루언서가 이틀차 일반 타임도 신청할 수 있게 둘지, 행사 전체에서 1타임으로 제한할지(제한하려면 캠페인을 넘나드는 중복 차단을 추가해야 함).
