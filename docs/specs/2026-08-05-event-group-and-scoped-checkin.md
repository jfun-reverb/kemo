# 현장 확인 화면을 행사 단위로 + 「행사 묶음」 도입

**작성일:** 2026-08-05
**상태:** 설계 확정 — 사용자 결정 6건 반영. 구현 착수
**관련 사양서:** `docs/specs/2026-07-30-offline-popup-ticketing.md` (§4-4 가 현장 확인 화면)
**배포:** 개발서버 먼저 → 운영은 **2차 배포(8월 19일)**. **8월 8일 1차 배포 범위 아님**

## 0. 요청

관리자 「캠페인 진행현황 → 예약 현황」에서 **그 캠페인의 현장 확인 화면으로 바로 가는 버튼**이 있으면 좋겠다. 이어서 「**현장 확인 페이지는 캠페인별이어야 한다**」.

되묻는 과정에서 「같은 행사인데 캠페인 두 개로 만들었다면 연결할 방법이 없냐」는 물음이 나왔고, 그 답으로 **「행사 묶음」**이 이번 범위에 들어왔다.

## 1. 현재 상태 (직접 확인, 2026-08-05)

### 현장 확인 페이지 `dev/event-scan.html`
자립형 페이지(빌드가 루트로 복사, `storage.js` 미사용·`sb` 직접 호출).
- `loadRoster()` 가 `event_slots` 를 **캠페인 구분 없이 전량 조회** → 날짜 탭 생성 → 고른 날짜의 타임만 남김
- 명단은 `fetchAllTickets(slotIds)` 로 **타임 기준** 조회
- 입장 기록 초기화가 `dev_reset_event_checkin` 을 **`p_campaign_id: null`**(=모든 행사)로 호출. ⚠️ 이 함수는 **개발 데이터베이스에만** 있다(운영에는 없음 — 그게 진짜 방어선)
- **실측**: 지금 날짜 탭에 「08/08」·「09/02」가 함께 뜬다 = 서로 다른 행사 캠페인이 한 화면에 섞여 있다

### 관리자 예약 현황
별도 페인이 아니라 캠페인 진행현황(`#adminPane-camp-applicants`) 안의 **탭**. 헤더 줄(`dev/admin/index.html` 1256~1261행)에 상태 탭·타임 드롭다운·「명단 엑셀」.
- **관리자 화면에서 현장 확인 페이지로 가는 링크가 지금 0개** — 이번 버튼이 유일한 진입점이 된다(북마크 제외)

### 캠페인 편집 폼 (위험 지점)
2026-08-03 에 「숨긴 칸을 규칙이 계속 읽어」 12건이 한꺼번에 터진 자리. 그 뒤 **행사 옵션을 한 곳에서 통째로 켜고 끄는 자리**가 생겼다:
- `admin-event.js` 136~137행 — `#{prefix}CampEventOpts` 를 한 줄로 표시/숨김
- `dev/admin/index.html` 366~385행 — 행사장 칸(`event_place`)이 그 묶음 **안**에 있다
- `EVENT_MODE_CLEARED_FIELDS`(1105행) = **행사 모드를 켜면 비우는 칸** 목록
- `applyEventModeFormLock` 138~143행 `if (!on)` 블록 = **행사 모드를 끄면 비우는** 자리

### 충돌 가능성 있는 기존 동작
- **「새 탭 열기 금지」 규칙**(`CLAUDE.md` 개발 워크플로)과 부딪힌다. 그 규칙은 **관리자↔인플루언서 앱 전환**을 겨냥한 것이고, 현장 확인 페이지는 제3의 자립형 화면(부스 단말에서 계속 띄워 두고 쓴다)이라 예외로 본다. **다음 세션이 되돌리지 않도록 주석에 사유를 남긴다**
- 그 외 예약·정원·입장 판정과는 **충돌 없음 — 확인 완료**. 명단을 좁히는 건 조회 조건 변경이고, 입장 처리는 서버가 예약번호 하나로 판정하므로 화면 범위와 무관하다

## 2. 의심·경우의 수

### 깨질 가능성

**① 캠페인에 완전 고정하면 8월 29일 아침 명단이 빈 화면이 된다 (UX·최대 위험)**
부스 단말은 사흘 내내 같은 자리다. 28일에 초대 전용 캠페인으로 열어두면 29일 아침에도 그 화면이고, 29일 예약자는 다른 캠페인 소속이라 명단이 빈다. 그 순간 줄이 선다.
→ **「행사 묶음」이 이 위험을 정확히 없앤다.** 묶음으로 열면 사흘이 한 화면에 들어온다.

**② 띄어쓰기 오타로 묶음이 조용히 갈라진다 (데이터)**
「REVERB팝업」과 「REVERB 팝업」이 다른 묶음이 되면, 화면은 정상으로 보이는데 명단 절반이 사라진다.
→ **별도 목록 + 정규화 유일 제약** 두 겹으로 막는다. 목록에서 고르는 것 외에 값이 생길 길이 없고, 새로 만들 때도 **공백(전각 포함)을 전부 제거하고 비교**하므로 같은 값으로 거부된다.

**③ 로그아웃 한 번이 옆 탭 관리자 화면까지 끊는다 (기술·UX)**
현장 확인 페이지와 관리자 앱은 같은 도메인·같은 로그인 저장소를 쓴다. 버튼이 생기면 **같은 브라우저에 나란히 열리는 게 기본 동선**이 되고, 부스 담당자가 「행사 끝났으니 로그아웃」을 누르면 옆 탭도 끊긴다.
→ 이번 범위에서 막지 않는다. **검증 항목으로 넣어 실제 동작을 보고** 안내 문구 필요 여부를 판단한다.

**④ 잘못된 주소·사라진 묶음으로 열렸을 때 (UX)**
지금 구조면 그냥 **빈 명단**이라, 「명단이 없다」와 「주소가 틀렸다」가 구분되지 않는다.
→ 오류 안내 후 **행사 고르기 화면**으로 보낸다. 「완전 고정」은 정상 운영 중 전환 장치를 두지 않는다는 뜻이지 막다른 골목을 만들라는 뜻이 아니다.

**⑤ 새 문구를 한쪽 언어에만 넣는다 (권한·환경)**
이 페이지는 한국어·일본어 **자체 사전**을 쓴다. 묶음 이름표·고르기·오류 안내를 양쪽에 다 넣지 않으면 일본인 운영진 화면에 한국어가 그대로 뜬다.

**⑥ 입장 기록 초기화의 사정거리 (데이터)**
지금 모든 행사가 대상이다. 화면이 「이 행사」로 보이는데 버튼이 전체를 지우면 인지와 동작이 어긋난다. 운영에는 함수가 없어 피해는 개발 환경 한정이지만, **다른 행사 검증 데이터를 통째로 날린다**.

**⑦ 편집 폼에 새 칸을 얹다가 2026-08-03 사고를 재현한다 (기술)**
아래 §4-2 에 회피 방법을 못 박는다.

## 4. 설계

### 4-1. 행사 묶음 (마이그레이션 1개)

- **묶음 목록** — 이름(필수) · 상태(사용중/보관) · 메모 + **정규화 이름 유일 제약**
  - ⚠️ 정규화는 **공백(일반·전각)을 전부 제거하고** 소문자로 비교한다.
    처음엔 회사 마스터의 공백 **압축** 패턴을 베이스로 잡았으나, 개발 데이터베이스 실측에서 **압축만으로는 「REVERB팝업」과 「REVERB 팝업」이 안 걸러진다**는 것이 드러나 완전 제거로 교체했다(291 은 수정하지 않고 292 가 함수만 재정의).
    **압축과 제거는 목적이 다르다** — 회사명은 「제이 펀」과 「제이펀」을 **다른 회사로 남기는 것이 맞아** 압축까지만 하지만, 행사 묶음은 **같은 행사로 봐야** 하므로 제거가 맞다. 같은 이름의 기법이라도 「무엇을 같다고 볼 것인가」가 다르면 그대로 가져다 쓸 수 없다
- **캠페인 연결 칸** — 묶음을 지워도 **연결만 끊기고 캠페인 저장은 안 막히게** 건다(브랜드↔회사와 동일)
- **걸지 않는 제약 2가지**: ①같은 브랜드끼리만(합동 팝업이면 브랜드가 다름) ②행사 모드만 묶기를 데이터베이스로 강제(나중에 형식이 바뀔 때 저장이 막힘)
- 접근 권한 — 조회는 관리자 전체, 만들기·고치기는 캠페인 관리자 이상. ⚠️ **「고치기」 권한은 나중에 관리 화면을 만들 때를 위한 것**이고, 이번 범위에서 화면이 쓰는 건 만들기뿐이다(아래 참조)

**★ 이번 범위는 「만들기 + 연결」까지다.** 묶음 목록·이름 수정·삭제를 위한 **별도 관리 화면은 만들지 않는다** — 묶음은 행사당 1개라 손댈 일이 드물고, 화면을 하나 더 만들면 2차 배포 일정을 잡아먹는다. 만들기는 캠페인 폼의 **즉석 추가**로 충분하다. 이름 수정·삭제가 필요해지면 관리자 도구(SQL 편집기)로 처리하고, 반복되면 그때 관리 화면을 별도 사양으로 만든다.
→ 그래서 §7 검증도 이름 수정·삭제는 **관리자 도구로 값을 바꾼 뒤 화면 반영을 보는** 절차로 적었다.

**보관(`archived`) 상태 묶음의 취급**: 캠페인 폼 선택지와 현장 화면 고르기 목록 **양쪽에서 제외**한다(새로 고를 수 있는 것은 사용중인 것뿐).
**단 캠페인 폼은 예외가 하나 있다 — 편집 중인 캠페인이 이미 연결한 보관 묶음은 선택지에 남긴다**(§4-2 3번. 빼면 그 캠페인을 저장하는 것만으로 연결이 끊긴다).
이미 보관 묶음에 연결된 캠페인은 연결을 유지하고, 주소로 그 묶음을 지정해 연 현장 화면도 정상 동작한다 — 보관은 「새로 고르지 못하게」일 뿐 기존 연결을 끊는 장치가 아니다.

**동시 저장 방어**: 새 칸은 마이그레이션 275 제외 목록에 없어 **자동 보호 대상**. 별도 작업 없음.
**변경 이력 화이트리스트(265·266)**: **넣지 않는다.** 행사 관련 앞선 칸 3개가 모두 같은 판단으로 빠져 있고, 세 곳이 어긋나면 캠페인 저장 트랜잭션 전체가 실패한다. 남는 값도 사람이 못 읽는 식별자라 이력의 목적에 기여하지 못한다.

### 4-2. 캠페인 편집 폼 — 2026-08-03 사고 회피 (★ 이 절이 이번 작업의 핵심 위험)

| 사고 유형 | 이번 회피 방법 |
|---|---|
| 표시 규칙을 호출자에 둬서 비동기 렌더가 되살림 | **새 표시 코드를 0줄로 만든다.** 새 칸을 `#{prefix}CampEventOpts` 묶음 **안**에 넣으면 기존 한 줄이 함께 켜고 끈다 |
| 숨김과 값 지우기를 한 함수에 묶어 멀쩡한 값이 지워짐 | ⚠️ **`EVENT_MODE_CLEARED_FIELDS` 에 넣지 않는다** — 그건 「켜면 비우는」 목록이라 방향이 정반대다. 넣으면 **행사 캠페인을 저장할 때마다 묶음이 지워진다.** 대신 `applyEventModeFormLock` 의 `if (!on)` 블록(=끄면 비우는 자리)에 한 줄 추가 |
| 숨긴 값을 검증이 읽어 저장이 막힘 | **필수 검증을 만들지 않는다.** 묶음은 선택 사항이다(대부분의 행사는 캠페인 1개). 「행사인데 묶음이 없다」를 차단으로 만들면 **지금 운영 중인 행사 캠페인 2개가 즉시 저장 불가**가 된다 |

**함께 손대야 하는 4곳** (빠뜨리면 조용히 어긋남)
1. `loadEventSettingsIntoEditForm` — 저장된 묶음을 선택 상태로 (행사장 칸 채우는 줄 옆)
2. `resetEventFormFields` — 폼 비울 때 묶음 선택 초기화
3. 신규·편집 두 폼의 선택지 목록 채우기 + 「신규 묶음 만들기」(브랜드 신규 등록과 같은 즉석 입력 방식). **보관 묶음은 선택지에서 제외** — ⚠️ **단 편집 중인 캠페인이 이미 연결한 보관 묶음은 선택지에 남긴다.** 빼면 그 캠페인을 열 때 칸이 빈 채로 열리고, 다른 칸만 고쳐 저장해도 4번이 빈 값을 읽어 **경고 없이 연결이 끊긴다**(필수 검증을 안 만들기로 했으므로 아무도 못 알아챈다)
4. **저장할 때 묶음 값 읽기** — 신규 등록·편집 저장 두 곳(`admin.js`). ⚠️ 이걸 빠뜨리면 **선택은 되는데 저장이 안 되는** 상태로 끝난다

**행사 모드를 처음 켤 때 묶음 칸이 비어 있는 이유**: 일반 캠페인은 연결값 자체가 없어 폼을 채울 때 자연히 빈 상태가 된다. **비우는 장치를 따로 두지 않는다** — 두면 위 표 2행(**숨김과 값 지우기를 한 함수에 묶는** 사고)과 같은 방향이 된다.

⚠️ 같은 파일에 「모듈 전역 기억값을 캠페인마다 안 비워 다음 캠페인에 옛 값이 새던」 사고 기록이 있다. **묶음 목록만 캐시하고 캠페인별 선택값은 캐시하지 않는다.**

### 4-3. 현장 확인 화면

- 주소로 **캠페인 또는 묶음**을 받는다
- 미지정·잘못된 값 → **행사 고르기 화면**(행사가 1개면 자동 선택)
  - ⚠️ **고르기 화면의 목록 단위도 묶음**이다. 묶음에 속한 캠페인을 개별 항목으로도 늘어놓으면 담당자가 「첫날」만 골라 이틀차 명단이 비는 사고가 되살아난다 — 묶음을 만든 이유가 사라진다
  - ⚠️ 고른 뒤 **주소에 식별자를 써넣지 않는다**. 써넣으면 새로고침해도 같은 행사로 돌아와 잘못 골랐을 때 탈출구가 없다
- ⚠️ 고르기 화면으로 돌아가는 것은 **오류로 열렸을 때와, 주소에 식별자가 없는 상태에서 새로고침했을 때뿐**이다. 관리자 버튼으로 연 화면은 주소에 식별자가 있으므로 **새로고침해도 그 행사가 유지된다** — 이 조건이 빠지면 부스 화면이 새로고침마다 고르기 화면으로 튕긴다. 이건 결정 1(「명단을 보는 중에는 전환 장치를 두지 않는다」)의 **의도된 예외** — 완전 고정은 정상 운영 중 실수로 다른 행사로 넘어가는 것을 막자는 뜻이지, 잘못 골랐을 때 막다른 골목을 만들라는 뜻이 아니다. 「전체 표시」를 지운 것과 방향이 다르지 않다(그건 **명단을 보는 중에** 범위를 넓히는 장치였다)
- 화면 맨 위에 이름표. **묶음이면 「묶음 이름 · 캠페인 2개」를 반드시 표시** — 없으면 캠페인 A 화면에서 눌렀는데 B 이름이 명단에 나와 「고장 났다」로 읽힌다
- **보관 상태(`archived`) 묶음은 고르기 목록에서 제외**(§4-1). 주소로 그 묶음을 지정해 열면 정상 동작한다. ⚠️ 여기엔 **§4-2 3번 같은 예외가 필요 없다** — 편집 폼과 달리 이 화면엔 「이미 연결한 것」이라는 상태가 없고, 주소로 지정해 열린 화면은 목록을 거치지 않기 때문이다
- 명단·날짜 탭을 그 범위로 한정. **보관 삭제된 캠페인 제외**(마이그레이션 254~258 은 캠페인 행을 남기므로, 안 거르면 지운 행사의 빈 타임이 띠로 남는다)
- 입장 기록 초기화 사정거리를 현재 범위로 좁힌다
- 새 문구는 **한국어·일본어 양쪽** 등록

### 4-4. 관리자 버튼

- 예약 현황 탭 헤더 「명단 엑셀」 옆, **새 탭**
- 묶음이 있으면 **묶음으로**, 없으면 **캠페인으로** 연다. 버튼은 1개이고 이름도 하나 — 어느 것을 가리킬지는 자동 결정
- 주소에 도메인을 붙이지 않는다(개발·운영 어느 쪽에서 눌러도 그 도메인 안에서 열리게)
- **새 탭 예외 사유를 주석에 명시**

## 5. 「다른 행사 예약번호 알림」을 넣지 않는 이유

- 「같은 행사인데 다른 캠페인」 → **묶음이 해소**
- 「진짜 다른 행사」 → 날짜가 달라 **기존 되묻기**(마이그레이션 287)가 잡는다
- **남는 구멍**: 「진짜 다른 행사인데 날짜까지 같은 경우」 → 아무것도 안 잡는다. 8월 28~30일에 겹칠 다른 팝업이 없어 **현실적으로 0**이고, 개발 데이터베이스의 검증용 캠페인에서나 재현된다

이 구멍 하나 때문에 입장 확인 함수를 **행사 2주 전에 다시 정의하는 것은 이득보다 위험이 크다.** 재정의 시 베이스를 **287** 로 잡아야 하고(283 으로 잡으면 「다른 날 되묻기」가 통째로 사라진다), 이 프로젝트에서 실제로 같은 유형의 사고가 난 적이 있다.

## 7. 검증 계획

**묶음 만들기·오타 방지**
- 「REVERB팝업」 뒤에 「REVERB 팝업」(공백 하나 차이) → **거부되는지**
- 보관 상태 묶음이 **(그 묶음에 연결되지 않은)** 캠페인 폼 선택지·고르기 목록에서 **안 보이는지**
- ★ **보관 묶음에 연결된 캠페인을 열어 다른 칸만 고쳐 저장 → 묶음 연결이 유지되는지.** 여기가 틀리면 경고 없이 연결이 끊긴다(§4-2 3번의 예외가 동작하는지 보는 항목)
- ⚠️ 아래 두 항목은 이번 범위에 관리 화면이 없으므로(§4-1) **관리자 도구로 값을 바꾼 뒤** 화면 반영을 본다
  - 묶음 이름을 바꾸면 현장 화면 이름표가 따라 바뀌는지
  - 묶음을 지워도 캠페인 저장이 막히지 않고 연결만 끊기는지

**편집 폼 사고 재발 확인 (2026-08-03 유형)**
- 행사 모드를 **껐다 켰다** 반복 → 묶음 선택이 엉뚱하게 바뀌지 않는지
- 캠페인 A(묶음 있음) 편집 → 나가서 B(묶음 없음) 편집 → **B 에 A 의 묶음이 옮겨붙지 않는지**
- 일반 캠페인에서 행사 모드를 처음 켤 때 묶음 칸이 **빈 상태**인지
- 묶음을 비운 채 저장 → **막히지 않는지**
- 행사 모드를 끄고 저장 → 묶음 연결이 **비워지는지**

**동시 저장** — 두 창에서 같은 행사 캠페인을 열고 한쪽에서 묶음만 바꿔 저장 → 다른 쪽이 충돌로 막히는지

**현장 화면**
- 묶음으로 열기 → 캠페인 2개 날짜가 **모두** 날짜 탭에, 이름표에 「캠페인 2개」
- 캠페인으로 열기(묶음 없음) → 그 캠페인만
- 지운 묶음 식별자 → 빈 명단이 아니라 **오류 안내 → 고르기 화면**
- 보관 삭제한 캠페인이 묶음에 있을 때 → 명단에 **안 섞이는지**
- 고르기 화면에 묶음 속 캠페인이 **개별로 또 뜨지 않는지**
- 일본어 전환 → 새 문구 전부 일본어
- **입장 기록 초기화 사정거리**(§2-⑥ 이 위험으로 지목한 항목) — 묶음 A 로 연 화면에서 초기화 → **다른 행사(캠페인 B)의 입장 기록이 남아 있는지**
- 입장 처리 회귀 — 오늘 예약 성공 / 다른 날 되묻기, 이때 **기록이 안 남는지**(판정은 마이그레이션 287 의 「되묻는 단계에서는 기록하지 않는다」 기준)
- **로그아웃 영향** — 현장 확인 탭에서 로그아웃 → 옆 관리자 탭이 어떻게 되는지 실제로 보고 안내 필요 여부 판단

**관리자 버튼 (3단계 산출물 — 틀려도 화면은 정상으로 보이므로 반드시 확인)**
- **묶음이 있는** 캠페인의 버튼 → **묶음으로** 열리는지(명단에 캠페인 2개 날짜가 다 나오는지). ⚠️ 여기가 틀리면 캠페인으로 열려 **명단 절반만 나오고도 정상처럼 보인다** — §2-① 과 같은 사고
- **묶음이 없는** 캠페인의 버튼 → 그 캠페인으로 열리는지
- 개발서버에서 누르면 개발 도메인, 운영에서 누르면 운영 도메인 안에서 열리는지
- 새 탭으로 열리고 **원래 보던 예약 현황이 그대로 남아 있는지**

⚠️ 예약·입장 관련 함수는 **관리자 도구(SQL 편집기)로 재현이 안 된다**(로그인 사용자 가드). 반드시 브라우저에서 테스트 계정으로.
