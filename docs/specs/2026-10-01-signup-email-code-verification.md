### 왜 직접 만드나 (결정 3의 근거)
인증 서비스(Supabase)의 코드 기능은 **코드를 보내는 순간 계정을 만든다.** 그러면 ①이름·동의 정보가 없는 빈 계정이 생기고 ②이미 가입된 주소면 코드 확인이 곧 **그 사람으로 로그인**이라, 이어서 비밀번호를 정하면 남의 비밀번호가 바뀌며 ③가입 트리거(382·420)의 동의 시각·생년월일 보호가 무력화된다. 가입 단추를 막아도 세 문제는 그대로다(계정은 「인증하기」에서 이미 생긴다).

## 의심·경우의 수

1. 🔴 **배포 순서를 어기면 가입이 막힌다**(기술) — 관문을 새 화면보다 먼저 **강제**하면 옛 화면(확인증을 안 보냄)의 가입이 전부 거부된다 → 관문에 **대기/강제 스위치**를 두고 순서를 고정한다(설계 ② · 「단계」)
2. 🔴 **인증 계정 표 트리거가 틀리면 가입이 전면 중단**(기술) — 362 를 아직 안 건 이유와 같다. 관리자 초대(245·417)·감사용 계정 생성(179)처럼 다른 경로로 계정을 만드는 곳을 통과시켜야 한다 → 설계 ②의 「인증 서비스가 넣을 때만 검사」. 강제 상태에서 문제가 나면 **대기로 되돌려 가입을 살린다**. ⚠️ 단 고쳐 쓰기 관문(설계 ②)의 **코드 자체가 틀려** 로그인이 막히면(조건을 잘못 써서 인증 완료 행을 통과시키지 못하는 등) **대기로 되돌려도 살아나지 않는다** — 그때는 그 트리거를 끈다(개발이 끄는 SQL 을 단계 1 에서 미리 준비. 완료 기준 7·13-③으로 사전 확인). 🔴 끈 동안은 경우의 수 12-①·③ 우회가 다시 열린다 — 고쳐서 **바로 다시 켠다**(그 사이 스위치가 강제면 옛 방식으로 지나가는 것은 **기존 미인증 계정의 재가입과 재설정 링크 인증**(경우의 수 12-①·③)이다. 스위치가 대기인 채 끄면 그 자체로 옛 흐름 구간이라 새 미인증 가입도 생긴다 — 설계 ⑤ 「안전장치」). **설정 표를 못 읽는 사고는 두 관문 모두 대기로 보고 통과하므로 저절로 풀린다**(설계 ②). 스위치로도 안 풀리는 것은 **조건을 잘못 쓴 코드 오류**다 — 고쳐 쓰기 관문이면 로그인이, 삽입 관문이면 정상 가입이 막힌다. 그때는 **그 관문의 트리거를 끈다**(두 관문 각각 끄고 다시 켜는 SQL 을 단계 1 에서 준비 — 완료 기준 15). 🔴 **삽입 관문을 끌 때는 스위치도 반드시 대기로 둔다**(사용자 결정 2026-10-01) — 강제인 채 삽입 관문만 끄면 대조 없이 생긴 미인증 계정의 확인 메일 발송이 고쳐 쓰기 관문에 막혀 아무도 인증할 수 없게 될 수 있다. 그래서 삽입 관문을 끈 동안은 곧 대기 구간이고, 대조가 없어 새 화면 가입도 미인증으로 생긴다(설계 ⑤ 「안전장치」 ②의 옛 흐름 구간). 재설정 메일 요청 검사는 고쳐 쓰기 관문 안에 있어 함께 꺼진다(경우의 수 12-③)

12. 🔴 **미인증 계정이 있는 주소로 다시 가입하면 인증 서비스는 새 계정을 만들지 않고 그 계정을 고쳐 쓴다(UPDATE)**(기술·보안 — 2026-10-01 개발서버 실측: 줄 수 1 그대로·`created_at` 그대로·`confirmation_sent_at` 갱신·확인 메일 재발송, `email_confirmed_at` 계속 NULL) — 삽입 직전 관문을 우회한다. ①확인증 없이 다시 가입한 뒤 재발송된 링크로 인증하면 **인증번호를 건너뛴다** ②새 화면으로 인증번호를 확인하고 가입한 정상 사용자도 관문이 안 돌아 **인증 완료 표시가 없고, 회원 행에는 옛 가입 값이 남는다** → 설계 ① 확인 함수의 옛 미인증 계정 정리(②를 막음) + 설계 ② 고쳐 쓰기 관문(①을 막음). 사용자 결정 2026-10-01 「둘 다」 ③ 🔴 **비밀번호 재설정 링크로도 인증을 건너뛴다**(2026-10-01 개발서버 실측 — 「확인 메일」 설정 켬, 새로 가입하고 확인 링크는 안 누른 계정): 재설정 메일 요청 때 `recovery_sent_at` 만 바뀌고(`confirmation_sent_at` 그대로), **링크를 누르는 순간 비밀번호를 바꾸지 않아도** `email_confirmed_at`·`last_sign_in_at` 이 같은 시각으로 채워져 인증 완료 + 로그인 상태가 된다 → 고쳐 쓰기 관문 조건에 안 걸린다. **사용자 결정(2026-10-01): 이 길도 막는다.** 막는 방법(기획 결정) — **고쳐 쓰기 관문의 검사 조건에 「재설정 메일 요청(`recovery_sent_at` 이 바뀜)」을 더한다**(설계 ②). 그래서 ①확인 메일 재발송과 **같은 규칙**을 따른다 — 미인증 행 + 인증 서비스 역할일 때만, 강제면 거부·대기면 통과·설정 표를 못 읽거나 예외면 통과, 비상 때는 같은 트리거를 끈다(별도 장치·별도 끄기 명령 없음). 막는 지점을 **링크 클릭이 아니라 메일 요청**으로 둔 이유: 링크 클릭 순간은 정상적인 확인 메일 링크 인증(대기 구간의 옛 흐름)과 칸 변화가 같아 가르기 어렵고, 요청에서 막으면 링크 자체가 나가지 않는다. 결과: **강제 상태에서 미인증 계정은 비밀번호 재설정 메일을 받을 수 없다** — 미인증 계정은 원래 로그인이 안 되고, 같은 주소로 새 화면에서 인증번호를 확인하면 옛 계정이 지워지고 새로 가입된다(설계 ① — 다른 기록이 있는 계정은 지우지 않고 운영팀 문의 안내). 인증 완료 회원의 재설정은 `OLD.email_confirmed_at` 이 있어 관문을 바로 통과하므로 그대로다. ⚠️ 비밀번호 찾기 화면은 계정 열거 방지 때문에 성공·실패를 같은 문구로 보여야 한다 — 요청이 거부돼도 화면이 「등록된 계정이라면 보냈습니다」와 다른 말을 하지 않는지 확인한다(완료 기준 13-⑤). ⚠️ 남는 구간: 스위치가 대기이거나 설정 표를 못 읽는 동안, 고쳐 쓰기 관문을 끈 동안, 강제 상태에서 그 관문이 판정 중 예외로 통과한 경우(①과 같다), 그리고 **강제 전환 전에 요청해 이미 받은 재설정 링크**(링크 유효시간 동안 — 짧아 감수)

### 의도와 다르게 읽힐 수 있는 곳
- 🔴 이 문서의 「인증」·「미인증」은 **이메일 인증**(인증 계정의 `email_confirmed_at`)만 뜻한다. 관리자 인플루언서 관리의 **「인증」 상태(운영자가 표시하는 인증/위반/블랙리스트 — `setInfluencerVerified`)와 무관**하다. 정기 삭제 대상도 이메일 인증 전 계정뿐이다
- 「인증번호 확인」은 **가입 완료가 아니다** — 확인 뒤에도 「登録する」를 눌러야 계정이 생긴다. 확인만 하고 떠나면 계정은 남지 않는다(번호 기록은 정기 삭제 — 설계 ①)
- 비밀번호 찾기·관리자 초대·로그인은 **바뀌지 않는다** — 기존 회원이 거치는 단계는 하나도 늘지 않는다(결정 5)(단, 강제 상태에서 **미인증 계정의 재설정 메일 요청은 거부된다** — 경우의 수 12-③. 인증 완료 회원은 불변)

## 설계

### ① 인증번호 발급·확인 — 익명 서버 함수 + 표 (243 패턴)
- **표 하나**(이름은 개발이 정함): `email_hash`(정규화 = 앞뒤 공백 제거 + 소문자, sha256) · `code_hash` · `expires_at` · `attempts` · `verified_at` · `ticket_hash` · `ticket_expires_at` · `ticket_used_at` · `invalidated_at` · `created_at`. **원문 이메일·원문 번호는 저장하지 않는다.** 행 단위 보안 정책 켜고 정책 없음(서버 함수만)
- **발송 함수**(익명): 이메일 형식 검사 → 요청 제한 판정 → 6자리 번호 생성 → Brevo 발송(인플루언서 메일 4줄 푸터 의무) → 해시 저장. 🔴 **가입 여부와 관계된 갈래는 같은 응답**(이미 가입된 주소도 「보냈습니다」) — 계정 존재·탈퇴 여부를 드러내지 않는다. 이미 가입된 주소에도 **실제로 번호를 보낸다**(경우의 수 7 — 안 보내면 메일 도착 여부로 존재가 드러난다). **발송 제한에 걸리면 보내지 않고 「잠시 뒤에 다시」 응답**(+ 다시 보낼 수 있는 시각) — 제한은 주소의 가입 여부와 무관하게 똑같이 걸리므로 알려도 존재가 드러나지 않는다. 「보냈습니다」로 꾸미면 화면은 새 남은 시간을 그리는데 서버는 옛 번호 기준이라 어긋난다. 새 번호를 보내면 **새 행**을 만들고 그 주소의 이전 행은 무효 표시(`invalidated_at` — 덮어쓰지 않는다. 재발송을 세려면 행이 남아야 한다). **실제로 보낸 경우**(가입 여부와 무관하게 — 이미 가입된 주소 포함) 응답에 새 번호 기준의 `번호 만료 시각`·`재발송 가능 시각`을 싣는다(설정 표 값에서 계산 — 가입 여부에 따라 달라지지 않으므로 「같은 응답」 원칙과 맞는다). 발송 제한 응답에는 `다시 보낼 수 있는 시각`만 싣는다(번호를 새로 만들지 않았으므로)
- **확인 함수**(익명): 번호 대조 → 맞으면 **확인증**(난수) 발급, 해시만 저장. 응답에 `확인증 만료 시각`을 싣는다. 틀리면 `attempts`+1, **상한 도달 시 그 번호 무효**(재발송 필요)
  - 🔴 **번호가 맞으면 같은 주소의 옛 미인증 계정을 지운다**(경우의 수 12-②) — 대상은 `email_confirmed_at` 이 비어 있고 설계 ⑤의 「다른 기록」이 없는 계정. 인증 계정과 회원 행 **둘 다** 지운다(설계 ⑤와 같은 방식 — 연쇄 삭제가 아니다). 그래야 이어지는 가입이 새 계정 만들기 경로를 타서 관문을 거친다. 다른 기록이 있어 못 지우면 확인증을 내주지 않고 「운영팀에 문의」 안내(그 주소의 주인임이 방금 확인됐으므로 알려도 된다)
- 시작값(사용자 결정 2026-10-01 — 「운영에서 재 보고 줄일 수 있으면 줄인다」): 번호 유효 **10분** · 재발송 대기 **60초** · 틀린 횟수 **5회** · 주소별 발송 **시간당 5회** · 전역 발송 상한(개발이 운영 가입량 보고 정함) · 확인증 유효 **15분**(폼 마저 채우는 시간)
- 🔴 **수치는 코드에 박지 않는다** — 설계 ② 설정 표에 함께 두고 발송·확인 함수·관문·정기 삭제 예약 둘(번호 기록·미인증 계정 — 설계 ①·⑤)이 거기서 읽는다(바꿀 때 배포 없이 SQL 로 — 단 보관 30일·삭제 7일은 방침 절차가 먼저, 설계 ②). 화면은 숫자를 갖지 않는다 — 번호 남은 시간·재발송 대기·확인증 만료를 **전부 함수 응답의 시각**으로 그린다
- **운영 측정 → 단축**(단계 4): 표의 `created_at`(발송)과 `verified_at`(확인) 차이를 모은다. 근거: 이메일은 즉시 도착을 보장하지 않고, 일본 휴대폰 회사 메일(docomo·softbank 등)은 지연·필터가 잦다. 비교 기준 — 미국 표준기술연구소 지침 10분 이내 / 한국 서비스 3~5분(문자 관행) / 해외 이메일 번호 15~30분
- 오래된 행은 정기 삭제 — **30일 지난 것**(이 기간도 설정 표의 수치 — 설계 ②)(단계 4 측정 기간을 덮는다. 원문 이메일·번호가 없고 해시만 있다. 보관 기간 문구는 단계 0 `/약관확인` 결과대로 방침에 넣는다 — 「단계 0 실측 결과」) — 예약 실행 1개

### ② 가입 관문 — 인증 계정 표 `BEFORE INSERT` 트리거 + 설정 표
- `signUp` 의 `options.data` 에 **확인증**을 함께 싣는다 → 트리거가 `NEW.raw_user_meta_data` 에서 꺼내 대조: 확인증 해시 일치 + 미만료 + 미사용 + **같은 이메일**(정규화 비교)
  - **맞으면**: `ticket_used_at` 기록(1회용) + **`NEW.email_confirmed_at` 을 지금 시각으로**(그 자리에서 인증 완료 — 로그인·응모 화면 검사 `application.js:1154` 에도 맞는다)
  - **확인증이 없거나 틀리면**(만료·사용됨 포함): 스위치가 **대기**면 지금처럼 통과(인증 완료 표시 없음 — 옛 흐름, 확인 메일 링크로 인증), **강제**면 거부. 🔴 **거부 사유는 회원에게 전달되지 않는다** — 인증 서비스가 트리거의 메시지를 일반 데이터베이스 오류로 덮어(362 와 같은 결론) 화면은 코드 구분 없이 일반 가입 실패 문구(`showSignupFailure`)로 끝난다. 그래서 막는 일은 **화면(인증 전 「登録する」 비활성 — 결정 2)이 먼저**이고 관문은 화면을 우회한 호출의 최종 방어선이다(고쳐 쓰기 관문의 재가입 거부도 같다. 단 재설정 메일 요청 거부는 화면이 막지 않아 관문이 유일한 차단이고, 비밀번호 찾기 화면은 성공 때와 같은 문구를 보인다 — 경우의 수 12-③·완료 기준 13-⑤). 관리자 오류 로그에 「미해결」로 쌓이는 것도 362 와 같다
- **설정 표** — 한 줄(이름은 개발이 정함). 칸: 스위치(기본 **대기**) · **스위치를 마지막으로 바꾼 시각**(설정 표 변경 트리거가 스위치가 바뀔 때마다 찍는다. 사람이 넣지 않는다. 참고 기록) · 수치 여덟(설계 ①의 시작값 여섯 + 번호 기록 보관 30일 + 미인증 계정 삭제 기간 7일 — 설계 ⑤). 바꾸는 것은 SQL 편집기로(화면 없음). 🔴 **보관 30일·삭제 7일을 바꾸려면 방침 개정 → 시행 7일 전 공지 → 시행일 뒤에 설정 값 변경** 순서(방침에 일수가 적힌다 — 「단계 0 실측 결과」와 같은 절차). 번호 유효시간 등 나머지 여섯은 방침에 없어 바로 바꿔도 된다. 스위치는 **강제 → 대기로도 바꿀 수 있다**(사고 대응 — 경우의 수 2. 관문 코드 자체가 틀려 로그인·가입이 막히는 사고는 스위치로 안 풀린다 — 그 관문의 트리거를 끄는 SQL 을 쓴다. 삽입 관문을 끌 때는 스위치도 대기로, 경우의 수 2)
- 🔴 **검사 대상은 인증 서비스가 넣는 행만** — 관리자 초대(245·417)·감사용 계정(179) 등 데이터베이스 함수·편집기 경로는 통과. ✅ 이 두 경로는 **스스로 인증 완료 시각을 `now()` 로 넣는다**(`417:609`, `179:536~538` 확인). 판별은 **접속 역할** — 인증 서비스 삽입은 `supabase_auth_admin`(단계 0 실측 확정)으로 들어온 삽입만 검사. ⚠️ 362 의 「`auth.uid() IS NULL` 통과 금지」는 여기서도 유효(가입이 그 상태)

### ⑤ 미인증 계정 정기 삭제 (결정 4)
