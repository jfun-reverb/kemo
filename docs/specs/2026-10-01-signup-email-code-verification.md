### 왜 직접 만드나 (결정 3의 근거)
인증 서비스(Supabase)의 코드 기능은 **코드를 보내는 순간 계정을 만든다.** 그러면 ①이름·동의 정보가 없는 빈 계정이 생기고 ②이미 가입된 주소면 코드 확인이 곧 **그 사람으로 로그인**이라, 이어서 비밀번호를 정하면 남의 비밀번호가 바뀌며 ③가입 트리거(382·420)의 동의 시각·생년월일 보호가 무력화된다. 가입 단추를 막아도 세 문제는 그대로다(계정은 「인증하기」에서 이미 생긴다).

### 의도와 다르게 읽힐 수 있는 곳
- 🔴 이 문서의 「인증」·「미인증」은 **이메일 인증**(인증 계정의 `email_confirmed_at`)만 뜻한다. 관리자 인플루언서 관리의 **「인증」 상태(운영자가 표시하는 인증/위반/블랙리스트 — `setInfluencerVerified`)와 무관**하다. 정기 삭제 대상도 이메일 인증 전 계정뿐이다
- 「인증번호 확인」은 **가입 완료가 아니다** — 확인 뒤에도 「登録する」를 눌러야 계정이 생긴다. 확인만 하고 떠나면 계정은 남지 않는다(번호 기록은 정기 삭제 — 설계 ①)
- 비밀번호 찾기·관리자 초대·로그인은 **바뀌지 않는다** — 기존 회원이 거치는 단계는 하나도 늘지 않는다(결정 5)

## 설계

### ① 인증번호 발급·확인 — 익명 서버 함수 + 표 (243 패턴)
- **표 하나**(이름은 개발이 정함): `email_hash`(정규화 = 앞뒤 공백 제거 + 소문자, sha256) · `code_hash` · `expires_at` · `attempts` · `verified_at` · `ticket_hash` · `ticket_expires_at` · `ticket_used_at` · `invalidated_at` · `created_at`. **원문 이메일·원문 번호는 저장하지 않는다.** 행 단위 보안 정책 켜고 정책 없음(서버 함수만)
- **발송 함수**(익명): 이메일 형식 검사 → 요청 제한 판정 → 6자리 번호 생성 → Brevo 발송(인플루언서 메일 4줄 푸터 의무) → 해시 저장. 🔴 **가입 여부와 관계된 갈래는 같은 응답**(이미 가입된 주소도 「보냈습니다」) — 계정 존재·탈퇴 여부를 드러내지 않는다. 이미 가입된 주소에도 **실제로 번호를 보낸다**(경우의 수 7 — 안 보내면 메일 도착 여부로 존재가 드러난다). **발송 제한에 걸리면 보내지 않고 「잠시 뒤에 다시」 응답**(+ 다시 보낼 수 있는 시각) — 제한은 주소의 가입 여부와 무관하게 똑같이 걸리므로 알려도 존재가 드러나지 않는다. 「보냈습니다」로 꾸미면 화면은 새 남은 시간을 그리는데 서버는 옛 번호 기준이라 어긋난다. 새 번호를 보내면 **새 행**을 만들고 그 주소의 이전 행은 무효 표시(`invalidated_at` — 덮어쓰지 않는다. 재발송을 세려면 행이 남아야 한다). **실제로 보낸 경우**(가입 여부와 무관하게 — 이미 가입된 주소 포함) 응답에 새 번호 기준의 `번호 만료 시각`·`재발송 가능 시각`을 싣는다(설정 표 값에서 계산 — 가입 여부에 따라 달라지지 않으므로 「같은 응답」 원칙과 맞는다). 발송 제한 응답에는 `다시 보낼 수 있는 시각`만 싣는다(번호를 새로 만들지 않았으므로)
- **확인 함수**(익명): 번호 대조 → 맞으면 **확인증**(난수) 발급, 해시만 저장. 응답에 `확인증 만료 시각`을 싣는다. 틀리면 `attempts`+1, **상한 도달 시 그 번호 무효**(재발송 필요)
- 시작값(사용자 결정 2026-10-01 — 「운영에서 재 보고 줄일 수 있으면 줄인다」): 번호 유효 **10분** · 재발송 대기 **60초** · 틀린 횟수 **5회** · 주소별 발송 **시간당 5회** · 전역 발송 상한(개발이 운영 가입량 보고 정함) · 확인증 유효 **15분**(폼 마저 채우는 시간)
- 🔴 **수치는 코드에 박지 않는다** — 설계 ② 설정 표에 함께 두고 발송·확인 함수·관문·정기 삭제 예약 둘(번호 기록·미인증 계정 — 설계 ①·⑤)이 거기서 읽는다(바꿀 때 배포 없이 SQL 로 — 단 보관 30일·삭제 7일은 방침 절차가 먼저, 설계 ②). 화면은 숫자를 갖지 않는다 — 번호 남은 시간·재발송 대기·확인증 만료를 **전부 함수 응답의 시각**으로 그린다
- **운영 측정 → 단축**(단계 4): 표의 `created_at`(발송)과 `verified_at`(확인) 차이를 모은다. 근거: 이메일은 즉시 도착을 보장하지 않고, 일본 휴대폰 회사 메일(docomo·softbank 등)은 지연·필터가 잦다. 비교 기준 — 미국 표준기술연구소 지침 10분 이내 / 한국 서비스 3~5분(문자 관행) / 해외 이메일 번호 15~30분
- 오래된 행은 정기 삭제 — **30일 지난 것**(이 기간도 설정 표의 수치 — 설계 ②)(단계 4 측정 기간을 덮는다. 원문 이메일·번호가 없고 해시만 있다. 보관 기간 문구는 단계 0 `/약관확인` 결과대로 방침에 넣는다 — 「단계 0 실측 결과」) — 예약 실행 1개

### ② 가입 관문 — 인증 계정 표 `BEFORE INSERT` 트리거 + 설정 표

  - **맞으면**: `ticket_used_at` 기록(1회용) + **`NEW.email_confirmed_at` 을 지금 시각으로**(그 자리에서 인증 완료 — 로그인·응모 화면 검사 `application.js:1154` 에도 맞는다)
  - **확인증이 없거나 틀리면**(만료·사용됨 포함): 스위치가 **대기**면 지금처럼 통과(인증 완료 표시 없음 — 옛 흐름, 확인 메일 링크로 인증), **강제**면 거부(코드값은 개발이 정하고 `friendlyErrorJa` 등록)
- **설정 표** — 한 줄(이름은 개발이 정함). 칸: 스위치(기본 **대기**) · **스위치를 마지막으로 바꾼 시각**(설정 표 변경 트리거가 스위치가 바뀔 때마다 찍는다. 사람이 넣지 않는다. 참고 기록) · 수치 여덟(설계 ①의 시작값 여섯 + 번호 기록 보관 30일 + 미인증 계정 삭제 기간 7일 — 설계 ⑤). 바꾸는 것은 SQL 편집기로(화면 없음). 🔴 **보관 30일·삭제 7일을 바꾸려면 방침 개정 → 시행 7일 전 공지 → 시행일 뒤에 설정 값 변경** 순서(방침에 일수가 적힌다 — 「단계 0 실측 결과」와 같은 절차). 번호 유효시간 등 나머지 여섯은 방침에 없어 바로 바꿔도 된다. 스위치는 **강제 → 대기로도 바꿀 수 있다**(사고 대응 — 경우의 수 2)
- 🔴 **검사 대상은 인증 서비스가 넣는 행만** — 관리자 초대(245·417)·감사용 계정(179) 등 데이터베이스 함수·편집기 경로는 통과. ✅ 이 두 경로는 **스스로 인증 완료 시각을 `now()` 로 넣는다**(`417:609`, `179:536~538` 확인). 판별은 **접속 역할** — 인증 서비스 삽입은 `supabase_auth_admin`(단계 0 실측 확정)으로 들어온 삽입만 검사. ⚠️ 362 의 「`auth.uid() IS NULL` 통과 금지」는 여기서도 유효(가입이 그 상태)
- 🔴 확인증 열쇠는 **관문이 `BEFORE INSERT` 에서 `NEW.raw_user_meta_data` 에서 직접 지우고**, `_strip_signup_meta`(383) 목록에도 추가한다(이후 저장 때 되살아나지 않게). ⚠️ 가입 트리거 안의 같은 목록(382 판은 420 으로 덮였고 사본은 `420:149~154`)은 **맞추지 않는다** — 맞추려면 420 을 재정의해야 해 아래 「420 무변경」과 부딪힌다(사용자 결정 2026-10-01, 개발 세션 대조로 정정)
- 대조 로직 밖의 예외는 **강제 상태에서만 거부**로 닫는다(통과로 열면 관문이 무력화). **대기 상태에서는 예외가 나도 통과**(옛 흐름 보호). 실제 가입 확인은 **단계 1(대기)·단계 3(강제) 둘 다**(383 선례)
- 가입 트리거(420)·생년월일·동의 시각 경로는 **무변경**

### ③ 가입 화면 `dev/index.html` + `dev/js/auth.js`
- 이메일 칸 옆 「認証する」 → 발송 → 칸 아래 번호 입력(`inputmode="numeric"` · `autocomplete="one-time-code"` · 글자 크기 16픽셀 이상) + 「確認」 + **남은 시간 표시**. 만료되면 입력 비활성 + 「再送信」(재발송). 재발송 대기 중엔 단추에 남은 초. **발송 제한 응답**을 받으면 「しばらくしてから再送信してください」(잠시 후 다시 보내 주세요) + 다시 보낼 수 있는 시각까지 재발송 단추 비활성(남은 시간이 길면 분 단위). 이미 번호 칸이 열려 있으면 그대로 둔다(살아 있는 옛 번호는 입력 가능). 이번 화면에서 번호 칸이 열린 적이 없으면 **열지 않는다**(만료 시각을 모르는 칸을 열지 않는다)
- 확인되면 「認証済み」(인증됨) 표시, 이메일 칸 잠금(고치려면 「変更」(변경) → 인증 풀림, 경우의 수 6)

- 🔴 **가입 성공 후 — 사용자 단계 없이 로그인 상태로**(결정 5):
  - **먼저** 돌려받은 사용자의 신원 목록이 비었으면(이미 가입된 주소 — 경우의 수 7) → 자동 로그인을 시도하지 않고 일반 실패 문구 + 「ログイン」·「パスワードを忘れた方」(로그인·비밀번호 찾기) 안내. 픽셀 안 보냄(지금처럼 새 가입이 아니다)
  - 세션이 있으면 그대로 로그인 상태
  - 세션이 없고 돌려받은 계정이 **인증 완료**면 → 화면이 **방금 입력한 이메일·비밀번호로 곧바로 로그인**(`signInWithPassword`) → 로그인 상태. 사용자에게 아무것도 묻지 않는다. 이 자동 로그인이 실패하면(통신 등) 「登録が完了しました。ログインしてください」(가입 완료, 로그인해 주세요) + 로그인 화면(이메일 미리 채움)
  - 세션이 없고 **인증 완료가 아니면**(대기 상태에서 관문 대조를 통과하지 못한 가입 — 설계 ②) → 지금의 메일 확인 안내(`#signupConfirmMsg`). 메일 링크로 인증하면 정상 회원, 끝내 안 하면 설계 ⑤ 대상

### ⑤ 미인증 계정 정기 삭제 (결정 4)
- **대상 = 가입(계정 생성) 뒤 설정 표의 기간(시작 7일)이 지났는데도 미인증인 계정.** 기존 40건도 이 조건(기간 경과·다른 기록 없음)을 만족하는 날 지워진다
- **이것은 안전장치다.** 새 화면은 인증번호를 확인해야 「登録する」가 켜지고(결정 2), 관문이 강제면 확인증 없는 가입은 서버가 거부한다. 미인증 계정이 생기는 길은 ①기존 40건 ②관문이 **대기**인 동안(단계 1~3 의 처음 강제 전 구간, 또는 사고로 되돌린 구간)의 옛 화면 캐시·직접 호출·대조 실패 가입뿐이다. 그래서 대부분의 날은 0건이다. 매일 **실행 시각·지운 건수·건너뛴 건수·건너뛴 계정 고유번호 목록**을 실행 기록 표(한 실행 = 한 행, 이름은 개발이 정함, 관리자 조회만 — 화면 없음, SQL 편집기로 본다)에 남긴다(경보 판단은 두지 않는다)
- 삭제 = 인증 계정 + 회원 행(관리자 완전 삭제 함수의 두 곳 삭제 방식 — 253:141 참고). **매일 예약 실행**(새벽, 다른 예약과 시각이 겹치지 않게 — 개발이 정함)
- 🔴 **응모·결과물·정산 등 다른 기록이 하나라도 있는 계정은 건너뛰고**(⚠️ **방침 통지 기록 `policy_notice_log` 는 「다른 기록」으로 보지 않는다** — 그것만 있는 계정은 삭제하고 그 기록도 함께 지워진다(연쇄 삭제, `153:99`). 사용자 결정 2026-10-01) 그 건수와 고유번호를 남긴다(인증 전 응모는 막혀 있어 0건이 정상). 관리자 확인은 **첫 실행 때**(아래) 하고, 그 뒤 건너뛴 계정은 필요할 때 실행 기록 표의 고유번호로 조회한다(정기 점검 일정은 두지 않는다)
- 🔴 **첫 실행은 사람이 지켜본다** — 켜기 전에 「기간이 지난 이메일 인증 전 계정」을 먼저 조회해 ①전부 이메일 인증 전이고 ②가입 뒤 기간이 지났는지 보고 ③다른 기록이 있는 계정이 몇 건인지 센다 — ③이 있어도 **멈추지 않는다**(그 계정은 건너뛰어진다). 다만 0건이 아니면 그 계정을 관리자가 따로 확인한다. 건수는 2026-10-01 실측 40건에 그 뒤 대기 구간의 미인증 가입이 더해져 40건보다 많을 수 있다(정상)(단계 3)

## 완료 기준
1. 이메일 입력 → 「認証する」 → 메일에 6자리 번호 → 입력·「確認」 → 「認証済み」, 「登録する」 활성
2. 번호 확인 전·확인증 만료 뒤에는 「登録する」 비활성
3. 유효시간(시작 10분, 설정 표 값)이 지나면 입력 불가 + 「再送信」으로 새 번호. 옛 번호는 거부
4. 틀린 횟수 상한(시작 5회, 설정 표 값) → 그 번호 무효, 재발송 필요
