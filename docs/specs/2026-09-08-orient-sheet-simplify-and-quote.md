### 1-3. 큐텐 자동 채움 실현 가능성 (2026-09-08 실측)

- 큐텐 상품 페이지에는 **`schema.org/Product` JSON-LD** 가 서버 HTML 에 들어 있다 — `name`(상품명)·`sku`(**상품번호** = URL 의 `/g/{번호}`)·`brand.name`(스토어/브랜드명, 예 「TITAD」)·`image[]`·`offers.price`.
- ⚠️ **가격이 세 겹이다** — `参考価格`(정가 6,600) · `販売価格`(판매가 4,950, DOM `#dl_sell_price strong[data-price]`) · `メガ割時`(행사가 3,960). **JSON-LD 의 `offers.price` 는 행사가(3,960)** 라 그대로 쓰면 틀린다. 포인테일은 판매가(4,950)를 채운다.
- 스토어명은 DOM 의 `a.name`(「TITAD 公式ショップ」) 에 있고 JSON-LD `brand.name` 과는 표기가 다르다.
- 🔴 **서버에서 그냥 부르면 막힌다** — `curl` 기본 요청은 한국 IP 에서 **「523 Error」 안내 페이지**(1.2KB)만 돌아왔다. 지역 차단이 아니라 **요청 모양(TLS·머리말) 판별**이다: 같은 IP 의 크롬은 정상이고, `curl` 도 **HTTP/2 + 크롬과 같은 머리말** 로 보내면 정상 HTML(105KB, JSON-LD 포함)을 받았다. Edge Function(Deno)의 `fetch` 가 같은 조건을 만족하는지는 **개발서버에서 먼저 확인해야 한다**(§7 3단계의 첫 일 「0)」).
- 브라우저에서 직접 읽는 길은 없다 — 작성 폼(`sales-dev.globalreverb.com`)에서 큐텐으로의 교차 출처 요청은 차단된다. **서버 함수가 대신 읽어야** 한다.

### 1-4. 이 제안과 충돌 가능성 있는 기존 동작

1. **§15-11 「1링크 = 다형식 · 카드 N개」 결정을 뒤집는다.** 카드 배열·uid·메모·발행 표시·연결/해제(237·238)가 전부 `cards[]` 위에 서 있으므로 **배열 구조는 그대로 두고 길이를 1로 제한**한다(§4-1). 배열을 없애면 여섯 함수를 다시 써야 한다.
2. `findInvalidField` 가 시딩에도 판매 URL·상시가를 **필수**로 요구한다(2026-06-25 결정). 이번 요청에 시딩 URL·가격 언급이 없어 **그대로 둔다** — 리뷰어는 견적 계산에 상시가를 쓰고, 시딩은 계산에는 안 쓰지만 발행 때 제품 정보로 관리자가 본다(§4-6 의 「가격을 못 읽음」 처리는 **리뷰어에만** 걸린다).
3. 발행 자동 채움이 사라지는 값 여섯(§1-1 표)을 읽는다 — 값이 없으면 지금도 빈 칸으로 두므로 **오류는 안 나지만 관리자가 손으로 채우는 칸이 늘어난다**(§4-4).
4. 제출 알림 메일(`notify-orient-submitted`)은 `data` 를 안 실으므로 무영향. 발급 메일 양식(`orient-sheet-invite.html`)은 「모집 형식을 카드에서 고르세요」 류 문구가 있으면 함께 고친다(구현 시 확인).
5. 관리자 상세 `osField` 는 빈 값도 줄을 그린다 — 항목을 빼면 **옛 시트는 값이 있고 새 시트는 없어** 같은 화면에 「—」가 늘어난다. 빈 값은 줄을 안 그리는 쪽으로 바꾼다(§4-3).

## 2. 의심·경우의 수 (규칙 B)

### 깨질 수 있는 경우

1. **(UX) 일정 요구를 적을 자리가 0개가 된다.** 마감·업로드일·「레버브 측 요청」을 다 빼면, 브랜드가 「9월 안에 올려야 한다」를 말할 곳이 없다. 실측상 업로드 마감을 62/70 이 적었다. → §4-2 시딩의 「예상 일정 안내」는 **읽기 전용 계산값**이라 요구를 담지 못한다. 「일정 관련 요청」 한 줄을 남기자고 제안했으나 **사용자가 안 남기기로 확정**(2026-09-08) — 일정 요구는 담당자가 폼 밖에서 받는다. 이 위험은 알고 감수하는 것으로 기록.
2. **(데이터) 옛 시트 14건이 카드 여러 개.** 새 폼이 카드 1개만 그리면 옛 시트를 열었을 때 나머지 카드가 **보이지 않은 채 저장돼 사라진다**(`collectData` 가 화면의 카드만 모은다). → 폼은 `data.issued` 유무로 갈라 **옛 시트는 옛 화면 그대로**(§4-1). 이 분기를 빠뜨리면 조용한 데이터 유실이다.
3. **(권한·법률) 견적서가 관리자 확인 없이 나간다.** 브랜드가 적은 상시가·인원으로 계산한 문서가 회사명으로 나간다. 상시가가 틀리면 틀린 견적이 문서로 남는다. → 문서에 **「브랜드 입력값 기준 예상 견적 · 최종 금액은 담당자 확인 후 확정」** 을 고정 문구로 넣고, 제목은 「견적서」로 두되 고정 문구를 넣는다(확정 ⓖ, §4-6). ⚠️ 사용자가 「최종 견적서」라 불렀지만 확인 없는 값을 「최종」이라 부르면 분쟁의 근거가 된다 — §8-② 확인.
4. **(기술) 큐텐 자동 채움은 언제든 조용히 죽는다.** 봇 판별이 바뀌거나 페이지 구조가 바뀌면 함수는 빈 결과를 돌려준다. → **폼은 자동 채움이 없어도 완전히 동작**해야 하고(빈 칸만 채우는 「제안」), 실패는 「자동으로 못 불러왔어요. 직접 입력해 주세요」 한 줄로 끝난다. 「자동 입력」이라 약속하는 문구를 쓰지 않는다.
5. **(기술) 서버 함수가 아무 주소나 대신 읽어 주는 「열린 대리 요청」이 된다.** 익명 함수라 남이 마음대로 부를 수 있다. → `qoo10.jp` 호스트만 허용 + 살아 있는 작성 토큰 필수(`orient_token_can_upload` 와 같은 관문) + 토큰당 분당 횟수 제한.
6. **(데이터) 견적 기준값을 나중에 바꾸면 옛 견적이 바뀐다.** 화면에서 매번 계산하면 환율을 바꾸는 순간 지난달 견적서가 달라진다. → 제출 시점에 **서버가 계산해 `data.quote` 에 스냅샷**으로 저장(§4-6). 재계산은 재제출 때만.
7. **(권한) 견적 기준값을 누가 바꾸나.** 정산 도입일(230)은 최고 관리자 전용이었다. 견적 단가는 영업이 자주 손댈 값이라 **캠페인 관리자 이상**(확정 ⓗ).
8. **(UX) 시딩 채널 1개 고정이면 인스타 피드+릴스를 같이 요구하는 캠페인은 링크가 두 개.** 사용자 결정(하나만 선택)이라 따르되, 발급 모달에 「채널이 여럿이면 링크를 따로 발급」 안내를 넣는다.
9. **(다국어) 견적서는 한국어(브랜드 대상).** 인플루언서 4줄 푸터 의무 대상 아님. 금액은 원화·엔화 병기.
10. **(환경) 작성 폼은 별도 배포 프로젝트.** 저장소 병합 ≠ 화면 반영 — 함수(데이터베이스) 먼저, 관리자 화면·작성 폼 순으로 나가고 **작성 폼은 브라우저로 눈 확인**.

## 4. 설계

### 4-1. 발급 단위 — 관리자가 형식·채널을 정해 보낸다

**발급 함수** `create_orient_sheet` 재정의(베이스 **205**): 인자 추가 `p_form_type text DEFAULT NULL`, `p_channel text DEFAULT NULL`. **관리자 화면은 형식을 항상 보낸다**(라디오 필수). 서버 검증 — `p_form_type` 이 **값을 가지면** reviewer|seeding 2종 외 거부(`proxy_purchase` 도 거부 — 새 구조에서는 가구매를 발급할 수 없다. ⚠️ 전환 구간의 NULL 발급은 옛 폼 경로로 열려 그 폼의 가구매 탭이 그대로 보인다 — 관리자 화면이 나가면 사라지는 며칠짜리 구멍이라 따로 막지 않는다), 시딩인데 채널 없음 거부, 채널은 `SEEDING_CHANNELS` 5종(`instagram_feed`·`instagram_reels`·`x`·`tiktok`·`youtube`) 외 거부. `p_form_type` 이 **NULL 이면 옛 구조로 발급**(205 와 같은 초기값 `{brand:{…}, cards:[]}`, `issued` 없음) — 데이터베이스가 먼저 나가고 관리자 화면이 뒤에 나가는 **전환 구간에서 옛 화면의 2인자 호출을 살리기 위한 것**이지 정식 경로가 아니다(§4-8 Ⓐ). 값이 있을 때의 저장 — `orient_sheets.form_type` 칸에 형식을 넣고(지금은 NULL 이던 칸 — CHECK 는 이미 맞는다), `data` 초기값을 아래로:

```jsonc
{ "issued": { "form_type": "seeding", "channel": "instagram_feed", "issued_at": "…" },   // 신규 — 폼·상세가 이 키로 새 구조를 판별
  "brand": { "name": "…", "contact_name": "", "email": "", "phone": "" },               // intro·official_accounts 키 제거
  "cards": [ { "form_type": "seeding", "product": {"name":"","slots":""},
              "recruit": {"recruit_start":""}, "sale": {"market":"Qoo10","url":"","price_regular":""},
              "seeding": {"channels":["instagram_feed"], "appeal":"", "hashtags":[], "account_tags":"", "shooting_guide":"", "shipping_note":""},
              "ng": "", "cautions": "", "images": [] } ] }                            // 카드 1개를 발급 시 미리 만든다(uid 는 첫 저장 때 서버가 붙임)
```

- ⚠️ **`cards` 배열은 그대로 둔다.** uid·메모·발행 표시·연결/해제·삭제 함수가 전부 `cards[i]` 를 본다. 길이 1을 **폼과 제출 함수가** 지킨다(발급 함수는 카드 1개를 만들 뿐 그 뒤 개수는 막지 않는다. 폼은 「제품 추가」 단추를 없애고, `submit_orient_sheet` 는 `issued` 가 있는데 카드가 2개 이상이면 `cards_limit` 거부 — 옛 폼이 캐시로 남아 있을 때의 안전판).
- ⚠️ 형식 값이 **세 곳**에 놓인다 — `data.issued.form_type`(**원본·잠금값**, 발급 때 서버가 쓰고 이후 아무도 안 바꾼다) / `cards[0].form_type`(옛 시트와 같은 경로로 화면·발행이 읽는 **사본**) / `orient_sheets.form_type` 칸(목록 필터·집계용 **사본**). 폼은 카드 형식을 `issued` 값으로 고정해 그리고, **`save_orient_draft`·`submit_orient_sheet` 둘 다** 저장 직전에 — **`issued` 가 있는 시트에서만** — `cards[0].form_type` 을 `issued.form_type` 으로 **덮어쓴다**(옛 폼 캐시·직접 호출로 어긋난 값이 들어와도 임시저장본부터 원본이 이긴다). 시딩이면 채널(`issued.channel` ↔ `seeding.channels[0]`)도 같은 규칙.
- **옛 시트 판별**: `data.issued` 가 없으면 **옛 구조** → 폼은 지금 화면(형식 탭·카드 여러 개)을 그대로 그린다. 살아 있는 4건과 발행된 23건이 여기 해당. 새 코드 배포 뒤에도 옛 폼 경로를 지우지 않는다.
- 🔴 **서버가 쓴 키는 서버가 지킨다** — `issued`·`quote`·`quote_history`·`quote_error` 는 **`save_orient_draft`·`submit_orient_sheet` 가 들어온 `data` 와 무관하게 저장돼 있던 값을 다시 얹는다**(카드 uid 안전망 293 과 같은 원칙). 예외는 하나 — 제출 함수가 견적을 계산한 뒤 **`quote`·`quote_error`·`quote_history` 를 스스로 새로 쓰는 것**(§4-6 세트 규칙)은 이 보존 뒤에 일어난다. 형식/채널 원본 덮어쓰기도 **두 함수 공통**이고, 카드 1개 제한(`cards_limit`)은 **제출 함수에만** 둔다 — 임시저장이 거부되면 자동저장이 반복 실패해 작성 중인 글을 잃는다(§4-2 글자 수 불릿과 같은 이유). 지금 두 함수는 `data` 를 투명하게 통째로 저장하므로, 옛 캐시 폼(이 키를 모른다)이 임시저장 한 번만 해도 `issued` 가 사라져 새 시트가 **옛 시트로 둔갑**하고 견적 스냅샷도 지워진다. 이 보존이 없으면 §4-1 의 판별·카드 제한·형식 덮어쓰기가 전부 헛돈다. → §4-8 Ⓑ 가 **두 함수를 함께** 재정의한다.
- **발급 모달**(`osOpenCreate`): 브랜드 → **형식 라디오(리뷰어/시딩)** → 시딩이면 **채널 드롭다운(5종, 단일)** + 안내 「채널이 여럿이면 링크를 따로 발급하세요」. 발급 결과 화면·메일 문구에서 「카드마다 형식 선택」 문구 제거. 진입점 3곳(현황 페인·서베이 더보기·브랜드 상세) 모두 같은 모달이라 한 번에 바뀐다.
- 목록 「모집 형식」 열(`osCardsSummary`)은 그대로 — 카드 1개면 형식 하나만 보인다. 시딩은 채널 이름을 덧붙인다(「시딩 · 인스타그램-피드」).

### 4-3. 관리자 상세·목록

### 4-5. 견적 기준값 — 관리자가 관리

**신규 표 `quote_settings`(싱글톤 아님 — 형식·항목별 행)**: `key text PRIMARY KEY`, `amount numeric NOT NULL`, `unit text`(krw|jpy|rate), `label_ko text`, `updated_at`, `updated_by`(트리거). 초기 행:

| key | 초기값 | 뜻 |
|---|---|---|
| `exchange_rate_krw_per_jpy` | 10 | 엔→원 환율(광고주 신청 폼과 같은 값) |
| `reviewer_transfer_fee_krw` | 2,500 | 리뷰어 1명당 해외 송금 수수료(111 과 같은 값) |
| `reviewer_recruit_fee_krw` | 0 | 리뷰어 1명당 모집비(111 의 `recruit_fee_krw` 에 해당) |
| `seeding_fee_krw_{channel}` | 채널 5종 × 0 | 시딩 1명당 채널별 진행비 — **값은 사용자가 정한다**(§8-③) |
| `vat_rate` | 0.10 | 부가세 |

- 조회: `get_quote_settings()` — 관리자 `is_admin()`. 익명(작성 폼)은 **표를 직접 못 읽고** 제출 함수가 서버 안에서 읽는다(값 자체는 비밀이 아니지만 익명 조회 함수를 늘리지 않는다 — 375 정리와 같은 방향).
- 수정: `update_quote_setting(key, amount)` — `is_campaign_admin()` 이상(확정 ⓗ). 이력은 `quote_settings_history`(key·prev·next·actor·at) — 금액 문서의 근거라 남긴다.
- 화면: **기준 데이터 페인**(`/admin#lookups`)의 종류 탭에 **「견적 기준값」 탭 하나를 더한다**(표 + 인라인 수정. 그 페인은 목록형 레이아웃이라 `admin-card` 를 하나 더 넣으면 정산 화면이 겪은 높이 배분 문제가 재현된다 — 작업 분해 stale 점검 ⑥, 2026-09-08 결정). 새 페인을 만들지 않는다(사이드바·권한 열쇠말 추가 없음 — `menu.lookups` 상속).
- ⚠️ 광고주 신청 폼(`dev/sales/reviewer.html`)과 트리거 111 의 고정 상수는 **이번에 손대지 않는다** — 같은 값을 여기서도 읽게 바꾸면 범위가 늘고, 서베이는 공개 제출이 막혀 있다(206). 다만 두 곳이 어긋날 수 있음을 §8-⑩ 에 적어 둔다.

### 4-6. 견적서 PDF

- **계산 시점 = 제출.** `submit_orient_sheet` 재정의(2단계 — 베이스는 **1단계에서 만든 판**, §4-8): `issued` 가 있는 시트면 카드 값 + `quote_settings` 로 계산해 `data.quote` 에 스냅샷 저장 —
  `{ quote_no, revision, issued_at, form_type, channel, basis:{…읽은 기준값 전부…}, lines:[{label, qty, unit_krw, amount_krw}], subtotal_krw, vat_krw, total_krw, price_regular_jpy, slots, note:"브랜드 입력값 기준 예상 견적" }`.
  - 리뷰어: `상시가(엔)×인원×환율` + `인원×송금수수료` + `인원×모집비` → 공급가, 부가세 = **`floor(공급가 × vat_rate)`**(트리거 111 과 같은 자릿수 규칙).
  - 시딩: `인원 × 채널 단가` → 공급가, +부가세. 제품 제공은 금액 0 줄로 표시. **상시가는 계산에 안 쓴다.**
  - **리뷰어에서** 상시가가 숫자로 안 읽히면(「3,429엔 (가격소구금지)」 같은 입력이 실제로 있다) 숫자만 뽑고, 그래도 없으면 **견적 없이 제출은 통과**시킨다 — **제출을 막지 않는다.** 시딩은 이 검사가 없다.
  - 🔴 **`quote`·`quote_error` 는 제출마다 한 세트로 다시 쓴다** (이 규칙 하나가 화면 판별의 전부다):
    - 계산 성공 → 이전 `quote` 가 있으면 `quote_history[]` 뒤에 붙이고, `quote` 를 새 판으로(`revision` = 지난 판 수 + 1, `quote_no` 는 그대로), **`quote_error` 는 지운다**.
    - 계산 실패 → 이전 `quote` 가 있으면 똑같이 `quote_history[]` 로 보내고, **`quote` 는 없앤 채** `quote_error='price_unreadable'` 을 적는다.
    - 따라서 **`quote` 가 있다 ⇔ 마지막 제출이 견적을 만들었다**, **`quote_error` 가 있다 ⇔ 마지막 제출이 못 만들었다** — 둘이 동시에 있는 상태는 없다. 지난 판을 남기는 이유는 브랜드가 이미 저장한 문서가 무엇이었는지 관리자가 되찾을 수 있어야 하기 때문(§2 경우 6 과 같은 이유 — 스냅샷을 덮어쓰면 그 보호가 재제출 경로로 다시 뚫린다).
    - §4-1 의 「서버가 쓴 키 보존」은 **임시저장과, 제출 중 이 세트를 다시 쓰기 전까지**의 규칙이다 — 제출 함수 자신이 이 세트를 새로 쓰는 것과 부딪히지 않는다.
  - **제출 함수는 결과를 돌려준다** — 329 의 반환값(`success`·`version`·`card_uids`)에 `quote`(성공 시)·`quote_error`(실패 시)를 더한다(§4-8 Ⓓ). 완료 화면은 이 반환값으로 갈린다: `quote` 면 **「견적서 · PDF 저장」** 단추, `quote_error` 면 「가격을 숫자로 적으면 견적서를 받을 수 있어요」 안내(+「내용 수정하기」). 새로고침 뒤에는 `get_orient_sheet` 가 돌려주는 `data` 의 같은 키로 같은 판별을 한다(그 함수는 `data` 를 통째로 돌려주므로 변경 없음).
- **견적 번호**: `{orient_no}-Q`(예 `B0012-O003-Q`), 판은 문서 안에 「판 2」로 따로 표시. 새 카운터를 만들지 않는다.
- **완료 화면(신설, 2026-09-08 결정)**: 작성 폼에는 지금 「제출 완료 화면」이 없다(제출하면 작성 화면으로 돌아가 배너·고정바 표시만 바뀐다). **새 화면 `screenDone` 을 만든다** — 제출 성공 직후 넘어가며, 큰 **「견적서 · PDF 저장」** 단추(이 이름 하나로 통일) + 「내용 수정하기」(작성 화면으로 복귀) + 「제출된 내용은 발행 전까지 수정할 수 있어요」 안내 + **「제출 후 흐름: 담당자 확인 → 견적 확정 → 캠페인 발행 → 모집」 한 줄**(포인테일 확인 단계 톤, §1-6). **`submitted` 상태로 다시 들어오면(새로고침·재진입) 완료 화면을 먼저 띄운다** — 작성 화면은 「내용 수정하기」로만 진입. 옛 구조 시트(`issued` 없음)는 완료 화면을 만들지 않고 지금처럼 작성 화면으로 돌아간다(견적이 없으므로)
- **문서**: 완료 화면의 단추 → 같은 페이지 안 인쇄용 화면(`@media print` 로 폼 숨김) → `window.print()` → 브라우저 「PDF 로 저장」. **외부 라이브러리 없음**(sales 는 정적 배포·CDN 만). 내용: 발행처(株式会社ジェイファン 고정 정보) · 수신(브랜드명·담당자) · 견적 번호·판·일자 · 제품명·판매 URL·형식·채널 · 인원 · 줄별 금액 · 공급가·부가세·합계(원) · 엔화 참고 · **고정 문구**(형식별) — 리뷰어 「본 견적은 브랜드가 입력한 상시가·인원 기준 예상 금액이며, 최종 금액은 담당자 확인 후 확정됩니다」 / 시딩 「본 견적은 브랜드가 입력한 모집 인원 기준 예상 금액이며, 최종 금액은 담당자 확인 후 확정됩니다」 · 유효기간(작성 기한과 같음).
- 🔴 **「PDF 저장」은 브라우저 인쇄 대화상자다**(확정 ⓕ). 모바일 사파리도 「공유 → PDF」 로 되므로 단추 아래 안내 한 줄을 둔다. 파일이 자동으로 내려오게 하려면 서버 생성(Edge Function + HTML→PDF)이 필요하고 이건 **이번 범위 밖**.

### 4-7. 큐텐 URL 자동 채움 (3단계 — 실현 가능성 검증 뒤)

- **Edge Function `qoo10-product-lookup`** (익명 호출): 입력 `{token, url}` → ①`orient_token_can_upload(token)` 으로 살아 있는 작성 토큰만 통과 ②호스트가 `qoo10.jp` 계열이고 경로에서 상품번호(`/g/{n}` 또는 `goodscode={n}`)를 뽑을 수 있을 때만 ③`https://www.qoo10.jp/g/{n}` 을 **HTTP/2 + 크롬 머리말**로 읽어 ④JSON-LD `Product` 에서 `name`·`sku`·`brand.name`·`image[0]`, DOM 에서 `販売価格`(`data-price`)·`参考価格`·스토어명(`a.name`)을 뽑아 `{goods_code, product_name, store_name, price_sale_jpy, price_list_jpy, image_url}` 로 돌려준다. 실패는 **모두 `{ok:false}`** 하나(이유는 로그에만).
- 요청 제한: 토큰당 분당 5회 — 🔴 **데이터베이스 표로 센다**(`orient_lookup_hits` + `orient_lookup_gate()`, 428). 함수 안 메모리는 개발서버 실측(2026-09-08)에서 6회 연속 호출이 전부 통과했다 — Edge Function 은 요청마다 인스턴스가 갈려 메모리 계수기가 0 을 센다. `qoo10.jp` 밖 호스트는 데이터베이스 왕복 없이 함수에서 즉시 거부.
- **폼 동작**: 판매 URL 칸에서 포커스가 빠질 때(`onSaleUrlBlur`) 호출 → 돌아온 값으로 **빈 칸만** 채운다(제품명·상시가) + 칸 아래 「큐텐에서 불러왔어요 · 확인해 주세요」 표시. 이미 값이 있으면 덮지 않고 「불러온 값으로 바꾸기」 링크만. 상품번호·스토어명·이미지 주소는 `sale.goods_code`·`sale.store_name`·`sale.image_url` 로 저장(화면에는 작은 글씨로 표시). 실패면 안내 한 줄, 폼은 그대로.
- ⚠️ **상시가에 어느 가격을 넣나** — 판매가(4,950) 기본, 정가(6,600)는 `sale.price_list` 로 함께 저장(확정 ⓚ).
- 🔴 **3단계 안에서도 읽기 검증(§7 의 「0)」)이 먼저다** — Deno `fetch` 로 개발서버 Edge Function 에서 실제 상품 3개를 읽어 JSON-LD 가 오는지 확인. 실패하면 이 조각은 「보류」로 두고 1·2단계(§4-1~4-6)는 그대로 나간다. 검증 결과를 「구현 결과」에 적는다.
- 큐텐 이용약관상 자동 수집 제한 여부는 확인하지 않았다 — 저빈도(브랜드 입력 1회당 1회)·공개 페이지·상품 정보만이라 위험은 낮게 보지만 §8-⑫ 에 적어 둔다.
