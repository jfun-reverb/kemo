# 모집 마감·결과물 제출 마감 서버(데이터베이스) 강제

**작성일:** 2026-07-29
**상태:** 기획 완료 — 구현 대기

---

## 배경

모집 마감일이 지난 뒤에 들어온 응모가 있는지 운영 데이터를 실측한 데서 출발했다. 결과는 **0건**이었으나, 확인 과정에서 「막혀 있어서 0건」이 아니라 **「우연히 0건」**이라는 것이 드러났다. 마감을 강제하는 서버 장치가 응모·결과물 양쪽 모두 없다.

- **충돌 1** — 화면 응모 차단은 상태 기준, 서버는 날짜 기준. 캠페인 연장 시 두 기준이 갈린다. → §설계 5에서 해소.
- **충돌 2** — 반려 예외 판정 축이 화면 내부에서도 둘(상단 안내문=종류 / 리뷰 인증샷 카드=채널). 서버가 어느 쪽을 재현할지 정하지 않으면 「일치」를 정의할 수 없다. → **§설계 1의 「현행 화면 정책」 정의**에서 **리뷰 인증샷만** 채널 단위로 확정(실제로 제출을 막는 쪽이 실효 정책). 영수증·게시물은 2단계까지 종류 단위로 남고, **게시물까지 채널 단위로 통일하는 것은 §설계 4(3단계)**.
- **충돌 3** — `submitDrafts` 의 에러 무시 설계는 「실패해도 조용히」를 전제로 짜여 있어 서버 차단 도입과 정면으로 안 맞는다. → 수정 필수(§설계 6).
- 그 외 영역(정산·감사 이력·알림 트리거)과 충돌 없음 — `deliverables` 를 자동으로 UPDATE 하는 서버측 트리거·예약 작업은 없고, 정산 자동 보류는 `settlements` 만 건드린다.

## 설계

### 1. 검사 장치의 위치 — 결과물 판정 함수 1개 + 검사 장치 2개

**결과물 판정은 데이터베이스 함수 하나로 모으고, 강제는 검사 장치(트리거) 둘(응모용·결과물용).** 응모는 판정이 「캠페인 마감일과 오늘을 비교」 한 줄이라 별도 함수를 두지 않고 검사 장치 안에서 처리한다 — 아래 (나)의 「검사 장치는 판정 함수만 호출, 자체 판정 금지」 규칙은 **결과물에만** 적용된다(결과물은 판정이 복잡하고 화면과 대조해야 하므로 단일 소스가 필요). 원격 호출 함수 내부 검증은 채택하지 않는다 — 결과물은 인플루언서가 보안 정책 범위 안에서 직접 INSERT·UPDATE 할 수 있으므로, 대리 등록 함수 안에만 검사를 넣으면 본인 경로가 통째로 뚫린다.

**(가) 응모 — `applications` BEFORE INSERT 검사 장치**

1. 조기 통과: `auth.uid() IS NULL`(배치·서비스 키) → `is_admin()`
   - ℹ️ 이 중 `is_admin()` 조항은 **현재로선 도달하지 않는 대비 조항**이다 — 관리자가 인플루언서 대신 응모를 넣는 경로가 코드베이스에 없기 때문(현재 상태 참조). 결과물 검사 장치와 형태를 맞추고, 향후 관리자 대리 응모 기능이 생겨도 막히지 않게 미리 둔다. **이 조항이 있다고 대리 응모 기능이 있는 것은 아니다.**
   - ⚠️ **「로그인 정보가 비어 있으면 통과」가 구멍이 되지 않는 근거는 결과물 검사 장치와 동일**(아래 (나) 1번의 근거 문단 참조) — `applications` 에는 익명 대상 쓰기 정책이 없어 익명 접근은 이 검사 장치까지 도달하지 못한다(익명 쓰기가 열려 있는 표는 광고주 신청 `brand_applications` 뿐). **향후 익명 쓰기 정책을 추가한다면 두 검사 장치를 함께 재검토할 것.**
2. 캠페인 `deadline` 조회 → NULL 이면 통과
3. `(now() AT TIME ZONE 'Asia/Tokyo')::date <= deadline` 이면 통과, 아니면 거부

기존 BEFORE INSERT 검사 장치와 서로 독립(각자 통과/거부만 판정)이라 실행 순서 영향 없음.

**왜 응모는 「새로 넣는 연산」만 막아도 충분한가** — `applications` 의 수정 권한은 **관리자에게만** 열려 있다(`001_enable_rls.sql:104` `applications_update_admin`, `USING/WITH CHECK = is_admin()`). 인플루언서는 자기 응모를 직접 고칠 수 없고, 본인 취소는 별도 함수(`cancel_application`)를 거치며 취소를 되살리는 본인 경로도 없다. 결과물과 상황이 다르므로 여기서는 INSERT 검사 장치 하나로 닫힌다.

**(나) 결과물 — 판정 함수 + `deliverables` BEFORE INSERT OR UPDATE 검사 장치**

판정 함수(이름 예시 `can_submit_deliverable`):

```
can_submit_deliverable(p_application_id uuid, p_kind text, p_post_channel text)
  → jsonb { allowed bool, reason text, submission_end date }
STABLE, SECURITY DEFINER, SET search_path = '', GRANT authenticated
```

판정 순서:

1. 신청 → 캠페인 `submission_end` 조회. NULL 이면 `allowed=true, reason='no_deadline'`
2. `(now() AT TIME ZONE 'Asia/Tokyo')::date <= submission_end` → `allowed=true, reason='within_deadline'`
3. 마감 후 → 반려 예외 판정. 대상 행은 `status<>'draft'` 인 것을 `ORDER BY created_at DESC, id DESC` 정렬한 **최신 1건**이 `rejected` 면 허용:
   - `review_image` = 같은 신청·같은 종류·**같은 `post_channel`** (채널 단위)
   - `post` = 같은 신청·같은 종류 (**2단계에서는 종류 단위** — 현행 화면 정책 그대로. 채널 단위 전환은 3단계, §설계 4)
   - `receipt` = 같은 신청·같은 종류 (채널 개념 없음)
   - `post_channel IS NULL` 인 옛 행은 판정 대상에서 제외
4. 그 외 거부

**★ 반려 예외 판정은 2단(Tier) 구조여야 한다 (2026-07-30 구현 중 발견 — 사양서 문언대로면 기능이 깨진다)**

위 3번을 「`deliverables` 의 **현재 status** 만 본다」로 문자 그대로 구현하면 **리뷰 인증샷·게시물의 마감 후 재제출이 오히려 막힌다.** 사양서가 의도한 것과 정반대다.

- 리뷰 인증샷·게시물의 재제출은 **새 행 추가가 아니라 기존 행을 `draft` 로 되돌리는 UPDATE** 다(채널당 1행 재사용 정책).
- 인플루언서 조작은 항상 **두 단계**로 나뉜다: ①파일·URL 선택 즉시 `rejected → draft`(임시저장) ②별도 「提出」 버튼으로 `draft → pending`. 서로 다른 요청이다.
- ①이 커밋되면 그 행의 현재 상태는 `draft` — **반려 흔적이 표에서 사라진다.** ②가 실행될 때 「`status <> 'draft'` 인 최신 행」을 찾으면 아무것도 없어 **거부된다.**
- 영수증은 재제출이 새 행 INSERT 라 옛 `rejected` 행이 남아 이 문제가 없다.

**해결 = Tier 2 폴백**: Tier 1(현재 상태)이 아무것도 못 찾았을 때만 `deliverable_events` 이력에서 **마지막 「결정」 이벤트**(`to_status IN ('approved','rejected')`)를 보고, 그것이 `rejected` 면 허용한다.
- 성립 근거 — 마이그레이션 073 이 「`draft` 가 OLD·NEW 어느 쪽이든 등장하는 전이는 이벤트를 남기지 않는다」고 정해 뒀다. 그래서 ①②는 이력에 안 남고 원래의 `pending → rejected` 결정이 「가장 최근 결정」으로 보존된다.
- `draft → pending` 시 별도 RPC 가 남기는 `submit` 이벤트는 `to_status='pending'` 이라 위 필터에서 자연히 제외된다.
- 결정 2(「최신 상태가 검수중·승인이면 예외 없음」)를 침해하지 않는다 — 마지막 결정이 `approved` 면 거부다.

⚠️ **대조 게이트로는 이 문제를 잡을 수 없다.** 화면 판정 함수를 스냅샷으로 비교하는 방식이라 「①과 ② 사이에 상태가 바뀐다」는 **타이밍**이 재현되지 않는다. 반드시 **반려 → 임시저장 되돌림 → (별도 요청으로) 최종 제출**을 두 단계로 나눠 실제로 눌러 봐야 한다(검증 시나리오 참조).

**「현행 화면 정책」의 정의** — 화면에는 판정 축이 둘 공존하지만(상단 안내문=종류 단위, 리뷰 인증샷 카드=채널 단위), **실제로 제출을 막는 쪽**이 실효 정책이다. 리뷰 인증샷은 카드에서 막히므로 채널 단위, 영수증·게시물은 종류 단위. 2단계 대조(집합 B)도 이 기준으로 생성한다.

검사 장치는 **이 함수만 호출**한다(자체 판정 로직 금지). 발동 범위를 좁히는 순서:

1. `auth.uid() IS NULL` → 통과 (배치·마이그레이션·서비스 키)
   - ⚠️ **이 조항이 구멍이 되지 않는 근거**: 로그인하지 않은 접근(익명 키)도 `auth.uid()` 가 비어 있지만, `deliverables`·`applications` 는 행 단위 보안 정책상 **익명 INSERT·UPDATE 가 아예 허용되지 않아** 이 검사 장치까지 도달하지 못한다. 실제로 여기로 들어오는 것은 서비스 키를 쓰는 서버측 작업(배치·마이그레이션)뿐이다. **향후 익명 쓰기 정책을 추가한다면 이 조항을 반드시 재검토할 것.**
2. `is_admin()` → 통과 (검수·되돌리기·대리 등록·게시물 교체 전부 면제. 대리 등록 함수가 SECURITY DEFINER 여도 `auth.uid()` 는 호출한 관리자 그대로라 정상 통과)
   - ⚠️ 감사용 계정은 관리자 계정이 아니므로 여기서 걸리지 않고 **실제 사용자와 동일하게 차단**된다(결정 7과 일치). 단 **같은 사람이 관리자 계정으로도 등록돼 있으면** 그 계정으로 로그인한 동안은 예외로 통과한다 — 감사용 동선 확인은 관리자 권한이 없는 별도 계정으로 해야 의미가 있다.
3. `NEW.status IN ('draft','pending')` 이 아니면 통과
4. 남은 것 = **인플루언서 본인이 만드는 「제출 방향」 연산뿐** → 판정 함수 호출, 거부 시 예외

이 구조로 관리자 예외가 검사 장치 상단 두 줄에 모이고, 판정 로직 자체는 신원과 무관해진다.

### 2. 시간대

- **`(now() AT TIME ZONE 'Asia/Tokyo')::date <= 마감일`** 로 고정. 즉 **마감일 당일 일본 시각 24시(23:59:59)까지 허용**. 연령 정책의 `calc_age_kst` 와 같은 표현이라 프로젝트 내 일관.
- `deadline`·`submission_end` 는 날짜 타입이라 시각 개념이 없으므로 「당일 끝까지」가 유일하게 자연스러운 해석이고, 화면 현행과 의미도 같다.
- 남는 차이는 기기 시간대뿐. 일본·한국 기기는 완전 일치, 그 외 지역은 최대 하루 어긋난다. **3단계에서 화면이 서버 판정을 소비하면 이 차이는 소멸.**
- 안내 문구에 「마감일 당일 24시(일본 시간)까지」 명시(문의 대응 근거).

### 3. 화면 판정과 서버 판정이 어긋나지 않게 하는 법

**선례:** 사이드바 검수대기 배지가 화면 목록과 숫자가 안 맞아 세 번 고친 사고(마이그레이션 248→249→250). 원인은 「화면 판정을 SQL 로 따로 재현」해서 같은 개념의 구현이 둘이 된 것.

**원칙: 구현을 둘 만들지 않는다. 방향을 뒤집어 데이터베이스를 유일 구현으로 두고 화면이 그 결과를 소비한다.**

**(1) 최종 형태 — 화면이 서버 판정을 소비 (3단계)**

- 배치 조회 함수 추가(예 `get_deliverable_gate(p_application_id)`) → 그 신청에 필요한 항목마다 판정 결과를 배열로 반환. 항목은 **영수증 / 캠페인 채널별 게시물 / 캠페인 채널별 리뷰 인증샷** — 게시물도 채널별로 전개해야 3단계 정책(인스타그램만 허용·틱톡 차단, §설계 4)을 화면이 표현할 수 있다
- 활동관리 화면 진입 시 결과물 목록을 불러오는 그 시점에 1회 호출 → 폼 비활성·제출 버튼 노출·안내 문구를 **전부 이 결과로** 결정
- `_latestNonDraftIsRejected` **는 삭제한다** — 차단 판정에서 손만 떼고 코드를 남기면 이중 구현이 그대로 유지돼 일원화 목적이 무너진다
- 조회 실패 시에는 **판정을 재현하지 않고 폼을 열어 둔다**(막지 않음). 이유: ①일시적 조회 실패로 정상 사용자의 제출을 막는 게 더 나쁘고 ②최종 방어선은 검사 장치라 마감 후 제출은 어차피 서버가 거부하며 ③이때 사용자는 §설계 6의 정확한 안내 문구를 보게 된다. **화면에 판정 로직을 되살리는 형태의 폴백은 금지.**

**(2) 전환 전 검증 — 양방향 집합 대조 (2단계 배포 전 의무 게이트)**

⚠️ **대조가 성립하려면 2단계에서 화면 정책을 바꾸지 않아야 한다.** 기준이 되는 화면 로직을 같은 단계에서 손대면 「무엇과 무엇을 맞추는지」가 사라진다. 그래서 **게시물 예외를 채널 단위로 바꾸는 작업은 3단계로 미룬다**(§설계 4). 2단계의 판정 함수는 **현행 화면 정책을 그대로 옮기기만** 한다.

- 집합 A(서버): 대상 전수(승인 신청 × 필요한 종류, 리뷰 인증샷은 캠페인 채널별로 전개)에 대해 판정 함수 결과를 `(application_id, kind, channel, allowed)` 로 추출
- 집합 B(화면): 아래 절차로 생성한다.
  1. **데이터 확보** — 개발서버 **관리자** 화면에서 결과물 전건을 내려받는다(인플루언서 앱은 행 단위 보안 정책상 본인 것만 보여 전수 대조가 불가능하므로 관리자 쪽에서 받는다).
  2. **판정 실행** — ⚠️ 화면 판정 함수(`_latestNonDraftIsRejected`·`applyFormGating`)는 **인플루언서 앱 `dev/js/application.js` 에만** 있고, 빌드 목록(`dev/build.sh` `ADMIN_JS_FILES`)상 **관리자 화면 빌드에는 들어가지 않는다.** 따라서 「관리자 화면에서 그 함수를 그대로 돌린다」는 성립하지 않는다. 대신 그 함수 원문을 **한 글자도 고치지 않고 복사**한 1회용 대조 스크립트에 1의 데이터를 통과시켜 같은 형태로 생성한다. 복사본은 대조 전용이며 **커밋하지 않는다**(고치면 그 순간 「현행 화면 정책」이라는 기준이 사라진다).
  3. **시간대 고정** — 화면 판정은 기기 로컬 시간, 서버 판정은 일본 시각 기준이다. 대조는 반드시 **한국 또는 일본 시간대 기기**에서 실행한다(둘은 같은 시간대라 결과가 일치). 다른 시간대에서 돌리면 하루 차이가 「불일치」로 잘못 잡힌다.
- 임시 표에 B 를 적재해 `A EXCEPT B`, `B EXCEPT A` 실행 → **양쪽 0행이어야 통과.** 한 건이라도 나오면 원인 규명 전 배포 금지
- 마감 지난 캠페인 데이터가 부족하면 개발서버에서 `submission_end` 를 과거로 조정해 조합(반려·승인·검수중·미제출·채널 혼합)을 만든 뒤 대조

**(3) 정의를 문장으로 고정** (사양서 + 코드 주석 + `CLAUDE.md`)

- 「최신 1건」 = `status<>'draft'` 인 행 중 `created_at` 내림차순, **동률이면 `id` 내림차순**
  - ⚠️ **화면 정렬에 이 규칙을 넣는 것은 3단계다.** 2단계에서 화면을 고치면 대조의 기준이 사라진다((2) 참조). 그런데 화면에는 지금 동률 규칙이 없어(현재 상태 참조) 같은 초에 생성된 2행이 있으면 서버와 순서가 갈릴 수 있다 → **2단계 대조에서 동률 행이 나오면 그 건은 「불일치」로 세지 말고 수동 확인 대상으로 뺀다**(대조 스크립트가 동률 행을 따로 출력하게 할 것). 3단계에서 화면이 서버 판정을 소비하면 화면 정렬은 판정에서 아예 빠지므로 이 예외도 소멸한다.
- 「채널 축」 = `review_image` 는 `post_channel` 일치. **`post` 는 2단계까지 종류 단위, 3단계부터 `post_channel` 일치**(§설계 4). 양쪽 모두 `post_channel` NULL 행은 제외
- 「반려 예외」 = 최신 1건이 `rejected` 일 때만. 관리자가 반려를 되돌리면 예외도 사라진다
- `CLAUDE.md` 에 「결과물 제출 가부 판정의 단일 소스는 `can_submit_deliverable`. 화면에 같은 판정을 다시 구현하지 말 것」 명시. 리뷰 점검 항목화

### 4. 게시물 반려 예외를 채널 단위로 — **3단계에서** 전환

현재 화면은 게시물을 종류 단위로 판정한다. 이를 **채널 단위로 좁힌다**:

- 인스타그램 게시물이 반려됐으면 **인스타그램만** 마감 후 재제출 가능
- 같은 캠페인의 틱톡 게시물을 새로 내는 것은 차단
- 게시물은 이미 채널별 1건 정책(2026-06-02)이라 개념상 정합하고, 리뷰 인증샷과 기준이 같아진다

**왜 3단계인가** — 2단계는 대조 게이트(§설계 3-(2))를 통과해야 하는데, 그 대조의 기준이 현행 화면 정책이다. 같은 단계에서 정책을 바꾸면 기준이 사라진다. 3단계에서는 화면이 서버 판정을 그대로 소비하므로 **판정 구현이 하나뿐**이고, 판정 함수 한 곳만 고치면 화면·서버가 동시에 바뀌어 어긋날 여지가 없다. 정책 변경은 구현이 하나가 된 뒤에 하는 것이 안전하다.

### 5. 날짜 변경 — 서버·화면 어긋남 해소 (2026-07-30 전면 재작성)

> ⚠️ **초안의 이 절은 전제가 틀렸다.** 「반대 방향(마감일을 과거로 당김)은 기존 자동 마감이 처리하므로 추가 작업 없음」이라고 썼지만, 자동 마감(`autoCloseCampaigns`)은 **`active` 상태만** 닫는다. `ended`·`expired`·`draft` 에 미래 마감일이 들어가면 아무 자동 전이도 손대지 않은 채 **서버가 응모를 받는다.** 또 「`ended`·`expired`·`draft` 는 제외」 결정은 안전을 뜻한 게 아니라 **그 칸의 어긋남을 방치**한 것이었다. 아래는 경우의 수 전수 조사(2026-07-30) 결과로 다시 쓴 것이다.

서버는 마감일 날짜만 본다. 화면은 캠페인 상태만 본다. 축이 다르므로 조합마다 어긋남이 생기고, 어긋남은 두 종류인데 **위험도가 전혀 다르다.**

- **화면 허용 / 서버 거부** = 인플루언서가 버튼을 눌렀는데 실패한다 → **혼선. 없애야 한다.**
- **화면 거부 / 서버 허용** = 받을 수 있었는데 안 받는다 → 기회 손실이지만 안전하다.

#### (1) 원칙 — 화면은 서버보다 「더 닫는」 방향으로만 판정을 얹는다

응모 버튼 비활성 조건 = (기존 상태 기준) **OR** (마감일이 오늘보다 과거)

§설계 3의 「판정 구현을 둘 만들지 않는다」와 부딪히지 않는다. 같은 판정의 재구현이 아니라 **보수적 상한을 하나 더 얹는 단방향 규칙**이다. 화면이 서버보다 **더 여는** 판정은 어떤 경우에도 추가하지 않는다. 이 규칙 하나로 아래 (2)의 「혼선」 칸이 전부 「안전」으로 내려간다.

판정 시각은 서버와 같게 **일본 시각 기준**으로 고정한다(기기 로컬 시간 아님). 일본·한국 기기는 차이가 없고, 그 밖의 지역·시각 오설정 기기에서 어긋나도 **「더 닫히는」 방향으로만** 나타나 안전하다. 기기 시각을 미래로 돌려 버튼을 여는 것은 서버가 막는다.

| **active** 모집중 | 카드 「募集中」 · 버튼 활성 · 서버 ✕ → 🔴 **가장 빈번**(아래 2-1) | 🟢 | 양쪽 허용 = 무기한 모집 ⚠️ |
| **closed** 모집마감 | 🟢 | 버튼 「募集締切」 · 서버 ○ → 🟡 (초안이 다룬 유일한 칸) | 🟡 |
| **ended** 종료 | 🟢 | 버튼 「終了」 · 서버 ○ → 🟡 **초안 미대응 · 저장이 실제로 됨** | 🟡 |
| **expired** 노출종료 | 비노출 · 링크 진입 시 버튼 활성 · 서버 ✕ → 🔴 | 비노출 · 버튼 활성 · 서버 ○ → 🔴 **운영자가 숨긴 건에 응모가 들어옴** | 🔴 |

**(2-1) 🔴 중 하루에 한 번 확실히 재현되는 것 — `active` + 마감일 과거**

관리자 조작으로는 만들 수 없다(편집 저장 가드가 차단). **시간 경과로만** 생기고, 상태 전이가 브라우저 주도라 경로가 이렇다:

1. 인플루언서가 23:5x 에 목록·상세를 열어 둠 → 캐시에 `status='active'`
2. 화면 잠금·앱 전환 후 00:0x 에 복귀 → **상세는 캐시를 쓰고 다시 조회하지 않는다**(`application.js` `openCampaign`)
3. 카드 「募集中」·버튼 활성 → 누름 → 서버 거부 → **토스트만 뜨고 버튼은 그대로** → 2~3회 재시도

여기에 「응모 실패 후 상세를 다시 그리지 않는다」가 겹쳐 「앱이 고장났다」로 인식된다.

**(2-2) 🔴 중 되돌리기가 가장 지저분한 것 — `expired`·`draft` + 마감일 미래**

화면도 서버도 허용해 **응모가 실제로 저장되고, 리뷰어형은 자동 승인까지 된다.** 운영자가 숨겼다고 믿는 건에 응모가 쌓이면 정리 경로가 없다(관리자 취소=반려뿐).

#### (3) 변경 방향별 확인·안내

| 방향 | 관리자가 할 수 있나 | 서버 판정 | 기존 응모 | 조치 |
|---|---|---|---|---|
| **과거 → 미래**(재개·정정) | `closed`·`ended`·`expired`·`draft` 에서 가능 | ✕ → ○ | 영향 없음 | **확인창 + 상태 동시 전환**(대상 4개 상태, 아래 (4)) |
| 과거 → 과거 (더 이전/더 이후) | 가능 | 변화 없음 ✕ | 없음 | 확인 불필요 |
| **미래 → 미래**(연장) | 모든 상태 | ○ 유지 | 없음 | 확인 불필요 + **(6) 날짜 정렬 검증** |
| **미래 → 미래**(단축) | 모든 상태 | ○ 유지 | 없음 (소급 무효 없음) | **확인창**(응모 기회 축소 경고) |
| **미래 → 과거**(즉시 마감) | `active`·`scheduled` 는 저장 차단(현행 유지) | ○ → ✕ | 없음 | 차단 유지 + **「지금 마감」 전용 버튼**(아래 (5)) |
| 없음 → 값 | 가능 | 값에 따라 | 없음 | **확인창 없음** — 마감일이 없던 건은 서버가 이미 무기한 통과였으므로 어긋남이 새로 생기지 않는다((4) 마지막 줄과 동일). 초안에 「재개와 동일 취급」이라 적었던 것은 (4) 와 모순이라 2026-07-30 정정 |
| **값 → 없음**(지우기) | **가능 — 검증 없음** | 무제한 ○ | 없음 | **확인창 필수** — 그 건만 서버 차단이 해제된다 |

#### (4) 재개 확인창 — 대상은 4개 상태

「마감일이 과거 → 미래」면 확인 후 마감일과 상태를 **함께** 저장한다. **「마감일만 저장」 선택지는 두지 않는다**(어긋난 상태를 남기지 않기 위해).

| 원래 상태 | 함께 저장할 상태 | 비고 |
|---|---|---|
| closed 모집마감 | active | 기본 경로 |
| ended 종료 | active | 결과물 제출 마감·구매 기간이 과거면 (6) 검증에서 먼저 막힌다 |
| expired 노출종료 | active | 다시 노출된다는 사실을 문구에 명시 |
| draft 준비 | **변경 없음** | 마감일만으로 미공개 건을 공개해서는 안 된다. 「공개하려면 상태를 직접 바꿔 주세요」 안내 |

- 「저장하지 않고 돌아가기」 시 아무것도 저장하지 않고 편집 화면에 머무른다(입력값은 화면에 남김)
- 원래 마감일이 없던(NULL) 건은 확인창 대상이 아니다 — 서버가 이미 무제한 허용이라 어긋남이 새로 생기지 않는다. (2) 표의 「없음」 열에 남는 안전측 어긋남은 그대로다

#### (5) 그 밖에 확인이 필요한 변경

- **마감일 단축**(미래 → 더 이른 미래): 상태는 바꾸지 않고 확인창만. 이미 접수된 응모는 **전부 유효 유지 — 마감일 단축은 응모를 소급 무효화하지 않는다**(이 원칙을 문장으로 고정)
- **마감일 삭제**(값 → 없음): 그 건만 서버 차단이 해제되므로 확인창 필수
- **「지금 마감」 버튼**(신설): 「미래 → 과거」 직접 저장은 계속 차단하고(지난 날짜가 인플루언서 화면 「募集期間」 에 남는다), 대신 `status='closed'` + 마감일=**오늘**을 함께 저장하는 전용 동선을 둔다. 오늘 24시(일본 시각)까지는 서버가 접수하지만 화면이 이미 닫혀 실질 영향은 없다(🟡, 안전측)

#### (6) 저장 검증 추가 — 재개가 만드는 「낼 수 없는 캠페인」 차단

현재 날짜 검증(`validateCampDateRanges`)은 `제출마감 ≥ 모집시작` 만 본다. 마감일을 `submission_end` 이후로 연장해도 통과하므로 **응모는 받지만 결과물을 낼 수 없는** 건이 저장된다. 2단계(결과물 서버 차단)가 들어오면 즉시 사고가 된다.

- **`제출마감 ≥ 모집마감` 규칙 추가** — 위반 시 저장 차단 + 「제출 마감일도 함께 늘려 주세요」 안내(사용자 지시: 알럿으로 알려 수정하게)
- **`제출마감`을 과거 날짜로 저장하는 것 차단** — 승인된 인플루언서 전원이 즉시 제출 불가가 된다
- 리뷰어형은 `purchase_end`(구매 기간)도 같은 문제 — 재개 시 이미 지났으면 경고

#### (7) 인플루언서 안내 — 알림 대상은 배타적이다

**모집 마감일은 아직 응모하지 않은 사람에게만, 결과물 제출 마감일은 이미 승인된 사람에게만 의미가 있다.**

| 무엇이 바뀌었나 | 기존 응모자 알림 | 근거 |
|---|---|---|
| 모집 마감일 연장·단축 | **보내지 않음** | 그들의 응모 상태가 변하지 않는다. 알림은 「내 응모에 무슨 일이 생겼나」 불안만 만든다(주의사항 변경도 알림 없이 응모이력 비교 표시로만 처리한 선례) |
| 결과물 제출 마감 **연장** | **보냄** | 마감이 지나 못 냈던 사람은 폼이 다시 열린 걸 알 방법이 없다(사용자 지시) |
| 결과물 제출 마감 **단축** | **보냄** | 제출 기회를 직접 빼앗는 불리한 변경 |

- 알림 종류 1종 신설 필요(`notifications.kind` CHECK 갱신 — **마이그레이션 1개**, 이번 보강에 포함)
- 문구는 「새 제출 기한 + 그때까지 내면 된다 + 문의 경로」 3단계(§설계 6에 초안)

#### (8) 화면 동반 조치 3종

1. **링크 진입 가드** — `draft`·`expired` 는 상세를 열지 않고 안내 후 캠페인 목록으로. `scheduled` 는 상세는 보여주되 응모 버튼을 「近日公開」 비활성으로
2. **제출 직전 재검사** — 응모 저장 직전에 화면 판정을 1회 더 실행(자정 경계용). 같은 화면 판정의 재실행이라 이중 구현이 아니다
3. **실패 시 재렌더** — 응모 실패 후 상세를 다시 그려 버튼을 「募集締切」 로 갱신 + 상단 안내 박스 1회. **반복 탭이 이걸로 끝난다**

#### (9) 근본 해소는 상태를 서버 권위값으로 (다음 단계 이월)

(2-1) 의 최빈 경로는 **상태 전이가 브라우저 주도**인 데서 온다. (1) 의 규칙이 증상을 막지만 원인은 남는다. 다음 단계에서 상태 자동 전이를 서버 예약 작업으로 옮겨 `status` 를 신뢰 가능한 값으로 만든다(마이그레이션 1개).

### 6. 인플루언서에게 보이는 문구

검사 장치는 머신 판독용 코드를 메시지 앞에 붙여 예외를 발생시킨다(`post_already_approved` 선례와 동일 구조):

- `recruit_deadline_passed: 모집 기간이 종료되었습니다`
- `submission_deadline_passed: 제출 기한이 지났습니다`

`friendlyErrorJa()` 에 정규식 2줄 + `_ERR_DICT` ja/ko 에 각 2키 추가 → **로케일 분기 경로를 그대로 탄다**(추가 작업 없음).

- 일본어: 「募集期間が終了したため、応募できません」 / 「提出期限が過ぎているため、提出できません。差し戻された項目のみ再提出できます」
- 한국어: 「모집 기간이 종료되어 신청할 수 없습니다」 / 「제출 기한이 지나 제출할 수 없습니다. 반려된 항목만 다시 제출할 수 있습니다」

**★ 수반 수정 — 2단계 필수 1건 / 3단계 이월 1건**

- **2단계에 반드시 포함**: `storage.js:1338` `submitDrafts()` 의 에러 삼킴 제거 → 예외를 호출부(`application.js:1525` `submitAllDrafts`)로 전파하고 안내 문구 표시. 이것 없이 2단계를 배포하면 사용자는 「제출할 것이 없습니다」라는 틀린 안내를 본다
- **3단계로 이월**: 마감 후에도 노출되는 리뷰 인증샷 통합 제출 버튼 게이팅 — 서버 판정을 소비하게 되는 3단계에서 함께 처리(2단계에서 화면을 고치면 대조 기준이 훼손된다). **2단계 배포 후 3단계 전까지는 「눌리는데 서버가 거부하는 버튼」이 잠시 남는다** — 위 문구 정비가 2단계 필수인 이유이기도 하다

### 7. 경계 상황

| 상황 | 처리 |
|---|---|
| 마감일이 NULL | **통과(무기한)**. **응모(`deadline`)는 실측 완료 — 전부 마감일 있는 캠페인이라 영향 0.** 결과물(`submission_end`)은 **미실측** — 검증 계획 「배포 전 실측 3」에서 확인한다(응모 실측을 결과물 근거로 쓰지 말 것). 향후 마감일 없는 캠페인이 생기면 그 캠페인엔 서버 차단이 없다 |
| 취소 후 재응모 | 같은 검사 장치를 탄다 → 마감 전이면 허용, 마감 후면 차단. 취소 이력·부분 유니크 인덱스와 충돌 없음 |
| 마감 후 남은 임시저장 | 시행 즉시 제출 불가로 굳는다. **배포 전 건수 실측 필수**. 구제는 관리자 대리 등록 |
| 감사용 계정 | 실제 사용자와 동일하게 차단 (결정 7). ⚠️ 동일인이 관리자 계정으로 로그인한 동안은 관리자 예외로 통과 — 감사용 확인은 관리자 권한 없는 계정으로 |
| campaign_manager | 검사 장치는 면제되나 대리 등록 함수는 상위 권한 가드라 실제 등록 불가. 「검사 장치 예외 = 대리 등록 가능」이 아님을 문서에 명시 |
| 보관 삭제된 캠페인 | 신청·결과물은 삭제 시 즉시 파기되므로 무관 |
| 마감 자정 경계 동시 요청 | 트랜잭션의 `now()` 로 단일 판정 → 경합 없음 |
| 배치·마이그레이션 UPDATE | `auth.uid() IS NULL` 통과 조항으로 보호 |

## 단계 분할

마이그레이션 번호는 개발 세션이 파일 생성 시점에 확정한다. **총 4개**(1단계-A 완료분 1 + 1단계-B 알림 1 + 2단계 1 + 3단계 1), 상대 순서는 아래 표 그대로.

| 순서 | 내용 | 마이그레이션 | 의존 |
|---|---|---|---|
| **1단계-A — 응모 마감 서버 차단** ✅ | 검사 장치 함수 + `applications` BEFORE INSERT 검사 장치 / 안내 문구 1종 / 마감일 연장 확인창(초판) | 1개 (272) | 없음 — **개발서버 완료, 운영 미배포** |
| **1단계-B — 어긋남 해소 보강** (운영 배포 전 필수) | ①화면도 마감일 확인(§5-(1)) ②링크 진입 가드·응모 버튼 「近日公開」(§5-(8)-1) ③응모 실패 후 재렌더+안내 박스(§5-(8)-3) ④제출 직전 재검사(§5-(8)-2) ⑤확인창 재설계 — 재개 대상 4개 상태·단축·삭제·버튼 이름 지정(§5-(3)(4)(5)) ⑥날짜 정렬 검증(§5-(6)) ⑦「지금 마감」 버튼 ⑧제출마감 변경 알림 | **1개**(알림 종류 추가) | 1단계-A 이후 |
| **2단계 — 결과물 제출 마감 서버 차단** | 판정 함수 `can_submit_deliverable`(**현행 화면 정책 그대로**) + 검사 장치 함수 + `deliverables` BEFORE INSERT OR UPDATE 검사 장치 / `submitDrafts` 에러 전파 + 안내 문구 1종 | 1개 | 1단계 배포·검증 후 |
| **3단계 — 화면 판정 서버 일원화 + 게시물 예외 채널 단위 전환** | 배치 조회 함수 + 실행 권한 부여 / `application.js` 폼 게이팅·제출 버튼 노출을 서버 결과로 교체 / `_latestNonDraftIsRejected` 삭제 / 판정 함수의 게시물 예외를 채널 단위로 변경 / 죽은 함수 `insertPostDeliverable`(호출부 0건) 정리 | 1개 | 2단계 배포 후 |

세 단계 모두 `dev/js/application.js`·`dev/lib/storage.js`·`dev/js/ui.js` 를 공유하므로 **병렬 작업 금지, 순차 진행.**

**2단계 내부 순서** — 대조 게이트(§설계 3-(2))는 2단계의 **선행 조건이 아니라 배포 직전 관문**이다. 게이트가 검사할 대상(판정 함수)이 2단계에서 만들어지기 때문이다: `판정 함수·검사 장치 개발 → 대조 게이트 통과 → 배포`. 게이트에서 불일치가 나오면 배포하지 말고 판정 함수를 고쳐 다시 대조한다.

## 검증 계획

### 배포 전 실측 (운영·개발 각각, 결과를 이 문서에 기록)

1. 제출 마감이 지난 캠페인에 남아 있는 임시저장 결과물 건수 + 해당 인플루언서 수 → 시행 즉시 굳는 대상 규모
2. 지금까지 마감 후에 제출된 결과물 건수와 그중 반려 예외로 설명되는 비율 → 이번 차단이 실제로 막게 될 규모
3. 마감일이 NULL 인 캠페인 수 → 서버 차단이 적용되지 않는 사각지대 크기
4. 응모 쪽은 실측 완료(마감 후 응모 0건) — 백필 불필요
5. `deadline` 이 NULL 인 건 수 — 서버 차단 사각지대
6. `deadline > submission_end` 인 건 수 — **이미 존재하는 「낼 수 없는 캠페인」**
7. `status IN ('ended','expired','draft')` 이면서 `deadline >= 오늘` 인 건 수 — **지금 이 순간 서버가 응모를 받고 있는 비노출 캠페인**(운영 배포 전 반드시 확인)

### 배포 전 실측 결과 (2026-07-30 운영 데이터)

| 항목 | 값 | 해석 |
|---|---|---|
| 마감일 없는 캠페인 | **0** | 응모 서버 차단 사각지대 없음 |
| `deadline > submission_end` 인 캠페인 | **0** | 이미 존재하는 「낼 수 없는 캠페인」 없음 |
| 비노출(`ended`·`expired`·`draft`)인데 마감일이 미래 | **0** | 지금 서버가 응모를 받는 숨겨진 캠페인 없음 |
| 제출 마감 지난 캠페인의 임시저장 결과물 | **14건 / 인플루언서 6명** | ↓ 아래 참조 |
| ㄴ 그중 **반려 예외로 지금도 제출 가능** | **0** | **2단계가 새로 막는 대상이 없다** |
| ㄴ 제출 이력 없음 | 12 | 마감 지나 못 낸 건. **화면이 이미 막고 있어** 2단계와 무관 |
| ㄴ 이미 제출·승인됨 | 2 | 최종 제출 후 남은 임시저장 잔존물. 무해 |
| 같은 캠페인들의 검수대기 | 37 | 이미 제출됨. 관리자 검수는 예외 통과라 영향 없음 |

**결론: 2단계 배포로 새로 불이익을 받는 인플루언서는 0명.** 초안에 「임시저장은 시행 즉시 제출 불가로 굳는다」고 썼으나 **부정확했다** — 결과물 제출 폼은 처음부터 `submission_end` 를 직접 봤으므로 화면은 이미 막고 있었고, 2단계는 「화면을 우회하면 들어가던 구멍」만 닫는다.

⚠️ **다만 검증 방법이 하나 바뀐다** — 반려 예외 대상이 실데이터에 0건이라, 대조 게이트에서 **그 축을 실데이터로 확인할 수 없다.** 개발서버에서 인위적으로 조합을 만들어 확인해야 한다(마감일을 과거로 조정):
1. 마감 후 × 영수증이 반려된 상태 → **재제출 허용**되어야 함
2. 마감 후 × 리뷰 인증샷 A채널만 반려 → **A만 허용, B는 차단**
3. 마감 후 × 아무 이력 없음 → **차단**

### 정합 대조 (2단계 **배포 직전** 관문 — 개발을 마친 뒤 거친다)

§설계 3의 `A EXCEPT B` / `B EXCEPT A` **양방향 0행**. 데이터가 부족하면 개발서버에서 마감일을 과거로 조정해 아래 조합을 만든 뒤 대조: 마감 전/후 × 미제출·검수중·승인·반려 × 채널 일부만 반려 / 채널 미지정 옛 행 포함.

⚠️ **동률 행 예외**(§설계 3-(3)) — 같은 초에 생성돼 `created_at` 이 같은 행이 섞인 건은 화면에 동률 규칙이 아직 없어 순서가 갈릴 수 있다. **이런 건은 「불일치」로 세지 말고 별도로 출력해 수동 확인**하고, 0행 기준에서는 제외한다. 대조 스크립트가 동률 행을 따로 뽑아 주도록 만들 것.

#### ★ 배포 후 즉시 발견된 버그 (브라우저 테스트로만 잡혔다)

마감일 연장 확인 게이트가 **한 번도 뜨지 않는 죽은 코드**였다. 원인은 편집 화면 원본 스냅샷 `_editCampOriginal`(`admin.js:731`)에 `deadline` 이 담기지 않았던 것 — 그 스냅샷은 원래 「주의사항·참여방법·NG 변경 감지」 용으로 만들어져 관련 필드만 담고 있었고, 게이트가 `_editCampOriginal.deadline` 을 읽으니 항상 빈 문자열이라 조건이 영구 거짓이었다. 결과적으로 마감일만 저장돼 **이 게이트가 막으려던 어긋난 상태가 조용히 만들어졌다.**

**왜 정적 리뷰로 안 잡혔나** — 리뷰에서 「`_editCampOriginal.deadline` 이 'YYYY-MM-DD' 문자열이라는 가정이 맞는가」를 명시적으로 물었고, 검토자는 **다른 코드에서 `camp.deadline` 을 어떻게 쓰는지**만 확인해 「가정 일치」로 답했다. 스냅샷 **정의**를 열어보지 않았다. 화면 상태 객체를 읽는 게이트는 「그 객체에 그 키가 실제로 담기는가」가 유일한 실패 지점이고, 그건 실행해 봐야 드러난다.

**교훈** — 화면 상태 스냅샷·캐시 객체를 조건으로 쓰는 게이트는 **정적 리뷰만으로 배포하지 말 것.** 최소한 그 스냅샷의 정의부를 직접 열어 키 존재를 확인하고, 브라우저에서 게이트가 실제로 발동하는지 1회 확인한다.

수정: `_editCampOriginal` 에 `deadline: camp.deadline || ''` 추가. 재검증 6단계 전부 통과(확인창 문구·취소 시 미저장·확인 시 상태 동시 전환·마감일 미변경 시 확인창 미등장).

#### ★ 브라우저 검증에서 잡힌 것 2건 (2026-07-31, 수정 완료)

데이터베이스 검증 4종(항목 전개·마감 전 통과·마감 후 차단·게시물 채널 단위 예외)이 전부 통과한 **뒤에** 개발서버 화면을 실제로 열어 보고 나온 것들이다. **정적 리뷰로는 둘 다 걸리지 않았다** — 이번 작업에서 브라우저 테스트가 결정적이었던 네 번째·다섯 번째 사례.

1. **리뷰 인증샷 통합 제출 버튼이 서버 판정을 무시하고 노출됐다.** `renderActivityReviewImageList` 가 버튼을 「임시저장 행이 있는가(`hasDraft`)」로만 띄우고 있어, 마감이 지나 서버가 거부할 채널의 임시저장만 남아도 버튼이 눌리는 상태로 떴다. **이 항목은 §설계 6 「수반 수정」에 「3단계로 이월」로 명시돼 있었는데 3단계 구현에서 빠졌다** — 이월 항목이 다음 단계 작업 목록으로 옮겨지지 않으면 그대로 증발한다는 뜻이다. → 「**서버가 허용한 채널의** 임시저장이 있는가(`hasSubmittableDraft`)」로 교체하고 `disabled` 도 함께 설정. 판정은 그 함수가 채널마다 이미 계산하던 `gateAllows('review_image', ch)` 를 재사용(판정 재구현 없음). 남은 임시저장은 카드의 삭제 버튼으로 정리 가능해 막다른 골목이 아니다.

2. **반려가 하나도 없는데 「기한은 지났지만 재제출 가능」 안내가 떴다.** 안내문 분기가 `gateAllowsAny('receipt') || gateAllowsAny('review_image') || gateAllowsAny('post')` 였는데, `gateAllowsAny` 는 「그 종류가 이 캠페인에 해당 없음(행 0건)」도 `true` 로 돌려준다(조회 실패 시 막지 않기 위한 폴백). 그래서 **리뷰어형은 게시물 행이, 시딩형은 영수증·리뷰 인증샷 행이 애초에 0건이라 무조건 참**이 됐다. → 서버가 실제로 내려준 행만 세도록 교체(`gateRows.some(g => g.allowed)`). 변수명도 `anyRejected` → `stillSubmittable` 로 정정(의미가 「반려 여부」가 아니라 「낼 수 있는 항목이 남았는가」).

**★ 그 수정에서 리뷰가 다시 잡은 것** — 위 2번을 고치며 `gateRows` 를 `[]` 로 폴백했더니, **조회 실패(`null`)와 「해당 항목 0건」(`[]`)이 뭉뚱그려져** 서버에 못 물어본 상황(네트워크 실패·DEMO_MODE)에서 폼은 열려 있는데 안내문만 「기한이 지났습니다」로 닫히는 어긋난 조합이 생겼다. 폼 활성(`gateAllowsAny`)과 안내문은 **폴백 방향이 같아야** 한다 — 조회 실패면 둘 다 막지 않는 쪽. → `null` 과 `[]` 를 구분하도록 재수정. **고치는 과정에서 새 어긋남이 생긴다**는 규칙 C의 전제가 코드에서도 그대로 재현됐다.
