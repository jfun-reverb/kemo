# 모집 마감·결과물 제출 마감 서버(데이터베이스) 강제

**작성일:** 2026-07-29
**상태:** 기획 완료 — 구현 대기

---

## 배경

모집 마감일이 지난 뒤에 들어온 응모가 있는지 운영 데이터를 실측한 데서 출발했다. 결과는 **0건**이었으나, 확인 과정에서 「막혀 있어서 0건」이 아니라 **「우연히 0건」**이라는 것이 드러났다. 마감을 강제하는 서버 장치가 응모·결과물 양쪽 모두 없다.

### 운영 데이터 실측

| 항목 | 값 |
|---|---|
| 전체 응모 | 3,358건 |
| 마감일이 설정된 캠페인의 응모 | 3,358건 (전부) |

### 응모(신청) 경로

- 저장 경로는 **단 하나** — `dev/lib/storage.js:759` `insertApplication()` → `applications` 직접 INSERT. 관리자가 인플루언서 대신 응모를 넣는 경로는 코드베이스에 없음(`from('applications').insert` 는 이 1곳뿐).
- 화면 차단은 `dev/js/application.js:273-275` — 캠페인 상태가 `closed`/`ended`면 버튼 비활성. **마감일 자체는 보지 않음.**
- `closed` 전이는 `dev/lib/storage.js:198` `autoCloseCampaigns()` — **브라우저가 캠페인 목록을 부를 때** UPDATE. 아무도 목록을 열지 않으면 마감일이 지나도 `active` 그대로. **서버 기준으로 status 는 신뢰할 수 없는 값.**
- `applications` BEFORE INSERT 트리거 4종(리뷰어형 정원 가드 / 리뷰어형 자동승인 / 감사용 / 연령 정책) — **마감일 검사 없음.**

### 결과물 저장 경로 — 실제로는 데이터베이스 연산 3종

| 경로 | 함수 | 연산 |
|---|---|---|
| 신규 등록 | `storage.js:1071` `insertDraftDeliverable()` | **INSERT** (status='draft') |
| 재등록(교체) | 같은 함수 내부 | **기존 행 UPDATE** — 리뷰 인증샷(`:1080`)·게시물(`:1110`)은 같은 채널 행을 찾아 `draft` 로 되돌림 |
| 최종 제출 | `storage.js:1338` `submitDrafts()` | **UPDATE** `draft`→`pending` + `submit_deliverable` 원격 호출 함수(이벤트 기록만, 검증 없음) |
| 관리자 대리 | `admin_create_deliverable_proxy` | INSERT 또는 게시물 교체 UPDATE (`is_campaign_admin()` 가드) |

→ **새로 넣는 연산(INSERT)만 막으면 뚫린다.** 인플루언서의 재제출·최종 제출은 전부 UPDATE.

현재 행 단위 보안 정책상 인플루언서는 `draft/pending → draft/pending`, `rejected → pending`, `rejected → draft` UPDATE 가 통과한다(재제출 교체 경로가 동작하는 이유). **마감 후 재제출을 막는 서버 장치는 전무.**

### 이 제안과 충돌 가능성 있는 기존 동작

- **충돌 1** — 화면 응모 차단은 상태 기준, 서버는 날짜 기준. 캠페인 연장 시 두 기준이 갈린다. → §설계 5에서 해소.
- **충돌 2** — 리뷰 인증샷 반려 예외 판정 축이 화면 내부에서도 둘(종류/채널). 서버가 어느 쪽을 재현할지 정하지 않으면 「일치」를 정의할 수 없다. → §설계 3에서 채널 단위로 통일.
- **충돌 3** — `submitDrafts` 의 에러 무시 설계는 「실패해도 조용히」를 전제로 짜여 있어 서버 차단 도입과 정면으로 안 맞는다. → 수정 필수(§설계 6).
- 그 외 영역(정산·감사 이력·알림 트리거)과 충돌 없음 — `deliverables` 를 자동으로 UPDATE 하는 서버측 트리거·예약 작업은 없고, 정산 자동 보류는 `settlements` 만 건드린다.

## 설계

### 1. 검사 장치의 위치 — 판정 함수 1개 + 검사 장치 2개

**판정은 데이터베이스 함수 하나, 강제는 검사 장치(트리거) 둘(응모용·결과물용).** 원격 호출 함수 내부 검증은 채택하지 않는다 — 결과물은 인플루언서가 보안 정책 범위 안에서 직접 INSERT·UPDATE 할 수 있으므로, 대리 등록 함수 안에만 검사를 넣으면 본인 경로가 통째로 뚫린다.

**(가) 응모 — `applications` BEFORE INSERT 검사 장치**

1. 조기 통과: `auth.uid() IS NULL`(배치·서비스 키) → `is_admin()`
2. 캠페인 `deadline` 조회 → NULL 이면 통과
3. `(now() AT TIME ZONE 'Asia/Tokyo')::date <= deadline` 이면 통과, 아니면 거부

기존 BEFORE INSERT 검사 장치와 서로 독립(각자 통과/거부만 판정)이라 실행 순서 영향 없음.

**(나) 결과물 — 판정 함수 + `deliverables` BEFORE INSERT OR UPDATE 검사 장치**

판정 함수(이름 예시 `can_submit_deliverable`):

```
can_submit_deliverable(p_application_id uuid, p_kind text, p_post_channel text)
  → jsonb { allowed bool, reason text, submission_end date }
STABLE, SECURITY DEFINER, SET search_path = '', GRANT authenticated
```

판정 순서:

1. 신청 → 캠페인 `submission_end` 조회. NULL 이면 `allowed=true, reason='no_deadline'`
2. `(now() AT TIME ZONE 'Asia/Tokyo')::date <= submission_end` → `allowed=true, reason='within_deadline'`
3. 마감 후 → 반려 예외 판정:
   - `review_image`·`post` = 같은 신청·같은 종류·**같은 `post_channel`** 행 중 `status<>'draft'` 인 것을 `ORDER BY created_at DESC, id DESC` 정렬한 최신 1건이 `rejected` 면 허용
   - `receipt` = 채널 개념이 없으므로 신청·종류 단위로 같은 판정
   - `post_channel IS NULL` 인 옛 행은 판정 대상에서 제외
4. 그 외 거부

검사 장치는 **이 함수만 호출**한다(자체 판정 로직 금지). 발동 범위를 좁히는 순서:

1. `auth.uid() IS NULL` → 통과 (배치·마이그레이션·서비스 키)
2. `is_admin()` → 통과 (검수·되돌리기·대리 등록·게시물 교체 전부 면제. 대리 등록 함수가 SECURITY DEFINER 여도 `auth.uid()` 는 호출한 관리자 그대로라 정상 통과)
3. `NEW.status IN ('draft','pending')` 이 아니면 통과
4. 남은 것 = **인플루언서 본인이 만드는 「제출 방향」 연산뿐** → 판정 함수 호출, 거부 시 예외

이 구조로 관리자 예외가 검사 장치 상단 두 줄에 모이고, 판정 로직 자체는 신원과 무관해진다.

### 2. 시간대

- **`(now() AT TIME ZONE 'Asia/Tokyo')::date <= 마감일`** 로 고정. 즉 **마감일 당일 일본 시각 24시(23:59:59)까지 허용**. 연령 정책의 `calc_age_kst` 와 같은 표현이라 프로젝트 내 일관.
- `deadline`·`submission_end` 는 날짜 타입이라 시각 개념이 없으므로 「당일 끝까지」가 유일하게 자연스러운 해석이고, 화면 현행과 의미도 같다.
- 남는 차이는 기기 시간대뿐. 일본·한국 기기는 완전 일치, 그 외 지역은 최대 하루 어긋난다. **3단계에서 화면이 서버 판정을 소비하면 이 차이는 소멸.**
- 안내 문구에 「마감일 당일 24시(일본 시간)까지」 명시(문의 대응 근거).

### 3. 화면 판정과 서버 판정이 어긋나지 않게 하는 법

**선례:** 사이드바 검수대기 배지가 화면 목록과 숫자가 안 맞아 세 번 고친 사고(마이그레이션 248→249→250). 원인은 「화면 판정을 SQL 로 따로 재현」해서 같은 개념의 구현이 둘이 된 것.

**원칙: 구현을 둘 만들지 않는다. 방향을 뒤집어 데이터베이스를 유일 구현으로 두고 화면이 그 결과를 소비한다.**

**(1) 최종 형태 — 화면이 서버 판정을 소비 (3단계)**

- 배치 조회 함수 추가(예 `get_deliverable_gate(p_application_id)`) → 그 신청에 필요한 항목(영수증 / 게시물 / 캠페인 채널별 리뷰 인증샷)마다 판정 결과를 배열로 반환
- 활동관리 화면 진입 시 결과물 목록을 불러오는 그 시점에 1회 호출 → 폼 비활성·제출 버튼 노출·안내 문구를 **전부 이 결과로** 결정
- `_latestNonDraftIsRejected` 는 차단 판정에서 손을 뗀다
- 호출 실패 시 기존 화면 판정으로 폴백(막지 않음) — 검사 장치가 최종 방어선이므로 안전

**(2) 전환 전 검증 — 양방향 집합 대조 (2단계 배포 전 의무 게이트)**

- 집합 A(서버): 대상 전수(승인 신청 × 필요한 종류, 리뷰 인증샷은 캠페인 채널별로 전개)에 대해 판정 함수 결과를 `(application_id, kind, channel, allowed)` 로 추출
- 집합 B(화면): 개발서버 관리자 화면에서 결과물 전건을 로드한 뒤 **현재 화면 코드 그대로** 돌려 같은 형태로 생성
- 임시 표에 B 를 적재해 `A EXCEPT B`, `B EXCEPT A` 실행 → **양쪽 0행이어야 통과.** 한 건이라도 나오면 원인 규명 전 배포 금지
- 마감 지난 캠페인 데이터가 부족하면 개발서버에서 `submission_end` 를 과거로 조정해 조합(반려·승인·검수중·미제출·채널 혼합)을 만든 뒤 대조

**(3) 정의를 문장으로 고정** (사양서 + 코드 주석 + `CLAUDE.md`)

- 「최신 1건」 = `status<>'draft'` 인 행 중 `created_at` 내림차순, **동률이면 `id` 내림차순**. 화면 정렬에도 같은 규칙을 넣는다(현재는 없어 같은 초 생성 2행에서 순서가 흔들림)
- 「채널 축」 = `review_image`·`post` 는 `post_channel` 일치, NULL 행 제외
- 「반려 예외」 = 최신 1건이 `rejected` 일 때만. 관리자가 반려를 되돌리면 예외도 사라진다
- `CLAUDE.md` 에 「결과물 제출 가부 판정의 단일 소스는 `can_submit_deliverable`. 화면에 같은 판정을 다시 구현하지 말 것」 명시. 리뷰 점검 항목화

### 4. 게시물 반려 예외를 채널 단위로 (화면 변경 동반)

현재 화면은 게시물을 종류 단위로 판정한다. 이를 **채널 단위로 좁힌다**:

- 인스타그램 게시물이 반려됐으면 **인스타그램만** 마감 후 재제출 가능
- 같은 캠페인의 틱톡 게시물을 새로 내는 것은 차단
- 게시물은 이미 채널별 1건 정책(2026-06-02)이라 개념상 정합하고, 리뷰 인증샷과 기준이 같아진다

### 5. 캠페인 연장 시 상태 자동 전환 (사용자 제안)

서버는 날짜만 보므로 마감일을 미래로 고치면 즉시 응모가 열린다. 그런데 캠페인 상태는 `closed`(모집마감) 그대로라 인플루언서 화면에서는 버튼이 닫혀 있다. 이 어긋남을 **캠페인 편집 화면에서** 해소한다.

- 편집 저장 시 「모집 마감일이 과거 → 미래」로 바뀌었고 현재 상태가 `closed` 면 확인 모달:
  > 모집 마감일을 미래로 바꾸셨습니다. 저장하면 캠페인 상태도 「모집중」으로 함께 바뀝니다. 진행할까요?
- 「예, 저장」 → 마감일 + `status='active'` **함께 저장**
- 「취소」 → **아무것도 저장하지 않고** 편집 화면에 머무름(입력한 마감일은 화면에 남겨 두어 되돌리거나 다시 고칠 수 있게)
- ⚠️ **「마감일만 저장」 선택지는 두지 않는다.** 마감일은 미래인데 상태는 모집마감인 상태가 남으면, 서버는 응모를 받고 화면은 버튼을 닫는 어긋남이 그대로 생긴다 — 이 설계가 없애려는 바로 그 상태다. 저장하려면 둘이 함께 움직인다.
- **적용 대상은 `closed` → `active` 한 방향만.** `ended`(종료)·`expired`(노출종료)·`draft`(준비중)는 제외 — 종료는 결과물 제출 마감까지 지난 상태이고, 노출종료는 노출 토글 전용이라 마감일 하나로 되돌리면 다른 규칙과 충돌한다
- 반대 방향(마감일을 과거로 당김)은 기존 자동 마감이 처리하므로 추가 작업 없음

### 6. 인플루언서에게 보이는 문구

검사 장치는 머신 판독용 코드를 메시지 앞에 붙여 예외를 발생시킨다(`post_already_approved` 선례와 동일 구조):

- `recruit_deadline_passed: 모집 기간이 종료되었습니다`
- `submission_deadline_passed: 제출 기한이 지났습니다`

`friendlyErrorJa()` 에 정규식 2줄 + `_ERR_DICT` ja/ko 에 각 2키 추가 → **로케일 분기 경로를 그대로 탄다**(추가 작업 없음).

- 일본어: 「募集期間が終了したため、応募できません」 / 「提出期限が過ぎているため、提出できません。差し戻された項目のみ再提出できます」
- 한국어: 「모집 기간이 종료되어 신청할 수 없습니다」 / 「제출 기한이 지나 제출할 수 없습니다. 반려된 항목만 다시 제출할 수 있습니다」

**★ 수반 수정 2건 (선택 아님)**

1. `storage.js:1338` `submitDrafts()` 의 에러 삼킴 제거 → 예외를 호출부(`application.js:1525` `submitAllDrafts`)로 전파하고 안내 문구 표시. 지금 상태로 배포하면 사용자는 「제출할 것이 없습니다」라는 틀린 안내를 본다
2. 마감 후에도 노출되는 리뷰 인증샷 통합 제출 버튼 게이팅 — 3단계에서 서버 판정으로 처리

### 7. 경계 상황

| 상황 | 처리 |
|---|---|
| 마감일이 NULL | **통과(무기한)**. 실측상 응모는 전부 마감일 있는 캠페인이라 영향 0. 향후 마감일 없는 캠페인이 생기면 서버 차단이 없다는 점 명시 |
| 취소 후 재응모 | 같은 검사 장치를 탄다 → 마감 전이면 허용, 마감 후면 차단. 취소 이력·부분 유니크 인덱스와 충돌 없음 |
| 마감 후 남은 임시저장 | 시행 즉시 제출 불가로 굳는다. **배포 전 건수 실측 필수**. 구제는 관리자 대리 등록 |
| 감사용 계정 | 실제 사용자와 동일하게 차단 (결정 7) |
| campaign_manager | 검사 장치는 면제되나 대리 등록 함수는 상위 권한 가드라 실제 등록 불가. 「검사 장치 예외 = 대리 등록 가능」이 아님을 문서에 명시 |
| 보관 삭제된 캠페인 | 신청·결과물은 삭제 시 즉시 파기되므로 무관 |
| 마감 자정 경계 동시 요청 | 트랜잭션의 `now()` 로 단일 판정 → 경합 없음 |
| 배치·마이그레이션 UPDATE | `auth.uid() IS NULL` 통과 조항으로 보호 |

| 순서 | 내용 | 마이그레이션 | 의존 |
|---|---|---|---|
| **1단계 — 응모 마감 서버 차단** | 검사 장치 함수 + `applications` BEFORE INSERT 검사 장치 / 안내 문구 1종 / 캠페인 연장 시 상태 자동 전환 확인 모달 | 1개 | 없음 |
| **2단계 — 결과물 제출 마감 서버 차단** | 판정 함수 `can_submit_deliverable` + 검사 장치 함수 + `deliverables` BEFORE INSERT OR UPDATE 검사 장치 / `submitDrafts` 에러 전파 + 안내 문구 1종 / 게시물 예외를 채널 단위로 변경 | 1개 | 1단계 배포·검증 후 |
| **3단계 — 화면 판정 서버 일원화** | 배치 조회 함수 + 실행 권한 부여 / `application.js` 폼 게이팅·제출 버튼 노출을 서버 결과로 교체 / 죽은 함수 `insertPostDeliverable`(호출부 0건) 정리 | 1개 | 2단계 배포 후 |

## 검증 계획

### 배포 전 실측 (운영·개발 각각, 결과를 이 문서에 기록)

1. 제출 마감이 지난 캠페인에 남아 있는 임시저장 결과물 건수 + 해당 인플루언서 수 → 시행 즉시 굳는 대상 규모
2. 지금까지 마감 후에 제출된 결과물 건수와 그중 반려 예외로 설명되는 비율 → 이번 차단이 실제로 막게 될 규모
3. 마감일이 NULL 인 캠페인 수 → 서버 차단이 적용되지 않는 사각지대 크기
4. 응모 쪽은 실측 완료(마감 후 응모 0건) — 백필 불필요

### 정합 대조 (2단계 배포 전 게이트)

§설계 3의 `A EXCEPT B` / `B EXCEPT A` **양방향 0행**. 데이터가 부족하면 개발서버에서 마감일을 과거로 조정해 아래 조합을 만든 뒤 대조: 마감 전/후 × 미제출·검수중·승인·반려 × 채널 일부만 반려 / 채널 미지정 옛 행 포함.

### 개발서버 시나리오

| # | 시나리오 | 기대 |
|---|---|---|
| 1 | 마감 전 응모 | 성공 |
| 2 | 마감일 당일 일본 시각 23:50 응모 | 성공 |
| 3 | 마감 다음 날 응모(화면 우회) | 서버 거부 + 일본어 문구 |
| 4 | 마감 후 취소 이력 있는 캠페인 재응모 | 서버 거부 |
| 5 | 마감일 없는 캠페인 응모 | 성공 |
| 6 | 마감 후 신규 임시저장 등록 | 서버 거부 + 문구 |
| 7 | 마감 후 임시저장 → 제출 | 서버 거부 + **정확한 문구**(「제출할 것이 없습니다」 아님) |
| 8 | 마감 후, 영수증이 반려된 상태에서 영수증 재제출 | **성공**(예외 유지) |
| 9 | 마감 후, 리뷰 인증샷 A채널만 반려 → A 재제출 성공 / B채널 신규 제출 거부 | 채널별 분리 확인 |
| 10 | 마감 후, 인스타그램 게시물만 반려 → 인스타그램 재제출 성공 / 틱톡 신규 거부 | 게시물 채널 단위 확인 |
| 11 | 마감 후 관리자 대리 등록·검수 승인·되돌리기 | 전부 성공(예외 확인) |
| 12 | 모집 마감일을 미래로 연장 → 상태 자동 전환 확인 모달 | 「예, 저장」 시 마감일+모집중 함께 반영 / 「취소」 시 **마감일도 저장 안 됨** |
| 13 | 관리자 화면 검수·정산·감사 이력 저장 | 회귀 없음 |

### 배포 후

관리자 오류 로그 화면(`/admin#errors`)에서 새 코드 2종의 발생 추이를 1주 관찰. 예상보다 많으면 화면 게이팅 누락 지점이 있다는 신호.
