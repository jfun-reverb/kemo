# 브랜드 페이지 — 시딩형 배송 리스트 · 형식별 캠페인 상세

**작성일:** 2026-10-19 (기획 세션)
**상태:** 기획 — 개발 착수 전 (브랜드 페이지 1차 범위)
**피그마:** 「레버브시딩_브랜드」 Brand 페이지 — 구역 「[1차] 05-1 캠페인 목록·상세」 · 「[1차] 05-2 배송 리스트 — 시딩형」 · 「[1차] a05-5 관리자 — 배송 리스트」(구역 이름 뒤 「(A → B → C)」 흐름 표기는 줄임)

> 한 줄 요약: 지금 구글 시트 링크로 브랜드에 주는 **시딩형 배송 리스트**를 브랜드 페이지 1차로 옮긴다. 운영팀이 「배송 리스트 전달」을 누르면 그 브랜드 계정에 **선정된 분의 이름·우편번호·주소·전화번호**가 열리고, 브랜드가 **송장번호를 한 줄씩 또는 엑셀로** 등록한다. 운영팀은 관리자 진행현황의 새 탭에서 같은 표를 보고 고친다. 인플루언서에게는 이번에 보이지 않는다.
> 함께 한 일: 피그마 캠페인 상세를 **리뷰어형·시딩형·방문형** 셋으로 나눠 그렸다(개발서버에 이미 있는 형식별 진행 단계와 맞춤).

## 1. 현재 상태 (2026-10-19, 직접 확인)

### 관련 코드·DB·화면
- **송장·배송 상태를 담는 칸이 어디에도 없다** — `tracking_number`·`shipping_status`·`shipped_at` 를 `dev/js`·`dev/lib`·`supabase/migrations` 에서 글자 검색해 0건(이름이 다른 칸이 있을 가능성은 「배송」·「송장」 한글 검색으로 보충 — 오리엔시트 안내 문구 2줄만 걸림). 완전히 새 기능이다
- 송장이 나오는 곳은 **오리엔시트 작성 폼의 안내 문구뿐** — `dev/js/brand-orient-form.js` 66줄(리뷰어형: 구매 뒤 3일 안 배송·송장 등록 — 큐텐 주문 쪽 이야기) · 72줄(시딩형: 「배송 리스트 전달 후 3일 이내 배송 및 송장번호 전달」)
- 배송지 원천: 응모할 때 확인한 주소가 `applications.address`(응모 줄에 저장), 회원 마이페이지 주소는 `influencers` 표. 둘이 다를 수 있다
- 브랜드 캠페인 탭(개발서버, 2026-10-19 병합): 함수 `get_my_brand_campaigns`·`get_my_brand_campaign`(마이그레이션 543, 「로그인 브랜드 + 자기 캠페인」 판정). 화면 `dev/js/brand-campaigns.js` 가 형식별 진행 단계를 이미 그린다 — 리뷰어형 모집·구매·결과물 게시·종료(선정 없음 — 응모가 곧 참여) / 시딩형 모집·선정·**배송**·결과물 게시·종료 / 방문형 모집·선정·방문·결과물 게시·종료(선착순 행사는 선정 없음)
- 결과물 표의 이름 가림(佐藤**)은 리포트 공유와 같은 규칙 — 배송 리스트와는 목적이 다르다

### 지금 운영 방식 (약관 사양서 「현재 상태」 4번)
- 관리자 화면에서 신청 데이터를 내려받아 **캠페인별 구글 시트**로 만들고 링크를 브랜드에 보낸다. 시트에는 **선정되지 않은 신청자까지** 이름·이메일·전화·주소·SNS·신청 동기가 있고, 공유가 「링크가 있는 모든 사용자 — 편집자」였다
- 결정(2026-10-19): 출시 전에 시트를 모두 지우는 것이 **브랜드 페이지 출시 관문**이고, 배송 리스트는 「추후 브랜드 페이지에서」 관리한다 → 이 사양서가 그 「추후」를 1차로 당긴다

### 약관·방침 초안과의 관계 (2026-10-19 확인)
- 브랜드 약관 제8조 1항이 이미 「배송지·전화번호를 **제품 배송 포함** 캠페인 진행 목적으로만」을 적고 있고, 3항이 내려받은 파일의 파기를 정한다 → 배송 리스트·엑셀 내려받기는 그 안에 든다
- 회원 방침 §3.1 표(브랜드 제공 항목)에 이름·배송지·전화번호가 「제품 배송」 목적으로 이미 있다
- 🔴 **어긋나는 곳 둘** — ①방침 개정안 B-2(제공 방법)가 「이름은 일부를 가린 형태로 표시」라고만 적어 배송 리스트(이름 전체)와 맞지 않는다 ②브랜드 약관 제7조(제공 기능)에 배송 리스트가 없다 → 이 사양서와 같은 병합 요청에서 둘 다 고쳤다(§5)

### 충돌 가능성 있는 기존 동작
- 본인 응모 취소·관리자 반려·대기로 되돌림이 전달 뒤에 일어난다 — 이미 발송한 뒤일 수 있다(§2 경우 1)
- 감사용(내부 점검) 계정 — 다른 집계처럼 빼야 한다
- 브랜드 계정이 없는 브랜드 — 전달할 상대가 없다

## 2. 의심·경우의 수 (반대론자 모드)

1. **(데이터) 전달 뒤 선정 취소** — 본인 응모 취소 · 관리자 반려 · 대기로 되돌림. 브랜드가 이미 보냈을 수 있다. 줄을 지우면 「어디 갔지?」가 되고, 그대로 두면 보내지 말아야 할 사람에게 보낸다 → 「취소됨」으로 **남기되 주소·전화번호는 서버가 비운다**(기본값 — 확인 필요 3)
2. **(동시성) 같은 줄을 둘이 고침** — 브랜드 멤버 둘, 또는 브랜드와 운영팀. 나중 저장이 앞 저장을 조용히 덮으면 송장이 사라진다 → 줄마다 버전 확인, 충돌이면 토스트로 다시 불러온다
3. **(UX) 엑셀 줄 맞추기** — 브랜드가 엑셀에서 정렬·필터·행 삭제를 하면 이름으로 맞추다 틀린다 → **줄 번호 열**(배송 줄 고유 번호)로만 맞추고, 반영 전 미리 보기(bw05-03a)를 거친다
4. **(UX) 진입 경로** — 브랜드는 「캠페인 → 상세 → 배송 카드 → 배송 리스트 열기」 한 길뿐이다. 전달 사실을 모르면 들어오지 않는다 → 전달 알림 메일을 보낼지 확인 필요 1
5. **(데이터) 주소 기준** — 응모 때 주소(`applications.address`)와 지금 마이페이지 주소가 다를 수 있다. 회원이 응모 뒤 이사하면 어느 쪽으로 보내나 → 확인 필요 2
6. **(법률) 이름 전체 공개** — 결과물 표는 이름을 가리지만 배송에는 전체가 필요하다. 방침 문장이 「가린 형태」로만 적혀 있으면 사실과 다르다 → §5 에서 고침
7. **(법률) 브랜드 제공 기록** — 일본 법 제29조의 제공 기록(3년)이 지금 시트 방식에는 전혀 없다 → 전달·열람·내려받기 기록을 서버가 남긴다(이 기능이 그 빈칸을 채운다)
8. **(외부 시스템) 올린 엑셀** — 주소가 다시 들어 있는 파일이 회사 서버·오류 로그에 쌓이면 새 보관이 생긴다 → 파일은 화면에서만 읽고 저장하지 않는다
9. **(권한) 여러 브랜드 계정** — 브랜드 전환으로 다른 브랜드를 보고 있을 때 주소를 바꿔 넣어 남의 리스트가 보이면 안 된다 → 서버가 매번 판정(목록 단위·줄 단위 두 단계 — §4-2)

### 현재 구현과 어긋나는 지점
- 송장 칸이 없어 **충돌 없음 — 새로 만든다**(검색 범위는 §1). 어긋나는 것은 약관·방침 초안 두 문장뿐(§1)

### 의도와 다르게 읽힐 수 있는 것
- 「배송 리스트」 = **선정된 분만**(지금 시트처럼 신청자 전원이 아니다)
- 「발송함」 = 브랜드가 송장을 넣은 상태. 실제로 도착했는지는 모른다(택배 조회 연동 없음)
- 리뷰어형은 회원이 큐텐에서 직접 사서 큐텐 주문으로 배송되므로 **이 기능 대상이 아니다**. 방문형은 배송이 없다

## 4. 설계

### 4-1. 형식별 캠페인 상세 (피그마 05-1)
- `bw05-01` 리뷰어형 · `bw05-01b` 시딩형(배송 리스트 전달 뒤) · `bw05-01c` 방문형 · `bw05-01a` 리뷰어형 종료 결과물 — 진행 단계·일정 줄은 개발서버 코드(위 §1)와 같다. 피그마가 코드보다 뒤처져 있던 것을 고쳤다 — 리뷰어형에서 「선정」 단계 · 「선정 발표」 줄을 빼고 「선정 / 정원」을 「참여 / 정원」으로 바꿨다
- 시딩형 상세에만 **「배송」 카드**: 전달 전 「준비 중」(bw05-91 ①), 전달 뒤 전달 시각 · 받는 사람 · 발송함 · 발송 전 · 취소됨 · 「배송 리스트 열기」

### 4-2. 브랜드 배송 리스트 (bw05-02)
- **열 수 있는가**(목록 단위) = 로그인 브랜드 + 자기 캠페인 + 시딩형 + 운영팀이 전달함
- **어떤 줄이 들어가나**(줄 단위) = 지금 선정(승인)된 분 + **전달 뒤 선정이 취소된 분**(본인 응모 취소 · 관리자 반려 · 대기로 되돌림 — 셋 다 「취소됨」 한 가지로 보인다). 전달 전에 빠진 분은 넣지 않는다. 감사용 계정 제외
- 칸 = 이름(한자·가나) · 우편번호 · 주소 · 전화번호 · 택배사 · 송장번호 · 발송일 · 상태(발송 전 / 발송함 / 취소됨). **이메일·SNS 계정·신청 사유는 없다**
- 이름은 가리지 않는다. 「취소됨」 줄은 이름만 남기고 주소·전화번호를 서버가 비운다(보내지 말아야 할 분을 알아보게)(기본값 — §6 확인 3. 다르게 정하면 방침 개정안 B-2 단서도 함께 고친다)
- 「입력」·「수정」 → 그 줄만 입력칸 → 「저장」. 송장을 저장하면 「발송함」, 발송일을 비우면 저장한 날
- 「엑셀 내려받기」 = 화면 칸 + 줄 번호. 안내 줄에 이용약관의 파기 의무
- 저장은 줄마다 버전 확인. 저장 사이 응모가 취소되면 거부

### 4-3. 엑셀 올리기 (bw05-03 · 03a)
- 파일은 화면에서만 읽고 **줄 번호·택배사·송장번호·발송일**만 서버로 보낸다. 파일·내용을 저장·기록하지 않는다
- 줄 번호로만 맞춘다. 다른 캠페인 파일이면 거부
- 반영 전 미리 보기: 새로 등록 · 바뀜(이전 번호) · 그대로 · 반영 안 됨(취소된 분 · 송장 빈칸 · 없는 줄 · 형식 오류). 반영 안 됨은 건너뛴다
- 반영은 한꺼번에(일부만 저장되고 멈추지 않게). 미리 보기 뒤 다른 사람이 고친 줄은 반영할 때 다시 검사

### 4-4. 관리자 (피그마 a05-5)
- 캠페인 진행현황에 **「배송 리스트」 탭**(시딩형만, 신청자 목록과 결과물 목록 사이)
- 「배송 리스트 전달」 → 확인 모달(a05-10: 계정 수 · 사람 수 · 자동 추가 · 기록이 남음) → 전달. 브랜드 계정(비밀번호를 정한 연결 계정)이 0명이면 거부
- 운영팀도 송장을 넣고 고칠 수 있다(전달 전에도). 줄마다 「입력한 사람」(브랜드 · 운영팀)
- 관리자 표에는 SNS 계정을 함께 보인다. 취소 줄은 이유와 함께 그대로 보인다
- 새 권한 항목(배송 리스트 보기·전달)을 관리자 권한 표에 등록

### 4-5. 제공 기록
- 서버가 남긴다 — 전달(누가·언제·몇 명) · 브랜드 열람(누가·언제) · 엑셀 내려받기(누가·언제). 화면이 따로 보내는 기록에 기대지 않는다
- 관리자 a05-09a 초록 줄에 요약, 「전달·열람 기록」 모달(아직 그리지 않음)
- 보관 기간은 약관 사양서 「기간 【미정】」과 함께 정한다(일본 법 제공 기록 3년)

### 4-6. 데이터베이스 (번호는 개발 세션이 정한다)
- 새 표 1개(배송 줄 — 응모 1건당 1줄: 택배사 · 송장번호 · 발송일 · 입력한 사람 · 버전) + 캠페인별 전달 기록 + 열람·내려받기 기록 — 표를 몇 개로 나눌지는 개발 판단
- 함수: 브랜드 조회 · 브랜드 저장(한 줄·여러 줄) · 관리자 전달 · 관리자 저장. 브랜드 함수의 판정은 §4-2 의 두 단계 — 목록 단위(543 과 같은 「로그인 브랜드 + 자기 캠페인」 + 시딩형 + 전달됨)와 줄 단위(지금 선정 또는 전달 뒤 취소). **저장은 지금 선정인 줄만** 받는다
- 순서: ①표 → ②함수 → ③관리자 화면 → ④브랜드 화면

## 6. 사용자 확인 필요
1. 전달했을 때 **브랜드에 알림 메일**을 보낼지(보내기로 하면 메일 양식을 bw05-01b 옆에 그린다 — 번호 bw05-95)
2. **배송지 기준** — 응모 때 확인한 주소 vs 지금 마이페이지 주소
3. 전달 뒤 선정이 취소된 분(본인 취소·반려·대기로 되돌림)을 **「취소됨」으로 남기고 주소를 가리는** 기본값이 맞는지(그림·방침 단서는 이 기본값 — 바꾸면 둘 다 고친다)
4. 택배사 목록(우체국 EMS · K-Packet · CJ대한통운 국제 · 사가와 · 야마토 · 기타 등)
5. 운영팀이 **전달을 되돌릴**(브랜드 화면에서 다시 닫을) 수 있게 할지
6. 캠페인 매니저 등급도 「배송 리스트 전달」을 누를 수 있게 할지
7. 한 분에게 보낼 **옵션(색상·종류)·수량**이 다를 때 리스트에 칸이 필요한지(지금 시트에 그런 칸이 있었는지)
8. 모바일 배송 리스트(bm05-02)를 둘지
9. 발송 기한 문구(「받은 날부터 3일」 — 오리엔시트 안내를 옮김)가 계약 조건과 같은지
